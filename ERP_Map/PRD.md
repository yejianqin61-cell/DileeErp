# ERP_Map 产品需求文档

> 类型：产品 PRD  ·  版本：0.1 草案  ·  日期：2026-10-28  ·  状态：路线建议

## 结论：ERP_Map 要交付什么？

ERP_Map 是一套可复用的 ERP 业务地图工具。它展示业务管线、各 stage 的操作人、跨管线交接，以及作为字段集合的单据如何流转。首个参照项目是 Dilee ERP。
首版先盘点该 ERP 的全部管线，并把一条跨模块链路建模到字段级，交付可离线交互的 HTML 地图。后续扩大深度，再验证第二个 ERP 产品的接入。
主要成本是持续核对业务规则与代码，主要风险是地图过期。因此每条关键关系都要标明依据和核验状态。

## 1. 解决谁的什么问题？

| 使用者 | 当前问题 | ERP_Map 提供的结果 |
| --- | --- | --- |
| 产品负责人 | 难以看清完整业务链和产品边界 | 管线总览、分叉汇合、覆盖状态 |
| 业务分析与实施人员 | 不清楚谁在何处操作、字段如何推动下一环节 | stage、操作人、触发条件与字段流向 |
| 开发与测试人员 | 跨模块规则散落在代码和文档中 | 可定位来源的交接契约与验收路径 |

本项目已有[业务管线总览](../docs/business-pipeline-overview.html)、
[跨模块数据管线规格](../docs/design/cross-module-data-pipeline-improvement-spec-2026-09-03.md)、
[能力目录](../docs/product/module-capability-catalog.md)、表单定义和状态机能力。
这些材料是首批输入；ERP_Map 不把其中任何一份材料直接视为已经验收的运行事实。

## 2. 地图里的对象怎么定义？

| 对象 | 定义 | 必须记录的内容 |
| --- | --- | --- |
| 管线 | 围绕一个业务结果持续推进的流程 | 名称、起点、终点、上下游 |
| stage | 管线中可辨认的业务环节 | 操作人/角色、输入、动作、完成条件、异常路径 |
| 单据 | 一组有名称和用途的字段 | 字段清单、类型、必填性、业务键、版本 |
| 交接 | 一个 stage 向另一个 stage 交付单据字段或推进结果 | 触发方式、来源与目标、门禁、失败/回退 |
| 字段映射 | 交接时字段的去向与处理 | 来源字段、目标字段、转换、快照或引用、必填性 |
| 依据 | 支撑上述定义的材料 | 代码或文档位置、核验人、核验日期、状态 |

管线可以分叉、汇合和循环。一条管线可以有多个操作人；操作人只定义在 stage，必要时列出多个角色及各自动作。stage 是业务环节，不等同于数据库中的 `status` 值。单据是字段集合，不另建与字段平行的业务对象；创建、填写、确认和流转发生在 stage 与交接中。交接箭头表示字段或推进结果如何流转，不表示页面跳转。订单号等业务编号用于人阅读；内部外键仍按各 ERP 的实际模型记录。

## 3. 用户怎样使用它？

1. 在总览中找到一条业务管线，并看到它与其他管线的输入、输出关系。
2. 进入管线，查看每个 stage 的操作人、单据字段、推进条件、阻塞条件和异常路径。
3. 点开交接，查看单据字段映射、快照规则、触发位置及依据。
4. 按单据、字段或业务编号搜索，反查它在哪些交接中被创建或消费。
5. 查看“已核验 / 待核验 / 与实现不符”，区分设计意图与当前实现。

示例链路取自 Dilee ERP：销售单/BOM → 采购单 → 到货批次 → 来料质检 → 原料入库；到货或入库还会向应付分叉。具体应付来源时点必须以当前代码核验后写入地图，不能仅凭旧文档定案。

## 4. 当前版本的能力边界是什么？

**ERP_Map 0.1：本地、只读、以 Dilee ERP 为样本的可审查版本。**

| 能力 | 0.1 边界 | 验收方式 |
| --- | --- | --- |
| 管线覆盖 | 盘点 Dilee ERP 全部实际业务管线；每条至少有起终点、stage、操作人和上下游 | 可从总览逐条进入；每个 stage 有操作人或明确标为系统自动 |
| 字段深度 | 一条跨模块主链路及其关键分叉达到交接和字段级 | 能从销售来源追到入库与应付来源，逐跳说明字段去向 |
| 呈现 | 单个 HTML 地图支持总览 → 管线 → stage/交接的逐层浏览、搜索和聚焦 | 可在本地浏览器离线打开；点击节点和关系可查看详情 |
| 依据与状态 | 每个关键交接有来源位置与核验状态 | 点击关系能看到依据；未核验内容明确标出 |
| 模板复用 | 地图内容与 HTML 模板分开；模板统一样式和交互 | 同一输入和模板版本重复生成，HTML 文件内容一致 |
| 跨产品复用 | 地图内容不写死 Dilee ERP 术语 | 换一份符合约定的数据即可展示另一 ERP，不改模板 |

“全部管线”在 0.1 指广度盘点，不表示全部字段已录完。验收时先核对现有总览中的条目；报表、告警、订单工作台等聚合视图是否构成独立管线，要按其是否推进业务事实判断，不能直接照搬现有分类。

## 5. 工具形态与交付形态是什么？

- **查看形态**：地图交付为单个可离线打开的 HTML 文件。文件包含必要的样式、交互和地图内容；默认只读，不要求连接 ERP 数据库或登录生产环境。
- **制作形态**：0.1 优先采用 Skill，组织资料核对、地图编写、校验和 HTML 生成。若后续需要稳定的外部系统读取或服务化调用，再评估 MCP；二者生成同一种地图文件。
- **模板约定**：地图内容与 HTML 模板分开维护。模板统一导航、展开/收起、搜索、聚焦、详情面板和视觉风格。相同输入与模板版本重复生成，HTML 文件内容必须一致，不增加重复节点。
- **首版交付**：ERP_Map Skill、HTML 模板、Dilee ERP 样例地图、数据格式说明与校验命令。发布包不含真实业务数据或凭据。
- **产品关系**：ERP_Map 独立于 Dilee ERP 运行。Dilee ERP 是第一个样例和验收对象，不是工具代码的硬编码前提。
- **开源方向**：工具与通用格式作为开源候选；发布前确认许可证、第三方依赖和样例内容的公开边界。

## 6. 路线图和里程碑怎么走？

里程碑按可验证结果排序，不预设日历日期。每一阶段验收后再给下一阶段排期。

| 里程碑 | 产品结果 | 可见的完成证据 | 本阶段不做 |
| --- | --- | --- | --- |
| M0 定义基线 | PRD、术语、stage 操作人和一条样例交接获得统一口径 | 产品、业务、开发能对同一交接说清谁操作、来源、触发、字段和下游 | 工具开发 |
| M1 全局可见（0.1） | Dilee ERP 全部管线总览；一条链路达到字段级；HTML 地图与制作 Skill 可用 | 按第 4 节逐项演示；相同输入重复生成的文件一致 | 全站字段覆盖、实时运行监控 |
| M2 全链可追（0.2） | Dilee ERP 关键交接均有字段映射、异常路径和依据 | 从任一关键单据反查来源与去向；抽样对照代码通过 | 让地图驱动业务执行 |
| M3 跨产品可用（1.0） | 第二个 ERP 产品接入；通用格式稳定；具备发布资料 | 第二个产品不修改模板即可生成 HTML 地图；示例与发布包可公开 | 通用低代码流程引擎 |

M0 若发现“管线、stage、交接”无法准确表达一个真实场景，先修正模型，再进入 M1。每个里程碑保留上一个可用版本；地图数据可回退到前一已核验版本。

## 7. 什么明确不在当前范围？

- 不替换现有 ERP 的状态机、表单系统或业务服务。
- 不在 0.1 自动从代码推断全部业务规则；人工核验仍是发布条件。
- 不在 0.1 为每条管线设置一个统一操作人；操作人归属 stage。
- 不在 0.1 修改业务数据、审批单据或推进流程。
- 不在 0.1 接生产数据做实时流程监控或客户订单追踪。
- 不以图的节点数量代替业务正确性；缺依据的关系要标记为待核验。

## 8. 现在有哪些假设与待定项？

| 类型 | 内容 | 解决方式 |
| --- | --- | --- |
| 假设 | 首版用户最需要的是业务结构与规则查询，而非实时实例监控 | 在 M1 用产品、实施、开发各一次真实查询任务验证 |
| 假设 | Dilee ERP 足以检验首版信息模型，但不足以证明跨产品复用 | M3 以第二个 ERP 接入作为复用验收 |
| 待定 | 开源许可证及 Dilee 样例可公开到什么粒度 | M3 发布前完成仓库和样例审查 |
| 待定 | 地图内容由谁维护、多久核验一次 | M1 试用后根据变更频率确定负责人和流程 |
| 待定 | 0.1 的字段级样例是否采用采购主链及应付分叉 | M0 对照当前代码与业务负责人确认 |
