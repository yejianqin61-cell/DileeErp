# 0821-01 初链路打通计划

## 状态

待执行

## 问题陈述

迪礼 ERP 已完成平台和业务建模的基础设计，但当前认证、健康检查、客户、销售单、BOM 与前端页面尚未形成一个可在厂内浏览器中真实操作的闭环。现有前端以演示数据和模块占位为主，后端尚无业务领域表，因此无法验证订单号主线、审计、状态机和模块间来源关系是否真正可用。

本计划优先交付最小真实业务链路：操作员完成登录后，维护客户，创建销售单并手工输入唯一 `order_no`，确认销售单，物控基于销售单版本创建 BOM。该链路是后续采购、生产、仓库和财务接入的共同上游。

## 解决方案

以一个端到端纵向切片取代分散的模块占位：

```text
健康检查 -> 登录/会话 -> 客户 -> 销售单/订单号 -> 销售确认 -> BOM
    \_________________________________________________________/
                  浏览器端到端验收缝隙
```

先完成认证与健康检查的真实数据库、API 和浏览器验证；再建设销售域最小数据库 schema 与 REST API；最后将前端从演示/占位数据切换为该 API。每一阶段都复用统一的 API 信封、错误处理、附件、审计、软删除和状态机，不重新定义平行基础设施。

## 用户故事

1. 作为操作员，我想登录 ERP 并保持会话，以便只能以自己的身份录入和修改业务数据。
2. 作为操作员，我想在登录失效时收到明确提示，以便重新登录而不是误以为业务数据丢失。
3. 作为系统维护人员，我想通过健康检查确认 API 和数据库均可用，以便在厂内部署后快速定位故障。
4. 作为销售人员，我想创建、编辑、查询和停用客户，以便销售单始终引用可追溯的客户资料。
5. 作为销售人员，我想维护一个客户的多个联系人，以便销售单可以保留当次业务联系人的快照。
6. 作为销售人员，我想创建销售单草稿，以便在信息未齐全时保存工作进度。
7. 作为销售人员，我想手工输入唯一的订单号，以便它作为所有下游单据的一致身份证。
8. 作为销售人员，我想在订单号重复时立刻看到明确错误，以便修正录入而不产生重复订单。
9. 作为销售人员，我想填写销售单的固定核心信息和可扩展字段值，以便满足当前客户产品要求而不锁死未来字段。
10. 作为销售人员，我想查看销售单当前版本、状态和审计信息，以便知道数据由谁、何时修改。
11. 作为销售人员，我想确认满足必填条件的销售单，以便将订单交接给物控建立 BOM。
12. 作为销售人员，我想在确认后看到编辑影响预览，以便知道修改会要求哪些下游人员复核。
13. 作为物控人员，我想只从已确认销售单创建 BOM，以便 BOM 来源明确且不会引用未定稿订单。
14. 作为物控人员，我想让 BOM 记录销售单来源版本，以便后续销售变更可以形成差异提示而不篡改原 BOM。
15. 作为物控人员，我想先维护 BOM 固定核心关系并预留可扩展明细，以便后续补充物料和工艺字段时不推翻已上线链路。
16. 作为管理员，我想以模块权限限制客户、销售和 BOM 操作，以便每位操作员只访问获授权的功能。
17. 作为审计人员，我想追踪创建、编辑、确认和逻辑删除操作，以便发生录入错误时能够还原业务事实。
18. 作为前端使用者，我想在所有已展示模块中看到真实空状态或可用页面，而不是演示数据和“待确认/占位”文案，以便系统可以用于负责人验收。

## 实施决策

### 1. 首先完成认证与健康检查全链路

- 采用数据库受控会话认证，不采用 JWT。系统是厂内 Web 应用，不需要跨端令牌分发；服务端仅保存会话令牌哈希，因此可以立即退出、撤销、停用用户和使全部会话失效；
- 不开放自助注册。用户账号只能由管理员在管理功能中创建、停用、重置密码和分配角色，避免未经许可的厂内账号进入系统；
- 保留现有 Cookie 会话认证、`/api/v1/auth/login`、`/api/v1/auth/me`、`/api/v1/auth/logout` 与 `/api/v1/health` 路由；
- 密码使用 Argon2id 哈希存储，绝不记录、返回或可逆加密密码。创建/重置密码执行长度和弱口令策略；登录失败统一提示，不泄露账号是否存在；
- 会话令牌使用密码学安全随机值，仅以哈希落库；Cookie 使用 `httpOnly`、`sameSite=lax`，生产环境必须启用 `secure`。登录后轮换会话，退出、停用用户、密码重置和管理员强制下线均使对应会话失效；
- 为登录接口设置按账号与来源地址的限流/短时锁定，记录安全审计事件；不实现验证码、短信、外部 SSO 或手机端认证；
- 启动本地 PostgreSQL，执行 Prisma 生成与迁移，创建最小初始管理员数据；
- 健康检查应返回应用状态和数据库连通状态。数据库不可用时返回可诊断的失败响应，不得伪造“健康”；
- 浏览器端提供登录页、当前用户恢复和退出入口；前端 API 客户端统一携带 Cookie 并处理 `401`。

### 1.1 权限模型

- 采用 RBAC（基于角色的访问控制）。用户可以拥有多个角色，角色拥有模块权限；管理员角色拥有全部模块与账号/权限管理权限；
- V1 模块权限键统一为 `sales`、`procurement`、`production`、`warehouse`、`finance`、`hr`。客户池、销售单和 BOM 归属 `sales` 模块，物控人员通过 `sales` 权限使用 BOM；
- 权限检查在 API 守卫中强制执行，前端导航/按钮仅用于体验提示，不能作为安全边界；未登录返回 `401`，无权访问返回 `403`；
- V1 不实施字段级、行级、临时授权和审批权限。审批人/批准人字段仅作为后续扩展预留；
- 权限授予、撤销、账号启停、密码重置和会话强制失效均必须产生审计记录；权限变更在下一次 API 请求立即生效。

### 2. 建设客户、销售单和 BOM 的最小领域 schema

- 新建销售域模块，替代当前仅称为 `customers` 的临时占位命名；客户池属于销售域子资源，而非独立平行订单域；
- 业务表使用 UUID、统一审计字段、逻辑删除字段和数据库外键；
- 客户名称与客户代码各自唯一；联系人归属客户，销售单保存客户与联系人快照；
- 销售单固定 `order_no`、客户、下单日期、产品名称/规格、数量、单位、交期、币种、单价/金额、状态、版本和扩展字段值；一张销售单对应一款产品；
- `order_no` 在有效销售单范围内唯一，由数据库唯一约束和服务层错误转换双重保障；外部合同号和客户 PO 是可选参考号；
- 销售单状态仅允许 `draft -> confirmed -> closed` 的已确认流转；确认动作必须走状态机；
- BOM 先落最小核心：所属 `order_no`、销售单/销售版本来源、版本号、状态、扩展字段值和审计信息。BOM 明细、工艺字段、QC 项目均不在本次硬编码；
- 可扩展字段采用版本化表单定义引用和结构化字段值，保留记录所使用的定义版本。不得创建万能业务单据表或 EAV 替代核心领域关系。

### 3. 固定后端资源与跨模块口径

- 资源按 `customers`、`sales-orders`、`boms` 提供 REST API；确认和 BOM 创建使用明确业务动作端点；
- 所有响应遵循 [全局 API 与错误处理契约](global-api-contract.md)：成功信封、`request_id`、结构化错误、`snake_case`、十进制字符串和 ISO 8601；
- 使用 `ORDER_NO_CONFLICT`、`INVALID_STATE_TRANSITION`、`SALES_ORDER_NOT_CONFIRMED`、`VERSION_CONFLICT` 等稳定业务错误码；
- 所有跨模块关联传递 `order_no`、`source_type`、`source_id`、`source_version`，而不是传递整个上游对象；
- 销售确认、BOM 创建和未来影响下游的编辑均在数据库事务中完成，并写入审计与状态记录；
- 本阶段的影响预览至少识别是否已有 BOM；已存在 BOM 的销售变更不得自动改写 BOM，而是生成/返回复核提示。

### 4. 移除前端占位并打通真实操作

- 删除演示数据适配器、演示公告和模块占位组件在实际页面中的使用；不以静态假数据伪装业务功能；
- 实现登录、会话恢复、退出、未授权跳转和 API 错误展示；
- 实现客户列表/表单、销售单列表/表单/详情、订单确认、BOM 创建/详情页面；统一使用 TanStack Table、React Hook Form 与现有 UI token；
- 尚未实现的采购、仓库、生产、财务和人事功能页改为真实的“暂未开放”空状态和导航禁用/标识，不展示假业务表格；在其后续链路实现时替换；
- 工作台只展示真实 API 可返回的数据；在尚无聚合数据前显示真实空状态，不使用演示数据。

## 测试决策

- 测试以外部行为为准，不测试 NestJS/Prisma 的内部调用顺序；沿用现有 Node 测试作为平台契约测试入口，并为本阶段补充 API 集成测试。
- 健康检查测试覆盖应用可用、数据库可用和数据库不可用三种结果。
- 认证测试覆盖初始用户登录、Cookie 会话恢复、退出后失效、错误密码 `401`、未登录访问受保护资源 `401` 和无模块权限 `403`。
- 客户测试覆盖唯一名称/代码、联系人快照、逻辑删除和已被销售单引用后的停用保护。
- 销售单测试覆盖订单号唯一性、草稿编辑、确认前必填校验、合法/非法状态流转、版本记录、审计字段和已有关联 BOM 时的影响预览。
- BOM 测试覆盖仅允许从已确认销售单创建、来源销售版本保存、同一订单多 BOM 版本和不自动改写历史 BOM。
- 浏览器端到端测试覆盖“登录 -> 客户 -> 销售单 -> 确认 -> 创建 BOM -> 查看来源”的唯一验收缝隙，并验证无演示数据/占位内容残留在已开放页面。

## 阶段与门槛

1. 平台验证：认证、会话、数据库健康检查和初始管理员可在本机真实运行。
2. 后端链路：迁移可在空 PostgreSQL 重复执行，客户、销售单、确认和 BOM API 通过集成测试。
3. 前端链路：浏览器使用真实 API 完成验收缝隙；前端不再使用演示数据或模块占位。
4. 交付验证：`npm run build`、`npm run typecheck`、`npm run test` 通过；开发日志记录实际迁移、测试和未决事项。

后续阶段不得越过前一阶段的门槛。

## 非范围

- 询盘、报价、打样、英文合同、报关、Excel 导出模板和销售单打印；
- BOM 具体物料明细、损耗、工艺字段与 QC 检验项目；
- 采购、原料入库、生产、工序日报、薪资、成品收发存、应收应付；
- 审批流、字段级权限、移动端、离线操作、仁和云或其他外部系统集成；
- 为未实现模块构造演示数据或假操作页面。
