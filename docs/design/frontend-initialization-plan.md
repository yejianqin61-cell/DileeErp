# 迪礼 ERP 前端初始化开发文档

## 1. 文档目的

本阶段先搭建一个可供迪礼各模块负责人查看、讨论和反馈的前端框架。页面展示业务模块的入口、信息层级、列表/详情/表单的基本形态和订单主线，但不提前固化生产、采购、财务、仓库、人事或客户池的业务字段和流程。

## 2. 初始化目标

- 建立统一的 ERP 工作台布局和导航。
- 让六个业务模块都有可访问的占位页面。
- 提供订单推进、生产进度、应收应付等全局信息的展示占位，便于访谈时讨论优先级。
- 先验证页面信息架构、术语、密度和操作路径，再根据负责人反馈补模块细节。
- 所有占位数据明确标记为演示数据，不连接未确认的业务 API。

## 3. 技术与依赖

- React + Next.js + TypeScript。
- UI：shadcn/ui，所有颜色、间距、字体、边框、阴影和交互状态使用统一 design token。
- 表格：TanStack Table。
- 表单：React Hook Form；初始化阶段只建立表单容器和校验展示方式，不定义业务字段。
- API：通过独立 API client 访问 NestJS `/api/v1`；占位页面默认使用本地演示数据或空状态。
- 语言：只提供中文界面；业务内容可以展示英文示例。
- 客户端：厂内电脑浏览器 Web UI，不做手机端和 Tauri 客户端。

## 4. 页面信息架构

### 4.1 全局布局

- 顶部栏：系统名称、当前用户、环境提示、退出入口。
- 左侧主导航：工作台、生产、采购、财务、仓库、人事、客户池。
- 主内容区：页面标题、面包屑、筛选/操作区、主要内容、反馈状态。
- 页面不使用营销型 Hero 或装饰性大卡片，优先保证信息扫描和重复操作效率。

### 4.2 初始路由

```text
/                         工作台
/production               生产占位
/procurement              采购占位
/finance                  财务占位
/warehouse                仓库占位
/hr                       人事占位
/customers                客户池占位
```

后续模块详情路由遵循资源复数名和 kebab-case，例如 `/production/orders`、`/purchase-orders`；具体路由在模块规格确认后确定。

## 5. 工作台占位页面

工作台只呈现已确认的管理视角，不假设最终指标算法：

- 订单推进状态：展示订单号、客户、当前状态、交期等占位列。
- 生产工序进度：展示生产单、工序、计划数量、完成数量等占位列；工序字段标记待车间确认。
- 应收应付：展示往来方向、关联订单、币种、原币金额、已收/已付和余额等占位列。
- 待处理事项：展示待采购、待检验、待入库、待出货等状态提醒占位。

页面必须同时提供空状态、加载状态和错误状态，避免用静态卡片掩盖真实交互需求。

## 6. 六个模块占位页面

每个占位页面统一包含：模块标题、职责简介、建议的首屏列表形态、一个主操作按钮占位、空状态和“待负责人确认”提示。不得展示未确认的真实字段为既定规则。

| 模块 | 页面暂时展示 | 访谈重点 |
| --- | --- | --- |
| 生产 | 生产单列表、订单推进、工序进度占位 | 工序、数量、外发、返工和物料需求 |
| 采购 | 供应商/采购单列表占位 | 采购计划、到货、分批到货和退货 |
| 财务 | 应收应付和收付款列表占位 | 形成节点、部分收付款、对账和币种 |
| 仓库 | 原料/成品/退料/不良品库存列表占位 | 库存分类、成本、批次、单位和盘点 |
| 人事 | 员工、考勤、绩效、薪资台账列表占位 | 字段、周期、权限和人工计薪 |
| 客户池 | 客户列表和详情占位 | 客户字段、联系人、分类和状态 |

## 7. 统一组件边界

初始化阶段先建设或配置以下公共组件：

- `AppShell`：全局布局和导航。
- `PageHeader`：页面标题、说明和主操作。
- `DataTable`：基于 TanStack Table 的列表容器，支持列定义、空状态和加载状态。
- `FilterBar`：筛选条件容器。
- `StatusBadge`：状态展示，不内置业务状态集合。
- `EmptyState`、`LoadingState`、`ErrorState`：统一反馈状态。
- `DetailPanel` / `FormPanel`：详情和表单的通用承载，不提前定义业务字段。
- `AttachmentPanel`：只展示附件能力入口，具体必传规则待模块确认。

组件必须保持“数据由页面提供、行为由组件约定”的边界，避免公共组件直接依赖生产或采购业务。

## 8. Design token 初始范围

- 颜色：页面背景、内容背景、边框、正文、次要文字、主色、成功、警告、错误和信息。
- 间距：采用固定间距阶梯，不在模块内随意写新值。
- 字体：中文正文、标题、数字和表格数据的层级。
- 尺寸：导航宽度、按钮高度、输入框高度、表格行高和页面最大内容宽度。
- 状态：hover、focus、disabled、loading、error 和 selected。
- 圆角与阴影：仅用于必要的控件、弹窗和重复项，不把整页设计成卡片堆叠。

具体 token 值在实现前形成单独设计决策，并与 `docs/product/SRS.md` 的前端规范保持一致。

## 9. 演示数据与 API 边界

- 初始化页面使用独立的 typed demo fixtures，数据结构只表达页面讨论所需的最小字段。
- 演示数据必须标记来源，不得写入 PostgreSQL 或伪装成真实业务数据。
- API client 统一处理 `/api/v1` 前缀、JSON 信封、错误码、分页和请求状态。
- 当后端接口尚未确定时，页面通过 adapter 接入演示数据；模块确认后替换 adapter，不重写页面结构。

## 10. 访谈验收方式

带前端给模块负责人时，重点不是验收最终字段，而是确认：

1. 这个模块的首屏是否符合实际工作入口。
2. 列表需要比较哪些信息，哪些信息不应出现。
3. 哪些动作是主操作，哪些动作应放在详情或更多菜单。
4. 订单号、单据号、状态和经办人是否处于正确的信息层级。
5. 空数据、异常数据、部分完成和待处理状态是否符合实际。

访谈反馈必须回写术语词典、模块说明、模块设计文档和对应 task，不直接在占位页面中偷偷固化。

## 11. 本阶段不做

- 不定义六个模块的最终业务字段、数据库模型或状态集合。
- 不接入真实业务 API，不写入业务数据库。
- 不实现复杂审批、自动排产、库存成本、批次、单位换算或自动计薪。
- 不实现完整打印模板、报表算法和附件必传规则。

## 12. 开发顺序

1. 建立 design token、全局布局和导航。
2. 建立工作台占位页及统一反馈状态。
3. 建立六个模块路由和模块占位页。
4. 建立列表、筛选、详情和表单容器的演示交互。
5. 使用浏览器在厂内桌面尺寸验证页面密度、术语和导航。
6. 记录负责人反馈，再进入对应模块的详细规格和业务实现。

## 13. 验收标准

- 所有初始路由可访问，导航和返回路径清晰。
- 六个模块均有统一结构的占位页，并明确标注待负责人确认。
- 工作台展示订单推进、生产进度、应收应付三个已确认视角。
- 页面具备加载、空数据、错误和正常数据状态。
- 表格使用 TanStack Table，表单容器使用 React Hook Form，UI 使用 shadcn/ui 风格组件。
- `npm run typecheck` 和 `npm run build` 通过。
- 页面可作为访谈材料使用，且不会把演示数据误认为生产数据。
