# 采购计划的金额口径（单价 / 行总价 / 计划合计）

用户 2026-09-30：

> 「针对当前的采购计划，要求添加价格字段，单价，总价。不然财务没法付钱。
> 你也排查一下采购链路和财务链路的对齐度」

**结论先说**：单价**本来就有**（`purchase_plan_items.unit_price`，明细表第 8 列），缺的是**总价**。
而「不然财务没法付钱」这句话指向的不是"少一个显示字段"，是**两个真问题**：

1. **BOM 带出来的计划行单价固定是 0**，而下单门禁只要求「单价不为负」——
   所以一张计划可以**一路下单成 0 元采购单**，到货入库后变成一条 **0 元应付**：财务确实没法付钱，
   而且系统里没有任何一处会报错。本轮把这条链路掐断（§1.4）。
2. **计划上没有任何金额汇总**，也没有币种落点，所以「这张 BOM 一共要花多少、还差多少没买」
   在计划里答不出来，财务只能等入库之后才知道要付多少（§1.2 / §1.3）。

采购链路与财务链路的逐条排查结论另见
[`procurement-finance-alignment-2026-09-30.md`](./procurement-finance-alignment-2026-09-30.md)。

---

## 1. 口径（已与用户逐条确认）

### 1.1 钱的真源是「数量 × 单价」，不是另存一个金额

`purchase_plan_items` **不加 `amount` 列**：金额是 `quantity × unit_price` 的**派生量**，
落列就会有第二个真源，早晚与两个乘数漂移（改数量忘了改金额，而界面上两个数都"看起来对"）。

这一点与采购明细**故意不同**：`purchase_order_items.amount = 数量 × 单价 + extra_fee`，
它多了一项**独立输入**（额外费用），所以必须落列。计划里没有额外费用这一项，因此只派生。

### 1.2 「行总价」进明细表，「计划合计」进表下与列表

| 位置 | 内容 |
|---|---|
| 明细表新增一列 `行总价` | 只读，= 数量 × 单价，紧挨「单价」右侧 |
| 明细表下方 `plan-total` | **计划合计**（全部行）+ **其中未下单**（未下单行的合计） |
| 计划列表新增一列 `计划金额` | 与明细同一口径的按币种合计 |

「其中未下单」不是装饰：计划列表的「未下单 N」回答"还有几行没买"，
金额那一栏回答"还剩多少钱没买"—— 采购员和财务问的是后一个问题。

### 1.3 币种**按行记**（`purchase_plan_items.currency`，默认人民币）

为什么不是计划头上一个币种：一张计划里同时有**多个供应商**（口径 1），
而"一个币种"是**一张采购单**的属性（采购单的粒度 = 一个供应商 × 一个币种）。
计划头写一个币种，等于把"多个供应商可能报不同货币"这件事从数据模型里删掉。

为什么明细表里**不开一个「币种」列**：表已经 13 列（加总价 14 列），
而币种的**唯一决策点**本来就是「收束下单」预览里那个按供应商组选的下拉（口径 10）。
所以：

- 行上的 `currency` 默认 `CNY`；
- **收束下单时按该供应商组选的币种写回这一组每一行** —— 写回之后，
  已下单行的币种**永远等于那张采购单的币种**（不是两次输入，是一次输入两处记录）；
- 「退回采购计划」**不清**这一列：退回的是"哪张单"，不是"谈的是哪国钱"，
  重新下单前那个 USD 应该还在；
- **合计按币种分列**（`金额不跨币种合计`，仓库既有约定）：计划里既有人民币行又有美元行时，
  显示成 `CNY 12,345.60 · USD 2,000.00`，绝不加成一个数。

### 1.4 单价 > 0 才能下单

BOM 带出来的行单价是 `0`（`itemsFromBom`），必须由采购员按报价填。
原来只校验「不为负」，于是 0 单价可以一路走到应付。现在：

- **收束下单前**逐行校验，单价为 0 直接拒绝，错误码 `PURCHASE_PLAN_PRICE_REQUIRED`，
  报文说清"这一行的钱就是应付金额的来源"；
- **采购单侧的下单门禁**（`assertOrderableItems`）同步从「不为负」收紧成「必须大于 0」——
  否则同一个洞还留在 `POST /purchase-orders` 与 `POST /purchase-orders/split` 两个原始接口上
  （它们现在没有前端调用点，但接口是活的）。

**草稿不受影响**：这条门禁只管"下单"。计划里单价可以先是 0（还没谈价），
不能做的是**带着 0 单价下单**。

### 1.5 计划金额只是「提前看 / 对账」，实际付款仍只认入库金额

用户确认：不动账务链路。现状是

```
原料入库过账 → 应付来源（金额 = 入库数量 × 采购明细单价）
            → 确认应付（挂账：借 成本/存货，贷 应付账款）
            → 登记付款（借 应付账款，贷 银行存款）
```

到货单**被明确禁止**作为应付来源（`PURCHASE_RECEIPT_PAYABLE_DISABLED`），
所以「到货了但没入库」时财务看不到应付——这是既有口径，本轮不改。
计划合计与采购单总额的作用是让财务**在下单时就知道要准备多少钱**，以及在付款时对得上哪张单。

## 2. 不做的

- **不做计划 Excel 导出**（用户没要）。
- **不把额外费用并入应付**：采购明细的 `extra_fee` 计入采购单总额、不计入应付金额，
  而前后端界面都没有这个字段（只有原始 API 能传），实际不会产生差异。
  本轮把它**写进口径文档**而不是改账务逻辑（用户选定）。
- **不给明细表加「币种」列**：见 §1.3，币种的决策点在收束预览。
- **不做多币种折算**：合计按币种分列，不引入汇率。

## 3. 部署

一条迁移 `20260930140000_purchase_plan_currency`：给 `purchase_plan_items` 加
`currency VARCHAR(10) NOT NULL DEFAULT 'CNY'`。

- 纯加列 + 常量默认值，PostgreSQL 11+ 不重写全表；历史行自动得到 `CNY`。
- 前后端**不需要同时上线**：`currency` 只参与计划的**读取**展示；
  旧前端（不传 currency）下单时服务端仍会按组币种写回。
- 部署顺序见 `docs/task/PENDING-USER-COMMITS.md`（先 `db:generate` → `migrate deploy` → 再切代码）。

```sql
-- 迁移后确认列建出来了
SELECT column_name, data_type, is_nullable, column_default
FROM information_schema.columns
WHERE table_name = 'purchase_plan_items' AND column_name = 'currency';
-- 期望一行：character varying / NO / 'CNY'::character varying
```

  两边各自会红 —— 但不是类型系统保证的，靠的是这两份用例。
