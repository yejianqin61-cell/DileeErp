# 产品建模收束与编码基线

## 状态

已确认，2026-08-21

## 决策

迪礼 ERP 的产品建模阶段在现有业务边界下收束，进入编码准备阶段。V1 覆盖销售、采购、仓库、生产、人事和财务六个业务域，并以订单全链路运作模型作为跨模块验收基线。

本阶段不再追求一次性穷举每个业务表的全部字段。后续编码采用“小而美、先纵向贯通、逐模块深化”的方式：先完成平台能力和一条可运行的业务链路，再按业务负责人访谈结果扩展各模块。

## BOM 与 QC 的字段策略

### 固定核心

以下关系和约束属于系统核心，不由业务人员删除或改写：

- 订单号 `order_no` 及其跨模块追踪关系；
- 单据身份、版本、状态、来源单据和审计字段；
- BOM 与销售单版本的来源关系；
- QC 与被检单据、批次、检验结果及合格/条件接收/不合格数量的关系；
- 库存、生产、应收应付所需的数量和金额一致性校验；
- 逻辑删除、状态流转、审计日志和上下游影响预览。

### 可扩展明细

以下内容通过版本化的表单定义和字段值承载，由物控或授权操作员自行维护：

- BOM 的物料明细、用量、损耗、工艺备注、扩展属性；
- QC 的检验项目、检验标准、检测值、图片/附件、检验分组；
- 未来新增的业务字段、区段、重复明细和导出列。

表单定义变更不得改变既有记录的解释。业务记录必须保存所使用的定义版本和必要的字段快照；已使用的定义通常停用而不是删除。

## 编码约束

1. 先复用平台层的 UUID、审计字段、软删除、附件、字典、状态机和 REST JSON 约定。
2. 业务表采用明确的领域实体和固定核心字段；可变明细使用版本化配置加结构化值，禁止以一个无法解释的“万能单据表”替代领域关系。
3. 所有订单相关接口必须接收或返回 `order_no`，并提供来源链路和影响预览信息。
4. 编辑、撤销、退回、调整等操作保留原事实，不进行静默覆盖；跨模块派生数据在同一业务事务中重算或生成差异告警。
5. 每完成一个纵向切片，必须补充最小自动化测试和开发日志，再进入下一切片。

## 首个纵向切片

先实现“销售单草稿 -> 手工订单号校验 -> 销售单确认 -> BOM 版本占位/来源引用”的最小闭环。该切片验证订单号主线、表单版本、审计、状态机、影响预览和前后端 API 约定；不在本切片内实现完整 BOM、QC 或库存业务。

## 未提前固化的内容

- BOM 和 QC 的具体业务字段、分组、检验项目和导出布局；
- 各模块全部数据库表及复杂报表；
- 审批人/批准人规则的具体角色配置。

这些内容在对应模块编码前，由模块负责人访谈结果更新设计文档和任务文档后再实现。

## 决策记录

- 决策人：项目发起人/迪礼 ERP 产品负责人；
- 依据：已确认的模块设计文档、订单全链路运作模型及“灵活为上”原则；
- 影响：业务模块可以逐步实现，但不得绕过固定核心关系和可追溯性要求。
