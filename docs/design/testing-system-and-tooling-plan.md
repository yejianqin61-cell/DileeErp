# 迪礼 ERP 测试体系与测试工具建设方案

## 文档信息

- 文档类型：测试体系与工程工具建设方案
- 版本：V1.0 初版
- 状态：已实施，真实链路环境待接通
- 编制日期：2026-08-21
- 适用范围：API、数据库、Web 前端、跨模块业务链路、部署验收
- 上游依据：`docs/task/coding-roadmap-todolist.md`、各模块设计文档、`.agent/constitution/constitution.md`

## 1. 问题与目标

当前项目已有少量 Node 原生单元测试、API/Web 构建和类型检查，但测试仍以服务层 mock 为主，缺少真实 PostgreSQL 集成、HTTP 契约、浏览器操作、链路夹具、数据清理和持续集成门禁。这样容易出现“单个模块测试通过，但数据无法在上下游正常流转”的问题。

本方案的目标是建立一套适合单人开发、小规模厂内 ERP 的轻量测试体系：

1. 每完成一条业务链路，立即具备对应的自动化回归测试，不等全部模块完工后集中排错。
2. 证明数据从上游单据到下游事实的完整流转，而不仅是页面能打开或函数能返回。
3. 证明数量、金额、状态、`order_no`、审计和来源关系等跨模块不变量始终成立。
4. 在 PostgreSQL 不可用时仍能运行快速静态/领域测试；在数据库可用时自动升级到真实集成和端到端测试。
5. 测试失败能定位到业务链路、接口、数据夹具和具体不变量，避免依赖人工猜测。

## 2. 固定测试原则

### 2.1 测试外部行为

优先测试 API 响应、数据库事实、状态转移、库存/金额结果和浏览器可见行为，不测试私有函数的实现细节。服务层单元测试只用于快速覆盖复杂规则；最终门禁必须由更高层测试证明真实数据流。

### 2.2 测试金字塔

```text
少量：浏览器端到端链路（真实 API + 测试数据库）
较少：HTTP/API 集成与数据库事务测试
适量：领域规则和服务层单元测试
大量：纯函数、契约序列化、校验器测试
```

每个纵向业务切片至少包含一条端到端主路径、关键负向路径、一次回退/冲销路径和一个并发/幂等路径。

### 2.3 数据事实优先

测试不能只断言接口返回 200。每条链路结束后必须从数据库或只读查询接口核对：

- `order_no` 是否贯穿所有相关事实；
- 来源 ID、版本和快照是否保持一致；
- 状态是否符合显式状态机；
- 数量/金额派生值是否由事实正确汇总；
- `created_by`、`updated_by`、操作时间和审计事件是否存在；
- 逻辑删除、冲销和调整是否保留原事实；
- 重复请求是否没有重复库存、应付或应收。

### 2.4 失败优先保护数据

负向测试必须确认失败后没有部分写入。事务失败、数量不平、权限不足、来源版本失效、库存不足和幂等冲突都要核对数据库没有留下半成品事实。

## 3. 工具与运行环境

### 3.1 已有工具的定位

- Node.js 内置 `node:test`：保留为快速领域/服务层测试入口，避免为简单规则引入新测试框架。
- TypeScript `tsc --noEmit`：作为类型门禁。
- Nest build：作为 API 编译和模块装配门禁。
- Prisma CLI：负责 Schema 校验、Client 生成、迁移状态和测试数据库准备。
- Next.js build：作为 Web 编译、路由收集和生产构建门禁。

### 3.2 新增工具决策

- HTTP 集成测试：优先使用 Node 原生 `fetch` 调用已启动的 API，复用统一 JSON 契约；只有需要 Nest 测试模块隔离时才使用 `@nestjs/testing`。
- 浏览器端到端：采用 Playwright，固定 Chromium 版本和 `playwright.config`，只测试用户可见流程和网络结果，不绕过登录或直接调用数据库完成验收。
- 数据库测试：采用专用 PostgreSQL 测试数据库。优先复用本地 Docker Compose；不能拉取镜像时，允许只运行无数据库测试，但不得把 mock 结果宣称为集成通过。
- 覆盖率：第一阶段使用 Node `--experimental-test-coverage` 或等价原生能力生成报告；待测试量稳定后再统一覆盖率工具，避免过早引入复杂配置。
- 测试报告：统一输出 JUnit/JSON（供 CI）和人可读 Markdown 摘要（写入 `docs/test/`）。

### 3.3 测试脚本分层

根目录脚本最终统一为以下语义，具体命令可按当前环境使用 `npm` 或 `npm.cmd`：

```text
npm run test:unit       # 不依赖 PostgreSQL 的快速规则测试
npm run test:api        # 已启动 API 的 HTTP 契约/权限测试
npm run test:integration # 真实 PostgreSQL + Prisma 事务/数据流
npm run test:e2e        # Playwright 浏览器链路
npm run test             # 本地默认快速门禁：unit + build + typecheck
npm run verify:chain    # 当前已完成链路的集成/端到端验收集合
```

`test` 不应强制依赖 Docker，保证单人开发可快速反馈；提交前或 CI 再执行数据库和浏览器门禁。

## 4. 测试目录与证据规范

建议目录结构：

```text
apps/api/test/unit/             # 纯规则与服务层快速测试
apps/api/test/http/             # API 响应、错误码、权限与契约
apps/api/test/integration/      # 真实 Prisma/PostgreSQL 数据流
apps/web/test/                  # 前端组件/交互测试（有明确外部行为时）
tests/e2e/                      # Playwright 跨页面业务链路
tests/fixtures/                 # 可复用业务夹具和测试用户
tests/helpers/                  # API 客户端、数据库清理、断言、不变量
docs/test/cases/                # 链路用例与人工验收补充
docs/test/results/              # 每次重要验收的结果摘要
```

每条自动化测试的命名应包含模块和场景，例如：

```text
procurement.inbound.post.generates_inventory_and_payable_source
procurement.qc.reject_does_not_enter_available_inventory
sales.order_no.remains_traceable_through_purchase
```

测试结果记录至少包含：提交号、执行命令、环境、通过/失败数量、数据库是否真实可用、失败原因、遗留风险和关联任务。

## 5. 共享测试夹具

### 5.1 测试用户

固定创建以下最小角色，不复用生产管理员：

- `sales_operator`：销售权限；
- `procurement_operator`：采购权限；
- `warehouse_operator`：仓库/QC 权限；
- `finance_operator`：财务权限；
- `administrator`：仅用于平台管理测试。

每个测试用例使用独立会话和随机密码，测试结束清理会话。禁止在仓库提交真实密码、真实客户或真实供应商数据。

### 5.2 业务夹具

测试夹具按依赖顺序提供工厂方法，而不是在每个测试中手写长串 SQL：

```text
createCustomer()
createConfirmedSalesOrder(order_no)
createPublishedBom(order_no, materials)
createMaterialAndUnit()
createSupplier()
createPurchaseOrder(order_no, bom)
createReceipt(purchase_order_item, quantity)
createIncomingInspection(receipt, accepted, conditional, rejected)
createRawMaterialInbound(inspection, quantity)
postInbound(inbound)
```

夹具必须通过业务 API 或 Prisma 测试客户端创建合法初始状态；不得绕过业务规则制造“已过账但没有来源”的脏数据，除非测试名称明确是在验证坏数据恢复。

### 5.3 隔离与清理

- 每个集成测试套件使用独立测试数据库或独立 schema；不能依赖测试执行顺序。
- 默认每个用例使用事务回滚或唯一测试前缀；跨事务行为（并发、异步、状态流转）使用独立数据并在 finally 清理。
- 订单号、采购单号、入库单号等业务编号使用测试前缀和 UUID，避免并行冲突。
- 清理必须按外键依赖逆序执行，失败时保留失败数据库标识供诊断，不静默吞掉清理错误。

## 6. 跨模块不变量与通用断言

建立 `assertBusinessInvariant` 断言库，所有链路复用：

### 6.1 身份与来源

- 相关事实均存在同一个 `order_no`；
- 派生单号不能替代 `order_no`；
- 来源 ID、版本和快照指向创建时有效的上游事实；
- 逻辑删除的来源不能被新业务继续引用。

### 6.2 审计与可追溯

- 所有业务表具备四个统一审计字段；
- 创建、编辑、状态动作、冲销和逻辑删除均有审计事件；
- 冲销/调整包含原因、操作人、时间和原事实引用；
- 测试不得接受客户端传入的 `created_by` 覆盖服务端当前用户。

### 6.3 数量与金额

- QC：`accepted + conditional + rejected = inspected`，累计 inspected 不超过到货数量；
- 采购到货、原料入库、生产日报、成品出入库均按事实累计，超量只在明确规则允许时告警；
- 库存余额只由有效动态事实汇总，不接受直接余额写入；
- 应付/应收来源使用实际业务事实数量和价格快照；
- 分批收付款和核销不得超过可核销余额。

### 6.4 状态与回退

- 非法状态动作返回稳定 `4xx` 错误且不写入状态变化；
- 已确认事实不能被静默覆盖；
- 冲销产生反向事实，原事实仍可查询；
- 幂等重试不重复增加库存、金额或来源记录。

## 7. 链路级测试门槛

每个纵向任务完成时，必须同时交付代码测试和测试记录。最低门槛如下：

| 链路 | 主路径 | 必测负向/回退 | 最低证据 |
| --- | --- | --- | --- |
| 客户 -> 销售单 -> `order_no` -> 销售确认 -> BOM | 创建、确认、BOM 来源 | 重复订单号、草稿建 BOM、确认后来源编辑 | API + 浏览器主路径 + 来源断言 |
| BOM -> 采购 -> 分批到货 | 发布 BOM、手工采购、两次到货 | 未确认销售单、未发布 BOM、停用物料、超收告警 | Schema + API + 真实数据库 |
| 到货 -> 来料 QC | 合格、条件接收、不合格分流 | 分流不平、累计超过到货、无权限 | API + 事务回滚 + 数量断言 |
| QC -> 原料入库 -> 应付来源 | 分批入库过账、来源生成 | 超 QC 入库、重复过账、库存负数、冲销 | 真实事务 + 幂等 + `order_no` 链路 |
| 原料库存 -> 生产领退料 | 待生产模块接入 | 负库存、超领、退料上限 | 库存事实断言 + 回退测试 |
| 生产 -> 成品 QC -> 成品入库 | 待生产模块接入 | 超单、不合格、条件接收 | QC/库存/生产累计断言 |
| 成品出库 -> 应收 -> 收款核销 | 待销售/财务模块接入 | 超发、超额核销、退款冲销 | 真实数据库 + 浏览器链路 |
| 员工日报 -> 薪资 -> 工资支付 | 待人事财务模块接入 | 计时件数不计薪、日报差异、重复支付 | 薪资来源不可变断言 |

“链路完成”必须同时满足：代码测试通过、数据不变量通过、错误路径通过、审计可追溯、测试结果入 `docs/test/results/`。仅有 build/typecheck 不得关闭链路任务。

## 8. 当前采购链路的首批测试基线

针对已经实现的 `BOM -> 采购 -> 来料 QC -> 原料入库 -> 应付来源`，先建立以下测试套件：

1. 静态门禁：Prisma validate、API/Web typecheck、API build、Web production build。
2. 领域门禁：BOM 发布只读、基础资料引用保护、QC 分流合计、入库数量门禁、冲销负库存门禁。
3. API 门禁：认证、RBAC、统一错误信封、来源版本校验、采购状态动作、分批到货、幂等过账。
4. 数据库门禁：真实迁移、seed、采购单快照、QC/入库/库存事实/应付来源同事务提交与回滚。
5. 浏览器门禁：登录 -> 采购单 -> 到货 -> QC -> 原料入库 -> 应付来源查询，所有页面展示同一 `order_no`。
6. 回归门禁：每次后续生产、成品、财务改动都重跑本链路，确认没有破坏采购来源和库存事实。

当前已存在的服务层测试只能作为第 2 层快速反馈；在 PostgreSQL 可用前，不得把它们标记为真实链路验收。Docker 镜像网络阻断时，测试报告必须明确区分“mock/静态通过”和“真实数据库未执行”。

## 9. CI 与本地开发门禁

### 9.1 提交前快速门禁

```text
npm run typecheck
npm run test:unit
npm run build --workspace=@dilee/api
npm run build --workspace=@dilee/web
```

Web 构建在低内存开发机上统一允许通过 `NODE_OPTIONS=--max-old-space-size=4096` 执行，但不得用跳过类型检查或跳过页面生成代替构建。

### 9.2 链路提交门禁

```text
npm run db:test:prepare
npm run test:integration
npm run test:api
npm run test:e2e
npm run verify:chain
```

任何一项失败都不能将对应链路标记为已完成。测试数据库准备失败时，报告为环境阻断，不得自动降级为 mock 通过。

### 9.3 失败诊断

失败报告至少输出：测试名、提交号、请求 ID、用户角色、`order_no`、来源 ID、数据库状态、响应状态/错误码和截图/trace（浏览器测试）。敏感密码、Cookie 和真实业务数据必须脱敏。

## 10. 测试数据与生产安全

- 测试数据库与生产数据库使用不同连接串、账号和存储目录；
- 测试夹具禁止使用迪礼真实客户、供应商、员工和订单数据；
- 备份恢复测试使用脱敏测试库；
- 浏览器 trace、日志和失败响应中不得保存密码、会话令牌和敏感结算信息；
- 任何需要导入生产样本的测试必须先形成 memo，记录脱敏方式、授权人和清理期限。

## 11. 实施顺序

1. 统一测试脚本命名、目录和结果格式，保留现有 Node 测试。
2. 建立共享夹具、测试用户、数据库清理和跨模块不变量断言。
3. 为当前采购链路补 HTTP 集成和真实 PostgreSQL 测试，并记录真实环境阻断状态。
4. 引入 Playwright，完成客户/销售/BOM 和采购链路浏览器验收。
5. 把每个后续业务任务的测试门槛写入对应 task 文档，编码与测试同提交。
6. 最后接入 CI、覆盖率趋势、备份恢复和性能验收；不在业务链路尚未稳定时追求覆盖率数字。

## 12. 完成判定

测试体系建设完成的标准：

- 本地一条命令可运行快速测试，数据库可用时一条命令可运行真实链路测试；
- 每条已完成链路都有主路径、负向、回退、幂等和审计断言；
- 测试失败能定位到提交、链路、订单号和错误码；
- PostgreSQL、浏览器和备份恢复失败不会被 mock 或静态检查掩盖；
- 测试结果与任务文档、每日开发日志和提交记录互相可追溯。

## 13. 暂不纳入

- 移动端测试、离线同步测试；
- 外部系统接口契约测试（当前明确独立运行）；
- 大规模压测和复杂混沌测试；
- 未确认业务规则的自动化快照；
- 以覆盖率百分比作为唯一质量指标。
