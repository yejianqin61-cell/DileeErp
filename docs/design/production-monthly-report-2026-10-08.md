# 生产月报表导出（2026-10-08）

用户 2026-10-08：

> 「3.生产部分，要支持，导出每月的生产月报表。展示这个月所有的订单的生产总量。这个是模板：`Dilee\example\财务\2026.6月同安.xlsx`」

按用户习惯先问后做，他选了：**总表 + 每道工序一张明细 sheet**（整本模板的形状），数量口径
**与生产进度页一致：工序日报与员工日报取大**。

## 1. 交付物

| 东西 | 位置 |
|---|---|
| 路由 | `GET /api/v1/production/reports/monthly-production-report.xlsx?month=YYYY-MM`（`@RequireAdministrator()`） |
| 文件名 | `迪礼ERP-生产月报表.xlsx` |
| 取数 | `ProductionPayrollExportService.exportMonthlyProduction()`（`production-payroll-export.service.ts`） |
| 入口 | 生产页导出面板第 6 个按钮「生产月报表」（`payroll-export-panel.tsx`），复用面板上的月份选择 |
| 多 sheet | 新抽出 `buildBook()`；既有 6 个单表导出仍走 `buildSheet()`（＝ buildBook 的单 sheet 特例），输出未变 |

sheet 构成：`生产月报表`（总表）+ **当月有数据的每道工序一张明细**（没有数据的工序不出空表）。
总表每格与对应明细 sheet 的「汇总数量」**同一个数**——明细直接调用总表用的 `cellValue()`，不是另算一遍。

总表列：`月份 | 订单号 | 订单数量 | 规格 | <工序…> | 各工序合计（非完工量）`，一个订单一行、订单号升序。
工序列**读工序字典**（`operation_catalogs`，运行时可改），不写死：模板工序列在前
（客户叫法「验伞面/品验」按字典名 `验片/品检` 列出；`拉边` 按生产单执行方式分 `本厂/外发`），
再按字典顺序追加当月有数据的其余工序，最后补上「有数据但已不在字典里」的历史工序名
（三层兜底：**没有任何数量会被静默丢掉**）。

## 2. 数量口径（这一节是这份报表的全部风险所在）

**数量 ＝ max(工序日报日合计, 员工日报日合计) 逐日取大后累加。**
取大的键是 `(订单号, 工序, 单位, 生产单执行方式, 日期)`。

- 两个登记面是**同一事实的两次人工登记**：相加会双重计数，只取一面会低估。这条规则本身是仓库既有的
  （`production-progress.service.ts:121-132`、`finished-goods-inbound-notices.service.ts:163-169`）。
- 为什么是**逐日**取大而不是整月取大：两个面常常录在不同日期（3 号录工序日报、7 号录员工日报），
  整月取大等于把其中一天的量静默丢掉。逐日取大在「只用一面」时与生产进度页同值，混用时更准。
- 为什么把 `单位` 与 `执行方式` 也放进键：**数量不跨单位合计**是全站纪律（`reorder.domain.ts:11`），
  而本厂与外发是两批不同的活。放进键以后，不同单位/不同执行方式的日合计**根本不在同一个桶里**，
  口径在数据结构上就落地了，而不是靠后面求和时记得判断。
- 同一 `(订单, 工序)` 当月出现多个单位时，该格**不合计**：按单位分行写成文字（如 `4 打 + 60 支`），
  末列写「单位不一致，不合计」。金额是元，不受这条约束（纪律针对数量）。
- 工人列（`姓名 数量 / 姓名 金额`）**只能**来自员工日报——只有它有员工维度。
  因此某天只有工序日报报了数时，这天进「汇总数量」但不进任何工人列：**工人列之和可能小于汇总数量**，
  这不是漏算，是两个登记面的差（明细 sheet 的口径说明里写明了）。
- 末列「**各工序合计（非完工量）**」＝本行各工序横向相加。同一件产品要经过多道工序，
  横向相加会把同一批货数好几遍（缝伞 218 打 + 包装 218 打 = 436 打，而订单只有 218 打）；
  生产进度表因此干脆不做横向合计（`production-progress.service.ts:188-190`）。这里保留这一列只为量级核对，
  所以口径写进**列名本身**——备注里的说明没人会读，列名是唯一一定会被看到的地方。

## 3. 与模板的对照（能填 / 不能填）

| 模板里的东西 | 能不能填 | 依据 |
|---|---|---|
| 14 张工序 sheet 里的 12 张（大裁/小裁/拉边/打顶打带/验片/剪线头/打珠尾/合片/品检/折伞/缝伞/包装） | ✅ | 工序字典 14 项（`prisma/seed.ts:30`）+ `employee_daily_reports` |
| `Sheet1` 的「订单号 × 工序」矩阵 | ✅ 本报表的总表 | 行＝`order_no`，列＝`operationNameSnapshot`，值＝逐日取大的月合计 |
| `拉边` 拆「本厂 / 外发」 | ✅ | `production_orders.executionMode`（经生产单工序关联） |
| `大裁` 拆「布 / 伞带 / 布套」 | ❌ | 全库没有这个维度：日报只有工序粒度，拆分只能来自材料明细，与工序日报对不上 |
| `计时` 列 | ❌ | 那是计薪方式不是工序；计时行已经按工人列进明细（`wageMode = time_rate`），单列出来会与工序列重复计数 |
| `房补`/`总合计` 行 | ❌ | 全库没有住房补贴字段；没有房补时「总合计」与「合计」必然同值，重复一行只会让人以为漏看了一行 |
| `是否完成` 列 | ❌（刻意不做） | `targetQuantity` 挂在**生产单工序**上，而一个订单可以有多张生产单：按「订单 × 工序」给完成判定等于自己发明一个口径。完工量请读「包装」列 |
| `刘伟群`/`傅振锋`（外发对账单）、`布套`/`拉伞带` | ❌ | 前两张是外发对账（无工序粒度）；后两个工序在字典里**没有行**，先要在「生产 → 工序」里建工序并录日报 |

- **独立验收（Lead 自跑，不用子代理的 fixture）**：用编译后的真实服务 + 自己的假 prisma 生成真 xlsx，
  再用 openpyxl 读回：16 条断言全过——其中 `大裁` 一格＝`70`（5 号工序日报 50 + 6 号员工日报 20，
  逐日取大；整月取大会得 50、相加会得 100）、软删行与 7 月数据都不进表、拉边本厂 400/外发 300 分列、
  总表与 4 张明细 sheet 的汇总数量逐个同值、数量格是 Excel 数值类型、订单号是文本。

## 5. 已知边界

- 生产单工序的元数据（单位/执行方式）取不到时（工序行被删）**不丢数量**：单位记空、按本厂。
  这是有意的选择（金额/数量出现在表里等人核对，好过静默消失），但数据治理上应视为异常。
- 员工日报沿用既有 `LIMIT = 10000` 护栏：单月超过 1 万条员工日报会 422 `EXPORT_LIMIT_EXCEEDED`（需缩小范围）。
  工序日报走的是分组查询（行数上界＝订单×工序×天数），不额外设限。
- 月份边界是 **UTC**（`monthRange`），与 `report_date` 按 UTC 零点落库自洽（见
  `employee-daily-reports.service.ts:345`）；若将来改成按时间戳切月会差 8 小时。
- 「两源同日不一致」只在同一天两个面**都报了数且数不同**时在明细行备注里标出来
  （只有一面报数是常态，全标等于全是噪音）。
