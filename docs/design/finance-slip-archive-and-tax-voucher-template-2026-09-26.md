# 收付款单存档 + 汇率栏 + 交税凭证模板（2026-09-26）

用户这一轮的话很短，两句：

> 1. 付款单要有填写汇率的地方，保存键。生成凭证时要有交税的那一项。
> 2. 提交，push

第 2 句是操作（文档入库 + 推送，见 `docs/log/2026-09-26.md`），第 1 句是三件事。
用户对三件事各拍了一次口径，本文记的就是那三次拍板与落地方式。

## 0. 三件事的边界（一句话版）

| # | 要什么 | 落地什么 | 刻意不做什么 |
|---|---|---|---|
| ① | 付款单能填汇率 | 版式加一整行 R6：**币种 / 汇率 / 折合人民币** | 不按「合计 × 汇率」自动折算 |
| ② | 保存键 | 单子**落库**（`finance_slips` + `finance_slip_lines`），可再打开、再改、再导 | 不改任何账（不写流水、不生成凭证、不动应付状态） |
| ③ | 凭证里有交税那一项 | 记账凭证模板新增「交税」：借 应交税费 / 贷 银行存款 | 不自动填金额、不猜税种明细 |

## 1. 汇率与折合人民币（R6）

### 版式

模板原样只有四行表头，前面两轮已经加到五行（R5 = 我方账户，用户 2026-09-24）。这一轮加第六行，
三组「标签 + 值」正好占满六列（与 R2 同一种排法）：

```
R6   A: 币种：   B: USD   C: 汇率：   D: 7.12345678   E: 折合人民币：   F: 1064.44
```

行号常量 `HEADER_ROW = 7` / `FIRST_LINE_ROW = 8` 跟着下移。**这类下移最容易漏改 `totalRow`** ——
漏了的话合计行正好压在最后一条分录上，导出不报错、只是印歪。所以行号只有一个来源，测试再钉一遍
（`finance-slip.test.cjs` 逐格断言 R1–R15）。

### 精度：8 位，而不是跨行转账单的 6 位

这是本轮**唯一一处刻意偏离「照跨行转账单」**的地方。跨行转账单自己写了一个「最多 6 位小数」的
正则（`bank-transfer-slip.ts`），而全站汇率的唯一实现在 `money.ts`（`toRateUnits`，1e-8，
与 `exchange_rates.rate` 的 `DECIMAL(18,8)` 同精度）。为收付款单再定一套 6 位，就是第二份汇率口径 ——
而汇率的精度只该有一个出处。前端同理：`parseSlipRate` 与后端同精度、同一批用例两侧各跑一遍
（它**不能**直接 import `exchange-rate.ts` 的 `parseRate`：`lib/*.test.mjs` 用 `node --test`
直接载入 `.ts`，那种加载方式解析不了无扩展名的相对导入，见 `finance-slip.ts` 文件头）。

### 为什么不自动折算

「折合人民币」是**手填**的一格，留空就是留空（导出的单子上那一格也是空的）。理由与
「不按税率自动拆进项税」完全一样（`finance-slip.ts` 文件头第 2 条）：银行的折算价与我们的报价
本来就可能不同，而自动算出来的数在单子上看不出错。

界面上必须**把这句话说出来**（`SLIP_CNY_EMPTY_HINT` → 编辑器里的 `payment-slip-editor-cny-hint`）：
这两格看起来是一对（跨行转账单上就是一对），不说的话财务会以为系统替她算过了。

## 2. 保存键：单子落库

### 口径的变化，以及变化的边界

2026-09-20 的设计文档写着「单子**不落库** —— 它是一张打印件，不是系统单据」。这一轮改了，
但改的**只是「存不存」**，不是「它算不算账」：

- 保存**不改任何账**：不写收支流水、不生成凭证、不动应付/应收的状态与金额。
  「钱到底付没付」仍然由确认付款那条链回答（`supplier-payment.service.ts`）。
  这条边界必须守住，否则会出现「存了一张付款单，应付就自己变成已付」这种没人能解释的账。
- 落库解决的问题很具体：一次集中付款会拆出十几张单子，财务改到第五张去接个电话，
  回来时**那张单子就没了** —— 她只能从头再勾一遍、再改一遍。

### 表结构上的三条取舍

1. **分录行是从表**（`finance_slip_lines`），不是 JSON 列。金额落在 `DECIMAL` 上时，
   「这一侧没有金额」只能是 `NULL`（写 0 会被读成「确实为零」的事实），JSON 里做不到这条；
   形状与凭证分录（`voucher_lines`）一致，`line_no` 从 1 开始 —— 就是单子上的第 N 行。
   覆盖保存时**整组重写**（`deleteMany` + `create`）：逐行 diff 会让行号与实际印出来的序列错位。
2. **`slip_no` 不加唯一约束**。编号是财务本子上的东西（界面上可改、可以重复），
   加唯一约束会让她导出不了重号的那张。系统给的只是建议值（`suggestNumber`，原样保留）。
3. **`source_entry_ids` 是 JSONB 且不建外键**。勾选的应付/应收条目可以被删掉，
   而这张单子已经打出去、必须留着。它只用于追溯（列表/审计里能回答「这张单结的是哪几条」）。

### 保存与导出的门槛**分层**

单子有了「保存键」之后，校验必须分两层，否则互相打架：

| 函数 | 拦什么 | 谁用 |
|---|---|---|
| `validateFinanceSlipShape` | 日期、附单据张数、汇率/折合人民币格式、每行金额格式 | **保存**（结构坏了连存都存不进去：`slip_date` 是 DATE 列） |
| `validateFinanceSlip` | 上面全部 + 编号、对方单位、借贷平衡 | **导出**（拿去银行/走签字的那张纸） |

逼财务「填平了才能存」等于把保存变成「必须一次做完」，而这一轮做保存键的原因恰恰是
「一次十几张，改到一半被叫走」。前端同理：`financeSlipBlockers`（导出）与
`financeSlipSaveBlockers`（保存）是两个函数，弹窗里两条提示分开显示 ——
不然「保存能点、导出不能点」会被当成 bug。

### 界面：存下来的单子去哪了

新增财务板块 **收付款单**（`/finance/slips?kind=payment|receipt`，
`finance-slips-workspace.tsx`）。保存这个动作必须回答「存下来的单子在哪」，否则保存只是往库里
丢一条没人再看到的记录。这一页做三件事：**找回来**（列表 → 打开 → 同一个编辑器）、
**再导出**（不打开也能出文件，走的是与编辑器**同一个**导出请求体）、
**作废**（逻辑删除，原因必填）。

单子**在这一页建不出来**，页面上有一句说明写着它的起点是「勾一批应付/应收条目」——
否则用户会在这页找「新建」按钮，找不到就以为功能没做完。

### 第二层保险：第二次保存是覆盖

编辑器把后端返回的 `id` **记回队列里的那一条**，所以再点保存走 `PATCH /finance/slips/:id`
（覆盖同一张）而不是 `POST`（再建一张）。写错的表现是「财务点两次保存得到两张一模一样的单子，
而她分不出哪张是最后改的」—— 组件测试与服务端测试各钉一条。

## 3. 交税凭证模板

财务要的形状就是两行：**借 应交税费 / 贷 银行存款**。落在既有的模板机制里
（`voucher-template.ts`，与「工资计提」「原材料采购」同一套）：

- 候选科目只给「应交税费」本体，**不猜明细**：科目表里有 `应交税费-进项税 / -销项税`，
  但交的是哪一种税只有财务知道（增值税 / 所得税 / 附加税的科目都不同），
  猜一个具体的反而更容易错 —— 税种选错了，凭证上看不出任何异常。
- 资金行（`role: "fund"`）只是标记、不带金额：科目与银行账户由**被套用的那张凭证**决定
  （它来自哪条收支流水，钱落在哪张卡上是已确认的事实）。
- 金额一律留空（与另两张模板同一条既定口径）。

## 5. 刻意没做 / 留待确认

1. **不自动折算**（见 §1）。要改成自动，只需在导出前用 `money.ts` 的 `convertUnits` 补一格，
   但那就得同时回答「以谁的牌价为准」。
2. **存档没有版本历史**：覆盖保存只留最后一次（审计里有 `created: false` 与每次的金额，
   但不是逐版可比对）。要做「改过几版」得再加一张版本表。
3. **单子仍然不参与对账/核销**：一张付款单印出去之后，系统不知道钱是否真的付了 ——
   那仍由确认付款回答。若将来要让单子驱动出账，那是账务口径的改动，需要财务拍板。
4. **收款单的对方账户仍然要手填**：客户主数据没有结算信息列（与 2026-09-24 同一处缺口）。
5. **`slip_no` 建议值仍可能重复**（`suggestNumber` 按本月已确认条数推算）。
   本轮**没有**改成权威序列 —— 落库之后其实可以做了，但那会让「财务按自己本子上的号」这条路变窄，
   属于产品口径，先留着。
