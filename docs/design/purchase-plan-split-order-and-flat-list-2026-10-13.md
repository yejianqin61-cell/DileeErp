# 采购计划「分开下单 + 同供应商自动收束」与列表展平（2026-10-13）

> 用户原话：
> 「1.针对采购部分的，采购计划，现在改成可以分开下单，有确定单价的物料先下单。如果相同的供应商的不同物料
> 没有同时下单，下单之后也要自动收束在一个采购单里。
> 2.采购计划的那个页面，也要显示物料名称等等column。都要显示」

本文档是实施依据。口径在实现中不得擅自改变；要改先改本文档，并在 `docs/log/` 里记下改的理由。

开工前问了两道二选一，用户的选择（都是推荐项）：

| 问题 | 回答 |
| --- | --- |
| 自动收束的边界 | **已有单「已下单 + 无任何到货」且币种相同 → 并入；有到货或币种不同 → 新建一张单** |
| 「显示物料名称等 column」指哪个页面 | **列表页展平成「一行 = 一条计划明细」** |

---

## 1. 这一轮改的到底是什么

用户提的两条，各有一半**已经是既成能力**，这一轮只补缺的那一半 —— 分清楚才不会把好的东西重做一遍。

| 用户的话 | 现状 | 本轮动作 |
| --- | --- | --- |
| 「分开下单」 | ✅ 已有（2026-09-27 口径 6 的多波次：勾选哪几行就下哪几行，没收进组的行留在计划里） | 不动 |
| 「有确定单价的物料先下单」 | ✅ 已有（2026-10-11：0 价行一律不下单，前端把它们排除在本次请求外并复核） | 不动 |
| 「同供应商不同物料没同时下单，下单后**自动收束在一张采购单里**」 | ❌ **没有**：现在每一波都新建一张单 —— 分两波买同一家 = 两张采购单 | **本轮的主改动** |
| 「列表页也要显示物料名称等等 column」 | ❌ 没有：列表一行 = 一份计划，只显示计划级信息（编号/单号/货号/客户/版本/行数/未下单/金额/状态/最后更新） | **列表展平成一行 = 一条明细** |

### 1.1 为什么「自动收束」必须做，而不是"让采购员自己合并"

用户 2026-09-17 就定过一条：**「一个采购单内，一个供应商下一个单」**。现在这条只在一波之内成立
（`collectGroups()` 把同一供应商的行合成一张单），**跨波次不成立** —— 而跨波次正是
2026-10-11 那条「没确定单价的先不下单」的**必然后果**：没价的行要等报价，回来了就得再下一波。

于是同一条需求同时生产了"必须分波"和"必须同单"两个约束，只有系统能同时满足它们：

```
辅料 A（有价）+ 面料 B（有价）       辅料 A、B → PO-1
       ↓ 客户资料来了，辅料 C 有价了
辅料 C                            → 必须进 PO-1，不能再来一张 PO-2
```

靠人手动合并（`POST /purchase-orders/:id/split` 那条老路）不可行：它要"把两张单的行重新收束一次"，
而采购员手上根本没有"这两张单是同一家、应该合"的信息 —— 计划里有。

## 2. 口径（7 条，实现中不得擅自改）

| # | 口径 | 理由 / 代价 |
| --- | --- | --- |
| 1 | **并入的判据四条**，缺一不可：① 这张单是**这份计划自己下出来的**（它的明细里有计划行回写的链接，即 `purchase_plan_items.purchase_order_item_id` 指向它）；② 供应商与**币种**都对得上；③ 状态还是 `ordered`；④ 任一未删明细**都没有到货记录**。多条候选时取其中 `createdAt` 最新的那一张 | ① 防"把别人手工建的同供应商单吞进来"——按供应商猜一定会错；② 一张单一个供应商、一个币种，收束不能改变这两件事；③④ 到货是既成事实，往一张已经收到货的单上追加物料，会让到货/质检/应付的来源说不清（2026-09-17 的 `assertEditable` 就是这条）。候选取**仍然未到货**的那些里最近的一张：更早那张若还没收货，它本来就是一张有效、未收货的对外凭证，往里追新料不算篡改 |
| 2 | 不满足口径 1 时**新建一张单**，并且**在下单预览里说清为什么**（这一组显示「新建一张」而不是「并入 PO-xxx」） | 静默地"有时候并、有时候不并"是一种最难查的坏：采购员以为收束了，实际没有 |
| 3 | 并入时**只追加明细**，绝不改已有明细：单号、供应商、币种、**采购日期**、交货日期、备注、打印字段一概不动；只有 `total_amount` 累加 | 那些字是**已经发给供应商的凭证**上的内容。改它们等于在对方手上那份单之外另有一份"真实的单" |
| 4 | 并入的留痕有两处：单头 `extension_data.purchase_plan_merges`（只保留最近 20 条）与审计 `purchase_order.append_plan_items`；计划侧审计 `purchase_plan.order` 另记 `merged_purchase_order_nos` / `merged_line_count` | 单头 JSON 不设上限会被一个长期存在的单养成一个越来越大的字段 |
| 5 | **计划侧不新增任何字段**：并入之后 `purchase_plan_items.purchase_order_item_id` 照旧指向**新追加的那条采购明细**（同一张单） | 「已下单」的表示仍然只有一个（2026-09-27 §3.2），退回流（断开链接）也跟着不变 |
| 6 | 详情接口新增 `open_purchase_orders`（这份计划下**还能并入**的单：供应商/币种/已下单/无到货），前端每组显示「并入 PO-xxx」或「新建一张」 | 用户的原话是"自动"，但"自动做了什么"必须看得见 —— 与 2026-10-09「我真没看到哪里可以手填单价的」同一类坑 |
| 7 | 列表页 `/procurement/plans` **展平**成「一行 = 一条计划明细」，13 列，列宽显式和 = 100%；计划级汇总（行数/未下单行数/金额/状态/最后更新）**不再单独成列**，改成挂在「计划编号」那一格的 `title` 上 | 一行一条明细才能"都要显示"物料名称；计划级汇总与明细列塞在同一张表里会变成 20+ 列（1366px 上每列不到 70px），那正是 2026-09-27 口径 5 要防的事。点「计划编号」进详情，汇总仍在详情头上 |

### 2.1 币种为什么是硬条件（口径 1 ②）

「一个币种」是**一张采购单**的属性（2026-09-30 起计划合计按币种分列的口径）。
把美元的行并进一张人民币的单，会有两个后果，而且两个都不报错：

1. 应付金额 = 入库数量 × 采购明细单价，而单头 `currency` 只有一个 —— 财务收到一张"单价是美元、
   单头写着人民币"的单；
2. 计划的金额合计（按币种分列）会与采购单的合计对不上。

所以币种不同就**新建一张单**（用户已确认）。多数场景下币种都是 CNY，这条不构成日常阻碍。

### 2.2 「有到货就新建」会不会让用户觉得"没自动收束"

会，而且这是**有意的**：一张已经收到货的单，它的行、批次、质检、应付都已经挂上去了；
往里追一条新物料等于让"这批到货是哪张单的"多出一个答案。用户这一单的物料是**新谈的**，
本来就该有一张属于它自己的单。预览里会明确写「（已有到货，本次新建一张）」。

## 3. 实现

### 3.1 后端：`PurchaseOrdersService` 新增三个方法

| 方法 | 职责 |
| --- | --- |
| `findMergeTarget(tx, {order_no, bom_id, supplier_id, currency, linked_order_item_ids})` | 按口径 1 找出要并入的那张单；多条候选时取 `createdAt` 倒序第一张（="上一波下的那单"） |
| `appendItems(tx, order_id, merged, user)` | 在**调用方的事务里**追加明细 + 累加 `total_amount` + 写留痕；返回新建的明细（含 id，供计划行回写链接） |
| `openOrdersForPlan({order_no, bom_id, linked_order_item_ids})` | 详情接口用：列出所有还能并入的单（含供应商、币种、行数、金额） |

三条共用一段查询（`queryLinkedOpenOrders()`），所以"什么算可并入"只有一处实现。

**为什么放在采购单这一侧**：判据（状态、到货、币种、金额累加）全是采购单的不变式；
放在计划侧就等于把它们抄第二遍，而两份拷贝迟早会漂移成"预览说能并、下单却被拒"。

**为什么 `findMergeTarget` 在事务里调**：两个窗口同时下同一家的单，若在事务外判定，
两边都会看到"没有可并入的单"从而各建一张 —— 正是这个功能要消灭的场景。事务内判定 + 行锁
（`appendItems` 用 `SELECT … FOR UPDATE` 不需要：`order()` 整体在事务里，
而 `purchaseOrder.update` 本身会锁行）。

### 3.2 后端：`PurchasePlansService.order()` 的循环

```
collectGroups(splitInput, true)                  ← 校验与收束口径不变
  └─ 事务内，逐个分组：
       linkedOrderItemIds = 这份计划已下单行指向的采购明细 id
       target = orders.findMergeTarget(tx, {…, supplier, currency, linkedOrderItemIds})
       target ? orders.appendItems(tx, target.id, group)      → 记 merged: true
              : orders.createOrdersFromGroups(tx, [group])     → 记 merged: false
  └─ 按 `extension_data.purchase_plan_item_id` 回写计划行的链接（**只认这一波新建的明细**）
```

「只认这一波新建的明细」是这次新增的一处小心：并入的那张单上**原有**的明细带的是
上一波写进去的同一个认领标记，不加过滤就会把那些计划行的 `updatedBy/updatedAt` 再刷一遍
（不算错，但会把"最后更新"说成这次下单的人）。

响应体在原有 `orders[]` 上加了两个字段（向后兼容，不删不改）：

```jsonc
{ "orders": [{ "id", "purchaseOrderNo", "currency", "totalAmount",
               "merged": true, "lineCount": 3 }],   // merged=true 表示"并进了已有单"
  "mergedOrderCount": 1 }
```

### 3.3 后端：计划列表接口下发明细行

`GET /purchase-plans` 的每一项新增 `lines[]`（**展示投影**，与详情的 `items[]` 不是同一个形状：
详情的是可编辑行，含快照与 BOM 参考价；列表的只够渲染那 13 列）：

```jsonc
{ "id", "materialId", "materialCode", "materialName", "model", "unitName",
  "quantity", "unitPrice", "amount", "currency",
  "supplierId", "supplierName", "expectedDate",
  "ordered": false, "purchaseOrderNo": null }
```

计划级的 `lineCount` / `unorderedCount` / `amounts` / `unorderedAmounts` 原样保留
（口径 7 说它们不再单独成列，但**接口不断**：删字段会让别的入口静默拿到 undefined）。

### 3.4 前端：列表页 13 列（宽度百分比，和为 100）

| 列 | 宽 | 列 | 宽 |
| --- | --- | --- | --- |
| 计划编号（链接，title 挂计划汇总） | 9% | 单价 | 5% |
| 销售单号 | 9% | 行总价 | 7% |
| 货号 | 6% | 供应商 | 9% |
| 客户 | 8% | 下单状态（未下单 / 已下单 PO-xxx） | 9% |
| 物料名称 | 12% | 预计到货 | 7% |
| 型号 | 8% | | |
| 单位 | 4% | | |
| 本次采购量 | 7% | | |

`COLUMN_WIDTH` 常量集中在一处（照 `app/procurement/materials/page.tsx` 的既有做法），
守卫用例按它断言"和 = 100%"。

**一份计划行了 0 条时仍要出现**（占位一行，物料名称写「（这份计划一行都没有）」）：
否则一份被删空行的计划会从列表里消失，而它只能从列表点进去。

### 3.5 前端：收束预览要说清"并到哪张单"

`PlanOrderPreview` 每组那一行末尾追加一句：

- 有可并入的单 → `并入 PO-20261013-XXXXXXXX（已有 4 行）`
- 没有 → `新建一张（该供应商还没有未到货的已下单采购单 / 已有到货 / 币种不同）`

下单成功提示按服务端返回的 `merged` 分开说：
`本次下单 3 行：并入 PO-1（3 行）` / `本次下单 3 行：新建 PO-9（3 行）`。

## 4. 不做的改动（以及为什么）

- **不动 0 价不下单的口径**（2026-10-11），也不恢复 2026-10-09 的 `allow_pending_price` 后门。
- **不做"反收束"**（把已并入的行再拆出去）：`POST /purchase-orders/:id/split` 已经存在，
  要拆的人是极少数，不该为它把自动收束的逻辑复杂化。
- **不动 `purchase_plan_items` 的 schema**（口径 5）：没有新列、没有新表、**没有迁移**。
- **不改采购单页**：它仍然只有打印字段可编辑，明细仍只能在计划里改（口径 7 / 2026-09-27）。
- **不给列表加"计划级汇总"列**（口径 7）：汇总挂在计划编号的 `title` 上，详情里仍在。

未在本机验证的项（部署时请人工确认）：

1. **真库上的并发**：两个窗口同时给同一供应商下单时，`findMergeTarget()` 在**事务内**查
   （它见得到本事务自己的写入），理论上只有一个会并入。这条只靠推理，没有压测 —— 上服务器后值得试一次。
2. **列表展平后的实际排版**（1366 / 1440 / 1920 三个视口）：jsdom 不排版，13 列的省略号是否
   按预期生效只能目视。宽度的算术和已由 `lib/purchase-plan-list-table.test.mjs` 钉住（= 100%）。
3. **同供应商 / 同 BOM / 同币种 / 无到货的已下单单若有两张以上**（本功能上线前分波下的历史数据）：
   下一波会并进**最近那一张**；两张并存这件事本身不会自动被合掉（要合走 `POST /purchase-orders/:id/split`）。
4. **老客户端**：`POST /purchase-plans/:id/order` 的请求体没变（`groups[]`），响应体只**新增**
   `merged` / `lineCount` / `mergedOrderCount`，所以前后端不必同时上；列表接口新增 `lines[]`，
   旧前端忽略它即可（`PlanRow.lines` 在前端也是可选的）。
