# 销售单材料明细：同类目可填多款（2026-10-29）

## 1. 需求原话

> 针对销售单，现在支持材料明细那边可以在现有基础上自行添加类目。比如我这一单有3款伞头，
> 2款伞布。就支持自行添加类目来填写。同时，销售单的导出件也要同步跟上

## 2. 先查清：哪一半已经有了

系统里 **2026-10-08 就有「其它」区**（`sales_order_material_extras` + 编辑页底部的「其它」块）：
可以自己起类目名（弹簧/螺丝/胶袋…）、填内容、挂物料引用，工艺单导出会印在 18 项之后。
所以「自己加类目名」这件事是**已经有的**。

这次真正缺的是：**同一个固定类目要能填好几款**。
18 个固定类目（伞骨、伞布规格、伞头…）每一格只有一个输入框，这一单有 3 款伞头时：
- 用「其它」区能凑出来，但三行会分散在最下面（印在「弹簧/胶袋」那一堆里），
  与上面的「伞头」那一格没有视觉关系；
- 而且类目名要用户手打三次，打错一个字（「伞 头」）纸上就多出一个没见过的类目。

老板在 A/B 两个做法里选了 **A：固定类目下点「再加一款」，同类目可以填多行**。
（B 是「材料明细改成一张自由增行的表」，改动大、所有老单表样会跟着变，没有选。）

## 3. 数据模型：一行多一个归属键，不新开表

`sales_order_material_extras` 加一列：

```sql
ALTER TABLE "sales_order_material_extras" ADD COLUMN "spec_key" VARCHAR(40);
```

- **可空**：`NULL` = 原有「其它」自由类目行（行为一个字都没变）；非空 = 属于 18 个固定类目之一。
- 为什么复用这张表而不是新表：一行仍然是一条「类目 + 内容 + 物料引用」，
  新表相对它只多一个归属键；而「谁先印」是**导出顺序**问题 ——
  拆成两张表等于把印刷顺序拆到两处（固定类目在导出常量里、追加行在新表里），
  而这个功能的全部意义就是「3 款伞头在纸上连在一起」。
- 不建唯一键：同一类目就是可以有多行（这正是需求），整块替换语义与 `sales_order_spec_details` 一致
  （软删旧的 + 建新的），代价是行 id 每次保存都变 —— 图片导出用 `extra:<行 id>` 已经按这个代价设计过。
- 迁移：`20261029200000_sales_order_material_extra_spec_key`。

## 4. 接口语义

`material_extras[]` 里的每一行多一个可选 `spec_key`：

| 场景 | 请求 | 落库 `label` | 落库 `spec_key` | 导出位置 |
|---|---|---|---|---|
| 原有「其它」 | `{ label: "弹簧", content: "5cm" }` | 用户写的字 | `NULL` | 18 项之后 |
| 同类目再加一款 | `{ spec_key: "handle_spec", content: "弯柄黑色" }` | **服务端按类目清单填「伞头」** | `handle_spec` | 紧跟「伞头」那一行 |

三条硬规则（`normalizeMaterialExtras`）：

1. `spec_key` 必须是那 18 个键之一，否则 422 `MATERIAL_EXTRA_SPEC_KEY_UNSUPPORTED`；
2. 带 `spec_key` 时**忽略请求里的 label**，一律用 `sales-material-labels.ts` 里的中文名 ——
   否则纸上可能印着「伞布」却排在「伞头」后面；那种错车间照做出来才发现，而单子已经下给工厂了；
3. 类目名清单**只有一份**（`sales-material-labels.ts`）：导出、服务层、校验三处共用，
   导出服务的 `MATERIAL_LABELS` 直接 re-export 它。服务层不能 import 导出服务（会成环），
   所以放在独立模块里，避免三份清单漂移成「页面与纸面不一样」。

整块替换语义不变（`undefined` = 不动、`[]` = 清空）；返单预览、普通复制、版本快照都带上 `spec_key`
（漏一处就会让新单把追加款退化成「其它」行，印到最下面）。

## 5. 导出件（工艺单）

`materialLines` 的组装顺序：

```
18 个固定类目，按模板印刷顺序，每个类目：
  ① 本类目自己那一格（有值才印）
  ② 紧跟它的 [spec_key] 追加款（按 sortOrder）
然后：自由类目的「其它」行（按 sortOrder）
```

- 「本类目那一格空着、只加了款」也要印 —— 用户可能就是只用了追加款；
- 空的追加款（只加了行没填）不印，与「空盘位自动省略」同一条口径；
- **图片导出候选**的排序同样跟着类目走（`类目序号 + 0.5 + sortOrder/1000`），
  而不是全堆到 18 项之后：勾选弹窗里的顺序与纸上一致，用户才对得上。

样例（`docs/samples/工艺单-样例.xlsx` + 预览图）就是 3 款伞头 / 2 款伞布：
纸上依次是「伞布规格 190T 素色黑 / 伞布规格 210T 藏青 / 伞头 直柄银色 / 伞头 弯柄黑色 /
伞头 三折伞头（银）」，最后一行是自由类目「弹簧」。

## 6. 前端

材料明细每一格下面多一个「再加一款」按钮；点出来的行只填**内容 + 物料引用**（类目名不给改）：

- 追加款用虚线框、字号小一号，视觉上属于该格（`.material-ref-field .material-extra-row`）；
- 原来的「其它」块只渲染**自由类目行**（`specKey` 为空），给模板以外的新类目用；
- 两组行在同一个数组里，保存时整块发出（`specPayload` → `material_extras`），行号互不挤占；
- 判空：追加款只看内容与引用（类目名是系统给的，不能因为「有类目名」就永远不算空行）；
- 报错文案带类目名（「伞头：内容与引用的物料至少要有一个」），因为这类行没有「类目」输入框，
  只说「第 2 行」用户找不到是哪一行；
- 回填两种形状都认：接口的列名 `specKey` 与返单/快照的请求键 `spec_key`。

- `apps/api/test/unit/sales-order-material-extras.test.cjs`（+6）
  - 归一口径：只给 `spec_key` 也能存、类目名服务端补、未知键 422、覆盖请求里的 label；
  - 新建落库带 `specKey` + 版本快照带 `spec_key`；
  - 返单/复制 `spec_key` 跟着走；
  - 导出正文按类目归位（3 伞头 / 2 伞布逐行断言）、固定格空着也要印；

  - 迁移与 schema 都有这一列。

- `apps/web/test/sales-order-material-extra.test.tsx`（+2）：伞头填 3 款、伞布 2 款、删一款后

## 8. 非目标

- 原有的 18 个固定类目**不增不减不改名**（用户要的是「在现有基础上」加款，不是改类目表）；
- 「其它」自由类目区行为不变（含物料引用、缩略图、带图导出）；
- BOM、采购、生产侧不感知 `spec_key`：它只影响销售单的工艺单表样。
