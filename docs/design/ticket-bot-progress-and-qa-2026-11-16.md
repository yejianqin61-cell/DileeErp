# 飞书工单机器人：主动进度同步 + 非需求问答

日期：2026-11-16｜版本：1.1｜状态：**已实施并验证**｜类型：设计

上游：[Agent 应用层架构](agent-application-layer-architecture-2026-11-14.md)（v1.1，已实施）。

## 0. 这两条要求怎么来的

2026-11-15 10:51（用户本地时间），用户在真实群里 @ 机器人：

> @迪礼顾问 汇报T-0007进度

机器人回：

> 这条我还不够开工，麻烦补两点：1. 你希望它变成什么样（例如：应该按单号倒序）

又发一条「@迪礼顾问 针对工单T-0007，汇报进度」，得到同一句话。

而事实是：**T-0007 正在跑，14 分 43 秒后成功产出**（`git log`：`2ede7e51 fix(production): 修复新建领料单物料下拉被表格裁切无法选择`）。
用户在那 14 分钟里看不到任何过程信息，问一下还被当成「需求没写清楚」挡回来。

用户 2026-11-16 12:23 提两条要求：

1. **飞书的 agent 能主动同步施工进度。**
2. **Agent 能理解 @它的信息，非需求类的询问，也要有能力进行回答。**

## 1. 现场证据（服务器 `/opt/dilee/agent/tickets`）

| 工单 | 原话 | 旧行为 | 应该的行为 |
|---|---|---|---|
| T-0007 | 「针对新建领料单页面，物料明细表单，物料选择的下拉列表…请你排查」 | 正常建单、跑 883 秒、成功 | 不变 |
| T-0008 | 「汇报T-0007进度」 | 判 needs_info，回「你希望它变成什么样」 | 直接答：施工中/已用 6 分钟/当前在改什么 |
| T-0009 | 「针对工单T-0007，汇报进度」 | 同上 | 同上 |
| T-0006 | 「你好」 | 判 needs_info | 回招呼，说明能干什么 |
| T-0010 | 「卧槽你特么是傻逼吗」 | 判 needs_info | 平静接住，请他说现象；不建单 |
| T-0011 | 「部署」 | 判 needs_info | 如实说部署通道还没接通，并列出待部署单 |

**代价**：T-0008/T-0009 不仅没答上，还白占了两个工单号；用户情绪从「问进度」升级到 T-0010。

## 2. 根因

`coordinator.handle()` 里只有两条分支：**回复卡片 = 追加**，**其余 = 新需求**。
「是不是在问你事情」从来没被判断过。分诊（`triage.ts`）只回答「这条需求能不能开工」，
对「这不是需求」的输入，它只能给出「不够开工」——语义上正确，行为上完全错。

所以缺的不是话术，是**意图层**。

## 3. 设计

### 3.1 消息先分意图，需求才进工单

在 `coordinator.handle()` 最前面加意图判定（`intent.ts`，纯函数）：

| 意图 | 判定（命中即停） | 行为 | 建单 |
|---|---|---|---|
| `status` | 进度/进展/状态/到哪/好了没/改好了/跑完了/还在跑/还要多久/卡住/失败了吗/结果/汇报 | 用本地事实回答 | 否 |
| `command` | 整句只有 部署/上线/发布/回滚/重启/停 | 如实说明与建议 | 否 |
| `chitchat` | 招呼/致谢/确认/身份询问/情绪话 | 短答 + 能干什么 | 否 |
| `question` | 请问/怎么/如何/为什么/是什么/在哪/有没有/支不支持/吗？… | 带上下文的模型回答 | 否 |
| `requirement` | 以上都不中（**默认**） | 走原流程：分诊 → 建单 → 跑 DSH | 是 |

判定顺序刻意把 `status` 放第一：`改好了吗` 同时含「改」和「好了没」，
按需求处理会把一句询问变成一次改代码。反过来，`把显示改成按单号倒序` 不含状态词，
落回 `requirement`，行为不变。

**默认是需求**，不是问答：这套系统的本职是改代码，把不认识的输入当需求，
最坏是问一句「你希望它变成什么样」；当问答处理则会让真实需求石沉大海。

### 3.2 进度查询：本地事实，不调模型

进度是可枚举的事实（状态、已用时长、当前阶段、工具调用数、子 Agent 数、上次结论），
用模型回答只会引入编造风险，且要等几秒。所以 `progress.ts` 直接拼文本：

```text
T-0007｜施工中，已用 6 分 32 秒
当前：正在修改代码（apps/web/app/production/…）
过程：工具调用 23 次，其中派发子 Agent 1 次
原话：针对新建领料单页面…
```

状态不同文案不同：`queued`（前面还有 N 单）、`building`（上面）、`gated`（已完成待部署 + 结论）、
`failed`（失败原因）、`needs_info`（还缺什么，怎么补）。没给票号时列出在用与最近完成的单。

### 3.3 其它询问：带工单上下文的模型回答

`answerer.ts` 直接调 DeepSeek `chat/completions`，**不占 DSH 车道**：

- 2 核机器上 DSH 一次 run 5–15 分钟，让一句「你是谁」排队 15 分钟不可接受；
- 问答不产生产出，不需要沙箱、会话、子 Agent。

system prompt 里给的事实（全部来自本地，不编）：
- 角色与边界：只答迪礼 ERP 维护相关；不承诺部署；不臆造功能细节；
- 模块清单（销售/采购/生产/质检/仓库/财务/人事/报表/补货）；
- 最近 8 张工单：票号、状态、原话前 60 字、结论前 80 字；
- 输出约束：中文、≤200 字、不用 Markdown 表格、不确定就说「需要查/改可以建单」。

模型调用失败（无 key / 超时 / 5xx）→ 兜底话术 + 当前工单概览，绝不静默。

### 3.4 主动同步施工进度

三个通道，频率不同：

| 通道 | 时机 | 内容 |
|---|---|---|
| 卡片原地更新 | 阶段变化或每 20 秒 | 标题「施工中｜T-0007」；已用、阶段、工具数、子 Agent、最近动作 |
| 群内进度播报（回复原消息） | 开工时、进入「验证/收尾」时、之后每 5 分钟 | 一行：`T-0007 施工中 8 分 12 秒：已改 3 个文件，工具调用 31 次` |
| 结果卡片 | run 结束 | 沿用现有绿/红/紫卡，补「已用时长」 |

为什么不把事件逐条刷群：一次 run 几十个事件，会把群刷爆（架构文档 §7 已定）。
只播报**阶段**与**心跳**，两者都是用户真正想知道的东西。

事件 → 阶段的映射（`progress.ts`，纯函数，可回归）：

| 事件 | 阶段 |
|---|---|
| `session` | 开工 |
| `tool_call` 名含 read/grep/glob/ls | 读代码 |
| `tool_call` 名含 edit/write/patch | 改代码 |
| `tool_call` 名含 bash/shell/exec | 跑命令/验证 |
| `tool_call` 名含 subagent/workflow | 派发子 Agent |
| `final` | 收尾 |

进度写入工单（`ticket-store.progress`），**进程被杀后重启仍能回答「进度如何」**。

### 3.5 排队也要可见

建单时卡片写明「前面还有 N 张单」；轮到自己开工时立刻播报一次。
当前单车道，一张改动单 5–15 分钟，排队位次是用户最缺的信息。

### 3.6 顺带修掉的三处

1. `askForMissing` 只有一项时仍说「补两点」——按项数变「补一点/补两点」。
2. `needs_info` 不建卡片，导致后续无法「回复卡片追加」——仍然只回文本，但话术里写明「直接发一条新的需求描述」，不让用户卡死。
3. 情绪话（骂人）不再当需求：接住情绪，给出下一步动作。

## 5. 不做什么

| 不做 | 理由 |
|---|---|
| 不接部署 | 与本需求无关；`gated` 仍是终点，如实告知用户 |
| 不按语义把消息归到旧工单 | 2026-11-14 拍板：只认回复卡片，误归单代价高于漏归单 |
| 不让问答走 DSH | 占单车道、吃 2 核、5 分钟起；答案本身不需要改代码 |
| 不逐条刷事件到群 | 会把群刷爆 |
