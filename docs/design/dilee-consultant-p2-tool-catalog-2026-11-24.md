## 2. 缺口判定：最近邻差异

### 2.1 问题

**列出自有，永远无法证明缺少。** 35 条「我有 X」加起来不等于「我没有 Y」。
让模型凭感觉说缺，它只会在三种情况下说缺：词不认识、试了一次 0 行、或者编。

「需要新增工具吗」等价于「现有工具答不了这个问题吗」。让模型从抽象分类里**生成**这个判断很难，
也没法核对；让它在具体候选里**辨认**最接近的一个并说出差在哪，容易得多，且每一项都能对照真源核对。

### 2.2 运行时：模型报「最近邻 + 差什么」

新增工具 `report_gap`，参数全部结构化：

```
report_gap {
  nearest_operation: "list_low_stock_materials",
  missing: "group_by" | "filter" | "metric" | "time_series" | "object",
  missing_detail: "按仓库分组",
  missing_param?: "q" | "status" | "customer_q" | "product_q" | "from" | "to",
  needed_fields?: ["<Prisma 模型>.<字段>", ...]
}
```

- `missing` 是封闭枚举，取值穷举如上；`object` 表示「现有工具都不以这个对象为主体」。
- `missing_detail` 是短语，不是用户原话 —— 与 prompt-builder 的既有纪律一致。
- `missing_param` 可选，只在缺某个筛选参数时填；取值是各条目 `accepts` 的并集去掉 `order_ref` 与 `page`。
  没有它，第 2 条核对无从比对。这个字段没有经过实验。
- `needed_fields` 可选，只作线索。工具描述里写明格式 `<Prisma 模型>.<字段>` 并给一个例子；
  对不上 schema 的项不导致驳回（§2.3 第 3 条）。

### 2.3 代码核对（不可省）

编排层收到 `report_gap` 后逐条核对。第 1、2、4 条不过即驳回，第 3 条只做标注；**驳回不计入失败预算**：

| # | 核对 | 真源 | 不过时 |
|---|---|---|---|
| 1 | `nearest_operation` 存在且当前档位可见 | `TOOL_CAPABILITIES` | 回可用 operation 列表 |
| 2 | 填了 `missing_param`，而该 operation 其实接受它 | L2 条目的机器可读参数清单（§3.1 `accepts`） | 回该条目原文，让模型改用它 |
| 3 | `needed_fields` 逐项是否存在 | Prisma DMMF | **不驳回**；存在的留在 `needed_fields`，其余移到 `unverified_fields` |
| 4 | 最近邻本轮成功执行过且每次都是 0 行 | 本轮 tool 结果 | 判为缺数据，不进缺口路径 |

第 4 条是规则，不交给模型判断：最近邻查到 0 行不算缺工具。只看最近邻，别的检索落空不挡住之后的缺口。

第 3 条不驳回有两个原因：目录从不向模型展示 Prisma 模型名，它只能猜；实验里 C 组填了 115 个字段名，
符合 `模型.字段` 格式的是 0 个（§2.8）。字段到底有没有，由开工前的探针对着真实 schema 判（§2.5）。

第 2 条的「反向教」沿用 v1.0 的判断：P1 实测模型能吃进 tool 错误并自纠（7/7），
比改 prompt 措辞有效。误报的代价是一次模型往返，不是一张白跑的工单。

### 2.4 归并：按最近邻与差异类型去重

去重键 = `(nearest_operation, missing)`，**不含差异短语，不按用户原句**。
每次声明的 `missing_detail` 原样追加到候选上，供人看和探针用。

v1.1 的键含归一化后的短语。实验里 C 组对 10 道真缺口题报了 28 次，短语没有两次相同，
含短语得 28 个键，去掉短语得 12 个键（§2.8）。

代价有两面。同一缺口仍可能因模型选了不同最近邻或差异类型而分成两条（实验里 10 题中有 2 题如此），
门槛会因此晚一些达到。反过来，同一最近邻、同一差异类型下的两个不同缺口会并成一条，
例如「按仓库分组」与「按供应商分组」；题集里没有这种组合，实验没有测到。
后者靠候选上保留的全部短语在开工前区分。

### 2.5 开工前：可行性探针（P3 之后接通）

误判真正贵的地方是白跑一次构建与部署，所以**精确度放在开工前保证，不放在问答时保证**。
工单第一步不写正式工具，只让 Builder 写一条只读查询在只读库上跑一次：

| 探针结果 | 判定 | 去向 |
|---|---|---|
| 字段齐、查出合理数据 | 缺形状，真缺口 | 进入正式 Builder → Validator |
| 字段齐、查出 0 行 | 缺数据 | 转业务补录，关单 |
| 查询所需字段在 schema 里不存在 | 超出系统范围 / 需新业务模块 | 转人工，不自动施工 |
| 现有某个 operation 其实能答 | 误报 | 关单；该问法进黄金集，并补进对应 L2 条目的问句形状 |

最后一行让目录越用越准：每次误报都给 L2 多一种问法。

### 2.6 闭合矩阵为什么降级

v1.0 设计用四条轴（对象 / 度量 / 粒度 / 时间基准）的笛卡尔积判缺口。复核后发现五处不成立：

1. **模块声明只给各轴取值的集合，推不出组合。**「金额在、跨单行集也在」不等于有一个 operation 给跨单金额。
   能可靠证明的只剩「某轴值整体为 0」（趋势、科目），这等于一份四个维度的否定清单。
2. **坐标由模型自己判。** 代码能核「这个坐标有没有覆盖」，核不了「这句话该不该判成这个坐标」；
   模糊只是挪了一层。
3. **轴不够描述覆盖。**「按供应商汇总」与「按物料汇总」都是「分组汇总」，但 `list_low_stock_materials`
   只按物料。复核会把真缺口当已覆盖驳回。
4. **多数空格子没有意义**（科目 × 进度 × 趋势），「空格子 = 缺口、可数」不成立，仍要人筛。
5. **现有数据里没有它要解决的失败。** P0/P1 的失败都是入口缺失、句柄丢失、检索词问题，
   没有一条是「模型没认出这是缺口」。

**保留的部分**：四条轴作为写 L2 条目「边界」字段时的检查清单，逐轴过一遍，避免漏写否定项。
轴不进模型推理，不进代码判定。

### 2.7 对照实验（决定 D-4 的最终形态）

在目录（阶段 1）完成后、写缺口代码前跑，离线进行，不改编排器：

| 项 | 内容 |
|---|---|
| 题集 | 约 30 题：真缺口 10（趋势、科目、按供应商汇总、计数等）；诱饵 10（现有工具能答，但换了问法）；缺数据 5（有入口、库里 0 行）；无结构 5（「这张单为什么卡住」）。每题标注期望判定与期望最近邻，**标注需用户审** |
| A 组 | 目录 + 否定清单；`report_gap` 只收自由文本理由 |
| B 组 | A + 四轴模块声明；`report_gap` 收四轴坐标（坐标按 v1.0 §2.3 初稿标注，见提交 `ebf2cce`；仅实验用，不入注册表） |
| C 组 | A + 本节方案；`report_gap` 收最近邻差异 |
| 方式 | `deepseek-chat`，每题每组 3 次，约 270 次调用；假 `report_gap` 只记录不放行 |
| 指标 | 真缺口召回率；诱饵误报率；缺数据误报率；判出缺口前的工具调用次数；同题三次结论一致率；最近邻与标注一致率 |

判据：

- C 达到底线（真缺口召回 ≥ 80%、诱饵误报 ≤ 10%）且不明显劣于 B → **采用 C**，即本节方案。
- B 在召回与误报上**同时**比 C 好 10 个百分点以上 → 重开闭合矩阵，回到 v1.0 §2（提交 `ebf2cce`）并补用户审坐标。
- 三组都达不到底线 → **停在观测层**，缺口只记日志、不进候选，前端阶段照常推进。

### 2.8 实验结果（2026-11-25）

[实验报告](../review/agent-gap-experiment-2026-11-25.md)：270 次运行，0 出错，判据结果 **采用 C**。

| 指标 | A | B | C |
|---|---|---|---|
| 真缺口召回 | 24/30 | 29/30 | 28/30 |
| 诱饵误报 | 5/30 | 0/30 | 1/30 |
| 缺数据误报 | 0/15 | 0/15 | 0/15 |

领域工具由桩应答固定的示例值，A、C 的误报理由都提到拿到的是占位数据，所以误报数偏高于真实数据下应有的值；
真实数据下的误报率没有测过。实验也只用了一个模型。

## 3. 工具注册表分层

| 层 | 内容 | 何时进 prompt |
|---|---|---|
| **L1 模块** | 模块名 + 一句「管什么」+ operation 数 + 否定清单 | **常驻**，约 10 行 / 150 token |
| **L2 operation** | 五字段条目 + 机器可读参数清单（见 §3.1） | **按需展开**，经 `describe_module` |

### 3.1 L2 条目五个字段，缺一个就判不准

| 字段 | 例 | 缺了会怎样 |
|---|---|---|
| `name` | `list_overdue_arrivals` | 模型调不了 |
| 问句形状 | 「列出预期到货日已过、且未全部到货的采购单」 | 只有名字，模型不知道它答什么问题 |
| 输入要求 | 无需单据根；可选 `page` | 模型会瞎传 `order_no`，撞参数错误 |
| 粒度 + 输出 | 跨单行集；每行含单号/供应商/预期日/逾期天数 | 模型不知道拿到的是明细还是汇总 |
| 边界（不覆盖） | 不按供应商分组、不区分是否已质检 | **这一栏最关键，且现实里几乎总被省略**；按 §2.6 的四轴逐轴过一遍再写 |

外加两项机器字段（不必全文给模型看，但代码要读）：

- `status`：`implemented` / `registered_not_implemented`。后者是白送的缺口信号，且可被代码证实（是否允许见 §10）。
- `accepts`：该 operation 接受的参数名与可选的筛选、分组维度。§2.3 第 2 条核对靠它；
  现在这份信息散在各执行器的校验里，P2 要把它收进注册表。

### 3.2 单一真源

catalog **从 `TOOL_CAPABILITIES` 生成**，不另手写一份。
双向核对测试：每个 capability 必有 catalog 条目；每个 catalog 条目必有 capability。
少一边就红 —— P1 已用同一模式盯住前端标签（32→35 那次靠它拦住）。

### 3.3 候选集接口

「给模型哪些候选工具」收成一个函数：

```ts
candidateOperations(question: string, tier: AgentAccessLevel): CatalogEntry[]
```

现在的实现：按档位过滤后**返回全部**条目，`question` 不参与。
`describe_module`、`report_gap` 的核对、实验脚本都经由它取候选。以后要上检索（§5），只换这个函数的实现。

## 4. 缺口 → 工单

### 4.1 缺口分两种，混成一个工单会让 tickbot 白跑

| 类型 | 判据 | 该谁修 |
|---|---|---|
| **缺形状** | 数据在库里，但没有这个投影的入口 | tickbot 写一条只读查询（通常很便宜） |
| **缺数据** | 入口存在，但库里没有这份数据 | 业务补录，不是代码问题 |

活例：`finance-positive-reconciliation` 调到了 `get_reconciliations`，但库里无对账记录。
**入口是好的**；若当「缺工具」开工单，tickbot 跑一趟啥也改不出来。

运行时靠 §2.3 第 4 条挡住最常见的缺数据；漏网的由 §2.5 探针兜住。

### 4.2 从声明到工单

1. **声明**：模型调 `report_gap`（§2.2）。
2. **核对**：编排层按 §2.3 核对，驳回项回传原文，字段项只做标注。
3. **候选**：通过的声明按 §2.4 的键归并进候选表，记出现次数。
4. **升级**：同一个键累计达到门槛才升为待开工（门槛见 §10）。
5. **开工**：经桥接建 `tool_gap` 工单，第一步是 §2.5 探针。P2 阶段桥接未建，到第 4 步为止。

工单正文只有最近邻、差异类型、历次差异短语与两组字段（已核对、未核对），**没有用户原话**。

## 5. RAG：暂不上，预留接口

### 5.1 为什么现在不上

1. **规模用不上。** 35 个 operation 的 L2 全量约 400–500 token，整份给模型比检索 top-k 更准。
2. **检索会放大误报。** 缺口判断的前提是模型看得到「最接近的那个」。检索漏掉它，模型就会报缺工具；
   判断准确率的上限变成检索召回率。全量列出时这类错误不存在。
3. **基础设施成本。** 要另找中文 embedding（服务或本地模型），建向量库，维护索引更新；
   2 核服务器上不划算。
4. **与 D-1 冲突的那一种不做。** 检索历史答案或查询结果等于把工具事实带进上下文。

### 5.2 两种 RAG 的触发条件

| 场景 | 触发条件 | 检索什么 |
|---|---|---|
| **工具检索** | operation 超过约 100 个，或 L2 总量超过约 2k token；或 §5.3 的漂移率持续升高 | L2 条目（问句形状 + 边界） |
| **案例检索** | P3 之后运行日志积累起来 | 历史「问句 → 成功调用的 operation 链」，**只取映射，不取结果** |

工具检索可能比预想来得早：`tool_gap` 工单会自动造工具，数量会持续增长。

案例检索对缺口判断最直接（相似问题以前用 X 答成功过，就不是缺口），且不一定要向量：
黄金集作种子，BM25 或 Postgres `pg_trgm` 做相似匹配即可起步。

### 5.3 漂移观测

记录一项指标：`report_gap` 报的 `nearest_operation` 与事后核定的应用工具不一致的比例
（黄金集里的缺口题有标注，可直接算；线上由 §2.5 探针的「误报」行回填）。
这个比例持续升高，说明条目多到模型看不过来，是上工具检索的信号。

## 7. 两个必须提前说清的约束

### 7.1 会话权威：服务端权威 + 本地缓存（已获拍板）

chat-demo 的会话只活在浏览器 IndexedDB，换设备即丢、服务端无记录。我们有三个它没有的硬需求：

1. 工单桥接要让服务端知道「这个问题对应哪个 run」；
2. 财务档位被降权后，历史 full 答案不得还能从本地读出来；
3. 运维要能回答「用户到底问过什么」。

所以：**服务端事件日志仍是唯一真源，IndexedDB 只做缓存 + 草稿 + 分支。**
首屏从本地秒开 → 后台拉会话快照覆盖对账，进行中的轮次从快照游标续接（不加后端接口）。
财务档轮次不写本地，读取处仍按当前档位过滤。

### 7.2 注释政策（用户 2026-11-22 拍板「全量删除，禁止再写」）

| 类别 | 例 | 处理 |
|---|---|---|
| 散文注释 | `// 单号是业务自己编的…` | **删除** |
| 功能性指令 | `// eslint-disable-next-line`、`// @ts-expect-error`、`/// <reference>`、shebang | **保留**，进白名单 |
| **许可头** | 移植进来的 chat-demo 文件（MIT） | **必须保留**；删掉是法律问题 |
| Prisma `///` | `schema.prisma` | 单独一轮，不掺在 TS 清理里 |

`scripts/strip-comments.mjs` 用 TypeScript Compiler API 按语法删，**不用正则**（正则会打坏 URL、
正则字面量、JSX 文本、模板字符串）。

存量清理放在 P6；**P2 新写和改动的代码从现在起就不写散文注释**，免得 P6 守卫一上线就红。

## 9. 成本

| 项 | 量 |
|---|---|
| L1 常驻 | 约 10 行 / 150 token |
| L2 展开一次 | 35 条 × 5 字段 ≈ 400–500 token，仅按需 |
| 对照实验 | 约 30 题 × 3 组 × 3 次 ≈ 270 次 `deepseek-chat` 调用；题集标注需用户审 |
| 误报缺口 | 一次模型往返（代码核对驳回） |
| 真缺口 | 一条候选；达门槛后一张 `tool_gap` 工单，先跑探针再施工 |

对照现状：每轮都带着 6 行模糊描述 + 13 个共用参数说明，模型永远看不到「哪个 operation 答哪类问」。
花 150 token 换掉试错往返，`model_steps` 从 3 往下走是大概率事件。
