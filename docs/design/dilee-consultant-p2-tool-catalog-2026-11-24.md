## 2. 缺口判定：闭合矩阵

### 2.1 问题

**列出自有，永远无法证明缺少。** 35 条「我有 X」加起来不等于「我没有 Y」。
让模型凭感觉说缺，它只会在三种情况下说缺：词不认识、试了一次 0 行、或者编。

### 2.2 解法

把「用户能问什么」压成一个**有限的笛卡尔积**。每个模块声明自己在四条轴上有哪些取值；
**空格子就是缺口，可数、可核对**。

四条轴，取值**穷举**（不是举例）：

| 轴 | 取值集合 |
|---|---|
| 对象 | 单据 / 物料 / 客户 / 供应商 / 员工 / 科目 |
| 度量 | 定位 / 数量 / 金额 / 状态 / 进度 / 时间 / 差异 |
| 粒度 | 单张明细（需单据根）/ 跨单行集 / 分组汇总 / 计数 |
| 时间基准 | 当前快照 / 区间 / 趋势 |

**矩阵不展开。** 6 模块 × 4 轴 × 约 5 值 ≈ 每模块 20 个短词，全表约 120 token。
若展开成 500 个格子，没人读得完，方案即失败。模型用交叉的方式自己推。

### 2.3 用现有 35 个 operation 落坐标（初稿，待审）

| 粒度 | 数量 | 谁 |
|---|---|---|
| 单张明细（需单据根） | 29 | 绝大多数 `get_*` |
| 跨单行集（无根） | 4 | `search_documents`、`search_orders`、`list_documents`、`list_overdue_arrivals` |
| 分组汇总 | 2 | `list_low_stock_materials`（按物料聚合）、`get_raw_material_balance`（按物料+单位聚合） |
| 计数 | 0 | — |

其余轴的空洞：

| 轴值 | 覆盖 |
|---|---|
| 时间基准 = **趋势** | **0 个 operation** |
| 对象 = **科目** | **0 个直接入口** |
| 对象 = **供应商**（作主体，非订单附属） | 只有财务的应付/付款，且需单据根、限 full 档 |
| 对象 = **员工** | 只有 `get_order_payroll`，需根、限 full 档 |
| 度量 = **差异**（对账差异、库存差异） | 只有 `get_reconciliations`，需根 |

**这些空洞今天就存在，但没有任何地方写出来。** 只有等用户问到、模型试错失败、人工排查才发现。

### 2.4 模型如何「不用试就知道缺」

示例：用户问「按供应商看本月采购金额，哪些供应商涨了」

模型落坐标：`对象=供应商 · 度量=金额 · 粒度=分组汇总 · 时间基准=趋势`

对照声明：

- 采购模块粒度集合 = {单张明细, 跨单行集}，**无分组汇总**
- 全局时间基准里 **趋势一个 operation 都没有**

模型立刻知道这条问法缺两道，调 `request_capability`，参数带上坐标。
这是**可被代码复核**的结构化声明，不是「我感觉缺」。

### 2.5 每个模块的声明形状（模型看到的样子）

```
采购模块 · operations 5 个
  对象：单据
  度量：定位、数量、金额、状态、时间
  粒度：单张明细（需单据根）、跨单行集
  时间：当前快照、区间
  不支持：分组汇总、趋势、写操作
```

### 2.6 三条边界

1. **矩阵覆盖不到无结构问题**（「这张单为什么卡住」）。所以每模块必须另有一行**显式否定清单**。
2. **轴值可能不全**。要先分清「全轴都不匹配」（该登记新轴值）与「轴值缺一格」（该造工具），
   两者工单类型不同。
3. **坐标赋值是域语义**，须由用户审。否则矩阵一开始就错，模型照错边界判缺口。

## 3. 工具注册表分层

| 层 | 内容 | 何时进 prompt |
|---|---|---|
| **L1 模块** | 模块名 + 一句「管什么」+ operation 数 + 四轴声明 + 否定清单 | **常驻**，约 10 行 / 150 token |
| **L2 operation** | 五字段条目（见 §3.1） | **按需展开**，经 `describe_module` |

### 3.1 L2 条目五个字段，缺一个就判不准

| 字段 | 例 | 缺了会怎样 |
|---|---|---|
| `name` | `list_overdue_arrivals` | 模型调不了 |
| 问句形状 | 「列出预期到货日已过、且未全部到货的采购单」 | 只有名字，模型不知道它答什么问题 |
| 输入要求 | 无需单据根；可选 `page` | 模型会瞎传 `order_no`，撞参数错误 |
| 粒度 + 输出 | 跨单行集；每行含单号/供应商/预期日/逾期天数 | 模型不知道拿到的是明细还是汇总 |
| 边界（不覆盖） | 不按供应商分组、不区分是否已质检 | **这一栏最关键，且现实里几乎总被省略** |

外加机器可见的 `status`：`implemented` / **`registered_not_implemented`**。
后者是白送的缺口信号：模型能说「登记了但没实现」，比「我认为缺失」强，**且可被代码证实**。

### 3.2 单一真源

catalog **从 `TOOL_CAPABILITIES` 生成**，不另手写一份。
双向核对测试：每个 capability 必有 catalog 条目；每个 catalog 条目必有 capability。
少一边就红 —— P1 已用同一模式盯住前端标签（32→35 那次靠它拦住）。

## 4. 缺口 → 工单

### 4.1 缺口分两种，混成一个工单会让 tickbot 白跑

| 类型 | 判据 | 该谁修 |
|---|---|---|
| **缺形状** | 数据在库里，但没有这个投影的入口 | tickbot 写一条只读查询（通常很便宜） |
| **缺数据** | 入口存在，但库里没有这份数据 | 业务补录，不是代码问题 |

活例：`finance-positive-reconciliation` 调到了 `get_reconciliations`，但库里无对账记录。
**入口是好的**；若当「缺工具」开工单，tickbot 跑一趟啥也改不出来。

### 4.2 触发 run 的三层

1. **模型声明**：调新增工具 `request_capability`，参数是结构化
   `{module, object, measure, granularity, timeBasis, question_shape, reason}`。
   **不接受用户原话当参数** —— 与 prompt-builder 的既有纪律一致。
2. **代码复核**（不可省）：编排层拿坐标去注册表查；若存在覆盖该形状的条目，
   **不是失败**，而是把那条目原文回给模型让它改用它。误报的代价是一次模型往返，不是一张白跑工单。
3. **反向教**：驳回时把覆盖条目塞回 tool 消息。P1 实测模型能吃进 tool 错误并自纠（7/7），
   这比改 prompt 措辞有效。

### 4.3 去重

按 `(module, 坐标)` 归并，**不按用户原句**。否则十个人问同一句会开十张单。

### 4.4 触发门槛（需拍板，见 §9）

「试了一次 0 行」**不能**触发 `request_capability` —— 那属于缺数据。
只在「矩阵穷举完仍无格可落」时触发。

## 6. 两个必须提前说清的约束

### 6.1 会话权威：服务端权威 + 本地缓存（已获拍板）

chat-demo 的会话只活在浏览器 IndexedDB，换设备即丢、服务端无记录。我们有三个它没有的硬需求：

1. 工单桥接要让服务端知道「这个问题对应哪个 run」；
2. 财务档位被降权后，历史 full 答案不得还能从本地读出来；
3. 运维要能回答「用户到底问过什么」。

所以：**服务端事件日志仍是唯一真源，IndexedDB 只做缓存 + 草稿 + 分支。**
首屏从本地秒开 → 后台按游标补差量。

### 6.2 注释政策（用户 2026-11-22 拍板「全量删除，禁止再写」）

| 类别 | 例 | 处理 |
|---|---|---|
| 散文注释 | `// 单号是业务自己编的…` | **删除** |
| 功能性指令 | `// eslint-disable-next-line`、`// @ts-expect-error`、`/// <reference>`、shebang | **保留**，进白名单 |
| **许可头** | 移植进来的 chat-demo 文件（MIT） | **必须保留**；删掉是法律问题 |
| Prisma `///` | `schema.prisma` | 单独一轮，不掺在 TS 清理里 |

`scripts/strip-comments.mjs` 用 TypeScript Compiler API 按语法删，**不用正则**（正则会打坏 URL、
正则字面量、JSX 文本、模板字符串）。

## 8. 成本

| 项 | 量 |
|---|---|
| L1 常驻 | 约 10 行 / 150 token |
| L2 展开一次 | 35 条 × 5 字段 ≈ 400–500 token，仅按需 |
| 误报缺口 | 一次模型往返（代码复核驳回） |
| 真缺口 | 一张 `tool_gap` 工单，结构化需求已填好 |

对照现状：每轮都带着 6 行模糊描述 + 13 个共用参数说明，模型永远看不到「哪个 operation 答哪类问」。
花 150 token 换掉试错往返，`model_steps` 从 3 往下走是大概率事件。

## 9. 未定与待拍板

1. **四条轴的取值集合由谁定。** 建议用现有 35 个 operation 反推初稿（它们已隐含这些轴），
   用户审一遍定稿；之后允许 tickbot 按工单扩充**轴值**，但**轴本身不经工单改动**。
2. **`registered_not_implemented` 中间态是否允许。** 允许则缺口信号更强，但注册表会出现
   「有名字没实现」的项。
3. **缺口的工单自动开工，还是先攒候选。** 用户已拍板「全自动上线」，但缺口误判一次就是白跑
   一次构建+部署。建议同一坐标反复出现（≥3 次）再自动开单。
