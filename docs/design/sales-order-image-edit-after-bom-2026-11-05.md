# 建立 BOM 之后，销售单还能编辑图片（2026-11-05 第二轮）

## 1. 用户反馈与澄清

> 「现在，用户反馈，希望在销售单确认后，在系统的 BOM 表中也可以编辑图片。
> 而且当前换图和删除图片都不能实现」

追问后澄清：

> 「诶不对不对，不是在 BOM 表里面，而是建立了 BOM 表之后，还能编辑销售单中的图片」

所以这不是「BOM 表加图片字段」的需求，而是：**销售单建了 BOM 之后，行图片的换图/删除存不上**。

## 2. 根因（一个，不是两个）

`apps/web/components/sales/sales-order-editor.tsx` 保存时把**整份表单**发上去：11 个核心字段
（品名/规格/数量/单位/币种/单价/金额/税率/结算价/应收金额/本币金额）+ 37 个细化标量。
这是必要的 —— 「空串 = 清除这一格」必须表达得出来，前端不能只发"改过的键"。

而服务端守卫的判定是：

```ts
const coreFieldsChanged = current.status === "confirmed" && coreFields.some((field) => input[field] !== undefined);
```

即「请求里带了这个键」= 改核心字段。于是：

1. 已确认单只要**有 BOM（非空壳）**，任何一次界面保存都会命中 `SALES_ORDER_CORE_FIELDS_LOCKED`；
2. **只改了图片**（`slot_images` / 行上 `image_ids`）的保存也被算成「改核心字段」→ 被挡住；
3. 于是换图/删图在界面上做了、点保存却存不上 —— 用户看到的就是「换图和删除图片都不能实现」。

顺带修掉的同类问题：**改订单号**（编辑器同样整份回传）在已确认 + 有 BOM 的单上也会被这道锁误挡，
而 2026-09-30 的口径是「改号任何时候都行」（它不动任何单的数量与金额）。以前只是测试直接调
service 传单键，没走到这条真实路径。

## 3. 修法

### 3.1 服务端：核心字段锁按**值**判定，不按**键**

`apps/api/src/modules/sales/sales-orders.service.ts` 新增纯函数：

```ts
coreFieldsActuallyChanged(current, input): boolean
```

- 只比 `CORE_LOCK_FIELDS` 这 11 个字段；
- 文本字段：`null` / `undefined` / 空串同义、首尾空白不算改动；
- Decimal 字段（数量/单价/金额/税率/结算价/应收/本币）：按 `Prisma.Decimal` 规范写法比较，
  `"100"` 与 `"100.0000"` 是同一个值 —— 不能因为编辑器回传的写法不同就当成"改了"；
- 请求里**没带**的字段直接跳过（`undefined` = 不动）。

`update()` 里：

```ts
const coreFieldsChanged = current.status === "confirmed" && coreFieldsActuallyChanged(current, input);
```

- 为假 → **完全跳过** BOM/采购/生产守卫（连下游计数查询都不发）；
- 为真 → 走原来的 `releaseEmptyShellBoms`：空壳 BOM 自动清理并放行、非空 BOM / 采购 / 生产事实照旧挡住，
  文案不变（说清挡路内容并指路【采购 → BOM表】）。

反向不放松：**真改了数量/单价/金额**的保存仍然被锁挡住（测试钉住 0.01 的单价改动也会被识别）。

### 3.2 前端：把「保存后生效」和「兜底图」说清楚

用户报的另一半「点按钮没反应」有两个界面层的误会来源，一并修：

1. **换图/上传成功没有提示**：原来只有失败才 toast。现在上传/换图成功都提示
   「第 N 张图片已上传/已换（保存销售单后生效）」—— 图片字节是即时上传的，但**挂在哪一行**是保存时整块提交的，
   不说这一句，用户刷新后发现没挂上会以为"没反应"。
2. **删掉行图后物料图立刻顶上来**：删掉这一行自己的图之后，如果这一行引用了物料、而物料清单里有图，
   兜底图会马上显示在同一格 —— 看起来像"删了还在"。现在兜底图带 `title`「引用的物料清单图片
   （不是这一行自己的图）」，删除提示也写明「若仍显示图片，那是引用的物料清单图」。

没有改：图片仍然要**保存后生效**（没有 DELETE 端点，保存末尾清理无引用图片，与 2026-11-04 的设计一致）；
已确认单改图**仍要填写修改原因**（这条业务规则不变）。

### 3.3 明确不做

- **不在 BOM 表里加图片编辑**（用户已澄清不是这个需求）；
- 不因为"要改图"就放开核心字段锁（数量/价格真的变了，下游 BOM/采购/生产仍必须先回退）；
- 不把图片改成"点一下立即落库"（会绕过版本快照与孤儿清理，且与其它字段的保存语义不一致）。

## 4. 测试

`apps/api/test/unit/sales-order-image-edit-after-bom.test.cjs`（5 例）：

1. 确认单 + 有明细 BOM + 11 个核心字段原值整份回传 + 只改图片 → 保存成功、版本 +1、图按 `slot_index` 落库，
   **且采购/生产/BOM 一次都不查**；
2. 同值不同写法（`100` vs `100.0000`、`null` vs 空串）不算改动；
3. 真改数量 → 仍 422 `SALES_ORDER_CORE_FIELDS_LOCKED`、一个字段都不写；
4. 只改单价 0.01 → 识别为真改动并挡住；
5. 纯函数口径（空值/空白/Decimal 写法/未传键）。

另外既有 `sales-order-empty-bom-release.test.cjs`（13 例）继续覆盖空壳 BOM 自动清理与采购/生产下游拦截，
全量 API 单测 **2830/2830**。

Web：上传/换图/删除的提示与兜底图 title 不影响载荷；既有编辑器测试（3 张上传/换图/删除、回填、载荷）全绿。
