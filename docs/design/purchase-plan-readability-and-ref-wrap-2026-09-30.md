## 二、逐件方案

### 1. 明细表里那一格**永远**显示这一行的物料/单位

用户说第 1 条前半句是自己看错了，所以**没有**动采购计划列表的列。但顺着这句话查出一个真实缺陷，
成本只有十来行，一并补掉（`components/procurement/plan-detail-sheet.tsx`）：

- **症状**：物料被停用 / 软删 / 改成成品之后就不在 `GET /materials` 里；单位被停用后不在
  `GET /units` 的可用项里。而 Radix 的 `SelectValue` **只在选项列表里找得到对应项时**才显示文字——
  找不到就退回占位符。于是计划里明明记着物料的那一格看起来是空的，像"这份计划漏买了这个部件"。
- **服务端其实已经兜过一次**：`purchase-plans.service.ts` 的 `get()` 写着
  `materialName: item.material?.name ?? snapshotName(item.materialSnapshot)`，并把
  `unitName` 也从快照兜回来 —— 前端不能把它丢掉。这与供应商那一格（停用/软删后仍用快照显示
  "当时记的是哪一家"）是同一条教训，前后端各踩过一次。
- **做法**：这一行的选项 = 物料池 + **这一行自己那个值**（`materialOptionsOf` / `unitOptionsOf`）。
  补进来的一项带 `disabled`：Radix 对**选中的项**即使 disabled 也会把它的文字放进触发框，
  所以名字显示得出来；但它选不到**别的行**上 —— 真选了服务端会以 `PURCHASE_PLAN_REFERENCE_NOT_FOUND`
  （"物料或单位不存在或已停用"）拒绝**整份计划**，那是个只有撞上才知道原因的错。

### 2. 明细表加高（行高与行内控件）

`.purchase-plan-sheet` 的密度是 2026-09-27 为"13 列一次展示、不横滑"调出来的（内边距 4px、
控件 30px、字号 11px）。用户现在要更容易看清：

| | 改前 | 改后 |
|---|---|---|
| 单元格内边距 | `4px 5px` | `8px 6px` |
| 行内输入/下拉高度 | `30px` | `34px` |
| 表格字号 | `11px` | `12px` |

行高由"内边距 + 控件高度"决定（表格没有写死 `height`），所以调大不需要碰别的东西；
**13 列的宽度总和仍然是 100%** —— 加高行不会把用户要的"不横滑"弄丢（`lib/purchase-plan-table.test.mjs` 盯着这两条）。

真实 Chromium 实测（1400px 宽的 `.purchase-plan-sheet`，一行 = 13 个真实单元格，改前用覆盖样式还原）：
**行高 45px → 53px**，表格横向溢出两者都是 0px。

### 3. 引用下拉的长文字换行（共用原语，影响面不止销售页）

- **为什么原来会"超出页面范围"**：弹层是 `left: 0; right: 0; overflow: auto`，而选项文字是个
  flex 项，最小宽度 = `min-content` —— 它既不换行也不收缩，于是弹层横向滚动，那行字被切在可视范围之外。
  引用下拉的 label 又是"编码 / 名称 规格 颜色"四段拼的（`materialOptionLabel`），长物料名必然撞上。
- **做法**：`.ui-searchable-select-option-text { min-width: 0; white-space: normal; overflow-wrap: anywhere; }`
  —— `min-width: 0` 让它能收缩，`overflow-wrap: anywhere` 让没有空格的编码/长英文也有断点
  （中文本来就能逐字断行）。弹层高度仍由 `max-height: 288px` 封顶，只是每项可能要占两行。
- **刻意不做省略号**：用户要的是**看全**，`text-overflow: ellipsis` 只是把"看不见"换个形式
  （`lib/searchable-select-wrap.test.mjs` 有一条反向断言钉着）。
- 这是**共用原语**上的改动：会计科目筛选、BOM 供应商、生产单候选、采购计划的新建都走它 ——
  统一在这里改，比在销售页另写一套好。

真实 Chromium 实测（320px 宽的弹层 + 一条超长物料 label，改前用覆盖样式还原）：

| | 改前 | 改后 |
|---|---|---|
| 选项列表的横向溢出 | **201px**（文字被切在可视范围之外，只能横向拖） | **0px** |
| 选项文字高度 | 17px（一行，超出部分看不见） | 34px（两行，看全） |

### 4. 采购计划下单 → 采购单：**已经是自动的**（核查结论，未改代码）

用户第 2 条是"检查"，结论是**不需要改动**，链路如下（三处都在同一个事务里）：

1. `POST /purchase-plans/:id/order`：勾选的行按供应商分组 → 交给采购单服务
   `createOrdersFromGroups(tx, merged, "ordered", user)`；
2. 同一个事务里按 `extension_data.purchase_plan_item_id` 回写计划行的 `purchase_order_item_id`
   （分成两次事务会留下"采购单已经建好、计划还显示未下单"的中间态 —— 那正是重复采购的入口）；
3. 落库状态是 **`ordered`（已下单）**，而 `GET /purchase-orders` 的列表范围
   （`LISTED_PURCHASE_STATUSES`）就是 `ordered / partially_arrived / arrived_complete` ——
   所以单子一定出现在采购单模块，计划行同时显示落到哪张 `PO-` 上，计划状态派生为
   部分下单 / 已完成。

**风险点只有一个**：落成 `draft` 的话，单子永远不进采购单列表，而界面上不会有任何报错。
所以新增的守卫断言的是**状态**而不是"接口被调用了"：
`purchase-plans-service.test.cjs` → `createdOrders.every(order => order.status === "ordered")`。

## 三、刻意不做

- **采购计划列表不加「采购物料」列**：用户明确说第 1 条前半句是看错了。要用的话是
  `list()` 的 `items` 里加物料名 + 一个会换行的单元格，随时可做。
- **收束下单预览里不列物料明细**：同上，等他确认。预览现在只有"供应商 · 行数 · 金额"。
- **采购单列表也不加「采购物料」列**：本轮没要求（采购单详情页里每个物料块是有的）。
- **不把"不在池里"的物料改成可再次选择**：那会让服务端整份计划被拒，属于把问题往后挪。
- **不为引用下拉单写一套省略号样式**：见 §二.3。
