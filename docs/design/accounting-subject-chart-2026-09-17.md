| 损益类 | 45 |

三条刻意的处理：

1. **科目名称照抄原文，不做"顺手修好"**：表里有 `销售- 办产地证`、`管理 -财产保险`、
   `货拉拉 物流费`、`管理 验厂费` 这类原表手误空格（与当初处理收支项目标签同一原则）。
   口径表就是财务手上的那张表，系统里的名字与它逐字一致才有意义。
2. **`balanceDirection`（借/贷）保留**：本期不参与任何计算，但凭证/账簿将来要靠它判断科目的
   自然余额方向；现在丢掉，以后要再问一次财务。只存不显示成业务列（列表页有这一列，只读）。
3. **`期初余额 / 借方累计 / 贷方累计 / 年初余额` 四列不采纳**：它们是**账簿数据**（而且样本里全是 0），
   不是科目定义。建账是另一件事，混进科目表会让「科目表」变成「科目余额表」。

科目常量以 `apps/api/src/modules/finance/accounting-subject-catalog.ts` 为**唯一来源**，
迁移 SQL 与 `prisma/seed.ts` 都从它生成（生成脚本见 `docs/task/0917-accounting-subject.md` §4），
避免「老库升级」与「新库初始化」种出不同的两张表 —— 收支项目字典当年就踩过这个坑。

## 3. 数据模型

```prisma
model AccountingSubject {
  id               String    @id @default(uuid()) @db.Uuid
  category         String    @db.VarChar(30)   // 分类 = 科目类别
  name             String    @db.VarChar(100)  // 项目 = 科目名称
  balanceDirection String?   @map("balance_direction") @db.VarChar(4)
  sortOrder        Int       @default(0) @map("sort_order")
  isActive         Boolean   @default(true) @map("is_active")
  // …审计列（createdAt/By、updatedAt/By、deletedAt/By）
  @@unique([category, name])
  @@index([category, sortOrder])
  @@map("accounting_subjects")
}
```

**为什么不做成 `dictionary_items` 的一种字典类型**：字典项是平表，科目表多一个「分类」维度；
硬加一列 `category` 会让所有字典都背上一个只有科目表才有意义的字段。用户也明说了合并后的东西
叫「会计科目」而不是「字典项」。

**为什么唯一键是 `(category, name)` 而不是 `name`**：科目表里同一分类下不允许重名（迁移/seed 靠它幂等），
但不同分类下允许同名明细科目 —— 现在不必，将来要时也不用再迁移一次。

**为什么只停用不删除**（宪法《Configurable Business Categories》）：已被流水/单据引用的科目
必须留成历史快照，否则历史凭证与报表会指到一条不存在的科目上。`DELETE` 只在「一次都没被引用」时放行，
被引用时后端回 `ACCOUNTING_SUBJECT_IN_USE`（「该科目已被业务单据引用，不能删除；请改为停用」）。

**同分类内名称唯一，且**唯一性检查必须连软删的科目一起查**。库层唯一键 `@@unique([category, name])`
不认 `deleted_at`，所以「删掉一个没人用过的科目 → 再用同名新建」如果只查 `deletedAt: null`，
会通过服务校验、再撞在数据库唯一索引上，变成一个财务看不懂的 500。服务层提前拦住并说明
「名称仍被占用」（实现见 `AccountingSubjectService.assertUnique`）。

**停用的科目必须仍能显示**：三个读科目表的界面（收支流水、应收/应付的科目下拉与标签还原、
财务报表筛选）都带 `?include_inactive=true` 取数 —— 只取启用科目会让历史单据上的科目名变成 `-`。
下拉框自己再过滤成「只列启用项」（应收/应付/收支流水），报表筛选则保留停用项并标注「（已停用）」，
这样财务还能把停用科目的行单独筛出来核对。

### 4.2 迁移怎么改指（关键设计）

`20260917120000_accounting_subjects` 做四件事：

1. 建 `accounting_subjects`；
2. 种入 121 条。其中**一对一映射的 32 条沿用旧收支项目字典项的 id**；
3. 旧 `cash_flow_item` 字典整体**软删**（保留成历史快照，不物理删除）；
4. 5 张表的外键从 `dictionary_items` 换到 `accounting_subjects`，列名 `item_id` / `cash_flow_item_id`
   → `subject_id`。

**为什么「沿用旧 id」而不是「按映射 UPDATE 改指」**：5 张表都要改指，任何一处写漏就是某类流水
静默换了科目，而且只有财务对账时才会发现。沿用 id 让数据库自己保证一致性 —— 历史流水的分类归属
靠主键天然延续，改的只是它现在指向哪张表、显示成什么名字。

**合并组必须显式改指**：一对多的 5 组里，科目只能沿用一个 id，另一条旧项目上的历史引用
（`cash_flow_entries.item_id`、4 张单据表的 `cash_flow_item_id`）由迁移里的 5 条 UPDATE 补齐。
这 5 条 UPDATE 按一张**临时映射表**跑（表结构只写一遍 VALUES，不抄 5 遍），所以不会漏表。

**未写进对照表的自定义旧项目**：财务在界面上自己加过的收支项目不能因为「没写进对照表」就丢掉，
它们以原 id、原名并入分类 `未分类`，由财务重新归类。空库/未自定义过时这一行都不插入。
若连「未分类」都插不进去（同名冲突），迁移会 `RAISE EXCEPTION` 并中止 —— 宁可部署失败，
也不要静默丢一条已经记过账的分类。

**可追溯性**（宪法《Reversible Business Changes》）：迁移把一个审计事件
`accounting_subject.merge_legacy_cash_flow_items` 写进 `audit_events`，payload 里带
`reason` / `source`（科目表文件名）/ 完整 37 条 `mapping`（旧项目 → 分类 + 科目），
操作人与时间由审计表自带。旧字典项本身也只是软删，没有消失。

## 5. 受影响的表与 API 契约

| 表 | 列 | 可空 |
| --- | --- | --- |
| `cash_flow_entries` | `subject_id` | 否（每条流水必须归一个科目） |
| `customer_payments` | `subject_id` | 是 |

| `receivable_reconciliations` | `subject_id` | 是 |

而它现在是会计科目；这一列是全站报表的口径依据，名字必须说真话。

**HTTP 契约变更**（同步改了 `apps/web`）：

| 旧 | 新 |
| --- | --- |
| 请求体 `cash_flow_item_id` | `subject_id` |

| 报表查询 `item_id` | `subject_id`，并新增 `category` |

## 6. 报表口径（用户：「很多报表都要根据这个来统计」）

- **收支明细表**：老表 6 列之外，新增 `分类` + `项目`（原「收支项目」）+ `银行账户`，
  共 9 列，顺序为「日期 / 对方名称 / 币种 / 分类 / 项目 / 收入 / 支出 / 银行账户 / 结算方式」。
- **收支汇总表**：新增 `分类` 列，并在**每个分类段末**给出该分类在本币种内的小计，
  币种段末仍是该币种合计。科目清单 = 启用科目 ∪ 本期出现过的科目（停用的标注「（已停用）」），
  - 小计是用户「根据这个来统计」的直接落地：这张表本身就能回答「这个月销售费用一共花了多少」。
  - **归类靠分组，不靠「恰好连续」**：`buildCashFlowSummaryTable` 按**首次出现的顺序**把科目分组，
    所以哪怕调用方给的顺序被打乱，每个分类也只会有一段、一个小计。原实现靠「分类变化就插小计」，
    要求输入必须连续；而财务在早段分类下新增一个科目随时会打破它（同一币种段里出现两个
    「资产类 小计」，算术没错但看着像重复计算）。
  - **全站只有一个科目排序口径**：`compareAccountingSubjects`（分类按科目表顺序 → `sortOrder` → 名称）。
    列表页与汇总表都用它，`AccountingSubjectService.list()` 与 `cashFlowSummary()` 都在服务层排序，
    不依赖库层 `orderBy` —— 库层排不出「分类优先」（新增科目拿到的是本分类内的号，可能大于别的分类）。
    5 类之外的分类（迁移带出来的「未分类」、财务自建分类）一律排在最后。
- **收支流水列表页**：新增 `分类` 列 + 分类筛选；`项目` 列改为「分类 / 项目」形式。
- **财务报表页筛选**：收支两张表新增「分类」下拉，原「收支项目」下拉改为「会计科目」
  （选项形如 `损益类 / 主营业务收入` —— 唯一键是 `(分类, 项目)`，只显示名称分不清同名科目）。

## 7. 凭证的会计科目（接入正式科目表）

`voucher.domain.ts` 顶部原来写着「库里还没有正式会计科目表……将来接入正式科目表时只需要改
`subjectKey`/`subjectLabel` 的取值来源」。本次就做了这件事：

- 业务分录科目 = 该流水的会计科目（`subject_label` = 科目名称）；
- 科目编码 `subject_key` = `分类/项目`（科目表没有唯一编码，两段拼起来才唯一）；
- 资金分录仍是 银行存款 / 库存现金（**银行账户 → 科目 的映射本期没做**，见 §8）。

凭证、分录模型、页面与打印视图一行没动 —— 验证了当时的判断。
