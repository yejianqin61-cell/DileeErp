# 迪礼 ERP 跨模块合并施工计划

状态：已确认，可直接开发  
确认日期：2026-09-03  
主规格：`docs/design/2026-09-master-development-improvement-spec.md`

## 1. 使用规则

本文件是跨模块开发的施工入口。业务术语、状态机和数据边界以主规格为准；本文件只负责把需求合并成可执行、可验收的任务。历史设计文档可以提供背景，但与主规格冲突时以主规格为准。

每个任务完成后必须独立验收并提交一次 Conventional Commit。未完成该任务的 API、前端、迁移或测试，不得标记为完成，也不得在发布说明中宣称整条管线完成。

## 2. 全局不可变约束

- 用户可见身份统一使用“订单号”；UUID 只用于内部关联。
- “物料清单”统一称为“BOM 表”。BOM、采购和原料库存只能引用 `raw_material`；销售产品属于成品链路。
- 库存余额只能由原料入库、生产领料、退料、报废及其反向事实改变；到货、质检和入库草稿不改变库存。
- 草稿可编辑、删除；确认、过账和完成后的事实只能按状态机回退或冲销，必须填写原因并记录审计。
- 所有跨模块写入必须具备幂等键或业务唯一约束，并在事务内完成来源检查和下游创建。
- 前端写操作使用项目组件库；新增类目保存后返回原页面、恢复表单并立即刷新下拉。
- Excel 导入导出只在内存处理，不保存原始文件。

## 3. 合并后的开发任务

### T01 基础约束、历史数据与状态机

范围：统一物料类型和单位维度，建立业务唯一键，清理/合并历史重复日报，补齐状态迁移和审计约束。

依赖：无。  
阻塞：T02-T07。

验收：原料/成品边界、单位隔离、日报重复键、草稿/确认/过账/回退规则均有 API 测试；历史数据迁移数量和金额守恒。

### T02 采购到货、来料质检、原料入库、应付批次管线

范围：采购单分批到货；累计达到计划量显示超单并支持关闭；每批到货自动生成唯一来料质检和待确认应付来源；质检分次累计；合格/条件接收量才能建立原料入库；入库支持多批、草稿编辑、过账、冲销。

依赖：T01。  
阻塞：T07。

验收：同一批次可从采购追溯到质检、入库和应付；重复提交不重复创建；关闭后禁止到货；每个回退动作恢复正确的上游可操作性。

### T03 库存事实与生产领料

范围：按物料+单位聚合库存；实现生产领料、退料、报废及反向事实；阻止负库存；提供原料仓储情况表格页和草稿更正。

依赖：T01；原料入库接口与 T02 对接。  
阻塞：T06、T07。

验收：只有库存事实改变余额；不同单位不抵销；并发过账和幂等请求不产生重复事实；领料不足被拒绝。

### T04 生产工序员工日报与人工计薪

范围：按生产单、工序、日期隔离；同员工/工序/日期重复登记累加；计件不强制时长、计时不强制件数；单价人工填写；日报保存后形成或刷新工资来源；表头显示计划数量和超单状态，表格列不重复展示。

依赖：T01。  
阻塞：T05、T07。

验收：跨生产单、工序和日期不会串数；重复日报只保留一行；计薪条件和人工单价校验正确；日报修改/删除同步工资来源。

### T05 生产工序完成与进度约束

范围：进行中的生产单允许追加工序；完工必须校验所有有效工序计划量和告警；外加工以回厂交接累计量判断完成；日报工作区按生产单和工序进入。

依赖：T04。  
阻塞：T06。

验收：未完成工序不能完工；追加工序立即出现在对应日报入口；外加工发出量不被当作完成量。

### T06 成品质检、成品库存与应收

范围：成品 QC 合格/条件接收后分批入库；存在下游入库事实时 QC 受控更正；成品出库校验库存和销售单价并生成唯一应收来源；收款必须核销应收。

依赖：T03、T05。  
阻塞：T07。

验收：QC、入库、出库、应收按批次可追溯；库存不足或无销售单价不能过账；收款无有效应收来源不能过账；回退不破坏历史事实。

### T07 财务、人事、基础资料与全站体验

范围：应付/应收/工资结算与来源锁定、按姓名生成工资台账、车间/非车间工资总览；员工离职和固定类型；部门/岗位/工序/地点池；员工 Excel 导入导出；全站新增类目返回刷新；确认单据编辑/回退；PWA 与发布验收。

依赖：T02、T04、T05、T06。  
阻塞：发布验收。

验收：财务事实不能静默改写；工资来源变化可追踪；重名员工必须选工号；导入错误整批不落库且不留原文件；所有新增类目返回调用页并自动选中新项；PWA manifest、service worker 和新版本 chunk 无 404。

## 5. 统一交付门槛

每个任务完成时必须提供：

1. 数据库迁移和回滚/回退说明。
2. API 构建、相关单元/API/PostgreSQL 事务测试结果。
3. 前端构建和关键浏览器链路证据。
4. 幂等、并发、权限、错误输入及回退/冲销测试。
5. Conventional Commit，提交信息说明实际完成的边界。

整体验收通过后，发布包只能从已提交 `HEAD` 生成；服务器使用 Docker PostgreSQL 与 PM2，部署后必须检查 API 健康、Web 首页、manifest 和关键静态 chunk。

## 6. 明确不在本次施工范围

自动排产、自动采购建议、自动标准计薪、税费社保、银行自动对账、订单级库存预留、库位/批号成本、无审批盘盈盘亏，以及自动把销售单核心修改同步改写到历史 BOM/采购/生产单。
