# 凭证重新生成、银行存款引用具体账户、确认页过滤与台账导出（2026-09-16）

## 来源需求（用户原话）

1. 「现在要支持凭证重新生成。」
2. 「凭证中的那个会计科目的银行存款，要引用的是具体的银行账户」
3. 「确认应付，确认应收，表单里如果是已付或者已收款，那个条目就不要出现在那里了！」
4. 「冲销是什么意思？」
5. 「确认应收，确认应付，两处表单。要支持导出excel。支持按照已付未付，已收未收。还有按照时间范围筛选。」

---

## 一、凭证重新生成（需求 1）

### 问题

凭证内容来自**流水那一刻的快照**：收支项目、结算方式、金额、对方名称都是在生成时写进分录的。
流水后来被更正（改金额、改项目、改银行、改备注）时，原凭证就与流水对不上了，
而原来只有一条路 —— 删掉重来（丢凭证号、丢审计链）。用户要的是「重新生成」。

### 口径（四条，都是「不能静默改账」的推论）

| 情形 | 结论 | 错误码 |
| --- | --- | --- |
| 凭证是**草稿** | 允许重新生成 | — |
| 凭证**已过账** | 拒绝：已过账是账务事实，只能红冲 | `VOUCHER_NOT_REGENERABLE` |
| 凭证是**红冲件**（`source_type = voucher_reversal`） | 拒绝：它的内容由被红冲那张决定，重算会得到一张「不红」的红字凭证 | `VOUCHER_NOT_REGENERABLE` |
| 来源流水已不存在 | 拒绝 | `VOUCHER_SOURCE_MISSING` |
| 来源流水已冲销（`status ≠ posted`） | 拒绝：钱没真的动过 | `CASH_FLOW_ENTRY_NOT_VOUCHERABLE` |

`POST /finance/vouchers/:id/regenerate` 的实现：

1. 校验上面五条（在事务外先拒，避免锁了才发现不该做）；
2. 事务内 `SELECT ... FOR UPDATE` 再确认一次仍是草稿 —— 两个页签同时点「重新生成」时，
   后到的那个报「凭证已被其他操作处理」，而不是把分录删了一半；
3. **删除全部分录 → 按当前流水重算重建**（不是原地 diff：分录条数会因为收支项目/资金科目的
   变化而变，逐条改会留下孤儿行）；
4. 同时刷新凭证头的日期、会计期间、摘要、币种与借贷合计（日期/期间跟着流水走，
   否则「7 月的流水重算成 8 月的凭证」会落进错误的期间）；
5. 审计 `voucher.regenerate`，**before/after 都记**（金额、摘要、分录条数、来源单号）——
   重新生成会覆盖财务手工改过的分录，审计里必须看得出覆盖前是什么。

### 页面

- 凭证列表行（草稿 + 来源是收支流水）：`voucher-regenerate-<id>`；
- 收支流水页行（该流水已有草稿凭证）：`voucher-regenerate-from-entry-<id>`；
- 两个入口都先弹确认框，文案写明「手工改过的分录会被覆盖」。

### 与「删除 / 红冲」的分工

| 想做的事 | 用哪个 |
| --- | --- |
| 草稿凭证内容与流水不一致（流水被更正过） | **重新生成** |
| 草稿凭证本来就该作废 | 删除 |
| 已过账凭证内容错了 | 红冲（生成一张红字凭证把原来的账冲平），再按更正后的流水**另建**凭证 —— 同一流水不能再生成第二张（`vouchers_source_type_source_id_key`），见 §六 |

## 二、银行存款 → 引用具体银行账户（需求 2）

### 改前

资金科目靠**猜**：`settlementMethod` 或 `settlementAccountLabel` 里含「现金」→ `库存现金`，
否则 → `银行存款`。所以所有转账类的凭证都记在一句光秃秃的「银行存款」上，
账上看不出钱在哪个账户 —— 而出纳最常问的恰恰是「这笔在哪个账户」。

### 改后

`voucher_lines` 新增 `bank_id`（可空，`ON DELETE SET NULL` + 索引），取值优先级：

1. **流水上挂了 `bank_id`**（财务在收付款/确认时从银行池里选的账户，第十三/十四/十五轮已经写进流水）
   → 科目 = `银行存款`，并引用该账户；科目名快照写成 `银行存款—农业银行5706`；
2. 没有 `bank_id`，但结算方式/结算账户名含「现金」→ `库存现金`；
3. 都没有 → `银行存款`（不引用账户）。

三条设计约束：

- **`subject_key` 仍是「银行存款」**（不是「银行存款—农业银行5706」）：科目要保持可汇总，
  「银行存款」总额才是一个数；具体账户是**引用**（`bank_id`）+ **名称快照**（`subject_label`）
  两层，前者给报表 join，后者给「账户被改名/删除后凭证纸仍然可读」。
- **账户名快照格式** `${bankName}${accountNumber}`（如「农业银行5706」），与收支流水
  「结算方式」列的口径一致（同一件事在两个页面用同一个写法）。
- **账户被停用/删除不影响已有凭证**：`SET NULL` 只是丢了引用，快照文字还在，
  凭证内容不会因为银行池的增删而改变。
- 红冲分录**带着同一 `bank_id` 一起红**（红字凭证也要能看出原账户）。

已知缺口：科目汇总目前仍按 `subject_key`，所以「银行存款」下钻到账户的**明细账报表还没做**
（数据齐了，报表未做）。

## 三、确认页不再显示已付 / 已收（需求 3）

「确认应付」是**待办清单**：确认即记账（第十三/十五轮口径），一条应付一旦确认，
钱就已经从所选银行账户出去了 —— 它留在「确认应付」表里没有任何可做的事，
只会让待办清单越用越长。所以**默认只看未付 / 未收**。

但需求 5 又要「按已付未付筛选」，两者不矛盾：**默认收窄，而不是删除**。

## 四、两处台账的筛选与导出（需求 5）

### 「已付 / 未付」在这个系统里到底是什么

这是本轮唯一需要业务确认的**语义决定**，写在这里以便纠正：

| 界面上的付款情况 | 状态 |
| --- | --- |
| 未付 / 未收 | `draft`（还没确认，钱没动） |
| 已付 / 已收 | `confirmed`（确认即记账，钱已经进了/出了所选账户） |
| 部分付款 / 已付清 / 部分收款 / 已收清 | `partially_paid` / `paid`（来自收付款核销，历史数据或接口写入） |
| 已冲销 / 已作废 / 已取消 / 已关闭 | 既不算未付也不算已付，**只在「全部」里出现** |

为什么把「已确认」当作「已付」：界面上**没有第二步付款**（第十五轮把登记付款从确认页去掉了）。
若把「已付」定义成「有付款单核销」，这个筛选项永远是空的。

### 筛选项（两侧对称）

- **付款情况 / 收款情况**：`未付（n）/ 已付（n）/ 全部（n）` —— 括号里的条数是**当前关键字与
  日期筛选之后**的实时条数，默认 `未付` / `未收`；
- **日期范围**：应付 = **确认日期**（`confirmation_date`），应收 = **出库日期**（`created_at`，
  即成品出库过账生成来源的日期）；标签按此区分，不写含糊的「日期」；
- 三个条件与搜索框是**与关系**，先关键字、再日期，再按付款情况分桶（计数也基于同一批数据）。

**没有日期的行在设置了时间范围时不算命中**（宁可少列，也不要列错）。

### 导出 Excel

两条新路由（静态路径，都排在 `:id` 之前）：

| 路由 | 内容 |
| --- | --- |
| `GET /finance/payable-entries.xlsx` | 应付台账（17 列，含「付款情况」「状态」） |
| `GET /finance/receivable-sources.xlsx` | 应收台账（16 列，含「收款情况」「状态」） |

- **所见即所得**：导出把当前的 `payment` / `from` / `to` / `q` 原样带给后端，
  页面筛出 3 条、文件里就是这 3 条 —— 前端筛选是纯前端分页的（表格是前端分页），
  如果导出走后端全量，用户会拿到一份和屏幕对不上的文件。
- **金额与数量是 Excel 数值类型**（走 `NUMBER_FORMAT`），否则财务在 Excel 里 `SUM` 得 0；
  这条由 `ledger-export.test.cjs` 钉住。
- **不做合计行**：台账是多币种同表，跨币种相加没有意义；含两种以上币种时在表尾写一行
  「本表含 CNY / USD 共 2 种币种，金额列不做合计」。
- 文件名 `迪礼ERP-应付台账-<时间戳>-<N>行.xlsx`，`Content-Disposition` 用 `filename*=UTF-8''`
  （中文文件名不靠 ASCII 回退）。

前端筛选逻辑（`apps/web/lib/finance-ledger-filter.ts`）与后端（`apps/api/src/modules/finance/ledger-filter.ts`）
是**两份同口径实现**：一份给界面（要立刻响应、要出计数），一份给接口（要接受任意客户端直接调
`.xlsx`）。两边文件顶部互相点名，改一处必须改另一处 —— 有 lib 单测钉住前端那份的口径。

## 五、冲销是什么（需求 4，概念说明）

**一句话：冲销不是删除，是补一笔方向相反的分录（红字/反方向）把原来的影响抵平 ——
原来的那笔永远留在账上。**

系统里所有「错了要改」的路径都遵守同一条规则：**已经成立的事实不删除，只追加一条反向事实**。
理由很直白 —— 账、库存、流水都是「发生过」的记录，删掉就没有痕迹了；审计问「上个月这笔
100 万去哪了」时，正确答案是「8 号付出、12 号冲销」，而不是「查不到这笔」。

具体到本系统：

| 位置 | 冲销做了什么 |
| --- | --- |
| 应付 / 应收 / 收付款单 | 原单状态变 `reversed`（已冲销）+ 生成一条等额反向的收支流水，银行余额复原 |
| 银行互转 | 同上：余额回到转账前 |
| 记账凭证 | 生成一张**红字凭证**（借贷方向相反、金额取负），两张一起看净额为零 |
| 原料入库 / 出库 / 日报 | 反向库存事实 + 状态推进，原单不可再编辑 |

**冲销 ≠ 删除**，也**≠ 修改**，三者在本系统里的分工：

- **修改**：只有 `draft`（草稿）能改 —— 草稿还没有产生任何事实，改它不留痕迹是对的；
- **冲销**：已经过账/已确认的（事实已成立）只能冲销，原单保留、状态标记、反向事实补齐；
- **删除**：只有草稿能删；已过账的单据查不到「删除」按钮。

所以界面上你看到的现象都有同一个原因：凭证一旦过账就只能红冲不能重新生成（§一），
确认后的应付不在「未付」里（§三）—— 因为钱已经动过了。

## 六、已知缺口

- **已过账凭证的更正路径仍然绕**：红冲后不能对同一流水再生成凭证（唯一约束 + 状态门禁），
  需要「更正流水 → 新建一条流水 → 对新流水生成凭证」。要不要放开「红冲后允许重新生成」
  （会破坏 `vouchers_source_type_source_id_key` 的唯一性语义）需要业务确认。
- **重新生成不做「差异预览」**：直接覆盖，财务只能从审计里看到覆盖前后。
  若实际使用中觉得危险，下一步应该做成「先显示新旧分录对照，再确认覆盖」。
- **银行账户的明细账报表还没做**：`bank_id` 已经在分录上了，但没有「按账户的银行存款明细账」。
- **确认页默认收窄到未付/未收之后，已冲销的条目在默认视图里看不见**（只在「全部」里）：
  这是有意的（待办清单只列待办），但如果财务习惯用这个页面查历史，需要适应切筛选。
- **导出的时间范围不含时间**：起止都是整天闭区间，跨时区的边界未定义（本机与工厂同区，本期不处理）。
