# 迪礼 ERP 前端全量组件化改造工作计划

## 1. 工作目标

本期目标不是继续增加组件，而是完成全站前端迁移：所有业务页面真正使用已建立的 shadcn/ui 风格组件和统一交互模式。

最终页面应突出功能本身，文字简洁，信息可扫描，避免组件堆叠，不人为制造主次层级。所有用户输入、编辑、确认、过账、冲销和更正都必须在统一弹窗或抽屉中完成。

## 2. 当前基线

已完成：

- `components.json` 和 Radix primitives 已配置。
- Button、Input、Textarea、Select、Form、Table、Dialog、Sheet、AlertDialog、Toast、ActionDialog 等组件已建立。
- 浏览器原生 `window.prompt`、`window.alert`、`window.confirm` 已清除。
- 销售、采购部分操作已使用 ActionDialog/Sheet。

未完成：

- 生产主页面、生产日报、外加工、成品 QC 仍大量使用原生表单和表格。
- 仓库仍大量使用原生表单、表格和内嵌详情。
- 人事、财务、报表的列表仍直接使用原生 `<table>`。
- 登录和工作台仍未完成统一组件迁移。
- AlertDialog、Toast、Form、Select、Textarea、DataTable 的业务页面采用率不足。

## 3. 全站统一规则

### 3.1 页面结构

业务页面统一采用：

```text
页面标题区
查询与筛选区
主数据表
详情 Sheet
新增/编辑 Dialog
高影响操作 AlertDialog
```

页面标题区只保留标题、极短描述和一项主操作。辅助说明、帮助文字和技术字段不得占据首屏主要空间。

### 3.2 组件使用规则

业务页面禁止直接出现以下原生元素：

- `<input>`
- `<select>`
- `<textarea>`
- `<form>`
- `<table>`

例外仅限组件实现内部、登录凭证输入的底层封装，以及文件上传控件的必要实现。业务页面必须通过统一组件暴露这些能力。

映射规则：

| 业务需求 | 统一组件 |
| --- | --- |
| 单行输入 | Input |
| 多行备注/原因 | Textarea |
| 枚举或关联选择 | Select/搜索选择器 |
| 业务录入 | Form + React Hook Form |
| 短业务动作 | Dialog/ActionDialog |
| 复杂详情、审计、影响预览 | Sheet |
| 过账、关闭、冲销、删除 | AlertDialog |
| 列表 | DataTable + Table |
| 成功反馈 | Toast |
| 错误、加载、空数据 | 统一反馈组件 |

### 3.3 业务交互规则

- 不再让操作员手动录入内部 ID；统一显示编号/名称，提交内部 ID。
- 表单必须有标签、字段校验、提交中禁用、失败保留输入和错误定位。
- 详情 Sheet 关闭后保留列表筛选、分页和滚动上下文。
- 高影响操作必须显示对象、影响范围、原因字段和确认按钮。
- 成功后刷新受影响查询，不整页无条件刷新。
- 文字简短，不在页面中解释系统架构和模块职责。

## 4. 实施阶段与顺序

### 阶段 0：公共基础收敛

目标：确保组件可以覆盖全站迁移。

- 完善 FormField、字段错误、提交中状态和未保存离开提示。
- 完善 Select 的搜索、空选项、禁用和错误状态。
- 完善 DataTable：列定义、空状态、加载 Skeleton、行操作、详情触发。
- 完善 AlertDialog 和 Toast Provider，在应用根部挂载。
- 统一状态标签、间距、边框、焦点态和响应式 token。

出口标准：公共组件有至少一个真实业务页面示例，类型检查和生产构建通过。

### 阶段 1：生产全量迁移

目标：优先解决当前原生控件最密集的模块。

覆盖范围：

- 生产主页面基础资料：地点、工序、单位选择
- 生产单创建、详情、添加工序、启动、状态推进
- 工序日报、员工计件/计时日报
- 日报历史、超单告警、差异告警、进度查看
- 外加工直发、签收、余料回厂、成品回厂、直装柜
- 成品送检、QC 结果、复检/返工入口

改造要求：

- 基础资料和生产单创建改为 Dialog。
- 生产单列表改为 DataTable，行详情改为 Sheet。
- 日报、外加工、成品 QC 的内嵌表单改为 Dialog 或 Sheet 内的 Form。
- 历史记录全部使用 DataTable。
- 删除、告警确认、过账等使用 AlertDialog。

出口标准：生产主流程和一条错误/更正流程完成真实 API 与浏览器验收。

### 阶段 2：仓库全量迁移

覆盖范围：

- 原料库存查询和流转历史
- 领料、影响预览、过账
- 退料、报废、冲销
- 成品入库、成品 QC、成品出库、客户退货
- 审计时间线、附件、库存影响详情

改造要求：

- 所有原生表单改为 Form + Input/Select/Textarea。
- 库存和流转历史改为 DataTable。
- 影响预览、审计和附件入口集中到 Sheet。
- 过账、报废、冲销、删除草稿使用 AlertDialog。

出口标准：采购入库、生产领料、成品出库三条真实链路浏览器验收通过。

### 阶段 3：销售与采购补齐

覆盖范围：

- 客户池、联系人、客户状态
- 销售单、BOM、模板字段
- 采购单、到货、来料 QC、原料入库、应付来源

改造要求：

- 将现有原生 table 替换为 DataTable/Table。
- 客户、供应商、物料、单位和订单全部改为可搜索选择器。
- 补齐编辑、详情、停用、发布和影响预览。
- 将采购批次和 QC 结果放入详情 Sheet，不再与主表纵向堆叠。

出口标准：客户 → 销售单 → BOM，以及 BOM → 采购 → 到货 → QC → 入库真实验收通过。

### 阶段 4：人事与财务补齐

覆盖范围：

- 员工目录、考勤、绩效、薪资、工资支付
- 应收、收款、应付、付款、核销、冲销、对账

改造要求：

- 人事和财务原生 table 全部替换为 DataTable/Table。
- 员工、客户、供应商、期间和来源选择使用 Select/搜索选择器。
- 薪资台账、收付款、核销和对账详情使用 Sheet。
- 确认、关闭、过账、冲销和对账处理使用 AlertDialog。

出口标准：薪资主流程、成品出库 → 应收 → 收款、原料入库 → 应付 → 付款真实验收通过。

### 阶段 5：工作台、报表、登录和全局回归

覆盖范围：

- 订单全链路工作台
- 报表筛选、导出、告警中心
- 登录页
- 应用壳、导航、反馈状态、错误边界

改造要求：

- 工作台按 `order_no` 展示链路状态，详情和审计使用 Sheet。
- 报表使用统一筛选栏和 DataTable，导出使用 Toast/错误反馈。
- 告警处理、备注和解决使用 Dialog/AlertDialog。
- 登录使用统一 Input、Label、Form 和错误反馈。
- 清理旧面板、占位组件和重复 CSS 规则。

出口标准：全站浏览器回归、窄屏检查、静态扫描和生产构建全部通过。

## 5. 任务交付方式

每个阶段继续拆为可独立提交的任务，执行规则：

1. 一个任务对应一个明确页面或一组紧密相关的子页面。
2. 一个任务完成后必须有独立 Conventional Commit。
3. 不在同一提交中混入后端模型、API 或无关重构。
4. 每个任务必须更新真实接口联调和浏览器验收证据。
5. 当前阶段未达出口标准，不进入下一阶段。

## 6. 全站验收门禁

### 静态门禁

- 业务页面扫描不到原生 `<input>`、`<select>`、`<textarea>`、`<form>`、`<table>`。
- 扫描不到 `window.prompt`、`window.alert`、`window.confirm`。
- 业务页面实际导入并使用统一组件，而不是仅保留旧 HTML。
- 不再直接堆叠重复面板；详情、表单和确认有明确容器。

### 工程门禁

- Web 类型检查通过。
- Web lint 通过。
- Web 生产构建通过。
- 组件和页面无新增 TypeScript 绕过。

### 业务门禁

- 每个模块至少一条真实主链路。
- 每个模块至少一条校验失败或更正/冲销链路。
- 表单提交失败时输入内容保留。
- 操作成功后数据状态、余额、告警和 `order_no` 上下文正确刷新。
- Playwright 覆盖弹窗打开、字段填写、提交、错误显示、关闭和详情抽屉。

## 7. 最终交付物

- 全站组件迁移后的前端代码。
- 组件采用情况静态扫描结果。
- 各模块真实 API 联调记录。
- 浏览器验收截图或测试报告。
- 未完成项和已知限制清单。
- 最终前端交付评估公报。

## 8. 明确不做

- 不重写后端领域模型、数据库和 REST 契约。
- 不增加移动端和离线模式。
- 不加入营销式首页、装饰性动画或大段产品说明。
- 不以“组件文件已创建”“构建通过”替代页面迁移验收。
