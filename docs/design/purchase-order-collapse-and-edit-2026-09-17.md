# 采购单「收束」与「编辑」——2026-09-17 设计

> 用户原话（四条）：
> 1. 「采购板块，要支持对已经建好的采购单进行编辑」
> 2. 「新建采购单这个页面，勾选框太宽了，要窄一点，然后让名称和型号那栏宽一点。预计到货那个 column 也要宽点」
> 3. 「已经选中并下单的 BOM 物料，再新建采购单中要显示已下单。因此要多一个 column」
> 4. 「采购单现在有点乱。我们的逻辑是，导入 BOM 物料之后，用户对采购单进行编辑，填写供应商等等 column。
>    支持保存草稿。然后再根据供应商收束下单。一个采购单内，一个供应商下一个单。当前这个功能完全缺位」

开工前按既定纪律先问后做（「有问题就向我询问，问完再开工」），四个问题用户全部选了推荐项：

| 问题 | 结论 |
| --- | --- |
| 保存草稿落几张单？ | **也按供应商收束**：几个供应商就落几张草稿，一家一张 |
| 可编辑范围？ | 草稿自由编辑；**已下单但无任何到货**也能直接编辑（必填原因、留审计）；有到货事实的只能改打印信息 |
| 「已下单」列显示到什么程度？ | 四态：未下单 / 草稿中 / 部分下单 / 已下单足量，带累计数量 + 采购单号 |
| 收束时还有行没选供应商？ | **阻断**，报出第几行，一行都不下单 |

## 1. 事实核查：用户说「完全缺位」，缺的到底是什么

第 4 条说这个功能「完全缺位」。先查证再动手，实际情况是**半成品**：

| 已有 | 缺 |
| --- | --- |
| `POST /purchase-orders/split` 按供应商分组、一个事务建 N 张单 | 入口藏在一个 `draftGroups.length > 1` 才渲染的预览面板里 |
| 分组预览列出每家的行数与金额 | **已保存的草稿不能再收束**（前端硬拦：「已保存的采购单不能再拆分」） |
| 「带入 BOM 表明细」开关 | 主要的「保存草稿 / 下单」两个按钮仍然写**一张可以混多个供应商**的单 |

第三条是根子上的问题：**头部供应商、币种、金额在一张混供应商的单上没有单一含义**，
而到货、应付、对账都挂在采购单上。既有设计文档（`docs/log/2026-09-14.md`）自己写着
「组内明细的供应商强制取组供应商，保证采购单头部供应商与后续到货/应付/对账只有一个口径」——
也就是说，原来那条「保存草稿」路径违反了自己写下的规则。

所以本轮的改动不是「新增一个功能」，而是**把收束变成唯一路径**：
`保存草稿` 与 `收束下单` 走同一个请求体，只差 `place_order`。

## 2. 保存 / 下单的语义表

工作区里的两个按钮不再是「一张单」与「拆成 N 张」的区别，而是**草稿还是正式单**的区别：

| 打开的工作区 | 按钮 | 落库结果 |
| --- | --- | --- |
| 新建（无 id） | 保存草稿 | N 张 `draft` |
| 新建（无 id） | 收束下单 | N 张 `ordered` |
| 已存在，`draft` | 保存草稿 | N 张 `draft`，**第 1 组沿用原单**（单号不变） |
| 已存在，`draft` | 收束下单 | N 张 `ordered`（同上，并补采购日期） |
| 已存在，`ordered`（无到货） | 保存修改（必填原因） | N 张 `ordered`，状态不变 |
| 已存在，有到货事实 | 不给编辑入口 | — |

**为什么第 1 组沿用原单，而不是「新建 N 张再把原单取消」**：草稿从来没有发给供应商，
把它的内容重新组织一次不是一次「取消」业务。标成已取消会让列表里凭空多一条作废记录、
白烧一个采购单号，而且「原单到底去哪了」要靠备注去猜。沿用原单则在界面上明说
（预览面板里一行字：「第 1 组沿用本单单号 PO-XXXX，其余组新建采购单」）。

**为什么「已下单」的单不能靠保存草稿退回草稿**：那张单已经发给供应商了，
在系统里退回草稿等于假装没下过单，而供应商手里那份单还在。

## 2.1 「导入 BOM 明细」也算一次编辑：未选供应商的行必须存得下来

用户在看到上面这张表之后补了一句：「**导入 BOM 明细，也视为对采购单的编辑，允许保存**」。

这一句推翻了我刚写下的「收束时没选供应商的行直接阻断」在**草稿**场景的适用性。
刚「带入 BOM 明细」时每一行都还没有供应商，而当时 `validateDraft` 会拦下：
「第 1 行明细还没选供应商，收束不了」—— 也就是说 30 行的供应商没填完之前，**一个字都存不下来**，
草稿功能对主流程等于没有。这正是用户描述的流程（导入 → 编辑 → 保存草稿 → 收束下单）里最先卡住的一步。

所以定了：**草稿允许有「还没选供应商」的行**。它们单独合成一组，落成一张
**供应商为空的草稿**；下次打开它继续填，填完再收束。

### 数据库层面的代价：明细行的供应商改回可空

`purchase_order_items.supplier_id` 与 `supplier_snapshot` 从 NOT NULL 改回可空
（迁移 `20260920120000_purchase_order_item_supplier_nullable`）——
这是 `20260908120000_purchase_order_item_supplier_expected_date` 那条 `SET NOT NULL` 的反向改动。
当时连草稿都要求每行有供应商，所以约束成立；现在业务明确要「草稿可以先没供应商」，约束就必须退回。

**「一个供应商一张采购单」的不变式没有丢，只是从数据库层挪到了两处业务门禁**：

| 门禁 | 位置 | 作用 |
| --- | --- | --- |
| 下单门禁 | `assertOrderableItems` | 每一行都必须有供应商，否则 422 `PURCHASE_ORDER_INCOMPLETE`（`ITEM_INCOMPLETE`，原因里点名「供应商」） |
| 写入门禁 | `refs()` | 一张单上不允许出现两个不同供应商 → 422 `PURCHASE_ORDER_MULTIPLE_SUPPLIERS` |

为什么这样仍然安全：到货只能登记在**已下单**的采购单上，应付来源由到货/入库派生、
应付单由应付来源派生 —— 任何有下游事实的明细行必然走过下单门禁，也就必然有供应商。
可空只影响「还没定供应商的草稿」。

顺带补上的一条**新**约束（以前只靠界面保证）：`refs()` 现在会拒绝「一张单两个供应商」。
旧的 `POST /purchase-orders`（非收束路径）本来可以写入混供应商的单，只是界面不走那条路。
`/split` 的每一组天然只有一家，所以这条不会误伤。

两个下游读写点各加了一道可读的守卫（`PURCHASE_ITEM_SUPPLIER_MISSING`），
免得历史脏数据撞上数据库的 NOT NULL 违约变成 500：
`raw-material-inbounds.service.ts`（入库单 + 应付来源）与 `outsource-logistics.service.ts`（外加工应付来源）。

### 保存 / 下单的完整性要求（更新后的完整口径）

| | 明细行数 | 每行的物料/单位/数量/单价 | 每行的供应商 | BOM | 预计到货 |
| --- | --- | --- | --- | --- | --- |
| 保存草稿（新建或草稿） | 可以为 0 | 必须完整 | **可以没有** | 可空 | 可空 |
| 保存修改（已下单未到货） | ≥1 | 必须完整 | **必须有** | 必须 | 可空 |
| 收束下单 | ≥1 | 必须完整 | **必须有** | 必须 | 必须每行都有 |

「明细行数为 0」的空草稿走**普通建/存单接口**（`POST /purchase-orders` / `PATCH :id`）：
没有供应商可分组，收束接口会以「至少需要一个分组」拒绝，而「选定销售单即可保存」
是 2026-09-17 之前就有的行为，不该在这轮丢掉。

## 3. 「下单状态」列的四态

数据来自新端点 `GET /purchase-orders/bom-item-status?bom_id=…`，
按 `purchase_order_items.bom_item_id` 归集，**只算未删除的明细行、排除已取消的采购单**：

| 状态 | 判定 | 界面 |
| --- | --- | --- |
| `ordered` 已下单足量 | 已下单量 ≥ BOM 需求量 | 绿字「已下单 5（PO-77）」 |
| `partial` 部分下单 | 已下单量 > 0 且不足 | 黄字「部分下单 2 / 需求 5」 |
| `draft` 草稿中 | 只有草稿覆盖 | 灰字「草稿中 3（PO-79）」 |
| `none` 未下单 | 什么都没有 | 灰字「未下单」 |

两个刻意的口径：

- **草稿不算「已下单」，但要单独标出来。** 只显示「已下单 / 未下单」两态的话，
  已经被另一张草稿盖住的行会显示成「未下单」，那正是重复开单的来源。
- **需求量为 0 的行不判成「已下单足量」。** `0 ≥ 0` 会把空行显示成买齐了。

## 4. 修掉的三个真缺陷

### 4.1 「勾选框太宽」是 CSS 权重泄漏，不是审美问题

这一页的 `<SheetContent>` 带着 `material-issue-sheet`（借用它的全屏版式），
于是也继承了原本写给**领料单**的列宽规则：

```css
.material-issue-sheet .data-table th:nth-child(1),
.material-issue-sheet .data-table td:nth-child(1) { width: 24%; }   /* 领料单的物料列 */
.material-issue-sheet .data-table th:nth-child(2),
.material-issue-sheet .data-table td:nth-child(2) { width: 8%; }
```

在 `table-layout: fixed` 下这两条是硬约束，而 `.draft-select-cell { width: 40px }`
的权重是 `(0,1,0)`，输给 `(0,3,1)`：

- 行首复选框列 = 24% × 100vw ≈ **1920px 屏上 460px**；
- 名称列 = 8% ≈ **154px**，反而比没有指定宽度的型号列（8.5%）还窄；
- 预计到货 = 8.5% ≈ 163px。

修法是给草稿表逐列写显式宽度，选择器**故意叠到 `(0,4,0)`**：

```css
.purchase-workspace.material-issue-sheet .data-table .draft-col-material { width: 19%; }
```

为什么不写 `.purchase-workspace .draft-col-material`：那样是 `(0,3,0)`，仍然输给
`(0,3,1)`；而写 `.purchase-workspace .data-table td.draft-col-*` 是 `(0,3,1)`——
**同分**，谁生效取决于样式表里的先后顺序，以后挪一下就会静默退回 24%。
叠到 `(0,4,0)` 才是与顺序无关的。

### 4.2 「添加行 → 保存草稿」在选了 BOM 时必然失败

后端 `refs()` 有一条规则：选了 BOM 时，凡是不引用 BOM 行（`bom_item_id` 为空）的明细
**必须给 `extension_data.outside_bom_reason`**，否则 422 `PURCHASE_OUTSIDE_BOM_REASON_REQUIRED`。
而界面上**根本没有任何地方能给出这个值** —— 于是「添加行」之后保存，一定失败，
报错还是整单级别的（不指行），用户无从下手。

本轮补上「BOM 外新增原因」输入框（只在草稿里真的有 BOM 外行、且选了 BOM 时出现），
一个值应用到所有 BOM 外行；打开已存在的单时把原值带出来，不用重打。

### 4.3 换掉物料会撞 `PURCHASE_BOM_ITEM_MISMATCH`

BOM 行上的物料下拉是可以改的，但改完 `bom_item_id` 还留在行上，
后端校验「引用的 BOM 行的物料必须与本行物料一致」就会拒绝**整张单**。
现在换物料时一并清掉 `bom_item_id`（与 `bomMaterialId`），这一行随之变成「BOM 外新增」，
按 4.2 要求填原因。

## 5. 接口面

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `purchase-orders/bom-item-status?bom_id=` | BOM 每行的累计下单情况（四态）。**必须声明在 `@Get(":id")` 之前** |
| `POST` | `purchase-orders/split` | 新建：按供应商收束成 N 张（`place_order` 决定草稿还是正式单）。已存在 |
| `POST` | `purchase-orders/:id/split` | 收束一张**已存在**的单：第 1 组沿用原单，其余组新建 |
| `PATCH` | `purchase-orders/:id` | 整体替换。可编辑范围放开到「已下单未到货」，并要求 `reason` |

DTO 上跟着放松的两处：`ItemDto.supplier_id` 与 `SplitGroupDto.supplier_id` 改成
`@IsOptional() @IsUUID()`。前端必须把「未选供应商」发成**缺省**而不是空串 ——
`@IsOptional()` 只跳过 `null`/`undefined`，空串会撞上 `@IsUUID()` 直接 400。
（`JSON.stringify` 会丢掉 `undefined`，所以前端写 `group.supplierId || undefined`。）

错误码一览（本轮新增/变动）：

| 错误码 | 含义 |
| --- | --- |
| `PURCHASE_ORDER_MULTIPLE_SUPPLIERS` | 一张单上出现了两个不同供应商 |
| `PURCHASE_SPLIT_UNASSIGNED_DUPLICATE` | 未选供应商的明细被拆成了多组（它们只能同属一张草稿） |
| `PURCHASE_SPLIT_SUPPLIER_REQUIRED` | **下单**时某一组没有供应商（草稿保存不受此限） |
| `PURCHASE_ITEM_SUPPLIER_MISSING` | 生成入库/应付时明细行没有供应商（历史脏数据的可读兜底） |
| ~~`PURCHASE_ITEM_SUPPLIER_REQUIRED`~~ | 已从 `refs()` 移除，职责交给 `assertOrderableItems` |

服务层把两处共用逻辑抽了出来，避免两条路径漂移：

- `collectGroups(input, placeOrder)`：结构校验 → 参照物解析 → 下单前校验。**新建与收束共用同一套校验**，
  否则会出现「新建时不允许的写法、编辑时却放过去了」。
- `replaceOrder(tx, id, prepared, input, user, extra)`：老明细软删 + 新明细批量建 + 头部字段更新。
  两条路径共用同一段写入，漂移的后果是头部供应商/金额与明细对不上。
- `assertEditable(po, action)`：草稿随便改；已下单未到货也能改（要原因）；其余拒绝。

`reason` 只在 `PurchaseOrderSplitExistingDto` 上，**不在** `PurchaseOrderSplitDto` 上 ——
`ValidationPipe` 开了 `forbidNonWhitelisted`，新建路径多带一个键会直接 400。
前端因此按「有没有 `purchaseDraft.id`」决定要不要带 `reason`。

## 6. 刻意不做的事

- **不给采购单加「采购计划」实体。** 2026-08-20 已确认「什么狗屁采购计划？只有采购单」，
  所以收束的工作面就是一张普通采购单（草稿态），不引入第二种单据。
- **不新增 `superseded` 状态。** 收束一张已存在的单靠「第 1 组沿用原单」，不需要作废任何单，
  也就避免了给 `PurchaseOrder.status` 加第五个值（导出筛选白名单 `@IsIn([...])` 等地方都要跟着改）。
- **不让「保存草稿」把已下单的单退回草稿**（见第 2 节）。
- **不把草稿计价/比价做成单独视图。** 用户没提，且「当前库存量」列已经在做决策支持。
- **不改「回到草稿」按钮。** 直接编辑已下单单之后它变得少见，但它仍是一个合法的业务动作
  （「这单还没发出去，退回去重来」），且撤销一次业务动作属于可逆性要求，不该顺手删。

## 7. 明确没做完 / 未验证

- 迁移 `20260920100000_purchase_order_item_bom_item_index`（`purchase_order_items` 加
  `bom_item_id` 索引）与 `20260920120000_purchase_order_item_supplier_nullable`
  （两列 DROP NOT NULL）**都从未在真实 PostgreSQL 上执行**：本机没有可用的数据库实例。
  后者会放松一个数据库约束，风险高于前者 —— 部署时请先确认
  `SELECT is_nullable FROM information_schema.columns WHERE table_name='purchase_order_items' AND column_name='supplier_id'`
  在迁移后变成 `YES`。
- `bomItemOrderStatus` 的查询只跑过手写假 Prisma，**没有对真实库验证过 SQL**。
- 导出、Playwright、`test/http`、`test/integration` 均未运行（无数据库）。
- 列宽改动没有在真实浏览器里量过像素：本机只做了权重推导与构建，**建议部署后目测一次**
  （1200–2560px 各看一眼）。
- `PURCHASE_ITEM_SUPPLIER_MISSING` 这两道守卫是**防御性**的，正常路径到不了；
  没有测试覆盖「有到货的明细行却没有供应商」这种需要构造脏数据的状态。

## 8. 留给用户的口径问题

见 `docs/memo/0917-采购单收束与编辑待确认事项.md`。其中一条值得在这里点明：
**「已下单」列的统计口径是按 `bom_item_id` 归集的**，所以只对「从 BOM 带进来的行」有效；
手工添加的行（补料/替代料）天然没有 `bom_item_id`，永远显示「BOM 外新增」。
如果业务上希望「补料也要能看出买过没有」，那要按「物料 + 订单号」归集，是另一套口径。
