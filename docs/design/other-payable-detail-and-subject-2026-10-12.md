# 其他应付的「明细」与「会计科目」：采购对账明细加两列 + 其他应付可指定科目（2026-10-12）

## 一、触发这件事的原话

用户 2026-10-12 转来财务反馈，并附了那张导出件
（`迪礼ERP-采购对账明细-20261010153051-97行(1).xlsx`，2026-10-10 15:30 出的）：

> 「财务反馈，这边的周金红那几行，也就是备用金付款，看不到明细。你排查一下，
> 系统中是否有相应填写会计科目的地方，导出时，会计科目和明细会放在表格的哪些 column？
> 能不能如果是其他应付，就在订单号那边写出明细」

三问对应三答，本文件就是那三答的落地记录。

**先把那张表看清楚**（我逐格读了，不是听描述）：97 个数据行里

| 类别 | 行数 | 特征 |
| --- | --- | --- |
| 采购行 | 31 | 产品名称 / 订单号 / 采购单号 / 产品代码 / 规格 / 单位 / 数量 都有值 |
| 其他应付行 | 66 | 这些列**全空**，只有 日期 / 供应商名称 / 币种 / 单价 / 数量=1 / 金额 |
| ↳ 其中「周金红」 | 62 | 第 25–86 行；她不是单独一类，是同一批备用金里的一家 |
| ↳ 另外 4 行 | 4 | BOSS 直聘 1、陈镝 1、`示例-请替换成供应商名称` 2 |

> 顺带一个**数据卫生问题**：那两行 `示例-请替换成供应商名称` 是导入模板自带的示例行
> （`OTHER_PAYABLE_SAMPLE_ROWS`，金额 1200 / 86.5、内容「9 月厂房租金」「8 月快递费」），
> 有人把模板连示例一起导进了正式库，于是系统按名称**自动建了一个叫「示例-请替换成供应商名称」的供应商**。
> 本文件不改数据，但这条值得清掉（模板说明第 1 条已经写了「上传前请删掉或改掉示例行」，没人看）。

## 二、答第一问：系统里能填会计科目的地方，原先**一个都没有**

排查结论（这是本轮的根因，比「少一列」严重得多）：

| 单据 | 有没有会计科目字段 | 谁能填 |
| --- | --- | --- |
| **其他应付条目**（`supplier_payable_entries`） | ❌ **没有这一列** | —— |
| 「新建其他应付」弹窗 | ❌ 没有这一格（供应商 / 金额 / 币种 / 支出说明 / 确认日期 / 备注） | —— |
| 其他应付导入模板 | ❌ 没有这一列（供应商编码 / 名称 / 金额 / 币种 / 费用说明 / 确认日期 / 备注） | —— |
| 应付对账单（`SupplierPayableReconciliation.subjectId`） | ✅ 有 | 创建对账时**整体填一个** |
| 供应商付款单（`SupplierPayment.subjectId`） | ✅ 有 | 登记/合并付款时填 |
| 收支流水 / 收款单 / 工资付款单 | ✅ 有 | 建单时填 |

于是备用金的科目是**系统按来源类型猜**出来的：其他应付的来源类型是 `other`，
`PAYMENT_SUBJECT_NAMES.other = ["管理费用", "其他管理费用"]`（`accounting-subject-catalog.ts:348`），
候选链首位是**损益类「管理费用」**。

**这是错的，而且是账务性的错**：备用金在财务那张科目表里是**资产类「库存现金（备用金）」**
（同一份表里还有「其他应收款」）。钱出去了但**还是自己的资产**，记成管理费用等于凭空多一笔费用、
少一笔资产。房租（成本类「房租费」）、水电（成本类）同理 —— 它们的来源类型**全都是 `other`**，
一条候选链分不开它们，只能由录单的人指。

## 三、答第二问：会计科目和明细原先分别在哪些 column

| 导出件 | 会计科目在哪 | 明细（费用说明）在哪 |
| --- | --- | --- |
| **采购对账明细**（这张表） | ❌ 17 列里**没有** | ❌ 没有任何一列（62 行只剩空白） |
| 收支明细 | 「分类」列（科目类别）+「项目」列（科目名称） | 无 |
| 收支汇总 | 「分类」+「项目」，还按分类给小计 | 无 |
| 付款单（打印件） | 「总账科目」列，值取确认时实际记的那个科目 | 摘要 = 「支付<供应商><物料名>款」 |
| 应付台账（确认应付页导出） | ❌ 原先没有 | 「备注」列（但常写「银行转账」，不是费用说明） |
| 应付对账单 | 有（对账单上的科目） | 「纳入对账的应付条目」子表里有来源批次 |

**明细本来存在**，只是没进这张表：其他应付落库时把说明写进了
`source_no_snapshot = '其他应付-<说明>'`（`supplier-payable.service.ts:456`，说明被截到 30 字），
用户填的「备注」是**另一格**。所以「明细」有值可取，缺的是出口。

## 四、答第三问：明细写在哪一列 —— 用户选定「新增一列」而不是塞进订单号

用户原话是「能不能如果是其他应付，就在**订单号那边**写出明细」。我把两个方案摆出来问了，
用户选了 **新增一列「费用说明」**。理由（也是我不建议塞订单号的原因）：

- 「订单号」列的口径是**销售单号**（2026-09-20 用户要求加的，作用是回答「为哪张销售订单买的」）。
  同一列里既放 `DL260122` 又放「9 月厂房租金」，这一列以后按单号筛选/排序/透视全废，
  而且**没有列名能同时说清两种含义**。
- 报表是给人读的：财务扫一眼「费用说明」空着就知道这一行是采购行，不必先猜这一格里的东西是什么。

## 五、最终口径（本轮实现）

### 5.1 采购对账明细：其他应付**留在表里**，加两列

> ⚠️ 这**推翻了 2026-10-11 的处置**（`sourceType: { not: "other" }` 整行排除 + 表尾报笔数）。
> 用户 10-11 说「备用金不要进采购对账单」，10-12 说「排除之后看不到明细」——
> 两次都是同一件事的两面：她不要的是**认不出来的空壳行**，不是那笔钱本身。

| 改动 | 内容 |
| --- | --- |
| 取数 | `purchaseReconciliationDetail()` **去掉来源过滤**，返回 `{ rows, purchaseRowCount, otherRowCount }` |
| 列 | 17 列 → **19 列**：`费用说明` 紧跟「采购单号」之后，`会计科目` 插在合计列之前 |
| 合计列 | `[15,16]` → **`[17,18]`**（逐列数出来的；下标错了合计会悄悄落到别的金额列上） |
| 表尾 | 报「本表共 N 行：采购行 X 行 + 非采购支出（其他应付）Y 行」，并说明这两类行靠哪列认、科目在哪看 |

**两个新列的取值**：

- **费用说明** = `source_no_snapshot` 去掉 `其他应付-` 前缀；快照认不出来时回落用户填的「备注」。
  **不优先用备注**：备注是另一格（导入模板里常写「银行转账」「月结」），拿它当费用说明会让财务看到
  「这一笔花在 银行转账 上」。采购行恒为 `null`（空单元格）。
- **会计科目** = 条目上**手选过**才有值（`分类 / 名称`，与界面下拉、付款单同一写法 —— 见 `accountingSubjectLabel`）。
  **不替财务预写候选链**：其他应付没手选科目时，科目是**确认应付那一步**才按来源归类的
  （`other → 管理费用`）。报表上写出来就是一句「可能还没发生的归类」，而且备用金会被显示成一个费用科目 ——
  这张表是拿来核对的，宁可留空 + 表尾点名。

### 5.2 其他应付可以指定会计科目（两个入口）

| 层 | 改动 |
| --- | --- |
| 库 | `supplier_payable_entries.subject_id`（可空，外键 RESTRICT 到 `accounting_subjects`，带索引）——迁移 `20261013090000_other_payable_subject` |
| API | `POST /finance/payable-entries/other` 接受可选 `subject_id`，**建单时当场校验**（`cashFlow.requireSubject`：不存在/已停用 → 422） |
| 导入模板 | 新增「会计科目」列（别名：科目 / 科目名称 / 费用科目 / 总账科目），**可留空**；认不出或重名**按行报错、该行不入库**，好行照常 |
| Web | 「新建其他应付」加一格「会计科目（留空按来源自动归类）」，用可搜索下拉（120 多条科目靠滚动找不到） |

**科目优先级（本轮最容易写歪的地方，**五处**必须一致）**：

```
条目自己填的科目  >  对账单 / 确认弹窗的科目  >  按来源类型的候选链
```

| 入口 | 位置 | 写法 |
| --- | --- | --- |
| 一键确认应付（对账单） | `supplier-payable-reconciliation.service.ts` | `contra_subject_id: entry.subjectId ?? result.subjectId` |
| 确认应付（逐条） | `supplier-payable.service.ts` 的 `accrue` | `row.subjectId ?? options.subject_id` |
| 确认应付（勾选批量） | 同上（取数 `select` 必须带 `subjectId`） | 同上 |
| 付款单「总账科目」 | `finance-slip.service.ts` | `entry.subject` → 确认流水的科目 → 候选链首位 |
| 应付台账（页面 + 导出） | `supplier-payable.service.ts` 的 `ledgerSubjectName` | 条目 → 覆盖它的对账单 → `catalogSubjectLabel(候选链首位)` |

> 前四处是**写账**、最后一处是**显示**；显示的取值链故意与写账逐字对齐，
> 否则会出现「台账写着管理费用、凭证上却是别的科目」——那种偏差只有财务对账时才会发现。
> 复核（`docs/review/...2026-10-12.md`）正是在这里抓到「逐条/批量确认」两处漏了条目科目
> （备用金经那条路照样被记成管理费用），已修 + 补测试。

**为什么条目优先**：一张对账单可以同时含备用金、房租、水电（来源类型都是 `other`），
而对账单上的科目只有**一个**值 —— 拿它盖住所有条目，备用金又会被记成管理费用。
同理，批量确认弹窗的那个科目只在**条目自己没填**时才生效（前端也只在整批科目一致时才带出默认值，
不一致就留空，避免拿第一条的值盖住整批）。

**为什么迁移列可空、不回填**：历史行为（NULL = 没指定 → 走候选链）一字不变；
回填等于替财务决定历史账目，那是她的活。

### 5.3 连带项

- `AccountingSubjectService.usageCount()` 补上 `supplierPayableEntry`：外键是 RESTRICT，
  少数一张表 → 财务删科目时撞数据库约束（报错她看不懂）。
- 应付台账导出加「会计科目」列（`ledger-workbook.ts`，插在「备注」与审计四列之间）——
  用户问的就是「导出时科目在哪些 column」，台账是另一张她会看的表。
- 「新建其他应付」的 4 个表尾/落地文案与导入模板的填写说明同步提到科目。

## 六、遗留与待确认

1. **备用金到底该记哪个科目**是**会计判断**，不是技术选择：资产类「库存现金（备用金）」/
   「其他应收款」都可能对（取决于这笔钱是「预付出去要报销」还是「就是现金在谁手上」）。
   系统现在只是**把选择权交回去**，默认值仍是管理费用 —— 需要财务给一句口径。
2. **那条候选链的首位要不要改**：`other → 管理费用` 对「房租/水电/运费」是对的，对备用金是错的。
   在没拿到财务口径前不动它（改了会让所有历史的自动归类跟着变）。
3. **历史「已下单但单价是 0」的行**与本轮无关，但同样只有上服务器才查得到。
4. 那两行 `示例-请替换成供应商名称` 的应付（含自动建档的同名供应商）建议在正式库里删掉。

### 7.1 对抗性复核提出的三条缺陷与处置

复核报告在 `docs/review/other-payable-detail-and-subject-review-2026-10-12.md`，
其中三条「不通过」全部已修，并各自补了会红的守卫：

| 复核结论 | 处置 | 守卫用例 |
| --- | --- | --- |
| **（高）** `confirm` / `batchConfirm`（确认应付页的两条入口）挂账时**完全不看条目自己的科目**，备用金经这条路照样被记成管理费用；`batchConfirm` 的 `select` 连 `subjectId` 都没查 | `accrue` 改成 `row.subjectId ?? options.subject_id`；两条入口的取数都带上 `subjectId`；前端两个确认弹窗默认带出条目科目 | `supplier-payable-service.test.cjs`「条目自带科目时以条目为准」「逐条按各自的科目挂账」；`payable-page.test.tsx`「逐条确认弹窗默认带出条目自己的科目」「整批不是同一个科目时留空」 |
| **（中）** 迁移写 `RESTRICT` + 索引，`schema.prisma` 没写 `onDelete`（默认 SET NULL）、没有 `@@index` —— 两边永久漂移 | schema 补 `onDelete: Restrict` 与 `@@index([subjectId])`；迁移注释改成如实说明（`supplier_payments.subject_id` 那两处走的是 SET NULL，**不同形**，不要照抄） | 靠 `docs/review` 的静态核对；本仓库无法用 `prisma migrate diff`（无 `migration_lock.toml`） |
| **（中）** 应付台账的「会计科目」列只看 `row.subject`，看不到对账单级科目，可能与凭证不一致 | 台账改走与记账口径**逐字对齐**的三级链：条目 > 覆盖它的对账单 > 候选链（新增 `accountingSubject.findMany` 一次批量取科目） | `supplier-payable-service.test.cjs`「条目手选 > 对账单填的 > 按来源候选链」 |

仍写「16 列」。
