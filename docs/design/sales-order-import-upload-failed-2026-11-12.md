# 销售单 Excel 补录「读取失败」定位与修复（2026-11-12）

## 1. 用户原话与样本

> 针对销售模块的 excel 补录，用户反馈上传 excel，但是读取失败。

样本：`DL260003ZG-424038.xls`（1,520,128 字节，OLE2/BIFF8，sheet `D生产单模板`，A1:L65）。

## 2. 结论先说

**病灶在边缘，不在解析器。**

生产 nginx 的站点配置里从来没写过 `client_max_body_size`，于是吃 nginx 的默认值 **1m**。
这份 1.5MB 的样本在上传时被 nginx 在**转发之前**就以 `413 Request Entity Too Large`（HTML 错误页）挡掉：

- 请求**没有到达 API** —— 生产 `dilee-api-out.log` 里 `import-preview` 一条请求记录都没有（逐条 grep 过，只有路由注册行）；
- 前端 `response.json()` 解析 HTML 失败 → `body` 为 null → 落到兜底文案「读取失败」，
  而那句话的后半截是「请确认文件没有损坏、且是 .xlsx / .xls」——**这句话把排查方向指到了文件上**。

同一台机器上实测（`curl` 直发边缘，未登录，未登录必 401 说明请求到达了 API）：

| 上传体积 | 修复前 | 修复后 |
|---|---|---|
| 300 KB | 401（穿过） | 401 |
| 900 KB | 401（穿过） | 401 |
| 1,100 KB | **413** | 401 |
| 1.5 MB（真实样本） | **413** | 401 |
| 5 MB | **413** | 401 |

分界正好在 1MB —— 这就是「nginx 默认值」的指纹。

## 3. 为什么以前没人发现

1. **这层配置不在仓库里**。站点配置只存在于服务器 `/etc/nginx/sites-available/dilee`，来源是
   `.deploy-run-118/16-nginx.sh`，而 `.deploy-run*/` 被 `.gitignore` 排除。于是边缘既没有版本、
   也没有测试、也不在部署标准的范围内。
2. **开发环境没有这一层**。开发时前端 `next` 直接把 `/api/v1/*` 反代到 API，6.9MB / 8.6MB 的两份
   `example/销售单/` 样本都能跑通 —— 功能「在开发机上是对的」。
3. **错误面把原因吃掉了**。`413` 走的是 HTML，前端只留一句「读取失败」，
   连状态码都没露出来。

## 4. 修复（三层，缺一层就会复发）

### 4.1 边缘：把配置纳入仓库并设上限

- 新增 `scripts/deploy/nginx-dilee.conf`：站点配置的唯一来源，显式 `client_max_body_size 20m`
  （**边缘只能比应用宽，不能比应用窄**：应用侧 Multer `limits.fileSize = 10MB`，前端
  `SALES_ORDER_IMPORT_MAX_BYTES` 同一个数；20m 是给 multipart 边界留的余量）。
  同时给 `client_body_timeout` / `proxy_read_timeout` 120s：大 Excel 解析偶发超过 nginx 默认 60s，
  超时同样会表现成「读取失败」。
- 新增 `scripts/deploy/remote-nginx.sh`：幂等安装 + `nginx -t` + 平滑重载 + **实测**（真发一个
  10MB 的上传包过边缘，413 即失败；期望 401 = 请求确实到达 API）。
  这里刻意**不看配置文本、只看实测**：文本对而 worker 没换，一样是坏的。
  探针体积取 10MB 而不是「比 1m 大就行」的 2MB：探针要证明的是**产品承诺成立**，
  只传 2MB 的话，把边缘悄悄调回 5m 也照样绿 —— 那正是这次故障的形态。
- `scripts/deploy-incremental.ps1` 第 6/6 步调用它 —— 配置漂移每次部署都会被拉回，且失败会终止部署。

### 4.1.1 「单文件上限 10MB」按字面成立（用户 2026-11-12 明确）

查这件事时顺手发现应用侧的 10MB 是**排他的**：Multer/busboy 在 `>= limits.fileSize` 时判超限，
所以 `fileSize: 10 * 1024 * 1024` 之下，**正好 10MB（10,485,760 字节）的文件会被拒**，
10,485,759 才能过（本地实测）。既然口径写的是「单文件 10MB」，就得让 10MB 这一格能过。

- 新增 `apps/api/src/platform/http/upload-limits.ts`：`MAX_DOCUMENT_UPLOAD_BYTES = 10MiB`（产品口径）
  与 `MULTER_DOCUMENT_FILE_SIZE_LIMIT = 上限 + 1`（给 Multer 的数，注释里写清为什么 +1）。
- 5 个文档导入端点（销售单 / 物料 / 盘点 / 员工花名册 / 其他应付）改用它，不再各写一遍裸数字 ——
  「同一个 10MB 抄 5 遍」正是这次「应用 10MB、网关 1MB」能长出来的土壤。
- 实测（本地 API，带登录态）：10,485,760 → 通过体积门（422「没认出任何字段」= 进了解析器）；
  10,485,761 → 413 `File too large`。
- 前端 `SALES_ORDER_IMPORT_MAX_BYTES` 保持 10MB、判据是 `>`，与后端同一边界。

### 4.2 前端：不同的失败说不同的话

`apps/web/lib/sales-order-import.ts` 新增 `importFailureMessage({ status, serverMessage, fileSize })`：

| 情况 | 以前 | 现在 |
|---|---|---|
| 413 | 「读取失败：请确认文件没有损坏…」 | 「文件太大，被服务器网关挡在门外（这份文件 1.4MB）…请管理员检查边缘 nginx 的 client_max_body_size」 |
| 401 | 同上（把登录过期说成文件问题） | 「登录已失效，请重新登录后再传这份文件」 |
| 403 | 同上 | 有服务端原话就用原话，否则「没有补录权限…」 |
| 502/503/504 | 同上 | 「服务器暂时不可用（HTTP 5xx），请稍后重试」 |
| 无业务信封 | 同上（状态码不露出） | 「读取失败（HTTP 500）：服务器没有返回可识别的错误内容」 |

页面也改成先 `response.text()` 再尝试 `JSON.parse`：网关的 HTML 错误页不再把整条原因吃掉。

### 4.3 解析器：这份样本本身读错的地方

见 §5。这些**不是**「读取失败」的原因（请求根本没到解析器），但网关修好之后用户会立刻看到它们，
所以一并修掉。

## 6. 验证

- 边缘（生产实测）：1.5MB 样本 `413 → 401`；`remote-nginx.sh` 在服务器上跑通（2MB 探针 401）。
- 守卫测试 `npm run test:deploy`：新增 3 条，钉住「配置必须进仓库」「上限不许窄于应用」
  「必须实测且 413 即失败」「探针必须可重试（平滑重载期旧 worker 仍会接连接）」。
- 前端 `apps/web/lib/sales-order-import.test.mjs`：新增 6 条，钉住各状态码的文案分离。
- 解析器 `apps/api/test/unit/sales-order-import.test.cjs`：新增本样本的断言，原有两条 `example/销售单/` 样本全绿。

## 7. 刻意不做

- **不给 nginx 加 443/证书**：与本缺陷无关，且涉及域名与证书，另立一单。
- **不把边缘上限提到「无限」**：上限是保护，不是麻烦；错的只是「边缘比应用窄」。
- **不在前端直接读 Excel**：解析口径（版式驱动、不猜、不丢）已经在服务端且被 30+ 用例钉住，
  挪到浏览器等于把同一套口径写两份。

## 8. 已知边界（登记，不在本轮解决）

- 生产 `ecosystem.config.cjs` 里 web 的 `API_INTERNAL_URL` 没显式配置，Next 的 rewrite 目标
  落到默认 `http://localhost:3001`。同机可用，但一旦 API 换端口/换机就会静默失效 ——
  本次故障里这条 rewrite 并未参与（浏览器走的是 nginx `location /api/` 直连 API）。
- `Next.js` rewrite 在**上游提前关闭连接**（例如未登录时 API 立刻 401）时会 `write EPIPE` 并回 500。
  走 nginx 时不会命中这条路径，但直接访问 3000 端口会。
