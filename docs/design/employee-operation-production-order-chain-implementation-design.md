# 员工、工序池与生产单链路实现设计

> 文档类型：跨模块纵向链路开发设计
>
> 链路：员工/部门岗位 -> 工序池与工序计价 -> 生产单（厂内/外加工分支）
>
> 对应路线图：D1-D3，补充 A7、B4 的必要最小能力
>
> 状态：待开发

## 1. 问题陈述

当前系统已经具备已确认销售单、`order_no`、已发布 BOM、物料采购和原料库存事实，但还不能把订单转成可追溯的生产任务。物控员需要为订单建立生产单，选择厂内车间或外加工点，并从全厂共用工序池中选取实际工序；后续仓库领料、车间日报、成品 QC 和薪资都必须以这些稳定对象为来源。

若先做领料、日报或薪资，系统将不得不依赖手工文本或未受控的工序名称，无法保证订单号、人员、工序和生产单的一致性，也会使后续的审计、告警和回退失去可靠边界。

## 2. 方案与边界

本批交付下列可用闭环：

```text
已确认销售单 + 已发布 BOM
  -> 维护部门 / 岗位 / 员工
  -> 维护工序池、工序计价与执行地点
  -> 以 order_no 创建生产单
  -> 为厂内生产单选择并排序工序任务
  -> 启动、暂停、完成、关闭生产单
```

生产单是订单生产任务的汇总对象，不记录每日报工。`order_no` 是跨模块可见的订单身份证；所有关系使用 UUID 外键，同时在生产事实中冗余保存 `order_no` 以支持查询、导出和人工核对。

外加工只建立必要的订单、地点、数量、状态和工序说明追溯，不录入外加工现场日报、员工薪资或生产进度。外加工直发物料、回厂/直装柜成品、加工费和质量交接留给后续 D4-D7、E1-E5 与财务链路。

## 3. 用户故事

1. 作为管理员，我要维护部门和岗位，并停用不再使用的记录，以便员工资料具有稳定组织归属且不破坏历史。
2. 作为管理员，我要维护员工目录、在职状态和可选系统账号，以便后续生产日报和薪资可准确指向员工。
3. 作为物控员，我要维护全厂共用的工序池，以便每张生产单都从统一术语中选择工序。
4. 作为物控员，我要维护员工加工作业的计件/计时单价和生效日期，以便后续日报能取得正确的价格快照。
5. 作为物控员，我要维护厂内车间和外加工点，以便生产单准确表达实际执行位置。
6. 作为物控员，我要基于已确认订单和已发布 BOM 创建标准生产单，以便将订单需求转为厂内可执行任务。
7. 作为物控员，我要为同一订单新建补单、返工单或拆分单，并关联父生产单和原因，以便保留订单的完整生产历史。
8. 作为物控员，我要在厂内生产单中选择、排序和调整工序任务及目标数量，以便实际工艺不受固定模板限制。
9. 作为物控员，我要让系统保存工序名称和单位快照，以便工序池后续调整不会改写历史生产单。
10. 作为物控员，我要启动、暂停、恢复、完成和关闭生产单，并在例外完成或关闭时填写原因，以便生产推进可追溯。
11. 作为操作员，我要按订单号、生产单号、执行方式、地点和状态查询生产单，以便定位订单当前生产任务。
12. 作为操作员，我要查看生产单的操作审计和关联附件，以便追溯谁在何时因何原因改变了生产任务。
13. 作为仓库操作员，我要获得有效厂内生产单及工序任务的稳定引用，以便下一批实现领料、退料和报废时不重复定义来源关系。
14. 作为生产负责人，我要让外加工生产单不要求外加工点登录或提交日报，以便 ERP 仅记录迪礼需要管理的边界事实。

## 4. 实施决策

### 4.1 领域对象与数据约束

| 对象 | 关键字段/关系 | 约束 |
| --- | --- | --- |
| 部门 | 名称、编码、启用状态、备注 | 名称和编码在有效记录中唯一；禁止物理删除。 |
| 岗位 | 部门、名称、编码、启用状态、备注 | 可被多个员工引用；停用后不可用于新员工。 |
| 员工 | 工号、姓名、部门、岗位、员工类型、在职状态、可选用户账号、入离职日期、备注 | 不保存身份证和银行卡；已被日报或薪资引用后只能停用。 |
| 工序池 | 工序编码、名称、默认单位、启用状态、备注 | 全厂与外加工共用；禁止物理删除；已引用工序仅可停用。 |
| 工序计价 | 员工、工序、计薪方式、单价、生效日、失效日、备注 | `piece_rate` 与 `time_rate` 分开维护；日期范围不得重叠；仅为后续日报提供候选单价。 |
| 执行地点 | 名称、类型、启用状态、联系人、电话、地址、备注 | `workshop` 表示厂内车间，`outsource_site` 表示外加工点；停用地点不可用于新生产单。 |
| 生产单 | 生产单号、订单 UUID、`order_no`、BOM UUID/版本快照、类型、父生产单、执行方式、地点、计划数量/单位、产品规格、工艺说明、状态和日期 | 一个订单默认创建一个标准生产单，但不建立数据库唯一约束阻止人工扩展。 |
| 生产单工序 | 生产单、工序池、工序名称/单位快照、顺序、目标数量、取消标记与原因 | 厂内生产单启动前至少一项有效工序；同一生产单中的顺序唯一。 |

所有新表使用 UUID 主键、`created_at`、`updated_at`、`created_by`、`updated_by`、逻辑删除字段及备注字段；所有修改、状态动作和逻辑删除均写统一审计日志，保留执行人、审批人预留字段、时间、原因、前后值和关联 `order_no`。

### 4.2 订单与 BOM 关联

- 仅已确认销售单可创建生产单；创建时必须填写 `order_no`，服务端据此解析订单 UUID，禁止客户端传入不一致的双重来源。
- 生产单记录创建时的已发布 BOM UUID 与版本号快照。BOM 不是本批生产单的实时从属明细；后续 BOM 变更不得静默改写生产单。
- 标准生产单为默认类型；`supplement`、`rework`、`split` 必须关联同一订单下的父生产单并填写原因。
- 生产单号由服务端生成，格式遵循全局派生单号规范；不得替代人工录入的 `order_no`。

### 4.3 厂内与外加工分支

- `execution_mode = in_house` 必须引用 `workshop`，草稿转生产中前至少有一条有效工序任务。
- `execution_mode = outsourced` 必须引用 `outsource_site`；可选维护工序作为工艺说明，但本批不创建外加工日报、进度和超单数据。
- 执行方式和执行地点类型必须一致。草稿可调整；一旦进入生产中，改动执行方式或地点必须经过影响预览、填写原因并写审计事件。

### 4.4 生产单状态机

```text
draft -> in_progress <-> paused -> completed -> closed
                           \-> completed
completed -> in_progress  (恢复原因必填)
```

- 仅草稿可逻辑删除，且必须填写删除原因。
- 草稿进入生产中前校验订单、地点、计划数量、单位；厂内生产必须存在有效工序任务。
- 暂停状态不允许后续批次新增或编辑日报；本批虽不实现日报，但状态机必须预留该服务端门禁。
- 生产中转已完成、已完成转已关闭均要求原因；本批不以日报或完成数量自动阻止转换。
- 返工不重新打开原生产单，而是在同一订单下建立 `rework` 类型生产单；已关闭单恢复为生产中必须记录恢复原因。

### 4.5 接口与页面

REST API 位于版本前缀下，统一返回 JSON 信封与全局错误格式。至少提供：

- 部门、岗位、员工、工序池、工序计价和执行地点的列表、创建、编辑、停用/恢复接口；停用不是物理删除。
- 生产单列表、详情、创建、编辑、逻辑删除、状态动作、影响预览和审计查询接口。
- 生产单工序的新增、编辑、排序、取消接口；取消已有下游日报的工序只做状态变更，不删除历史。
- 订单查询接口可返回可用于创建生产单的已确认订单、已发布 BOM 与现有生产单摘要，避免前端拼接跨域数据。

前端在生产模块提供三类页面：生产基础资料、生产单列表、生产单详情/编辑。使用既定 TanStack Table、shadcn/ui 与 React Hook Form；表单只展示本批字段，产品规格与工艺说明采用可选预留区，不假设未确认的工艺模板。

### 4.6 权限与附件

- 管理员拥有基础资料和生产单全权限；物控拥有工序、计价、地点及生产单维护权限；其他角色默认只读或无权，具体模块授权复用现有 RBAC。
- 生产单复用统一 `attachment`：可关联产品图片、工艺资料、客户要求、变更说明、外加工交接资料及其他附件。附件不强制上传。
- 所有拒绝操作使用已有稳定错误码体系；状态非法使用 `INVALID_STATE_TRANSITION`，下游事实存在时使用 `DOWNSTREAM_RECORD_EXISTS`，无权限与资源不存在复用平台错误码。

## 5. 测试决策

最高测试缝隙是生产模块 REST API。它必须以真实 PostgreSQL 测试库验证业务可见结果，不针对 Prisma 或页面内部实现断言。

沿用现有测试分层：Node `node:test` 规则测试、HTTP/API 合同测试、真实 PostgreSQL 集成测试、Playwright 浏览器测试，并将通过结果写入 `docs/test/results/`。

至少覆盖：

1. 已确认订单和已发布 BOM 可创建标准厂内生产单，订单 UUID、`order_no` 和 BOM 版本快照一致。
2. 未确认订单、未发布 BOM、订单号不一致、无效地点类型、零或负计划数量均被拒绝。
3. 同订单可创建补单/返工/拆分单，但必须有同订单父生产单和原因；不阻止多个生产单。
4. 停用员工、工序或地点不可用于新记录，历史引用及快照仍可查询。
5. 厂内生产单启动前必须有工序，外加工生产单可无工序；执行方式与地点类型不一致被拒绝。
6. 状态机允许和拒绝的转换符合定义；草稿删除、恢复完成单和关闭均生成审计事件。
7. 工序排序、目标数量和取消操作保留审计；存在后续日报时取消而非删除的保护由后续 D5 测试补充。
8. 浏览器以物控身份维护工序、创建厂内生产单并启动；匿名用户跳转登录、无权限用户看到可见错误。

## 6. 不在本批范围

- 原料领料、退料、报废、外加工直发和库存变动。
- 工序日报、员工计件/计时日报、超单与日报差异告警。
- 成品送检、成品 QC、成品入出库、应收来源与发货。
- 考勤、绩效、薪资汇总、工资支付和外加工费用结算。
- 自动排产、产能计算、移动端、离线操作，以及外加工点登录 ERP。
- 生产工艺模板、复杂产品规格、产品维度计价规则；待生产和物控负责人确认后再扩展。

## 7. 后续衔接

本链路完成后，D4 以有效厂内生产单和工序作为领退料来源；D5 以工序任务、员工和工序计价作为日报与薪资参考来源；D6 在外加工生产单基础上增加直发与回厂/直装柜事实；D7 汇总生产进度和告警。

在开始编码前，需由生产负责人确认首批部门、岗位、员工类型、工序、计价口径和执行地点的初始数据；这些是运营数据，不应硬编码进 schema 或前端选项。
