## 一、备用金不该出现在采购对账明细表（真缺陷）

### 1.1 根因

「备用金」在系统里是**资产类科目**（`资产类 / 库存现金（备用金）`，见
`apps/api/src/modules/finance/accounting-subject-catalog.ts:35`）—— 它是钱从银行取出来放在手边周转，
**不是欠供应商的货款**。

但财务录入它走的是「其他应付」（手工新建或 Excel 批量导入），而**其他应付落库时就是一条
`supplier_payable_entry`**，`source_type = "other"`（见 `supplier-payable.service.ts` 的 `otherEntryData`）。

而采购对账明细表原来的 `where` **一个来源类型都没筛**：

```ts
// 修改前
this.prisma.supplierPayableEntry.findMany({
  where: { deletedAt: null, status: { in: [...] }, ... },
```

于是备用金、房租、水电、运费全进了采购对账明细表。这些行**没有供应商物料、没有数量、没有采购单**，
在表里就是一排对不上的空壳 —— 财务逐行核对时永远对不平，而她对不平的第一反应只能是怀疑整张表。

### 1.2 改法

**按来源收窄**（`sourceType: { not: "other" }`），而不是白名单：

- 采购对账取的是「原料入库 / 采购到货 / 外加工签收」三类，用 `not` 让**将来新增的采购类来源自动进表**，
  只有非采购的其他应付被挡住（写白名单则每加一种来源都要记得回来改这里，漏改就是静默漏数）；
- `schema.prisma:1349` 的 `sourceType` 是 `String`（**非空**），所以 `not: "other"` 不会连 NULL 一起漏掉
  —— 这一条是特意查过的，可空字段上写 `not` 会静默丢掉所有 NULL 行。

**为什么不干脆把其他应付从「应付」里摘掉**：其他应付确实是应付，它进**应付对账**是对的
（`docs/design/other-payable-batch-import-2026-09-16.md`：其他应付导入后立刻出现在应付对账 → 待创建对账）。
本轮只把**采购**对账明细表收窄，不动应付侧任何口径。

**排除必须在表尾点名**：这张表里原本**有**那些行，现在不见了。只删不说的话，财务对不上时
只能靠回忆「是不是上个月还有一笔备用金」，且无从知道是被有意排除还是导出漏了。所以取数层
额外数一遍被排除的笔数（`excludedOtherCount`），表尾写：

> 本表不含「其他应付」N 笔（备用金 / 房租 / 水电 / 运费等非采购支出）：采购对账按供应商与物料数量
> 逐项核对，这些条目没有采购单与物料，故不纳入本表。它们仍在「应付管理 → 应付对账」与
> 「收支管理 → 收支流水」里。

句子的后半段是刻意的：只说「不含」会读成「这些钱不在系统里」，给出去处才算说清。

### 1.3 一个必须一起改的连带项：返回类型

`purchaseReconciliationDetail` 从 `Promise<T[]>` 改成
`Promise<{ rows: T[]; excludedOtherCount: number }>`，controller 的 `tableFor` 分支相应解构。

**被排除的笔数必须与主查询同一筛选范围**（共用一个 `scope` 对象）：否则财务筛了某个供应商，
表尾却报出全公司的备用金笔数，那句话就成了假话。单测里有一条逐键比对两个 `where` 的守卫
（`finance-report-query-service.test.cjs`）。

## 二、生产月报表新增「工序月度汇总」sheet

### 2.1 需求形状

用户确认选 **乙**：要「**一行一个工序 × 全月跨所有订单汇总**」的表，而不是已有的
「一个订单一行 × 工序横向展开」。

**为什么财务需要它**：核算表的「计件人工」就是（`employee_daily_reports.calculated_amount`
按 `order_no` 归集后）按工序逐道累加出来的；她拿一张按工序汇总的表才能和账对上。
总表回答的是「哪张单做到哪道工序了」，回答不了「这个月缝伞一共做了多少、花了多少人工」。

### 2.2 位置与形状

工作表顺序改为：**总表 → 工序月度汇总 → 每道工序一张明细**。

汇总紧跟总表而不是放最后：财务翻这份文件先看「哪张单做到哪」，紧接着看「这个月每道工序多少」，
再往下才是逐工序逐工人的明细。明细 sheet 有十几张，汇总放最后等于每次都要翻到最后。

| 工序 | 执行方式 | 单位 | 数量 | 计件金额（元） | 工时（小时，仅计时） |
| --- | --- | --- | --- | --- | --- |

### 2.3 四条口径（都写进了代码注释与 sheet 表头）

1. **与总表共用同一份 `cells`（同一套逐日取大结果），但切法不同 —— 是加总关系，不是单格相等。**
   总表按**工序列**切，而一列可能把多个东西并进同一格（字典名与客户叫法 `验片`/`验伞面`、
   以及未按执行方式拆分的工序列里本厂与外发两批活）；本表按 **(工序, 单位, 生产单执行方式)**
   切成明细行。所以成立的是：

   > **本表同一道工序各行相加 = 总表该工序列各订单格子相加。**

   单看一行可能小于总表那一格（总表把几批活并成了一格），这不是算错。

   ⚠️ **第一版这里写错了，代价值得记下来**：原话是「数量与总表对应工序列**同一个数**」，
   而且分组键用的是**原始工序快照名**。后果是同一道工序在两张表里对不上：
   别名 `验伞面` 与字典名 `验片` 在总表是**同一列**（合计 300），在本表却成了**两行**
   （各 100 / 200）—— 而且两行的工序列显示的都是「验片」，看起来像系统把同一道工序重复统计了。
   修法是**分组键改用总表列名**（`labelFor`），别名真正合成一行；单测里加了别名用例钉住
   （断言「只能有一行验片、绝不能有验伞面那一行」）。
2. **分组键是 (工序列名, 单位, 生产单执行方式)**：
   - 单位进键 = 全站纪律「数量不跨单位合计」（`reorder.domain.ts:11`）。`包装` 同时有「支」和「打」时
     出两行，绝不相加成一个 64；也正因为单位进了键，每一行内部单位必然一致，数量永远给**数值**
     （不会退化成「60 支 + 4 打」这种文本，Excel 里那样就没法求和/筛选）；
   - 执行方式进键 = 本厂与外发是**两批不同的活**（同一道工序名不等于同一批货）。`拉边` 因此
     出「本厂 / 外发」两行；
   - 金额是元，不受那条纪律约束，跨单位照常各自累计。
3. **金额与工时只来自员工日报**（只有它有员工维度与计薪方式），所以两列不做等值假设：
   那天只有员工面报了数而被工序面顶掉时，数量会取更小的工序面（甚至 0），金额却照记 ——
   sheet 表头写明了这是正常现象而不是漏算。
4. **工时只统计计时行**（`wageMode === "time_rate"`），且**没有计时工时是留空而不是 0**：
   计件行不产生工时；一行是一道工序的全月汇总，全月没有任何计时行时它不是「零工时」这个事实，
   而是「这道工序这个月没有计时工」—— 写 0 会被读成「有计时工但一小时都没干」。
   与「计件人工 = 0 与收入 = 空是两件事」同一条取舍（见 `finance-report.tables.ts`）。
   为此单独加了 `hoursOrBlank`，**没有改 `hours()`**（明细表那一行的 0 分钟是真的「报了 0 小时」）。

**合计行的数量刻意留空**：一行一个单位，跨行相加要跨单位（全站纪律）。金额与工时照常合计。

### 2.4 空月份

不给一张只有表头的空表，而是给一行「（本月无生产日报数据）」+ 一行合计（数量空、金额 0）：
空白表格分不清「没数据」和「导错了」，这与「原料对应表」的「（无采购记录）」同一做法。

## 五、未处置 / 待确认

1. **管理费的筐到底装什么**（财务第 1 条）——**没动**。她说的「除原材料以外的所有费用」是**定义**，
   而系统现在的做法是「财务手工填一个总额」（`overhead_allocations`），两者差别在于：
   运费 / 外加工费 / 管理人员工资如果在系统里记成了其他应付或收支流水，**现在一点都不会进核算表**。
   两条必须她先回答：
   - 是**手工填总额**，还是要系统**自动汇总**这个月的费用流水？
   - 若自动汇总，**哪些科目算进这个筐**（科目表 121 条，不圈定就必然算错）？

   ⚠️ **更要紧的风险**：若改成自动汇总，她在面板上手填的那笔（如 22 万）可能被**重复计一次**。
   这条口径不确认就动手，做出来的表会静默多算一块费用。
2. **销售对账汇总表加「数量 / 加权平均单价」**（财务第 2 条）——**没动**。指认到
   `SALES_RECONCILIATION_SUMMARY_COLUMNS`（10 列，只有「销售金额」一个金额列），这不是 bug：
   当年是照抄她给的 `销售对账汇总表.xls`（那张表本身只有表头没有数据）。要加的话须先确认
   「单价」是**加权均价**（金额 ÷ 数量）还是别的口径 —— 汇总表一行一张单，逐行单价不能相加。
3. **`not: "other"` 是排他而非白名单**：将来若出现第五种来源类型且它**不是采购类**（例如某种纯手工
   计提），它会自动进表。当前四种来源已穷尽（见 `supplier-payable.domain.ts` 的三类 + `other`），
   所以按当前模型是对的；新增来源类型时需回到这里确认一次。
4. **真实 PostgreSQL 未跑**：本轮两个改动都只在假 prisma / 内存夹具上验证。`source_type` 的
   `not` 语义依赖 Prisma 生成的 SQL（`<> 'other'`），建议上线后在真实库上导一次采购对账单确认
   备用金确实不在表里、且表尾笔数与「应付对账」里的其他应付条数一致。
5. **工序汇总的「计件单价」列没做**：财务口头提过单价，但同一道工序全月往往有多个单价
   （夹具里缝伞就有 0.3 与其他），一列放不下一个数，取平均值在计薪争议时最容易被误读。
   本表只给**数量 + 计件金额**，需要单价时用金额 ÷ 数量自算。若她要的是逐单价的分布，那是另一张表。
