# 销售的分批出库通知与成品出库总览（2026-09-16）

## 来源需求（用户原话）

> 「销售模块，成品出库这边，支持分批出库。给仓库发出库通知。仓库再选择出库。
> 销售模块还要支持查看当前全部成品数，已出库数，未出库数」

用户对三条追问的选择：

1. **分批的主动权**：销售通知时就能填数量（默认全部可出库，可只通知一部分，余量以后再通知）
   **+** 仓库再按通知分批实际出库；
2. **三个数字放哪**：销售页顶部给**全部销售单合计**，打开某张销售单详情再给**该单合计**与逐生产单明细；
3. **口径**：全部成品数 = 累计成品入库量；已出库数 = 累计已过账/已发出/已签收出库量；
   未出库数 = 全部 − 已出库；并且**按「产品 + 单位」分行列**。

---

## 一、先盘点：这条链路的「分批」缺在哪一段

改前逐个查证（读代码 + 读既有测试）：

| 环节 | 改前状态 |
| --- | --- |
| 仓库按通知建出库单 | ✅ **本来就支持分批**：`createOutboundFromNotice` 不传数量按剩余量建单，传了只出一部分；数量 ≤ 通知剩余量且 ≤ 库存余额 |
| 通知状态随累计出库推进 | ✅ `syncNoticeStatus`：`pending → outbound_created（有草稿）→ partially_outbound → completed` |
| 草稿取消退回剩余量 | ✅ `cancelOutbound` 会重新推导通知状态 |
| 仓库页展示剩余可出库量 | ✅ 「已出库 / 剩余」列 + 建单弹窗默认值 = 剩余量（含「可分批出库」提示） |
| **销售按部分数量发通知** | ❌ **缺**：`POST /sales-orders/:id/outbound-notices` 不接收数量，服务端把 `noticeQuantity` 写成当时**全部**可出库量；界面按钮写死「整批出库」 |
| **销售模块看三个数字** | ❌ **缺**：只有打开某张销售单才看得到该单的情况，且没有「全部 − 已出库」这个数 |

**所以本轮真正要补的是销售这一段。** 用户说的「仓库再选择出库」在系统里已经成立，
本轮只做了两件事：把它与销售的「分批通知」接成一条完整链路，以及把三个数字摆到销售页面上。
仓库侧代码**一行没改**，仓库那 9 条既有用例（默认出剩余量 / 改小数量 / 部分出库后继续出库 /
幂等键 / 失败不误报）本轮原样通过。

## 二、做法

### 1. 销售通知可以只通知一部分

- `OutboundNoticeDto` 新增可选 `notice_quantity`（`@EmptyStringToUndefined` + 十进制正则，
  空串按「未填写」处理 —— 否则表单留空会 400）；
- `createNotices` 里数量走平台统一的 `parseQuantity`（拒绝 `NaN` / `0` / 负数 / `1e3` / 超过 4 位小数；
  `NaN` 特别危险，它会绕过所有数量比较）；
- **不传数量仍是整批**（保持原行为，销售页的「通知仓库出库（全部可出库批次）」不受影响）；
- 传了数量就**必须 ≤ 当前可出库量**，超过报 422 `OUTBOUND_NOTICE_QUANTITY_EXCEEDED`，
  并在 `details` 里给出 `available_quantity` / `requested_quantity`。
  **不静默截断**：截断会让销售以为整批都通知了，余量悄悄留在手里；
- **按数量通知必须指定生产单**（`OUTBOUND_NOTICE_QUANTITY_REQUIRES_PRODUCTION_ORDER`）：
  一张通知只对应一个生产单，不指定生产单时一次会建多张通知，把同一个数量套到每个批次上
  用户无法预期。

数量在事务内、锁住生产单行之后再与「当时可出库量」比较，因此与仓库建单/过账并发也不会超发。

### 2. 三个数字只留一份算法

`unshippedQuantity(入库, 出库) = max(入库 − 出库, 0)`，被「销售单合计」与「模块总览」共用：

- **全部成品数** = 该生产单 `status = posted` 的成品入库合计（草稿不算）；
- **已出库数** = `posted / shipped / signed` 的出库合计（草稿、已取消、已冲销不算）；
- **未出库数** = 全部 − 已出库，也就是「还在成品仓里的」（含已通知仓库但还没建单/还没过账的）；
- **下限保护**：客户退货回仓会让实际库存高于「入库 − 出库」（退货不是「未出库的成品」，
  按用户确认的口径不计入），出现负数说明数据异常 —— 显示负数会被当成系统错误，所以夹到 0。

### 3. 总览按「产品 + 单位」分行，**不做跨单位合计**

`GET /sales-orders/finished-goods-summary` 返回 `{ production_order_count, groups[] }`，
`groups[]` 每行是 `{ product_name, unit, inbound_quantity, outbound_quantity, unshipped_quantity, production_order_count }`。

- 分组键是 `产品名 + NUL + 单位名`（NUL 连接，产品名里有空格/斜杠时不会与单位名串味）；
- **故意不给一个跨产品的总计**：系统里不同销售单的单位并不统一（件 / kg / 套），
  加起来是一个没有业务含义的数，还会让「未出库」看起来像能一起发货；
- 范围是**所有非取消销售单下的非取消生产单**（含还没入库、还没出库的 —— 销售要看到的就是「全貌」）；
- 实现是 3 条查询（1 条生产单 + 2 条 `groupBy`），不是按生产单逐条聚合（生产单一多就是 N+1）。

销售单详情里 `summary()` 另外返回 `totals[]`（同一套 `totalsRow` 形状，按产品+单位把明细行折起来），
销售页在明细行上方显示「连衣裙 件 · 全部成品 90 · 已出库 10 · 未出库 80」。

### 4. 路由顺序：静态段必须声明在 `:id` 之前

`@Get("finished-goods-summary")` **必须**声明在 `@Get(":id")` 之前 —— Nest 按声明顺序匹配，
否则 `finished-goods-summary` 会被当成销售单 ID 去查库（与「其他应付导入模板被 `:id` 吃掉」同类问题）。
代码里留了注释，契约测试里留了护栏（单段静态路径必须命中自己的处理器、返回 `groups` 数组）。

### 5. 前端（`apps/web/app/sales/page.tsx`）

- **顶部的「成品出库总览」面板**：表头就是用户说的三个词（全部成品数 / 已出库数 / 未出库数）+
  生产单数，面板说明写清口径与「不同单位不做合计」；带「刷新」（仓库发货后销售能自己刷出新数字）。
  **独立加载、独立错误态**：总览挂了不影响客户池与销售单两张表，也不停在「正在加载」；
- **销售单详情**：`totals` 一行合计 + 原有的逐生产单明细；
- **「通知仓库出库」按钮改成弹窗**：`本次通知数量`（默认 = 该行可出库量，占位文案写明
  「可出库 X 件（可只通知一部分，余量以后再通知）」）+ `备注`；
- 弹窗失败**抛错**（不 `notifyError` + return）：`ActionDialog` 会把服务端原因显示在弹窗里、
  保留用户已填的数量；用 toast 的话弹窗会被关掉、手里的数量跟着丢（第十四轮的教训，
  仓库页已经这么做了）；
- 成功提示用**服务端返回**的通知号与数量（`已通知仓库出库：OGN-… 本次 20 件`），
  不用用户输入的数字 —— 服务端才是权威。

## 三、为什么仓库侧一行没改

用户说的「仓库再选择出库」在系统里已经存在（见 §一表格）：仓库页的「成品出库通知（销售发起）」
表本来就有「已出库 / 剩余」两列，点「生成出库单」弹窗里默认出剩余量、可以改小，
并把数量与幂等键一起发给 `POST /finished-goods/outbound-notices/:id/create-outbound`。
本轮把它接进分批链路后，完整流程是：

```
成品入库 → 销售「通知仓库出库」本次 20（可分批）
        → 仓库页看到剩余 20 → 选择实际出库数量（本次 12）→ 生成出库单 → 过账 → 生成应收
        → 通知变为 partially_outbound，剩余 8 可再出库（或销售取消剩余）
```

## 五、未执行 / 已知缺口

- **没有真实 PostgreSQL**：`notice_quantity` 的落库、`groupBy` 的两条聚合 SQL、
  `FOR UPDATE` 下的并发都不算端到端验证过（本机没有任何数据库，migration 也从未跑过）；
- **总览是「进页面/手动刷新」的快照**：仓库发货后销售不刷新就看不到新的已出库数，
  没有轮询也没有推送（与系统里其它「待办」一致 —— 不进页面就不知道）；
- **总览不能搜索/筛选**：产品一多会很长。若要按客户/订单收窄，需要后端支持参数；
- **`groupBy` 用了 `productionOrderId: { in: ids }`**：生产单数量极大（上万）时这条 `IN` 会很长，
  届时应改成按关系过滤或用一条原生 SQL 聚合；
- **分批通知没有「剩余量提示」以外的引导**：销售通知 20/100 后，行上不会主动说
  「还剩 60 可通知」，要靠「可出库 60」这个数自己看出来；
- **一张销售单下同一生产单可以有多张通知**（分批的必然结果），列表按时间倒序平铺，
  通知多了以后需要按生产单分组的折叠展示；
- **出库通知仍无提醒/推送**：仓库不进页面不知道有新通知（与待入库通知现状一致）。
