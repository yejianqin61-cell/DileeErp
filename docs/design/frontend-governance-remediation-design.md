# 迪礼 ERP 前端治理整改设计

## Problem Statement

当前前端已经接入多个业务模块，但仍处于“能展示、能调用接口”的早期状态，距离厂内操作员可长期使用的交付版本有明显差距：

- 页面主要由多个面板纵向堆叠，信息密度高，缺少稳定的页面层次和操作上下文。
- 部分操作使用浏览器原生 `prompt`、`alert`、`confirm`，无法承载多字段录入、校验、错误恢复和业务确认。
- 项目存在少量自建 UI 组件，但尚未建立真正的 shadcn/ui 组件基础层。
- 各模块的加载、空数据、错误、成功反馈和表单行为不一致。
- 前端页面没有统一落实“列表 + 筛选 + 详情抽屉 + 表单弹窗 + 操作确认”的 ERP 工作模式。

这会直接影响数据录入准确性、业务人员的操作效率、错误更正能力和后续维护成本。

## Solution

建立统一的前端治理基础，在不改变后端业务契约和 `order_no` 关联规则的前提下，逐模块将前端重构为可交付的业务工作台。

治理结果应满足：

1. 用户看到的是业务对象和业务操作，不是 API 或数据库结构。
2. 页面层级清晰，突出功能本身，不用大段说明文字制造视觉噪声。
3. 所有需要输入、编辑、确认、冲销或更正的动作，都由统一弹窗或抽屉承载。
4. 所有页面共享同一套 shadcn/ui 风格和交互语义。
5. 每个模块治理完成后，都进行真实 API 联调和浏览器验收，再进入下一个模块。

## User Stories

1. 作为业务操作员，我希望打开模块后先看到可筛选的主数据表，以便快速定位待处理单据。
2. 作为业务操作员，我希望列表只显示必要字段，以便在有限屏幕空间内完成扫描和比较。
3. 作为业务操作员，我希望点击一行即可打开详情抽屉，以便查看上下游信息而不丢失列表上下文。
4. 作为业务操作员，我希望新增和编辑使用弹出表单，以便集中填写完整数据并获得字段级校验。
5. 作为业务操作员，我希望选择客户、供应商、员工、物料和订单时使用下拉选择或搜索选择，而不是手动输入内部 ID。
6. 作为业务操作员，我希望过账、关闭、冲销等不可逆或影响上下游的操作有明确确认页，以便避免误操作。
7. 作为业务操作员，我希望冲销时填写原因并看到影响范围，以便后续审计和更正。
8. 作为业务操作员，我希望提交失败时保留已填写内容，以便修正后再次提交。
9. 作为业务操作员，我希望页面明确区分加载中、无数据、请求失败和操作成功，以便知道下一步该做什么。
10. 作为业务操作员，我希望成功反馈不会阻塞页面操作，并且能在短时间内看到最新数据。
11. 作为生产人员，我希望生产日报、员工日报和 QC 录入都有结构化表单，以便减少数量和日期录入错误。
12. 作为采购人员，我希望采购单、到货、来料 QC 和入库操作按业务顺序组织，以便沿链路处理批次。
13. 作为仓库人员，我希望入库、出库、退料和报废操作显示库存影响预览，以便在过账前发现风险。
14. 作为人事人员，我希望考勤、绩效、薪资和工资支付表单共享员工和期间选择器，以便减少重复录入。
15. 作为财务人员，我希望收付款核销可以在抽屉中选择来源和金额，以便支持分批核销而不是记忆内部 ID。
16. 作为销售人员，我希望客户、销售单和 BOM 的关联关系在详情页中可见，以便沿 `order_no` 追踪订单。
17. 作为任何模块的操作员，我希望保留筛选条件、分页和详情上下文，以便处理完一条记录后继续处理下一条。
18. 作为管理员，我希望所有表单、按钮和状态展示遵循统一组件规范，以便降低维护和培训成本。
19. 作为开发者，我希望 UI 组件有明确的输入、状态和可访问性约定，以便新增模块不会复制临时实现。
20. 作为验收人员，我希望每个模块都有真实接口和浏览器验收证据，以便区分静态构建通过与业务真正可用。

## Implementation Decisions

### 1. 组件基础层

- 采用 shadcn/ui 的 open-code 方式建立本地组件，组件源码归项目维护，不直接依赖黑盒 UI 框架。
- 统一提供并持续复用：`Button`、`Input`、`Textarea`、`Label`、`Select`、`Table`、`Dialog`、`AlertDialog`、`Sheet`、`Form`、`Toast`、`Badge`、`Card`、`Separator`、`Skeleton`。
- 组件变体使用现有的 class variance 模式；颜色、间距、圆角、阴影、焦点态和禁用态使用全局设计 token。
- 图标统一使用 lucide-react；图标按钮必须提供可访问名称或 tooltip。
- 组件不得在业务页面内重复实现同类弹窗、按钮、表单字段或状态标签。

### 2. 表单和校验

- 所有业务录入使用 React Hook Form。
- 表单字段必须有标签、必填标记（如适用）、错误信息和提交中状态。
- 关联实体使用可搜索的 Select/Combobox；界面显示业务编号或名称，提交内部 ID。
- 数量、金额、日期、期间和状态字段在客户端做基础校验，后端错误仍作为最终校验来源。
- 保存失败不得清空表单；关闭未保存表单时必须提示是否放弃修改。
- 表单提交按钮在请求期间禁用，避免重复提交。

### 3. 弹窗与抽屉规则

- `Dialog`：新增、编辑、短表单、简单确认。
- `Sheet`：列表行详情、审计时间线、上下游关联、复杂核销和影响预览。
- `AlertDialog`：过账、关闭、冲销、删除（软删除）等高影响动作的二次确认。
- `Toast`：成功、一般提示和短暂状态反馈；错误需同时在页面或表单内可见，不仅依赖 toast。
- 禁止使用 `window.prompt`、`window.alert`、`window.confirm`。
- 弹窗标题使用动作和对象的简短组合，例如“新建采购单”“登记到货”“冲销收款”。不在弹窗内堆叠长篇业务说明。

### 4. 页面结构

每个业务页面按以下结构组织，允许根据模块删减，但不得回到多个无层次面板堆叠：

```text
页面标题区：标题 + 极短描述 + 主操作
查询筛选区：关键词、状态、日期、order_no、筛选/重置
主数据表：必要字段、状态、行操作、分页
详情抽屉：基本信息、关联单据、审计、影响预览
新建/编辑弹窗：结构化表单
操作确认弹窗：影响说明、原因、确认按钮
```

主操作只保留当前页面最常用的一项或少数几项，其余动作放入行操作菜单或详情抽屉，避免标题区按钮堆叠。

### 5. 状态、反馈和数据刷新

- 所有请求必须有 loading、error、empty、success 四类状态。
- 列表加载使用 Skeleton 或明确的加载状态，不通过空表误导用户。
- 空状态只说明当前没有数据和可执行的下一步，避免大段功能介绍。
- 操作成功后只刷新受影响的数据查询，不无条件重载整页。
- 错误显示后提供重试；字段错误定位到字段，业务冲突显示后端错误码和可读消息。
- 状态标签颜色和文案全局统一，不在页面内临时定义颜色。

### 6. 表格和导航

- 所有业务表格统一使用 TanStack Table，支持稳定列宽、排序（如接口支持）、筛选、分页和响应式横向滚动。
- 表格行操作不超过常用动作数量，其余动作放入菜单或详情抽屉。
- 一级导航只保留：工作台、销售、采购、仓库、生产、人事、财务、报表。
- 告警作为跨模块入口；基础资料归入所属模块，不单独占用一级导航。
- 详情页和抽屉中的跨模块跳转必须保留 `order_no` 上下文。

### 7. 模块治理顺序

按业务链路和复用价值分批实施：

1. 销售与客户：建立客户选择、销售单、BOM 的通用详情和表单模式。
2. 采购：复用实体选择器，治理采购单、到货、来料 QC、原料入库。
3. 仓库：治理库存表、入库/出库/退料/报废和影响预览。
4. 生产：治理生产单、工序、日报、员工日报、外加工和成品 QC。
5. 人事：治理员工、考勤、绩效、薪资和工资支付。
6. 财务：治理应收、收款、应付、付款、核销、冲销和对账。
7. 工作台与报表：统一跨模块详情、告警、时间线和报表筛选导出。

### 8. 每模块交付门禁

每个模块完成以下事项后才允许进入下一模块：

- 页面不再使用原生浏览器输入或确认弹窗。
- 页面符合统一结构，且移动/窄屏下不发生文字和控件重叠。
- 新增、编辑、详情、过账/冲销等关键操作均有对应 Dialog/Sheet/AlertDialog。
- 通过类型检查、lint 和生产构建。
- 使用真实 API 完成至少一条主流程和一条错误/更正流程。
- 使用 Playwright 或等价浏览器验收记录页面、表单、错误反馈和数据刷新。
- 记录验收证据和遗留问题，未完成项不得标记为已交付。

## Testing Decisions

- 测试关注用户可观察行为：打开页面、筛选、打开详情、填写表单、提交、错误提示、确认、刷新和跨模块追踪。
- 组件测试覆盖表单校验、禁用状态、弹窗打开关闭、未保存离开提示和错误展示。
- API 联调测试使用真实认证和测试数据库，不以静态 mock 作为唯一证据。
- 浏览器验收覆盖每个模块的主流程、至少一个后端校验失败场景和一个更正/冲销场景。
- 回归测试确保治理 UI 不改变既有 REST API 字段、状态机和 `order_no` 关联行为。
- 优先复用现有 API HTTP、集成和 Playwright 测试工具；新增测试应从页面交互入口验证，不测试组件内部实现细节。

## Out of Scope

- 本整改不重新设计后端领域模型、数据库表和 REST API 契约。
- V1.0 不新增手机端、离线操作、复杂审批流、总账会计和税务功能。
- 不为装饰性动画、营销式首页或大段产品说明投入开发资源。
- 不在本阶段追求所有页面一次性完成；按模块门禁逐批交付。
- 不把静态构建成功、接口返回 200 或 demo 数据展示视为业务验收完成。

## Further Notes

- 当前前端已具备部分页面和业务 API 接入，但组件层尚未达到 shadcn/ui 的完整治理要求；本设计将“组件基础层建设”视为第一阶段工作。
- 视觉目标是安静、清晰、可扫描的厂内业务工具：减少卡片和说明文字，保留必要留白，避免按钮和信息块相互争夺注意力。
- 所有新增前端代码必须遵守本设计；临时实现若确有必要，必须在对应任务文档中记录替代原因和后续清理点。
