# 应付流转打通与收支流水覆盖排查（2026-09-15）

> 用户反馈（原文）：
> 1. 「财务，应付管理，原料入库条目，为什么点击接受应付没有反应，没有流转到应付对账那边去创建条目。
>    是不是应付对账创建完对账，也没有流转到确认付款那边去？！这个流转的步骤，是最重要的！」
> 2. 「应付对账，column 还要加上该批原料对应订单号，采购的物料名称。」
> 3. 「排查当前收支流水会把什么收纳进去。现在收支流水没有办法把全部的收支纳入进去。」

## 1. 排查结论（先回答「为什么感觉没有流转」）

### 1.1 应付链路：接口是通的，但有三处让流转「断在看不见的地方」

| # | 问题 | 证据 | 后果 |
| --- | --- | --- | --- |
| A | **对账的系统余额只算已确认应付，不含待确认草稿** | `supplier-payable-reconciliation.service.ts` 的 `create()` 用 `status: { in: ["confirmed","partially_paid","paid"] }` | 流程是「先对账、再确认应付」，而它对账的对象恰恰是**草稿**：财务刚接收完应付去做对账时，系统余额恒为 0、差异恒等于 −外部余额，永远对不平 |
| B | **「到确认应付确认 N 条」的提示读的是详情接口的 `details`，列表接口不返回** | 前端 `row.original.details?.draft_count`，而 `list()` 既没有 `details` 也没有 `flow` | 对账单行上那句下一步提示**永远不显示**；用户看不出「对账已经完成、下一步是确认应付」 |
| C | **「批量确认该对账范围的应付」接口没有任何界面入口** | `POST /finance/supplier-payable-reconciliations/:id/confirm-payables` 只有后端与单测调用 | 最后一步只能在「确认应付」里逐条点确认，对账与确认之间是断的 |

接收应付本身（`POST /finance/payable-entries/from-source`）是**好的**：它生成草稿应付，草稿随即出现在
「应付对账 → 待创建对账」分组里（按供应商 + 月份）。用户觉得「没反应」，是因为点完之后页面停在同一
个子栏目、没有任何「下一步」指引（B/C 两点）。

### 1.2 收支流水：查清了「收纳了什么」，也找到了大头缺失

自动写入收支流水**只有三处**（都是收付款过账时）：

| 来源 | 方向 | 项目 key（原实现） | 结果 |
| --- | --- | --- | --- |
| 客户收款过账 `customer_payment` | 收入 | `货款` | ✅ 正常 |
| 供应商付款过账 `supplier_payment` | 支出 | `外加工费` | ❌ **字典里没有这一项**（内置 37 项里是「外加工费 晋江大田工资」）→ `autoCreateFromPayment` 当时遇到缺项 `return null` → **每一笔供应商付款都被静默丢掉** |
| 工资付款过账 `salary_payment` | 支出 | `人 工费` | ✅ 正常（字典里确有这一项，含老表原文的空格） |

即：**收支流水此前只可能收到「客户货款」「工资付款」和手工录入**，全部采购/外加工/其他应付的付款
都不在流水里 —— 这正是「没有办法把全部的收支纳入进去」。

另外两个缺陷：
- `settlementAccountId` 恒为 `null`、结算方式只写「转账」：银行账户信息从收付款单据丢失
  （老表「结算方式」列是 `转账--农业银行5706` 这种格式）；
- **冲销不回冲**：收付款冲销后，流水里那笔收入/支出一直留着，收支汇总比银行账多一笔。

## 2. 本次改动

### 2.1 应付流转（A/B/C 三个问题）

- **A：对账口径含草稿**。`create()` 的应付状态集合改为
  `["draft","confirmed","partially_paid","paid"]`（与服务端 `get()` / `confirmPayables` / 前端
  「待创建对账」分组完全一致），常量 `ENTRY_STATUSES` 单一来源 + 注释说明为什么必须含草稿。
- **B：列表返回流转摘要 `flow`**：`{ entry_count, draft_count, draft_amount, can_confirm_payables,
  order_nos, purchase_order_nos, material_names }`。一次查询取回全部对账范围内的条目（OR 精确复刻
  `entryScope`，不做 N+1），逐行按范围过滤后汇总。
- **C：对账行上新增「确认 N 条应付」按钮**（`matched`/`resolved` 且有草稿时出现），点击直接调
  `confirm-payables`，成功提示回报实际确认条数与金额、跳过条数；有差异时只给「处理差异」。
- **流转看板**：应付页顶部新增四步链路（① 待接收来源 → ② 待确认应付草稿 → ③ 已对平待确认 →
  ④ 已确认未付），每一步给出当前数量 + 入口链接，卡住的步骤高亮。接收应付的成功提示也改成
  「已接收为应付草稿；下一步：到「应付对账」按供应商 + 月份创建对账」。

### 2.2 应付对账新列（用户要求）

- 待创建对账分组：新增**订单号**（范围内草稿的订单号去重）与**采购物料**；
- 已创建对账单：新增**订单号**（按订单创建时显示订单号，按供应商 + 月份创建时列出范围内全部订单号）、
  **采购单号**、**采购物料**、**待确认应付**（`N 条 / 金额`）；
- 对账详情里「纳入对账的应付条目」明细新增**采购物料**与**采购单号**两列。

### 2.3 收支流水覆盖

- **项目解析改为候选链**（`cash-flow-catalog.ts` 的 `PAYMENT_ITEM_KEYS` / `paymentItemKeys()`）：
  按业务来源给一串候选，第一个存在的生效。原料入库 → `原材料 成本`（备选 `货款`）；
  外加工 → `成品外加工费`（备选 `加工费`）；其他应付 → `管理费用`；客户收款 → `货款`；工资 → `人 工费`。
- **缺项不再静默跳过**：候选一个都不存在时显式 422 `CASH_FLOW_ITEM_NOT_FOUND`，错误信息列出需要
  哪些项目、去哪补 —— 宁可让过账失败并说明原因，也不能让整笔资金动账从流水里消失。
- **结算方式带上银行**：供应商付款过账时把银行写成老表格式 `转账--农业银行5706`，并把银行名 + 账号
  作为 `settlementAccountHint` 传给收支流水；`CashFlowService.matchSettlementAccount()` 按
  「账号数字完全一致 + 银行名互相包含」把它匹配到**结算账户字典**（老表 `农业银行5706`、
  `中国银行（美元）7624` 这类），匹配上就写 `settlement_account_id`，匹配不上留空
  —— 银行来自 `banks` 表、结算账户来自字典，两者没有外键关系，宁可留空也不造假关联。
- **冲销回冲**：新增 `CashFlowService.autoReverseFromPayment(sourceType, sourceId, reason, user)`，
  客户收款、供应商付款、工资付款三处冲销都会把对应流水置为 `reversed`（找不到则返回 null 不阻断冲销）。
- **对方名称不再退化成 UUID**：优先付款人/收款人，其次客户/供应商名称，最后才是 id。

## 3. 决策记录

- **D1：对账必须含草稿**。这是「先对账、再确认应付」的前提；应收侧（`reconciliation.service.ts` 的
  `snapshot` 用 `status: { not: "cancelled" }`）本来就是含草稿的，应付侧属实现偏差，按应收口径对齐。
- **D2：流转必须在列表行上可见可点**。摘要走列表接口而不是详情接口：用户不点开详情就该知道自己
  卡在哪一步、下一步点哪里。
- **D3：资金动账缺字典项时**错误可见**优于**静默丢弃。规则是「每一笔过账的收付款都要在流水里有落点」，
  做不到时必须让人知道，而不是把账做丢。
- **D4：不自动创建字典项**。收支项目是管理员可维护的业务类目（用户 2026-08-20 确认的「可配置字典」），
  程序自动往里塞项目会让字典失控；缺项时给出可执行的报错。

## 5. 仍未覆盖的收支（如实记录）

自动纳管覆盖到「有收付款单据并过账」的资金动账。以下情况**仍然只能手工录入**（收支管理页）：

- 采购付款以外的支出：房租、水电、运费、差旅、办公等（老表 37 项里的绝大多数）；
- 无单据的资金往来：老板借款/还款、备用金、押金、退税（`国家退税`）、利息与手续费；
- 退款：系统里「退款」是应收调整（`adjustment_type=refund`，只减少应收，不产生现金流水），
  实际退款到客户时目前要手工记一笔支出；
- 收款/付款草稿未过账：按设计不写流水（钱还没动）。

要把上面这些也自动纳管，需要在对应业务里新增资金事实（例如退款单、费用报销单），
属于新的模块范围，本次不做。
