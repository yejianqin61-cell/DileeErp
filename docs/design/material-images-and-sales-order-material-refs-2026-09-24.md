# 物料图片与销售单材料引用（2026-09-24）

用户这一轮给了四件事，原话：

> 1.付款单/收款单上,我方和对方账户都分别设置对应的字段
> 2.现在，销售单导出，用户反馈行高需要自己调，不美观，太扁了。我们能不能根据行数进行自动的行高调整
> 3.现在，物料清单，要给物料配上图片。图片上传之后要压缩成 webp 再存进数据库里。所以要允许用户对
>   对应的物料进行图片的上传。
> 4.然后销售板块，在编辑销售单的时候，每个部件，既支持填空，也支持从现有的物料清单中引用。
>   同时要体现对应的物料的图片。导出销售单的时候，每个有图片的物料允许用户勾选是否 excel 中
>   一并导出这个图片。excel 中图片我们就单独排成一排放在底下的一个图片区。然后让用户自行拖拽就好了

三个需要拍板的地方先问了用户，答案是：

| 问题 | 用户的选择 |
|---|---|
| 第 4 条的「部件」指哪一块 | **材料明细那 18 项**（伞骨/伞布规格/伞头/伞带…），不是细分明细的花色行 |
| WebP 压缩在哪做 | **浏览器 canvas 转 WebP**，服务端**只校验**（不引 sharp 那种原生依赖） |
| 单子上两方账户怎么来 | 我方 = 确认时实际走的那张卡；对方 = 手工填，能从供应商结算信息里认出来就预填 |

## 一、收/付款单：我方与对方账户分开

### 问题

模板上「收款单位 / 开户银行 / 银行账号」三格说的都是**对方**；而预填塞进去的是
`cash_flow_entries.bank` —— 那是**我们自己的**账户（确认这笔应付时钱从哪张卡出去）。
于是一张付款单印出来是「收款单位：富雨鑫，开户银行：农业银行 4039…」，
而那个账号其实是迪礼自己的。这不是文案问题，是**单据内容错**。

### 做法

`FinanceSlip` 从一对银行字段拆成两对，**删掉旧的 `bank_name` / `bank_account`**（不是改名）：

- `our_bank_name` / `our_bank_account`：预填自确认流水的账户（唯一可靠的我方来源）；
- `counterparty_bank_name` / `counterparty_bank_account`：供应商从 `settlementInfo`（自由 JSON）里
  按常见键名认出来（`counterpartyBankOf`，认不出就留空）；**客户主数据没有结算信息列**，
  所以收款单的对方账户一律留空由财务照回单填。

版式从四行表头变五行（新增 R5 我方开户银行/账号），分录区整体下移一行 —— 行号写成
`HEADER_ROW` / `FIRST_LINE_ROW` 常量，避免「合计行压在最后一条分录上」这种不报错的错位。

为什么删旧字段而不是共存：留着它只会让「这四个值填到哪一格」继续含糊，而这是**钱的字段**。
这是一次有意的破坏性改动，前后端同一提交内改完。

### 没做

给供应商/客户主数据加正式的「开户银行 / 银行账号」列。本轮按用户拍板「不动主数据」，
只从既有的结算信息 JSON 里认；认不出的留空。要长期规整，那是下一步（见遗留 1）。

## 二、工艺单行高自适应

用户的话是「行高需要自己调，不美观，太扁了」。根因：**ExcelJS 不做自动行高** ——
`row.height` 只有「写死」与「不写」两种，不写时 Excel 用默认 15 磅，开了自动换行的长文字被截成一行。

所以在服务端算：`apps/api/src/platform/excel/row-height.ts`（纯函数、可单测）。

| 口径 | 取值 | 为什么 |
|---|---|---|
| 显示宽度 | 汉字/全角/emoji = 2，其余 = 1 | Excel 列宽单位是「字符 `0` 的宽度」，按 `text.length` 算会让全中文的格子**少算一半行数** —— 那正是「太扁」的病根 |
| 余量 | `可用宽度 = 列宽 − 1` | 按满宽算会「恰好差一点」，最后一个字被挤到下一行，行高又少算一行 |
| 显式换行 | 优先，`\n` / `\r\n` 各占一行，空段落也算一行 | 财务在备注里敲的回车不能被当成自动折行吃掉 |
| 左右两栏 | 取**需要行数更多的那一栏**（max，不是相加） | 材料在 B:F、工艺要求在 G:J，是并排的两个合并区 |
| 下限 / 上限 | 20 磅 / 300 磅 | 短行不挤在一起；注意事项最多 2000 字，不封顶会把一张工艺单撑成两页 |

落点：表头三行、注意事项、材料/工艺正文、明细分组头、明细行（品番/品名）、正唛侧唛、布量、表尾。
`pairs()` 与 `block()` 会把「这一块跨了几列」回报给调用方，行高按真实可用宽度算。

**只改了工艺单**：别的导出（采购单/领料单/财务报表）有同样的病，但一次改十个版式会同时动十份
版式测试 —— 这次先把工具做出来（`platform/excel/row-height.ts` 与它无关业务），下一次逐个接。

## 三、物料图片：WebP 入库

### 表为什么是独立的一张 1:1 从表

`materials` 是**热表**：采购、BOM、库存、生产到处 `findMany` 它（`include: { material: true }` 遍地都是）。
字节列一旦挂在主表上，每一次列表查询都会顺手把几百 KB 的图片读回来。Prisma 只在该关系被
**显式** select/include 时才取关系，所以 `material_images`（`material_id` 唯一）是这里唯一安全的形状：
`listMaterials()` 只 `select` 元数据（`MATERIAL_IMAGE_SUMMARY`），字节走 `GET /materials/:id/image`。

### 压缩在前端、校验在后端

用户选了「不引 sharp」那条路，于是：

- **前端**（`apps/web/lib/material-image.ts`）：读原图 → 最长边缩到 1600 → `canvas.toBlob("image/webp", 0.82)`。
  旧 Safari 的 `toBlob(..., "image/webp")` 会**静默回退成 PNG**，所以那里显式检查 `blob.type`，
  不是 WebP 就报「换 Chrome / Edge」——不能把一个 PNG 传上去等后端说「不是 WebP」，那样用户看不到真原因。
- **后端**（`apps/api/src/modules/procurement/material-image.ts`）：`Content-Type` 与扩展名都不可信，
  所以真的把容器解开看一眼 —— `RIFF....WEBP` + `VP8 `/`VP8L`/`VP8X` 三种块头里读出**真实像素尺寸**，
  再判大小（≤2MB）与边长（≤2000）。声明长度与实际字节数不一致的一律拒（不存半张图）。
  「压缩炸弹」压缩后体积很小，只看字节数是拦不住的，边长上限就是为它准备的。

单测里的三个 WebP 夹具是**真实编码器（sharp，仅用于生成夹具）**产出的字节，三种容器各一份 ——
只用手搓的字节测会有一个致命盲区：解析器「只认自己造的那种格式」也能全绿。

### 路由分布

| 路由 | 控制器 | 权限 | 为什么在这一侧 |
|---|---|---|---|
| `POST /materials/:id/image` | `ProcurementMasterDataController` | `procurement` | 上传是写主数据 |
| `DELETE /materials/:id/image` | 同上 | `procurement` | 同上 |
| `GET /materials/:id/image` | `MasterDataReadController` | ANY(procurement/warehouse/production/sales) | **销售**也要看物料图（销售单编辑器与导出弹窗），放写侧控制器里销售会拿到一排 403 破图 |

读侧带 `ETag` = 内容 sha256 + `must-revalidate`：换图 = 换 sha，所以「校验一次、没变就 304」
既省流量又不会拿到旧图。

## 四、销售单材料明细引用物料 + 工艺单带图导出

### 引用为什么是一张表、以及为什么必须 upsert

`sales_order_material_refs`：一行一个引用（`spec_key` + `material_id`），
唯一键 `(sales_order_id, spec_key)`。

为什么不往 `sales_orders` 上加 18 个可空外键列：能让引用的栏位清单（`SPEC_MATERIAL_KEYS`）
以后增删而不动 schema；而且 18 个可空外键会把这行推宽到 60+ 列。

**替换语义是 upsert 而不是「软删 + 新建」**：唯一索引**不看 `deletedAt`**，
删了再建必然撞唯一约束 —— 同一张单子改一次引用就会 500。所以按栏位逐行对齐：
值变了改这一行（顺手把 `deletedAt` 清回来 = 复活）、请求里没提到的软删、新出现的才插入。
这样每一行始终是同一条记录，`createdAt` 也真的表示「这一格第一次引用是什么时候」。

引用还进**版本快照**：物料会被改名/换图，只看当前值答不了「当时引用的是谁」。

### 选中物料为什么顺手填文字

`materialSpecText(material)` = `名称 规格型号 颜色`。工艺单上印的是**文字**（工厂照字做伞），
只记一个引用的话那一格在纸上是空的。填完仍可改 —— 用户要的是「既支持填空，也支持引用」，
引用只是省掉手打，不是把这一格锁死。清除引用**不动已写好的文字**（想留着就留着）。

### 带图导出：浏览器转 JPEG，字段名就是栏位键

库里存 WebP，而 **Excel 不认 WebP**（ExcelJS 写进去的 webp media part 在 Excel 里是一个红叉；
ExcelJS 自己只支持 png/jpeg/gif）。服务端要转就得有解码器 —— 就是用户不要的那个原生依赖。
所以：

1. 界面 `GET /sales-orders/:id/export-images` 取候选（只列**这一单引用过**的物料）；
2. 用户勾选（默认全勾、每行带缩略图）；
3. 浏览器取回 WebP → 画到画布 → `toBlob("image/jpeg", 0.85)`（最长边 640）；
4. `POST /sales-orders/:id/production-sheet.xlsx`，**multipart**，一个勾选的栏位 = 一个文件，
   **字段名 = `spec_key`**（`AnyFilesInterceptor` 的 `fieldname` 原样就是栏位键），
   于是不必发明「第几个文件对应哪一格」这种必然错位的约定。

为什么是 multipart 而不是 JSON：图片字节走 JSON 会撞上 Express 默认 **100KB** 的 body 上限，
而放开全局上限是拿整站攻击面换一个导出接口。

服务端的三道闸门：`spec_key` 必须是这一单引用过的、且那个物料**确实有图**（查库，不信请求）、
字节必须是 JPEG（看头三字节）、单张 ≤2MB 且合计 ≤12MB。
**像素内容信任上传者**：解不了就验不了，最坏情况是有人给自己导出一张别的图 —— 内部工具的导出件，
这个取舍写在 `checkSelectedImage` 的注释里。

### 表尾图片区

一排 5 张（A–J 十列，每张占 2 列），每张占 7 行 × 20 磅 ≈ 187px（比 130px 的最大图略高，留出拖拽余量），
图片正下方是它的标签序号 + 栏位名 + 物料编码/名称。
锚用 `oneCellAnchor`（`tl` + `ext`）—— 图片只是浮在这一排上面，用户在 Excel 里一拖就走，
正好是用户要的「让用户自行拖拽就好了」；标签是补「拖走之后还认得出是哪一格」这个风险。

## 六、遗留

1. **供应商/客户主数据没有正式的开户行与银行账号列**：本轮只从结算信息 JSON 里认。
   要长期规整（并让付款单对方账户稳定预填）需要加列 + 迁移 + 两个主数据页面。
2. **图片字节的内容只校验到容器头**（不解码）：与「不引原生依赖」这个前提直接相关。
   哪天愿意引 sharp，可以做「服务端重新编码」这条更硬的保证。
3. **行高工具只接到了工艺单**：采购单/领料单/财务报表的同款问题还在。
4. **`suppliers.settlement_info` 的 PATCH 传 null 会 5xx**（更早的 KNOWN_DEFECT，本轮没动）。
5. 付款单/收款单确认弹窗里的「入账/支付银行 + 款项性质」现在只对收款/付款登记有意义，
   界面还没把这两个字段从确认弹窗里拿掉（与上一批同一件事）。
