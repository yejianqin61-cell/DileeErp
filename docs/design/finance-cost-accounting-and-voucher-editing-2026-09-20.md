# 财务：核算表（管理费分摊）与记账凭证分录编辑（2026-09-20）

用户一次提了 8 条，两条大的（**核算表**、**凭证可编辑**）需要先定口径，其余 6 条是明确的修复。
开工前问了 4 个问题，用户全部选推荐项：

1. **管理费怎么录** → 新增「月度管理费」登记（期间 + 金额 + 单位），分摊数量自动取本月计件日报数量（可人工覆盖）；
2. **分摊单位** → 登记时指定单位，核算表加一列「分摊单位」，只对单位一致的订单套费率，不一致的留空并在表尾点名；
3. **凭证怎么改** → 完整分录编辑器（增删行、改借贷方向、科目下拉、改金额/摘要）+ 内置「工资计提」「原材料采购」模板；
4. **进项税怎么来** → 模板只给结构、金额留空由财务手填（不按税率自动拆：取得普票不抵扣、优惠税率会被自动填错），
   编辑器实时显示借贷合计，不平不让保存。

## 一、核算表（第 4 条）

### 1.1 样本与财务的口径

用户交付 `example/财务/核算表.xlsx`，并转述财务原话：

> 只有采购输入原材料　物控有录人工费。我这边录管理费，就可以出这个表。
> 我这里的管理费是一个月的所以费用的总合平摊在本月生产的总数量中。
> 比如这个月管理费是22万　生产了4000打货　管理费就是55元

样本 `Sheet1` A1:S101，两行合并表头，数据 4–100 行，第 101 行是 `SUM()` 合计行。版式：

| 列 | 含义 |
| --- | --- |
| A | 日期 |
| B | 订单号 |
| C | 客户 |
| D | 规格 |
| E:F:G | 收入（单价 / 数量 / 金额） |
| H:I:J | 原材料（单价 / 总价 / 占比） |
| K:L:M | 计件人工（单价 / 总价 / 占比） |
| N:O:P | 管理费用（单价 / 金额 / 占比） |
| Q | 费用合计 |
| R | 利润 |
| S | 备注 |

样本里 E–R 全是 0 / `#DIV/0!`（数据没填），所以**推导方式没有证据**，只能按财务那句话反推：
`占比 = 该块总价 ÷ 费用合计`、`金额 = 单价 × 数量`、`费用合计 = 原材料 + 计件人工 + 管理费用`、`利润 = 收入 − 费用合计`。

### 1.2 三条口径（都写在代码注释里）

**① 费率不四舍五入，金额是权威值。** 22 万 ÷ 4000 打恰好是 55，样本看不出问题；但 22 万 ÷ 3700 打 =
59.4594…，先把费率修约成 2 位再乘数量，`单价 × 数量 ≠ 金额`，财务逐行验算就会对不上。
做法与 `finance-report.domain.ts` 的 `localUnitPriceFor` 一致：**金额是权威值，单价由金额 ÷ 数量反推**。

**② 单位是分摊的一部分，不是备注。** 老核算表**没有单位列** —— 这是老表的真实缺陷，不是要照抄的东西。
「55 元/打」与「55 元/支」差 12 倍，而全站纪律是「不跨单位相加」。所以：

- 登记时必须填单位；
- 核算表只对**归一后单位相同**的订单套费率（`allocationUnitMatches`，支/pcs/个→piece，打/dz→dozen）；
- 单位不一致的行：`分摊单位` 列照填（让人看得出用的是哪个单位），`管理费用 / 金额 / 占比` 三格留空，
  订单号在表尾点名。**不做打↔支换算**（换算需要每款伞的装箱数，系统里没有）。

**③ 分摊数量可以人工覆盖。** 自动值是「本月计件日报（`employee_daily_reports`）的数量」，
按**工序的单位**过滤（单位过滤下推到 SQL 的 `IN`，含 `打.` / `打。` 这类带末尾标点的写法）。
但计件日报是**按人按工序逐条**填报的，同一件货经过三道工序会出现在三条日报里，跨工序合计会重复计件 ——
所以自动值只是参考，财务在面板上覆盖成「本月实际生产数量」才是准的。

### 1.3 字段映射（用户问的「怎么与我们系统中字段进行映射」）

| 核算表列 | 系统取数 |
| --- | --- |
| 日期 | `sales_orders.order_date` |
| 订单号 | `sales_orders.order_no` |
| 客户 | `customers.name` |
| 规格 | `sales_orders.product_spec` |
| 收入单价 / 数量 / 金额 | 数量 = `sales_orders.quantity`；金额 = **本币收入**（`local_currency_amount`，人民币单退 `total_amount ?? receivable_amount`）；单价 = 金额 ÷ 数量 |
| 原材料单价 / 总价 | **BOM 原料成本**（复用 `BomMaterialCostService`，与毛利表同一个取价口径：最近一次未取消采购单的 `unit_price`），按销售单汇率折本币 |
| 计件人工单价 / 总价 | Σ `employee_daily_reports.calculated_amount`（`order_no` = 销售单号的工序日报，系统里唯一的计件口径），人民币 |
| 管理费用 / 金额 | 费率来自「月度管理费登记」；金额 = 订单数量 × 费率 |
| 费用合计 / 利润 | 三段之和 / 收入金额 − 费用合计 |
| 备注 | `sales_orders` **没有**备注字段（只有工艺字段），恒 null |

**币种**：老表没有币种列，而美元单的收入与人民币的管理费不能直接相加。本表统一按**本币（人民币）**口径出，
并在表尾写明；外币订单缺本币金额时该行收入金额**留空**（不写 0）并列进表尾。

**占比的除零**：老表这里是 `#DIV/0!`，我们写**空单元格**。三对（8/9、11/12、15/16）用同一条规则：
金额格为空 → 占比格为空。只给一列加闸比三列都不加更坑 —— 会得到「原材料总价空、原材料占比 0.00%」
这种读起来像「这项成本是零」的假话。

**列（20 列，单行表头）**：日期 / 订单号 / 客户 / 规格 / 收入单价 / 收入数量 / 收入金额 / 原材料单价 /
原材料总价 / 原材料占比 / 计件人工单价 / 计件人工总价 / 计件人工占比 / **分摊单位** / 管理费用 /
管理费用金额 / 管理费用占比 / 费用合计 / 利润 / 备注；
`totalColumns = [6, 8, 11, 15, 17, 18]`（数量不合计：跨单位；单价与费率不合计；占比不合计）。

**计件人工 = 0 与收入 = 空 是两件事**：没有计件日报 = 「这个订单这个月没录计件人工」这个事实，
Σ 空集就是 0（老表这一格写的也是 0.00）；而外币订单缺本币金额是**真的缺数据**，写 0 会被读成
「这单收入是 0」。两处取舍故意不同，注释里写明了别照着一边改另一边。

### 1.4 月度管理费登记

新表 `overhead_allocations`（`period` 唯一）：`period`(YYYY-MM) / `amount` / `unit` / `quantity_override` / `remark` + 审计四列。

- **为什么单独一张表**，不直接汇总「本月管理费用类科目的收支流水」：财务的口径是**先有总额、再有费率**，
  而总额必须是「财务确认过的这个月的管理费」。流水常常滞后（月底的费用下月才报销），
  直接汇总会让本月费率凭空偏低，而报表上看不出来。
- **`period` 唯一，且软删后仍占着这个期间**：两条并存就会有「用哪条算费率」的歧义。
  写入走按期间 upsert；软删过的那条**恢复它**而不是新建（否则「删了再录」会直接撞唯一索引，
  用户看到的是一个数据库错误）。
- 接口：`GET /finance/overhead-allocations`、`GET /finance/overhead-allocations/resolved?period=`、
  `POST /finance/overhead-allocations`（upsert）、`DELETE /finance/overhead-allocations/:id`。
  读与写都只走 `finance` 模块权限，**不额外要求管理员**：录管理费是财务的本职动作，一个月一次，
  锁管理员等于把这条链掐断（与「会计科目维护」不同 —— 那是全站基础数据）。
- **面板与报表同屏**（核算表 tab 上方）：录管理费与看核算表是同一件事的两半，
  分成两个页面财务就得来回跳，而且看不出来「刚改的费率有没有进到表里」。保存后自动重取报表。

## 二、记账凭证的分录编辑与模板（第 8 条）

财务原话：

> 借：应付职工薪酬——工资（应发）／贷：其他应付款——社保（个人部分）、应交税费——应交个人所得税、银行存款（实发）
> 我完整的一个工资是这样的，但是现在都不能改
> 原材料的也是要加上应交税费：借 原材料 18000 / 应交税费——应交增值税（进项税额）/ 贷 应付账款
> 现在自动生成的不能改、。这是什么意思？

**「不能改」的确切含义**：服务端的 `PATCH` 一直支持整组分录，但页面上的「编辑」是一个通用表单弹窗，
只能改**已有两行**的科目（还是手打文本）与金额 —— 不能增行、不能改借贷方向。
工资计提是「一借三贷」、原材料是「两借一贷」，这两个形状根本表达不出来。

### 2.1 分录编辑器（新增）

`apps/web/components/finance/voucher-line-editor.tsx` + 纯逻辑 `apps/web/lib/voucher-lines.ts`：

- 逐行编辑：方向 / 科目（**带搜索框**的科目下拉）/ 摘要 / 金额 / 删除；增行、套模板；
- 底部实时显示借/贷合计与差额，**不平或金额非法时保存按钮禁用**，并把三种原因分开说
  （金额非法 / 科目没填 / 借贷不平）—— 合成一句「请检查分录」会让财务在四行金额里逐个试；
- 金额一律按**整数分用 BigInt 相加**（`parseCents` / `formatCents`）。用 `Number` 求和时
  `0.1 + 0.2 = 0.30000000000000004`，而这张表要拿合计决定保存按钮能不能点 ——
  差一位小数就是「明明平了却不让保存」。前端与后端 `voucher.domain.ts` 的 `toCents` 用同一条正则。

### 2.2 模板（新增）

`apps/api/src/modules/finance/voucher-template.ts` + `GET /finance/vouchers/:id/templates`：
`工资计提`（一借三贷）、`原材料采购`（两借一贷）。三条口径：

1. **模板只给结构，金额一律留空**（用户拍板）。不按税率自动拆进项税：系统里采购单价是含税价，
   `不含税 = 含税 ÷ (1+税率)` 在取得普票（不抵扣）、优惠税率或部分抵扣时会被自动填错，而那种错误
   在凭证上看不出来。
2. **科目按名称候选解析，候选全部落空时不编一个科目 id**。财务的科目表里**没有**
   「应交个人所得税」也没有「应交税费——应交增值税（进项税额）」，所以每行给一串候选名（从最贴近
   财务说法到最宽的兜底），命中哪个用哪个；一个都不命中就返回 `subject_id: null` + 建议名，
   让财务在编辑器里自己选（也可以先去「会计科目」页把这两个科目建出来，之后模板就自动命中了）。
3. **资金行（`role: "fund"`）带上被套用那张凭证的科目与银行账户**：钱落在哪张卡上是已确认的事实，
   模板不该把它清掉。只有后端知道这件事，所以模板接口挂在凭证上（`:id/templates`）。

### 2.3 顺带修掉的一个真缺陷：银行账户引用的「按行号沿用」

`update()` 原来对未传 `bank_id` 的分录按**行号**沿用原分录的银行账户。分录编辑器会在每行都带
`bank_id`（业务行是 `null`），而 `null ?? 原值` 会退回「按行号沿用」—— 于是在资金行前面插入一行之后，
那张卡会被挂到新插入的业务行上，**银行存款明细账从此对不上银行对账单，而凭证上完全看不出来**。

修法：区分「没传」（`undefined` → 按行号沿用，兼容旧调用方）与「显式 `null`」（这一行不该挂账户）。
`normalizeLines` 不再把 `undefined` 折叠成 `null`；`VoucherLineDto` 新增可选 `bank_id`，
并在写入前校验它确实存在（否则外键会在事务提交时抛一句数据库错误，而不是「这个账户不存在」）。

## 三、其余六条

### 3.1 会计科目下拉全部加搜索框（第 1 条）

科目表 121 条、标签是「分类 / 名称」，普通 Radix 下拉只能靠滚动找，而财务心里想的是科目名。
已有一处 `searchable-select`（`components/ui/searchable-select.tsx`），本轮把所有涉及会计科目的下拉换成它：

- `ActionDialog` 的科目字段（9 处）：cash-flow 新增/更正、payable 逐条确认/批量确认/创建对账/按对账确认、
  receivable 同四类 —— 只改 `type: "select"` → `type: "searchable-select"`；
- 两个筛选器（原始 `<Select>`）：收支流水的「会计科目」、财务报表的「会计科目」。

`SearchableSelect` 新增 `testId` 属性（默认 `searchable-select`）：testid 落在**根 div** 上，
替换 Radix Select 时原来的 testid（如 `cash-flow-subject-filter`）还能按同名找到控件。

### 3.2 其他应付允许逻辑删除（第 2 条）

`DELETE /finance/payable-entries/:id`（body 带 `reason`）+ 服务层 `removeOther`。三条边界：

- **只有 `sourceType === "other"`**：原料入库 / 外加工签收形成的应付是**入库与签收事实的账**，
  删掉它等于把一笔真实到货从账上抹掉；那些录错了应当冲销或回退来源。其他应付是财务手工录（或导入）的
  非订单支出，来源就是这一次录入本身，录错了除了删掉没有别的纠正办法；
- **只有草稿**：已确认的已经记账（金额从银行账户支出、收支流水里有来源单号），删条目会让那笔流水失去来源；
- **被对账单覆盖时拒绝**（覆盖判定复用 `payableInReconciliationScope` 这个纯函数，与台账列表同源），
  错误里点名是哪张对账单 —— 对账单上的快照是发给供应商的既成事实。

软删除 + 原因必填（写进备注并单独记一条审计）。界面上按钮只出现在「其他应付 且 草稿」的行上。

### 3.3 确认应付不再需要左右滑动（第 3 条）

**根因不是规则不够，而是规则没生效。** `globals.css` 在 2026-09-16 就为财务表写好了「紧凑 + 允许换行」
四条规则（当年还用真实 Chromium 在 4 个视口实测过溢出像素），但它们选择器写的是
`.finance-page .data-table` —— 而 `DataTable` 渲染出来的 `<table>` 带的是 **`ui-table`**
（`components/ui/table.tsx`），`.data-table` 这个类在财务页根本不存在。

于是单元格一直是 `.ui-table-cell` 的 `padding: 12px` + `white-space: nowrap`，最小宽度等于整段文本宽度，
列多的表必然溢出容器、底下出现横向滚动条。修法是把 `.ui-table` / `.ui-table-head` / `.ui-table-cell`
一并写进那四条规则（不改任何页面），并补 `overflow-wrap: anywhere` 让单号这类长串也能断行。
`apps/web/lib/finance-table-width.test.mjs` 里加了守卫：**规则必须同时命中 `.ui-table`**，
并钉住「基础表格类从来不是 `.data-table`」这个事实（改了 `table.tsx` 就会红）。

### 3.4 采购对账明细表加订单号（第 5 条）

老表 16 列 → 17 列，`订单号`（= `supplier_payable_entries.order_no`）紧跟「产品名称」之后、
排在「采购单号」之前（与应付管理列表里那两列的顺序一致）。合计列下标随之从 `[14,15]` 变成 `[15,16]`
（逐列数出来并用测试钉住）。

### 3.5 记账凭证固定列宽 + 悬停看全文（第 6 条）

`DataTable` 支持列元数据 `meta: { width, ellipsis }`（用 TanStack 的 `ColumnMeta` 扩展，
写在列定义里而不是两个平行的 `Record` —— 后者靠列 id 字符串对齐，改个 id 就静默失效）：

- **只要有一列给了宽度，整张表切 `table-layout: fixed`**（不切的话「宽度」只是建议值，
  长摘要照样把列撑宽、把表顶出容器，而用户要的恰恰是「保证一次性展示全部column」）；
- `ellipsis: true` 的列：省略号截断 + 原生 `title` 显示全文。只对**字符串/数字**格给 `title`
  （按钮那种 ReactNode 不给 —— 把按钮文案拼成「确认应付编辑回退」比没有提示更让人困惑）；
  也刻意**不**用整行的「双击查看详情」兜底：hover 一列是想看这一格被省略掉的全文。

记账凭证页两份宽度表**只给自己的列**，创建人 / 最后修改人两列（来自 `auditColumns`）不写死：
固定布局下浏览器会把剩余百分比均分给它们（各约 8%），以后调整 `auditColumns` 不会连带撑破这一页。

样式权重要写足：`.finance-page .ui-table-cell { white-space: normal }` 是 `(0,2,1)`，
省略号规则写成 `.cell-ellipsis`（`(0,1,0)`）会**静默失效**（页面看起来只是「没省略」），
所以叠到 `(0,4,1)` 并且不依赖样式表先后顺序。

### 3.6 应收 / 应付全部表单加查询（第 7 条）

关键字是同一个，但**每张表都要接上它**：

- 应付：搜索框原本就有，但只作用在「应付条目」上 —— 应付对账页的**已创建对账单**渲染的是原始数组，
  搜索框看着在、打了字却没有反应，而对账单正是财务翻得最多的表。现在两张表都跟着收窄，
  面板上的「对账单 N 张」也跟着走；搜索框补上 `data-testid="payable-search"`（它是本页唯一没有 testid 的筛选器）。
- 应收：缺口更大 —— 搜索框只画在「成品出库条目」那一段里，而它一直是「确认应收」页的**实际**筛选器
  （`matchedSources` 就吃它），用户切过去只能看到一个来路不明的关键字在生效；「应收对账」页连一个
  筛选器都没有。现在搜索框提到页签外面（四个页签都有），两张对账单表接上它，并补 `receivable-search`。
- 顺带删掉一份重复的匹配规则（`outboundSources` 与 `matchedSources` 只差一个字段，迟早漂移）。

## 五、未验证 / 待确认

1. **没有真实 PostgreSQL**：`overhead_allocations` 的迁移与 `period` 唯一键、软删后恢复的实际行为
   都只在替身上验证过；`laborByOrder` 的 `groupBy` 同样只在桩上验证了 `where`/`_sum` 形状。
2. **计件日报的数量口径需要财务过目**：自动分摊数量按工序单位过滤后**跨工序相加**，
   同一件货经过三道工序会重复计件。这是有意留成「参考值 + 人工覆盖」的，但第一个月的实数出来后
   应当和财务核对一次。
3. **科目表缺两个科目**：「应交个人所得税」「应交税费——应交增值税（进项税额）」在财务那张
   `科目表(2).xls` 里没有，模板会给建议名并让财务在下拉里改选（或在「会计科目」页建出来）。
   要不要由我们把它们补进科目表，需要财务确认。
4. **凭证模板只有两张**：财务提到的就是这两套。红冲重开、多借多贷等其它形状靠编辑器手搭。
5. **`SearchableSelect` 与 Radix Select 的焦点交接**：测试里「先选一个 Radix 下拉、紧接着打开
   会计科目搜索框」需要显式等一个宏任务（Radix 关闭时**延迟**把焦点还给它的 trigger，
   那个回调会把搜索框的焦点抢走并触发它的 blur 关闭）。真实用户两次点击之间隔几百毫秒，
   碰不到这件事，所以只按测试时序处理并在用例里写明了原因；如果以后要在同一次事件循环里
   连续切换控件，需要让 `SearchableSelect` 参与 Radix 的焦点管理。
6. **`npm run lint` 跑不了**：仓库没有安装 eslint（不是本轮引入的）。
