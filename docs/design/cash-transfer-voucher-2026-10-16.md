# 备用金付款（资金搬运）的凭证口径 + 旧凭证纠正（2026-10-16）

用户原话：

> 财务部分,凭证管理,如果该笔应付选择的是备用金付款,该笔凭证的会计科目没法正常显示.我需要其正常显示.;
> 并排查,凭证这边,是否能够正常显示所有相应的会计科目.

按「先问清现象、再动账」的规矩问了三轮（现象决定改哪一侧，口径决定改不改账），用户选：

| 问题 | 用户选择 |
| --- | --- |
| 在哪一处看到科目不对 | **凭证纸**（列表行点「凭证纸」弹出的那张） |
| 那一格显示成什么 | **「应付账款」** |
| 凭证纸两行的会计科目 | **借：应付账款 / 贷：银行存款（或库存现金）**（再确认：贷方是**库存现金**） |
| 期望的口径 | **借：库存现金（备用金） / 贷：银行存款** ——「从银行取现到备用金」 |
| 改法范围 | 确认时不该出现「应付账款」；**旧的那些也一起纠正过来**（已过账的按需红冲，草稿直接改） |

## 1. 根因：把「资金搬运」当成了负债

「备用金付款」这类支出在系统里是一条**其他应付**，它的「会计科目」被财务选成了
**资产类的资金科目**（`库存现金（备用金）`）—— 表达的是「把钱从银行搬进备用金柜」，
**不是欠谁的钱**。而代码一律按「应付」两步走：

| 步骤 | 旧口径生成的凭证 | 问题 |
| --- | --- | --- |
| 确认应付（挂账） | 借 库存现金（备用金） / **贷 应付账款** | 凭空造出一笔应付账款 |
| 付款（销账） | **借 应付账款** / 贷 银行存款 | 用户点开凭证纸看到的正是这一张：会计科目写着「应付账款」 |
| 净效果 | 借 库存现金（备用金） / 贷 库存现金 | 两边都是现金科目 ——「钱从哪来」判错了（`fundSubjectFor` 只看结算方式里有没有「现金」二字） |

三处叠加才是用户看到的完整现象：

1. `createAccrual` 只看「有没有指定对方科目」，不区分资金科目与损益/成本科目 → 造出应付账款；
2. `SupplierPaymentService.post` 在「已挂账」分支把借方钉成 `应付账款`，付款单上填的科目
   （备用金那种）只进了「收支类目」，不参与记账；
3. `fundLineFor` 的资金侧只看结算方式文本里有没有「现金」；「提现--备用金现金」「备用金现金」
   这类文本会把**去向**当成**来源**，于是两边都判成现金。

## 2. 口径（用户拍板）

**其他应付的「会计科目」是资金科目（`库存现金（备用金）` 这类）＝ 资金搬运，不是负债。**

- 确认应付：只改状态，**不挂账**（不生成凭证，也不会出现「贷 应付账款」）；
- 付款：一条流水、一张凭证 —— **借 库存现金（备用金） / 贷 银行存款**（有账户就写「银行存款—账户」；
  凭证分录引用该账户，银行明细账照样对得上）；
- 三大报表：`库存现金（备用金）` 计入资金科目族 → 取现是**内部划转**，不进现金流量表；
  用备用金报销费用时才作为资金侧进表（原来那种凭证会被当成「没有资金分录」整笔丢掉）。

判定放在 `createAccrual` 里（它同时拿着「已解析的对方科目」与来源类型），于是
「逐条确认 / 勾选批量确认 / 按对账单确认」三条入口自动同一口径。

## 3. 改了什么

| 文件 | 改动 |
| --- | --- |
| `voucher.domain.ts` | 新增 `isCashFamilySubject` / `isBankFamilySubject`；`fundLineFor` 增加第 0 条判定：**业务科目本身是现金科目 → 资金侧只能是银行存款**（`bankLine()` 抽出来复用） |
| `voucher.service.ts` | `createAccrual`：对方科目是资金科目（应付侧）时不挂账，写 `voucher.accrual_skipped` 审计；`createOrReviveVoucher`（见 §4）；`cashTransferRepairPreview` / `repairCashTransferVouchers` || `supplier-payment.service.ts` | 未挂账的付款：借方 = **人工选的 > 条目自己的科目 > 来源候选链**（原来一律候选链 → 备用金会被写成管理费用）；已挂账的付款借方仍然是应付账款，人工选的科目改走「收支类目」 |
| `finance-three-statements.ts` | `isFundSubject` 把「库存现金」族（含`库存现金（备用金）`）算作资金科目；**有意不**对「银行存款」用前缀（`美金转入` 那类历史数据把银行账户名当业务科目，前缀匹配会把客户货款判成内部划转） |
| `voucher.controller.ts` | `GET/POST /finance/vouchers/cash-transfer-repair`（单段路径，声明在 `@Get(":id")` 之前） |
| `voucher-workspace.tsx` | 页头「纠正备用金/取现凭证」按钮 + 预览弹窗（要删几张/红冲几张/重算几张 + 逐条清单） |
| `payable-workspace.tsx` | 确认应付的提示按事实说话：没有挂账凭证的那些明确说「不挂账、付款时按 借 该科目 / 贷 银行账户 记一张」 |

## 4. 旧凭证纠正（用户：「旧的那些也一起纠正过来」）

`POST /finance/vouchers/cash-transfer-repair`，先 `GET` 预览（不写库）：

- **挂账凭证**：草稿 → 软删（草稿不是账务事实）；已过账 → 红冲后**把红字凭证也撤掉**（软删）——
  这一对在账上必须是 0（这张挂账凭证本就不该存在）；
- **付款流水**：主科目改成条目自己的科目（`库存现金（备用金）`）；
- **付款凭证**：草稿 → 原地按新口径重算分录（科目快照连**分类**一起换掉）；已过账 → 先红冲
  （旧内容原样留在红字凭证上，可追溯），再撤掉那张红字凭证、原地重开成新口径草稿。
  流水没有凭证的只改科目（去点「生成凭证」就是正确的）；
- **一条流水混着非资金搬运的应付时不动它**，只点名（一个主科目拆不开两种语义 —— 按金额最大的硬改，
  那种账事后没人说得清）。

**为什么要撤红字凭证**（`dropReversalsOf`）：红字凭证是「旧内容」的对冲件，而纠正之后旧内容要么被
重写成新口径、要么整个从账上消失。报表取数只认 `status = "posted"`（原凭证 `reversed` 不进表），
红字还留在表里就会剩下一笔**没有任何对应正分录的反向金额** —— 比不改还糟。撤掉的行仍在库里
（`deletedAt`），谁在什么时候撤的都在审计里。

顺带修了两个**它必然会撞上的**缺陷：

1. `vouchers(source_type, source_id)` 是**全量**唯一索引（软删除的行照样占键），所以
   「删掉草稿凭证 → 再生成一次」原来会撞唯一键报数据库错误。现在两条生成路径（由流水生成 /
   手工与挂账）**与红冲**共用 `createOrReviveVoucher`：**原地复活**那一行（清软删、重写分录、
   沿用原凭证号）。这条路径在纠正之后必然被走到（删掉草稿挂账凭证 → 应付回退草稿 → 再确认，
   以及「红冲过的凭证被再次红冲」——红字凭证同样按来源占位）。
2. 由此，本轮的纠正动作是**可重复执行**的（第二次点：挂账凭证已不在、流水科目已是目标值、
   凭证已按新口径），不会因为唯一键而报错。

## 5. 「凭证这边能不能正常显示所有会计科目」的排查结果

| 显示位置 | 会计科目来源 | 结论 |
| --- | --- | --- |
| 凭证纸 / 打印 / 导出 PNG | `voucher_lines.subject_label`（快照） | 正常；本次修的是**快照内容**本身 |
| 记账凭证列表 | 无「会计科目」列（一张凭证多行科目） | 打开凭证纸看；见 §6 待确认 |
| 收支流水表 | `cash_flow_entries.subject`（分类 / 名称） | 正常；备用金付款现在显示「资产类 / 库存现金（备用金）」 |
| 导出 Excel（`voucher-workbook`） | 同上（一行一条分录） | 正常 |
| 分录编辑器 | 科目表（只取启用项；对不上表就原样保留文本） | 正常（代码里有意如此，停用科目不进新分录） |
| 收款/付款单（打印件） | `finance-slip` 的 `general_subject` | 与台账同一条显示链（条目 > 对账单 > 候选链） |

## 6. 未做 / 待确认

1. **记账凭证列表要不要加一列「会计科目」**（把该凭证各行的科目拼起来，如
   「库存现金（备用金） / 银行存款」）：现在必须点开凭证纸才看得到科目；加列要重排列宽
   （那一页的列宽总和被守卫测试钉着：显式列 84% + 审计列 16%）。
2. **已挂账的付款仍可被付款单上的科目顶替借方**：本次只把「人工选的科目」在已挂账时改走
   「收支类目」，没有改成 422（怕打断历史操作）。要不要显式报错由用户定。
3. **停用科目在分录编辑器里退化成自由文本**：保存时 `subject_key` 会丢掉「分类/」前缀。
   现状是刻意的（历史凭证要能原样显示），未改。
4. 纠正接口一次处理**全部**资金搬运应付（没有按期间/勾选筛选）；数据量大时预览清单会很长，
   但纠正本身是幂等的（改完再点一次：`accruals` 为空、流水科目已是目标值、凭证已按新口径重算）。
5. **红冲与报表取数的口径本身不一致**（本轮排查发现，未改）：三大报表只取 `status = "posted"`
   （`finance-three-statements.service.ts:203`），而红冲把原凭证置 `reversed`、另开一张 `posted` 的
   反向凭证 —— 于是「原凭证 + 红字凭证」在表里剩下的是**反向那一笔**（不是净零），
   而设计文档 `finance-three-statements-2026-09-24.md` 写的是「净额正确」。这条影响所有红冲
   （不只是备用金）。本轮的纠正动作因此把红字凭证一并软删，不留悬空的反向金额。
6. 顺带发现并修掉的一处：`vouchers(source_type, source_id)` 是**全量**唯一索引（软删行照样占键），
   「删掉草稿凭证 → 再生成」/「红冲过的凭证再次红冲」原来会撞唯一键报数据库错误；现在统一走
   `createOrReviveVoucher` 原地复活。
