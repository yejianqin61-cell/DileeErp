# 采购计划：填单价入口重新设计 + 「价格待定」下单与补价（2026-10-09 第八轮）

## 一、用户原话与追问

> 「我还是希望在采购计划中前端也能允许填写价格。也可以选择导入BOM的对应的物料的价格。
> 因为用户反馈：其他辅料是要等客户确认资料了，才有价格出来的，现在客户都没给资料，也问不来的价格的。」

追问他「0 价（价格待定）怎么下单」时，他的回答不是选项，而是一句更根本的话：

> 「我真没看到哪里可以手填单价的。可以重新设计这一块。」

（导入范围他选了：**只填还没填（0 价）的未下单行**。）

所以这一轮的重点不是"再加一个字段"，而是**把填价这件事从 14 列的表里搬出来**，
并给"现在问不到价"的辅料一条**有边界**的出路。

## 二、改前：为什么"看不到哪里能填单价"

计划详情是一个右侧浮层，里面有 **14 列**，单价是第 8 列，宽度 **6%**（`globals.css` 的
`.plan-col-price { width: 6% }`）。它就是一个没有标签、没有说明的数字输入框，混在
「本次采购量 / 当前库存量 / 单位 / 单价 / 行总价 / 供应商 / …」中间。采购员要在这样一张表里
找到"哪一格能改价"，找不到是正常的 —— 用户的原话就是证据。

同时，"价还不存在"这件事当时只有一条硬门禁：**单价 0 不能下单**（前端拦一次、后端再拦一次），
理由是应付金额 = 入库数量 × 采购明细单价，0 单价会变成一条 0 元应付。对辅料来说，
这个门禁在"客户还没确认资料"时等于把整条采购流程卡死。

## 三、方案（四块，都是用户点名的）

### 1. 填价入口：状态条 + 「填单价」浮层

- **状态条**（计划面板顶部，`data-testid="plan-price-bar"`）：一行字说清"共几行、还有几行是 0 价"，
  旁边一个按钮 —— 0 价时按钮自己写着「填单价（还有 N 行没填）」，一眼就能看见。
- **浮层**（`components/procurement/plan-price-dialog.tsx`）：一行一行大字填，列是
  「行 / 物料 / 数量 / 单价（可填）/ 行总价 / 状态」。物料与数量就在单价左边 ——
  知道自己在给什么定价，是这一格能不能填对的前提。
- 它改的是计划草稿的**同一份状态**：关掉浮层，表里第 8 列也变了；**点「保存计划」才落库**
  （与原来的模型一致，不新增"改了就算"的语义）。

### 2. 「导入 BOM 参考单价」（只补空）

- 按钮就在浮层顶部。**先重新取一次详情**再导：BOM 上的参考价可能是这份计划打开之后才填的
  （采购员去 BOM 表补了价再回来点它）—— 只拿内存里那份数据，这个按钮等于什么都没做。
- 合并时只并**参考单价两个字段**（`mergeBomReferences`），数量/单价/供应商/预计到货一律不动。
- 只填**未下单且单价还是 0**、且 BOM 上有 > 0 参考价的行。手填过的价不覆盖、已下单的行不碰
  （那些行的价已经是发给供应商的价了）。
- 结果文案把"没填上的"也说清楚：「已按 BOM 参考单价填了 1 行；1 行 BOM 上也没有参考价（请手填）；
  1 行已经填过价（不动）；2 行已下单（不动）」—— 否则用户以为"都导过了"。

### 3. 「价格待定」下单（0 价也有出路，但要走明路）

- 勾选的行里有 0 价时，点「收束下单」**先弹确认框**：写清是哪几行、以及后果
  （"到货登记前必须先补单价"、"价没补上不会让它们入库出应付"）。**确认前一个请求都不发**。
- 确认后请求体才带 `allow_pending_price: true`（`POST /purchase-plans/:id/order`）。
  这个键**只存在于计划这个接口**的 DTO 里 —— `POST /purchase-orders` 与 `/split`
  两个原始接口没有它，所以那两道门一个字都没松（有守卫钉着）。
- 后端把放行做成 `collectGroups(input, placeOrder, { allowPendingPrice })` 的**显式选项**，
  默认仍然 `isPositive`（> 0），放行时也只接受"非负"（负数一律拒绝）。审计里记下
  `pending_price_row_nos` / `pending_price_line_count`：事后能回答"这张单当初为什么没价"。

### 4. 补价：把价补回那张已经发出去的单

- 已下单的行在计划里本来是**全锁**的（要改先「退回采购计划」，而退回会作废那张单）。
  这一轮开一个**窄口**：已下单行**库里单价是 0** 时，允许把单价补成一个正数，
  其余字段（物料/单位/供应商/型号/数量）照旧锁死；补过价（> 0）之后这一行也重新锁死。
- 补价在同一个事务里改三处：计划行、**采购明细**（`unitPrice` + `amount` = 数量 × 价 + 其它费用）、
  **采购单头** `totalAmount`（= Σ 未删明细的 amount，与建单时 `prepare()` 同一口径）。
- 已经有**到货事实**的 0 价行不许补（`PURCHASE_ORDER_ITEM_PRICE_LOCKED`）：那条链上的钱早就按 0
  走过账了，事后改单价只会让账实不符 —— 正确动作是走财务侧的应付调整。
- 审计留两条：计划更新里 `refilled_prices`，以及采购明细上单独一条
  `purchase_order_item.price_refilled`（它改的是**已经发给供应商**那张单上的钱）。

### 5. 钱的那道门挪到"到货登记"

`PurchaseOrdersService.receipt()` 新增门禁：明细单价 ≤ 0 时拒绝登记到货
（`PURCHASE_ITEM_PRICE_PENDING`），提示"先在采购计划里补单价"。这样"价格待定"这条链的终点仍然是
**不会出现 0 元应付**：0 价可以下单（占住供应商与交期），但货到之前必须把价补上。

边界说清：
- **不做**入库过账处的第二道门 —— 到货是货物已经进厂的事实，卡在那里操作上更疼；
  正常链条上到货登记是唯一入口，第二道门只在"本轮上线之前就已经按 0 价收过货"的历史数据上才有意义，
  那批数据走财务调整（`应付` 有编辑与回退入口）。
- 已下单 0 价行在表里有 **「价格待定」** 标记（下单状态那格），行总价同样标红：这笔钱还没定下来。

## 四、取舍

- **不做**"给个占位价再改"（比如先填 1 元）：那会让采购单上出现一个假数字，而供应商手上的单是凭证。
  空着 + 标记「价格待定」比假数字诚实，也更容易在系统里被拦住。
- **不做**"0 价也能直接到货入库、应付先记 0"：财务确实没法付 0 元应付，等于把这个洞从采购挪到财务。
- 计划列表的「计划金额」列**不显示**"价格待定"的行能有几个钱（它们就是 0）—— 那一列是"已定的钱"。
- 导入**不覆盖**手填的价：BOM 上的是"参考价"，计划里那一格才是"谈定的价"。
