# 工资：税/社保上表 + 工资付款归类到「工资支付」（2026-09-20）

用户原话（两条）：

> 现在，工资的确认支付也要加上会计科目，会计科目里面多加一个工资支付。这样确认支付工资的时候
> 就能归类到工资支付里面。好做账，好出表。

> 工资现在还要体现出 税，社保。这些字段允许财务自行填写。最终总工资要扣掉税和社保。

---

## 一、税与社保：模型一直都在，缺的是「看得见、填得进」

先澄清一个容易误判的地方 —— **`social_insurance` / `individual_tax` 早就存在，而且早就在扣**：

| 位置 | 状态 |
|---|---|
| `payroll_ledgers.social_insurance` / `individual_tax` 两列 | 已有（`20260915140000_payroll_ledger_salary_categories` 引入） |
| 应发公式 `payrollBaseAmount` | `.minus(social_insurance).minus(individual_tax)` —— 已在扣（`hr-payroll.domain.ts:46-47`） |
| DTO：`PayrollGenerateDto` / `PayrollUpdateDto` | 都有 `social_insurance` / `individual_tax` |
| 「编辑工资台账」弹窗 | 有「社保」「个税」两个输入框 |
| **工资台账表格** | ❌ 两列**都不是列**，被叠进只读的「其他增减」净额里 |

所以财务说「工资还要体现出税、社保」，问题不在算得对不对，而在**看得见与填得进**：
主表格上只有一个只读的「其他增减」，社保与个税和加班、考勤扣款、补贴、其他调整**加在一起**，
财务既看不到单独的社保/个税是多少，也没法在表里逐行改 —— 想调只能开弹窗，一格一格点。

### 1.1 改了什么

1. **`payrollOtherAdjustmentAmount` 去掉社保与个税**（`hr-payroll.domain.ts`）：
   该只读列现在的口径是「加班 − 考勤扣款 + 补贴 + 其他调整」，加号后面再由调用方另加已过账的工资调整。
   不把它们摘出来，表上会出现「社保」显示两次、而应发只扣了一次的错觉，财务根本无法核对。
2. **新增 `payrollDeductionAmount(社保, 个税)`**：两项代扣的合计（**正数**），
   让前端与导出用同一份口径算「扣了多少」，而不是各处各写一遍 `plus`。
3. **表格加「社保」「个税」两列**（`salary-workspace.tsx`）：与绩效/房补同级 ——
   各自一列、可逐格编辑（同一套 `commitCell` → `PATCH /hr/payroll-ledgers/:id`）、可合计、随筛选留存。
4. **不变式更新**：`表上可见列之和 = 应发` 仍然成立，只是现在写成了
   `基本工资 + 绩效 + 房补 − 迟到 − 旷工 − 早退 + 其他增减 − 社保 − 个税 = 应发`。
   这条不变式原来由 `hr-payroll-domain.test.cjs` 的「六个可编辑类目 + 其他增减」守着，
   现在守「八个可编辑类目 + 其他增减」并显式减去两项代扣。

### 1.2 符号口径（写死，别再问）

**社保与个税在库里、在界面上都是正数，表示「被扣掉的金额」**，由 `payrollBaseAmount` 做减法。
不是「填负数表示扣款」—— 那种写法在表上会与「其他增减」的正负号混在一起，没人能一眼看懂。

### 1.3 出表

工资付款表与按月导出（`payroll-payment-sheet.ts`）都加了这两列：

- 导出列序：`… 币种 / 应发工资 / 社保 / 个税 / 已付 / 未付 / 是否付款 …`（**18 列 → 20 列**）；
- 五个金额列（应发工资 / 社保 / 个税 / 已付 / 未付）都是**数值列**并参与合计 ——
  数值列少一个，Excel 里 `SUM` 得 0；多一个，文本列会被当成金额；
- 表尾新增一句口径说明：**「应发工资」= … − 社保（个人部分）− 个税，即实际应发放给员工的金额**。
  没有这句，财务看到「应发工资」比工资表低会以为漏发了。

## 二、工资付款的会计科目：新增「工资支付」并可选

### 2.1 为什么之前归不到「工资支付」

工资付款过账时会写一条收支流水，业务科目取自**写死的候选链**
（`accounting-subject-catalog.ts` 的 `PAYMENT_SUBJECT_NAMES.salary_payment`）：

```
salary_payment: ["临时工资", "基本生产成本"]   ← 2026-09-20 之前
```

于是自动生成的工资凭证是 `借 临时工资 / 贷 银行存款`，财务要的「工资支付」这个类别在科目表里
**根本不存在**，也无从选择。

### 2.2 三处改动

**① 科目表新增「工资支付」**（成本类 / 借 / `sortOrder` 715）。

新增的是 `SUPPLEMENTARY_SUBJECTS`（**系统补充科目**），不是直接塞进 `ACCOUNTING_SUBJECTS`：

> `ACCOUNTING_SUBJECTS` 的口径是「财务那张 `科目表(2).xls` A2:H122 共 121 行的照抄」，
> `accounting-subject-catalog.test.cjs` 用长度与分类计数**守着这一点**（它是「老库升级 / 新库初始化
> 种出同一张表」的唯一保障）。把新增科目混进去，那条守卫就会为了迁就我们而放松，
> 以后再也分不清「哪些是财务的表、哪些是我们加的」。

于是拆成：`ACCOUNTING_SUBJECTS`（121，不动） + `SUPPLEMENTARY_SUBJECTS`（我们的新增）
= `ACCOUNTING_SUBJECT_SEEDS`（按 `sortOrder` **归并成一张有序表**，122 条）。
迁移、`seed.ts`、守卫测试全部用 `ACCOUNTING_SUBJECT_SEEDS`。

`sortOrder = 715` 的取法：夹在「临时工资 610 … 印刷费 710」之后、「实收资本 720」之前，
保持成本类整块连续（分类交错会把列表与报表的「分类小计」拆成两行）。

**② 默认候选链首位改成「工资支付」**：

```
salary_payment: ["工资支付", "临时工资", "基本生产成本"]
```

后两个保留，只为兼容「科目被停用 / 改名」的历史环境 —— 一条候选都不命中会让整笔资金动账
写不进流水（`CashFlowService` 抛 `ACCOUNTING_SUBJECT_NOT_FOUND`，不是静默跳过）。
**效果：不额外选任何科目，工资付款也会自动归到「工资支付」。**

**③ 工资付款单带会计科目**（`salary_payments.subject_id`，新增迁移）。

与 `customer_payments.subject_id` / `supplier_payments.subject_id` **同一口径**
（这两张表早就有这个列，工资付款一直是缺的那一方）：

- 列可空 + `ON DELETE SET NULL`：历史付款单没有这个值；科目是「只停用不删除」的配置数据，
  真被删时应当把引用置空，而不是连带删掉付款单或报数据库约束错；
- 优先级：**过账时传的 → 付款单上存的（建草稿时选的）→ 都不给则按来源自动归类（首位「工资支付」）**；
- `requireSubject`（科目校验的唯一实现）在**建单前**与**过账前**各校验一次，
  非法科目直接 422 且不落任何单据 —— 不允许出现「指向不存在科目的付款单」。
  只在真有值时才查库，所以「不指定」这条路径不为每次付款白跑一次查询；
- `AccountingSubjectService.usageCount` 补上 `salaryPayment`：漏掉这一处，
  财务删除一个只被工资付款引用的科目会撞外键 RESTRICT（数据库报错，财务看不懂）。

### 2.3 界面

行内付款与批量付款弹窗都加了「会计科目」下拉（`searchable-select`，与全站科目下拉一致）：

- **默认预选「成本类 / 工资支付」**：不改也能归对；
- 可改选别的科目；
- 有一个「**（不指定，按来源自动归类为「工资支付」）**」哨兵项：选中时**不发送** `subject_id`，
  让后端走自己的候选链 —— 发空串会被 DTO 的 `@IsUUID()` 判非法而 400；
- 科目表里没有「工资支付」（老库还没迁移）时不预选，提交也不带 `subject_id`，**付款照常能用**。

## 四、未做 / 待确认

1. **社保与个税仍由财务手填，系统不自动算**。自动算需要社保基数、险种比例、个税累计预扣法
   （专项附加扣除、年度累计），这些数据系统里没有。用户这次的用词也是「这些字段允许财务自行填写」，
   所以本轮只做「可填 + 可看 + 扣减 + 出表」。
2. **没有公司承担部分的社保**。`social_insurance` 是**个人部分**（从员工应发里扣）。
   公司承担部分属于费用，要单独挂账，目前没有对应字段 —— 财务要的话需要新增。
3. **迁移未在真实 PostgreSQL 上跑过**。本机没有可用数据库，迁移的正确性只由静态守卫
   （`salary-payment-subject-migration.test.cjs`）与 Prisma schema 校验保证。
   第一次部署时请留意：`ALTER TABLE salary_payments ADD COLUMN subject_id`
   与 `INSERT ... ON CONFLICT DO NOTHING`。
4. **历史工资凭证的科目不会自动改**。之前已经生成的凭证仍是 `借 临时工资`；
   改口径只影响**这次之后**过账的付款。要修历史，用凭证红冲 + 重开（注意：凭证红冲后
   当前无法重开，见 `docs/design/sales-order-create-400-fix-2026-09-20.md` 与冲销审计的遗留项）。
5. **凭证仍只能从收支流水生成**。这次让工资付款这笔支出能归到「工资支付」，
   但**计提**工资（借 应付职工薪酬 / 贷 其他应付款、应交税费）依旧没有凭证可出 ——
   那是「手工凭证 / 从业务单据生成计提凭证」的事，尚未开工。
