# 收支明细表的「收支类目」+ 确认应付的搜索与批量删除（2026-10-13）

> 用户原话：
> 「1.财务部分，收支明细表，也要显示收支类目。比如说采购某个物料，或者其他应付其他应收也要带上会计科目。
> 而且导出的excel也要显示相应的column。
> 2.财务，确认应付，加一个搜索框，加一个批量删除（只支持其他应付的删除）」

本文档是实施依据。口径在实现中不得擅自改变；要改先改本文档，并在 `docs/log/` 里记下改的理由。

---

## 一、收支明细表的「收支类目」

### 1.1 排查结论：现有两列是「现金分录的科目」，不是「这笔钱算什么」

`财务 → 报表 → 收支明细表` 2026-09-17 起就有「分类（科目类别）+ 项目（科目名称）」两列，
取的是 `cash_flow_entries.subject_id`。而这条流水上的科目是**销账那条现金分录的对方科目**：

| 行来自 | 流水的 `subject_id` 是什么 | 财务看到的 |
| --- | --- | --- |
| 供应商付款（采购 / 外加工 / 其他应付） | 本次核销的应付**都挂过账** → `应付账款`；没挂过账（历史数据）→ 按来源类型的候选链（`其他` → **管理费用**） | 一列全是「应付账款」/（历史的）管理费用 |
| 客户收款 | 同理 → `应收账款`，否则 `主营业务收入` | 应收账款 |
| 工资付款 / 手工流水 | 单子上选的科目 | 正确 |

所以财务说「看不到收支类目」：**应付账款 / 应收账款 回答的是"这笔现金分录的另一头是谁"，
回答不了"这笔钱花在什么上"**。而"这笔钱算什么"这件事，单据上是**有**的：

| 来源 | 这笔钱算什么的科目在哪 |
| --- | --- |
| 其他应付（备用金 / 房租 / 水电） | 条目自己的 `supplier_payable_entries.subject_id`（2026-10-12 加的）→ 否则覆盖它的应付对账单 `subject_id` |
| 采购 / 外加工应付 | 条目一般没填 → 按来源类型的候选链（原材料 / 主营业务成本 / 加工费） |
| 其他应收 / 客户收款 | 覆盖这条应收的**应收对账单** `receivable_reconciliations.subject_id` → 否则 `主营业务收入` |

### 1.2 口径：不动账，**另加一列**「收支类目」

用户问过「要不要把『项目』这一列直接改成收支类目」，选了**另加一列**。理由（也是我不建议改原列的原因）：

- 从一条流水**生成凭证**时（`POST /finance/vouchers/from-cash-flow/:entryId`），凭证的对方科目就是
  流水上的 `subject_id`。已挂账的付款正确写法是 **借 应付账款 / 贷 银行存款**；把这一列改成
  「房租费」，生成出来的凭证就是 **借 房租费 / 贷 银行存款** —— 而房租费在**确认应付**那一步
  已经借过一次（挂账凭证），成本会**重复记一次**，且账面上看不出来。
- 「分类 / 项目」与凭证一致、「收支类目」回答业务口径，两列各答一个问题，不互相污染。

**优先级（写进 `cash_flow_entries.category_subject_id`）**：

```
① 本次核销的单据上写的科目（应付：条目 > 覆盖它的对账单；应收：覆盖它的应收对账单）
     多条时取「核销金额最大」的那一条 —— 与主科目按「金额最大的来源类型」同一条思路
② 单据上没有 → 按来源类型的候选链（采购 → 原材料/主营业务成本；其他应付 → 管理费用；收款 → 主营业务收入）
     即用户说的「猜的只当兼底」
```

**宽松取值**：① 来自单据，科目可能早已停用/改名 —— 认不出就**安静地退回 ②**，
绝不让一笔已经发生的付款因为一个分类字段过不了账（与主科目 `subjectId` 的严格 422 语义刻意不同）。

### 1.3 落库与出口

| 层 | 改动 |
| --- | --- |
| 库 | 新列 `cash_flow_entries.category_subject_id`（可空，FK → `accounting_subjects`，**ON DELETE SET NULL**，带索引）——迁移 `20261013160000_cash_flow_category_subject` |
| 写入 | `CashFlowService.autoCreateFromPayment()` 新增 `categorySubjectId` / `categorySubjectNames` 两个入参；两个调用方（供应商付款、客户收款）按上面的优先级算好传进来 |
| 报表 | `CASH_FLOW_DETAIL_COLUMNS` 在「项目」之后插一列**「收支类目」**（9 → 10 列）；`cashFlowDetail()` 取数带上它 |
| 导出 | 与预览同一张 `ReportTable` → Excel 自动跟着多这一列（口径 5 的既定事实：预览与导出共用一个列定义） |
| 前端 | **不改**：报表页的列由后端 `ReportTable.columns` 下发（`finance-report-workspace.tsx`），加列不必动前端 |

**手工流水这一列留空**（页面上显示空单元格）：手工录一笔时财务只选一个会计科目，
那个科目**就是**这笔钱的类目，`分类 / 项目` 已经写着它了；再抄一列没有信息量。
表尾写明这一点，免得财务以为是漏填。

**为什么不是「删除科目的处理」问题**：可空 + `SET NULL` 与 `supplier_payments.subject_id`
（2026-10-12 复核里点名的两处）同形 —— 这一列是**展示用的业务分类**，不是记账依据，
删科目时不该被它挡住，也不进 `AccountingSubjectService.usageCount()`。

### 1.4 刻意不做

- **不拆流水**：一笔付款同时核销备用金（库存现金）与房租（房租费）时，流水仍是**一行**，
  「收支类目」取金额大的那条。拆成两行会动到「一条付款一条流水」的既有不变式
  （幂等、银行余额、付款单取数都建立在它上面），代价远大于收益。已写进「待确认」。
- **不改收支汇总表**：它按「分类 × 科目 × 币种」聚合，聚合维度是 `subject_id`（账务口径），
  与新列的「业务口径」不是一回事。用户这次只提了明细表。
- **不动手工流水的录入表单**：只选一个科目，见 1.3。

## 二、确认应付：搜索框 + 批量删除（仅其他应付）

### 2.1 搜索框：面板里再给一个

页面顶部本来就有一个搜索框（`data-testid="payable-search"`，一个框管三个页签的全部表格）。
但它在**流转看板之上、离「确认应付」那张表很远**，财务坐在那张表前面看不见它 —— 她要的是一个
**就在表上方**的搜索框。所以在这一张面板的筛选栏里再加一个（`data-testid="payable-ledger-search"`），
并且它比顶部那个**能搜更多字段**：单号 / 订单号 / 采购单号 / 供应商 / 物料 / **费用说明** / **会计科目**。

两个框是**两个独立的状态**（顶部的 `filter` 管全页，面板里的 `ledgerFilter` 只管这张表），
不互相改写 —— 否则「在确认应付里搜了一下，切到应付对账发现那张表也被过滤了」会让人莫名其妙。

### 2.2 批量删除：逐条结果，只删其他应付

| 层 | 改动 |
| --- | --- |
| API | 新增 `POST /finance/payable-entries/batch-delete`，body `{ ids: string[], reason: string }`（ids ≤ 200、reason 必填） |
| 服务 | `SupplierPayableService.batchRemoveOther()` —— **逐条**调用既有的 `removeOther()`（每条一个事务），收集成功与失败 |
| 返回 | `{ deleted: [{ id, payable_no }], failed: [{ id, payable_no, code, message }] }`，前端点名说清哪几条没删及原因 |
| 前端 | 「确认应付」面板的批量栏加一个「批量删除其他应付（N 条）」按钮 + 一个必填原因的弹窗 |

**为什么逐条而不是整批原子**（用户已确认）：批量删除的典型场景是"一次录错了一整批"，
而一大批里偶尔会有一条已经被对账单覆盖（后端会拒）。整批回滚会让她先把那条摘出去再重来一遍；
逐条结果则"能删的删、不能删的点名"，且每条删除**本身**仍是原子的（含已确认的会回冲那笔支出流水）。

**按钮的边界**（与后端三条边界一致，界面不摆点了必然报错的按钮）：

- 只有 `sourceType === "other"`（其他应付）才可删 —— 原料入库 / 外加工签收的应付来自到货事实，录错了要走冲销；
- 只有 `draft` / `confirmed`（尚未付款）可删；部分付款 / 已付清的拒绝（核销记录会指向一条不存在的应付）；
- 已被对账单覆盖的拒绝，并给可执行的下一步（先去「应付对账」删那张对账单）。

界面上这三条各自给一句理由（锁在勾选框与弹窗里），后端仍然是**唯一**的判据（逐条 422 被吞成
`failed` 的一条），所以「前端说能删、后端却拒」这种漂移不会成为死胡同。

## 三、实施结果（2026-10-13）

| 检查 | 结果 |
| --- | --- |
| `npm run build --workspace=@dilee/api` / `tsc --noEmit`（api、web） | 双绿 |
| API 全量单测 | **见 `docs/log/2026-10-13.md`**（本轮新增：迁移守卫 4 条、`autoCreateFromPayment` 的收支类目 4 条 + domain 1 条、供应商付款 4 条、客户收款 1 条、批量删除 5 条；另有 5 条既有的收支明细表用例按 10 列改写） |
| web lib / 组件测试 | 同上（`payable-page` 新增 5 条、`finance-report-page` 新增 1 条） |
| `test:api` / `test:integration` / `test:e2e` | **环境阻断**（本机没有 PostgreSQL 与已启动的 API） |

未在本机验证的项（部署时请人工确认）：

1. **迁移没在真库上跑过**（本机没有 PostgreSQL）。本仓库的迁移是手写 SQL，schema 与 SQL 的对齐
   只能靠静态核对 —— 已由 `cash-flow-category-migration.test.cjs` 逐字段钉住（列类型 / 可空 /
   外键动作 / 索引 / 反向关系）。
2. **历史行不会回填**：已有的收支流水 `category_subject_id` 全是 NULL，报表那一格空着。
   要填只能重下那些付款（或者手工补），本轮的迁移**不动**历史数据。
3. **一笔付款核销多种科目**时只显示金额大的那一条（见 1.4）；要逐条看到需要把一条流水拆成多行。

设计文档的**待确认**（留给财务一句话就能定）：

1. 上面第 3 条：要不要把流水按科目拆成多行（那样收支汇总表也能按类目统计得更准）。
2. 历史「未挂账」的付款流水，主科目仍是按来源类型的候选链（`其他` → 管理费用）。
   新列会把真正的类目显示出来，但**旧行的主科目不会被回填**（改历史账是财务的活）。
3. 手工录入的收支流水「收支类目」为空 —— 要不要在录入表单上也加一格（现在它只选一个主科目）。

## 四、2026-11-05 口径变更：分类/项目改为「业务科目」，原「收支类目」列改名「记账对方科目」

> 用户报障：「针对财务部分，用户反馈，每一笔确认应付中选择的会计科目，到了收支流水中都是错的。
> 但是凭证里的会计科目又是对的。你可以看一下线上数据库里收支流水 CF-20261105-9CFB412B 这笔流水」
> （补充点名确认应付 `APO-20261027-CE78BFBC`）。

线上事实（生产库只读查询）：

| 落点 | 值 |
| --- | --- |
| 应付条目 `APO-20261027-CE78BFBC`（其他应付，拼多多 ¥27.2，采购窗帘夹子） | 损益类 / **管理费用** —— `supplier_payable_entries.subject_id` |
| 它的付款单 `SPAY-20261105-586A2F56` | 损益类 / **管理费用** —— `supplier_payments.subject_id` |
| 付款流水 `CF-20261105-9CFB412B` 主科目 | 负债类 / **应付账款** —— `cash_flow_entries.subject_id`（销账那条现金分录的对方科目） |
| 同一条流水的收支类目 | 损益类 / **管理费用** —— `cash_flow_entries.category_subject_id` |

收支流水页的「分类 / 项目」取的是前者，于是已挂账付款整页显示「应付账款」、按「损益类 / 管理费用」
筛选一条都筛不出来；凭证纸上是对的（挂账凭证借方 = 管理费用）。这正是 §1.1 描述的那个问题在
**流水页与汇总表**上的残留 —— 2026-10-13 只给明细表加了「收支类目」一列，流水页和汇总表没跟上。

### 4.1 改了什么

| 层 | 改动 |
| --- | --- |
| 口径 | 「分类 / 项目」= **业务科目**（`category_subject_id`，手工流水退回主科目）。§1.2 里「另加一列、原列不动」改为「原列改成业务科目，对方科目单独一列」 |
| 领域 | `cash-flow.domain.ts` 新增 `cashFlowBusinessSubject()` 与 `cashFlowSubjectWhere()`：显示与筛选共用一条规则，不在页面/报表各写一份 |
| API | 列表 `ENTRY_INCLUDE` 带上 `categorySubject`；`?subject_id=` / `?category=` 按业务科目匹配（类目为空才退回主科目）；`PATCH` 新增 `category_subject_id`（自动流水改类目，**不动**主科目） |
| 收支明细表 | 第 6 列「收支类目」→「记账对方科目」，内容改为主科目（与业务科目相同时留空） |
| 收支汇总表 | 聚合键从 `subject_id` 改成业务科目 id —— 否则「这个月管理费用多少」仍然只能看到一行「应付账款」 |
| 收支流水页 | 「分类 / 项目」显示业务科目；对方科目挂在项目格 `title`；更正弹窗对自动流水改 `category_subject_id`，并写明「对方科目由来源单据决定」 |
| 凭证模块 | 「收支流水」表同口径（显示业务科目），搜索也带业务科目名 |

### 4.2 为什么不是「把主科目也改成管理费用」

主科目是**生成凭证时的业务分录科目**（`POST /finance/vouchers/from-cash-flow/:entryId` 用它）：
已挂账的付款必须记「借 应付账款 / 贷 银行存款」，改成管理费用就是重复记一次费用，
而且账面上看不出来。§1.2 的那条理由仍然成立 —— 变的是**展示与统计口径**，不是记账。

### 4.3 没做

- 历史流水**不回填** `category_subject_id`（除 `supplier_payment` 外多为 NULL）：显示按业务科目回退到主科目；
  手工流水与「确认即记账」流水本来就是主科目，不受影响。
- 不拆流水（一笔付款核销多个科目时仍取金额最大的那条，同 §1.4）。
- 手工流水录入表单仍只有「会计科目」一格：那个科目**就是**它的业务科目，不需要第二格。
