# 销售单「复制」+ 采购计划「没确定单价的先不下单」（2026-10-11 · 第二轮）

用户一次提了两条需求：

> 「1.销售部分：销售单这边添加一个复制，把别的单的所有详情可以整单导入。用户原话"就是订单描述基本差不多，
> 可以直接用原有的复制，然后我们改下单号和里面的细节就行了，可以这样吗"
> 2.采购部分，采购计划，要支持，确定单价的能下单，没确定单价的先不下单。」

开工前问了三个问题（每题给推荐项），用户的回答：

| 问题 | 回答 |
| --- | --- |
| 「复制」的适用范围 | **普通复制**：任何状态的单都能复制（含草稿）、不要求货号；新单**不记来源**；与既有「返单」并存 |
| 复制出来的新单号 | **留空、必填**（与新建单一致） |
| 采购计划 0 价怎么处置 | **去掉「价格待定」放行**：0 价的行就是不下单，留在计划里 |

## 一、销售单「复制」

### 1.1 与既有「返单」的区别（这是本轮最要紧的一处判断）

系统里**早就有**一套复制机制：**返单**（`/sales/orders/new?reorder_from_order_no=…`，
后端 `SalesOrdersService.resolveReorderSource()` / `reorderPreview()` / `reorderInput()`）。
但它有三道硬门槛：

1. 来源必须**已确认或已关闭**（草稿不能返单 —— 草稿还没下给工厂，拿它返单等于复制一件没做过的事）；
2. 来源必须**有货号**（老板要的是「返单货号不变」，没有货号就变不出来）；
3. 复制出来的单**记下来源**（`reorder_from_order_no`），并因此归进【返单与总结】的货号分组。

用户这次要的「复制」**三条都不需要**：任何状态、不要求货号、不记来源（新单就是一张普通新单）。
所以它是**另一个功能**，不是返单的开关。两者并存，各用各的场景。

### 1.2 复制什么 / 不复制什么

规律与返单**同一条**（照抄它的取舍，不另发明一套）：

| 这一类 | 复制吗 | 内容 |
| --- | --- | --- |
| 「这一单卖的是什么」 | ✅ 复制 | 客户（含联系人）、产品名称/规格、单位、币种、客户单号、外合同号、结算方式、单价/结算单价/税率、货号、37 个细化标量、`extension_data`、细分明细（含列名）、材料引用、「其它」行 |
| 「这一单卖多少、什么时候交」 | ❌ 不复制 | 数量、下单日、交期 |
| 「由数量派生的金额」 | ❌ 不复制 | `total_amount` / `receivable_amount` / `local_currency_amount`（抄过来必然与新的数量矛盾，而矛盾会一路传到应收来源） |
| 「这一单走到哪了」 | ❌ 不复制 | 状态、版本号、BOM、下游事实、返单来源 |

### 1.3 关键安全点：失效的物料引用必须剔掉

一张旧单可能引用过**已经被删掉的物料**。不过滤的话，新建页会在 `assertMaterialsExist` 处卡死在
`MATERIAL_NOT_FOUND`，提示还叫人「刷新物料清单后重选」—— 而复制这条路**根本没有"重选"这个动作**，
用户只会看到一张打不开的空表。返单已有这一步，复制必须复用（剔掉了什么要回报出来，不静默吞）。

### 1.4 建单仍走标准接口

复制出来的数据由前端预填进新建页，**保存走标准 `POST /sales-orders`**，不另写建单路径。
`create()` 已经支持 `spec_details` / `material_refs` / `material_extras` / `spec_detail_labels` /
`extension_data` / 37 个细化标量，所以不需要为复制开后门 —— 后门会绕过币种校验、客户/联系人解析、
材料存在性校验与 `ORDER_NO_CONFLICT` 处理，那类绕过不会当场报错，只会在几个月后爆掉。

## 二、采购计划「没确定单价的先不下单」

### 2.1 这条推翻了 2026-10-09 的「价格待定」

必须记下这个来回，因为它是一次**明确的口径反转**，而且同一个人前后两次要求相反：

| 日期 | 原话 | 结论 |
| --- | --- | --- |
| 2026-10-09 | 「其他辅料是要等客户确认资料了，才有价格出来的，现在客户都没给资料，也问不来的价格的」 | 允许**显式**带 0 价下单（`allow_pending_price`），先占住供应商与交期 |
| 2026-10-11 | 「确定单价的能下单，没确定单价的先不下单」 | **0 价一律不下单** |

所以本轮**先问后做**，用户选了「去掉放行」。附注：10-09 那条需求的真实痛点（辅料要等客户资料、
价问不到）在**新口径下仍然能满足** —— 办法变成「先下有价的，没价的等报价来了再下一波」，
而分波下单本来就是系统的既有能力（没收进任何组的行留在计划里）。

### 2.2 改法：三处一起删，不留后门

| 位置 | 改动 |
| --- | --- |
| `purchase-plans.controller.ts` 的 `PlanOrderDto` | 删掉 `allow_pending_price`（连同只在它身上用的 `IsBoolean` 导入） |
| `purchase-plans.service.ts` 的 `order()` | 删掉例外分支：0 价**一律** `PURCHASE_PLAN_PRICE_REQUIRED`；`pending_price_row_nos` / `pending_price_line_count` 两条审计字段一并删（不再存在这一档） |
| `purchase-orders.service.ts` | 删掉 `assertOrderableItems` 的 `options.allowPendingPrice` 例外与 `collectGroups` 的第三个参数 |

**为什么必须三处一起删**：只改默认值而留着开关，等于仍然有一条通往 **0 元采购单 → 0 元应付** 的路
（应付金额 = 入库数量 × 采购明细单价，见 `raw-material-inbounds.service.ts`）。现在没有任何调用方
能放行 0 价；`receipt()` 的 `PURCHASE_ITEM_PRICE_PENDING` 仍留着兜住 10-09~10-11 之间已下出去的历史单。

### 2.3 前端：0 价的行「留在计划里」要在页面上看得见

`plan-detail-sheet.tsx` 的 `order()` 不再有「确认放行」分支：

- **勾中的行全都没价** → 直接拦住，错误条说清「都还没有单价（第 N 行）：先点「填单价」填上，再下单」，一个请求都不发；
- **有价与没价混在一起** → 下单请求只含**有单价的行**（`placedGroups`），弹一次复核框说清
  「第 N 行本次不会下单、留在计划里、补价后再下一波」；
- 预览面板多一句 `plan-held-back-note` 点名哪几行被留下；通知文案也带上「第 N 行没单价，留在计划里」。

**按钮禁用的三种情况**（这里踩过一次坑）：一行都没勾 → 灰；**勾了但都没价 → 不能灰**
（灰着而页面上没有任何解释，采购员只会以为系统坏了 —— 与 2026-10-09「我真没看到哪里可以手填单价的」
是同一类坑）；有价但有价的行还没选供应商 → 灰（预览里已标红说明）。

### 2.4 为什么「补价」那条路留着

`PlanPriceDialog` 仍允许给**已下单且单价还是 0** 的行补价，`plan-price-pending-*` 标记也留着。
理由：10-09~10-11 之间按「价格待定」下过的单**还在库里**，删掉这个入口等于让那些行永远卡在没价、
无法登记到货。页面上这一档的文案已改成「价格待定（需补价）」并写明它是**历史单**。

## 三、门禁

| 门禁 | 结果 |
| --- | --- |
| `npm run build --workspace=@dilee/api` | 干净 |
| API 全量单测（193 文件，逐文件 in-process） | **2393 / 2393** |
| web 组件测试（**全量 65 文件**） | **1104 / 1104** |
| web lib 测试 | **337 / 337** |
| `tsc --noEmit`（api） | 干净 |
| `tsc --noEmit`（web） | 我的改动零错误；工作区里另余 17 个错误**全在 `payable-workspace.tsx`**（另一笔在途改动） |
| `apps/api/test/http/*` | **跑不了**（`TEST_BLOCKED: INITIAL_ADMIN_USERNAME and INITIAL_ADMIN_PASSWORD are required`）—— 本机没起 API 与数据库，与本轮改动无关 |

**环境坑**：本机内存紧张，`nest build` / `tsc` / vitest 用默认 heap 会 OOM
（`NewSpace::EnsureCurrentCapacity`）。稳的跑法是
`NODE_OPTIONS="--max-old-space-size=1536 --max-semi-space-size=16"`，vitest 用 `--maxWorkers=2`。

**分工与终验**：两条需求互不相干、文件不重叠，所以「销售复制」整块派给一个同伴（task-1），
采购那条由 Lead 改。两边都会碰 `dist/`，因此**全量门禁由 Lead 在收口时统一跑一次**（上表就是那一次）。

## 四、Lead 对同伴交付的独立复核

同伴交付后**没有只看它的测试报告**，而是自己读代码核了最要紧的几处（测试通过 ≠ 合同正确）：

| 复核项 | 结果 |
| --- | --- |
| `GET /sales-orders/:id/copy-snapshot` 的路由顺序 | ✅ 声明在 `@Get(":id")` **之前**（否则 Nest 会把两段路径当成销售单 id 去查库） |
| `copy` 里**不含** `order_no` / `order_date` / `quantity` / `delivery_date` | ✅ 四个键都不在 |
| `copy` 里**不含**金额三兄弟（`total_amount` / `receivable_amount` / `local_currency_amount`） | ✅ 都不在 |
| **没有来源键**（`reorder_from_order_no`） | ✅ 返回里没有；编辑器在 copy 分支只带 `extension_data` |
| 失效物料过滤的签名与返回 | ✅ `usableMaterialRefs(refs) → {refs, dropped}` / `usableMaterialExtras(extras) → {extras, dropped}`，调用形状对得上 |
| 复制是否走了标准建单 | ✅ 保存走 `POST /sales-orders`（`else if (copySource)` 分支不写任何来源键） |

顺手修掉同伴留下的两处占位日期（`2026-10-XX` → `2026-10-11`）。

## 五、未处置 / 待确认

1. **复制是否该拦「有下游事实」的单**：本轮的实现按用户口径**不拦**（任何状态都能复制）。
   复制一张已经有 BOM/采购/出库的单是安全的（只是抄字段），但**下游事实不会跟着复制** ——
   新单是一件干净的新工作。若以后希望「有 BOM 的单复制时也把 BOM 抄一份」，那是另一个功能。
2. **历史「价格待定」单的存量**：库里到底还有多少「已下单但单价是 0」的行，本机查不到（没有数据库）。
   上服务器后值得看一眼 —— 那些行在补价之前**不能登记到货**，采购员会卡住。
3. **`allow_pending_price` 的向后兼容**：DTO 已删该字段，旧的前端版本若还带着它发请求，
   会被 class-validator 的 `forbidNonWhitelisted` 拒绝（这是有意的：宁可报错，也不要让它静默生效）。
   部署时前端与后端要一起上。
