# 收/付款单（可编辑 + 导出）与「对账 / 确认」合并（2026-09-20）

财务这一天提了三件事，后两件是同一条线上的：

1. 「她需要在付款界面能导出付款单……允许用户编辑付款单中的一些字段。比如**我要付款 100，
   我可以自己填加行，我可以写付款备注**。」
2. 「**应收管理中，应收对账和确认应收我们合并在一起。合并到一个视图里。但是仍然需要用户进行
   先创建对账，再确认的这两个动作。同样的，应付管理中，应付对账和确认应付也要合并在一起，
   仍然需要两个动作。**」
3. 「应收，应付。**支持勾选多选条目，进行收束集中收款付款。并提供付款单的编辑和导出。
   同理，收款单的编辑和导出。**」

落到代码上：
`apps/api/src/modules/finance/finance-slip{,.service,.controller}.ts` +
`apps/web/lib/finance-slip.ts` + `apps/web/components/finance/finance-slip-editor.tsx`（收付款单）；
`apps/web/lib/finance-sections.ts` + 两个工作区组件（合并与集中收付）；
外加上一轮已交付、本轮沿用的一对删除接口（§10）。

## 1. 一份实现、两种单据

收/付款单是**同一张表**的两种叫法：版式、借贷合计、人民币大写、校验、xlsx 渲染全都一样，
差别只有三条 —— 用词、钱走哪一侧、勾的是哪张表。所以它们共用一份实现，用 `kind: "payment" | "receipt"`
区分（`SLIP_KIND_LABELS`）：

| | 付款单 `payment` | 收款单 `receipt` |
| --- | --- | --- |
| 标题 / sheet 名 | 付 款 单 | 收 款 单 |
| 对方单位 | 收款单位（供应商） | 付款单位（客户） |
| 日期 / 方式 | 付款日期 / 付款方式 | 收款日期 / 收款方式 |
| 大写与备注抬头 | 付款金额（大写）/ 付款备注 | 收款金额（大写）/ 收款备注 |
| 签字栏最后一格 | 领款人 | 交款人 |
| 预填勾选的是 | **应付条目**（`payable_entry_ids`） | **应收来源**（`receivable_source_ids`） |
| 预填的借贷形状 | 借 业务科目 / 贷 银行存款 | 贷 业务科目 / 借 银行存款 |
| 单号前缀 / 文件名 | `FK-` / 迪礼付款单 | `SK-` / 迪礼收款单 |

写成两份的代价不是多敲一遍字，而是「付款单修好的一个大写金额 bug，收款单上还在」。

## 2. 付款单：模板逐格对照

样张（`付款单` 截图）里的每一格都在下面有出处。**加粗**的是财务可以改的。

| 模板格子 | 来源 | 可编辑 |
| --- | --- | --- |
| 标题「付 款 单」 | 固定 | — |
| 单据编号 | `FK-<年月>-<序号>`，序号 = **该供应商本月第几笔结算** | **✅** |
| 付款日期 | 打开当天（北京时间） | **✅** |
| 付款方式 | 默认「银行转账」 | **✅** |
| 收款单位 | 所选应付条目的供应商 | **✅** |
| 开户银行 / 银行账号 | 该条应付**确认时实际记账的那条流水的银行**；多条指向不同账户时**留空** | **✅** |
| 附单据 N 张 | 本次付款覆盖的应付条数（一条应付 = 一张来源单） | **✅** |
| 摘要 / 总账科目 / 明细科目 / 借方 / 贷方 / 备注 | 一行一条应付（金额**全额**）+ 末尾一行「银行存款 = 合计」 | **✅ 可增删行** |
| 合  计 + √借贷平衡 | 按「分」（BigInt）精确求和 | — |
| 付款金额（大写） | `amountInWords(借方合计)` | —（后端算，见 §6） |
| 小写金额（样张在备注列下方） | 借方合计（Excel 数值类型） | — |
| 付款备注 | 空 | **✅** |
| 制单人 | 当前登录用户 | 只读 |
| 审核 / 出纳 / 部门审批 / 财务负责人 / 领款人 | 空（手签） | — |
| 表尾落款 | `makerStamp(user)`：制表人 + 制表时间（北京时间） | — |

## 3. 收款单：镜像

财务没有给收款单的样张，所以按「同理」做成**逐格镜像**（版式一模一样，只是 §1 那张表里的用词与
借贷方向反过来）：

- 一行一条应收 → **贷** 该条确认时实际用的科目（`主营业务收入` 等，查不到时退候选链）；
- 末尾一行 → **借** 银行存款 = 合计，明细科目带确认时入账的那张卡；
- 单元格、合计、大写、备注、签字栏的位置与付款单**逐格相同** —— 测试两边各跑一遍（`finance-slip.test.cjs`）。

财务要拆收入与税、要扣手续费（把贷方改小、加一行借「财务费用」）都靠「自己填加行」，
与付款单拆进项税是同一条路。

## 4. 四条路由，以及一个**前缀**陷阱

| 方法 | 路径 | 干什么 |
| --- | --- | --- |
| POST | `/finance/payment-slips/draft` | 按勾选的**应付条目**预填付款单（不写任何数据） |
| POST | `/finance/payment-slips.xlsx` | 把界面上编辑好的付款单渲染成 xlsx |
| POST | `/finance/receipt-slips/draft` | 按勾选的**应收来源**预填收款单 |
| POST | `/finance/receipt-slips.xlsx` | 把界面上编辑好的收款单渲染成 xlsx |

**为什么不合并成一条**：预填要读库（对方单位 / 银行 / 科目 / 单号），导出只认界面提交的内容。
合成一条就会出现「导出的到底是我改过的，还是系统又算了一遍的」这种说不清的情况。

**前缀陷阱（本轮踩到并修掉的真实缺陷）**：预填走 `apiPost`，而 `api-client` 会自己补 `/api/v1`
（`api-client.ts:32`），所以 `financeSlipDraftPath` **不能**带前缀；导出走 `downloadPost`
（**裸 fetch**），必须自带 `/api/v1`。上一轮付款单导出写成了 `/finance/payment-slips.xlsx`，
在生产上会打到 Web 服务、拿回 404 的 HTML —— 用户看到「导出失败」，而请求根本没到后端。
两个 helper 现在各自带注释说明这件事，`finance-slip.test.mjs` 逐字断言这两条路径。

## 5. 预填口径（三条，两种单据共用）

1. **一行一条，金额全额，不自动拆税**。系统里的采购单价是含税价，
   `不含税 = 含税 ÷ (1+税率)` 在取得普票（不抵扣）、优惠税率或部分抵扣时会被自动填错，
   而这种错误在单子看不出来；收款侧同理（收入与税怎么拆是财务的判断）。
   「要拆」正是财务说的「我可以自己填加行」——拆完两边同时变大，仍然平。
   这与记账凭证模板（`voucher-template.ts`）是同一条既定口径。
2. **科目优先用「确认时实际记账的那个」**（`cash_flow_entries.subject`），查不到时退回
   `paymentSubjectNames(sourceType)` / `RECEIVABLE_CONFIRM_SUBJECT_NAMES` 的候选链首位。
   单子上的「总账科目」不能猜 —— 财务改过科目的话，猜出来的那条与账上的不一致。
3. **跨对方单位 / 跨币种直接 422**，不静默取第一条：单子只有一个「收款单位 / 付款单位」、
   一个大写金额。错误码按种类分开（`PAYMENT_SLIP_MULTI_COUNTERPARTY` /
   `RECEIPT_SLIP_MULTI_COUNTERPARTY`），文案给下一步（「请按供应商/客户分批导出」）。

## 6. 校验：借贷不平不许出单，且一次把问题说完

- 前端 `financeSlipBlockers(kind, …)`（`apps/web/lib/finance-slip.ts`）与后端 `validateFinanceSlip`
  是**同一套规则的两份实现**，逐条对应：单据编号 / 对方单位 / 日期 / 附单据张数 / 至少一行 /
  每行（摘要或总账科目）/ 每行只能填一侧 / 金额是大于零的最多 4 位小数 / 借贷合计相等。
  错误码是**与种类无关**的 `SLIP_*`，文案里才出现「付款单 / 收款单」与对方的称谓。
- 前端**把原因写在界面上**（不是只禁用按钮）：按钮禁用就点不动，原因不能只在点击后出现。
- 后端一次返回**全部**问题（含行号），`details` 里带 `code` 与 `row`；校验不过一个字节都不下发、不记审计。
- 「摘要」与「总账科目」**有一列就算写过**（样张第 2 行就是把科目名写在摘要里）；
  **空白行**（点了「新增行」没填）在提交时整行丢掉，不变成「第 N 行请填金额」挡住导出。
- 借贷合计用 BigInt「分」：浮点求和的 `0.1 + 0.2 = 0.30000000000000004` 会让财务看到
  「明明平了却不让导出」。
- **金额转中文大写只有后端一份实现**（导出的文件是权威）：`149.50 → 壹佰肆拾玖元伍角整`、
  `100 → 壹佰元整`、`0.05 → 伍分`；4 位小数按分**四舍五入**（不是截断）。
  前端编辑器刻意**不预览**它 —— 与其在两个 workspace 各写一套「金额转中文」，不如不显示。
- **空单元格不写空串**（ExcelJS 写 `""` 会落成文本单元格）；金额一律落 Excel 数值类型
  （`numFmt = 0.####`）。**银行账号是例外**：它本来就是文本（写成数值会丢前导零），
  所以「不允许文本型数字」的守卫只扫分录表的金额列。

## 7. 「对账 + 确认」合并成一个视图（两个动作仍在）

| | 合并前 | 合并后 |
| --- | --- | --- |
| 应收 | 成品出库条目 / 应收对账 / 确认应收 | 成品出库条目 / **应收对账与确认** |
| 应付 | 原料入库条目 / 外加工签收 / 应付对账 / 确认应付 | 原料入库条目 / 外加工签收 / **应付对账与确认** |

合并后的那个页签里，三张表**按业务顺序**排开（以应付为例）：

1. **待创建对账**（逐条草稿 + 行内「创建对账」）→ 这是动作一；
2. **已创建对账单**（对平/差异、一键确认、删除）；
3. **确认应付**（台账 + 勾选 + 批量确认 + 导出付款单）→ 这是动作二。

**故意不把两步合成一步**：对账对不清的金额不该被确认成生效负债（`confirmPayables` 至今拒绝
`difference` 状态）。合并的只是「不用再切页签」。

布局改动顺带补了两件事：每张表外面包一层带 testid 的容器
（`payable-reconciliations` / `receivable-reconciliations`，与 `*-pending-entries` 对称），
否则合并之后「数一页有几行」在测试里必然漂移；四步流转看板里 ②③④ 的链接现在指向同一个页签
（它们仍然各自说明「卡在哪一步」）。

## 8. 老地址与老 tab 的兼容

合并意味着 `?tab=confirmed` 不再是页签，但它**已经在别人的收藏夹里**
（还有 `FINANCE_LEGACY_REDIRECTS` 里的三个老地址）。处理方式：

- `RECEIVABLE_TAB_ALIASES` / `PAYABLE_TAB_ALIASES` 把 `confirmed` 折到 `reconciliations`；
- 解析集中在 `resolveFinanceTab(tabs, aliases, tab)` 一处，**页面与组件都用它** ——
  组件里的 `tab` 既可能来自服务端解析过的 searchParams、也可能是调用方直接传进来的（测试就是），
  两条路必须得出同一个页签；不认别名的那条路会**默默落到第一个页签**（看起来像「功能没了」）；
- 入参类型是 `PayableTabParam = PayableTabKey | "confirmed"`：把旧值写进类型，
  调用方就不必各自折算一次（那种写法迟早漏一处）。

## 9. 集中收款 / 集中付款

财务说的「勾选多选条目，进行收束集中收款付款」= 已经存在的**勾选批量确认**
（`POST /finance/{receivable-sources,supplier-payable-entries}/batch-confirm`）：勾选若干条 →
整批只问一次「钱进哪个账户、归哪个会计科目」→ 后端仍然**每条写一条流水**（每条都有自己的来源编号，
合并成一条就再也追不回是哪张出库单/入库单的钱）。本轮把它与单据串起来：

- 勾选 → **批量确认**（钱动一次、账逐条记）；
- 勾选 → **导出付款单 / 收款单**（一张单、一行一条），财务可以在弹窗里改金额、增删行、写备注。

两者互不依赖：可以先出单再付款，也可以付完再补单（单子不落库，见下）。
行内也给单个条目的出单入口（草稿 = 准备收付、已确认 = 钱已经动过）。

**为什么单子不落库**：它是银行打印件，不是系统单据。代价与好处都写在这里：

- **单号只是建议值**：没有表可以顺延，所以不存在权威序列。与其编一个看起来权威、实际会重号的序列，
  不如把编号权交回财务（字段可改）。序号规则「该对方单位本月第几笔结算」=
  本月已确认条数 − 本次条数 + 1。
- **不产生任何账务影响**：导出一次既不确认应收/应付、也不写收支流水，审计里只留一条
  `payment_slip.export` / `receipt_slip.export`（单号 / 对方单位 / 金额 / 行数）。

## 10. 其他应付 / 应付对账单的逻辑删除（上一轮，本轮沿用）

| 情形 | 结果 |
| --- | --- |
| 其他应付 · 草稿 | ✅ 删 |
| 其他应付 · **已确认（未付款）** | ✅ 删，**同一事务里回冲那笔支出**（钱回到账上） |
| 其他应付 · 已被付款核销（部分付款/已付清） | ❌ `SUPPLIER_PAYABLE_HAS_ALLOCATIONS` |
| 原料入库 / 外加工签收形成的应付 | ❌ `SUPPLIER_PAYABLE_NOT_OTHER`（到货事实的账，走冲销） |
| 已被对账单覆盖 | ❌ `SUPPLIER_PAYABLE_IN_RECONCILIATION`（下一步是删那张对账单） |
| 应付对账单 · 未用于确认应付 | ✅ 删（`DELETE /finance/supplier-payable-reconciliations/:id`） |
| 应付对账单 · 已用于确认应付并记账 | ❌ 拒删并点名那笔支出流水 |

- **删除 ≠ 冲销**：行软删除、**不改状态**，审计记 `status_when_deleted` 与回冲掉的流水号。
- **回冲与软删除同生共死**（`CashFlowService.reverseSourceFlowInTransaction` 放进调用方事务）：
  软删除提交了、回冲却失败的话，条目已经从列表消失、用户再也点不到它补救。
- 删掉对账单之后，被它覆盖的草稿应付重新回到「待创建对账」，也就重新可删。

## 12. 遗留

- **单子不落库**：关掉弹窗就得重来，也没有「谁开过哪张单」的台账。要做成系统单据需要新表 +
  迁移 + 编号序列。单子上也没有税率列 —— 进项税/销项税要财务自己算一个数填进去。
- **对账单删除仍然只放给「没确认过」的**（§10 的理由：对账范围内哪几条应付是它确认的没有单独记录）。
- **合并后页面变长**：三张表串在一个页签里，表多时要滚动。若财务反馈「找不着确认台账」，
  下一步是给页签内加锚点/折叠（而不是再拆回两个页签）。
- 收款单的样张是**按付款单镜像推的**（财务只给了付款单）。收到她的收款单样张后要逐格核对一遍。
