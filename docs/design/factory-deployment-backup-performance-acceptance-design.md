# G4 厂内部署、备份恢复与并发性能验收设计

## 1. 目标与边界

G4 将当前可构建的 ERP 交付为可在迪礼厂内局域网运行、可恢复、可测量的部署基线。数据、附件、数据库和备份均留在厂内。G4 不包含历史数据迁移、业务规则新增或云端托管。

## 2. 部署拓扑

首版采用一台厂内服务器运行 Docker Compose：PostgreSQL、NestJS API 和 Next.js Web 三个服务。Web 对厂内浏览器提供入口，API 只在 Compose 网络和厂内端口暴露，PostgreSQL 不对局域网暴露。生产配置通过环境文件注入，密钥不进入 Git。

必须提供：

- 健康检查：API `/api/v1/health` 必须同时确认 API 与数据库可用。
- 迁移入口：启动前显式执行 `prisma migrate deploy`，失败禁止标记部署成功。
- 持久化卷：数据库、附件和备份分别使用明确目录或卷。
- 重启策略、日志查看、停止和升级回滚命令。

## 3. 备份与恢复

每日执行 PostgreSQL custom-format dump，备份文件写入独立厂内存储；同时生成 SHA-256 校验文件。恢复必须要求操作者明确指定目标数据库和备份文件，先校验哈希，再执行 `pg_restore`，避免误恢复到生产库。恢复后依次执行迁移状态、健康检查、管理员登录和关键只读接口抽检，并记录操作人、时间、文件哈希和结果。

## 4. 性能验收

以 2-3 名并发操作员为首版目标。提供可重复的 HTTP 压测脚本，至少覆盖健康检查、订单工作台和报表查询。记录请求总数、并发数、成功率、P50/P95/P99 和错误样本。验收目标：常规列表/详情 P95 <= 1 秒，复杂报表 P95 <= 3 秒，错误率为 0；真实数据量和厂内硬件不足时标记阻断或风险，不伪造通过。

## 5. 验收输出

每次部署验收生成一份 Markdown 记录，包含版本、环境、命令、结果、备份恢复证据和性能原始摘要。未具备 Docker、PostgreSQL 或 API/Web 运行地址时，测试脚本必须返回明确的环境阻断码。

## 6. 安全与运维约束

- 生产密钥、数据库密码和初始管理员密码只从环境变量或厂内密钥文件读取。
- PostgreSQL 不直接暴露到厂内网络；API/Web 只暴露必要端口。
- 不执行破坏性恢复，除非操作者明确指定目标数据库并确认。
- 部署、迁移、备份、恢复和性能测试均保留命令与操作者记录。
