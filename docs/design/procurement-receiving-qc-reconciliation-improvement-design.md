# 采购收货、来料质检与可逆入库改进设计

## Problem Statement

当前生产基础资料把工序和加工地点全部平铺在生产页面，信息密度过高，基础资料与生产业务混在一起，员工难以定位和维护。

工序员工日报保存时偶尔出现“编号或代码已被占用，请更换后重试”。该提示过于笼统，无法说明冲突来自哪一种业务编号、哪一条记录或哪一个字段，导致操作员无法判断应修改什么。

采购单的到货、应付、来料质检和原料入库被拆成多个不可方便回退的操作。员工无法在采购单内连续维护第一批、第二批等分批到货，也无法清楚看到每批到货对应的应付、质检和入库状态。质检也没有在到货后稳定形成待检任务，原料入库无法以采购单批次为单位进行可逆流转。

## Solution

本期将采购单作为原料收货流程的主入口。采购单详情内提供可重复添加的收货批次工作区，每个批次维护到货数量、到货日期、应付来源和后续质检/入库状态。界面可以将批次呈现为“第一批、第二批……”的分组或列，但底层使用独立批次记录，不创建动态数据库列。

每次确认到货后，系统自动产生对应的来料质检任务；同一采购单允许多批到货、多批来料质检和多批原料入库，每批都显示采购单号和批次序号。质检完成后，操作员在可逆状态机中选择入库；入库过账形成库存事实，回退通过受控冲销或退回待入库状态完成，不静默覆盖历史事实。

工序池和加工地点改为生产模块的二级基础资料页面，生产主页仅保留入口和启用数量摘要。日报冲突错误改为返回明确的业务对象、字段和冲突值，便于纠错。

## User Stories

1. 作为生产负责人，我希望生产主页只展示工序池入口和摘要，以便首屏聚焦生产单和工序进度。
2. 作为物控员，我希望进入二级工序池页面查看全部工序，以便集中维护生产基础资料。
3. 作为管理员，我希望在工序池中新增、编辑、启用、停用工序，以便统一控制生产单可选项。
4. 作为管理员，我希望停用工序后历史生产单仍显示名称快照，以便历史记录可解释。
5. 作为生产负责人，我希望加工地点有独立地点池，以便管理厂内车间和外加工点。
6. 作为管理员，我希望在加工地点池中新增、编辑、启用、停用地点，以便避免在生产主页堆叠基础资料表单。
7. 作为生产负责人，我希望停用加工地点后不能被新生产单选择，以便防止错误派工。
8. 作为操作员，我希望日报保存失败时看到具体冲突对象和字段，以便知道是员工、工序、单据还是幂等编号冲突。
9. 作为操作员，我希望冲突错误显示可读名称、编号和当前占用记录，以便快速处理重复数据。
10. 作为系统维护者，我希望不同唯一约束返回不同错误码，以便前端展示准确的修复提示。
11. 作为采购员，我希望在采购单详情直接维护到货批次，以便不在多个页面之间往返。
12. 作为采购员，我希望为采购单添加第一批到货，以便记录实际到货数量和日期。
13. 作为采购员，我希望继续添加第二批、第三批到货，以便支持供应商分批交货。
14. 作为采购员，我希望每批到货显示采购单号和批次序号，以便装卸、仓库和财务人员明确来源。
15. 作为采购员，我希望批次数量不能超过该采购明细尚未到货的可用数量，除非明确记录超收原因，以便保护采购事实。
16. 作为采购员，我希望可以编辑或删除尚未确认的到货批次，以便修正录入错误。
17. 作为采购员，我希望已经产生下游质检或库存事实的批次不能被静默修改，以便保留业务历史。
18. 作为财务人员，我希望每批到货产生对应的应付来源，以便按实际收货确认应付款。
19. 作为财务人员，我希望应付来源带有采购单号、采购明细、批次序号、数量、单价、税率、金额和币种，以便核对供应商账款。
20. 作为财务人员，我希望应付来源可以回退或作废，但不能删除原始到货事实，以便账务可追溯。
21. 作为仓库人员，我希望每次确认到货后自动出现来料质检任务，以便不漏检。
22. 作为质检员，我希望来料质检列表能显示采购单号和第几批，以便知道检验对象。
23. 作为质检员，我希望同一采购单可以有多批独立来料质检，以便按批次处理不同到货。
24. 作为质检员，我希望每批质检记录显示送检数量、合格数量、条件接收数量和不合格数量，以便完整分流。
25. 作为质检员，我希望质检数量不能超过该到货批次数量，以便防止重复检验。
26. 作为质检员，我希望质检记录支持编辑、逻辑删除和状态回退，并保留修改原因，以便纠正录入错误。
27. 作为仓库人员，我希望质检完成后可以选择是否入库，以便质量和仓库职责清晰分离。
28. 作为仓库人员，我希望只有质检合格或允许条件接收的数量可以进入可用原料库存，以便不合格物料不会进入正常库存。
29. 作为仓库人员，我希望同一采购单可以有多批原料入库，以便分批上架和收货。
30. 作为仓库人员，我希望原料入库记录显示采购单号、批次序号、质检批次和入库状态，以便追溯库存来源。
31. 作为仓库人员，我希望入库在过账前可以编辑或删除，以便纠正数量和仓位信息。
32. 作为仓库人员，我希望已过账入库可以通过冲销回退，而不是直接修改库存余额，以便库存事实一致。
33. 作为财务人员，我希望入库或质检回退时相关应付来源进入待复核状态，以便财务不会继续按失效数量付款。
34. 作为采购负责人，我希望采购单详情看到每批到货、质检、入库和应付状态，以便快速判断供应链进度。
35. 作为采购负责人，我希望能按采购单号、供应商、批次序号和状态筛选记录，以便处理异常批次。
36. 作为审计人员，我希望批次新增、修改、确认、质检、入库、回退和冲销都记录操作人、时间、原因和前后值，以便还原全过程。
37. 作为系统管理员，我希望重复执行数据初始化不会重复生成工序、地点或批次，以便部署和重试安全。
38. 作为前端使用者，我希望工序池、加工地点、采购批次、质检批次和入库批次均使用现有组件库，以便交互和无障碍行为一致。
39. 作为前端使用者，我希望从采购单进入质检或入库时返回后仍保留原页面筛选和编辑内容，以便连续操作多个批次。
40. 作为模块负责人，我希望批次编号由服务端生成且唯一，以便员工无需手工维护内部 ID。

## Implementation Decisions

- 生产页面只展示工序池、加工地点的入口和统计摘要；全部列表、搜索、新增、编辑、启用/停用放入二级基础资料页面。
- 工序池继续使用工序目录作为唯一来源。生产单只引用启用工序目录，并保存工序名称、单位等历史快照；停用采用逻辑停用，不物理删除。
- 加工地点继续区分厂内车间和外加工点。生产单只能选择启用地点；已有生产单保留地点快照。
- 工序员工日报的冲突处理在服务端统一翻译数据库唯一约束。至少区分日报幂等键、员工编号、工序编码、生产单号和其他业务单号；响应必须包含稳定错误码、对象类型、字段、冲突值和可读修复建议。不得继续统一返回“编号或代码已被占用”。
- 采购单新增“收货批次”概念。批次使用服务端生成的批次编号和从 1 开始的批次序号，唯一归属于一个采购单明细；序号只增不重用，逻辑删除后仍保留历史。
- 每个收货批次至少包含采购单 ID、采购单号快照、采购明细 ID、供应商快照、批次序号、到货数量、到货日期、单位、状态、备注和审计字段。批次数量使用 Decimal。
- UI 可以把批次呈现为横向“第一批到货/第一批应付/第二批……”列，也可以采用批次分组卡片；数据库不得为每一批新增列，新增批次通过重复记录实现。
- 收货批次状态采用可逆状态机：`draft -> confirmed -> cancelled`。草稿可编辑/删除；确认后自动创建来料质检任务。确认后的数量不直接覆盖，纠错通过取消并新建修正批次或受控调整记录完成。
- 采购明细的累计确认到货量由有效收货批次汇总。超出采购数量时默认拒绝；若业务允许超收，必须填写原因并产生风险记录，不能由前端绕过。
- 每个确认收货批次必须幂等地产生来料质检任务。质检任务与收货批次一对一，质检记录可在同一批次上多次修订，但不能重复生成第二个未删除任务。
- 来料质检记录包含采购单号快照、采购批次序号、收货批次 ID、送检数量、合格数量、条件接收数量、不合格数量、检验状态、检验日期、备注和审计字段。合格、条件接收、不合格数量之和不得超过送检数量。
- 来料质检状态采用 `pending -> inspecting -> completed`，并支持 `completed -> pending` 的受控回退和 `completed -> cancelled` 的逻辑取消。回退必须填写原因，并在已有入库或应付事实时先展示影响预览。
- 质检完成后，仓库可以针对合格数量和允许进入可用库存的条件接收数量创建一个或多个原料入库批次；不合格数量只能进入不良品分流，不得增加可用原料库存。
- 原料入库批次包含采购单号、采购批次序号、质检记录 ID、入库数量、库存分类、单位、状态和审计字段。一个收货批次允许多次入库，但有效入库累计数量不得超过质检允许入库数量。
- 原料入库状态采用 `draft -> posted -> reversed`。草稿可编辑/删除；过账在事务内重读质检余额和当前库存，创建库存事实；冲销创建反向库存事实并将原入库标记为 `reversed`，不物理删除库存事实。
- 每个收货批次确认后生成应付来源草稿或待财务确认来源，带采购单、采购明细、收货批次、数量、单价、税率、金额、币种和来源快照。财务确认、作废和回退必须与收货/质检状态联动并保留审计。
- 应付金额按批次实际确认数量和采购明细单价计算；财务允许新增调整记录，但不直接改写采购单原始数量或价格快照。
- 采购单详情是主工作区，提供批次列表、批次新增/编辑、质检状态、入库状态、应付状态及影响预览入口。采购、质检和入库独立页面仍保留查询能力。
- 所有跨模块回退先返回影响预览：受影响的质检、入库、库存事实、应付来源、可用余额和待复核风险；操作员明确确认后才执行事务。
- 新增收货批次、质检批次、入库批次均使用现有 Dialog/Sheet、DataTable、Button、Select、Input 等组件；不使用原生 `alert`、`confirm`、`prompt`、原生 select 或动态数据库列。
- 批次编号、质检编号、入库编号和应付编号由服务端生成并设置唯一约束；重复请求使用幂等键返回原结果，不创建重复事实。
- 既有采购收货、来料质检、原料入库和应付接口尽量向后兼容；新增接口优先补充批次关系和过滤参数，旧记录通过迁移建立可解释的历史批次标识。
- 生产主页二级页面的新增类目流程必须支持返回调用页面、保留筛选/表单内容、刷新选项并自动选中刚创建的工序或加工地点。

### Recommended state relationships

```text
采购单明细
  └─ 收货批次 draft -> confirmed -> cancelled
       ├─ 来料质检 pending -> inspecting -> completed
       │                          └─ 回退 pending / cancelled
       ├─ 原料入库 draft -> posted -> reversed
       └─ 应付来源 pending_finance -> confirmed -> voided / review
```

状态之间不是简单级联覆盖：回退必须检查下游事实，库存通过反向事实冲销，应付通过作废/调整记录回退，审计记录永久保留。

## Testing Decisions

- 测试只验证外部业务行为和跨模块结果，不绑定 Prisma 查询实现细节。
- 生产基础资料测试覆盖：二级页面入口、工序/地点 CRUD、启用/停用、新生产单过滤、历史快照和重复初始化幂等。
- 日报错误测试覆盖：重复幂等键、重复业务编号、冲突响应的错误码/字段/对象、前端可读提示，以及成功保存不受无关编号影响。
- 收货批次服务测试覆盖：单批确认、同一明细多批、数量累计、超收拒绝/带原因风险、草稿编辑删除、确认后不可静默修改和重复请求幂等。
- 质检服务测试覆盖：确认到货自动生成待检任务、多批质检、数量守恒、重复触发不重复建任务、质检回退影响检查和不合格数量不入可用库存。
- 原料入库测试覆盖：质检允许数量上限、多次入库累计、草稿编辑删除、过账事务库存事实、重复过账幂等、冲销反向事实和并发余额校验。
- 应付联动测试覆盖：每批到货生成唯一应付来源、数量/金额快照、质检或入库回退后的待复核/作废状态，以及财务调整不改写原始采购事实。
- API 测试沿用现有 Nest 服务集成测试和 HTTP 合约测试；需要数据库的测试使用 `TEST_DATABASE_URL`，没有测试数据库时必须明确标记为未执行。
- Web 测试使用现有 Playwright 流程，检查采购单详情中批次新增、批次序号、质检入口、入库回退、二级基础资料页面和无原生控件回归。
- 页面验收检查桌面端采购单批次表格可读、批次状态和错误提示不重叠；移动端允许纵向布局但不得隐藏关键状态和回退操作。

## Out of Scope

- 本期不实现供应商自动对账、电子发票、付款审批流或会计总账。
- 本期不把采购批次设计成可由用户任意改名或删除的动态数据库字段。
- 本期不改变订单、BOM、生产单的既有业务含义，不把销售成品加入原料收货链路。
- 本期不自动排产、不改变工序日报和员工日报的计薪规则。
- 本期不实现批次级库存成本核算、先进先出或单位换算；数量必须在同一单位下核算。
- 本期不允许物理删除采购、质检、入库、应付和库存事实。
- 本期不扩展外加工实际生产过程的日报和员工计薪。

## Further Notes

- “第一批到货、第一批应付、第二批……”是用户界面称谓，正式领域对象统一称“收货批次、来料质检批次、原料入库批次、应付来源”。
- 每一批都必须同时展示采购单号和批次序号；不能只显示内部 UUID。
- 需要在实施前补充现有旧数据迁移策略：没有明确收货批次的历史到货记录，统一归为“历史批次 1”或标记为“历史未分批”，由业务负责人确认后执行。
- 需要在实施前确认条件接收物料是否立即进入可用原料库存，还是必须单独进入待处理库存；本设计默认只有明确允许入库的数量才能进入可用库存。
- 需要在实施前确认“质检完成”是否允许零合格数量；本设计允许完成但不会产生可用原料入库数量。
- 推荐测试切入点为批次服务层：收货批次一次校验数量和状态，质检与入库只消费其稳定批次 ID，减少跨模块重复判断。
