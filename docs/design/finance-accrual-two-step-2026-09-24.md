# 权责发生制两步：确认 = 挂账，收付 = 销账（方案，待财务点头后再动代码）

- 日期：2026-09-24
- 状态：**应收侧与应付侧都已实施**（确认 = 挂账、收付 = 销账；历史数据保持原样）。
- 相关：`docs/design/finance-three-statements-2026-09-24.md` §2 事实②、§8.4；`docs/log/2026-09-24.md`

## 零、已实施的部分（2026-09-24，应收链）

- `VoucherService.createAccrual()`（新）：挂账凭证 = 借 `应收账款` / 贷 收入类科目（默认主营业务收入，
  确认弹窗里选的科目生效），**没有资金分录**，落草稿，幂等靠唯一键 `(source_type, source_id)`；
  科目缺失显式 422（`ACCOUNTING_SUBJECT_NOT_FOUND`），0 元往来返回 null 不挂空账。
- 确认应收的**三个入口**（逐条 / 勾选批量 / 按订单 / 按对账单）全部改为挂账：不再写 `cash_flow_entries`，
  响应里 `cash_flow_entry_ids` 为空、新增 `accrual_voucher_id(s)`、`bank_missing` 恒为 false。
- **销账**：收款过账那条现金分录的对方科目改成「有条件」的 ——
  `VoucherService.accruedSourceIds()` 判定这批核销的应收**是否都挂过账**：
  都挂过 → 贷 `应收账款`；有一条没挂过（历史数据 / 当年「确认即记账」的）→ 仍按老口径贷收入。
  **历史不动**：老数据没有挂账凭证，收款照旧贷收入，不会把「应收账款」记成负数。
- 界面：确认应收的成功提示改成「已确认并挂账（借应收账款 / 贷收入）；收到钱后在「登记收款」里记现金」，
  不再说「金额已记入所选银行账户」（钱还没到，这句话是错的）。
- 测试：`voucher-service.test.cjs` +4（挂账分录方向 / 幂等 / 科目缺失 / `accruedSourceIds`）、
  `customer-payment-service.test.cjs` +1（挂过账贷应收、没挂过账与混合都按老口径）、
  应收与对账两个套件里的确认用例全部改写成挂账断言（并把 `cashFlowCalls` 留成反向护栏：
  哪天有人把 `recordConfirmation` 加回确认路径，这些用例会立刻红）。

**应付侧同日按同一方案对称落地**：`SupplierPayableService.confirm` / `batchConfirm` 与
`SupplierPayableReconciliationService.confirmPayables` 改为挂账（借 成本/存货类科目 / 贷 `应付账款`，
科目候选链按来源类型选定），`SupplierPaymentService.post` 的销账科目同理由 `accruedSourceIds()` 决定。
两条链现在同一口径，界面文案也一并改（不再说「金额已记入/转出所选银行账户」）。

## 一、现在是什么样（事实，不是猜测）

确认应收（`receivable.service.ts:149 confirm`）与确认应付（`supplier-payable.service.ts` 同构）**一步做两件事**：

1. 把 `receivable_sources.status` 从 `draft` 改成 `confirmed`（这是**权责发生制**的那一步：应收账款成立）；
2. 调 `cashFlow.recordConfirmation({ sourceType: "receivable_source", direction: "income", bankId, subjectNames: RECEIVABLE_CONFIRM_SUBJECT_NAMES })`
   —— 写一条 `cash_flow_entries`，也就是**记了一笔「钱进了银行」**（这是**收付实现制**的那一步）。

写出来的流水还要财务到「凭证管理」点「生成凭证」，才变成凭证（`vouchers.source_type = cash_flow_entry`，
唯一键 `(source_type, source_id)` 保证一条流水只生成一张）。**三大报表取的是凭证**，所以在点「生成凭证」之前，
这笔应收在报表里根本不存在。

两个后果：

- **确认那一刻钱还没到，账上却记了收款。** 财务的真实动作是：先跟客户确认这笔应收，真正收到钱时再登记收款
  （`customer-payments` + 核销 `receivable_allocations`）。现在等于把「应收成立」和「钱收到」压成了一个动作，
  于是「应收账款」这个科目在凭证上永远不会出现 —— 报表里资产负债表只有货币资金那一行会有数。
- **「确认应收」弹窗必须问银行账户**（`options.bank_id`），而那个时点她根本不知道钱会进哪个账户
  （代码注释里已经写了「没有银行账户时流水照写，响应带 `bank_missing` 让界面提示」——这是被现实逼出来的补丁）。

用户当年的原话是「一旦确认应收，金额就要进入对应的账户」，所以**这不是 bug，是她要过的口径**。
改成两步会改变她每天的操作，因此必须先让她明确点头。

## 二、改成两步之后的样子（口径）

| | 触发动作 | 分录 | 现金流动 | 报表影响 |
|---|---|---|---|---|
| **挂账** | 确认应收 / 确认应付 | 借 `应收账款`／贷 `主营业务收入`（+ 销项税，若有）<br>借 `库存商品/主营业务成本`／贷 `应付账款` | **不产生**（钱没动） | 应收账款 / 应付账款 / 收入 / 成本各行有数；现金流量表**不动** |
| **销账** | 登记收款 / 登记付款 + 核销 | 借 `银行存款`／贷 `应收账款`<br>借 `应付账款`／贷 `银行存款` | 产生（钱动了） | 现金流量表「销售商品收到的现金」等行有数；银行存款减少应收 |

关键点：**现金流量表仍然只认销账那一步**（钱真的动了），这与它现在的口径完全一致 ——
变的只是「确认」这一步不再伪造现金流动。挂账凭证是**非现金凭证**，现金流量表本来就会跳过它
（`nonCashVouchers` 那条口径已经在内核里）。

## 三、要改的地方（文件级）

### 3.1 数据层

- **不新增表**：`receivable_sources.status`（draft → confirmed → paid/closed）已经是「挂账」这个事实的载体；
  应付侧 `supplier_payables.status` 同理。
- **新增一个凭证来源类型**：`Voucher.sourceType = "receivable_source" | "supplier_payable"`，
  `sourceId` = 该条应收/应付的 id。理由：一条应收只允许挂一张账，`(source_type, source_id)` 唯一键
  天然给出这个幂等根（与现在的 `cash_flow_entry` 同一套机制，不需要新的约束）。
  `vouchers.source_id` 刚刚因为手工凭证改成可空（迁移 `20260924100000`），这里**不需要新迁移**；
  需要的是 `SOURCE_*` 常量加两个值 + 生成/红冲路径认这两种来源。
- **历史数据不动**：已经确认过的应收（有 `cash_flow_entry` 的那些）保持原样 —— 那些钱很可能**真的到了**
  （她当时就是这么用的），事后按新口径重新挂账会把同一笔钱记两遍。方案里给一条只读的核对清单
  （`GET /finance/reports/accrual-cutover`：列出「已确认且已有流水」的应收/应付），让她自己看哪些要保留。
  这是「保留历史事实」这条宪法的直接推论：我们不知道那些钱到没到，**不猜、不改**。

### 3.2 服务层

- `receivable.service.ts` / `supplier-payable.service.ts` 的 `confirm` / `batchConfirm` / `confirmByReconciliation`：
  - **去掉** `cashFlow.recordConfirmation(...)`；
  - **改成** `voucherService.createAccrual({ sourceType, sourceId, voucherDate, currency, amount, counterparty, subjectKey })`；
  - 弹窗参数 `bank_id` / `subject_id` 从「确认」这条路径上移除（挂账不涉及银行）；`payment_nature` 同理。
  - **落草稿还是直接过账**：建议**草稿**（与手工凭证一致：财务核对后再过账）——
    确认应收是业务动作，凭证是账务动作，两者分开也顺带让「挂账凭证要不要过账」成为她的日常判断。
    代价是多一步点击；若她要求省事，可以加一个「确认并过账」的复选。
- `cash-flow.recordConfirmation` 保留：它就是**销账**那一步要用的东西（收款 / 付款登记时调用），
  只是不再由「确认」调用。
- 新增一条**只读**校验接口 `accrual-preview`（给确认弹窗用）：告诉她「这次挂账会写什么分录」，
  免得她点完才发现科目不是她想的那样。

### 3.3 报表侧

- **三大报表不用改**：取数只认凭证，挂账凭证与手工凭证、流水凭证在它眼里是同一件事。
- 现金流量表**不需要改**：非现金凭证已经被 `nonCashVouchers` 排除（现有口径），
  挂账凭证的资金分录一行为 0，自然不进表。
- 唯一要补的是**提示**：如果挂着账却还没登记收款，现金流量表本期可能「什么经营活动都没发生」——
  这本来是对的，但要在表尾说明「本期只有挂账、没有实际收付」，否则财务会以为报表坏了
  （表尾已有「未生成凭证的流水」这类提示的位置，加一条同型的即可）。

### 3.4 界面

- 「确认应收 / 确认应付」弹窗：去掉银行账户与会计科目，改成「确认后系统会挂账：借应收账款 / 贷主营业务收入」的预览，
  外加一个「同时登记收款」的入口链接（把两个动作连起来，但不合并）。
- 「收款登记 / 付款登记」弹窗保持现状（那里才是问银行账户的地方）——**这是她已经在用的流程**，
  所以这个改动落到她身上的实际增量是「点了确认之后不用再填银行」。
- 文案必须直说差别：「确认 = 挂账（钱还没到）；收到钱再登记收款」。

## 四、测试怎么钉（改动前先写）

1. **确认不再产生现金流动**：`confirm` 之后 `cash_flow_entries` 计数不变，`receivable_sources.status = confirmed`；
   挂账凭证的借贷是 `应收账款` / `主营业务收入`（不是银行存款）。
2. **幂等**：同一条应收重复确认（另一个入口抢跑）只挂一张账 —— 靠 `(source_type, source_id)` 唯一键，
   并断言抛的是「已确认」而不是数据库唯一约束错。
3. **销账才动现金**：登记收款 + 核销之后才出现 `cash_flow_entry`（方向 income、银行账户是收款登记里选的那个），
   现金流量表「销售商品收到的现金」+ 该金额；挂账那张凭证仍不进表（`nonCashVouchers` 计数 +1）。
4. **应收余额对得上**：`应收账款` 挂账 − 核销 = 台账上的未收金额（拿现有 `allocationBalance` 对一次总数）。
5. **历史不动**：一条「已确认 + 已有流水」的老数据在新代码下**不会**被重新挂账（回归守卫）。
6. **弹窗**：不再发送 `bank_id` / `subject_id`；确认后的成功提示里出现「挂账」两个字（别让她以为钱到了）。
7. **反向**：`reopen`（回退草稿）与 `cancel` 在「已挂账未收款」时的行为 —— 挂账凭证要一并红冲/作废，
   否则应收回到了草稿、凭证却还在。

## 五、要她拍板的三件事（应收侧已按推荐默认值落地，仍可改）

1. **要不要改** —— 已改（应收侧）。她原来的口径是「一旦确认应收，金额就要进入对应的账户」，
   现在改成：确认 = 挂账（钱还没到），收到钱时在「登记收款」里记现金。
   如果她更想保持原样，回退点只有三处（确认路径调回 `recordConfirmation`、销账科目不用 `accruedSourceIds`、
   成功文案改回去），方案与测试都在，随时可退。
2. **挂账凭证落草稿还是直接过账** —— 已按**草稿**落地（与手工凭证、流水生成的凭证一致：财务核对后过账）。
   若要省事可以改成过账，但那样「确认」就会直接改报表。
3. **历史数据** —— 已按**保持原样**落地：老应收没有挂账凭证，收款时按老口径贷收入；
   系统不去猜「那些钱到底到没到」。若她提供清单，可以逐条补挂账（逐条挂账是幂等的，补一次不会重复）。
