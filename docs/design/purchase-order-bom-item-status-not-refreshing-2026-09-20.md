# 采购单「下单状态」不及时/不更新 —— 两个根因与修复（2026-09-20）

用户报告：**采购单里有些物料已经下单了，但新建采购单里「下单状态」这一列没有及时更新**；
又补了一句「但是我刚刚试了一单，又可以了？」—— 说明它**时对时错**，不是恒定失效。

「下单状态」列是用户 2026-09-17 要求的：「已经选中并下单的 BOM 物料，再新建采购单中要显示已下单。
因此要多一个 column」。它的**唯一用途是防止对同一行 BOM 需求重复采购**，所以它一旦显示
「未下单」，后果不是「看着不对」，而是**真的会再下一张单**。

时对时错 ⇒ 至少两个独立机制。两个都找到了，都有先跑红再修绿的用例。

---

## 根因 1（后端·口径错）：BOM 表存过一次，已下单量就整块消失

**先跑红的复现**（`apps/api/test/unit/purchase-order-bom-item-status.test.cjs`）：

```
✖ 回归：BOM 表存过一次之后（明细整体替换 = 行 ID 全换），已下单量仍要看得见
  AssertionError: 已经下过单的物料不许显示成「未下单」——那会让人再下一张，重复采购
  'none' !== 'ordered'
```

机制是一条链：

1. `PUT /boms/:id/items`（界面上的**保存 BOM 表**；采购单页里就摆着「编辑BOM表」入口，
   生产模块也能改）走 `BomsService.replaceItems` = **软删全部旧行 + 整批建新行**
   （`boms.service.ts:97` / `:109`）—— **存一次 BOM，所有行 ID 都换掉**。
2. 采购明细里存的 `bom_item_id` 是**下单当时那一版**的 ID（`refs()` 当时校验过它属于这张 BOM）。
3. 而 `bomItemOrderStatus` 原来是「取当前未删除的行 ID，再 `bomItemId in [...]`」——
   老行已软删，**不在 `in` 里** → 那些量统计不到 → `state: "none"` → 界面「未下单」。

于是：**先下过单、后来有人保存过 BOM 表**的那些行会集体显示「未下单」（「有些物料」就是这么来的）；
没保存过 BOM 的行一切正常（「刚刚试了一单，又可以了」）。

### 修复：归集范围按「采购单挂的那张 BOM」，行 ID 只用来做精确归集

```ts
const rows = await this.prisma.purchaseOrderItem.findMany({
  where: { deletedAt: null, bomItemId: { not: null },
           purchaseOrder: { deletedAt: null, bomId, status: { not: "cancelled" } } },
  select: { bomItemId: true, materialId: true, quantity: true, purchaseOrder: { select: { purchaseOrderNo: true, status: true } } },
});
```

- 行 ID **还在**当前 BOM 里 → 按行精确归集（与原来完全一致，不动既有行为）；
- 行 ID 已被换掉 → 按**物料**摊回该物料在当前 BOM 的**第一行**（同一物料在 BOM 里有多行时只摊第一行，不重复计数）；
- `bom_item_id` 为空 = BOM 外新增行（补料/替代料）→ **不占任何 BOM 行的需求量**（与原来一致）；
- 物料已从 BOM 里删掉 → 那条历史下单**不摊到别的行上**（宁可少显示，也不能张冠李戴）。

用 `purchase_orders.bom_id` 而不是「行 ID 世系」还有两个好处：不需要把历史上所有软删行都捞出来
（BOM 每存一次就多一整份副本，那个集合会长），而且哪怕老行被硬删也仍然算得出来。

## 根因 2（前端·不刷新）：这一列只在「带入 BOM 明细」那一刻拉过一次

**先跑红的复现**（`apps/web/test/procurement-order-collapse.test.tsx`）：

```
✖ 回归 2026-09-20：别的窗口刚下过单，切回本页要刷新「下单状态」（不是只刷采购单列表）
  Expected: "已下单"   Received: "未下单"
```

`refreshBomOrderStatus()` 原来只在两处被调用：带入 BOM 明细、打开一张已存在的单。
而页面上**已经有**焦点/可见性刷新（`refresh-policy`，2026-09-14 为「入库状态没有及时更新」加的），
它只刷采购单列表 —— **偏偏漏了草稿表里这一列**。

后果：采购员乙的「新建采购单」开着，采购员甲（或乙的另一个窗口）把其中几行下了单，
乙切回来看到的仍然是「未下单」→ 再下一张 = 重复采购。

### 修复：把两个数据源合到一个刷新入口，并让状态跟着焦点走

- 新增 `refreshListAndOrderStatus()`：先 `load()` 再 `refreshBomOrderStatus(当前草稿的 BOM)`；
  焦点/可见性刷新（静默）与列表操作后的刷新都走它。
- 当前草稿的 BOM 用 **ref** 记（`draftBomIdRef`）：焦点监听只挂一次，闭包里的 `purchaseDraft`
  永远停在打开那一刻 —— 直接读它会「打到上一张 BOM 上，越刷越错」。
- 刷新失败时**不再一律清空**：换了一张 BOM 才清（旧状态本来就是错的）；**同一张 BOM 刷新失败则留着
  上一次的结果**。把「已下单」刷成「未下单」正好会诱发这一列要防的事，宁可略微过期，
  也不给一个错误的「没买过」。

## 顺带收紧了一条已经变空的守卫

`apps/web/lib/refresh-policy.test.mjs` 的「后台刷新必须静默」原来只查**文件里出现过**
`load({ silent: true })`。采购单页在「保存打印信息」里也有这一句，于是焦点刷新改成非静默也照样绿
—— 守卫盯错了地方。现在断言的是 `const refresh = () => …` 这一段（焦点/可见性那一条路径）本身
必须带 `silent: true`。

## 回归护栏

| 层 | 用例 | 钉住什么 |
|---|---|---|
| API | 「BOM 表存过一次之后…仍要看得见」 | 行 ID 全换后已下单量与单号仍归到当前行 |
| API | 「仍按行 ID 精确归集」 | 分摊只针对已消失的行；当前行 ID 还在的逐行精确 |
| API | 「物料已从 BOM 删掉不摊到别的行」 | 不张冠李戴 |
| API | 「BOM 外新增行不占 BOM 行需求量」 | `bom_item_id` 为空的不计入 |
| API | 假 Prisma 按 `where` 真实过滤 | 归集口径的查询条件本身是被测对象，恒返回全部的桩会让断言永远通过 |
| web | 「切回本页要刷新下单状态」 | 焦点刷新必须连这一列一起刷 |

## 仍存在、但**没有**在本次修的相邻问题

- **在采购单页里「编辑BOM表」并保存之后，已经打开的草稿行仍然指着旧行 ID**：
  保存那一刻 `bomSaved` 只 `load()`，草稿的 `bomItemId` 不会更新，于是这张草稿**提交时**会被
  `PURCHASE_BOM_ITEM_MISMATCH`（「采购明细必须引用当前 BOM 表中的对应物料」）整张拒掉，
  而界面上的报错看不出是哪一行。修它要先决定口径（重新带入 BOM？清掉 `bom_item_id` 转成补料行？
  还是禁止在有草稿时改 BOM），所以先报出来，没有自作主张。
- BOM 行 ID 每次保存都整体更换，是这一整类问题的源头。若改成「按物料保留未变动行的 ID」，
  下游所有按 `bom_item_id` 归集/校验的地方都会一起受益 —— 但那会动「整块替换」的写语义与审计口径，
  属于独立的一次改造。

## 教训

1. **「某个 ID 是某一时刻的快照」这件事必须写在读侧的口径里。** 写侧存的是当时那一版的行 ID，
   而读侧按「当前」的行 ID 去找它 —— 中间只要有人保存过一次 BOM，链路就断了，且**不报错**。
2. **一个页面里有两个数据源时，刷新必须成对。** 焦点刷新只刷一半，就会自相矛盾（列表里已下单、
   草稿里未下单），而人只会相信眼前那个格子。
3. **守卫要盯住那条路径，不是盯住那个字符串。** 「文件里出现过 silent: true」这种断言在文件里
   第二处出现同样写法时就已经失效了。
