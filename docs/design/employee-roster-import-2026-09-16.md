# 员工花名册导入口径（2026-09-16）

## 1. 背景

人事模块原来用一份 8 列导入模板：

```
工号、姓名、部门编码、岗位编码、员工类型、入职日期、离职日期、备注
```

2026-09-16 用户导入了一份新模板 `迪礼员工更新员工花名册(1).xlsx`（《在职员工花名册》，28 列），
要求**员工信息口径包含该模板里的所有字段**，并相应调整模板与导入解析过程。

已与用户确认的三条口径：

1. 以《在职员工花名册》为准（不是另一份 `花色生产单`）；
2. 花名册没有「工号」列 → 模板补一列工号，**留空时按已有规则自动生成**（`EMP-当天日期-序号`，与物料 `MAT-`／供应商 `SUP-`／客户 `CUS-` 同一套规则）；
3. 年龄、工龄、当月生日员工、合同即将到期人员、劳务合同即将到期人员是公式派生列 → **不落库**，由后端按当天日期实时计算，导出时带上。「本月生日」只是页面上的一个筛选，同样不进模板。

证据：`example/人事/迪礼员工更新员工花名册(1).xlsx` 与 `example/销售单/迪礼员工更新员工花名册(1).xlsx`
是同一份文件（SHA256 相同），git 里旧的花色生产单示例已被删除。

| 28 | 劳务合同即将到期人员 | 派生 `laborContractStatus` | 否 | 劳务合同的档位 |

系统侧另有 3 列不在花名册里，属于系统必需信息：**工号**（可留空自动生成）、**员工类型**（车间/非车间，
决定计件/计时工资规则）、**离职日期**。

派生列的判定规则（列表与导出时按当天日期算）：

- 年龄／工龄：满年才加 1（未到生日当天不算一年）。
- 当月生日员工：导出写 `1` / `0`；员工目录用布尔 `birthdayThisMonth`，并有一个「本月生日」筛选。
- **合同档位**（统一成三档，去掉原先「合同即将到期 / 合同已过期」的写法）：
  结束时间 < 今天 → `已过期`；今天 ≤ 结束时间 ≤ 今天 + 31 天（1 个月内）→ `即将过期`；
  更远 → `正常`；没填结束时间 → 空（**不假装「正常」**）。到期当天算 `即将过期`，不算过期。
- **合同情况**（`contractSituation`，员工目录里合并后的那一列）：把劳动合同与劳务合同**并成一个档位**，
  取两者中最紧急的一档（`已过期` > `即将过期` > `正常`）；两份都没填结束时间才是空。
  导出仍按花名册原样保留两个分开的列（`合同即将到期人员` / `劳务合同即将到期人员`）。

## 3. 导入解析

### 3.1 按表头名匹配，不按列序号

解析以**表头名**为准（`EMPLOYEE_HEADER_ALIASES`，每个字段带一组同义写法），因此：

- 操作员挪动列顺序、增删无关列都不会错位；无关列被忽略，并在导入结果里如实上报（`ignoredColumns`）；
- 旧版 8 列模板仍可导入（`部门编码`/`岗位编码`/`员工类型`… 都有别名），不需要一次性切换；
- **导出的员工名单可以直接回灌导入**（派生列与展示列会被识别为「已忽略」）。

### 3.2 手工维护的花名册可以直接上传

系统模板是「首行即表头」；而手工花名册是文档形态：

- 首行是公司名、第二行是表名，**表头在第 3 行**；
- 「合同起止时间 / 开始时间」「劳务合同 / 开始时间」是**两行合并表头**；
- 数据块之后还有「绿色：…／黄色：…／工龄：…」说明批注。

解析器按下面的规则处理，两种形态都认：

1. 在前 10 行内向下找「同时含 姓名 + 部门 + 职务」的行作为表头；
2. 若下一行像子表头（只含「开始时间/结束时间」这类短标签），把它与父列拼成 `合同起止时间-开始时间`，数据再下移一行；
3. 文档形态下，数据块在**第一个空行**处结束，避免把末尾批注当成数据行；被跳过的行数在 `ignoredTrailingRows` 里回报。
   系统模板形态（表头在第一行）不受此规则影响，中间的空行照旧跳过。

找不到表头（例如误传了花色生产单）时只回一条整体错误，**一行都不解析**；只缺 1~2 列时
（例如漏了「职务」）提示精确到「缺少必需列：职务/岗位」。

**行级错误不连坐**：整批不可导入只在「找不到表头 / 缺必需列 / 没有数据行」三种情况成立；
其余情况通过校验的行照常导库，出错的行单独列出，`status=partial`。

导入结果里除计数外还回传 `hints`（操作员接下来该做什么）、`autoNumbered`、
`inferredEmployeeTypes`、`ignoredColumns`、`ignoredTrailingRows`、`headerRow`、`missingColumns`、
`documentLayout`、`presentFields`，前端在导入对话框里逐条展示。

### 3.3 工号自动生成

工号留空时按 `EMP-YYYYMMDD-####` 生成，序号取当天已有工号的最大数字后缀 +1，同一批内连续递增。
生成时会同时避开「文件里已声明的工号」与「库里当天的已有工号」，避免同一批自撞号。
并发下撞唯一约束时，自动编号的行会**换号重试一次**；手工填写的工号不重试（重试没有意义）。

### 3.4 身份证号反推

- 18 位：校验位必须匹配（能挡住手抄错号），出生日期取第 7–14 位，性别取第 17 位奇偶；
- 15 位老号：出生日期按 19YYMMDD 补全；
- 出生日期/性别留空 → 用反推值补齐；手填了且与身份证不一致 → 该行报错（`不一致`），不静默覆盖用户输入；
- 编辑员工时，档案里已有出生日期/性别不会被反推值覆盖。

### 3.5 员工类型：留空时按部门推断（并如实报告）

手工花名册没有「员工类型」列，而它决定工资规则，不能瞎猜。规则是：

- 明确填了 → 用它（填错则报错）；
- 留空且该部门已有员工的员工类型**完全一致** → 照该类型推断，计数进 `inferredEmployeeTypes` 回报给操作员复核；
- 留空且该部门已有多种类型／还没有员工 → 逐行报错，要求手工填写。

### 3.6 日期：必须用 `cellDates: false` 读工作簿

SheetJS 的 `cellDates: true` 会把 Excel 序列号 42877（= 2017-05-22）转成 `2017-05-21T15:59:35Z`——
比本地零点早 25 秒，日期整整错一天（旧模板导入也有这个缺陷）。因此导入读工作簿时固定用
`cellDates: false`，让日期保持数字形态，再走精确的「1899-12-30 + 序列号」换算，不依赖服务器时区。

序列号窗口设为 10000（≈1927-05-18）～ 60000（≈2064-03-06）：窗口外的数字（例如把年份写成 `2026`、
把手机号塞进日期列）一律按非法日期报错，而不是换算成一个荒谬的日期。文本日期
（`2026-01-05`、`2026/1/5`、`20260105`、`2026年1月5日`、带时间的 ISO）也都能认。

## 4. 模板与导出

- **导入模板**（`GET /production/employees/import-template.xlsx`）：26 列 = 花名册的 23 个非派生字段
  + 工号 + 离职日期 + 员工类型；第二张「填写说明」表说明填写规则。示例行的身份证号是**校验位自洽**的
  （否则操作员下载模板直接上传就会被自己的校验挡下来）。
- **员工名单导出**（`GET /production/employees/export.xlsx`）：37 列 = 花名册原始顺序（含 5 个派生列）
  + 系统列（员工类型、部门编码、岗位编码、绑定系统用户名、离职日期、员工备注、创建/更新时间）；
  年龄/工龄导出为**数字**，Excel 里可直接排序与做条件格式。
- **员工目录列表接口**（`GET /production/employees`）在员工行上附带
  `age`/`tenureYears`/`birthdayThisMonth`/`contractStatus`/`laborContractStatus`/`contractSituation`
  派生字段。员工目录页展示合并后的「合同情况」一列；「本月生日」是这一页的一个筛选下拉
  （全部生日 / 本月生日），不写进导入模板，也不需要额外字段——它读的就是 `birthdayThisMonth`。

## 5. 落库形态

新增 17 个可空列（`apps/api/prisma/migrations/20260916120000_employee_roster_fields/migration.sql`）：

`birth_date`、`gender`、`ethnicity`、`id_card_no`、`education`、`blood_type`、`social_insurance`、
`commercial_insurance`、`contract_start`、`contract_end`、`labor_contract_start`、`labor_contract_end`、
`home_address`、`current_address`、`phone`、`emergency_contact`、`emergency_phone`。

全部可空：历史员工没有这些信息，新建/导入也允许先留空后补录，迁移只加列、不改写既有行。
另外附三条边界检查（与既有的 `employees_employee_type_check` 同一套约定）：
`gender ∈ (男, 女) 或 NULL`、劳动合同区间单调、劳务合同区间单调；并为 `id_card_no` 建普通索引
（**不建唯一约束**：历史花名册里存在空值与人工占位值，唯一约束会把整批导入直接顶掉）。

## 6. 删除员工（逻辑删除）

员工列表的行内「删除」= **逻辑删除**：写 `deleted_at`/`deleted_by`，物理行保留。

- **刻意不做引用检查**。员工被生产日报、考勤、绩效、工资台账引用是常态；像部门/岗位那样
  「被引用就不许删」（`DEPARTMENT_IN_USE` / `POSITION_IN_USE`）会让删除几乎永远失败。
  真正要停掉的业务由状态控制（离职 / 停用），删除是更高一层的事实：「这条不该在册」。
- **删掉之后**：员工从 `GET /production/employees` 默认结果里消失（所有选择器、花名册导入的
  部门类型推断、工序计价的可选员工一并消失）；工资月台账 `importMonth` 的候选员工也过滤
  `deleted_at`，不会给已删除员工新建台账；登录账号绑定（一个用户只能绑一名员工）随之释放。
- **历史不受影响**：日报/考勤/绩效/台账通过外键指向物理行，名称与工号照旧能查到，也不动
  `employment_status`——所以恢复之后状态与删除前完全一致。
- **可恢复**：`POST /production/employees/:id/restore` 只清行上的 `deleted_at`，原始
  `deleted_by`/`deleted_at` 写进审计事件（`employee.restore`）。员工列表的状态筛选新增
  「已删除」一档专门看这些行（「全部状态」刻意**不含**已删除——删除就该从列表里消失；
  `listEmployees` 用 `include_deleted=true` 才返回它们）；已删除的行只留一个「恢复」按钮。
- **权限**：`DELETE` 与 `restore` 都是 `@RequireAdministrator()`，与员工的新建/编辑/离职一致。
- **重复删除**返回 404 `EMPLOYEE_NOT_FOUND`（不是静默成功）；**恢复没删过的员工**返回 404
  `EMPLOYEE_NOT_DELETED`，与部门/岗位同一套约定。
- 「已删除」默认不会进任何出口：员工名单导出按钮不传 `include_deleted`，所以导出的永远是在册
  名单（接口层仍允许显式传 `include_deleted=true` 导出全部，留给管理员对账用）。
- 前端确认弹窗用 `components/ui/dialog.tsx`，**不用** `components/ui/alert-dialog.tsx`：
  后者的 `AlertDialogContent` 在当前 Radix 版本下渲染即抛
  `Primitive.div failed to slot onto its children`，且全仓库没有任何调用方（属未验证过的死代码）。

## 7. 口径变更与已知缺口

- **政策变更**：2026-08-20 备忘曾确认「身份证，银行卡，不需要」，2026-08-21 日志也写明员工不保存身份证。
  花名册口径要求身份证号码，因此**身份证号码现在会落库**（历史日志文档保留原样，作为当时的决策记录）。
  **银行卡信息仍然不保存**。
- 社保/商业险只是登记事实，**不参与自动算薪**（V1.0 决策不变）。
- 地址只给「省 + 市 + 县」前缀，**镇/村/门牌一律手填**。导入时**住址为空**才用身份证解析出的
  省市县补个前缀，并在导入结果里如实回报补了几行（`addressedFromIdCard`）；文件里写了住址就
  原样入库，绝不用解析结果去改操作员填的内容。解析不出地区（如老到查不到的代码）时也不编造，
  地址就保持为空。

## 7.1 身份证 → 出生日期 / 性别 / 省市县

花名册绿色批注要求「输入身份证号就自动跳出相应信息」，现已完整落地，**两处都会解析**：

| 场景 | 行为 |
|---|---|
| 页面单个新建/编辑员工 | 填完身份证号**立即**在表单里带出出生日期、性别，以及家庭住址的省市县前缀（`apps/web/lib/id-card.ts`，本地解析，不需要请求接口） |
| Excel 批量导入 | 逐行解析出生日期与性别；与手填值不一致则报错（不静默覆盖）；**家庭住址为空的行走同一条规则补省市县前缀**（有地址的行原样保留） |

自动填充是**非破坏性**的：只补空着的字段，操作员手填过的值一律不覆盖；身份证没填完或校验位
不对时一个字段都不动。

### 行政区划数据怎么来的

身份证前 6 位是**签发当时**的区划代码，而且终生不变，所以只查现行 GB/T 2260 是不够的：
本厂花名册 10 个人里就有 3 个是老码（`413028` 原信阳地区罗山县、`522228`/`522224` 原铜仁地区
沿河县/石阡县），只查现行表这些号码只剩省级。因此数据表**合并了两份来源**：

| 来源 | 作用 | 指纹记在生成物里 |
|---|---|---|
| [modood/Administrative-divisions-of-China](https://github.com/modood/administrative-divisions-of-china) `dist/pca-code.json` | 现行省/市/区县名称（优先） | ✅ |
| [yescallop/areacodes](https://github.com/yescallop/areacodes) `codes.json` | 1981 年以来的历史代码，补齐已撤销的省市县 | ✅ |

生成方式：`npm run regions:generate`（脚本 `scripts/generate-china-regions.mjs`，默认联网下载，
也可以传两个本地快照路径离线重跑）。产出**同一份内容**写到两个 App：

- `apps/api/src/modules/production/china-region.ts`
- `apps/web/lib/china-region.ts`

为什么不做共享包：本仓库是 `apps/*` 双 workspace、没有共享包（币种字典也是两边各一份的既有约定），
而 Web 必须本地解析。两侧一致性由测试守住 —— API 单测比对两份文件**逐字节相同**，
Web 测试用同一批身份证号断言同样的结果。

当前表覆盖 34 个省级单位 / 554 市 / 5859 区县（共 6447 条，其中 3100 条只存在于历史区划）。
取名规则：逐级独立查表，**能查到哪一级就给哪一级**（区县缺→省市，市缺→省），全部查不到就是空串；
直辖市/省直辖的「市辖区/县/省直辖县级行政区划」这类伪市级会被跳过，不会拼出
「北京市市辖区东城区」。区划代码查不到**不影响**出生日期与性别的解析，也不判定身份证非法。

已知取舍：行政区划会继续调整，表是**静态快照**（指纹可核对），遇到更新的代码时降级为
「能查到哪一级用哪一级」，地址宁缺勿错。

## 8. 验证

用真实文件打穿「Excel → 服务层导入 → 导出 → 再导入」全链路（内存 prisma 替身，3 个场景）：

| 场景 | 结果 |
