## 一、采购 → BOM表：没有新建入口的根因是**取数**，不是权限

### 1.1 根因

`app/procurement/boms/page.tsx` 原来这样取销售单：

```ts
apiGet<Reference[]>("/sales-orders")            // 不带状态；服务端默认只给最近 20 张
const confirmedSalesOrders = salesOrders.filter((item) => item.status === "confirmed");  // 再在前端过滤
```

而 `GET /sales-orders` 的默认是 `page=1&page_size=20`（`sales-orders.service.ts` 的 `list(page = 1, pageSize = 20, ...)`），
返回**最近更新的 20 张任意状态**的销售单。于是：

- 这 20 张里如果一张「已确认」都没有（最近动过的都是草稿），这一页**整页空**：显示"暂无已确认销售单"，
  **连「新建BOM表」按钮都不存在** —— 用户说的就是这件事；
- 就算有几张，**更早的已确认单永远轮不到**。

对比：生产页的 BOM 入口一直是对的 ——
`/sales-orders?status=confirmed&page=1&page_size=200`（`app/production/page.tsx`）。

### 1.2 改法（只改取数，不动业务规则）

| 位置 | 改动 |
| --- | --- |
| 取数 | `/sales-orders?status=confirmed&page=1&page_size=200` —— 与生产页**逐字一致**（服务端筛、一次 200 张） |
| 前端过滤 | **删掉**（口径 1）：服务端已经筛过；再过滤一次正是这次的缺陷形态（"在最近 20 张里挑"）。万一服务端回了别的状态，页面上的「BOM状态」列会如实显示出来，比静默吞掉强 |
| 空状态 | 列表为空时**才**多问一次 `?status=draft&page_size=1`，拿 `meta.total` 写出「还有 N 张销售单是草稿：BOM 只能建在已确认的销售单上」 |

**为什么保留「只有已确认才能建 BOM」这条规则**（用户也选了这一档）：BOM 是"按这张单买料/投产"的清单。

- 草稿单随时会被改（数量、产品、规格），拿它建 BOM 等于给一份还会变的单子承诺物料；
- 而且**下游全都要求已确认**：采购计划 `loadBom()` 要求 `salesOrder.status === "confirmed"`、
  采购单 `refs()` 要求销售单已确认、生产单的候选也只从已确认单来。放开草稿建 BOM 只会造出
  "有 BOM 但什么都开不出来"的死角。

所以"有销售单事实"= 销售单**已经确认生效**（这份单子上的东西是既成事实）；用户看不到入口，
是因为取数把那 20 张之外的、或者恰好没被抽中的已确认单挡在了外面。

### 1.3 那一句"还有 N 张草稿"为什么值得单独问一次

BOM 只能建在已确认单上，而"为什么这一页是空的"对用户是个谜 —— 一句"暂无已确认销售单"等于什么都没说。
2026-09-16 的「BOM表的新建物料按钮怎么不见了」就是同一类"按钮/表空着但不说原因"的坑。

这次请求**不在那个 `Promise.all` 里**：一是失败不影响主数据（空列表时才发、失败就退回原来那句文案），
二是那个位置型解构有 `lib/page-data-alignment.test.mjs` 盯着（顺序与绑定表）。

## 二、记账凭证导出：一行一条**分录**，带摘要

### 2.1 为什么是"一行一条分录"

用户原话是「记账凭证中，摘要也要一并导出」。排查结论：

| 出口 | 有没有摘要 |
| --- | --- |
| 凭证纸（页面） | ✅ 有「摘要」列，取 `voucher_lines.summary`，空则回退凭证总摘要 |
| 导出 PNG（`lib/voucher-image.ts`） | ✅ 有（表头「摘要」+ 每行都印，与页面同一批字段） |
| **Excel 导出** | ❌ **原先不存在** |

而摘要与会计科目是**分录行**（`voucher_lines`）上的字段：凭证头上只有一个总摘要。
所以新导出的粒度必须是**一行一条分录** —— 一行一张凭证的话，"这笔钱记到什么科目、凭什么"
恰恰看不见，而那正是财务要的摘要。同一张凭证的多行共用前几列（凭证号/日期/期间/状态/来源），
Excel 里按凭证号筛选即可，比再拆"头表 + 行表"好读。

### 2.2 列定义（`voucher-workbook.ts`）

```
凭证号 | 日期 | 期间 | 状态 | 来源 | 行号 | 摘要 | 会计科目 | 借方金额 | 贷方金额 | 币种 | 备注
```

四条口径：

1. **摘要**取分录行的 `summary`，没写就回退凭证总摘要 —— 与凭证纸、导出 PNG **同一口径**
   （三处各判一次的话，屏幕上有一句、导出的表里空着，财务会以为导出坏了）。
2. **借/贷分两列、没有的那一边是空单元格**（照凭证纸）。写 0 会被读成"这一行借贷各有一笔 0"，
   而 0 在金额列是"确实为零"的事实。
3. **金额落数值类型**（`numFmt`）：导出到 Excel 后要能求和/筛选，文本型数字会混进筛选。
4. **不设合计列**：一列里可能混着多个币种，跨币种相加没有意义（与收支明细表同一口径，R7）。
   每张凭证的借贷合计在凭证头上（页面与凭证图上都有）。

### 2.3 端点与权限

| 层 | 改动 |
| --- | --- |
| API | `GET /finance/vouchers/export.xlsx`，筛选与列表接口**同一个 DTO**（`period` / `status`），所以"看到的就是导出的"这条口径成立 |
| 路由顺序 | `export.xlsx` 是**单段**路径，必须声明在 `@Get(":id")` **之前**，否则会被当成一个凭证 id 吃掉（同 `import-template.xlsx` 的教训） |
| 权限 | 不加 `@RequireAdministrator()`：它与列表是**同一份数据、同一道 finance 门** —— 能看到清单就能导出，导出多不了一层保护。真正的边界是类级 `@RequireModules("finance")` |
| Web | 凭证管理页头加一个「导出 Excel」（凭证为空时置灰），走 `downloadFile`，文件名用后端给的（含生成时间与行数） |

## 三、实施结果（2026-10-13）

| 检查 | 结果 |
| --- | --- |
| `npm test`（typecheck + deploy 脚本 + API + web） | 见 `docs/log/2026-10-13.md` |
| 定向新增用例 | API：`voucher-workbook`（6 条）；web：`procurement-bom-page`（+2）、`finance-page`（+2） |
| 改到的既有用例 | `procurement-bom-page` 的桩从"精确匹配 `/sales-orders`"改成**前缀匹配**（请求现在带查询串） |
| `test:api` / `test:integration` / `test:e2e` | **环境阻断**（本机没有 PostgreSQL 与已启动的 API） |

未在本机验证的项：

1. **`page_size=200` 的上限**：一次拿 200 张已确认销售单。超过 200 张的厂子会只看到最近更新的 200 张
   （与生产页同一取舍）。真要更多，正确做法是给 BOM 页一个"待建 BOM 的销售单"专用端点（分页 + 搜索），
   不是把 200 调大 —— 那只是把问题推后。
2. **导出的 Excel 在真机上的列宽/数字格式**只能目视（单测断言的是单元格值与类型）。
3. **凭证量很大时的导出**：一次性把全部凭证与分录读进内存（与其它报表导出一致）。本仓库既有口径如此，
   未额外分页；上服务器后如果凭证上万，值得加期间筛选（筛选参数已经预留）。
