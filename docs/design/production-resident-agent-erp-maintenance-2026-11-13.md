# 生产常驻 Agent 自动修 ERP（2026-11-13）

日期：2026-11-13｜版本：1.0｜状态：待评审｜类型：架构与施工计划

用户原话：

> 用户天天向我反馈一些缺陷，但是我很忙，经常没办法及时处理 bug。所以我决定在生产服务器里面常态运行一个 DeepSeekHarness，
> 然后监听飞书群消息，涉及 bug、新需求，就启动 Harness runtime 开始改动 ERP，基线冒烟测试，脱敏数据库测试，
> 通过后，原地热重载部署。这样可以解放我一些精力。只需要用户反馈的语句准确，Coding Agent 完全可以很好胜任。

本条拍板（2026-11-13 会话给定）：

| # | 拍板 | 后果 |
|---|---|---|
| 1 | **全自动上线，失败自动回滚** | 不设人工点「上线」的卡口 |
| 2 | **黑名单而非白名单：除「不准动生产库」外全部放开** | 见 D14；改动范围由反例定义，不由正例清单定义 |
| 3 | **不算 token 预算** | R-12 收回，只留进程外硬超时保资源 |
| 4 | **飞书先开免审** | 自建应用改权限/事件订阅即生效，不必等管理员审核 |
| 5 | **负责人是用户本人** | 唯一会被叫醒的人；接管与叫停都由他做 |

文档形态选 Markdown 进 `docs/design/`，与仓库既有 100+ 份设计文档同构（宪法 §Decision Traceability 1、3）。

## 0. 结论

方案可行，但**瓶颈不是 Agent 能力，是这台机器的资源余量**，所以施工顺序必须先把资源证死，再谈自动化。

1. 飞书这一层选**长连接**，不选回调。服务器有公网 IP 但只开 80、没有 TLS；
   长连接只要求出站，实测 `open.feishu.cn` 可达，能省掉验签、防重放、3 秒预算和 nginx 改动。
2. **本机实测 DSH 在 Node 22.23.2 上能启动并完成任务**，但两个包都声明 `engines.node >= 24.9.0`，
   `apps/coding-worker/src/runtime-contract.ts:3` 还会硬拒。所以仍需为 Agent 单独装 Node 24，不复用线上的 22。
3. 现有部署四件套 `remote-build/migrate/switch/verify.sh` **可以原样复用**，
   只需补一个 Linux 侧打包脚本。这是本次最大的成本节省：部署主链一行不改。
4. 真正的新东西只有三件：飞书收发、工单状态机、门禁编排。其余全是已有能力。
5. 单车道串行：一次只跑一个工单。理由见 §6 D5，这是资源决定论，不是保守。

## 1. 已核对的事实

以下为 2026-11-13 实测，非估算。

| 项 | 实测值 | 对方案的影响 |

| 机型 | Ubuntu 24.04 / 2 vCPU / 1740 MB / 4 GB swap / 40 G 盘 | 内存是硬约束 |
| 磁盘 | 已用 18 G，可用 20 G（48%） | 每个完整 install 约 1.9 G，最多再放 6 份 |

## 2. 范围与非目标

**做**

- 飞书群内 @机器人 的消息变工单，状态与结果用卡片回写。
- Agent 在服务器上的**独立 git 工作区**改代码、跑门禁、提交。
- 通过后按既有标准上线，失败自动回滚到上一个 `app.backup-*`。
- 每个工单留一份可复跑的证据目录。

**不做**

- 不改生产目录 `/opt/dilee/app` 的任何源码。它仍然只能由发布包覆盖。
- 不做 Next.js HMR 或打包器热更新。此处「原地热重载」= 目录切换 + PM2 重启（D1）。
- 不做多工单并行、不做多机、不做跨群共享状态。
- **不动生产库**（D13 唯一的硬黑名单）：不写、不迁移、不动容器与卷、不删 `db-snapshots`。
- 不接飞书以外的渠道。

与 `docs/SelfEnvolvingTry/` 的关系：那边是让 Agent 生成**查询工具**；这边是让 Agent 修 **ERP 代码**。
两者共用 DSH 与沙箱事实，但门禁与产物完全不同，不合并。

## 3. 需求清单

- **R-1 群消息进得来，结果回得去** — 用户本次要求
- **R-2 语句不准确时不开工，先追问** — 用户原话「只需要用户反馈的语句准确」
- **R-3 Agent 只在独立工作区改代码，生产目录不被它碰** — 部署标准:8 与宪法 §Reversible 1
- **R-4 基线冒烟是第一道门** — 用户原话
- **R-5 脱敏数据库测试是第二道门** — 用户原话
- **R-6 通过后原地热重载上线** — 用户原话
- **R-7 上线失败自动回滚** — 本次会话选项
- **R-8 无人值守仍不越界** — 会话审批策略 `never` + `dsh-user-approval` 事实
- **R-9 不和线上抢资源** — 实测 2 核 1.7 G
- **R-10 每个工单可追溯、可复跑、可叫停** — 宪法 §Decision Traceability 5
- **R-11 迁移类改动不进自动链路** — D13 唯一硬黑名单的推论
- **R-12 超时保护** — 2 核机器上跑飞的进程会占死线上；用户取消 token 预算

## 4. 逐项实施方法

### R-1 群消息进得来，结果回得去

- **做法**：自建应用开长连接，订阅 `im.message.receive_v1` 与卡片回调；消息落库转工单，卡片按状态原地更新。
- **涉及**：飞书应用、新的 `apps/ticket-agent` 服务、工单表。
- **测试入口**：现有 `scripts/run-tests.mjs` 的 `unit` 模式加一个飞书适配器的假 transport。不新增测试框架。
- **验收**：`[ ]` @机器人 的消息 3 秒内落库并回一张卡片 `[ ]` 同一 `message_id` 重投不产生第二张工单 `[ ]` 机器人自己发言不触发新工单
- **难点**：长连接下每应用最多 50 条连接，且是随机投递。只能单实例，不能靠多副本扩容（D4）。

### R-2 语句不准确时不开工

- **做法**：消息先过一道分诊，输出「要改哪个模块、期望行为、复现入口」。缺项就回卡片追问，不建构建任务。
- **涉及**：分诊提示、工单元数据。
- **测试入口**：分诊函数用固定语料做表驱动单测，纯函数，无网络。
- **验收**：`[ ]` 缺模块或缺期望时不出构建任务 `[ ]` 追问卡片列出还缺哪几项 `[ ]` 追问两轮仍不完整则转人工
- **难点**：分诊判「太含糊」的阈值很难一次定对；用真实历史缺陷语料回归，不靠感觉。

### R-3 Agent 只在独立工作区改代码

- **做法**：`/opt/dilee/agent/repo` 是一份独立 clone，每次工单切一个分支；产物用 `git archive` 打成发布包，走既有部署脚本。
- **涉及**：新 clone、分支命名、打包脚本。
- **测试入口**：复用 `scripts/deploy-scripts.test.mjs` 的守卫风格，新增打包脚本自身的断言。
- **验收**：`[ ]` 一次工单只产生一个提交 `[ ]` 发布包只含已提交内容 `[ ]` `/opt/dilee/app` 的源码文件在任何时刻都只由发布包写入
- **难点**：这是对「服务器不作为 Git 工作区」的**超越而非违反**（D2）。生产目录仍无 git，git 只存在于 Agent 工作区。

### R-4 基线冒烟是第一道门

- **做法**：构建成功后起一个临时实例，打一组只读冒烟：health、登录页、manifest、关键页面与关键 API。
- **涉及**：冒烟脚本、临时端口、临时库。
- **测试入口**：新增 `scripts/agent/smoke.sh`，`curl` + 退出码，不引入 Playwright。
- **验收**：`[ ]` health 返回 `status=ok` 且 `build` 等于候选版本号 `[ ]` 登录页与 manifest 200 `[ ]` 5 个核心列表接口 200 `[ ]` 任一失败即止，不进入下一道门
- **难点**：临时实例要连**脱敏库**，不能连生产库；端口必须避开 3000/3001。

### R-5 脱敏数据库测试是第二道门

- **做法**：把生产快照灌进专用库并脱敏，在候选目录上跑集成与契约测试。
- **涉及**：快照导出、脱敏、`provision-test-databases.mjs`、`run-tests.mjs`。
- **测试入口**：既有 `npm run test:integration` 与 `npm run test:api`，`TEST_DATABASE_URL` 指向脱敏库。
- **验收**：`[ ]` 库名含 `test`，否则脚本以 `exit 3` 拒绝 `[ ]` 集成测试零失败 `[ ]` 契约测试零失败 `[ ]` 原生产库与快照库未被写入
- **难点**：现有 `fetch-prod-snapshot.ps1` 只会在 Windows 本地跑；服务器侧需要一条等价的 Linux 取数与脱敏路径（D8）。

### R-6 通过后原地热重载上线

- **做法**：按 `.agent/deployment/server-incremental-deployment-standard.md` 的四步：build → migrate → switch → verify。原地重启 PM2，不换机器不改 nginx。
- **涉及**：`remote-build/migrate/switch/verify.sh`、`RELEASE_VERSION`、PM2。
- **测试入口**：既有成功判定（两个进程 online、health build 匹配、manifest 与登录页 200）。
- **验收**：`[ ]` health 的 `build` 等于新提交号 `[ ]` 两个 PM2 进程 online `[ ]` 部署后核验脚本退出码 0
- **难点**：构建占满 2 核约 10 分钟，期间线上延迟会抖动，要有预期而不是当故障（R-9）。

### R-7 上线失败自动回滚

- **做法**：切换后任何一步失败，调 `remote-rollback.sh` 回到上一个 `app.backup-*`，再跑一次成功判定。
- **涉及**：回滚脚本、自动触发条件。
- **测试入口**：新增一个「故意让 health 版本不匹配」的演练用例，断言确实回滚。
- **验收**：`[ ]` 切换失败后 60 秒内回到旧版本 `[ ]` 回滚后 health build 等于回滚目标 `[ ]` 失败目录保留为 `app.failed-*` 不删除
- **难点**：迁移已应用后不能「回滚」迁移（D9）。回滚只回代码，数据前向兼容。

### R-8 无人值守仍不越界

- **做法**：Agent 进程固定 `--approval-policy never` + `workspace-write` 预设 + 工作区白名单；需要更宽权限的调用直接失败而不是等待。
- **涉及**：DSH 启动参数、permission preset、工具白名单。
- **测试入口**：一次「要求写工作区外路径」的对抗用例，断言被拒且工单落 `failed`。
- **验收**：`[ ]` 工作区外写入被拒 `[ ]` 无人工审批请求堆积 `[ ]` 拒绝原因写进工单证据
- **难点**：`never` 是失败封闭而非放宽。设计上必须保证常态路径不触发审批，否则工单会因「无审批人」而失败。

### R-9 不和线上抢资源

- **做法**：单车道串行；构建前检查可用内存与负载；Agent 与构建互斥，构建期间不跑 Agent 的重活。
- **涉及**：队列、资源闸、调度。
- **测试入口**：调度器纯函数单测（给定资源快照返回 run/queue/reject）。
- **验收**：`[ ]` 同时最多 1 个构建 `[ ]` 可用内存低于阈值时排队而不是硬上 `[ ]` 线上 API 的 p95 在构建期间不被判为故障
- **难点**：门禁本身是重活，而门禁又是上线前提。预算必须写死，不能靠「应该够」。

### R-10 每个工单可追溯、可复跑、可叫停

- **做法**：每单一个证据目录，含消息原文、分诊结论、提交号、门禁输出、部署与核验日志、卡片时间线。
  群里发「停止」即清队列，并回滚未完成的上线。
- **涉及**：证据目录、日志、卡片。
- **测试入口**：证据写入用纯函数生成索引，单测覆盖字段完整性。
- **验收**：`[ ]` 任一历史工单能只靠证据目录复述全过程 `[ ]` 停止指令 30 秒内生效 `[ ]` 密钥类字段零出现
- **难点**：模型往返内容可能含真实业务数据，落盘前必须脱敏，口径沿用 `desensitize.sql` 与 `verify-quality.mjs`。

### R-11 迁移类改动不进自动链路

- **做法**：候选只要含 `prisma/migrations/` 变更，**一律拒绝自动上线**，工单落 `needs_human`。
  迁移必然对生产库执行 DDL，与「不准动生产库」直接冲突，故不设「预检后放行」。
- **涉及**：候选差异检查、工单闸门、卡片提示。
- **测试入口**：给一个只改前端、一个含新迁移目录的候选，断言前者放行、后者拦下。
- **验收**：`[ ]` 含迁移的候选不部署 `[ ]` 卡片写明「需人工执行迁移」`[ ]` 拦截发生在构建之前
- **难点**：`prisma migrate deploy` 在部署脚本里是无条件执行的；即使没有新迁移它也是安全空转。
  这条要求的实质是**保证「没有新迁移」这个前提为真**，而不是给迁移加预检。

### R-12 超时保护（原「成本与滥用上限」）

- **做法**：不算 token、不设每日工单上限（用户 2026-11-13 明确取消）。只保留进程外硬超时，
  防止跑飞的进程把 2 核占死。
- **涉及**：进程外监督、超时。
- **测试入口**：一次注入超时的用例。
- **验收**：`[ ]` 超时的工单终止且不回退已上线版本 `[ ]` 超时后不留孤儿进程 `[ ]` 线上仍可用
- **难点**：超时要在**进程外**监督。Agent 自己退出这件事不能作为前提，跑飞正是它退不出的情形。

## 5. 整条链怎么走

| 顺序 | 执行者 | 输入 | 终点 |
|---|---|---|---|
| 1 | 飞书长连接 | 群内 @机器人 消息 | 消息落库，`message_id` 去重 |
| 2 | 工单服务 | 消息原文 | 分诊结论；不完整则追问卡片并结束 |
| 3 | 调度器 | 分诊通过的工单 | 入队；资源不足则排队 |
| 4 | Agent | 工作区分支 + 任务书 | 一个提交 |
| 5 | 门禁一 | 候选构建 | 冒烟结果 |
| 6 | 门禁二 | 脱敏库 | 集成与契约测试结果 |
| 7 | 部署 | 候选发布包 | 切换 + 核验，或回滚 |
| 8 | 工单服务 | 全部证据 | 卡片终态 + 证据目录 |

状态机固定为九态，不新增：
`received → triaged → queued → building → gated → deploying → done`，
异常侧 `needs_info`、`failed`、`rolled_back`。

## 6. 固定设计边界

1. **D1 「原地热重载」= 目录切换 + PM2 重启。** 不引入 Next.js HMR，不做进程内热替换。
   词面与 `docs/SelfEnvolvingTry/` 里的「热重载」是两回事，那里指工具快照指针切换。
2. **D2 生产目录继续不是 Git 工作区；Git 只存在于 Agent 工作区。** 这是对部署标准:8 的**追加**而非推翻。
   `/opt/dilee/app` 仍只由发布包写入；`/opt/dilee/agent/repo` 是新增的、与生产隔离的工作区。
3. **D3 飞书选长连接，不选回调。** 只要求出站；实测可达；不占 80、不改 nginx、不进 3 秒预算。代价是单实例，见 D4。
4. **D4 单实例、单车道。** 长连接是随机投递，多副本会丢事件；机器也只有 2 核。一次只跑一个工单，其余排队。这把两个约束一次解决。
5. **D5 串行是资源决定，不是保守。** 构建实测 10 分钟占满 2 核；并行两单必然把 swap 打满并拖慢线上。
6. **D6 为 Agent 单独装 Node 24。** 两个 DSH 包声明 `engines >= 24.9.0`，`runtime-contract.ts:3` 硬拒低于 24.9.0。
   实测 22.23.2 能跑，但这是不受支持的运行时，不据此省事。
7. **D7 复用现有部署四件套，不重写。** 新增的只是 Linux 侧打包：`git archive` → 写 `RELEASE_VERSION` → tar。`remote-*.sh` 一行不改。
8. **D8 脱敏库在服务器侧生成。** 现有取快照脚本只有 Windows 版。
   新增 Linux 等价路径：导出 → 还原到 `*_test*` 库 → 跑现有 `desensitize.sql`。脱敏口径不新写。
9. **D9 回滚只回代码，不回迁移。** 迁移必须前向兼容；迁移前的预检是 R-11，回滚后仍需人工确认数据面。
10. **D10 门禁顺序固定且失败即止**：冒烟 → 单测/类型 → 脱敏集成 → 契约 → 上线 → 核验 → 回滚。任一步失败不进下一步。
11. **D11 审批策略固定 `never` + `workspace-write`。** 常态路径不允许出现需要人批准的调用；出现即视为设计缺口，修工具而不是放宽策略。
12. **D12 证据先脱敏后落盘。** 沿用 `verify-quality.mjs` 的 `password|token|cookie` 脱敏与快照脱敏的字段口径。
13. **D13 唯一的硬黑名单：不准动生产库**（用户 2026-11-13 拍板）。具体含义：
    不写入生产库、不执行迁移、不动 `app-postgres-1` 容器与数据卷、不删 `/opt/dilee/db-snapshots`、
    不对生产库跑任何 DDL。**读**生产库仍允许（`pg_dump` 只读取快照是脱敏库的来源）。
    备份目录 `app.backup-*` 与 `app.failed-*` 的清理**可以**自动化，那不属于生产库。
14. **D14 除 D13 外全部放开，不设白名单。** 代码、前端、后端、配置、样式、导出、权限判断逻辑都可以改。
    判定方式由反例定义：只有「需要动生产库」这一条会拦。原「首批白名单」清单作废。
    出现问题用回滚兜底（R-7），而不是用准入清单预防。

## 7. 施工阶段

### Phase 1 — 这台机器扛得住一次完整闭环吗

**状态**：已完成（2026-11-13）。实测报告见
[Phase 1 实测报告](../test/results/2026-11-13-phase1-resource-measurement.md)。

**结果**：能构建，但构建期 health p95 从 46 ms 劣化到 826 ms，峰值出现 5 秒超时，
可用内存最低 152 MB，swap 峰值 2093 MB。构建全程不碰生产库与生产 API。
结论是**带约束通过**：构建必须挑时间，且先解决 `npm ci` 的内存峰值。

**覆盖**：R-9 不和线上抢资源；为 R-4、R-5、R-6 探路。

**目标**：在一个隔离目录里跑通「打包 → 构建 → 起临时实例 → 冒烟 → 收工」，全程旁观线上 API 延迟。

**任务**

- 装 Node 24 到独立前缀，与线上 22 并存，验证互不影响
- 写 Linux 侧打包脚本，产物结构与现有发布包一致
- 起临时实例到备用端口与脱敏库，打一轮最小冒烟
- 构建期间连续采样线上 health 延迟与可用内存，记录曲线
- 记录磁盘增量的实际值，给出可保留份数

**证明**：一份实测记录：构建峰值内存、swap 峰值、线上 p95 偏移、一次闭环的墙钟与磁盘增量。
**本阶段不做**：飞书、Agent、上线。

### Phase 2 — 消息进得来，卡片回得去

**覆盖**：R-1 群消息进得来，结果回得去；R-2 语句不准确时不开工。

**目标**：在群里 @机器人 说一句话，收到一张带分诊结论的卡片；再发一次同一条消息，不产生第二张卡。

**任务**

- 建飞书自建应用，只申请「仅 @我」与「以应用身份发消息」两项
- 起长连接服务，消息落库，`message_id` 去重，留存 24 小时
- 写分诊纯函数，用历史缺陷语料做表驱动单测
- 发卡片、更新卡片，按状态换标题与颜色
- 加「停止」口令与每日上限

**证明**：群里真实走一遍：@ → 卡片 → 重投不重复 → 含糊消息被追问 → 停止生效。
**本阶段不做**：改代码、跑门禁。

### Phase 3 — 一个工单真的改一行代码并上线

**覆盖**：R-3 Agent 只在独立工作区改代码；R-6 通过后原地热重载上线；R-10 每个工单可追溯、可复跑、可叫停。

**目标**：一个黑名单外的真实小缺陷，从群里一句话走到线上生效，中间无人干预。

**任务**

- 建 `/opt/dilee/agent/repo` 独立 clone，按工单切分支
- 用 headless 入口跑任务，固定 `--approval-policy never` 与工作区白名单
- 提交后打发布包，走既有四步部署
- 每个工单落证据目录，卡片写提交号与核验结果
- 演练一次「停止」

**证明**：一张工单的全链路证据 + 线上 `health.build` 等于该工单提交号。
**本阶段不做**：脱敏库门禁、自动回滚、迁移预检。

### Phase 4 — 门禁变硬，失败自己退回去

**覆盖**：R-4 基线冒烟是第一道门；R-5 脱敏数据库测试是第二道门；R-7 上线失败自动回滚。

**目标**：故意让一个改动过不了门禁，工单停在 `failed` 且线上不动；再故意让切换后核验失败，60 秒内自动回到旧版本。

**任务**

- 服务器侧生成脱敏库，复用现有 `desensitize.sql`
- 接冒烟门禁与集成/契约门禁，失败即止
- 接自动回滚，演练「版本不匹配」触发
- 把门禁输出写进证据目录
- 校核回滚后数据面仍可用

**证明**：两次演练的结果：一次被门禁拦住、一次被回滚救回，线上版本号都正确。
**本阶段不做**：迁移类改动。

### Phase 5 — 黑名单护栏与资源保护

**覆盖**：R-8 无人值守仍不越界；R-11 迁移类改动不进自动链路；R-12 超时保护（原「成本与滥用上限」）。

**目标**：把 Agent 按在工作区内，越过边界就失败而不是等待；
含迁移的候选在构建前被拦下；跑飞的进程被进程外超时杀掉。

**任务**

- 做一次越界写入对抗，确认被拒且原因落证据
- 加迁移检测：候选含 `prisma/migrations/` 即拦下，工单落 `needs_human`
- 加进程外硬超时与孤儿进程清理
- 收紧备份保留份数，给出磁盘回收规则
- 补一份无人值守的 runbook 与人工接管步骤

**证明**：对抗用例与超时用例落 `failed` 且线上不受影响；含迁移候选零部署。
**本阶段不做**：把迁移处置权交给 Agent（D13 硬黑名单，永久保留在人）。

### Phase 6 — 常态化与交接

**覆盖**：加固 R-10 每个工单可追溯、可复跑、可叫停。

**目标**：连跑两周不出事，且下一个人能只靠文档接管。

**任务**

- 每日一页工单汇总：进了几单、成了几单、退回几单、回滚几次
- 把设计文档、状态机与证据目录格式写进 `.agent/` 下的运维标准
- 补 `docs/log/` 的日常记录模板
- 复核黑名单：确认「不准动生产库」这条仍然够用，且没有需要追加的第二条

**证明**：两周记录 + 一份可被第三人独立执行的接管清单。
**本阶段不做**：多机、多群、并行。

## 9. 失败与回退矩阵

| 失败点 | 处置 | 线上影响 |
|---|---|---|
| 长连接断开 | 自动重连；断连期消息靠飞书 4 次重投，仍可能丢 | 无 |
| 分诊判错 | 卡片可人工改判，改判后重新入队 | 无 |
| 构建失败 | 工单 `failed`，不迁移不切换 | 无 |
| 冒烟失败 | 同上 | 无 |
| 脱敏库门禁失败 | 同上 | 无 |
| 迁移失败 | 既有 P3018 恢复流程，人工介入 | 可能需停机 |
| 切换后核验失败 | 自动回滚到上一 `app.backup-*` | 短暂中断 |
| 超时 | 进程外监督终止，工单 `failed` | 已在线的版本不回退 |
| Agent 越界 | 调用被拒，工单 `failed` | 无 |
| 候选含迁移 | 构建前拦下，工单 `needs_human` | 无 |
| 改错了但测试没抓到 | 用户反馈 → 新工单 → 回滚或再修 | 视缺陷而定 |
