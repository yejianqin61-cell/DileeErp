# 其他应付批量导入（2026-09-16）

## 来源需求

> 「财务模块，应付管理，因为有一些非原料类的支出。也就是其他应付现在要支持批量导入这类应付对账条目。
> 我们提供模板，用户填写上传。直接进入应付对账。然后再流转到确认应付。」

已与用户确认的三条口径：

| 问题 | 用户选择 |
| --- | --- |
| 「直接进入应付对账」的落点 | **只生成应付草稿条目**（与页面上的「新建其他应付」同形），它们立刻出现在【应付对账 → 待创建对账】，也可以在【确认应付】勾选批量确认 |
| 供应商池里没有的对方 | **自动建进供应商池**（按名称建档、编码自动生成），并在导入结果里列出建了哪些 |
| 模板列 | 供应商编码 / 供应商名称 / 应付金额 / 币种 / 费用说明 / 确认日期 / 备注（**七列**；提问时我写成了「六列」，实际按这七列实现） |

## 一、为什么是「草稿」而不是「对账单」

系统里的付款流转是两段式的：

```
其他应付/原料入库应付 ──(接收)──> 应付草稿 ──(创建对账)──> 对账单 ──(确认)──> 已付（钱从账户出去）
                                        └────────(确认应付：勾选批量确认)────────┘
```

「确认应付」本来就能直接勾选草稿批量确认（不需要非得先有对账单），所以导入只要产出**草稿**，
两条下游路径就都通了。这也让「批量导入」与「逐条新建其他应付」在数据上完全一样 ——
财务在对账/确认里看不出这条是导入的还是手填的，这正是我们要的（同一种东西不该有两种形状）。

## 二、模板与解析口径

导入模板（`GET /finance/payable-entries/import-template.xlsx`）两页：数据页（表头 + 两行示例）
与「填写说明」。列口径：

| 列 | 必填 | 规则 |
| --- | --- | --- |
| 供应商编码 | 与名称至少一个 | 先在供应商池里按编码匹配（忽略大小写与空格） |
| 供应商名称 | 与编码至少一个 | 编码没命中时按名称匹配（忽略大小写与空格）；都不命中 → 自动建档 |
| 应付金额 | ✅ | 必须大于 0；容忍千分位、货币符号、全角数字与数字单元格（`1,200.00`／`￥1200`／`１２００` 都认） |
| 币种 | | 留空按 CNY；认 人民币/美元/欧元/港元/日元 与 3~10 位字母代码；**乱写会报错而不是静默按 CNY** |
| 费用说明 | ✅ | 它会成为应付单的来源说明（`其他应付-<前 30 字>`），也是列表里唯一能看出「这笔是什么」的字段 |
| 确认日期 | | 留空按导入当天；容忍文本日期与 Excel 日期单元格（复用花名册那份 `parseRosterDate`） |
| 备注 | | 最多 1000 字 |

解析规则与员工花名册导入完全一致（操作员面对的是同一件事）：

- **按表头名认列，不按列序号**：挪列、加无关列都不会错位；无关列在结果里如实上报（`ignoredColumns`）；
- 表头可以在前 10 行的任意一行（有人习惯先写个标题行）；数据块到第一个空行为止，
  表尾的「说明：本表由财务手工维护」这类批注不会被当成数据；
- **整批失败只有三种**：找不到表头 / 缺必需列 / 表头下面没有数据行 —— 这时一行都不写；
- **行级错误不连坐**：其余情况通过校验的行照常导入，出错的行逐条列出（`{row, field?, reason}`，
  行号就是 Excel 里看到的行号），状态为 `partial`。

### 重复行直接拒绝

同一份文件里「同一供应商 + 同一金额 + 同一币种 + 同一日期 + 同一说明」的第二行起会被拒绝，
并指出「与本文件第 N 行重复」。理由很直白：**重复入账等于重复付款**，比少导入一行危险得多。
（跨文件的重复不能靠这一条拦 —— 见 §五 已知缺口。）

### 供应商自动建档

用户选择「认不到就自动建」，于是规则是：**编码匹配 → 名称匹配 → 建一个新的**。
新建时编码走平台统一的 `SUP-当天日期-序号`（`daily-sequence-code.ts`，与物料 `MAT-`、
客户 `CUS-` 同一套），同一批内同名（忽略空格与大小写）只建一个，并在结果里回报：

```
新增供应商：上海房东（SUP-20260916-0002，3 条）：请到【采购 → 供应商池】补联系方式
```

同时写 `supplier.create_from_payable_import` 审计 —— 财务的导入会改动采购模块的主数据，
这件事必须在审计里看得见（将来要查「这个供应商是谁建的」）。

## 三、写库是原子的（与花名册导入的唯一区别）

花名册导入按 200 行一批写、一批失败退化成逐行独立事务；**这里刻意不这样**：

- 通过校验的行在**一个 `$transaction`** 里建供应商 + 建应付草稿，**要么全进、要么全不进**；
- 金额行最怕「半个文件进去了」，用户重传一次就变成重复记账；
- 逐行错误仍然逐条回报 —— 那是**校验阶段**的事，与写入阶段无关。

代价：写库阶段任何一行因数据库原因失败（例如并发下自动编码撞唯一约束）会让整批回滚，
用户需要重传。这是有意的取舍（宁可不写，也不要写一半），已写进日志的已知缺口。

## 四、接口与前端

| 路由 | 说明 |
| --- | --- |
| `GET /finance/payable-entries/import-template.xlsx` | 模板下载（附件名用 `filename*=UTF-8''`） |
| `POST /finance/payable-entries/import` | multipart（字段名 `file`），10MB 上限，只放行 `.xlsx/.xls` |

**路由顺序陷阱**：`payable-entries/import-template.xlsx` 必须声明在 `payable-entries/:id`
**之前**，否则会被 `:id` 当成一个 id 匹配掉（`payable-entries.xlsx` 之所以不受影响，
是因为它的段名与 `payable-entries/:id` 不同）。Nest 按声明顺序匹配，顺序即优先级 —— 已写在代码注释里。

权限：只要求 `finance` 模块权限，不额外要求管理员 —— 与「新建其他应付」同权限。
批量只是同一件事的批量入口，不该变成另一档权限。

前端入口在【应付管理 → 确认应付】的工具条上，紧挨着「新建其他应付」
（那是「其他应付」唯一的现有入口；导入结果里给一条「去应付对账 →」把两条下游路径接上）。
弹窗内容：下载模板 + 选文件 + 结果面板（行数统计 / 缺列 / 忽略列 / 新增供应商 / 提示 / 逐行错误表）。

**为什么不做成一条 toast**：「第 7 行金额不合法」这类信息必须能被逐条看清，否则操作员只能瞎猜。
文案遵守财务页第①条要求（2026-09-16）——**只留数据与去处，不写说明性句子**。

## 五、已知缺口 / 未做

- **重复上传同一份文件会重复建草稿**：草稿是可删的，但没有「导入批次」这个概念，
  也就没有幂等键。若实际使用中经常重传，下一步应加导入批次号（落进 `extension_data`）并据此去重。
- **币种不校验字典**：与「新建其他应付」一致（那里也不校验），认不出的写法在批量里会报错，
  但认得出的任意 3~10 位代码都会收下。要不要按币种字典收紧需要业务确认。
- **并发下自动建档可能撞编码**：两个财务同时导入、各自新建供应商时，`SUP-当天-序号` 可能撞唯一约束
  → 整批回滚（不会写一半）。真实并发量极低，故未加换号重试。
- **没有「撤销这次导入」**：只能逐条删除草稿。
- **附件不能导入**：模板没有附件列；其他应付的 `attachment` 字段导入时为空数组。
- **只在单测层验证**：本机无 PostgreSQL，`$transaction` 的真实回滚、`SUP-` 编码在并发下的唯一约束
  都只有单测（手写 Prisma 替身）覆盖；Excel 文件也没有在真实 Excel/WPS 里打开过。
- 与花名册导入共用 `parseRosterDate` / `textCell`（从 `modules/production/employee-roster.ts` import）。
  跨模块引用一个纯函数是权宜：**若将来出现第三个使用者，应把这两个函数提到公共工具模块**
  （如 `platform/xlsx/excel-cells.ts`）再各自引用。
