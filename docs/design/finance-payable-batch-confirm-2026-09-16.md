# 应付「勾选批量确认」与财务界面文案精简（2026-09-16）

## 来源需求（用户原话）

1. 「财务部分，这种说明性的语句，全部去掉。比如说每次成品出库过账生成一条应收来源；
   一个订单分批出库就是多条，双击查看全部字段」
2. 「应付管理，原料入库条目这边，已接收的条目，就不要在这边的表单出现了。」
3. 「确认应付这边，就不要再搞那么多繁琐的步骤了。不要又是登记付款又是确认应付了。
   直接就是支持勾选，批量确认。」

## 一、文案口径（需求 1）

### 删掉什么

| 类别 | 例子 |
| --- | --- |
| 页面/板块/子栏目的 `description` | 「每次成品出库过账生成一条应收来源；一个订单分批出库就是多条，双击查看全部字段」 |
| `panel-heading` 里解释功能的说明句 | 「上半张「应付台账」= 欠供应商多少（负债事实）…」 |
| 独立的说明段落 `<p class="panel-note">` | 「负债事实：一笔应付 = 一个来源批次…」 |
| `EmptyState` 的 `description` | 「接收应付来源后，尚未纳入对账单的草稿条目会逐条列在这里。」 |
| 双击详情弹窗的 `description` 与 `sections[].note` | 「双击列表行打开的详情：展示该条目的全部字段与当前可执行操作。」 |
| 表单字段 label 里的解释性括注 | 「入账银行（可选；账户在「财务 → 银行账户」里维护）」→「入账银行（可选）」 |
| `type: "info"` 确认文案里的说明句 | 「将确认应收 AR-001（120 USD），并把该金额记入下面选定的银行账户。确认不可逆。」 |

### 保留什么（有意保留，不是漏删）

- **数据本身**：「共 N 条」「待接收 3 条 · 已接收 1 条」「合计 800.0000 CNY」这类计数与金额。
  说明句被替换成数据，而不是整块删掉 —— 用户要的是「别解释」，不是「别告诉我」。
- **校验规则类括注**：「（金额与来源不一致时必填）」「（必填）」「（可选）」。这些直接决定用户怎么填。
- **确认弹窗里的「几条 / 多少钱」**：`type: "info"` 字段保留，但只留数据（`确认 2 条草稿应付（合计 800.0000 CNY）`）。
  不可逆动作前「看得见要动多少钱」是安全底线，不是说明书。
- 表格列头、按钮文案、状态文案、错误提示、toast、权限报错。

### 为什么

同一个界面上长期堆着两类文字：一类是**数据**（有几条、多少钱、什么状态），
一类是**说明书**（这个模块怎么运作、你该怎么用）。第二类只在第一次看的时候有用，
之后每天读一遍就是噪音；用户已经用过十几轮，明确说「这种说明性的语句全部去掉」。
但把它们全删会把第一类也带走（例如「待确认应收 3 笔 / 合计 120.00」），所以规则是
**把说明句换成数据，而不是删掉这一行**。

## 二、已接收的来源不再出现在「待接收」列表（需求 2）

### 问题

`原料入库条目` / `外加工签收` 两个子栏目是**待接收工作清单**，但列表返回的是**全部**来源：
已接收的行也照样列着，只是把「接收应付」按钮换成了「应付单 AP-xxx（状态）」。
对财务来说这是噪音 —— 一条来源接收完就应该从待办里消失，它已经变成应付草稿（在
「应付对账 / 确认应付」里），留在原处只会让人再点一次「接收应付」。

### 做法

- 判定：`awaitingReceipt(item) = !item.payable_entry && item.status === "pending_finance"`。
  两个条件都要，因为历史数据里存在「来源状态停在 `pending_finance` 但已经有应付单」的行
  （接收动作曾经不推进来源状态，见 `supplier-payable.service.ts` 的 `markSourceReceived` 注释）。
- **两个子栏目同规则**：用户只点名了「原料入库条目」，但外加工签收是同一类待办清单，
  只改一个等于把同样的噪音留在隔壁一栏。
- **计数里点名**：面板标题旁显示「待接收 N 条 · 已接收 M 条」。
  行被隐藏但总数不隐藏 —— 否则「我明明接收过，怎么列表里一条都没有」会变成新的困惑
  （第十二/十三轮反复修过「东西不声不响地消失」这一类反馈）。

## 三、确认应付：勾选 + 批量确认（需求 3）

### 问题：确认即记账之后，「登记付款」是把同一笔钱再扣一次

第十三轮按用户要求把「确认应付」改成**确认即记账**：确认时金额作为一笔支出写进收支流水，
落到所选银行账户上（银行余额减少）。但页面里同时保留了原来的「登记付款 → 过账/核销」：
付款单过账时 `SupplierPaymentService.post` 会 `autoCreateFromPayment` **再写一笔支出流水**。
两条路都走一遍，同一个供应商的同一笔应付会让银行账户少两次钱。

这不是「步骤多」的问题，是**重复记账**。用户的原话正是「不要又是登记付款又是确认应付了」。

### 做法

- 「确认应付」子栏目变成**一张台账 + 勾选 + 批量确认**：
  - 表格首列是勾选框（**只有草稿行有**，已确认/冲销的行没有勾选框）；
  - 表头复选框 = 全选当前筛选出的可确认草稿；
  - 工具条显示「已选 N 条」并提供「批量确认（N 条）」按钮（未勾选时禁用）；
  - 弹窗只问两件事：**支付银行**与**收支项目**（整批共用一个），并显示「确认 N 条草稿应付（合计 X）」。
- 移除台账行内的「登记付款」，移除「付款」子表与它的折叠开关。
- 行内「确认应付」（单条）**保留**：勾一条再批量确认也是同一条路，单条只是个快捷方式，
  两条路走的是同一个 `confirm` / `batchConfirm` 记账口径。

### 后端契约

`POST /finance/payable-entries/batch-confirm`

```jsonc
// 请求
{ "ids": ["uuid", "..."], "bank_id": "uuid|null", "cash_flow_item_id": "uuid|null" }
// 响应
{
  "ids": ["实际确认的 id"],
  "confirmed_count": 2,
  "skipped_count": 1,
  "amounts": [{ "currency": "CNY", "amount": "800.0000" }],
  "cash_flow_entry_ids": ["cf-1", "cf-2"],
  "bank_missing": false
}
```

决策：

- **D1 每条应付各写一条流水**（与 `ReceivableService.batchConfirmByOrder` 同一口径）：
  一笔应付 = 一个来源批次，每条都有自己的单号；合并成一条流水就再也追不回是哪批料的钱。
- **D2 整批只问一次账户与项目**：用户要的是「不要繁琐」，逐条填 8 遍银行账户正是繁琐本身。
- **D3 跳过而不是整批失败**：只确认 `status = draft` 的条目；已被另一个入口先确认掉的、
  来源已作废的计入 `skipped_count` 并在提示里点名。整批失败会让「3 条里 2 条能确认」变成干不成事。
- **D4 一条都不能确认时 422 `NO_DRAFT_PAYABLES`**：静默返回「确认 0 条」会让用户以为点过了。
- **D5 `ids` 为空 422 `PAYABLE_IDS_REQUIRED`**：空数组是界面出问题，不是「确认了 0 条」。
- **D6 银行/项目**在事务之前**先校验**一次（`requireActiveBank` / `requireItem`）：
  等事务提交完才发现银行已停用，应付已经确认、流水却没写。
- **D7 状态被并发改动时整批回滚**（`PAYABLE_CONFIRM_CONFLICT`）：行锁之下本不该发生；
  真发生了宁可整批拒绝，也不要「界面说确认了、库里没确认」。
- **D8 合计按币种分组**（`amounts: [{currency, amount}]`）：跨币种相加得到一个没有意义的数，
  与财务报表「不跨币种相加」同一口径。
- **D9 `bank_missing`**：没指定银行时流水照写（收支事实不能丢），但响应带 `bank_missing`，
  界面必须给**错误态**警告而不是一句成功。

### 台账不再显示「已付 / 未付」

这两列来自**付款单核销**（`allocations`），而本轮已经把付款流程从确认页去掉。
留着它们的唯一效果是：每条已确认的应付都显示「未付 = 全额」，与「钱已经从账户支出去了」自相矛盾，
而且这个数字永远不会再变（界面里没有能改变它的操作了）。付款核销明细仍在**双击后的详情**里，
数据没有丢。

### 接口与数据没有删

`/finance/supplier-payments` 全套接口、`supplier_payment_allocations`、对账单的
`paymentAmountSnapshot` 全部**保留**：历史核销数据、采购侧「通知财务付款」、报表都还依赖它们。
本轮去掉的只是「确认应付」页上的入口。

## 四、应收侧本轮不动（需要业务确认）

「确认应收」也有同样的形状：确认时记一笔**收入**流水，同时页面里还留着「登记收款 → 过账核销」
（再记一笔收入）。用户本轮只说了应付，所以应收侧只做了需求 1 的文案精简，
结构保持原样。**要不要把应收也改成同款「勾选 + 批量确认」，需要业务确认**。

## 五、已知缺口

- **没有在真实 PostgreSQL 上验证**：本机没有可用的 PostgreSQL，`batch-confirm` 的事务行为
  （逐条行锁 + `updateMany` 计数校验）与 `ids` 参数只经过单测与类型检查。
- **没有真实数据库迁移**：本轮**不改 schema**，因此没有新迁移。
- **批量确认没有「一张批量凭证」**：N 条应付 = N 条流水。要做「一批一条汇总流水」需要新的凭证概念。
- **全选只覆盖当前筛选结果**：不是跨页全选（表格是前端分页）。
- **部分付款没有入口了**：付款 API 还在，但界面上不再有建付款单的地方。
  如果业务需要「先付一半」，要么给付款单一个新的入口，要么让确认支持「本次确认金额」。
- **文案精简会影响培训材料**：所有引用界面说明文字的文档都需要同步。本仓库内已同步这几处
  （把「页面上写明了 X」改成「X 只由文档承载」）：`accounting-vouchers-2026-09-15.md`（凭证不做图片）、
  `bank-account-pool-page-2026-09-15.md`（结算账户字典 vs 银行账户池）、
  `bank-balance-and-transfer-2026-09-16.md`（没指定银行的钱不进余额）、
  `supplier-code-and-procurement-stock-granularity-2026-09-15.md`（应付台账 vs 付款）；
  仓库外的培训材料/操作手册需要人来同步。

## 六、人工验收步骤（需要真实库）

1. 原料入库过账 → 财务「应付管理 → 原料入库条目」看到这行 → 点「接收应付」；
   刷新后该行**从列表消失**，标题旁显示「待接收 0 条 · 已接收 1 条」，应付草稿出现在「应付对账」。
2. 同供应商同月份建 3 条草稿应付 → 进「确认应付」→ 勾选全部 3 行（或点表头复选框）→
   工具条显示「已选 3 条」→「批量确认（3 条）」→ 选支付银行 → 提交：
   - toast 显示「已确认 3 条应付（合计 X CNY）」；
   - 「财务 → 银行账户」里该账户余额减少 X；
   - 「收支管理」里出现 **3 条**支出流水，每条各自带应付单号，银行账户为所选账户；
   - 「财务报表 → 收支明细表」按 3 行统计，收支项目与银行账户两列有值。
3. 不选银行再批量确认一次：流水照写（3 条），但 toast 是**错误态**且写明「不会体现在任何银行账户余额里」，
   账户余额不变。
4. 勾选里混入一条已被别的窗口确认掉的应付：提交后提示「跳过 1 条」，其它条正常确认，且没有重复流水。
5. 台账行内确认单条 → 与批量确认走同一口径（一条流水、余额减少对应金额）。
6. 全站检查财务页面：不应再出现任何「解释这个模块怎么运作」的成句说明；
   计数、金额、状态、按钮一个不少。
