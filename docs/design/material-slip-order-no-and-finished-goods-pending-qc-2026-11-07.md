# 领料单导出件补订单号 + 成品质检「所有待质检列表」

- 日期：2026-11-07
- 用户原话（两条，原文照录）：
  1. 「采购板块，领料单的导出件也要有订单号」
  2. 「成品提交质检入库，成品质检页面要显示所有待质检列表」

## 0. 两条需求的落点（先对齐「是什么」）

### 需求 1：领料单导出件补订单号

- 全站只有**一处**「领料单导出」：`GET /production/reports/material-issue.xlsx?movement_id=…`（批量是同前缀
  `material-slips.xlsx`），纸张版式在 `MaterialSlipExportService`（`apps/api/src/modules/production/material-slip-export.service.ts`）。
- 用户口中的「采购板块」在本系统里指采购/原料这一片（领料单入口在【仓库 → 原料流转】与【生产单详情】，
  同时被采购/仓库人员使用）；**采购单导出件早就印了「订单号」**（`purchase-order-export.service.ts` 的
  「订单号：销售单号（货号）」），只有领料单/补料单的纸头缺这一格 —— 所以本条 = 给领料单（连带补料单）
  的导出件补「订单号」。
- 数据源现成：`MaterialIssueDocument.orderNo` / `MaterialReplenishmentDocument.orderNo` 本来就组装好了
  （来自 `productionOrder.orderNo`），只是排版没用它。

### 需求 2：成品质检页面显示所有待质检列表

- 现状：`/qc/finished-goods`（`components/qc/finished-goods-qc-panel.tsx`）只有「按订单号查询 → 订单详情」，
  页面底部原是一句占位说明「全部订单概览：请选择订单号进入二级详情」。质检员**必须先知道订单号**才能看到
  要检什么，跨订单的待检工作量在页面上完全看不见。
- 目标：页面顶部常驻一张**跨订单的「待质检列表」**，列出所有已提交质检、尚未检完的成品送检单，
  一行一个待检批次，可直接「录入质检」。这正是「成品提交质检入库」之后质检员要处理的那张工作队列。

## 1. 需求 1：订单号印在哪一格

### 1.1 版式变更（导出 xlsx 与打印件同一版式）

领料单/补料单的纸头是「标题 + 三行 × 4 组『标签 + 填写格』」。样例模板第 3 行第 4 组本来就**留空**
（`docs/samples/领料单-样例.xlsx` 的 `G5:J5`、`docs/samples/补料单-样例.xlsx` 的 `E7:F7`），
订单号就落在这个**预留空格**里，不动任何已有字段的位置：

| 单据 | 行 | 第 1 组 | 第 2 组 | 第 3 组 | 第 4 组 |
| --- | --- | --- | --- | --- | --- |
| 领料单 | 第 3 行（表头区第 1 行，xlsx 第 3 行） | 生产单号 | 成品名称 | 成品代码 | 规格型号 |
| 领料单 | 第 4 行 | 颜色 | 领料单号 | 领料工序 | 领料单位 |
| 领料单 | 第 5 行 | 生产数量 | 操作人 | 操作时间 | **订单号（新）** |
| 补料单 | 第 1 行（xlsx 第 5 行） | 生产单号 | 成品名称 | 成品代码 | 规格型号 |
| 补料单 | 第 2 行 | 颜色 | 领料单号 | 领料单位 | 领料工序 |
| 补料单 | 第 3 行 | 操作人 | 操作时间 | **订单号（新）** | 补料原因 |

- 领料单：`G5 = 「订单号：」`，`H5:J5` 合并后写销售订单号（与模板其它第 4 组一样跨到最后一列）。
- 补料单：`E7 = 「订单号：」`，`F7 = 销售订单号`（仍在「补料原因」左边，**补料原因不挪位置**）。
- 打印件（`components/production/material-slip-print-sheet.tsx` → `lib/material-slip-print.ts`
  的 `materialSlipHeadRows`）必须**同位置同顺序**补这一组：导出的 xlsx 与浏览器打印件是同一份单据数据，
  仓库拿纸对料时两边的格子对不上就是缺陷（2026-10-29 已经吃过「页面与纸面对不上」的亏）。
- 样例文件由 `scripts/make-export-samples.cjs` 从导出服务生成，本轮改完导出后**重新生成**两张样例，
  保持「样例 = 导出件」这条参照关系不腐坏。

### 1.2 不改的东西

- 不改明细列、不改小计、不改标题（状态仍印在标题上）、不改纸张方向（A4 纵向，`fitToWidth: 1`）。
- 不把「订单号」拼进「生产单号」那一格（那是采购单的做法：订单号 + 货号拼一格）；领料单两号都要能单独看。

## 2. 需求 2：成品质检「待质检列表」

### 2.1 行集（口径）

`GET /finished-goods/inspection-submissions` 返回的全部未删除成品送检单中，**状态为
`submitted`（已提交待检）或 `inspecting`（部分已检）** 的行。排除：

- `draft`：送检单还没提交，质检员不该看到（在下方「按订单号查询 → 订单详情 → 送检记录」里编辑/提交）；
- `qc_completed`：已检完（进入「质检合格待入库」）；
- `cancelled`：已作废。

排序：**先送检日期升序（先进先检），同日按送检单号升序**。工作队列按「谁先送来」排，不按「谁最后改过」排。

### 2.2 列（10 列 = 9 业务列 + 1 操作列；声明宽度合计 84%，另 16% 给 `auditColumns()` 的创建人/最后修改人）

| 列 | 内容 | 宽度 | 说明 |
| --- | --- | --- | --- |
| 送检单 | `submissionNo`（FGIS-…） | 9% | 唯一标识一行 |
| 订单号 | `orderNo` | 8% | 识别一行的第一眼信息 |
| 生产单 | `productionOrderNoSnapshot` | 9% | 缺货/换线时按生产单找人 |
| 成品 | `productNameSnapshot / productSpecificationSnapshot` | 11% | 长文本，省略 + hover |
| 来源 | `成品入库通知` / `外加工回厂`（历史 `厂内完工（历史）`） | 8% | 与订单详情同一套 `sourceLabel` |
| 送检数量 | `submittedQuantity unitNameSnapshot` | 7% | 数字列 |
| 已检数量 | 服务端下发的 `inspectedQuantity` | 8% | 数字列（表头必须完整可读，见下） |
| 待检数量 | 服务端下发的 `pendingQuantity` | 8% | 数字列，= 送检 − 已检（不小于 0） |
| 状态 | `submitted → 待质检` / `inspecting → 质检中` | 6% | 中文状态词 |
| 操作 | 「录入质检」按钮 | 10% | 打开质检弹窗并**预选该送检批次** |

宽度取舍：**已检 / 待检各给 8%**（1366 屏约 89px，扣 24px 内边距后 65px，放得下 4 个汉字 ≈52px）。
这两列是质检员真正要看的数，表头不能省略；代价是送检单 / 生产单 / 成品 / 来源各让 1%（它们本来就
走省略 + hover，`accessorFn` 已让 `DataTable` 挂了完整 `title`）。合计仍是 84%。

被裁掉的长文本（成品、来源）靠 `accessorFn` 让 `DataTable` 自动挂 `title`（写法与订单详情那三张表一致）。

### 2.3 数据口径放服务端

`FinishedGoodsQcService.listSubmissions()` 每行**新增两个字段**（加字段，不改旧字段，既有调用方不受影响）：

- `inspectedQuantity`：该送检单下 `status = active` 的 QC 记录 `inspectedQuantity` 合计
  （**只算 active**：更正后的 `corrected` 记录不能重复计入，与 `createQcRecord` 的累计校验同一口径）；
- `pendingQuantity`：`max(送检数量 − inspectedQuantity, 0)`，字符串十进制（最多 4 位小数，与全站数量口径一致）。

为什么不让前端自己从 `qcRecords` 求和：累计口径只允许有一份实现（服务端创建/更正/列表三处共用同一份
「active 合计」语义），前端再算一遍就会出现「列表说还能检 2，点进去服务端说超量」的分叉。

### 2.4 页面交互

- 位置：`成品质检` 面板**第一个** panel-body，标题「待质检（全部订单）」+ 一句口径说明 + 「共 N 张」；
  替换页面底部原来那句「全部订单概览：请选择订单号进入二级详情」的占位说明（它的指引并进本块说明里）。
- 行操作「录入质检」：直接打开 `录入成品质检：<订单号>` 弹窗，并把「订单内送检批次」**预选为这一行**
  （`openQc(orderNo, { submission_id })`，沿用现有入口，不新开一套弹窗）。
- 双击行：进入下方「订单详情：<订单号>」（`loadOrder`），三张明细表该订单的成品来源 / 送检记录 / 质检记录。
- 空态：标题「暂无待质检的成品送检单」，说明写清「成品入库通知送检后要在送检记录里点『提交送检』，
  才会进入这里；草稿送检单在下方按订单号查询的订单详情里编辑」。
- 刷新：沿用现有 `load()`；同页其它面板写入后 `subscribeQcDataChanged` 已会重拉，无需新增通道。
- 删除底部「全部订单概览」占位块：它唯一的用途就是告诉用户「要按订单号查」，现在待质检列表 + 按订单号查询
  两块已经把这件事说清楚，留着只会多一块空面板。

### 2.5 后续变更（2026-11-09）：通知不再"隐形"，但没有混进这张表

用户 2026-11-09 又反馈「生产包装工序完成后提交成品入库通知，进入到成品质检，成品质检页面没有显示
这条记录」。原因正是 §4 第一条当时刻意不做的那个队列：通知不是送检单，两步「创建送检 → 提交送检」
没做完时，上面这张表一条都不显示（线上 3 张 `pending` 通知就是这样）。2026-11-09 的处理：

- 新增**独立**的「待送检（成品入库通知）」表（T25，叠在本表之上），数据仍取自
  `GET /finished-goods/qc/sources`（面板已有请求，不新增请求），行内「送检」= 建单 + 提交
  在一个事务里完成（`POST /finished-goods/inspection-submissions` 的 `submit: true`）；
- **没有把通知混进本表**：通知还没有「本次检验数量」，混排会让已检/待检两列一半是「—」；
- 所以 §4 第一条「不做待送检跨订单列表」已被本轮取代（做成了独立队列），其余非目标不变。

详见 `docs/design/finished-goods-overview-order-no-and-pending-notice-qc-2026-11-09.md` §2。

## 4. 没做 / 非目标

- 不做「待质检」的批量操作（批量录入、批量判定）：一次质检的数量配平必须逐单核对。
- 列表不显示来源单号（通知单号/批次）：送检单 DTO 里只有 `sourceId`（UUID）；要看通知号/批次，
  双击进订单详情的「成品来源」表即可。真需要再加字段，不在这一轮硬塞。
- 不做「待送检」（成品来源里可送检但还没建送检单）的跨订单列表；那是另一个工作队列，用户这轮说的是
  「提交质检之后」的待检列表。（**2026-11-09 已改为独立队列**，见 §2.5；本表仍不混排。）
- 不新增/修改任何 API 路由；只给现有 `GET /finished-goods/inspection-submissions` 加两个响应字段。
