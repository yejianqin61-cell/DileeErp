# 采购单收束与编辑：待确认事项（2026-09-17）

> 本轮设计见 [采购单「收束」与「编辑」](../design/purchase-order-collapse-and-edit-2026-09-17.md)。
> 开工前问过的四个问题用户已全部选定，**下面这些是开工过程中新冒出来的、需要业务拍板的口径**。

## 已确认（本轮开工前）

1. **保存草稿也按供应商收束**：几个供应商就落几张草稿，一家一张。
2. **可编辑范围**：草稿自由编辑；已下单但没有任何到货的也能直接编辑（必填原因、留审计）；
   已有到货/质检/入库/应付事实的只能改打印信息。
3. **「下单状态」列**：四态（未下单 / 草稿中 / 部分下单 / 已下单足量），带累计数量 + 采购单号。
4. **收束时还有行没选供应商 → 阻断**，报出第几行，一行都不下单。

## 已确认（用户看到上面四条之后补充）

5. **「导入 BOM 明细，也视为对采购单的编辑，允许保存」**：草稿允许有「还没选供应商」的行，
   它们单独落成一张供应商为空的草稿，选好之后再收束。第 4 条只在**下单**时生效。
   代价是 `purchase_order_items.supplier_id / supplier_snapshot` 改回可空
   （迁移 `20260920120000_...`），「一个供应商一张单」的不变式改由**下单门禁 + 写入门禁**保证。
6. 用户对上面第 5 条之外的事项回复「**其他的都按照你的建议来**」，即以下六条按本文档的建议执行
   （1、2、4、5、6 条都维持现状，第 3 条同样维持：改过的已下单单只留审计、不提示重发）。

## 待确认

### 1. 「已下单」列只对 BOM 内的行有效 —— 补料要不要也看得到？

现在的统计口径是 `purchase_order_items.bom_item_id`，也就是「这一行是从 BOM 带进来的第几行」。
手工添加的行（补料、替代料）没有 `bom_item_id`，所以永远显示「BOM 外新增」，
**看不出这个物料到底买过没有**。

- 建议：先按现状（口径干净、不会误报）。补料行本来就该靠「当前库存量」判断。
- 若要覆盖补料：改成按「物料 + 订单号」归集，代价是同一物料在不同供应商/不同用途下会被算到一起，
  需要先定清「同一个物料在这个订单上买两次算不算重复采购」。

### 2. 第 1 组沿用原单的「第 1 组」是按什么顺序定的？

按明细行的先后顺序，也就是**第一行明细的供应商**拿到原来那个采购单号。界面上会写明
「第 1 组沿用本单单号 PO-XXXX」。

- 建议：维持（对操作者无感 —— 单号本来就不是给人挑的）。
- 若要固定：可以改成「行数最多的一组」或「金额最大的一组」沿用原单，但那是猜业务意图，不建议。

### 3. 已下单的单被改过之后，要不要提示「需要重新发给供应商」？

现在改完只留审计（前后值 + 原因），**不会自动提醒重新打印/重发**。
`打印信息` 与导出各自独立，系统不知道供应商手里那份是什么版本。

- 这一条与上一轮（2026-09-15）留下的同一个问题相关：采购单的审计时间线还没接界面，
  出了「厂商说没收到单」的争议只能靠 `updated_at` 推断。
- 建议：等审计时间线接上界面之后一起做；现在先靠原因那几行字。

### 4. 草稿的 `purchase_split` 扩展数据要不要保留？

现在**所有**从工作区落下来的采购单（哪怕只有一家供应商）都带
`extension_data.purchase_split = { by, supplier_id, group_index, group_count }`，
沿用原单的那一组还多一个 `reused_purchase_order_no`。

- 好处：事后能追溯「这张单是收束出来的第几组」。
- 代价：单供应商的普通单也带着这段元数据（不影响任何计算与展示）。
- 建议：保留。真要去掉，得区分「收束」与「普通建单」两条写入路径，反而更容易漂移。

### 5. 收束的粒度是「整张草稿」还是「勾选的行」？

工作区里有逐行复选框，但那个复选框现在只服务「移除选中行」。
收束时是**整张草稿的全部行**一起按供应商分组。

- 若业务想要「先只下其中几家」：可以按勾选的行收束，未勾选的行留在草稿里 ——
  但那样必须给「没收束的行」一个落脚处（留一张草稿），否则会丢单。
- 建议：先维持整张。需要分批下单时，把不要的行移除即可（移除只改草稿，不动 BOM）。

### 6. 重新带入 BOM 明细会**静默丢掉**手工添加的行 —— 要不要先问一句？

「带入 BOM表明细」开关是「是」的时候，选一次 BOM 就把草稿明细**整体替换**成 BOM 的全部行；
开关从「否」拨回「是」同样会重建。也就是说：**先把行加好、再去选 BOM，那几行会无声消失**。

这是本轮之前的既有行为（开关的语义本来就是「草稿 = BOM 的全量」），本轮没有改动它。
但它与用户描述的流程（先导入 BOM、再编辑）边界相邻，所以列在这里。

- **结论（用户 2026-09-17 补充）**：「导入 BOM 明细，也视为对采购单的编辑，允许保存」——
  即重新带入 BOM 就是一次普通编辑，保存即可，**不加确认弹窗**。
  与下面的建议一致，所以维持现状：`selectPurchaseBom` / `toggleBomImport` 仍然是「整体替换」。

- 建议：**先维持**，靠「先选 BOM 再编辑」的操作顺序规避。
- 若要改：在「替换会丢行」时弹一次确认（说明会丢几行），代价是 `selectPurchaseBom`
  要多一次交互，且要新增一条测试。
