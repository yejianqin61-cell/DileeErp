# 财务、仓库与跨模块联动现状审计

- 审计日期：2026-08-31
- 审计范围：财务、仓库、采购、质量、生产、销售、人事及订单工作台
- 审计依据：当前代码、Prisma 数据模型、既有设计/任务文档、2026-08-30 审计及其后续提交
- 术语基线：跨模块统一使用“订单号”；原料、成品、库存事实、应收、应付、工资台账、收货批次、来料质检批次、原料入库批次为业务称谓

## 一、结论摘要

系统已经形成“业务事实 -> 库存事实/财务来源 -> 台账/余额”的后端骨架。原料入库过账会产生原料库存事实和待处理应付来源，成品出库可产生应收来源，生产工序员工日报可产生生产薪资来源，订单工作台可以按订单号聚合采购、质检、库存、生产和收付款摘要。

2026-08-30 审计提出的两个阻断项已经在后续提交中处理：

1. 财务可以查询待处理应付来源并幂等接收为应付条目。
2. 已有独立的供应商应付对账对象、服务和接口，不再复用应收对账模型。

当前系统仍不能视为完成生产验收。最大的风险不再是“没有接口”，而是跨模块链路在真实 PostgreSQL、登录权限、浏览器操作和异常回退场景下尚未被完整证明。

## 二、联动关系

```text
销售单（订单号）
  ├─ BOM ─> 采购单 ─> 收货批次 ─> 来料质检批次 ─> 原料入库批次
  │                                      ├─> InventoryFact（原料增加）
  │                                      └─> PayableSource ─> 应付条目 ─> 付款核销
  └─> 生产单 ─> 工序员工日报 ─> 生产薪资来源 ─> 工资台账 ─> 工资支付
                         ├─> 原料领料/退料/报废 ─> InventoryFact
                         └─> 成品质检 ─> 成品入库 ─> 成品出库
                                                   └─> ReceivableSource ─> 收款核销
```

订单号是跨模块业务身份。采购单号、生产单号、到货单号、检验单号、入库单号、出库单号和收付款单号均为围绕订单号产生的单据身份；UUID 只用于内部关联。

## 三、当前已具备能力

### 财务

- 应收来源、收款、分配核销、部分收款、过账、冲销和订单摘要。
- 原料入库/外加工签收产生的待处理应付来源。
- 待处理应付来源到供应商应付条目的幂等接收。
- 应付条目、付款分配、过账、冲销和供应商应付对账。
- 财务草稿单据的有限编辑；已确认/已过账事实不能静默覆盖。
- 财务页提供草稿编辑入口，但真实权限、版本冲突和影响预览仍需验收。

### 仓库

- 原料入库、原料领料、退料、报废及冲销均通过库存事实改变余额。
- 成品入库、不良品入库、成品出库和客户退货有独立服务。
- 原料仓储情况工作区已经能够按物料、单位、订单号查看派生余额。
- 库存余额不是可直接编辑字段，负库存和幂等过账由服务层校验。

### 采购、质量与生产

- 采购单绑定订单号和 BOM 明细，物料使用统一物料主数据 ID。
- 到货、来料质检和原料入库支持批次关联及部分数量处理。
- 生产领料按生产单和物料校验 BOM 参考量与库存风险。
- 工序员工日报按生产单、工序、员工和日期记录，并产生薪资来源和进度/超单告警。

### 订单工作台

- 可以显示 BOM、采购、到货、来料质检、原料入库、库存、生产、成品质检、成品入库、出库、应收、应付、收款和付款的摘要。
- 可以按订单号查看状态、阻塞原因和审计时间线。

## 四、缺陷与待开发点

## 四点一、代码证据矩阵

| 联动 | 当前代码证据 | 当前判断 | 缺口 |
|---|---|---|---|
| 原料入库 -> 库存 | 原料入库过账在同一事务中写入 `InventoryFact`；余额由库存事实聚合 | 已具备后端闭环 | 需要真实 PostgreSQL 和重复过账验收，证明幂等、冲销和负库存门禁 |
| 原料入库 -> 应付 | 原料入库过账创建唯一 `PayableSource`；财务通过来源幂等接收 `SupplierPayableEntry` | 已具备来源链路 | 到货批次、数量、单价和差异快照仍需在采购工作台完整可见 |
| 应付 -> 付款 -> 对账 | 付款分配表限制到应付条目；供应商应付对账按有效分配汇总 | 已修复跨单据误计问题 | 缺少真实环境下的部分付款、未分配付款、冲销和并发核销证据 |
| 生产领料 -> 库存 | 领料预览及过账按生产单、物料、单位计算库存影响 | 已具备后端门禁 | 订单工作台需呈现领料、退料、报废与生产进度差异 |
| 成品出库 -> 应收 | 成品出库事实可创建应收来源，收款分配更新应收状态 | 已具备后端骨架 | 成品 QC、成品入库、出库、应收和收款缺少一条真实浏览器验收链路 |
| 工序员工日报 -> 工资 | 日报服务写入工资来源，工资台账和工资支付接口已存在 | 已具备来源关系 | 财务页仍保留“登记绩效/生成薪资台账/登记工资支付”重复录入入口，职责边界未收敛 |
| 采购详情 -> 批次工作流 | 后端返回收货、来料质检、原料入库和应付来源；前端已定义批次类型/helper | 部分完成 | 采购详情 JSX 仍使用旧 `item.receipts` 表格，批次序号、QC、入库和应付状态尚未统一展示 |
| 物料 -> 库存 | 余额查询限制 `materialType = raw_material`，按物料、单位、订单号聚合 | 已修复主要边界 | 需要回归验证销售产品不会进入原料物料池，业务页面仍需清理 UUID 暴露 |

矩阵中的“已具备”只表示代码路径存在，不表示已完成生产验收；所有写入型链路仍须通过专用 PostgreSQL、HTTP 和浏览器测试。

### P0：发布前必须完成

1. **真实环境闭环尚未验收。** 当前主要证据是 API 构建、类型检查和单元测试；真实 PostgreSQL 迁移、认证会话、权限矩阵、HTTP 合约和 Playwright 写入型链路仍缺专用环境证据。不能用构建通过替代业务验收。
2. **生产环境部署可重复性风险。** 服务器不是 Git 工作区，依赖归档包、`.env`、PM2 和 Docker 容器。归档内容、解压目录、构建产物、环境变量端口和 PM2 启动脚本任何一项不一致，都会出现旧版本、缺少 `dist/main.js` 或前端 Chunk 404。应以 `.agent/deployment/server-incremental-deployment-standard.md` 作为唯一执行标准并增加发布后版本指纹检查。

### P1：应纳入下一轮开发/验收

1. **采购到货、质检、入库批次的完整业务可见性不足。** 后端已有批次关联，但需要在采购单详情中统一展示每个收货批次的到货数量、质检数量、合格数量、入库数量、应付来源状态和批次序号，并允许在合法状态下回退/更正。
2. **应付金额和库存数量的差异处理不够统一。** 入库、应付接收、付款和应付对账需要明确数量快照、单价快照、税率/币种、外部余额、差异原因和处理状态；已付款记录只能走调整、补付、退款或冲销。
3. **库存维度仍需全面收紧。** 所有余额和移动查询都必须返回物料 ID、物料名称/编码、单位 ID/名称、库存类别、订单号和有效数量；禁止跨单位聚合，禁止把销售产品混入原料物料池。
4. **财务与人事工资职责边界需固定。** 人事负责员工、考勤、绩效和日报来源；财务负责工资台账确认、调整和支付。当前部分入口存在跨页重复，需要统一权限与导航，避免同一工资事实被两个入口修改。
5. **财务草稿编辑能力仍非全局一致。** 应收、应付、收付款、对账和工资单据需要统一草稿编辑、乐观版本校验、影响预览和受控回退规则；确认或过账后的事实必须保留原记录和更正原因。
6. **订单工作台仍是摘要而非完整对账视图。** 应补充采购需求、已下单、已到货、QC 合格/不合格、已入库、待应付、已确认应付、已付款及生产/成品链路的数量金额差异和阻塞明细。
7. **业务查询仍有内部 ID 暴露风险。** 财务和仓库操作应通过姓名、员工编号、供应商名称、采购单号、入库单号和订单号定位；UUID 只能作为隐藏关联值。

### P2：治理与体验

- 财务页面拆分应收对账、应付对账和工资结算工作区，减少同页误操作。
- 所有跨模块列表统一提供日期、订单号、供应商/客户、批次、状态和风险筛选，并支持导出。
- 批次统一使用“收货批次、来料质检批次、原料入库批次”，避免用“第一批应付”等动态字段命名。
- 已使用的物料、单位、供应商和字典项应停用而非物理删除，历史单据保留快照。

## 五、建议的最高测试切入点

优先测试两个最高层接口：

1. **来源事实接收服务：** 验证同一原料入库批次重复接收不会重复生成应付，且采购单、订单号、物料、单位、数量、单价、金额和状态快照一致。
2. **订单号联动摘要：** 验证同一订单号下采购、仓库、质检、生产、应收和应付的数量/金额均可追溯，缺失链路会形成明确阻塞信息。

页面测试只验证用户可见行为、权限和错误反馈，不绑定 Prisma 查询实现。

## 六、最低验收链路

```text
已确认销售单 -> BOM -> 采购单 -> 收货批次 -> 来料质检 -> 原料入库过账
  -> 原料库存余额 + 待处理应付来源 -> 应付接收/确认 -> 分批付款/核销 -> 应付对账

生产单 -> 工序员工日报 -> 生产薪资来源 -> 薪资台账 -> 工资支付
生产单 -> 成品质检 -> 成品入库 -> 成品出库 -> 应收来源 -> 收款核销
```

每条链路必须验证：订单号追溯、数量/金额快照、重复请求幂等、草稿可编辑、已确认事实可通过受控方式更正、库存不出现负数、分配不超过余额、权限有效、审计记录完整。

## 七、实施决策

- 库存余额只由有效库存事实和调整事实派生，不提供直接改余额入口。
- 原料入库过账产生待处理应付来源；财务接收来源后才形成供应商应付条目。
- 应付对账按批次明细、采购单汇总；差异必须保留外部余额和处理说明。
- 已确认/已过账财务事实不允许静默覆盖；更正通过调整、冲销、退款、补收或补付完成。
- 批次使用重复记录建模，不使用动态数据库列。
- 业务页面和表单继续使用现有组件库；不以浏览器原生弹窗替代业务反馈。

## 八、不在本期范围

- 会计总账、会计凭证、税务申报、发票自动验真、银行或供应商系统直连。
- 多仓库、库位、批号成本、先进先出和自动单位换算。
- 自动排产、自动采购建议、自动计薪和工资税费计算。
- 可配置审批流的完整产品化，仅保留权限、操作人、原因和审计门禁。

## 九、待确认事项

- 条件接收数量是否立即进入可用原料库存，以及应付是否按条件接收数量计价。
- 应付来源的最终形成节点是否始终为原料入库过账。
- 历史无批次记录统一显示为“历史未分批”还是补建批次。
- 订单关闭前是否要求应付对账差异必须为零。
