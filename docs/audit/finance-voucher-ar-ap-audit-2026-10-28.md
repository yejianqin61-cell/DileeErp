# 财务凭证、应收、应付与三大报表审计（2026-10-28）

## 结论

当前三大报表以**已过账凭证分录**为唯一主要账务来源，应收、应付业务单通过“确认时生成挂账草稿凭证、收付时生成收支流水、再由流水生成凭证”间接进入报表。代码审计和最小复现已确认：现金流量表漏归位应付付款，红冲后的资产负债表出现反向余额。另有业务状态与凭证状态脱节、部分核销金额被整笔入账等高风险路径。因此现阶段不能把三大报表当作应收应付余额的可靠对账结果。

审计范围：`apps/api/src/modules/finance` 中凭证、应收、应付、收付款、三大报表的生成与回退路径；相关设计文档和单测。未读取生产账套数据，故本报告不判断具体错票数量或历史金额。没有修改业务代码或账务数据。

## 数据链实际如何运行？

| 业务动作 | 生成物 | 何时进入三大报表 |
| --- | --- | --- |
| 确认应收 | 借应收账款、贷收入的**草稿**凭证 | 财务另行过账凭证后 |
| 确认应付 | 借成本/存货、贷应付账款的**草稿**凭证 | 财务另行过账凭证后 |
| 收款/付款过账 | 核销分配 + 已生效收支流水 | 流水再生成凭证且凭证过账后 |
| 三大报表 | `voucher.status = posted` 的分录；另计科目期初余额 | 不直接按应收/应付业务单余额生成 |

证据：`voucher.service.ts:301-315,376-384,554-565`；`receivable.service.ts:165-181`；`supplier-payable.service.ts:231-248`；`finance-three-statements.service.ts:196-210`。报表缺口只统计草稿凭证张数和无凭证流水条数（`finance-three-statements.service.ts:368-375,397-408`），没有“已确认应收/应付与已过账凭证差额”。

## 哪些问题已经有代码与复现证据？

| 级别 | 问题与影响 | 代码证据 / 复现 |
| --- | --- | --- |
| **P0** | **现金流量表漏掉正常应付付款。** 付款凭证借方为`负债类/应付账款`，但“购买商品、接受劳务支付的现金”的匹配器把`应付账款`放在`资产类`里。100 元付款被放进未归位，报表该行是 0。 | `supplier-payment.service.ts:130-140`；`finance-three-statements.ts:314-321`。用现有 `buildCashFlowStatement` 运行 `借 负债类/应付账款 100 / 贷 银行存款 100`，得到 `purchaseCashPaid=0`、`unmapped=100`。 |
| **P0** | **红冲使报表出现反向余额。** 红冲把原凭证改成 `reversed` 并新建反向的 `posted` 凭证；报表只读 `posted`，于是只取到反向分录。原来借银行 100 的凭证红冲后，资产负债表货币资金是 **-100**，预期净额为 0；借贷仍平衡，勾稽不能发现。红冲日期还可能与原凭证所在期间不同。 | `voucher.service.ts:590-610`；`finance-three-statements.service.ts:202-210`。通过现有服务的内存桩复现 `actualAssets=-100, expectedAssets=0, actualDifference=0`。 |
| **P0** | **“挂账草稿”就被当成“已经挂账”来决定销账科目。** 应收/应付确认只创建草稿；`accruedSourceIds` 只排除 `reversed`，因此草稿也算已挂账。若挂账凭证尚未过账而收付流水凭证过账，报表只计入销账的贷应收/借应付，出现负应收/负应付，收入或成本缺失。 | `voucher.service.ts:301-315,326-333`；`customer-payment.service.ts:123-146`；`supplier-payment.service.ts:130-156`；报表过滤见上。现有 `voucher-service.test.cjs:715-728` 还断言挂账状态为草稿。 |
| **P0** | **确认状态与凭证创建分两次提交。** 单条、批量、对账确认均先提交应收/应付 `confirmed`，再调用 `createAccrual`。科目缺失、数据库失败或批量处理中断时，单据已确认但挂账凭证缺失；再次确认因状态不是草稿而不能自然补账。 | `receivable.service.ts:169-181,233-256`；`supplier-payable.service.ts:235-248,308-334`；`reconciliation.service.ts:163-193`；`supplier-payable-reconciliation.service.ts:211-233`。 |
| **P1** | **部分核销/混合来源付款的整笔科目可能错误。** 两侧均允许`核销合计 ≤ 收付款金额`，随后按**收付款全额**写一条流水与一张两行凭证。例：收款 100，只核销应收 60，若应收已挂账则凭证贷应收 100，业务应收余额只减 60。混合“已挂账/未挂账”来源时，整笔退回收入或成本科目，会重复确认已挂账部分。 | `customer-payment.service.ts:117,123-161`；`supplier-payment.service.ts:121,129-177`。这是代码路径推导，未用生产样本测算金额。 |
| **P1** | **业务回退/冲销未同步账务凭证。** 应收回退/取消、应付回退/冲销只变业务状态；收付款冲销会回冲收支流水，但不红冲已过账的流水凭证。报表仍会读到旧凭证。 | `receivable.service.ts:330-354`；`supplier-payable.service.ts:369-394`；`cash-flow.service.ts:572-605`；`finance-three-statements.service.ts:202-210`。 |

## 为什么现有检查没有挡住？

执行 `node --test` 跑了 `voucher-service`、`receivable-service`、`supplier-payable-service`、`finance-three-statements-service` 四组单测，**110/110 通过**。它们分别验证“红冲单生成”和“报表只读 posted”，没有把两个行为联测；应收/应付确认测试用内存桩验证 `createAccrual` 被调用，没有注入创建失败后的数据库状态；现金流量表测试覆盖收入与还款，但没有“负债类/应付账款”付款。

## 修复应按什么顺序？

1. 先锁定账务不变量：一张业务单的确认、凭证创建与撤销要有可恢复的一致状态；付款核销额、预付/预收余额和分录金额逐项相等。为上述两个已复现错误及“草稿挂账后收付”各留一条跨模块回归检查。
2. 纠正现金流量表应付账款匹配类别；重新定义红冲查询口径和红冲日期/期间规则，并对历史报表做差额核对。不要直接改历史已过账分录。
3. 处理确认与凭证生成的事务边界、失败重试、回退/冲销联动；对历史已确认但缺凭证、已冲销业务但仍有有效凭证的记录列出只读差异清单。
4. 财务确认“原料入库、税额、成本结转、定金/预收预付”科目规则后，再改默认映射；对历史凭证逐张预览需红冲重开的差异，保留审计痕迹。
5. 报表增加应收/应付业务余额与已过账往来科目余额的勾对，至少显示差额与来源单号；不能只显示草稿张数。

**待财务确认的业务口径**：原料入库是否先记原材料；含税金额如何拆进项/销项税；定金、超额收付款及未分配款是预收/预付还是其他往来；历史已确认单据是否已在外部账套入账。以上问题决定正确科目，不能由候选链猜定。
