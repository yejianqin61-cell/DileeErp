## 1 科目体系结构（分类/余额方向/资金科目）

### 1.1 五个分类怎么定义

| 结论 | 证据 |
| --- | --- |
| 五个分类是**代码常量元组**，顺序即会计制度顺序：资产类 → 负债类 → 成本类 → 所有者权益类 → 损益类 | `catalog:25-31`；排序权重 `catalog:223-226`（不在五类内 → rank 1000） |
| 同一套五类名在 DB 里是**类目表**的 5 行内置记录（`is_system=true`，sort_order 10..50） | `prisma/schema.prisma:2355-2370`；种入 `apps/api/prisma/seed.ts:62`；迁移 `apps/api/prisma/migrations/20261107200000_accounting_subject_categories/migration.sql:42` |
| 但**科目行的 `category` 仍是字符串**、不是外键，也不受「必须五类」约束（允许自建类目/历史「未分类」） | `prisma/schema.prisma:2313`、`2313-2317` 注释；`cat.svc:13-17`、`schema.prisma:2347-2350` |
| 内置五类**禁止改名/删除**（理由即「三大报表按这五个名字匹配科目」） | `cat.svc:133-137`、`cat.svc:183-187` |
| 科目清单 = 老科目表 121 条 + 系统补充 1 条（「工资支付」，成本类，sortOrder 715）= 122 条 | `catalog:34-156`、`catalog:173-179`、`catalog:189-192`；守卫 `apps/api/test/unit/finance-three-statements.test.cjs:67` |
| 科目**没有 code 字段**：老表的「科目代码」整列被明确放弃，唯一标识是 `(category, name)` 拼出的 `分类/名称` | `catalog:4-8`、`catalog:194-197`；唯一键 `prisma/schema.prisma:2338-2340` |

> 用户在需求里说「会计科目的编码可以不管」，代码照此实现；代价是**科目改名会改变唯一标识**（见 §8 SR-D-02）。

### 1.2 余额方向（借/贷）定义在哪、是否参与计算

| 结论 | 证据 |
| --- | --- |
| 字段是 `balanceDirection String? @db.VarChar(4)`，取值只能是「借」「贷」或 null；老表 D 列照抄 | `prisma/schema.prisma:2316-2317`；种子每行带方向 `catalog:19-21`、`catalog:35-155` |
| 服务层唯一校验点在 `direction()`：trim 后只接受「借」「贷」，空串/null 都存 null | `subject.svc:206-218` |
| **它不参与任何计算**：注释与 schema 都写明「本期只作口径参考，不参与任何计算」 | `catalog:12-13`、`prisma/schema.prisma:2308-2309`、`prisma/schema.prisma:2316` |
| 报表的方向**来自行定义 `side`**（`statement row.side`，默认 debit，负债/权益/收入行显式 credit），与科目余额方向无关 | `3s:135-153`（`side?: "debit"|"credit"`）、`3s:409-417`（`debitBalance`/`creditBalance`）、`3s:457-473` |
| 凭证借贷方向来自分录 `direction` + 「收入=借资金/贷科目、支出=借科目/贷资金」 | `v.domain:139-157`；`prisma/schema.prisma:2484-2486` |
| 期初余额的 `direction` 是另一套独立字段（debit/credit），录入时**不校验**是否等于该科目的余额方向 | `open.svc:218-231`（只校验 ∈{debit,credit}）；`prisma/schema.prisma:2431-2432` |

**数据本身是错的，不能直接拿来用**（若将来引入「按科目余额方向判符号」会立刻出错）：

- 损益类**全部**写成「借」，包括收入类：`主营业务收入`/`其他业务收入`/`投资收益`/`营业外收入` 都是「借」——`catalog:111-118`；
- 备抵科目 `累计折旧`（`catalog:64`）、`累计摊销`（`catalog:71`）写「借」（会计上是贷方备抵）；
- `应交税费-销项税` 写「借」（`catalog:88`），而销项税是贷方；
- 报表现在靠 `3s:184-197` 的「借−贷并入主科目行」处理备抵，**不读**该字段，所以这些错没暴露、但也没有任何约束力。

### 1.3 字段语义（code/name/category/方向字段）

| 字段 | 语义 | 证据 |
| --- | --- | --- |
| `category` | 科目类别 = 五分类之一或自建类目名，VARCHAR(30) | `prisma/schema.prisma:2312-2313` |
| `name` | 项目 = 科目名称，VARCHAR(100)，**照抄老表原文含手误空格**（`销售- 办产地证`、`销售 -业务提成`） | `prisma/schema.prisma:2314-2315`、`catalog:130-136` |
| —（无 code） | 没有科目编码列；`subject_key` 是运行时派生的 `分类/名称` 字符串 | `catalog:194-197`、`catalog:206-208` |
| `balance_direction` | 借/贷，仅展示与历史口径，不参与计算 | 见 1.2 |
| `sort_order` | 老表行序，间隔 10；列表/报表排序键之一 | `catalog:33`、`catalog:238-247`、`subject.svc:160-167` |
| `is_active` | 停用；停用的科目不能新建单引用（`requireSubject` 要求 `isActive:true`），但历史单据/凭证仍可显示 | `subject.svc:14-19`、`cf.svc:223-232` |
| `deleted_at` | 逻辑删除；被业务引用时**拒绝删除**，只允许停用 | `subject.svc:124-140`、`subject.svc:142-158` |
| **ledger_direction** | **不存在**这个字段；用户/审计口径中的「借方贷方/余额方向」对应 `balanceDirection` 与分录 `direction` 两个概念 | 全仓 grep 无 `ledger_direction` |

### 1.4 「资金科目」（银行存款/库存现金）的识别——**有三套互不一致的规则**

| 规则 | 定义 | 证据 | 影响 |
| --- | --- | --- | --- |
| ① 报表内核 `isFundSubject` | 分类必须是 `资产类` 或空，且名称**精确等于** `银行存款`/`库存现金`，或名称以 `库存现金` 开头 | `3s:64-78` | **`银行存款 中国银行（美元）` 这类银行明细不算资金**；`其他货币资金` 不算资金（刻意为之，见 `3s:73-76` 注释：避免把客户汇款误判为内部划转） |
| ② 资产负债表「货币资金」行 | `资产类` 且（前缀 `银行存款` ∪ 前缀 `库存现金` ∪ 等于 `其他货币资金`） | `3s:158` | 与 ① 不同：这里**算**银行明细和「其他货币资金」 |
| ③ 凭证资金分录 `fundSubjectFor` / `fundLineFor` | 结算方式/账户名含「现金」→ `库存现金`，否则 `银行存款`；有 `bank_id` → `银行存款`；业务科目本身是现金族 → 资金侧必为银行存款 | `v.domain:69-72`、`v.domain:84-91`、`v.domain:93-128` | 生成凭证时资金行 `subject_key` 恒为裸名 `银行存款`/`库存现金`（`v.domain:24-26`、`v.domain:113-128`），所以①能认出来；但**手工凭证**若把资金行写成 `资产类/银行存款 中国银行（美元）`，①认不出 |

后果（可验证的断点）：一张手工凭证若资金侧用 `资产类/银行存款 中国银行（美元）` 或 `资产类/其他货币资金`，`buildCashFlowStatement` 会把它当**没有资金分录的凭证**（`3s:665-666` 计入 `nonCashVouchers` 后跳过），于是：
- 现金流量表里这笔钱完全不出现（`3s:644-655` 的 `nonCashVouchers` 只在表尾提示张数，不给金额）；
- 现金流量表「期末现金」（`3s:696-703`）与资产负债表「货币资金」（`3s:158`）**对不上**，且勾稽不会报警。

补充：`normalizeSubjectKey` 只给裸名 `银行存款`/`库存现金` 补「资产类/」，银行明细裸名不会被归一（`3s:80-85`）。

### 1.5 同名科目

- 允许不同分类下同名（唯一键是 `(category,name)`，不是全局 name）：`prisma/schema.prisma:2338-2340`。
- 候选链**只按 name 查**（`name: { in: [...] }`），同名时取 `sortOrder` 最小的一条，**不区分分类**：`cf.svc:540-548`。
- 凭证侧 `subjectByName` 按 name 查但**没有 orderBy**，同名命中哪条取决于数据库返回顺序（口径不确定）：`v.svc:366-375`（对比 `cf.svc:544` 显式 `orderBy: sortOrder`）。
- 报表匹配同时用 category + name：`3s:87-96`，所以同名跨类不会互相串行；但 `splitSubjectKey` 只按**第一个 `/`** 切（`3s:50-54`），若科目名里含 `/`，分类/名称会被切错 → 静默失配。

### 2.3 候选链的匹配规则与失败行为

1. 解析实现 `firstCandidateSubject`：一次 `findMany({ name: { in: names }, deletedAt: null, isActive: true }, orderBy: sortOrder asc)`，再**按候选链顺序**挑第一条命中的（不是按库返回顺序）：`cf.svc:540-548`。
2. 一个候选都不存在 → **显式 422** `ACCOUNTING_SUBJECT_NOT_FOUND`，不静默跳过（`cf.svc:386-391`；`v.svc:366-374`）。这是 2026-11 之前「供应商付款写死字典 key 导致整笔流水消失」的教训，注释在 `cf.svc:318-323`。
3. 人工选了科目（`subject_id`/`contra_subject_id`）→ 走 `requireSubject`，必须**存在 + 启用**，否则 422；**绝不静默换成候选链**：`cf.svc:223-232`、`v.svc:378-382`、`supplier-payable.service.ts:234`。
4. 停用科目：新单据不能选（`requireSubject` 要求 `isActive:true`）；历史凭证/流水仍持有它（`subject.svc:14-19`）。
5. 改名科目：候选链按**名称**匹配 → 改名后候选链全部落空 → 该来源的新单据/过账直接 422（不是静默错记）；但**历史快照不会跟着改名**（见 §8 SR-D-02）。

### 2.4 「资金科目」在业务侧如何区分（与 1.4 的报表侧不同）

- 凭证生成：`fundSubjectFor(hint)` — 结算方式/结算账户名含「现金」→ 库存现金，否则银行存款（`v.domain:69-72`）。
- `fundLineFor` 判定顺序：⓪ 业务科目本身是现金族（`isCashFamilySubject`，名称前缀「库存现金」）→ 资金侧只能是银行存款；① 有 `bank_id` → 银行存款 + 该账户；② 否则按文本猜（`v.domain:93-128`）。
- 确认应付时的「资金搬运」：对方科目是现金族 → 不生成挂账凭证（`v.svc:277-297`），改由付款步骤一次记完（`supplier-payment.service.ts:145-155`、`v.svc:700-720`）。
- 注意：这套「现金族 = 前缀库存现金」与报表 `isFundSubject` 的「精确 银行存款/库存现金 + 前缀库存现金」**不是同一套**，`银行存款 中国银行（美元）` 在业务侧 `isBankFamilySubject` 为真（`v.domain:88-91`）、在报表侧 `isFundSubject` 为假（`3s:66-78`）。

## 3 期初余额

### 3.1 结构（按科目 + 建账日 + 币种，不是按期间）

`AccountingOpeningBalance`（`prisma/schema.prisma:2425-2448`）：

| 字段 | 语义 | 证据 |
| --- | --- | --- |
| `as_of_date` | **建账日期**（余额是这一天之前的累计），DATE | `schema.prisma:2426-2427`、`opening-balance.service.ts` 文件头 `10-24` |
| `subject_key` | `分类/名称` 字符串，**没有外键、没有科目 id** | `schema.prisma:2428`、`open.svc:218-220` |
| `subject_label` | 科目名快照（改名后不随动） | `schema.prisma:2429`、`open.svc:229` |
| `currency` | 币种；期初**按币种分组**，每组各自建账日 | `schema.prisma:2430`、`open.svc:178-208` |
| `direction` | `debit` / `credit` | `schema.prisma:2431-2432`、`open.svc:221` |
| `amount` | Decimal(18,4)，**恒正数**（方向由 direction 表达，不写负数） | `schema.prisma:2433`、`open.svc:222-228` |
| 唯一键 | `(as_of_date, subject_key, currency)`，**软删仍占键** | `schema.prisma:2442-2445`、`open.svc:128-140` |

### 3.2 录入方式：整批替换、可绕过凭证、无强校验

- API：`GET /finance/opening-balances`（某组期初 + 借贷合计/差额）、`PUT /finance/opening-balances`（整批替换）：`opening-balance.controller.ts:45-59`。
- 整批替换：事务内软删本次未出现的行 + upsert（软删行恢复）: `open.svc:109-161`。
- **不强制试算平衡**：借贷不平衡照样保存，只在响应与界面显示差额（`open.svc:22-24`、`open.svc:154-160`）。
- **不校验科目是否存在**：`subject_key` 只做 `normalizeSubjectKey`（裸名资金科目补「资产类/」），其它字符串原样入库（`open.svc:218-220`、`3s:80-85`）。因此期初可以指向一个已删除/改名/拼错的科目。
- **不校验方向与科目余额方向是否一致**（`open.svc:221` 只校验 debit/credit）。
- **可以绕过凭证直接改数**：PUT 直接覆盖，不生成任何凭证、不经过 `voucher_lines`；审计只记整批的 `saved/removed/debit/credit/balanced`，**不记逐科目的改前/改后**（`open.svc:154-160`）。因此「期初 + 凭证」是两套数据来源（见 §8 SR-D-08）。
- 前端科目下拉按 `分类/名称` 反查（`apps/web/lib/opening-balance.ts:67-73`、`apps/web/lib/opening-balance.ts:135-147`），提交的只有 `subject_key` 字符串、没有科目 id；改名后已存期初行靠 `subjectLabel` 兜底显示，但 `subject_key` 不会更新。
- 写权限：控制器只有 `@RequireModules("finance")`，**没有 `@RequireAdministrator()`**（`opening-balance.controller.ts:45-59`，对比科目维护 `accounting-subject.controller.ts:64-74` 写操作都是管理员）——任何有财务模块权限的账号都能整批覆盖期初。

### 3.3 报表如何取期初

- 取数：`effectiveForAll(toDate)` 一次读回**每个币种「不晚于期末的最近一次」建账期初**（`open.svc:178-208`，单币种版 `open.svc:164-176`）。
- 组装：`openingMapTo / openingMapYearStart / openingMapPrevious` 分别按期末月/上年 12 月/上期期末月的汇率折算（`3s.svc:288-313`）。
- 余额：`balancesAt(cutoff) = 建账日之后(≤cutoff)的凭证分录 + 期初`（`3s.svc:318-326`），即**建账日之前的凭证被丢弃**（`3s.svc:249-253`、`afterOpening()`），避免与期初重复计算。
- 进入哪张表：
  - **资产负债表**：期初按科目分类/名称并入 `balances`，参与行匹配与「未分配利润 = 本年利润 + 利润分配 + 未结转损益（含期初损益类余额）」的计算（`3s:555-599`，尤其 `3s:563-574`）；货币资金期初有两种来源：科目期初里有资金科目 → 用科目期初；否则退回银行账户档案的 `openingBalance`（`3s.svc:339-341`、`3s:549-559`）。
  - **现金流量表**：期初现金 = 银行期初兜底 + 期初里的资金类科目部分 + 建账日到本期期初之间的资金类净额（`3s.svc:370-381`）。
  - **利润表**：**不使用期初**，只取期间凭证（`3s.svc:151-161`）。期初的损益类余额只通过资产负债表的「未分配利润」体现。
- 期初与凭证相加的实现：`openingBalancesToMap` 把期初行转成与凭证同型的 `{debit,credit}` 累计，再 `mergeBalances`（`open.svc:39-51`、`open.svc:77-85`）。

> 本轮实测（只读，跑 `apps/api/dist` 的已编译产物，与 src 同源）：`checkStatementCoverage()` 当前全绿（unclaimed=0 / doubleClaimed=[] / emptyRows=[]，种子 122 条），说明**当前科目表**的映射完整；`isFundSubject("资产类/银行存款 农业银行") === false`、`isFundSubject("资产类/其他货币资金") === false`、`isFundSubject("银行存款") === true`，即 §1.4/§8 SR-D-06 的资金科目不对称可复现。

### 5.5 「改科目名会静默失配」清单（按风险从高到低）

1. **全部 `named(...)` 行**（约 40 处，见上表）：科目改名 → 该科目金额不再被任何行认领。利润表/现金流量表把缺口写进表尾（`3s.tbl:126-128`、`142-144`），**资产负债表连表尾都不写**（`3s.tbl:90-101` 不含 `unmapped`）。
2. **科目换分类**（`subject.svc:98-121` 允许，无护栏）：只要换出「五类」，所有 `only("损益类"/"资产类"/…)` 行全部失配 → 该科目从三张表一起消失（同样只有利润表/现金流量表会点名）。
3. **自建类目下的科目**：`cat.svc:108-117` 允许建新类目、`subject.svc:81-87` 允许把科目建/改到新类目；报表只认五类名（`3s:96`）→ 该类目下所有科目在报表里恒为「未归位」。
4. **前缀行**（货币资金、应交税费、销售费用、管理费用、现金流量表第 8 行）：新增科目会被自动吸入（好），但改名改掉前缀就失配；反之，任何新命名的 `销售xxx`/`管理xxx` 会被**自动**归入对应行，无需确认。
5. **覆盖度守卫只在单测里跑**：`checkStatementCoverage`（`3s:734-767`）的注释说「也供运行期报警」，但全仓只有 `apps/api/test/unit/finance-three-statements.test.cjs:62-68` 调用它，**生产运行时不校验**；因此线上通过科目维护页新增的科目不会触发任何告警。

**三套科目口径并存（本报告最核心的结构问题）**：

1. `accounting_subjects.id`（外键）— 流水/单据统计与显示用（`cf.domain:48-53`）；
2. `voucher_lines.subject_key`（`分类/名称` 字符串快照）— 三大报表唯一取数依据（`3s:425-436`、`3s:87-96`）；

## 8 流程性缺陷（SR-D-…）

### SR-D-01 红冲后报表不归零，反而单边反向入账

- **现象**：红冲一张已过账凭证后，资产负债表「银行存款」凭空多出一笔等同金额，「应付账款/应收账款」同时多一笔；现金流量表记一笔反向流量并在另一侧落 `unmapped`。报表**不会回到红冲前的状态**，且勾稽仍然平（两侧同增），看不出来。
- **根因**：`reverse()` 把原凭证置 `status="reversed"` 并把红字凭证直接 `status="posted"`（`v.svc:687-693`）；三大报表只取 `status="posted"`（`3s.svc:202-203`）→ 只计入红字那一笔，原分录未计入，二者不抵消。
- **影响**：任何红冲都会污染资产负债表与现金流量表；金额越大越明显。且因为「两侧同增/同减」，勾稽校验（`3s:577-585`）发现不了。
- **建议**：口径二选一并加测试——(a) 原凭证与红字凭证同时计入（`status in ("posted","reversed")` 但排除被红冲的原凭证之外的其它状态），或 (b) 原凭证与红字凭证都排除（需按 `source_type="voucher"` 反查）。同时补一条「红冲后报表净额为 0」的回归测试。
- **证据**：`v.svc:674-698`、`3s.svc:202-203`、`3s:631`（注释与实现矛盾）、无红冲用例（`apps/api/test/unit/finance-three-statements-service.test.cjs:5` 仅有注释）。

### SR-D-02 科目改名/换分类后，历史凭证与期初的科目快照失配 → 报表静默少钱

- **现象**：财务在「会计科目」页把「销售费 推广费」改名为「推广费」后：收支明细/汇总立刻显示新名（按 id 取当前名），但**已过账凭证**的 `voucher_lines.subject_key` 仍是 `损益类/销售费 推广费`，利润表 `match(category,name)` 匹配不到 → 该科目金额掉进「未归位」表尾（`3s.tbl:126-128`）；若改的是**分类**（如改到自建类目），该科目从三张表全部消失。期初余额表的 `subject_key` 同样不随动（`open.svc:218-220` 只 trim），改名后整行期初变成「无主余额」。
- **根因**：报表以字符串快照匹配（`3s:87-96`、`3s:425-436`），而科目改名只改 `accounting_subjects` 本体（`subject.svc:98-121` 只 `update` 当前行）；期初表与 `voucher_lines` 都不级联。`subject.svc:92-97` 的注释「改分类或改名都不影响历史」只对**流水**成立（流水存 `subject_id`），对凭证/期初不成立。
- **影响**：用户要求「会计科目跟着收入支出一路走下去」的直接反例——改一次科目名，历史报表静默变数；财务核对时极难发现（金额不是出错，而是消失）。
- **建议**：报表匹配改按 **科目 id**（`voucher_lines` 增加 `subject_id`，期初表增加 `subject_id`），或改名/换分类时在同一事务内级联更新 `voucher_lines.subject_key/subject_label` 与 `accounting_opening_balances.subject_key`；至少要在改名时给出「历史报表将改变」的强提示。
- **证据**：`3s:87-96`、`3s:425-436`、`subject.svc:92-121`、`cat.svc:155-160`（只级联 `accounting_subjects.category`）、`open.svc:218-220`、`prisma/schema.prisma:2488-2490`（快照注释）、`prisma/schema.prisma:2428-2429`。

### SR-D-03 新增科目 / 自建类目后报表静默归零，且资产负债表不暴露缺口

- **现象**：财务新建一个「资产类/展会物料费」→ 三张表没有一行 matched；利润表/现金流量表把缺口写进表尾（`unmapped`），**资产负债表什么都不提示**：资产少了这笔、勾稽不平，表尾只说「看期初说明」（`3s.tbl:98-101`）。若新建的是自建类目（如「销售类」）下的科目，连「未归位」都不会出现在利润表（分类名不匹配任何 `only("损益类",…)`），而是整类从报表消失。
- **根因**：映射表是**代码常量 + 名称硬编码**（`3s:156-372`），运行时没有覆盖度校验（`checkStatementCoverage` 只在单测调用，`3s:722-767`）；资产负债表的版式构造层不输出 `unmapped`（`3s.tbl:90-101` vs 内核 `3s:586-598`）。
- **影响**：科目表本应是「可配置」的，但配置出来的科目进不了报表；用户新增科目越多，报表越不准且越难发现。
- **建议**：① 资产负债表的表尾也输出 `unmapped`；② 把 `checkStatementCoverage` 挂到科目新增/修改与报表接口上（非阻断式告警 + 显式缺口）；③ 给科目维护页提供「报表归位」字段（报表行/现金流项目），把名字硬编码改为显式配置；④ 自建类目在报表里的落行使口径显式化（映射到五类之一）。
- **证据**：`3s:156-372`、`3s:722-767`、`3s:586-598`、`3s.tbl:90-101`、`subject.svc:77-90`、`cat.svc:108-117`。

### SR-D-04 建账日不在年初时，「年初余额」列等于建账期初（错误）

- **现象**：2026 年 9 月建账，出 2026 年 9 月资产负债表：资产侧「年初余额」列显示 9 月建账期初（如银行存款 100 万），而不是 2025-12-31 的余额；同一行「期末余额」也是期初+9 月凭证 → 年初/期末几乎一样。
- **根因**：`balancesYearStart = balancesAt(yearStart, …, openingMapYearStart)`（`3s.svc:311-326`），期初无条件并入；而 `afterOpening` 把建账日前的凭证全部丢弃（`3s.svc:249-253`）。注释 `3s.svc:145-146` 假设「期初余额对两个时点都成立（它发生在建账日之前）」，当建账日 > 年初时不成立。
- **影响**：所有「年中建账」的年度报表「年初余额」列错误，且与「期末余额」混同；跨年比对、报税口径失真。
- **建议**：仅当 `asOfDate ≤ yearStart` 时才把期初并入年初余额；否则年初余额标记为「无数据（建账日 X）」，并在表尾说明。
- **证据**：`3s.svc:145-146`、`3s.svc:196-200`、`3s.svc:311-326`、`3s.svc:318-323`。

### SR-D-05 建账日不在期间起点时，本期利润表漏记建账日之前的本期发生额

- **现象**：建账日 9-15，出 9 月利润表：9/1–9/14 的凭证被 `afterOpening` 排除，利润表只统计 9/15 之后的发生额，但表头期间仍写「9-01 至 9-30」。
- **根因**：同一处 `afterOpening` 同时过滤余额切片与期间切片（`3s.svc:249-253`、`329-330`），期间口径本不该受建账日影响。
- **影响**：建账当月的利润表少计半个月收入/费用；财务通常会误以为「系统漏了流水」。
- **建议**：余额切片按建账日过滤、**期间切片不过滤**（期初只影响余额起点，不影响本期发生额）；或在报表上把「建账日之前发生额」单列说明。
- **证据**：`3s.svc:253`、`3s.svc:329-330`、`3s.svc:318-326`。

### SR-D-06 资金科目三套识别规则 → 手工凭证/其他货币资金导致现金流量表整笔丢失

- **现象**：手工凭证用「资产类/其他货币资金」或「资产类/银行存款 农业银行」作资金分录时，资产负债表「货币资金」有数，现金流量表把它当「无资金分录凭证」跳过（只提示张数），期末现金与资产负债表对不上。
- **根因**：`isFundSubject` 只认精确名 `银行存款`/`库存现金` + 前缀 `库存现金`（`3s:64-78`），而资产负债表货币资金行用前缀 `银行存款` + `其他货币资金`（`3s:158`）；凭证生成路径只产出裸名（`v.domain:113-128`），手工凭证可自由填科目（`v.svc:602-625`）。
- **影响**：现金流量表少钱、期末现金不等于货币资金；勾稽（模板勾稽②）对不上但表尾只报张数。
- **建议**：统一资金科目判定为「科目表里的资金类科目」显式标记（如 `is_cash` 布尔，或分类+名单常量共用一份），三处引用同一函数；现金流量表对「有分录但认不出资金行」的凭证按金额进 `unmapped` 而非只数张数。
- **证据**：`3s:64-78`、`3s:158`、`3s:665-666`、`3s:644-655`、`v.domain:69-128`、`v.svc:602-625`。

### SR-D-07 「收支类目」可在收支流水页随时修改，且报表实时读取 → 历史现金流量表可被改数

- **现象**：财务把 8 月一条已过账流水的收支类目从「管理费用」改成「销售费 推广费」，再出 8 月现金流量表：落行从第 8 行变成第 4 行口径对应的行，金额整体搬家；而 8 月的凭证、利润表、资产负债表一个数都没变。
- **根因**：`cash-flow.service.update` 允许 `category_subject_id` 在流水 posted 后改（`cf.svc:143-191`，尤其 `170-175`，「只在显式提交时改」），而三大报表在**出表时**实时 join 该类目（`3s.svc:228-240`）→ 报表口径随主数据/单据变更而变，无快照、无审计明细（`cf.svc:185-189` 审计只记单号/金额）。
- **影响**：同一期间报表可被事后改写而无留痕；凭证（利润表口径）与现金流量表口径**分叉**；审计不可追溯。
- **建议**：现金流量表落行的科目应固化在凭证生成时（`voucher_lines` 增加现金流量项目/业务科目 id 快照），或对已过账流水的类目修改要求「重算凭证 + 记 before/after 审计」。
- **证据**：`cf.svc:143-191`、`cf.svc:185-189`、`3s.svc:228-240`、`3s:669-684`。

### SR-D-08 期初与凭证两套来源：期初可绕过凭证直接改数，且无逐行审计、无管理员限制

- **现象**：财务（或任何有 finance 权限的账号）在期初页整批替换，资产负债表/现金流量表当期数字立刻变化，但账上没有任何凭证；事后无法从审计里看出「改了哪个科目、从多少改到多少」。
- **根因**：期初是独立的 `accounting_opening_balances` 表（`schema.prisma:2425-2448`），`PUT` 整批替换不生成凭证（`open.svc:109-161`），审计只记汇总（`open.svc:154-160`）；`subject_key` 是自由字符串（`open.svc:218-220`），控制器无管理员限制（`opening-balance.controller.ts:45-59`）；报表把期初与凭证直接相加（`open.svc:77-85`、`3s.svc:318-326`），没有「期初是否已试算平衡」的门禁。
- **影响**：报表数字可被非管理员一次性改写且无法追溯；期初借贷不平只显示差额不阻断（`open.svc:22-24`），但资产负债表会被判「✗ 不平衡」并归因到期初说明，掩盖真实问题。
- **建议**：① 期初写操作加 `@RequireAdministrator()`；② 审计记逐行 before/after；③ 保存时强校验 `subject_key` 必须命中现有科目且方向与其 `balance_direction` 一致（或至少提示）；④ 期初可选「生成开账凭证」以便与凭证同源同审计。
- **证据**：`open.svc:109-161`、`open.svc:154-160`、`open.svc:218-231`、`opening-balance.controller.ts:45-59`、`3s.svc:318-326`、`schema.prisma:2425-2448`。

### SR-D-09 收支流水与凭证两套来源：金额/科目改了不重算凭证，报表之间对不上

- **现象**：已生成凭证的收支流水被「更正」金额或主科目后：收支明细/汇总显示新值，三大报表仍是旧凭证的数字（草稿凭证才可 regenerate，已过账只能红冲重开）。
- **根因**：`cash-flow.service.update` 直接改流水（`cf.svc:143-191`），凭证不联动；`v.svc:172-194` 生成时幂等命中即返回原凭证；`regenerate` 只对草稿开放。
- **影响**：收支报表与三大报表长期不一致；财务对账时无法判断哪边是对的。
- **建议**：已过账流水禁止直接改金额/主科目（或改后强制「重算凭证」流程：红冲 + 重开）；流水与凭证之间建立显式版本/校验（如 `voucher.generated_from` 金额快照对比告警）。
- **证据**：`cf.svc:143-191`、`v.svc:172-194`、`v.svc:430-470`（regenerate 只允许草稿）。

### SR-D-10 现金流量表「多业务分录」时类目被套用到所有对方分录

- **现象**：一条流水被手工改成多行对方分录（如 借 应付账款 100 / 借 应交税费-进项税 13 / 贷 银行存款 113），现金流量表用同一个 `categorySubject` 给**每一行**落行 → 13 的进项税也被算进「管理费用/其他经营支出」那一行，而不是第 5 行（采购）。
- **根因**：`buildCashFlowStatement` 的落行科目由 `categorySubject` 决定、与具体分录行无关（`3s:681-690`）。
- **影响**：现金流量表内部结构错（行间金额错配），但小计/净额/期末总额仍然对，勾稽不报警。
- **建议**：类目只用于「单对方分录」的凭证；多对方分录时按分录科目逐行落行，或要求按分录指定现金流量项目。
- **证据**：`3s:669-693`、`cf.svc:143-191`。

### SR-D-11 候选链按名称匹配 + 同名科目取 sortOrder 最小：科目归类可能落在另一个分类

- **现象**：若两个分类下存在同名科目（DB 允许，`schema:2338-2340`），候选链解析取 `sortOrder` 更小的那条，**与分类无关**；凭证侧 `subjectByName` 甚至没有排序，取哪条由数据库返回顺序决定（`v.svc:366-375`）。同一业务在不同入口可能挂到不同分类的同名科目。
- **根因**：候选链只有名字没有 id（`catalog:376-410`），而解析不指定分类（`cf.svc:540-548`、`v.svc:366-375`）。
- **影响**：科目分类错落 → 报表归行错误（例如同名科目一个在资产类一个在损益类，落到哪张表取决于 sortOrder）。
- **建议**：候选链改为「分类 + 名称」或直接配置科目 id；`v.svc:subjectByName` 补 `orderBy` 并限定分类。
- **证据**：`schema.prisma:2338-2340`、`cf.svc:540-548`、`v.svc:366-375`、`catalog:412-424`。

### SR-D-12 应付台账显示「候选链猜的科目」，应收台账没有科目列

- **现象**：「确认应付」列表的「会计科目」列在条目没手选科目时，显示**按来源类型猜的首位候选**（如其他应付 → 管理费用），此时凭证还没生成；而应收台账连这一列都没有。
- **根因**：`ledgerSubjectName` 的最后一级是 `catalogSubjectLabel(paymentSubjectNames(sourceType)[0])`（`supplier-payable.service.ts:47-62`），是展示层推断而非落库事实；应收导出列定义没有「会计科目」（`ledger.wb:205-223`）。
- **影响**：财务会把「台账写的科目」当成既定事实，与凭证实际科目不一致时无法察觉；应收/应付对账口径不对称。
- **建议**：台账列显示「已落库科目（来源：条目/对账单）」与水印或「待确认（候选：X）」区分；应收台账补同名列。
- **证据**：`supplier-payable.service.ts:47-62`、`catalog:412-424`、`ledger.wb:154-198`、`ledger.wb:205-223`。

### SR-D-13 现金流量表上期列的期初现金恒为 0、汇率影响不区分期间

- **现象**：现金流量表「上期金额」列的「加：期初现金及现金等价物余额」永远为 0，「期末现金」等于上期净增加额；汇率变动行（行 32）只在本期列有值。
- **根因**：`cashFlowStatement()` 对上期调用 `buildCashFlowStatement({ vouchers: previousVouchers, cashOpening: 0n })`（`3s.svc:171`），汇率影响也未传上期。
- **影响**：上期列勾稽（期初 + 净增加 = 期末）不成立，财务对比两期时会认为报表算错。
- **建议**：上期 `cashOpening` 取「建账期初 + 上期期初之前的资金净额」，并按上期口径计算汇率影响；或明确在表尾写「上期列不填期初」。
- **证据**：`3s.svc:170-174`、`3s:368-371`、`3s:695-703`。

## 10 结论

1. 科目体系本身是「五分类常量 + `(分类,名称)` 唯一键 + 一张 122 条的种子表」，**没有科目编码、没有报表归位字段、余额方向字段虽在但完全不参与计算**（`catalog:25-31`、`schema.prisma:2316-2317`），因此「科目」在报表里的全部意义就是**分类名 + 科目名字符串**。
2. 三大报表只认 `voucher_lines.subject_key` 快照并按名字匹配行（`3s:425-473`、`3s:156-372`）：利润表/资产负债表/现金流量表都用它，现金流量表额外优先用 `cash_flow_entries.category_subject_id` 落行（`3s:669-684`、`3s.svc:228-240`）——**这条「收支类目 → 现金流量表」是唯一打通的业务属性传导路径**。
3. 断点集中在三处：①**科目改名/换分类不级联凭证与期初快照**（SR-D-02），导致「科目跟着业务走」在历史数据上断链；②**收支流水与凭证两套来源**（SR-D-07/08/09），收支类目/金额可改而凭证不重算，利润表与现金流量表可能对同一笔给出不同分类；③**红冲后报表不归零**（SR-D-01），原凭证被排除而红字被计入，这是三张表共同的错账来源。
4. 「资金科目」有三套互不一致的识别规则（报表 `isFundSubject`、资产负债表行前缀、凭证文本判定，`3s:64-78`/`3s:158`/`v.domain:69-72`），加上「其他货币资金/银行明细」口径不一致，是现金流量表与资产负债表对不上的结构性原因（SR-D-06）。
5. 报表口径的护栏只有一条单元测试级的覆盖度守卫（`3s:734-767`，仅 `apps/api/test/unit/finance-three-statements.test.cjs:62-68` 调用）；生产环境新增/改名科目、新增自建类目都不会有任何告警，资产负债表甚至不输出 `unmapped`（`3s.tbl:90-101`），因此「报表静默少钱」是当前体系最危险的失败模式（SR-D-02/03）。
