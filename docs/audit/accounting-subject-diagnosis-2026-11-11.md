# 会计科目病灶诊断（2026-11-11）

> 范围：Dilee ERP 财务板块的「会计科目」全链路 —— 科目主数据 → 收支流水 → 凭证 → 报表 → 导出件 → 前端。
> 性质：**只诊断，不改业务代码**。
> 方法：4 路并行审计（A 主数据层 / B 三大报表匹配层 / C 凭证与流水语义层 / D 报表取数与前端层），共 71 条原始病灶（A16 + B13 + C19 + D23），去重合并后 **31 条**；关键结论均已由主审复核代码行号或实跑脚本验证。
> 原始报告：`tmp/subject-audit/{A,B,C,D}.md`（另附 `matrix.md` 覆盖矩阵、`audit.mjs`、`compare-catalog-sql-seed.mjs` 两个可复跑取证脚本）。

## 2. 问一：是否硬编码？—— 是，分三层，只有第 1 层是良性的

### 2.1 第 1 层：科目清单（硬编码，但**当前无漂移**，风险可控）

`ACCOUNTING_SUBJECTS`（121 条）是硬编码常量，**在迁移 SQL 里手抄了第二份**（`20260917120000_accounting_subjects/migration.sql:120-241`）；补充科目「工资支付」在 `SUPPLEMENTARY_SUBJECTS` 与 `20260921120000_.../migration.sql` 各一份；五个类目名在 catalog 常量与 `20261107200000_.../migration.sql` 各一份。

实跑比对结果（`tmp/subject-audit/compare-catalog-sql-seed.mjs`）：

| 比对项 | 结果 |
|---|---|
| 主表 121 条（分类/名称/余额方向/sortOrder） | **完全一致**，无差集、无字段不一致 |
| 补充科目「工资支付」 | 一致（成本类 / 借 / 715） |
| 五个类目名与顺序 | 一致 |
| `prisma/seed.ts` | **无第四份字面量**，直接 `import` 常量 |

**结论：这部分是良性硬编码。** 三处被三条守卫测试静态钉住，改一处漏一处会被测试拦住。
但要注意：**这些是一致性守卫，不是正确性守卫** —— 三份副本一起改错，测试仍然全绿。

### 2.2 第 2 层：科目 → 报表行的映射（**这是最重的病灶**）

三大报表的每一行都靠**科目名称字面量**认领科目。实跑统计（`finance-three-statements.ts`，排除注释）：**65 处 `named()` + 7 处 `prefixed()`，分布在 45 行报表定义里**：

```ts
// :214 货币资金
match: only("资产类", prefixed("银行存款"), prefixed("库存现金"), named("其他货币资金"))
// :311 销售费用
match: only("损益类", prefixed("销售"))
// :312 管理费用
match: only("损益类", prefixed("管理"), named("其他管理费用"))
// :381 进项税（连客户名都写进代码了）
only("负债类", named("应交税费-进项税", "应交税费-进项税--祥恩线业"))
```

而科目主数据是**财务随时可改**的：`accounting-subject.service.ts:77-122` 的 create / update 只校验「类目存在 + 同类别内不重名」，改名、改分类、新增都不设限。

文件自己的注释已经写明了这个风险（`:826`）：

> `named("应交税费-进项税--祥恩线业")` 少一个横杠就永远匹配不上，而那一行会静默变成 0。

### 2.3 第 3 层：业务判据（前缀/包含/裸名候选）

见 §5。这一层是「硬编码」与「前缀判断」两个问题的交汇点。

## 3. 问二：是否存在多种语义？—— 一个"科目"四种职责、五种表示法

### 3.1 四种职责，分散在 2 张表 4 个列，彼此无一致性校验

| 职责 | 字段 | 语义 | 谁写 | 谁读 |
|---|---|---|---|---|
| ① 记账对方科目 | `cash_flow_entries.subject_id`（必填） | 销账那条现金分录的**另一头**（已挂账付款 = 应付账款） | 所有建单/过账路径 | **凭证生成** |
| ② 业务分类 | `cash_flow_entries.category_subject_id`（可空） | 这笔钱**算什么**（管理费用 / 房租费） | 仅收付款单过账时由 `settledDocuments` 推导 | 流水列表、收支报表、**现金流量表落行** |
| ③ 记账科目 | `voucher_lines.subject_id` | 分录真正的记账科目 | 凭证落库时按**科目名**反查得出 | 利润表、资产负债表 |
| ④ 辅助核算维度 | `voucher_lines.business_subject_id` | 流水的收支类目副本 | 同上 | 凭证纸（可选显示） |

关键在于：**同一笔业务，现金流量表看 ②，利润表/资产负债表看 ③，两者不保证一致，冲突时静默取一个。** 这就是 C 报告里 C-3 那条 P0 的实质。

### 3.2 五种表示法，同一科目在不同地方长得不一样

| 表示法 | 格式 | 出现在哪 |
|---|---|---|
| `subject_id` / `category_subject_id` | UUID | 数据库 |
| 科目键 | `分类/名称`（无空格） | `voucher_lines.subject_key`、期初余额、报表归集 |
| 科目文案 | `分类 / 名称`（两侧空格） | 界面下拉、台账、采购对账明细、付款单"总账科目" |
| 裸名称 | `管理费用` | 收支明细「项目」列、`voucher_lines.subject_label`、记账对方科目列 |
| 带账户后缀 | `银行存款—农业银行5706` | 凭证资金行的 `subject_label` |

`sliceSubjectKey` 用**第一个** `/` 切分，所以科名含 `/` 恰好安全（类目在前），但**类目名含 `/` 会被切错**，而 DTO 只限制了 `@MaxLength`，没有字符白名单。

### 3.3 字段名复用一个 `subjectName`

`finance-report-query.service.ts:306` 的 `subjectName` 是 `分类 / 名称`（复合），`:931` 的 `subjectName` 是裸名称 —— 同名两义。这是导出件 6 种写法的直接来源。

## 4. 问三：多种语义混乱是否影响业务流程？—— 四条可复现的事故链

四条的共同特征：**金额错，但报表依然平衡、勾稽依然 ✓，系统不报任何错。**

### 事故链 S1：财务改一个科目名

```
财务在「会计科目」页把「销售费 运费」改成「运费」
  → prefixed("销售") 不再命中（名字不以"销售"开头）
  → 利润表「减：销售费用」行少算这一块
  → 该行是减项，勾稽靠「未分配利润」兜住 → 报表仍然平
  → 财务看到的是"这个月销售费用少了 N 元"
  → 系统没有任何提示（利润表表尾只在「一条行都没命中」时才点名，
     而这里命中的是"没有"这一状态，不是 unmapped）
```

同时：历史凭证的 `subject_label` 快照仍是旧名「销售费 运费」，如果该行 `subject_id` 为空，旧名还会继续命中 —— **同一个科目在报表里被拆成"新名的不进、旧名的进"两截**。

### 事故链 S2：财务停用一个科目

```
财务把「原材料」停用（完全合法：停用而非删除）
  → 候选链 raw_material_inbound = ["原材料", "主营业务成本"]
  → 第一个候选查不到（isActive: false 被过滤）
  → 静默退到「主营业务成本」
  → 采购入库从「存货」变成「成本」
  → 资产负债表存货减少、利润表营业成本增加，两张表同时错
  → 两个数看起来都"合理"，没有人会发现
若「原材料」与「主营业务成本」都停用 → 抛 422，采购付款全链卡死
```

### 事故链 S3：财务新增一个科目

```
财务新增「运费」（损益类，合法操作）
  → 63 处 named()/prefixed() 一个都不命中
  → 金额进入 unmapped
  → 利润表：表尾有一行小字点名 ✓
  → 现金流量表：表尾有一行小字点名 ✓
  → 资产负债表：完全没有出口 ✗ ← 静默少算
```

### 事故链 S4：一笔付款核销了多张单据

```
付款核销了「备用金」+「房租费」两张单据
  → 收支流水只有一格"收支类目"
  → 取"金额最大的那条单据的科目"（dominantDocumentSubject）
  → 备用金那部分金额在收支报表里被记成「房租费」
  → 凭证上却是「应付账款」（记账对方科目）
  → 同一笔钱在 3 个地方有 3 个科目
```

## 5. 问四：是否用"科目名字符串前缀"判断业务语义？—— 是，5 个判据族、11 个代码位置、15 处字符串判断

> 计数口径：`prefixed(` 7 处（:214×2、:267、:311、:312、:395×2）；`startsWith(` 6 处（:80、voucher.domain:85、:90、voucher.service:1036×2、:1537×2）；`includes("现金")` 1 处（voucher.domain:71）。合计 15 处字符串判断，落在 11 个代码位置、归属 5 个判据族。

| # | 判据族 | 位置 | 前缀/字面量 | 决定什么业务语义 | 改名后 |
|---|---|---|---|---|---|
| 1 | `prefixed()` 报表认领 | `finance-three-statements.ts:214` | `银行存款` / `库存现金` | 哪些科目进资产负债表「货币资金」 | 该行静默归零 |
| 2 | 同上 | `:267` | `应交税费` | 哪些进「应交税费」行 | 该行静默变 0 |
| 3 | 同上 | `:311` / `:395` | `销售` | 哪些进利润表「销售费用」行 / 现金流量表第 8 行 | 该行静默变小 |
| 4 | 同上 | `:312` / `:395` | `管理` | 哪些进「管理费用」行 | 该行静默变小 |
| 5 | `isFundSubject` | `:80` | `库存现金` + 精确名单 | 哪些分录算"资金分录"→ 决定现金流量表是否计入 | 整笔从现金流量表消失 |
| 6 | `isCashFamilySubject` | `voucher.domain.ts:85` | `库存现金` | 「备用金付款」≠欠款而是**资金搬运** → 决定资金侧科目 | 凭证变成「借 库存现金 / 贷 库存现金」自我转账（2026-10-16 修过的 bug 复现） |
| 7 | `isBankFamilySubject` | `voucher.domain.ts:90` | `银行存款` | 同上（银行侧） | 静默失效（**生产零调用**，仅单测引用） |
| 8 | `fundSubjectFor` | `voucher.domain.ts:71` | `includes("现金")` | 结算方式/账户名含"现金" → 库存现金，否则银行存款 | 财务改一个字典项名，资金科目整批翻转 |
| 9 | 凭证资金行定位 | `voucher.service.ts:1036` | 硬编码 `"银行存款"` / `"库存现金"` | 编辑凭证时找"哪一行是资金行" | 找不到 → 模板资金行留空 |
| 10 | 同上 | `voucher.service.ts:1537` | 常量版（同 9） | 回填资金行科目名 | 同上；且与同方法内 `:1533`（键精确相等）**判定不对称**，历史行永远修不好 |

**为什么这一层特别危险**：这些判定**全部发生在财务可自由修改的显示名上**。财务的合法操作（改名、新建细分科目、调整类目）会让判据失效，而系统**既不报错也不告警** —— 只是金额少了一块。

**一个需要澄清的事实**：前缀写法再乱也不影响今天的命中（「管理费厂房装修费用」「管理 -财产保险」「销售 -业务提成」「销售 潘通色卡」这些不规范的科目名都因为首字是「管理」「销售」而被 `prefixed` 覆盖）。真正的洞在反面：**没有这些前缀的新科目会三张表全落空**（「运费」「差旅费」「办公用品」「其他管理费」）。

## 6. 问五：其他问题

### 6.1 资产负债表没有「未归位科目」出口（P0）

`buildBalanceSheetTable`（`finance-three-statements.tables.ts:66-117`）**从头到尾没有引用 `report.current.unmapped`**；而利润表（`:126-128`）和现金流量表（`:142-144`）都引用了。`BalanceSheetResult` 里明明算出了 `unmapped`（`finance-three-statements.ts:624`），但资产负债表就是不显示。

更糟的是：勾稽不平衡时，`:98-101` 的提示**把它归因为"只录了银行账户期初"** —— 如果是未归位科目造成的不平衡，这条提示会把财务引向错误的方向。

**后果**：S3 那条链里新增科目的金额，在资产负债表里是**彻底静默**的。

### 6.2 现金流量表对成本类科目的覆盖是 12/18（P1）

现金流量表第 5/6/8 行按名字逐条硬编码，18 个成本类科目只覆盖 12 个。**落空的 6 条**（主审独立复算确认）：

```
生产成本、劳务成本、制造费用、工程施工、机械作业、辅助生产成本
```

其中最扎眼的是**「制造费用」**—— 制造费用的现金支出是最典型的经营现金流出，而它现在会整笔落进 `unmapped`。同族不一致：`基本生产成本` 进了"支付给职工"行（`:386`），但 `生产成本` 没进。

注意：仓库自带的覆盖度守卫（`checkStatementCoverage`）**抓不到这个洞**，因为它检查的是"该科目是否被**任意一张**报表认领"，而不是"每张表都认领"。

### 6.3 科目表里根本没有「库存现金」这个科目（P1）

`voucher.domain.ts:26` 定义 `FUND_SUBJECT_CASH = "库存现金"`，资金分录的 `subject_key` 就写它。但科目表 122 条里**只有「库存现金（备用金）」，没有「库存现金」**（`accounting-subject-catalog.ts:35`）。

后果：`resolveSubjectIdsByName` 按名字查不到 → 所有**现金**资金分录的 `voucher_lines.subject_id` 恒为 `null`。报表靠 `normalizeSubjectKey` 的文本归一兜住了（所以金额没错），但**任何按科目 id 聚合的明细账/新报表都查不到现金分录**。这是一个"幽灵科目"。

### 6.4 软删守卫漏了 4 类引用（P1）

`accounting-subject.service.ts:143-158` 的 `usageCount()` 只数了 7 张表，`remove()` 的注释承诺「已被**任何**业务数据引用时直接拒绝」。实际漏掉了：

- `voucher_lines.subject_id`（凭证分录的记账科目）
- `voucher_lines.business_subject_id`
- `cash_flow_entries.category_subject_id`（收支类目）
- `accounting_opening_balances.subject_key`（**文本键，完全没有外键保护**）

后果：软删一个只被凭证引用的科目能成功，之后 `finance-three-statements.service.ts:279-291` 的 `SubjectRefs` 索引（`deletedAt: null`）就不含它 → 凭证行回退文本匹配 → 若该科目改过名，新旧文本都不命中 → 金额进 `unmapped`（而资产负债表还不显示，见 6.1）。

### 6.5 `balanceDirection` 有 6+ 条种子数据方向写反，且全站无人消费（P1）

`grep balanceDirection` 全仓只命中三处：定义常量、写库、查库投影。**没有任何计算或校验读它**。而数据本身是错的：

| 科目 | 现值 | 应为 |
|---|---|---|
| 损益类/主营业务收入 | 借 | **贷** |

## 8. 根因（两条，其他都是派生）

### 根因 1：会计科目没有不可变编码，`分类/名称` 这段**人可读文本**被当成了编码

老表 `科目表(2).xls` 的「科目代码」整列（`1001` / `100201` / `222101001` 三层结构）被**明确丢弃**（`accounting-subject-catalog.ts:7`、`schema.prisma:2323`），理由是用户口径「那个编码的可以不管」。

代价是：`accountingSubjectKey(category, name)` 拼出来的字符串同时充当"稳定标识"和"科目编码"，而它**不稳定** —— 改名即换键。于是：

- 两张表把键当**快照**存下来（`voucher_lines.subject_key`、`accounting_opening_balances.subject_key`），改名后与主数据永久脱节；
- 所有"认科目"的地方只能退化为**按名称/前缀/文本相等**判断（63 处报表匹配 + 12 处前缀判据 + 5 处候选链）；
- 期初余额表连 `subject_id` 都没有，只有文本键，改类目名后级联不到。

**这条根因直接派生了 P0-1、P0-2、P0-3、P1-2、P1-11、P1-12、P1-13。**

### 根因 2：业务口径落在**可改的显示名**上，而一致性只靠人工纪律与静态测试

「什么是资金科目」「哪些科目进货币资金」「工资付款归哪个科目」「余额该在哪一侧」—— 这些本该是**数据属性**，现在全是代码里的字符串字面量。财务的合法操作（改名、新建、调类目）会让判据失效，而：

- 运行时**零守卫**（`checkStatementCoverage` 只在测试里跑）；
- 守卫测试只保护**常量**（第 122 个科目永远不在检查范围内）；
- 缺口出口不完整（资产负债表**完全没有**出口）。

于是事故的统一形态就是：**改一个名字 → 判据失效 → 金额落空或落错行 → 只有表尾一行小字（资产负债表连小字都没有）→ 勾稽照样平。**
