# 财务、仓库及跨模块联动审计

- 审计日期：2026-08-30
- 范围：财务、仓库、采购、销售、生产、人事及订单追溯
- 结论级别：P0 阻断闭环，P1 重要缺陷，P2 体验/治理改进
- 术语基线：跨模块统一使用“订单号”；原料、成品、库存事实、应收、应付、工资台账等沿用项目术语词典。

## 审计结论

当前系统已经具备一条可工作的“业务事实 -> 派生余额/来源”的后端骨架：原料入库过账会写入 `InventoryFact` 并创建待财务处理的应付来源，生产领料/退料会通过库存事实影响原料余额，成品出库可生成应收来源，员工日报会同步生产薪资来源。数据库模型也保留了订单号、来源单据、状态、审计和逻辑删除字段。

但系统还不能称为财务与仓库闭环，主要断点是：

1. **P0：应付链路断在“来源”与“应付确认”之间。** 原料入库生成的是 `PayableSource`，财务页面展示的是 `SupplierPayableEntry`；没有明确的页面动作把每批来源转成应付条目，财务人员无法稳定接收全部到货应付。
2. **P0：应付对账未实现。** 财务页面的“应付对账”实际复用了应收对账数据，后端只有 `ReceivableReconciliation`，没有供应商/采购单/原料入库维度的应付对账对象。
3. **P1：财务核心业务的编辑能力不完整。** 应收、应付、收付款、对账主要只有创建、确认、过账、冲销接口，没有统一的草稿编辑、确认回退、版本冲突和影响预览流程。
4. **P1：仓库入口和报表不完整。** 原料入库由采购目录承载，仓库页主要展示原料流转和成品质检组件；缺少以库存分类、物料、单位、订单号为中心的原料仓储情况独立工作区。
5. **P1：跨模块派生数据缺少统一的可见性。** 订单工作台/财务页未统一展示“采购数量 -> 到货 -> QC -> 入库 -> 应付 -> 付款”和“生产 -> 成品 QC -> 入库 -> 出库 -> 应收 -> 收款”的完整数量与金额差异。
6. **P2：部分查询仍偏内部 ID。** 财务薪资、绩效和部分来源操作使用员工/来源 UUID 输入或展示，降低业务人员按姓名、订单号、采购单号定位的可用性。

## 现状链路图

```text
销售单(订单号)
  ├─ 成品出库 -> InventoryFact(成品减少) -> ReceivableSource -> 应收确认 -> 收款核销
  └─ BOM -> 采购单 -> 收货批次 -> 来料质检 -> 原料入库
                                      ├─ InventoryFact(原料增加) -> 原料库存余额
                                      └─ PayableSource -> 应付条目确认 -> 付款核销

生产单(订单号)
  ├─ 生产领料/退料/报废 -> InventoryFact(原料变化) -> 原料余额
  ├─ 工序员工日报 -> ProductionPayrollSource -> PayrollLedger -> 工资支付
  └─ 成品 QC -> 成品入库 -> 成品库存 -> 成品出库 -> 应收来源
人事员工 -> 考勤/绩效 -> 薪资台账调整/参考
```

## 已实现能力核实

### 财务

- 应收来源可从已过账/已发货/已签收的成品出库生成，带订单号、销售单、客户、数量、价格快照和金额。
- 收款支持草稿、分配核销、部分收款状态、已过账冲销，并在事务中刷新应收状态。
- 原料入库生成的待处理应付来源包含采购单、采购明细、供应商、入库数量、单价、税率、币种和金额快照。
- 应付条目支持从来源创建、确认、付款核销和冲销；重复来源有唯一关系保护。
- 工资台账有生产薪资来源、基本工资、绩效、扣款、调整、支付分配和状态刷新。
- 财务页面已经接入应收、收款、应付、付款、对账和人事财务数据，但仍把若干人事操作作为财务页按钮，职责边界需要产品确认并统一导航。

### 仓库

- 原料入库只允许消费可入库的来料质检数量，支持草稿编辑/删除、过账、库存事实和入库冲销。
- 原料领料、退料、报废和冲销使用统一的原料流转事实，领料预览会返回当前库存、BOM 参考量、采购到货/未到货和累计领料风险。
- 成品入库、不良品入库、成品出库和客户退货已有独立服务，库存余额由事实汇总而来。
- 库存禁止直接编辑余额，过账/冲销在事务中校验余额和幂等性。
- 仓库页使用项目组件库的 `DataTable`、`Sheet`、`Dialog`、`Select`、`Input`、`Button`，没有发现以原生表单控件替代核心业务控件的路径。

### 其他模块联动

- 采购单绑定订单号和 BOM，物料使用统一物料主数据 ID；BOM 中的销售产品不应进入原料物料池，服务层已有原料类型校验。
- 生产日报按生产单、生产工序、员工和日期保存；日报保存会重算差异告警、生产薪资来源和生产进度。
- 成品出库是应收来源的触发事实，生产完工与销售发货之间仍需要订单工作台统一追溯视图。

## 缺陷与待开发点

### P0：必须先修复

#### 1. 应付来源无法稳定进入应付台账

**现象：** 原料入库过账写入 `PayableSource`，而财务查询的是 `SupplierPayableEntry`。财务页面没有“从待处理来源创建应付”或批量接收动作，导致到货已经入库但应付列表可能为空。

**影响：** 采购到货、库存和付款无法形成可核对的财务事实；同一批入库可能被人工重复建应付。

**改进：** 增加待处理应付来源工作区；单条/批量接收动作必须幂等，复制采购单、入库批次、物料、数量、单价、税率和订单号快照；接收后显示应付单号和差异。

#### 2. 应付对账对象缺失

**现象：** 财务页同时显示“应收对账”和“应付对账”，但后端对账服务和数据模型只覆盖销售订单/客户应收。

**影响：** 无法按供应商、采购单、原料入库批次核对系统应付与外部对账单。

**改进：** 新增供应商应付对账对象和服务，快照待确认/已确认应付、已付款、冲销/调整和外部余额；支持差异、处理说明、附件、订单号/采购单筛选和审计。

### P1：应在本期排期

#### 3. 财务单据编辑和可回退状态不统一

当前控制器以 POST 动作为主，缺少统一的草稿 `PATCH`、版本字段、影响预览和“已确认 -> 草稿/待复核”的受控回退。收付款只能冲销，不能修正草稿基本信息；应收/应付金额调整也没有统一入口。

应建立通用规则：草稿可编辑；确认后禁止静默覆盖；回退必须先做影响预览；已经核销/付款的记录只能通过调整、退款、补收、补付或冲销更正；所有动作记录原因和前后快照。

#### 4. 原料库存工作区缺少独立的业务视图

库存余额服务存在，但仓库页面没有独立的“原料仓储情况”工作区来按物料、单位、库存类别、订单号查看收发存、可用量和风险。原料入库入口位于采购页，仓库职责不清。

应在仓库模块提供只读库存总览、收发明细、来源追溯和导出；数量仍只能由动态事实改变，页面不得提供余额直接编辑。

#### 5. 跨模块数量/金额派生没有统一汇总

订单工作台应至少汇总：BOM 需求、采购下单、收货、QC 合格/不合格、原料入库、应付来源、应付确认、付款；生产侧应汇总：计划、日报、领料、成品 QC、成品入库、成品出库、应收、收款。当前这些信息分布在多个页面，缺少同一订单号下的差异与告警视图。

#### 6. 物料和单位维度校验需收紧

物料主数据使用 `materialType` 区分原料/产品，生产领料已有原料校验；但库存余额批量查询按物料聚合时未把单位作为返回维度，跨单位数据容易被误合并。应统一返回物料 ID、名称、编码、单位 ID/名称、库存类别和数量，并在所有入口阻止单位不一致。

#### 7. 财务业务查询应面向业务身份

员工、客户、供应商应使用名称+编号选择；来源应显示订单号、采购单号、入库单号/应收单号。内部 UUID 只作为不可见关联键，不能要求财务人员手工输入。

### P2：治理和体验改进

- 财务页的人事按钮与人事页重复，需确定“人事录入、财务结算”的职责分界，避免同一记录有两个入口但行为不一致。
- 应收对账当前命名与应付对账混在同一标题区域，需改为两个独立工作区，避免误操作。
- 采购、仓库、财务的批次命名应统一使用“收货批次、来料质检批次、原料入库批次”，用户界面可显示“第 N 批”，不能用模糊的“第一批应付”作为数据库字段。
- 所有跨模块列表补充日期、订单号、供应商/客户、状态、批次和风险筛选，并支持 CSV/Excel 导出。
- 继续补充真实 PostgreSQL + 登录会话 + 浏览器写入型回归；现有测试记录显示真实数据库/HTTP/E2E 环境缺失时会被阻断，不能以 TypeScript 构建通过替代链路验收。

## 推荐实施顺序

1. **应付接收闭环：** 待处理应付来源列表、幂等接收、应付条目详情和状态/金额差异。
2. **应付对账：** 供应商应付对账模型、API、页面、附件和差异处理。
3. **财务单据治理：** 草稿编辑、版本冲突、影响预览、受控回退和统一审计。
4. **仓库库存工作区：** 原料/成品库存总览、收发存、来源追溯、筛选和导出，调整仓库与采购入口边界。
5. **订单联动工作台：** 以订单号聚合销售、采购、仓库、生产、应收、应付和工资来源，显示缺失、差异和风险。
6. **回归验收：** 专用 PostgreSQL 测试库、API 合约、领域测试和 Playwright 端到端覆盖，至少跑通两条完整链路。

## 实施切入点与验收口径

推荐的最高测试切入点是“来源事实接收服务”和“订单号联动摘要”：前者一次验证入库来源到应付条目的幂等、一致性和状态；后者验证财务、仓库及上下游是否能看到同一订单的数量/金额事实。页面测试只验证可见行为和权限，不绑定 Prisma 查询实现。

最低验收链路：

```text
已确认销售单 -> BOM -> 采购单 -> 收货批次 -> 来料质检 -> 原料入库过账
  -> 原料库存余额 + 待处理应付来源 -> 应付接收/确认 -> 分批付款/核销 -> 应付对账

生产单 -> 工序员工日报 -> 生产薪资来源 -> 薪资台账 -> 工资支付
生产单 -> 成品 QC -> 成品入库 -> 成品出库 -> 应收来源 -> 收款核销
```

每条链路都必须验证：订单号可追溯、数量/金额快照可解释、重复请求不重复记账、草稿可编辑、已确认事实可回退或冲销、库存不出现负数、应收应付余额与支付分配一致、操作均有审计记录。

## 不在本期范围

- 会计总账、发票自动验真、银行/供应商外部系统直连。
- 多仓库、库位、批号成本、先进先出和单位换算。
- 自动排产、自动采购建议和工资税费自动计算。
- 审批流的完整配置；本期只保留权限、操作人、原因和审计门禁。

## 进一步决策

- 明确“原料入库过账即生成待处理应付来源”是否为最终财务口径；若改为 QC 完成即生成，必须保持入库数量和可计价数量一致。
- 确认条件接收数量是否立即进入可用原料库存，以及应付是否按条件接收计价。
- 确认历史数据中没有批次号的收货/入库记录如何标识，建议统一为“历史未分批”并保留原始来源。
- 确认应付对账按采购单汇总还是按入库批次逐笔对账；建议默认批次明细、采购单汇总。
