## 0. 结论页

### 0.1 六个判断

| # | 判断 | 依据（一句话） |
|---|---|---|
| **1** | **借贷方向没有写反，凭证也没有算错** | 21 张未删除凭证每张只有 2 行、借方合计＝贷方合计，0 张不平、0 张单边；自动路径的借/贷在代码里是对的 |
| **2** | **「会计科目」不是一个字段，而是 4 个落点共用一个词** | 应付/应收单据 `subject_id`、流水 `subject_id`（记账对方科目）、流水 `category_subject_id`（收支类目）、凭证行 `subject_label`（文本快照）；界面上 22 处全叫「会计科目」 |
| **3** | **生产库里所有「科目/方向不对」的凭证，都是财务手工改出来的** | 12 张挂账凭证中 6 张贷方不是「应付账款」，这 6 张**恰好**是 6 张有 `voucher.update` 记录的；改过的凭证全错，没改过的全对 |
| **4** | **但流程确实有错，而且是会让账错的错** | 挂账只落草稿却被当成已挂账、收付款凭证按单据全额而非核销额、冲销/红冲四套状态互不联动、确认与挂账跨事务、科目选了不落库、采购应付链路从未跑通 |
| **5** | **报表不可信不是算错，是「两套来源 + 文本快照」** | 三大报表只认已过账凭证；收支明细/汇总读流水；期初绕过凭证直改；凭证科目是「分类/名称」文本，主数据一改名就静默失配（现库 23.5% 的行已失配） |
| **6** | **三步走就能把这条链拉回正轨**：先堵手工改单的护栏、再把科目收敛成单一事实源、最后修报表口径与历史数据 | 见 §8 修复路线；其中 §8 批次 A 不依赖任何会计口径拍板，可立即开工 |

### 0.2 你的直觉哪里对了、哪里需要修正

**对的部分**：这条链上确实存在业务流程错误，而且正是它们让「会计科目、借贷方」看起来不可信。

**需要修正的部分**：问题不在「借贷写反」，也不在「系统把科目算错了」，而在下面这条因果链——

```text
系统按权责发生制生成两张正确的凭证
   挂账：借 业务科目 / 贷 应付账款
   付款：借 应付账款 / 贷 银行存款
        │
        ├─ 但界面上三个地方都叫「会计科目」，付款凭证上那个「应付账款」看着就像错的
        ├─ 而且挂账凭证只是草稿、没人过账 → 报表里根本看不到「应付账款」
        ├─ 而且确认弹窗里选的科目压根没落库 → 台账和凭证显示的科目不一样
        ▼
财务判断「系统科目错了」→ 去凭证编辑器手改 → 改成「借 费用 / 贷 银行存款」
        ▼
应付账款永远不贷、费用记两遍、银行记两遍；改单只记 {line_edited:true}，改前科目无痕
```

所以**修复的关键不是改借贷规则，而是**：把「业务科目 / 记账对方科目 / 分录科目」三个概念在系统里分开且贯通，同时堵住「手改自动凭证」这个口子。否则修完业务逻辑，用户过两天还会再改一遍。

### 0.3 一句话根因

> **一张业务事实的「科目」被拆成 4 个落点，其中 3 个落点没有一致性约束、1 个（凭证）还可以被任意手改且不回写来源；再叠加 6 个会让业务状态与账务状态脱节的流程缺陷，于是「台账有数、总账没有应付账款、流水全被红冲」。**

### 0.4 必须先拍板的 3 个会计口径（其余见 §9）

| # | 问题 | 现状 | 为什么必须你定 |
|---|---|---|---|
| **A1** | 原料入库确认应付时，借方记 **原材料（存货）** 还是 **主营业务成本（损益）**？ | 候选链首位是「主营业务成本」，即入库即费用化 | 这一条决定资产负债表「存货」和利润表「成本」两处的金额；制造业若采用「入库存货、领用时结转成本」，现在的口径是错的 |
| **A2** | 确认应付/应收后，挂账凭证是 **自动过账**，还是必须主管复核后过账？ | 只生成草稿，无人管；必须到凭证页逐张点过账，漏点无人发现 | 决定「确认后资产负债表能不能立刻看到应付账款」；也决定要不要做制单/审核分离 |
| **A3** | 「业务科目」的最终定位：**只做辅助核算维度**（凭证仍按会计准则记 应付账款），还是要求凭证分录上直接显示业务科目？ | 现在是前者（设计对），但界面没讲清楚，导致用户改单 | 决定 §8 批次 B 是「只改展示与护栏」还是「要改凭证结构」；推荐前者 |

## 1. 财务板块的骨架

### 1.1 边界：财务在系统里管什么、不管什么

| 管 | 不管（V1.0 明确没有） |
|---|---|
| 应收/应付来源的确认与金额最终确认 | 总账凭证的自动过账（要人点） |
| 客户收款、供应商付款、工资付款的登记与核销 | 发票/税务（`tax_rate` 只存不用，不拆进项/销项） |
| 应收调整（退款/红字/折让/坏账）、对账 | 银行自动对账、回单 |
| 会计科目主数据、收支流水、记账凭证、三大报表 | 成本核算（无领用结转、无标准成本、无批号成本） |
| 生产工资来源汇总、工资台账、工资支付 | 自动计薪、社保个税 |
| 期初余额、外汇一览表、账龄/管理报表 | 期间关账（无「已结账」状态）、审批流 |

### 1.2 六条管线全景

```text
① 应收（AR）
   成品出库过账 → ReceivableSource(draft) → 确认应收[挂账] → CustomerPayment(draft)
   → 分配 ReceivableAllocation → 收款过账 → 流水 → (人工)凭证 → 报表

② 应付（AP）
   原料入库过账 / 外加工签收 → PayableSource(pending_finance) → 接收应付 → SupplierPayableEntry(draft)
   → 确认应付[挂账] → SupplierPayment(draft) → 分配 → 付款过账 → 流水 → (人工)凭证 → 报表
   其他应付（手工/Excel 导入）没有上游业务单据，直接建 SupplierPayableEntry(draft)

③ 工资（Payroll）
   员工日报 → ProductionPayrollSource → PayrollLedger(draft→confirmed)
   → SalaryPayment(draft) → 分配 → 工资付款过账 → 流水 → (人工)凭证 → 报表

④ 资金（银行/现金）
   Bank(banks) 账户池；BankTransfer 账户互转（只进余额，不进流水/凭证）
   收支流水手工录入/更正/冲销

⑤ 账务（凭证）
   Voucher / VoucherLine：来源 = 收支流水 / 应付挂账 / 红冲 / 手工
   状态 draft → posted → reversed（+ 软删除）；红冲生成反向凭证

⑥ 报表
   三大报表（利润表 / 资产负债表 / 现金流量表）：只取已过账凭证 + 期初余额
   收支明细表 / 收支汇总表 / 外汇一览表：直接取流水
   账龄表、科目余额表、试算平衡表：**不存在**
```

### 1.3 四层财务事实与四套互不校验的状态机（这是所有错配的土壤）

| 层 | 对象 | 状态 | 谁能改 | 与其他层的关系 |
|---|---|---|---|---|
| L1 业务单据 | 入库单、签收单、出库单、工资台账 | 各自状态机 | 业务模块 | 过账后派生 L2 |
| L2 财务条目 | `supplier_payable_entries` / `receivable_sources` | `draft / confirmed / partially_paid / paid / reversed / voided` | 财务 | 确认时派生 L4 挂账凭证（**跨事务，见 §6.3-P0-4**） |
| L3 现金流水 | `cash_flow_entries` | `posted / reversed`（无草稿态） | 财务（**含金额/方向/科目，自动流水也能改**） | 过账后派生 L4 凭证（**人工逐条触发**） |
| L4 凭证 | `vouchers` / `voucher_lines` | `draft / posted / reversed`（+ 软删除） | 财务（草稿可改分录） | 报表唯一取数来源 |

**关键事实**：这四套状态之间没有事务边界、没有反向指针、没有一致性校验。L3 冲销不回写 L4，L4 红冲不回写 L2，L1 作废不检查 L2。于是同一笔业务在四层里可以有四种说法——§6.6 的生产数据就是这四种说法的合影。

### 1.4 财务动作总表（应付侧 21 个，其余见分报告）

| 段 | 动作 | 谁做 | 产出 |
|---|---|---|---|
| 产生 | 原料入库过账 / 外加工签收 | 仓库 / 采购 | PayableSource(pending_finance) |
| 接收 | 接收应付（来源→条目草稿） | 财务或采购 | SupplierPayableEntry(draft)；来源→received |
| 录入 | 其他应付单条/Excel 导入 | 财务 | SupplierPayableEntry(draft, source_type=other) |
| 对账 | 建对账单 / 处理差异 | 财务 | SupplierPayableReconciliation |
| 确认 | 逐条确认 / 批量确认 / 对账确认 | 财务 | entry→confirmed + **挂账凭证(draft)** |
| 付款 | 登记付款草稿 → 过账 + 核销 | 财务 | SupplierPayment(posted) + Allocation(active) + 流水 + entry 状态回算 |
| 记账 | 由流水生成凭证 → 过账 | 财务 | Voucher(draft→posted) |
| 更正 | 回退草稿 / 冲销应付 / 冲销付款 / 删除其他应付 / 入库冲销 / 签收冲销 / 对账单删除 / 凭证红冲 | 财务/仓库/采购 | 各自状态变化（**不联动**） |

## 2. 应付（AP）业务流程与规则

> 完整链路图、21 个环节的输入/写入/门禁/失败回退见 [01-ap-chain.md](finance-review-2026-11-07/01-ap-chain.md)。

### 2.1 五段链路

```text
【1 产生】 原料入库过账 → PayableSource(amount = 数量×结算单价；taxRate 只存不用；status=pending_finance)
          外加工签收   → OutsourcePayableSource(amount = 签收量×加工单价)

【2 接收】 来源 → SupplierPayableEntry(draft)
          金额默认取来源快照；人工覆盖必须填原因；source ↔ entry 一对一（重复调用复用）；来源→received

【3 确认】 entry(draft) → confirmed（事务内）＋ 挂账凭证(draft)（事务外）
          挂账分录：借 成本/费用科目 / 贷 应付账款
          科目优先级：条目 subject_id > 确认弹窗 subject_id > 按来源类型候选链
          例外①金额≤0 不挂账；②对方科目属「库存现金*」视为资金搬运，不挂账

【4 付款】 SupplierPayment(draft) → 过账：写 Allocation(active) + entry 状态回算 + payment=posted（事务内）
          → 事务外写 CashFlowEntry(expense, amount=付款全额)
          对方科目：全部被核销应付都已「挂账」→ 应付账款；否则 人工/条目科目/来源候选链
          收支类目：人工科目 > 核销单据中金额最大的那个科目

【5 记账】 财务到凭证工作台，对流水逐条点「生成凭证」→ 再逐张点「过账」
          付款凭证：借 对方科目 / 贷 银行存款—{结算账户}；金额 = 流水金额 = 付款全额
```

### 2.2 状态机

```text
          ┌───────── reopen(reason) ─────────┐
          ▼                                  │
      draft ──confirm──► confirmed ──付款核销──► partially_paid ──► paid
        │                   │                                        │
        │                   └────────reverse(reason)─────────────────┘ → reversed
        └──(来源作废)──► voided
        删除（仅 other，draft/confirmed，无 posted 核销）→ 软删除
```

### 2.3 业务规则（40 条中精选 18 条；强度＝强制/未强制/缺失）

| 编号 | 规则 | 强度 |
|---|---|---|
| AP-R-01 | 一笔来源最多一条应付；`payable_source_id` 唯一，重复接收复用（软删则恢复） | 强制 |
| AP-R-04 | 来源→应付金额默认取来源快照；人工覆盖**建单时**必须填原因 | 强制（建单） |
| AP-R-05 | 草稿应付可改金额/确认日期/币种；改金额**不需要原因、不回写来源** | 未强制 |
| AP-R-07 | 只有 draft 可确认；来源已作废不可确认 | 强制 |
| AP-R-08 | 挂账科目优先级：条目 `subject_id` > 确认弹窗 `subject_id` > 来源类型候选链 | 强制 |
| AP-R-10 | **确认＝挂账，不写收支流水、不动银行**（2026-09-24 两步制） | 强制 |
| AP-R-12 | 挂账凭证：借 成本/费用 / 贷 **应付账款**；金额＝应付全额；状态＝**草稿** | 强制 |
| AP-R-14 | **确认与挂账必须同一事务** | **缺失**（状态先提交、凭证后建） |
| AP-R-15 | 付款过账至少核销一条应付，同一付款不得重复核销同一应付 | 强制 |
| AP-R-17 | 单条核销≤应付未核销余额；**核销合计≤付款金额（允许小于）** | 强制 |
| AP-R-20 | **付款金额必须等于本次核销合计** | **缺失**（多付部分无科目） |
| AP-R-21 | 付款必须写收支流水，且与付款过账同生共死 | **缺失**（流水在事务外） |
| AP-R-22 | 付款凭证借方：已挂账→应付账款；未挂账→人工/条目/来源候选链；含混核销整笔按未挂账 | 条件强制 |
| AP-R-23 | 「已挂账」判定＝存在一张未红冲的挂账凭证（**草稿也算**） | **未强制（口径错误）** |
| AP-R-29 | 删除/冲销已确认应付必须联动撤销其挂账凭证 | **缺失** |
| AP-R-30 | 来源作废必须联动应付条目 | 部分（入库有、签收缺） |
| AP-R-36 | 对账差异必须生成调整分录/调整应付 | **缺失**（`adjustment` 恒 0） |
| AP-R-37 | 挂账凭证日期＝确认当日，而非应付 `confirmation_date` | 未强制（补录往期会落错月份） |

### 2.4 应付链的四个结论

1. **设计口径是对的**：2026-09-24 改成「确认＝挂账、付款＝销账」两步，符合权责发生制，不应退回「确认即记账」。
2. **但落地有三处硬伤**：确认与挂账跨事务（P0-4）、草稿凭证被当已挂账（P0-1）、付款凭证按付款全额记账（P0-2）。
3. **科目在应付侧没有单一事实源**：确认弹窗选的 `subject_id` 只在生成凭证那一瞬间有效，**不落条目**（`confirm` 事务里只改 `status`）；而台账显示链却是「条目 > 覆盖对账单 > 候选链首位」，所以台账会显示一个从未被记账的科目。
4. **「其他应付」承担了它不该承担的业务**：生产库 183 条应付 **100%** 是 `source_type='other'`，采购入库链路一条都没跑通（§6.6）。

## 3. 收支流水（CashFlowEntry）

> 完整链路图、12 条产生路径、字段语义表、25 条规则见 [02-cashflow-chain.md](finance-review-2026-11-07/02-cashflow-chain.md)。

### 3.1 只有 4 个真实写入口

| # | 入口 | 金额口径 | 方向 |
|---|---|---|---|
| 1 | 手工新增 / 手工更正 | 用户填 | 用户选 |
| 2 | 供应商付款过账后自动写 | **付款单全额** | expense |
| 3 | 客户收款过账后自动写 | **收款单全额** | income |
| 4 | 工资付款过账后自动写 | **工资付款单全额** | expense |

> 注：`recordConfirmation`（「确认应收/应付时写一条累计流水」）是 2026-09-24 两步制之前的旧口径，**现在全仓无调用方＝死代码**，但单测仍在测它、旧注释仍在引用它。生产库里 90 条 `source_type='supplier_payable_entry'` 的流水（合计 236,661.56，全部已红冲）就是这个旧口径的遗物。

### 3.2 核心：一个「会计科目」三个字段

| 字段 | 界面叫什么 | 谁写 | 干什么用 |
|---|---|---|---|
| `cash_flow_entries.subject_id` | 流水页悬停「记账对方科目」；**凭证纸「会计科目」** | 自动：已挂账→「应付账款」；手工：用户选 | **生成凭证的业务分录科目** |
| `cash_flow_entries.category_subject_id` | 流水页 / 收支明细 / 汇总表「会计科目」 | 自动：条目/对账单/候选链；手工流水**没有这个入参** | **仅显示、筛选、现金流量表落行**，不参与记账 |
| `voucher_lines.subject_label`（文本，无 FK） | 凭证页「会计科目」 | 由上面 `subject_id` 生成；**可被手工改成任意文本** | 利润表/资产负债表/现金流量表的取数依据 |

规则本身的注释写得很清楚（这是刻意的分工），但**界面从来没告诉用户**：付款凭证上那个「应付账款」是「销账对方科目」，不是「这笔钱花在什么上」。用户看到的就是「我选的销售费推广费，怎么变成应付账款了」。

### 3.3 规则（25 条中精选 10 条）

| 编号 | 规则 | 强度 |
|---|---|---|
| CF-R-01 | 金额恒为正数，方向由 `direction` 决定（income/expense） | 强制（库层 CHECK） |
| CF-R-02 | 流水状态只有 posted / reversed，创建即 posted | 强制 |
| CF-R-05 | 自动流水同一来源只写一条（应用层 `findFirst`） | **未强制**（库层无唯一键，且流水写在付款事务之外） |
| CF-R-08 | 自动流水可改金额/方向/日期/科目/银行 | **缺失护栏**（与来源单据完全脱钩） |
| CF-R-11 | 流水冲销＝改状态位，不生成反向流水 | 强制 |
| CF-R-12 | 流水科目必须存在且启用 | 强制（手工与严格路径） |
| CF-R-15 | 手工流水的「会计科目」写 `subject_id`，不写类目 | 设计如此（导致手工流水永远没有业务类目） |
| CF-R-20 | 结算账户（`settlement_account_id`）只做显示与凭证科目名后缀 | 强制（不参与余额/统计） |
| CF-R-24 | 银行余额＝账户期初 + 已过账流水 ± + 互转净额 | 强制（但互转不进流水/凭证） |
| CF-R-25 | 收支明细/汇总取流水；三大报表取凭证 | 强制（**两套来源**，见 §5.3） |

### 3.4 收支流的三个结论

1. **流水已经不是「账」，而是「现金事实的登记簿」**：它的 `subject_id` 是记账用的，`category_subject_id` 是给人看的；两者语义不同、写入方不同、可改性不同，却共用一个中文名。
2. **金额口径与核销脱钩**：流水记付款全额，核销可只覆盖一部分，差额（多付/预付）没有任何科目承接。
3. **流水改了、冲了，凭证不动**：这是「收支报表与三大报表长期对不上」的直接原因。

## 4. 凭证（Voucher）

> 完整来源全集、借贷矩阵逐行证据、生命周期、24 条规则、17 条缺陷见 [03-voucher-chain.md](finance-review-2026-11-07/03-voucher-chain.md)。

### 4.1 来源全集

| `source_type` | 含义 | 生成方式 | 备注 |
|---|---|---|---|
| `cash_flow_entry` | 由一条收支流水生成 | **人工**逐条点 | 幂等：一条流水一张 |
| `supplier_payable` | 应付确认的挂账凭证 | 确认应付时自动 | 一条应付一张，落草稿 |
| `receivable_source` | 应收确认的挂账凭证 | 确认应收时自动 | 同上 |
| `voucher` | 红冲凭证（来源＝被红冲的那张） | 红冲时自动 | 借贷对调、直接 posted |
| `manual` | 手工凭证（折旧/摊销/计提/结转/交税） | 手工 | 无来源，支持多借多贷 |

> `finance-slip*`（付款单/收款单打印件）是**第二套借贷记录，但不是第二套账**：它不写流水、不生成凭证、不动往来，科目是自由文本。但它让「一笔付款」在打印件、流水、凭证三处各有一套科目。

### 4.2 借贷方向矩阵（这是用户最关心的一张表）

| 业务动作 | 借 | 贷 | 金额 | 状态 | 判定 |
|---|---|---|---|---|---|
| 应收确认（挂账） | **应收账款**（按名称解析） | 收入科目（`contra_subject_id` 优先，否则候选链） | 应收全额 | draft | ✅ 对 |
| 应付确认（挂账） | 成本/费用科目 | **应付账款** | 应付全额 | draft | ✅ 对 |
| 　例外：对方科目是「库存现金*」 | 不生成挂账凭证（审计记 `accrual_skipped`） | — | — | 无凭证 | ⚠️ 设计如此，但与应付台账口径脱节 |
| 应付付款（销账） | **全部被核销应付已挂账 → 应付账款**；否则人工/条目/候选链 | 银行存款—账户 | **付款单全额** | draft | ⚠️ **金额口径错**（P0-2） |
| 客户收款（销账） | 银行存款—账户 | 已挂账 → 应收账款；否则收入科目 | **收款单全额** | draft | ⚠️ 金额口径错 + **人工科目可顶掉「应收账款」**（P0-2 附） |
| 工资付款 | 工资支付（成本类）/ 人工科目 | 银行存款 | 工资付款全额 | draft | ⚠️ 金额口径；且**无计提「应付职工薪酬」** |
| 其他应付（常规） | 确认：借 条目科目/贷 应付账款；付款：借 应付账款/贷 银行 | 同左 | 各自全额 | 两张 draft | ✅ 对 |
| 其他应付（资金搬运） | 确认不挂账；付款：**借 库存现金（备用金）/ 贷 银行存款** | 同左 | 付款全额 | draft | ⚠️ 借贷对，但用「应付」单据做资金调拨（见 P1-4） |
| **银行互转/现金调拨** | **无凭证** | **无凭证** | — | 无 | ❌ **整行缺失**（P1-4） |
| 手工凭证 | 提交的方向/行数不限（多借多贷） | 同左 | 借＝贷 | draft | ✅ 对（但科目**不校验科目表**） |
| 手工流水→凭证 | 支出：借 流水 `subject_id`；收入：借 资金科目 | 反向 | 流水全额 | draft | ✅ 对 |
| 红冲 | 原凭证的贷方行 | 原凭证的借方行 | 每行不变 | 红字 **posted**、原凭证 **reversed** | ❌ **报表口径错**（P1-1） |

**一句话**：11 行里凡是真正生成凭证的路径，借/贷符号都对；错的是**金额口径（收付款取单据全额而不是核销额）、状态（草稿被判为已挂账）、科目选取（人工可越过会计准则）**，以及**整行缺失（银行互转没有凭证）**。

### 4.3 生命周期

```text
生成（全部落 draft）
   │  手工 / 挂账 / 由流水
   ▼
 draft ──编辑分录（可增删行、改方向/科目/金额；只校验借贷平衡，不校验科目表）──► draft
   │  ├─ 套模板（工资计提 / 原材料采购 / 交税）
   │  ├─ 重新生成（按来源整张重算；只支持「流水」与「应付挂账」草稿）
   │  ├─ 删除（软删，仍占唯一键；重建走「复活」）
   │  └─ 过账 ──► posted ──红冲（原因必填）──► reversed（终态）
   │                              └─ 同事务新建红字凭证（posted，日期＝当天、期间＝原期间）
   └─ 注意：幂等查询不筛状态 → 红冲后再「生成凭证」返回的是那张已红冲的，无法补开
```

## 5. 会计科目：从业务选择到三大报表的完整路径

> 完整「科目→报表行」映射表、5 个断点、13 条缺陷见 [04-subject-reports.md](finance-review-2026-11-07/04-subject-reports.md)。

### 5.1 科目体系的真相：4 个落点，只有 1 个进报表

```text
                     ┌── 应付/应收单据 subject_id ──► 挂账凭证借方（一次性用掉，不落库①）
财务在确认弹窗选科目 ─┤
                     └── 收支类目 category_subject_id ──► 流水页显示 / 收支明细 / 现金流量表落行
                                                    
付款单据 subject_id ──► 未挂账时的付款凭证借方 / 收支类目兜底

流水 subject_id ──► 凭证业务分录 ──► voucher_lines.subject_label（文本快照）──► 利润表 / 资产负债表
                                                                      └──► 现金流量表（有类目时优先用类目）
```

① **「不落库」是本次核验发现的关键缺口**：`confirm()` 的事务里只 `update status`，`subject_id` 只作为本次 `createAccrual` 的参数传下去，没有写回 `supplier_payable_entries.subject_id`（只有「其他应付」建单时才会写）。后果：台账列、重新生成、付款时未挂账分支、收支类目都读不到这个选择。

### 5.2 三大报表的取数口径（各用各的）

| 报表 | 取数来源 | 科目匹配方式 | 期初 |
|---|---|---|---|
| 利润表 | **已过账凭证**的期间发生额 | 「分类 + 科目名」硬编码匹配（损益类按名称前缀/枚举） | 不涉及 |
| 资产负债表 | **已过账凭证**的累计余额 + 期初 | 同上（按分类 + 名称前缀） | 期初直接并入 |
| 现金流量表 | **已过账凭证**配对出资金分录 | **优先用来源流水的收支类目**，没有才退回凭证业务分录科目 | 期初/银行期初兜底 |
| 收支明细/汇总表 | **收支流水**（不是凭证） | 类目优先、主科目兜底 | 不涉及 |
| 账龄表 / 科目余额表 / 试算平衡表 | — | — | **均未实现** |

### 5.3 五个断点（用户要的「科目一条龙」就断在这五处）

| # | 断点 | 机制 | 后果 |
|---|---|---|---|
| 1 | **凭证科目是文本，不是 id** | `voucher_lines.subject_key = "分类/名称"` 字符串，无 `subject_id` 外键 | 科目改名/换分类后历史凭证不随动 → 报表静默少钱（现库 23.5% 的行已失配） |
| 2 | **两套来源** | 收支报表读流水、三大报表读凭证 | 流水改了金额/科目，凭证不重算 → 两张报表对不上 |
| 3 | **报表行是代码常量 + 名称硬编码** | `finance-three-statements.ts` 里逐行写死「销售*」「管理*」「应付账款」等 | 新增科目/自建类目进不了报表；资产负债表甚至不输出「未归位」缺口 |
| 4 | **现金流量表用类目、其他两表用凭证科目** | 类目是「这笔钱算什么」，凭证科目是「记账对方是谁」 | 同一笔支出在两张报表里可以是两个科目；类目还能在流水页随时改 → 历史现金流量表可被改数 |
| 5 | **期初绕过凭证** | `accounting_opening_balances` + `banks.opening_balance` 两套，整批替换、不生成凭证 | 报表可被直接改数、无逐行审计、不强制试算平衡 |

## 6. 诊断：为什么「会计科目、借贷方都不令人满意」

> 页面交互层 15 条缺陷逐条证据见 [05-web-ui.md](finance-review-2026-11-07/05-web-ui.md)。

### 6.1 三层原因模型

```text
第一层  语义层（你看到的）  ── 「会计科目」一名四义 + 付款凭证上必然出现「应付账款」
   │                              ↑ 不改记账规则，只改术语与展示即可消除
   ▼
第二层  流程层（真正做错账） ── 6 个 P0 硬缺陷：草稿当已挂账 / 金额口径 / 四套状态不联动 /
   │                          确认挂账跨事务 / 科目不落库 / 手改无护栏
   ▼
第三层  报表层（数字不可信） ── 5 个口径缺陷：红冲不归零 / 文本快照 / 期初两套 /
                                资金科目三套判定 / 含税不拆 · 采购链断
```

### 6.2 第一层：一个词四个落点（不修代码也能先消除的困惑）

| 用户在哪看到「会计科目」 | 实际绑定字段 | 它其实是 |
|---|---|---|
| 应付台账 / 确认弹窗 | `supplier_payable_entries.subject_id` | **业务科目**（这笔钱算什么） |
| 应付对账单 | `supplier_payable_reconciliations.subject_id` | 同上（对账粒度） |
| 付款单 / 收款单 | `supplier_payments.subject_id` / `customer_payments.subject_id` | 同上（单据粒度） |
| 收支流水页 / 收支明细 / 汇总表 | `cash_flow_entries.category_subject_id`（有则用） | **业务科目** |
| 收支流水（自动流水的悬停提示） | `cash_flow_entries.subject_id` | **记账对方科目**（销账用） |
| 凭证页 / 凭证纸 | `voucher_lines.subject_label` | **分录科目**（快照，可被手改） |
| 付款单打印件（finance-slip） | 自由文本「总账科目/明细科目」 | 打印用，不入账 |

界面上这 22 处全部只写「会计科目」四个字。**这是用户报障最直接的结构原因**：她在一处选了「销售费 推广费」，在另一处看到「应付账款」，自然判断系统错了。

### 6.3 第二层：6 个 P0 流程缺陷（会让账真的错）

#### P0-1 「已挂账」把草稿凭证也算进去 → 总账出现负应付

- **现象**：确认应付后挂账凭证是 `draft`；此时去付款，系统判定「已挂账」，付款凭证做「借 应付账款」；但三大报表只认 `posted` 凭证 → 报表里只有付款这一侧，**应付账款出现借方余额（负数）**，成本/费用从未入账。
- **根因**：`voucher.service.ts:355-362` 的 `accruedSourceIds` 只排除 `reversed`，不要求 `posted`；而 `finance-three-statements.service.ts:202-203` 只取 `posted`。
- **影响**：两账都错且互相掩盖——借贷仍然平，试算平衡发现不了。生产库正是这个形态：**posted 凭证 14,778.20 里 0 行涉及「应付账款」**。
- **修法**：「已挂账」只认 `posted`；确认时可选自动过账（取决于 §0.4-A2）；报表增加「已确认未过账」差额勾对。

#### P0-2 收付款凭证按单据全额，不按核销额

- **现象**：付款 100、只核销 60 时，流水 100、银行减 100、应付只减 60；凭证做「借 应付账款 100」→ 应付账款被多冲 40，多付的 40 没有科目承接（应是「预付账款」）。
- **根因**：核销只校验「合计 ≤ 单据金额」（`supplier-payment.service.ts:121`、`customer-payment.service.ts:117`），写流水与凭证都用单据金额（`:157`、`:135`）。
- **同源问题**：客户收款侧更严重——`subjectId` 显式传入时会越过「已挂账→应收账款」的候选链（`customer-payment.service.ts:148`），**人工科目顶掉应收账款**，收入重复、应收永不销账。供应商付款侧相反（`allAccrued` 时置 null），属实现遗漏。
- **修法**：凭证金额取核销额；差额按口径记预付/预收；两侧判定对称。

#### P0-3 四套状态机互不联动

| 动作 | 应该联动 | 实际 |
|---|---|---|
| 付款冲销 | 红冲/删除付款凭证 | ❌ 只冲付款 + 核销 + 流水 |
| 应付冲销 | 红冲/删除挂账凭证 | ❌ 只改 `status` |
| 删除已确认其他应付 | 处理挂账凭证 | ❌ 代码还在按「确认即记账」旧口径回冲一条**已不存在**的流水 |
| 流水冲销 | 红冲凭证 | ❌ 凭证不动 |
| 流水改金额/科目 | 凭证重算 | ❌ 凭证不动 |
| 凭证红冲 | 回写应付/付款状态 | ❌ 不动 |
| 对账单删除 | 检查是否已用于确认 | ❌ 守护条件查的来源类型已不再产生（死代码） |

- **生产后果**：41 笔已过账付款（77,748.23）的流水被红冲，付款单仍是 `posted`；43 笔 `posted` 付款 **0 张 posted 凭证**。

#### P0-4 确认与挂账跨事务 + 红冲后不可补开

- **现象 A**：`confirm()` 先在事务里提交 `status=confirmed`，再在事务外调 `createAccrual`。任一步失败（科目停用、编号冲突、DB 异常）→ 留下「已确认、无凭证」，且再确认会被「只有草稿可确认」挡住，只能回退重来。
- **现象 B**：挂账凭证被红冲后，再次确认会因幂等命中返回那张**已红冲**凭证（查询不筛状态），且已红冲凭证不能删除、不能再红冲 → 该应付**永远无法重新挂账**。
- **修法**：确认与挂账同事务（或 outbox 可重试）；幂等查询加 `status != reversed`；红冲时同步业务状态。

#### P0-5 科目「选了不落库」+ 四套取值链

- 来源型应付/应收在确认弹窗选的 `subject_id` **不写回单据**（`supplier-payable.service.ts:235-248` 只 update status；`receivable.service.ts:174-186` 同）。银行 `bank_id` 更是只做存在性校验后丢弃（确认不动现金）。
- 于是同一笔应付的科目有 4 套取值链：台账显示（条目 > 对账单 > 候选链首位）、挂账凭证（条目 > 弹窗 > 候选链）、付款凭证借方（是否挂账决定）、收支类目（条目/对账单）。
- **生产表现**：确认弹窗里填一次就没了，下次确认还得重选；`regenerate` 会按候选链重算，把当初人工选的科目换掉（应付侧）；应收侧则直接不支持重新生成。

#### P0-6 自动凭证可任意手改，且改单不留痕、不回写

- **机制**：任何草稿凭证都能在编辑器里改方向/科目/金额/增删行；只校验「借贷平衡 + 科目非空字符串」，**不校验科目表**；审计只记 `{voucher_no, line_edited: true}`，不记改前/改后科目；不提示「这是系统按来源自动生成的」。
- **生产事实**（本次专项核验）：
  - 12 张挂账凭证里 6 张贷方不是「应付账款」；这 6 张**恰好就是**有 `voucher.update` 记录的那 6 张，未改过的 6 张贷方全部正确。
  - 9 张由流水生成的凭证里，**0 次改单的只有 2 张**：`记-2026-11-0023`（借 应付账款 / 贷 银行存款—招商银行，正确形态）与 `记-2026-09-0001`（借 原材料 / 贷 银行存款—农行，按「未挂账」兜底口径生成）；其余 7 张全部有改单记录，且全部偏离系统口径（贷方被改成「其他应收款-备用金」或借方被改成费用科目）。
  - 凭证相关审计动作 183 次中，**182 次由同一个财务账号 `caiwu`** 完成（另 1 次 `laoban1`）。
- **结论**：**库里的错账不是系统生成的，是财务改出来的**。而财务之所以改，是因为前三层（语义不清 + 草稿不过账 + 科目不落库）让她无法相信系统生成的凭证。
- **修法（最优先）**：自动凭证的分录编辑器显示来源、要求原因、审计记 before/after；对「往来科目行 / 资金行」加锁或二次确认；提供「重新生成」把凭证拉回系统口径（已支持部分来源）。

### 6.4 第三层：5 个口径缺陷（报表数字不可信）
