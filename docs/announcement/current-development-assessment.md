# 迪礼 ERP 当前开发评估

- 评估日期：2026-08-23
- 代码基线：`1cddc43`（`fix: disambiguate production daily report fields`）
- 评估范围：业务链路覆盖、前后端实现、自动化测试、Docker 厂内部署基线、上线准备
- 文档性质：阶段性开发评估，不等同于正式上线验收

## 1. 总体结论

迪礼 ERP 的核心后端和前端业务代码已经基本覆盖 V1.0 规划的六个业务域，并已形成以 `order_no` 为主线的跨模块数据流转。认证、权限、审计、软删除、状态机、库存事实、应收应付、薪资和订单全链路工作台等平台能力已经落地。

本次复核发现，人事和财务后端虽已具备 API 与领域测试，但 Web 端此前仍为 `ModulePlaceholder`，因此此前评估将这两块误计入了前后端覆盖范围。该遗漏已修正：页面已接入员工、考勤、绩效、薪资、应收、应付、收付款和对账 API，并在 Docker 登录会话下完成列表接口 200 验证；真实写入、分批核销和冲销浏览器验收仍待专用 fixture。

本机 Docker Compose 厂内部署拓扑已经成功启动，PostgreSQL、API、Web 的容器健康状态和 Web 到 API 的代理链路已经验证。单元测试、类型检查、前后端构建和离线性能门禁通过，主要业务链路也有 API 或浏览器测试证据。

但项目尚未达到“正式上线完成”状态。生产日报的浏览器场景仍有一个选择器问题未闭环；真实备份恢复演练、厂内正式服务器部署、真实数据量性能记录、历史数据迁移和业务负责人最终验收仍未完成。因此当前状态应定义为：**核心代码基本完成，联调与上线准备进行中**。

## 2. 已完成范围

### 2.1 平台基础

- 用户登录、Cookie Session、JWT/会话鉴权和 RBAC 权限基础。
- 健康检查、统一 REST API、错误处理、审计事件和通用审计字段。
- Prisma 数据模型、迁移入口、初始管理员 seed。
- 前端 Next.js 应用壳、统一 UI/表格/表单技术栈和业务模块导航。
- Docker Compose 厂内部署基线，PostgreSQL 不暴露宿主机端口。

### 2.2 业务模块与链路

- 客户池 -> 销售单 -> `order_no` -> 销售确认 -> BOM。
- BOM/采购单 -> 采购到货 -> 来料 QC -> 原料入库 -> 应付来源。
- 员工、部门、岗位、工序池与工序计价 -> 生产单（厂内/外加工）。
- 原料领料、退料、报废和库存事实。
- 工序日报、员工计件/计时日报、超单与差异告警。
- 外加工物料直发、签收、余料回厂、成品回厂和直装柜来源事实。
- 成品送检、成品 QC、成品入库和不良品处理。
- 成品分批出库、发货资料、客户退货、应收来源、收款、核销和对账。
- 月度薪资台账与薪资支付。
- 订单全链路工作台、报表、CSV 导出和告警中心。

1. 修复 `production-daily-report.spec.mjs` 的表单定位，完成 D5 浏览器验收。
2. 使用已启动的 Docker 环境重跑完整 API、集成和 Playwright 质量门禁，更新测试结果文档。
3. 在本机独立数据库完成一次可审计的备份恢复演练，并记录恢复后的业务抽检。
4. 按 `docs/deployment/factory-runbook.md` 整理厂内服务器上线检查清单，完成首次部署彩排。
5. 由各模块负责人完成字段、状态、权限、模板和报表口径验收，登记遗留项。
6. 进入 G5 历史数据迁移、抽样核对和试运行，不在迁移完成前宣称正式上线。

## 8. 阶段结论

当前最准确的项目状态是：**核心业务代码基本完成，主要模块已经具备运行基础；本机容器联调通过，但仍处于上线准备和验收阶段。**

只有在 P0/P1 项关闭、厂内部署和恢复演练留证、业务负责人完成验收后，才可以将项目状态更新为“V1.0 可上线”。
