## 2. 这意味着什么

**方向定在「先量再改」这个顺序上，而且第一量就推翻了原先的假设。** 通过率 100% 而不是「失败率很高」，说明当下的病灶不是模型选错工具，而是工具目录缺了动作：31 个 operation 全部以一张已知单据为输入，没有一个是「列出 / 按条件筛」。

所以「最近有哪些订单」「哪些物料库存不足」这类最自然的问法，模型手里根本没有对应的工具，只能把「最近」「库存不足」当检索词塞进单号检索，必然 0 行。三次真实崩溃都追到了具体 run 的事件表，不是推测。

代价要说清：现在的高通过率是靠模型自纠撑住的。7 条用例各踩一次工具失败，全部靠模型自己换个说法重试才拿到结论——每次都在消耗失败预算（上限 3 次），也在拉长时延。

## 3. 仍未解决

- 列表与按条件筛选没有工具入口，所以「最近有哪些单」「已确认的订单有哪些」现在必答「查不到」。
- 跨单聚合被根守卫挡掉，「哪些物料库存不足」同样必答「查不到」，且报错文案把模型引向错误方向，每次多耗一轮。
- 句柄 `o_1` 只在本轮有效，第二轮追问必踩一次 `ORDER_REF_INVALID` 再重新检索；这是设计代价，边界没想清楚之前不动。
- 服务端单号归一仍是空白，全角、多余空格的容错现在靠模型代劳，换模型版本就会变。
- 基线自身有两个盲区：正向财务路径没验（本地库没有 `laoban`/`caiwu` 账号），`model_steps` 没采（SSE 不下发该字段）。
