# T11 覆盖度检查进运行时

## 1. 这份任务在哪

- **Phase 2 报表不再靠名字认科目**，目标是财务新增一个科目时三张报表都点名它没归位。
- **本任务把只在测试里跑的覆盖度检查接进运行期**：`checkStatementCoverage` 设计得不错，注释还写着「也供新增科目忘了归位时在运行期报警」，但全仓只有测试调用它。
- **开始于**：T8 把行映射落成数据。**后续等它**：Phase 3 起的所有新增科目都要靠它兜住。

## 2. 开发前需要知道什么

**先读**

- `apps/api/src/modules/finance/finance-three-statements.ts` — `checkStatementCoverage` 的三个方向（未认领 / 双重认领 / 空行）与它现在返回什么。
- `apps/api/src/modules/finance/accounting-subject.service.ts` — 科目的新建与修改入口，报警最该挂在这里。
- `apps/api/test/unit/finance-three-statements.test.cjs` — 既有守卫用例，确认改动不破坏它们。

**已定**

- 检查输入是**库里的全部科目**，不是 122 条常量。常量守卫保留，两者不互相替代。
- 触发点：科目新建/改名/改分类之后跑一次，结果写进**审计事件**（不是抛错）。理由：拦住录入会让财务没法干活，而审计里留痕能让问题被发现。
- 不阻塞写入。这一条是刻意的：本任务只负责「让人知道」。

**边界与缝**

- 触及科目主数据写入口、报表内核的覆盖度函数、审计。不碰取数与落行。
- 缝：既有科目服务测试入口与内核测试入口。不新增缝。

**运行**

- `npm run build --workspace=@dilee/api`
- `node --test apps/api/test/unit/accounting-subject-service.test.cjs apps/api/test/unit/finance-three-statements.test.cjs`
- `npx tsc -p apps/api/tsconfig.json --noEmit`

**未知**

- 运行时检查要读库（全部科目），可能让新建接口变慢。若实测明显，改成只查本次涉及的分类。

## 3. 流程

1. 读上面三个文件，用一句话复述本任务。
2. 写一条会失败的测试：新建一个不会被任何行认领的科目后，写出一条含该科目名的审计事件。
3. 在科目写入口挂上检查。
4. 让检查吃「库里的科目列表」而不是常量。
5. 跑构建、类型检查与测试。
6. 提交。

## 4. 测试用例

| 用例 | 输入 | 期望 | 缝 |
| --- | --- | --- | --- |
| 1 | 新建一个没有行认领的科目 | 写出一条审计事件，点名该科目 | 科目服务 |
| 2 | 新建一个能落行的科目 | 不写报警事件 | 科目服务 |
| 3 | 改名后原本落行的科目落空 | 写出一条审计事件 | 科目服务 |
| 4 | 常量守卫 | 122 条仍然无未认领、无双重认领 | 报表内核 |
