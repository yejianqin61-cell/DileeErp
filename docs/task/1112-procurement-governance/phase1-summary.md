# 采购治理 Phase 1 收口：选不到 BOM 的时候，系统现在说得出为什么

> 窗口：2026-11-12（本轮 Phase 1 的 6 个提交）
> 基线：`docs/audit/procurement-audit-2026-11-12.md`（本轮审计）与 `plan.md` 的 Phase 1

---

## 1. 头条

**本轮 Phase 1：5 项改动，全部完成。采购计划的新建弹窗不再是一个空下拉 —— 被挡住的 BOM 会带着原因出现在同一处。**

| # | 改动 | 位置 | 类型 | 状态 | 对读者的意义 |
|---|---|---|---|---|---|
| C-1 | 「哪些 BOM 能建计划」从 SQL 条件搬进领域纯函数 | `apps/api/src/modules/procurement/purchase-plans.domain.ts` | 改变 | 已完成 | 规则只有一处，候选与建计划不会再各说一套 |
| C-2 | 候选接口返回可建与被拦两半，被拦的带原因码 | `purchase-plans.service.ts`、`purchase-plans.controller.ts` | 新增 | 已完成 | `data` 形状不变，老调用方零改动；被拦原因进 `meta.blocked` |

---

## 2. 这意味着什么

审计里「选不到 BOM」的死锁链（计划有已下单行就删不掉 → BOM 永久占着唯一索引 → 候选永远不返回它）没有靠删数据解决，而是把**规则变成可读的答案**：能建的照旧可建，不能建的第一句话就说明是哪一类、下一步去哪。

这也把症状 1 与症状 3 拆开了：前者是能力问题（closed 单被误拦），后者是可见性问题（原因写在 SQL 里没人看得见）。两个都改完，用户手上才有可操作的信息。

代价是候选查询不再全在数据库里过滤：取回该看的 BOM 后在内存分类，量级与销售单同阶，被拦清单封顶 50 条。

---

## 3. 仍然开着的

- **已完成的计划仍然删不掉**，所以「这张 BOM 想再建一份新计划」这条路依旧不通；现在界面会把用户导到「打开那份计划、加一行」。这是引导，不是能力。
- **行级退回还没做**（Phase 2）：改一行仍要整张采购单回退，且已有到货的行依然零出口。
- **`meta.blocked` 只有计划页在用**，其它入口（如果将来有）还得各自接。
- 假 Prisma 现在更"诚实"了，仍有若干 where 形态没覆盖（如 `orderBy`、`take`），下一轮动候选查询时要留意。
