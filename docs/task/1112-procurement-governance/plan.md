## 2. 逐条方案的形状

### R-1 采购计划的候选要能解释「为什么选不到」

- **Approach**：候选查询不再在 where 里过滤，改成取回该看的 BOM 后在内存里**分类**；返回 `eligible[]` 与被拦下的 `blocked[]`（带原因码、人话、以及已有计划的编号）。`data` 仍是数组，向后兼容。
- **Touches**：采购计划服务与它的领域纯函数、计划页的新建弹窗。
- **Test seam**：既有的 `GET /purchase-plans/candidates`。不新增 seam。
- **Acceptance**：[ ] 被拦下的 BOM 出现在 `meta.blocked` 且带原因码　[ ] 原因文案里能读出下一步该做什么　[ ] 老调用方（只读 `data`）行为不变
- **Hard part**：现有单测里假 Prisma 的 `bom.findMany` 自己就把旧条件写死了；过滤一旦搬进服务层，假 Prisma 必须先改成"老实返回"。

### R-2 销售单已关闭（closed）的 BOM 也能建采购计划

- **Approach**：把「可建计划的销售单状态」收成一个常量（`confirmed` / `closed`），候选分类与建计划的前置校验共用它；关闭单排在被拦之外的正常候选里。
- **Touches**：采购计划的领域纯函数与服务前置校验。
- **Test seam**：同一个候选接口 + 既有的建计划接口（`POST /purchase-plans`）。
- **Acceptance**：[ ] 关闭销售单的 BOM 出现在候选里　[ ] 草稿销售单的 BOM 仍然被拦且给出原因　[ ] 候选与建计划两处口径由同一个函数决定
- **Hard part**：`loadBom()` 的 404 文案（"BOM 不存在或所属销售单未确认"）要跟着改，而它被既有用例钉着。

### R-3 已下单的一行可以单独退回采购计划

- **Approach**：新增行级退回动作——校验该行零到货事实、断开计划行与采购明细的 1:1 链接（数量/单价/供应商原样留在计划里）、软删该采购明细、按剩余明细重算单头金额；一行不剩时整单作废（与整单退回同结果）。
- **Touches**：采购计划服务（它拥有计划行链接）、采购单控制器。
- **Test seam**：新增一个 HTTP 入口 `POST /purchase-orders/:id/items/:itemId/revert-to-plan`，服务层落在采购计划服务的方法上。**新增 1 个 seam，取最低的那个**（直接测服务方法）。
- **Acceptance**：[ ] 只退一行时其余行与单号不动　[ ] 该行零到货才能退，有到货被拒并说明走哪条线　[ ] 单头合计等于剩余明细之和　[ ] 最后一行被退时整单作废　[ ] 退回后计划行回到未下单且数量/单价/供应商不变
- **Hard part**：退一行后重新下单要能**并回同一张单**（复用既有 `findMergeTarget`/`appendItems`），否则"退一行"仍然会换单号，等于没解决 §2.3 那个问题。

### R-4 「这份 BOM 已有计划」时的补料出路要在界面上说清楚

- **Approach**：候选被拦原因里，`PLAN_ALREADY_EXISTS` 带上计划编号与派生状态（未下单/部分下单/已完成），并给出一句"补料请打开这份计划、加一行"。
- **Touches**：领域纯函数的原因文案；计划页的新建弹窗信息行。
- **Test seam**：领域纯函数（纯字符串断言）+ 计划页组件测试。
- **Acceptance**：[ ] 完成态计划在候选里被拦时原因里出现计划编号　[ ] 新建弹窗能看见该原因　[ ] 计划列表里完成态有计划级提示
- **Hard part**：计划状态是**派生**的（不能落列），要在候选查询里顺带把行状态读回来算，而不是加一列。

### R-5 采购单详情页要有行级退回入口，计划页要显示不可选原因

- **Approach**：采购单详情页每个物料块加一个「退回这一行」（仅当该行零到货且单状态可退），复用既有 `ActionDialog` 收原因；计划页新建弹窗把被拦原因渲染成信息行。
- **Touches**：采购单详情页、计划页、以及两页共用的弹窗字段类型（新增 `type: "info"` 用法，类型已存在）。
- **Test seam**：两个页面的现有 jsdom 测试（不新起 seam）。
- **Acceptance**：[ ] 零到货的行出现「退回这一行」，有到货的行不出现　[ ] 提交后页面刷新且提示成功　[ ] 计划页能看到不可选原因
- **Hard part**：详情页的物料块是内联 JSX（一个文件 125 行里塞了三层 map），加按钮要挤进操作列而不打乱列宽约定。

## 3. 阶段

### Phase 1 — 选不到的时候，系统能说出为什么

**Covers**：R-1 采购计划的候选要能解释「为什么选不到」、R-2 销售单已关闭（closed）的 BOM 也能建采购计划。

**Goal**：采购员点「新建采购计划」时，能看见"能建的都在这里"以及"哪些建不了、为什么"，且关闭销售单上的 BOM 不再凭空消失。

**Tasks**

- 把「哪些 BOM 可建计划」抽成一个纯函数并在领域层配原因码
- 候选接口改成分类返回可建与被拦，`data` 保持数组
- 建计划的前置校验改用同一个纯函数
- 计划页把被拦原因渲染出来
- 覆盖它：关闭单可建、有计划的被拦且带计划编号、草稿单被拦

**Proof**：领域纯函数的用例 + 候选接口用例全绿；界面上新建弹窗能看见被拦原因。
**Not here**：行级退回，以及任何对采购单的写操作。

### Phase 2 — 改一行不用退一整单

**Covers**：R-3 已下单的一行可以单独退回采购计划。

**Goal**：采购员在采购单详情页退掉某一行，改完计划再下单时并回同一张单，单号不变。

**Tasks**

- 在采购计划服务上实现行级退回（校验零到货、断链、软删明细、重算单头）
- 最后一行被退时整单作废
- 挂上 HTTP 入口并写审计
- 覆盖它：退一行其余不动、有到货被拒、退空整单作废、退完能并回同一张单

**Proof**：这组用例全绿；其中"并回同一张单"一条要断言采购单号前后相等。
**Not here**：行级改数量/改供应商的直改（口径 7 不动），以及前端入口。

### Phase 3 — 让界面把出路递到手上

**Covers**：R-4 「这份 BOM 已有计划」时的补料出路要在界面上说清楚、R-5 采购单详情页要有行级退回入口，计划页要显示不可选原因。

**Goal**：采购员在界面上看得到"这一步为什么不行、下一步点哪里"，行级退回有按钮。

**Tasks**

- 计划页新建弹窗渲染被拦原因（含计划编号）
- 采购单详情页每行加「退回这一行」，收原因并调用新端点
- 计划列表里完成态计划加补料提示
- 覆盖它：页面测试断言按钮出现条件与原因可见

**Proof**：两个页面的 jsdom 用例全绿；手点一遍走得通。
**Not here**：批量退行、以及把退回做成可撤销。

### Phase 4 — 收口整期治理

**Covers**：加固 R-1 采购计划的候选要能解释「为什么选不到」、R-2 销售单已关闭（closed）的 BOM 也能建采购计划、R-3 已下单的一行可以单独退回采购计划、R-4 「这份 BOM 已有计划」时的补料出路要在界面上说清楚、R-5 采购单详情页要有行级退回入口，计划页要显示不可选原因。

**Goal**：口径写进设计文档、审计报告补上实施结果、全量 typecheck 与采购相关单测给出数字。

**Tasks**

- 在设计文档里记下「可建计划的销售单状态」与「行级退回」两条口径变更
- 审计报告补 §7 实施结果（含基线数字与既存失败说明）
- 全量 typecheck + 采购相关单测 + web 单测，记录数字
- 写本轮总结（easy-summary）

**Proof**：三项检查的数字落进文档，且没有新增失败。
**Not here**：跨模块的其它治理，与本轮无关的既存失败一律不动。
