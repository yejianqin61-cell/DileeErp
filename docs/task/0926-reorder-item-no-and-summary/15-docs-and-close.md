## 实施要点

**1. 与其它工作流共存**

同一工作树里有其它 agent 在改财务模块（`finance/**`、`voucher/**`、`schema.prisma` 的财务部分）。
写 `schema.prisma` 与 `data-dictionary` 时**只加自己的段落**，不要重排/格式化邻居的内容——
一次「顺手整理」会把别人的改动卷进你的提交，也会让 diff 无法评审。

**2. 提交纪律**

- `git commit -m "…" -- <显式路径>`；**禁止 `git add -A`**。
- 不要把 `example/人事/*.xlsx`（含真实姓名/身份证/住址/手机号，属 PII）带进任何提交。
- `schema.prisma` 与 `apps/api/prisma/migrations/**` 必须和用它的服务代码在**同一次提交**里，
  否则部署侧会读到"代码要求一列、库里没有"的状态。

**3. 验证计数要写清口径**

仓库里 API 单测有两套计数（`test:unit:api` 不含 `test/http`；作者侧含 `test/http` 的数字更大）。
在完成记录里写明**用的是哪条命令**，不要把两个数字混着报——历史上因为这个对齐浪费过时间。

**4. 未验证项要显式列出（这是本仓库的硬规矩）**

本机通常没有 PostgreSQL 与已启动的 API，因此以下一律记「环境阻断」而不是"已验证"：

- `prisma migrate deploy` 未在真实库执行（新迁移没跑过）。
- `npm run test:api`（`test/http/**`）、`test:integration`、`test:e2e`（Playwright）未运行。
- xlsx 导出的**打印观感**未在真实 Excel/WPS 打开看过（只做过回读断言）。
- 前端加列/加筛选的**像素观感**未在真实浏览器量过。

## 验收与验证

| # | 验收点 |
| --- | --- |
| 1 | 上面七处文档都动过或明确写了「本期未涉及」 |
| 2 | 设计文档 §十一 与任务文档的完成记录**不互相矛盾**（数字、结论一致） |
| 3 | 迁移/代码同提交；提交里不含他人文件与 PII 样本 |
| 4 | 未验证项按上述四类逐条列出，没有"应该没问题"这类措辞 |

命令：文档改动本身不需要测试；但收口提交前**必须**再跑一次 `npm run typecheck` 与当期相关的测试，
并把结果写进完成记录（文档提交与代码提交分开也行，但要在同一天完成）。
