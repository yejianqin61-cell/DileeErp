# Task 01：应收草稿确认与收款核销修复

## 目标

让成品出库过账产生的应收草稿能在财务页面被正确确认，并形成“应收确认 -> 收款登记 -> 分配核销 -> 部分/已收清 -> 冲销恢复余额”的可验收闭环。

## 背景与问题

- 成品出库过账会创建 `ReceivableSource`，初始状态为 `draft`。
- 财务页面当前把可确认条件写成 `pending_finance`，导致该草稿缺少确认动作。
- 应收来源、收款和调整已有后端基础，但状态和页面动作需要统一。

## 范围

### 后端

- 统一应收来源状态：`draft`、`confirmed`、`partially_paid`、`paid`、`cancelled`。
- `draft` 才允许确认和草稿编辑；确认后禁止静默修改来源金额和关联关系。
- 成品出库与应收来源保持一对一和幂等，重复请求返回原来源。
- 没有销售单价时，确认金额必须显式填写金额原因；有单价时使用数量乘单价作为默认金额。
- 收款过账只允许分配到非取消、已确认且余额大于零的应收来源；校验币种、重复分配和超额分配。
- 付款冲销后重算来源状态和可用余额。
- 应收调整（退款、红冲、折让、坏账、纠正）不覆盖原来源，过账前校验净余额。

### 前端

- 应收列表对 `draft` 显示确认、编辑和取消动作，状态标签与 API 一致。
- 收款核销选择项只展示可分配应收，并显示来源编号、订单号、客户、原金额和可用余额。
- 显示确认前后的状态、已收金额、未收金额和冲销结果。
- 错误提示区分无单价、余额不足、币种不一致、重复核销和已取消来源。

## 不做

- 不在本任务实现发票自动开具、税务计算或客户预收款。
- 不改变“成品出库过账创建应收草稿”的既定口径。

## 验收标准

1. 成品出库过账后，财务页能看到一条 `draft` 应收并能确认。
2. 无单价出库确认时，未填写金额原因会被拒绝；填写后可确认。
3. 同一出库重复创建不会产生第二条应收来源。
4. 一笔收款可部分核销，应收状态变为 `partially_paid`；核销足额后变为 `paid`。
5. 核销超过余额、币种不一致或同一收款重复分配会被拒绝。
6. 已过账收款冲销后，应收可用余额和状态恢复。
7. 退款/折让调整保留原应收来源，并正确减少净应收。
8. 所有确认、核销、冲销和调整均有审计事件。

## 测试

- 领域/服务测试：状态转换、金额原因、净余额和调整边界。
- HTTP 测试：草稿确认、收款过账、冲销、统一错误信封。
- PostgreSQL 集成测试：出库过账与应收创建事务、幂等和并发核销。
- Playwright：登录 -> 财务 -> 应收确认 -> 登记收款 -> 核销 -> 查看余额。

## 依赖与交付物

- 依赖成品出库过账和现有应收/收款表结构。
- 交付后端 API、财务页面动作、测试及迁移（如确有必要）。
