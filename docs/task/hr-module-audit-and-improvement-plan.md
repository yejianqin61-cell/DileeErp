# 人事模块审计与改进计划

## 1. 审计范围

本次只审计人事页面及其直接依赖，不修改业务代码。检查范围包括：

- 人事前端页面：`apps/web/app/hr/page.tsx`
- 共享操作表单：`apps/web/components/ui/action-dialog.tsx`
- 人事 API：`apps/api/src/modules/hr/hr.controller.ts`、`attendance-performance.service.ts`
- 员工主数据 API：`apps/api/src/modules/production/production-master-data.controller.ts`、`production-master-data.service.ts`
- Prisma 员工、考勤、绩效模型

## 2. 结论摘要

当前问题集中在两个层面：

1. 人事页面缺少完整的员工目录视图模型和考勤时间模型。
2. “新增类目”没有统一的异步返回协议。父页面有时只刷新列表，有时只保存旧字段值；共享 `ActionDialog` 还直接修改 `fields.defaultValue`，导致选项和原表单状态容易失同步。

因此，员工类型、绩效员工、部门、岗位等入口应统一支持“在当前表单中创建类目，创建成功后返回原表单、保留输入、刷新选项并选中新类目”。不能继续用“请到专门业务页面维护”的错误提示代替入口。

## 3. 现状与证据

### 3.1 新建员工

- [hr/page.tsx:30](../../apps/web/app/hr/page.tsx) 已有工号、姓名、部门、岗位、员工类型、入职日期，但没有离职日期。
- 员工类型是硬编码的三个选项：`workshop`、`office`、`management`，没有 `canAddCategory`，即使共享组件默认显示新增按钮，点击后也会落入通用错误分支。
- [hr/page.tsx:38](../../apps/web/app/hr/page.tsx) 员工表只有工号、姓名、部门/岗位、类型、状态和操作，没有入职时间、离职时间列。
- 页面没有搜索、状态、部门、岗位或员工类型筛选状态；员工数据直接完整传给 `DataTable`。
- 后端已经有 `hiredOn`、`leftOn`、`employmentStatus` 字段和离职接口，因此这部分主要是前端展示与表单契约缺失，不是从零设计后端。

### 3.2 登记考勤

- [hr/page.tsx:33](../../apps/web/app/hr/page.tsx) 只有 `attendance_date` 日期字段，没有时间字段。
- [hr.controller.ts](../../apps/api/src/modules/hr/hr.controller.ts) 的 `AttendanceDto` 只接收 `attendance_date`，服务层通过 `T00:00:00.000Z` 转换为日期。
- Prisma 的 `AttendanceRecord.attendanceDate` 当前为数据库 `DATE` 类型，现有模型不能保存具体时分。仅在前端增加时间输入会丢失数据，必须先确定并实施数据模型迁移。

### 3.3 登记绩效

- [hr/page.tsx:34](../../apps/web/app/hr/page.tsx) 的员工字段是普通员工下拉框。
- [hr/page.tsx:44](../../apps/web/app/hr/page.tsx) 的 `onAddCategory` 只识别 `department_id`、`position_id`，对 `employee_id` 统一显示“请在生产基础资料中维护”，所以绩效页面的新增类目点击没有业务动作。
- 同一问题也影响考勤、薪资台账等所有使用员工下拉框的人事流程。

### 3.4 共享新增类目链路

- [action-dialog.tsx:16-20](../../apps/web/components/ui/action-dialog.tsx) 在打开时从 `fields.defaultValue` 初始化值，点击新增类目时直接修改传入的 `fields` 对象，然后同步调用 `onAddCategory`。
- 回调不是异步协议，组件不知道“创建成功”或“创建失败”，也不能要求父级返回新类目。
- 人事页的部门、岗位回调尝试保存旧值，但创建成功后只 `load()`；旧 `dialog.fields` 的 options 不会可靠地包含新记录，且没有统一选中新记录的机制。
- 类目弹窗通过页面早退渲染，父表单虽然保留在 React 状态中，但恢复依赖父级手工复制，容易出现值、选项、弹窗关闭时序不一致。

## 4. 改进目标

### P0：统一新增类目契约

建立共享的异步类目创建流程：

1. 点击“新增类目”时，捕获当前表单值，但不修改传入的 `fields` 对象。
2. 打开类目表单并等待创建结果。
3. 创建成功后返回原表单上下文。
4. 重新生成字段 options，将新类目加入选项并自动选中。
5. 原表单其他字段全部保留；创建失败时保留原表单和错误信息。

人事页至少支持以下快速创建映射：

| 当前字段 | 快速创建页面 | 创建接口 | 返回后动作 |
| --- | --- | --- | --- |
| `department_id` | 新建部门 | `/production/departments` | 刷新部门选项并选中新部门 |
| `position_id` | 新建岗位 | `/production/positions` | 刷新岗位选项并选中新岗位 |
| `employee_type` | 新建员工类型 | 新增人事类型接口 | 刷新员工类型选项并选中新类型 |
| `employee_id` | 新建员工 | `/production/employees` | 刷新员工选项并选中新员工 |

员工类型是否继续使用硬编码值，或改为可维护字典，是实现前必须确认的领域决定。根据用户要求“新增类目”，计划按可维护类目处理，而不是继续写死在页面。

### P0：员工目录完整性

- 新建员工增加离职日期字段；编辑员工也能修改离职日期。
- 员工表展示入职日期、离职日期，日期为空显示 `-`。
- 增加筛选栏：关键字（工号/姓名）、员工状态、部门、岗位、员工类型。
- 筛选只作用于前端已加载数据，若数据量增长到分页阈值，再下沉为 API 查询参数。
- 离职动作继续使用现有状态接口，并在离职成功后立即刷新状态和离职日期。

### P1：考勤时间模型

推荐将考勤事实拆成：

- `attendance_date`：工作日期，保留日期语义；
- `attendance_time`：具体打卡/登记时间，使用 PostgreSQL `TIME` 或明确的 `TIMESTAMP` 语义。

实施前需要决定一条考勤记录代表“单次打卡”还是“出勤汇总”：

- 单次打卡：时间必填，允许同一员工同日多条不同时间记录；唯一约束需调整。
- 出勤汇总：增加上班时间、下班时间字段，服务层负责校验下班晚于上班。

迁移必须包含 Prisma schema、API DTO、服务校验、前端时间控件、列表展示和已有数据兼容策略。不能只在前端增加 `<input type="time">`。

### P1：绩效和人事流程类目入口

- 绩效员工下拉支持快速新建员工并返回当前绩效表单。
- 考勤员工、薪资台账员工同步复用同一入口，不做只修绩效的特例。
- 新建员工时其部门、岗位、员工类型也必须能继续通过快速创建完成，形成可嵌套但可控的返回链路。
- 所有创建成功后的选项刷新必须覆盖当前弹窗，不依赖页面重新加载后偶然生效。

## 5. 实施顺序

### 阶段一：共享表单状态契约

- 扩展 `ActionDialog` 的新增类目回调为可等待的创建流程，传出当前值。
- 移除对 `fields` 对象的直接 mutation。
- 增加统一的“恢复原表单 + 合并新选项 + 选中新值”父级模式。
- 为共享流程补一个最小组件级回归测试：创建成功、创建失败、取消创建、原值保留。

### 阶段二：人事员工目录

- 增加员工筛选状态和派生列表。
- 增加入职/离职日期字段及表格列。
- 接通员工类型类目 API 和快速创建入口。
- 接通部门、岗位创建后的即时刷新与选中。

### 阶段三：考勤数据模型

- 先确定单次打卡还是出勤汇总语义。
- 编写迁移和兼容读取策略。
- 更新 API DTO、服务校验、前端时间控件和列表展示。
- 增加跨日期、无效时间、重复记录、离职员工登记等回归测试。

### 阶段四：绩效及其他员工引用流程

- 绩效、考勤、薪资台账统一接入员工快速创建。
- 验证所有新增类目完成后回到原页面，原输入不丢失，新选项立即可见且已选中。
- 做一次人事模块全链路验收，而不是只点“登记绩效”。

## 6. 验收标准

- 新建员工页面可按关键字、状态、部门、岗位、员工类型筛选。
- 员工表同时显示入职日期和离职日期；在职员工可办理离职，离职日期可见。
- 员工类型新增类目按钮可打开创建表单，创建成功后回到新建员工表单并自动选中。
- 登记考勤可填写并保存用户要求的具体时间，刷新后仍能展示。
- 登记绩效的员工新增类目可创建员工并返回原绩效表单，周期、评分、等级等输入不丢失。
- 同一新增类目行为在考勤和薪资台账中表现一致。
- 失败和取消创建不会清空原表单，也不会把半成品写入业务记录。
- 前端类型检查、API 类型检查、相关单元/集成测试和浏览器验收全部通过。

## 7. 风险与待决策

- 考勤“时间”究竟是单次打卡时间还是上下班时间，决定数据库字段和唯一约束；需要产品确认后再迁移。
- 员工类型目前是代码常量，改为类目数据后需要确定初始种子、停用规则和历史记录展示名称。
- 快速创建员工可能在绩效/考勤表单内再打开部门、岗位、员工类型，需限制弹窗层级并保证返回路径可追踪。
- 员工数量增长后，当前一次性加载和前端筛选需要升级为服务端分页筛选；本次先保留现有加载方式，设置后续阈值。
