## 2. 需求 1：采购对账明细表——产品名称提到采购单号之前

老表（`采购对账明细表.xls`）的列序是 `日期 / 采购单号 / 供应商名称 / 产品名称 / …`。用户要求把**产品名称**放到**采购单号**前面。

- 为什么合理：这张表是财务拿它跟供应商**逐物料**核对的，先看到「是什么」再看到「哪张单」才顺。
- 影响面：只有列序。`金额` 与 `含税金额` 仍在最后两列，因此合计列下标 `[14, 15]` **不变**；单测里同时钉住了列序与合计列下标，避免以后有人挪列却忘了改下标。
- 与「列名与列序照抄老表」（R1）的关系：这是用户明确要求的一处**刻意偏离**，已在列定义注释里写清。

## 3. 需求 2、3：工资付款

### 3.1 批量付款（用户选定：**每人一张付款单**）

- 端点：`POST /api/v1/hr/payroll-ledgers/pay-batch`
  body：`{ items: [{ ledger_id, amount }], payment_date, payment_method, bank_id?, currency?, remark? }`
  返回：`{ requested_count, succeeded_count, failed_count, total_amount, bank, succeeded[], failed[] }`
- **每人一张付款单**（不是「一张付款单核销多人」）：与实际银行转账笔数一一对应，冲销按人、单人出错只影响单人。
- **串行**执行、逐条 `catch` 隔离：复用既有的 `payLedger`（生成应付 → 建付款草稿 → 核销过账），不另写一条资金路径。失败靠 `payLedger` 自己的「软删草稿 + rollback_draft 审计」收尾，不留孤儿单据。
- 发放银行**在动手之前**校验一次：发工资必须指定银行账户，半路才发现账户非法会留下一批已建好的单据。
- 前端失败时**保留失败行的勾选**、点名失败的人与原因，成功行退出勾选。

### 3.2 按月导出（18 列）

`月份 | 工号 | 姓名 | 部门 | 岗位 | 员工类型 | 币种 | 应发工资 | 已付 | 未付 | 是否付款 | 台账状态 | 付款笔数 | 末次付款日期 | 末次付款方式 | 发放银行 | 付款单号 | 备注`

- **「是否付款」**（用户要求的那一列）：`应发 ≤ 0 → 无需付款`；`未付 ≤ 0 → 已付清`；`已付 > 0 → 部分付款`；否则 `未付款`。
- 三个金额列（下标 7/8/9）是数值列，落 Excel 数值类型。
- **合计只在单币种时给**：混币种就完全不设合计列并在表尾说明 —— 绝不跨币种相加（工资实际一律 CNY，但字段允许别的币种，不假设）。
- 取数**不按状态过滤**（含草稿）：页面上的当月台账就是这个范围，导出必须与页面同批，否则「页面上看得到、导出里没有」。
- 表尾恒定三条：是否付款的口径 / 已付只算已过账 / 本表不是银行对账单。

## 4. 需求 4：外汇一览表

完整设计见 [外汇一览表设计](../design/foreign-exchange-register-2026-09-17.md)，字段映射与待确认事项见
[0917 外汇一览表字段映射](../memo/0917-外汇一览表字段映射.md)。

要点：

- 报表 key `forex-receipts`（财务报表第 7 个子栏目），导出是**一个工作簿两张表**（外汇一览 + 客户汇总）。
- **一行 = 一次成品出库**；期间按**收款（实际到账）日期**筛选（用户选定）。
- **定金在出货前收到**，那时系统里还没有应收来源（应收来自成品出库过账），所以定金只能作为手工收入流水录入 —— 这就是给收支流水加 `payment_nature` + `order_no` 两列的原因（用户选定「加在【收支流水】上，并给收入流水加一个可选订单号」）。
- 「跟单」「银行手续费」两列**恒空**（系统无字段，用户选定「留空 + 表尾写清」）。
- 归属规则与「一笔收款只出现一次」的不变量见设计文档 §5；归不到的到账按原因分类进表尾，**不塞进任何一行**。

## 6. 过程中发现并修掉的三个真缺陷

1. **`receivable_source` 流水被挂到「订单最早那次出库」上**：一张订单多次出库时，每笔货款都会堆到第一次出货上，那一行的欠尾款变成负数、后面几行虚高。已改为「自己指向的那次出库」，只有订单级收款（定金）才退化成「最早那次」。
2. **没有订单号也没有来源的手工收入流水被静默丢掉**：候选收款按「订单/来源」收窄查询，天然捞不到这类流水，于是它们连表尾都进不去 —— 表里的汇入总金额会小于银行流水，财务看不出少在哪。已把「期间内的全部收入流水」并回候选集合。
3. **测试暴露的 `cash-flow-page` 断言歧义**：新增两列后有多个 `-`，原测试的 `getByText("-")` 匹配到多个元素。改为按行、按列计数断言。

## 9. 过程中的一次事故与恢复（记录在案）

在实现外汇报表时，我用 PowerShell 做了一次「读全文 → 切片 → 写回」的文件编辑，读入编码不对导致中文变成乱码；随后我用 `git checkout -- <file>` 想回滚这一次乱码，**却把该文件在上一轮（会计科目重构）里尚未提交的改动一并回滚掉了**。

恢复方式：`apps/api/dist/modules/finance/finance-report-query.service.js` 是上一轮结束时的编译产物（早于本次事故，且不含本次的未完成代码），我用它作为**权威参照**重写了源文件，然后重新编译并与该产物做**逐字节比对，结果完全一致** —— 即函数体、语句与求值顺序都已精确还原；文件里的中文注释按本次会话早先读到的原文补回（编译产物里注释被剥离，这部分无法逐字节验证，但已复核）。

后续约定：**不再用 PowerShell 做文本文件的读写往返**；文本编辑一律走文件工具，回滚一律先用 `git stash`/显式备份而不是 `git checkout`。
