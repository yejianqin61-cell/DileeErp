# Phase 1 实测报告：这台机器扛得住构建吗

日期：2026-11-13｜状态：已完成｜类型：实测记录

对应设计文档：[生产常驻 Agent 自动修 ERP](production-resident-agent-erp-maintenance-2026-11-13.md) §7 Phase 1。

## 结论

**能构建，但构建期间线上会被明显拖慢。** 一次完整构建耗时 10 分 46 秒，
期间 health p95 从 46 ms 涨到 826 ms（18 倍），峰值出现一次 5 秒超时，可用内存最低只剩 152 MB。

结论不是「不能做」，而是「构建要挑时间，并且要压住内存峰值」。

不是「构建才导致换页」。

## 三、DSH 在 Node 24 下能跑吗

跑了一次真实任务，不是 `--help`：

```text
任务：Read num.txt and reply with only the result of the addition.
环境：/opt/node24/bin/node + --profile headless --approval-policy never --permission-mode workspace-write
结果：stdout 输出 "2"，退出码 0，耗时 10 秒
```

密钥从生产 `.env` 读取，只在进程环境里传递，未打印、未落盘。

这条证明了三件事：Node 24 可用、headless 入口可用、模型出口可用。
不需要自写 SDK 驱动。

## 四、构建期间机器发生了什么

这是本轮唯一真正要回答的问题。采样每 5 秒一行，共 118 点。

| 指标 | 空闲基线 | 构建期间 | 变化 |
|---|---|---|---|
| health p50 | 8 ms | 67 ms | 8 倍 |
| health p95 | 46 ms | **826 ms** | 18 倍 |
| health 最大 | 47 ms | **5002 ms** | 超时一次 |
| 可用内存 最低 | 1189 MB | **152 MB** | −1037 MB |
| swap 已用 峰值 | 583 MB | **2093 MB** | +1510 MB |
| 1 分钟负载 峰值 | 0.02 | **5.24** | 2 核跑满 |
| 根盘已用 峰值 | 48% | 55% | +7 个点 |

各步骤实际耗时：

| 步骤 | 耗时 |
|---|---|
| 打包（git archive → tar） | 2 s |
| `npm ci --include=dev` | 3 min 21 s |
| `prisma generate` | 9 s |
| 构建 API | 4 min 8 s |
| 构建 Web | 2 min 57 s |
| 装配 standalone | 1 s |
| **合计** | **10 min 46 s** |

内存元凶抓到了：构建期间 `npm ci` 单进程 RSS 达到 **993 MB**。
可用内存只有 1169 MB，等于一个进程就吃掉了几乎全部余量，剩下的靠 swap 顶。

那一次 5 秒超时是我的采样探针自己撞上的（探针超时设为 5 秒），
说明那一刻 health 确实超过了 5 秒。**真实用户在那个时间点会看到卡住。**

## 五、构建有没有碰到生产数据

专门查了，因为构建目录里放了生产 `.env`。

| 检查 | 结果 |
|---|---|
| 构建期生产库连接数 | 8 条，**全部来自 `pid 866046`（线上 dilee-api）** |
| 构建进程对 `15432` 的连接 | **零** |
| Web 构建时段生产 API 收到的请求 | 40 条，**全部是我自己的 health 探针**，全部 200 |
| 构建是否执行迁移 | 否，`phase1-build.sh` 里没有 `migrate deploy` |
| 是否重启 PM2 | 否 |
| 是否切换目录 | 否，产出在 `/opt/dilee/agent/build`，`/opt/dilee/app` 未动 |

结论：**构建全程不碰生产库，不碰生产 API，不碰线上进程。**
Next.js 页面都是 `○ (Static)` 预渲染的客户端外壳，构建期不取数。

## 六、磁盘账

| 项 | 体积 |
|---|---|
| Agent 工作区 clone（含 .git） | 78 MB |
| 发布包 | 26 MB |
| 候选构建目录（含 node_modules） | 2.3 G |
| **agent 目录合计** | **2.4 G** |
| 构建后根盘可用 | 20 G → 18 G |

现在服务器上有 `app` ＋ 3 份 `app.backup-*`，每份 2.3 G，合计 9.2 G。
再加 agent 的 2.4 G，磁盘是够的，但没有余量做「保留很多份候选」。

## 七、由这些数字得出的三条硬结论

1. **构建不能撞上工作时段。** p95 18 倍劣化、峰值 5 秒超时，工人正在录单时不能发生。
2. **`npm ci` 是内存峰值主因，不是编译。** 每次构建都重新 `npm ci` 是浪费：
   Agent 工作区的 `node_modules` 可以跨工单复用，只在 `package-lock.json` 变化时才重装。
   这一条能把 993 MB 的峰值砍掉。
3. **需要内存闸门。** 可用内存低于阈值时应排队而不是硬上，否则同样的事会重复发生。

## 九、留给后续阶段的问题

1. 构建时段的窗口怎么定：完全避开工作时段，还是只在内存充足时才跑。
2. `npm ci` 复用方案：工作区保留 `node_modules`，按 lockfile 哈希决定是否重装。
   需要验证复用的 `node_modules` 不会让构建结果与生产漂移。
3. 备份保留从 3 份降到 2 份，回收 2.3 G，给候选目录腾空间。
4. 构建期是否要临时把 `dilee-web` 的 `NODE_OPTIONS` 调低，给构建让路。
