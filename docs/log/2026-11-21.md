## 1. 为什么正则必须换掉

`intent.ts` 用约 40 组关键词做意图分类，`triage.ts` 用关键词抽「模块/期望/入口」。
2026-11-19 刚为「再次尝试部署」补过一次词表 —— 那次修补本身就是证据：
**每补一个词就多一份误判面，而且永远补不完没见过的说法。**

改造前的最后状态：`isCommand()` 要靠「剥客气前缀 + 长度上限 + 语气尾巴」判断一句话是不是指令，
`classifyKind` 靠 19 个动词区分缺陷与需求。这些规则真实、有用，但它们描述的是**我们见过的句子**，
不是**用户会说的话**。

## 2. 换成了什么

`dispatcher.ts`：模型只能通过 7 个工具表达意图，返回值归一化成 `DispatchAction`。

```
create_ticket   append_ticket   start_run   status
ask_more_info   reply           deploy
```

三条**不交给模型**的边界（写在代码里，不写在提示词里）：

| 边界 | 实现 |
|---|---|
| 进度答案不调模型 | `status` 只说「该查进度」，答案仍由 `progress.ts` 的本地事实生成 |
| 「回复卡片 = 追加」 | `decideRoute` 读 `parent_id`/`root_id`；模型说建新单也会被强制纠偏 |
| 模型不可用不动作 | 只回一句兜底话术，不建单、不开工、不部署 |

还有一条我主动加的：**动作里不带「用户原话」参数**。建单与追加一律存 Coordinator 收到的
原话，模型不可能改写或概括用户说的话。

## 4. 播报精简

**分两个通道看**：卡片是原地更新（不新增群消息），群消息才是刷屏源。

| 通道 | 改造前 | 改造后 |
|---|---|---|
| 群消息 | 开工 + 验证阶段 + 每 5 分钟心跳 + 结果 ≈ 5–7 条 | **开工 + 收尾 + 结果 = 3 条** |
| 施工卡片 | 5 行（含工具调用数、模型自述原文） | **3 行**（已用 / 当前 / 改动） |
| 状态查询 | 完整 | **完整不变**（那是查询通道，不是播报） |

部署也是：开始一条、结束一条，中间靠卡片。

## 5. 真机验证发现的两个真问题

### 5.1 DeepSeek 函数调用可用（原先唯一未知项）

`scripts/probe-dispatch.ts` 跑真实模型 14 条：**全部 `source=model`，无一条落兜底**，
延迟 **420–1500 ms**。`tool_choice: 'required'` 工作正常。

### 5.2 首轮判错两条 → 改提示词，不是改代码

| 原话 | 首轮 | 修正后 |
|---|---|---|
| 部署脚本要改，别每次都失败 | 追问「具体哪里失败」 | `create_ticket` |
| 首页任务提醒面板的任务点进去跳转错了 | 追问「点哪一类任务跳错了」 | `create_ticket` |

原话已点出具体页面/功能点，而 Coding Agent 读代码后补全「期望」的能力远强于群里追问。
为「你没说清期望」拦下来，正是用户反复抱怨的「问一句被挡回来」。

提示词新增「拿不准时怎么办」：**点出具体页面/模块/功能点就建单**，只有整句没有任何具体
位置（「这个不对」「有问题」）才追问，且必须问**一个**能让下一条消息直接开工的问题。

复测 15 条全部符合预期：`DISPATCH_PROBE_OK`。

### 5.3 附带观察：模型会自己认出重复需求

「领料单打印出来的规格型号带了个备注，太长了」→ `append_ticket T-0023`，正是同一件事，
没有重复开单。不在设计预期内，但行为是对的 —— 提示词给了最近 12 张工单的事实。
