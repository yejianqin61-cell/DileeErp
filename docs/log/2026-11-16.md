## 根因

`coordinator.handle()` 只有两条分支：「回复卡片 = 追加」「其余 = 新需求」。
从来没有判断过「这条消息是不是在问事」。分诊只回答「需求能不能开工」，
对非需求输入只能给出「不够开工」——语义正确，行为完全错。

## 设计（先落文档再动手）

见 [进度同步与问答](../design/ticket-bot-progress-and-qa-2026-11-16.md)。
架构文档升到 v1.2，补拓扑、进度三通道与新模块。

关键决定：

| # | 决定 | 理由 |
|---|---|---|
| 1 | 消息先分意图，默认是「需求」 | 把不认识的输入当需求，最坏是追问一句；当问答则会丢需求 |
| 2 | 进度查询不调模型 | 进度是可枚举事实，模型只会重述，还可能编「已完成 70%」 |
| 3 | 问答直连 DeepSeek，不占 DSH 车道 | 2 核上一次 run 5–15 分钟，让「你是谁」排这个队不可接受 |
| 4 | 进度落盘 | 用户随时可能问进度；进程重启后仍答得出 |
| 5 | 群内播报只发阶段与 5 分钟心跳 | 事件逐条刷群会把群刷爆 |

## 实施

三个新模块 + 三处改造：

| 文件 | 内容 |
|---|---|
| `tools/ticket-agent/src/intent.ts` | 五类意图：requirement / status / question / chitchat / command |
| `tools/ticket-agent/src/progress.ts` | 事件→阶段、进度卡、群内播报、状态回答文本 |
| `tools/ticket-agent/src/answerer.ts` | 带工单上下文的问答，模型失败有兜底 |
| `src/coordinator.ts` | 意图路由、主动同步（卡片/播报/落盘）、排队位次 |
| `src/ticket-store.ts` | `progress` / `result` 字段与写入方法 |
| `src/main.ts` | 问答模型、播报频率配置与启动日志 |

顺带修掉：追问只有一项时仍说「补两点」；`needs_info` 话术补「直接再发一条消息补充」。
