## 根因

`coordinator.handle()` 只有两条分支：「回复卡片 = 追加」「其余 = 新需求」。
从来没有判断过「这条消息是不是在问事」。分诊只回答「需求能不能开工」，
对非需求输入只能给出「不够开工」——语义正确，行为完全错。

## 设计（先落文档再动手）

见 [进度同步与问答](../design/ticket-bot-progress-and-qa-2026-11-16.md)。
架构文档升到 v1.2，补拓扑、进度三通道与新模块。

关键决定：

| # | 决定 | 理由 |
|---|---|---|
| 1 | 消息先分意图，默认是「需求」 | 把不认识的输入当需求，最坏是追问一句；当问答则会丢需求 |
| 2 | 进度查询不调模型 | 进度是可枚举事实，模型只会重述，还可能编「已完成 70%」 |
| 3 | 问答直连 DeepSeek，不占 DSH 车道 | 2 核上一次 run 5–15 分钟，让「你是谁」排这个队不可接受 |
| 4 | 进度落盘 | 用户随时可能问进度；进程重启后仍答得出 |
| 5 | 群内播报只发阶段与 5 分钟心跳 | 事件逐条刷群会把群刷爆 |

### 线上预检踩到的真实缺陷

第一次验收部署在预检就停了：

```
线上版本 3e0a8ccb 不是当前 HEAD 的祖先（工作区基线落后于线上）。
```

但手工在仓库里跑同一条 `git merge-base --is-ancestor` 是通过的。根因：
`deploy.ts` 的只读探测 `probe()` 没传 `cwd`，`git` 跑在机器人进程目录（不是 git 仓库），
直接以 128 退出，被当成「不是祖先」。修法：`probe` 增加 cwd，三处 git 探测统一传 `config.repoPath`；
测试补断言钉死 cwd。

### GitHub 推送

- 服务器已生成专用 deploy key（`/home/ubuntu/.ssh/dilee_github`），
  `origin` 的 fetch 用 HTTPS、push 用 SSH；**公钥需要用户在 GitHub 仓库 Deploy keys 加一次**。
- 本次代码由开发机推到 GitHub：`528b145 → f9cdd7a → ebc9d2d`（含两笔工单修复、机器人 v1.3、cwd 修复）。
- 服务器 `git fetch` GitHub HTTPS 遇到 `GnuTLS recv error (-110)`（网络中断，非权限），
  改用增量 bundle（269KB）同步仓库并 `reset --hard`。以后 push 走 SSH，fetch 可继续用 HTTPS 或 bundle。
