## 实测盘点（不是估算）

为避免方案建在假设上，今天对生产机 `ubuntu@118.178.95.156` 做了一次只读探测。

| 项 | 实测 | 对方案的约束 |
|---|---|---|
| 机型 | 2 vCPU / 1740 MB / 4 GB swap / 40 G 盘，可用 20 G | 内存是首要约束 |
| 现有进程 | api 100 MB + web 54 MB + postgres 75 MB ≈ 230 MB | 余量约 1050 MB |
| 现有目录 | `app` 2.3 G + 3 份 `app.backup-*` 各 2.3 G | 磁盘要先收紧备份策略 |
| Node | v22.23.2（线上）；DSH 两包声明 `engines >= 24.9.0` | 需为 Agent 单独装 Node 24 |
| DSH 包体 | `node_modules/@deepseek-ai` 653 MB，已随发布包上机 | 无需额外下载 |
| 出站 | `api.deepseek.com` 401、`open.feishu.cn` 404、npm/github 200 | 模型与飞书都能出站 |
| 入站 | 公网 health 200；无 443、无证书；nginx 只开 80 | 飞书回调不可行，应选长连接 |
| 权限 | `sudo -n` 通过，`ubuntu` 在 `docker` 组 | 部署脚本已按此写 |
| 云端构建 | npm ci 3 m 15 s + API 3 m 30 s + Web 3 m ≈ **10 min** | 一次上线占满 2 核 10 分钟 |
| 迁移/切换 | 迁移 6 s；切换 14 s | 切换很快，慢的是构建 |

另做了一次真实启动验证，确认 DSH 在这台机器上能跑通一次性任务：

```text
node node_modules/@deepseek-ai/dsh/lib/bin.js --profile headless --approval-policy never 'echo hi'
→ 返回 hi（Node 22.23.2）
```

这条结果同时说明两件事：入口可用，无需自写 SDK 驱动；以及 Node 22 虽能跑但不受支持（见 D6）。

## 结论：瓶颈不是 Agent，是资源

方案整体可行，但**施工顺序必须先把资源证死，再谈自动化**。理由是构建本身就吃满 2 核 10 分钟，
而门禁又是上线前提；如果不先量出峰值内存与线上延迟偏移，自动化会在第一次真实构建时把生产拖慢。

三件真正的新东西只有：飞书收发、工单状态机、门禁编排。其余全部复用。

## 关键技术判断

| # | 判断 | 依据 |
|---|---|---|
| 1 | 飞书选**长连接**，不选 HTTP 回调 | 服务器无 443/证书；长连接只需出站，实测可达；省掉验签、防重放与 3 秒预算 |
| 2 | 「原地热重载」= 目录切换 + PM2 重启，不做 HMR | 与 `docs/SelfEnvolvingTry/` 的「热重载」（工具快照指针切换）不是一回事 |
| 3 | 生产目录继续不是 Git 工作区；Git 只进 Agent 工作区 | 对部署标准:8 的追加而非推翻；`/opt/dilee/app` 仍只由发布包写入 |
| 4 | 单实例、单车道串行 | 长连接是随机投递，多副本会丢事件；机器也只有 2 核 |
| 5 | 复用既有部署四件套，只补 Linux 侧打包 | `remote-*.sh` 一行不改，这是本次最大的成本节省 |
| 6 | 审批策略固定 `never` + `workspace-write` | 常态路径不允许出现需要人批准的调用；出现即视为设计缺口 |
| 7 | 回滚只回代码，不回迁移 | 迁移必须前向兼容；迁移处置权永久留在人 |

## 决策记录（按宪法 §Decision Traceability）

- 现存原料数量 = 已过账 + 待入库（与原「合计」口径相同，仅正名；不再单独加「合计」列，避免两列同值混淆）

- 迁移前向兼容（只加列、加索引、回填，不删不改现有数据）
