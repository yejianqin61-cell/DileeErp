# 2026-11-05

## 用户反馈：想修改销售单，但「BOM 表已经建立」其实没填内容

> 「用户反馈，想修改销售单，但是销售单显示 bom 表已经建立，但是 bom 其实也没有填入内容，这时候怎么办？可不可以增加一个 Bom 表的删除键？或者有别的办法」

### 排查：不是操作问题，是一条死路

1. 销售单（已确认）→ 采购/生产在 BOM 表页点「新建 BOM 表」，`POST /boms/from-sales-order/:id` 只建**表头**
   （`boms` 一行、`status = draft`），明细要靠 `PUT /boms/:id/items` 再保存 —— 建完没录就关掉，库里留下 0 明细的空壳。
2. 销售单编辑页改品名/数量/单价/税率等**核心字段**保存 → 服务端 `SALES_ORDER_CORE_FIELDS_LOCKED`
   （「销售单已有 BOM、采购或生产下游事实，核心字段需先回退下游」）。
3. 想「回退草稿」再改 → 也被 `SALES_ORDER_DOWNSTREAM_EXISTS` 挡住（同一个判定）。
4. 想去删掉那张空 BOM → **没有任何删除入口**：`BomsController` 只有 list/get/create/patch/put items。

根因两条：**（a）空 BOM 被当成下游事实；（b）BOM 本身不可删。** 两条叠在一起，用户无路可走。

顺带发现：schema 与采购计划侧**早就按「BOM 可以软删」设计**（`purchase_plans.bom_snapshot` 注释
「BOM 被软删之后，计划上仍要看得见『这是哪一版 BOM 的计划』」、计划详情 `bomDeleted` 告警、
`loadBomForRevert` 允许已软删 BOM），只是删除入口一直没实现 —— 本轮补的就是这半截。

### 用户拍板（2026-11-05）

- 「空 BOM 一键删；有明细的 BOM 需填原因也能删」（不是只删空壳）；
- 「加按钮 + 保存时自动清理『空壳 BOM』」（不让用户自己绕到采购页）。

## 决策

| # | 决策 | 理由 |
|---|------|------|
| D1 | BOM 支持**软删**（表头 + 明细行一起软删），不物理删 | 外键 RESTRICT；采购单/生产单/采购计划按 `bom_id` 引用，物理删必被拒 |
| D2 | 空 BOM（0 明细、无计划、无采购单、无生产单）**一键删**，不填原因 | 不含任何业务事实 |
| D3 | 有明细或已有采购计划的 BOM 也能删，但**必须填原因** | 删的是有人维护过的资料，审计要说得清 |
| D4 | 被未取消采购单 / 未删除生产单引用时**拒绝删除**，提示先回退下游 | 与销售单核心字段锁同一口径；采购单可「退回采购计划」、草稿生产单可删 |
| D5 | 采购计划**不阻止**删除，BOM 软删后计划独立存活 | 既有设计（2026-09-27），计划页显示「BOM 已被删除」 |
| D6 | 销售单保存核心字段时**自动清理空壳 BOM**（审计 `auto: true`，响应 `released_empty_boms`，成功提示说出来） | 用户不用绕路；非空 BOM 仍照旧挡住 |
| D7 | 回退草稿用**同一条**空壳判定 | 否则「保存能过、回退不能过」，被挡理由本来是同一个 |
| D8 | 被挡时报错说清「在挡什么、下一步去哪」 | 原来一句笼统的「已有 BOM」正是用户困惑的来源 |

设计文档：[bom-delete-and-empty-shell-release-2026-11-05.md](../design/bom-delete-and-empty-shell-release-2026-11-05.md)。

## 实现

### API（`apps/api/src/modules/sales/`）

- **新增 `bom-facts.ts`（共享判定）**：`bomFacts` / `salesOrderBomFacts` / `isEmptyShellBom` / `bomHasDownstream` /
  `bomBlockedReason` / `AUTO_RELEASE_EMPTY_BOM_REASON`。销售单与 BOM 删除两条路径用**同一份**「下游事实」定义：
  明细只数未删行；采购单只数未删除且 `status != cancelled`；生产单数未删除的任何状态；采购计划单独给出（允许存在）。
  空壳 = 0 明细 + 无计划 + 无采购单 + 无生产单。
- **`boms.service.ts`**：`deletePreview`（只读，允许略陈旧；真删时行锁后重算）、`delete`（事务内
  `SELECT … FOR UPDATE` → 重算 → 判下游 → 判原因 → 表头 + 明细一起 `audit.softDelete`；事务外写
  `bom.delete` 审计，payload 带 `order_no/version/item_count/reason/purchase_plan_id/采购单数/生产单数`）。
- **`boms.controller.ts`**：`GET :id/delete-preview`、`DELETE :id`（`BomDeleteDto { reason? }`，
  `@MaxLength(500)`，trim 在服务层）；权限沿用类上 `@RequireAnyModules("procurement","production")`。
- **`sales-orders.service.ts`**：`releaseEmptyShellBoms(tx, …, mode)` 私有方法；`update()` 把核心字段守卫移入事务
  （避免「判完是空壳、写之前有人补采购单」的竞态），提交后逐张写 `bom.delete` 审计（`auto: true` + 固定理由），
  响应新增 `released_empty_boms: [{ bom_id, version }]`，`impact_warning` 按清理后 BOM 数算；
  `revertToDraft()` 锁行后先清理再按下游计数。草稿单 / 只改非核心字段 / 没有 BOM 三条路完全不查 BOM 表（旧查询面不变）。
  新报错文案例：`这张 BOM（v1 有 3 项明细、已有采购计划 PP-…），核心字段不能直接修改：请先到【采购 → BOM表】删除这张 BOM（已下单/投产的需先回退下游）`。

## 追加：建立 BOM 之后，销售单仍可换图/删图（核心字段锁按实际改动判定）

用户原话：「希望在销售单确认后，在系统的 BOM 表中也可以编辑图片。而且当前换图和删除图片都不能实现」，
澄清后：「不是在 BOM 表里面，而是建立了 BOM 表之后，还能编辑销售单中的图片」。

### 根因

编辑器保存时把**整份表单**（11 个核心字段 + 37 个细化标量）发上来（「空串 = 清除这一格」必须表达得出来），
而服务端守卫按「请求里带没带这个键」判定核心字段改动。于是已确认单只要**有 BOM（非空壳）**，
任何一次界面保存（包括**只改图片**）都会被 `SALES_ORDER_CORE_FIELDS_LOCKED` 挡住 ——
换图/删图在界面上做了、点保存却存不上，用户看到的就是「不能实现」。
顺带修掉同一条真实路径上的旧问题：改订单号（编辑器同样整份回传）也被这道锁误挡，
而 2026-09-30 的口径是「改号任何时候都行」。

### 改动

- API：新增纯函数 `coreFieldsActuallyChanged(current, input)`，按**值**判定 11 个核心字段是否真改：
  文本 null/undefined/空串同义、首尾空白不算；Decimal 按规范写法比较（`"100"` 与 `"100.0000"` 同值）；
  未传的键跳过。`update()` 只在为真时才跑 BOM/采购/生产守卫（为假连下游计数查询都不发）。
  真改数量/单价/金额仍照旧被锁挡住（0.01 的改动也会被识别）。
- Web：上传/换图成功都提示「第 N 张图片已上传/已换（保存销售单后生效）」；删掉行图后兜底出现的
  物料图带 `title`「引用的物料清单图片（不是这一行自己的图）」，删除提示也写明这一点 ——
  两个都针对「点了按钮像没反应」的误会（图片仍要保存后生效，没有 DELETE 端点）。
- 明确不做：不在 BOM 表里加图片字段（用户已澄清不是这个需求）；不因为要改图就放开核心字段锁；
  不把图片改成"点一下立即落库"。

凭证是对的（用户说的就是它：挂账凭证借方 = 管理费用）。错在**收支流水页与收支报表取的是主科目**：
已挂账付款的主科目一律是「应付账款」，于是整页付款流水的「分类 / 项目」都是「负债类 / 应付账款」，
按「损益类 / 管理费用」筛一条都筛不出来。业务科目一直在库里（`category_subject_id`）——
2026-10-13 只把它加给收支明细表一列，流水页与汇总表没跟上（正是
`docs/audit/finance-subject-chain-diagnosis-2026-11-04.md` §5 里 P1「展示打通」的遗留）。

### 口径

- **业务科目 = 收支类目，没有类目（手工流水 / 确认即记账流水）才退回主科目。**
  一条规则（`cash-flow.domain.ts` 的 `cashFlowBusinessSubject`）同时覆盖自动流水与手工流水。
- 「分类 / 项目」两列一律显示业务科目；主科目（记账对方科目）不再占这两列，但**信息不丢**：
  流水页挂在项目格悬停提示上，收支明细表单独一列，凭证仍用它生成。
- 为什么不是「把主科目也改成管理费用」：主科目是 `POST /finance/vouchers/from-cash-flow/:entryId`
  生成凭证时的业务分录科目，已挂账付款必须「借 应付账款 / 贷 银行存款」；改成管理费用等于把费用记两遍，
  账面上还看不出来。变的是**展示与统计口径**，不是记账。

### 实现

| 层 | 改动 |
| --- | --- |
| 领域 | 新增 `cashFlowBusinessSubject(row)`（业务科目）与 `cashFlowSubjectWhere({subjectId, category})`（筛选同口径；两个条件同时给是「交」不是「并」） |
| 流水列表 | `ENTRY_INCLUDE` 带上 `categorySubject`；`?subject_id=` / `?category=` 改按业务科目匹配（类目为空才退回主科目）—— 否则列表上写着「管理费用」、筛它却没有 |
| 流水更正 | `PATCH` 新增 `category_subject_id`：自动写入的流水改的是收支类目，**不动**主科目；传 null 清空、不传不改（与银行账户/款项性质同一约定）；选了停用/不存在的科目显式 422 |
| 收支明细表 | 第 6 列「收支类目」→「记账对方科目」（内容改为主科目；与业务科目相同时留空，不重复写） |
| 收支汇总表 | 聚合键从 `subject_id` 改成业务科目 id —— 否则「这个月管理费用多少」在表里只能看到一行「应付账款」 |
| 收支流水页 | 「分类 / 项目」显示业务科目；对方科目挂在项目格 `title`（「记账对方科目：负债类 / 应付账款」） |
| 更正弹窗 | 自动流水显示「收支类目」下拉（预填类目）+ 一行说明「记账对方科目：…（由来源单据决定，生成凭证用它，不在这里改）」；手工流水仍是原来的主科目下拉 |
| 凭证模块 | 「收支流水」表同口径显示业务科目（生成凭证仍用主科目），搜索也带业务科目名 |

### 边界与没做

- **不改线上数据**：历史流水不回填 `category_subject_id`（除 `supplier_payment` 外多为 NULL），显示按上面的回退规则；
  还款类/工资类等本身就是主科目。要补历史数据需要财务确认后单独做（当前生产库 165 条流水里 164 条是已冲销状态，属既有数据现状，本轮不动）。
- 不拆流水：一笔付款同时核销多个科目时，收支类目仍只取金额最大的那条（2026-10-13 的既有取舍）。
- 手工录入表单仍只有「会计科目」一格（那个科目就是它的业务科目），不新增第二格。
- 收支明细表的列头改名会让导出 Excel 的第 6 列表头变化（「收支类目」→「记账对方科目」），金额与行数不变；
  收支汇总表按新口径**分组**会变化（金额合计不变，只是从「应付账款」一行拆回各业务科目）。
