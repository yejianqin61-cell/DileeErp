# 2026-10-13

## 采购计划：分开下单 + 同供应商自动收束在一张采购单里 + 列表展平显示物料明细

用户一次提了两条：

> 「1.针对采购部分的，采购计划，现在改成可以分开下单，有确定单价的物料先下单。如果相同的供应商的
> 不同物料没有同时下单，下单之后也要自动收束在一个采购单里。
> 2.采购计划的那个页面，也要显示物料名称等等 column。都要显示」

**先问后做**（两个问题，每题给推荐项）：

| 问题 | 他的回答 |
| --- | --- |
| 自动收束的边界 | **已有单「已下单 + 无任何到货」且币种相同 → 并入；有到货或币种不同 → 新建一张** |
| 「显示物料名称等 column」指哪个页面 | **列表页展平成「一行 = 一条计划明细」** |

### 1. 两条需求各有一半是既成能力，先分清再动手

| 用户的话 | 查证结果 | 本轮动作 |
| --- | --- | --- |
| 「分开下单」 | ✅ 已有（2026-09-27 口径 6 的多波次：勾哪几行下哪几行，没收进组的行留在计划里） | 不动 |
| 「有确定单价的物料先下单」 | ✅ 已有（2026-10-11：0 价一律不下单，前端排除在本次请求外 + 复核框点名） | 不动 |
| 「同供应商不同物料没同时下单，下单后**自动收束在一张单里**」 | ❌ **没有** —— 每一波都新建一张单，分两波买同一家 = 两张采购单 | **本轮主改动** |
| 「列表页也要显示物料名称等等 column」 | ❌ 没有 —— 列表一行 = 一份计划，只有计划级信息 | **列表展平** |

**这两条其实是同一条链的两端**：2026-10-11 定了「没确定单价的先不下单」，同一家的物料就**必然**分波下
（辅料等客户资料才有价）；而 2026-09-17 又定了「一个采购单内，一个供应商下一个单」。
两条同时成立只有系统能办到 —— 一波一波下、落点还是同一张单，所以本轮先把这条补上。

### 2. 自动收束：判据四条，缺一不可

`PurchaseOrdersService` 新增 `findMergeTarget()` / `appendItems()` / `openOrdersForPlan()`，
三条共用一段查询 `queryLinkedOpenOrders()`（"什么算可并入"只有一处实现）。

| # | 判据 | 为什么 |
| --- | --- | --- |
| ① | 这张单是**这份计划自己下出来的**（明细里有计划行回写的链接，即 `purchase_plan_items.purchase_order_item_id` 指向它） | **不按供应商猜** —— 按供应商猜会把别人手工建的同供应商单吞进来，而这类错误不报错，只会让两张不相干的单悄悄长在一起 |
| ② | 供应商与**币种**都对得上 | 一张单一个供应商、一个币种；并错了财务会收到一张"单价是美元、单头写着人民币"的单 |
| ③ | 状态还是 `ordered` | —— |
| ④ | 任一未删明细**都没有到货记录** | 到货是既成事实，后面挂着质检/入库/应付来源。⚠️ 这条按**明细的到货记录**判，**不看状态**：`receipt()`（V1）登记到货时不刷单头状态，库里真的存在"status 还是 ordered、明细却已收货"的单 |

多条候选取其中 `createdAt` 最新的那一张（= 上一波下的那单）；**已经被到货排除的不算候选**，
所以"上一波那张收货了"不等于"这家不能收了"—— 更早那张若仍未收货，它本来就是一张有效、未收货的对外凭证。

**追加只往后加**（口径 3）：单号、供应商、币种、采购日期、交货日期、备注、打印字段一概不动，
只 `total_amount` 累加 + 单头 `extension_data.purchase_plan_merges` 留痕（**只保留最近 20 条**：
采购单是长期存在的，单头 JSON 不设上限会被养成一个越来越大的字段）。
审计分两处：计划侧 `purchase_plan.order` 记 `merged_purchase_order_nos` / `merged_line_count`，
采购单侧每条并入各记一条 `purchase_order.append_plan_items`。

**计划侧零新增字段**：并入之后 `purchase_plan_items.purchase_order_item_id` 照旧指向**新追加的那条明细**
——「已下单」的表示仍然只有一个，退回流（断开链接）也跟着不变，**没有迁移**。

### 3. 三处刻意的实现细节

1. **`findMergeTarget()` 在事务里调**：两个窗口同时给同一家下单时，事务外判定会让两边都看到
   "没有可并入的单"从而各建一张 —— 那正是这个功能要消灭的场景。
2. **回写链接只认这一波新建的明细**：并入的那张单上**原有**的明细带着上一波写进去的同一个认领标记，
   不过滤就会把那些计划行的 `updatedBy/updatedAt` 再刷一遍 —— 不算错，但会让列表的
   「最后更新（人 + 北京时间）」说成这次下单的人，而那个人根本没碰那些行。
3. **"并 or 新建"必须看得见**（口径 6）：详情接口新增 `open_purchase_orders`，收束预览每组写明
   「并入 PO-xxx（已有 N 行）」或「新建一张（这家还没有未到货的已下单采购单 / 已有到货 / 币种不同）」；
   下单成功提示也分成两半说。静默地"有时候并、有时候不并"是最难查的一类坏。

### 4. 列表展平：一行 = 一条明细，13 列

`GET /purchase-plans` 的每一项新增 `lines[]`（一次查询取回，**不新增接口** ——
`lib/page-data-alignment.test.mjs` 盯着这一页的请求绑定表，加接口会把那条有用的守卫顶红）。

13 列（宽度百分比和为 100%，`COLUMN_WIDTH` 常量集中一处）：
计划编号 9 / 销售单号 9 / 货号 6 / 客户 8 / 物料名称 12 / 型号 8 / 单位 4 / 本次采购量 7 /
单价 5 / 行总价 7 / 供应商 9 / 下单状态 9 / 预计到货 7。

三处取舍（口径 7）：

- **计划级汇总不再单独成列**：未下单行数 / 计划金额 / 状态 / 最后更新挂在「计划编号」那一格的
  `title` 上。它们与 13 个明细列塞在同一张表里会变成 20+ 列（1366px 上每列不到 70px），
  那正是 2026-09-27「一次性展示所有 column」要防的事。
- **计划编号就是入口**：不再单设「操作」列（它是 13 列里最先被牺牲的那一列）。
- **一行明细都没有的计划补一行占位**：否则它会从列表里凭空消失，而它唯一的入口就是这一页。

单价 0 的行在列表里也标红（与详情表同一口径：0 价不下单）；`有序 + 采购单号` 合成「下单状态」一格
（13 列里没有位置再拆一列单号，而这两件事本来就是同一个问题的两半）。

## 第二轮：收支明细表的「收支类目」+ 确认应付的搜索与批量删除

用户同一天又提了两条：

> 「1.财务部分，收支明细表，也要显示收支类目。比如说采购某个物料，或者其他应付其他应收也要带上会计科目。
> 而且导出的 excel 也要显示相应的 column。
> 2.财务，确认应付，加一个搜索框，加一个批量删除（只支持其他应付的删除）」

**先问后做**（每题给推荐项，共问了三轮）：

| 问题 | 他的回答 |
| --- | --- |
| 财务看到的是什么问题 | 列**有**，但采购 / 其他应付 / 其他应收这些行的**科目不对或不一致** |
| 「收支类目」怎么落地 | **另加一列**（不动现有的「分类 / 项目」） |
| 批量删除里有的行不能删时 | **逐条删**：能删的删、不能删的跳过并点名 |

### 1. 根因：现有两列回答的是「现金分录的另一头」，不是「这笔钱算什么」

排查（§1.1）：`cash_flow_entries.subject_id` 是**销账那条现金分录的对方科目** ——
2026-09-24 的「确认即记账 → 两步口径」之后，**已挂账**的付款销账一律记 `应付账款`、
收款记 `应收账款`（`supplier-payment.service.ts` 的 `settled = 全部挂账 ? ["应付账款"] : 候选链`）。
所以财务在收支明细表里看到的是一列「应付账款」，而"这笔钱花在什么上"（房租费 / 备用金 / 原材料）
只在**单据**上：其他应付的条目科目、覆盖它的对账单科目。

**不能把「项目」那一列改成类目**：从一条流水生成凭证时，凭证的对方科目就是流水上的 `subject_id`。
改成「房租费」后生成出来的凭证是「借 房租费 / 贷 银行存款」，而房租费在**确认应付**那一步已经借过一次
（挂账凭证），**成本会重复记一次**，账面上看不出来。所以按用户选择的方案 **另加一列**
`category_subject_id`（与主科目分家），并写进设计文档。

### 2. 收支类目怎么取（写进流水、页面与导出同步）

```
① 本次核销的**单据**上写的科目：应付 = 条目 > 覆盖它的对账单；应收 = 覆盖它的应收对账单
     多条时取「核销金额最大」的那一条（与主科目"按金额最大的来源类型"同一条思路）
② 单据上都没填 → 按来源类型的候选链（采购 → 原材料/主营业务成本；收款 → 主营业务收入）
```

三个刻意的取舍：

1. **宽松取值**：① 来自单据、可能早就停用 —— 认不出就**安静地退回 ②**，绝不让一笔已经发生的付款
   因为一个分类字段过不了账（与主科目"选了不存在的就 422"的严格语义刻意不同，各自测了用例）。
2. **落库在流水上**（新列 + 迁移），不是报表时现算：报表要能按它筛选/导出，而且手工流水没有来源可反查。
3. **手工流水这一格留空**并在表尾说明：手工录的时候只选一个科目，那个科目**就是**它的类目
   （`分类 / 项目` 已经写着它了），再抄一列没有信息量。

导出与页面**同一张 `ReportTable`**（既有的预览/导出同源口径），所以 Excel 自动多了这一列 ——
不需要动前端（报表页的列由后端 `ReportTable.columns` 下发）。

### 3. 确认应付：自己的搜索框 + 批量删除

- **搜索框**：页面顶部本来就有（`payable-search`），但它在流转看板之上、离「确认应付」那张表很远，
  而且它管三个页签。所以在**这张面板的筛选栏里**再加一个（`payable-ledger-search`），
  并且比顶部那个多搜两样：**费用说明**与**会计科目**（财务找其他应付时说的就是"那笔房租""备用金那几条"）。
  两个框各用各的状态，互不改写 —— 否则「在确认应付里搜了一下，切到应付对账发现那张表也被过滤了」。
- **批量删除**（`POST /finance/payable-entries/batch-delete`）：**逐条**调用既有的 `removeOther()`
  （每条一个事务），返回 `{ deleted, failed }`。判据只有一份 —— 后端仍然是唯一裁判，
  它拒了的进 `failed` 并由前端**点名到单号 + 后端那句人话**。
  按钮只数"可删的其他应付"（其他应付 + 草稿/已确认未付款 + 未被对账单覆盖），
  不能删的在弹窗里逐条写原因（不摆点了必然报错的按钮，也不静默少删）。

## 第三轮：采购 BOM 表列全已确认销售单 + 记账凭证导出（带摘要）

用户同一天又提了两条：

> 「1.采购模块,BOM表,没有新建BOM表的地方.只要有销售单事实的单子,就要允许也在采购中创建保存编辑BOM表.
> 2.财务模块,记账凭证中,摘要也要一并导出.」

| 问题 | 他的回答 |
| --- | --- |
| 「有销售单事实」放到哪一档 | **修取数**：列出全部**已确认**销售单（后端规则不动） |
| 「摘要也要一并导出」指哪种 | **新增凭证 Excel 导出**，一行一条分录，带摘要 |

### 1. 采购 BOM 表："没有新建入口"是**取数**的锅，不是权限

根因（一行代码）：那一页取的是 `apiGet("/sales-orders")` —— **不带状态**，
而 `GET /sales-orders` 默认 `page_size=20`，给的是**最近更新的 20 张任意状态**销售单；
页面再在这 20 张里按「已确认」过滤。于是"最近动过的都是草稿"时**整页空**、
连「新建BOM表」按钮都不存在，更早的已确认单也永远轮不到。

生产页的同一入口一直是对的（`?status=confirmed&page=1&page_size=200`）—— 现在两处逐字一致。
前端的二次过滤**删掉**了（口径 1）：再过滤一次正是这次的缺陷形态。

**保留「只有已确认销售单可以建 BOM」**（用户也选了这一档）：草稿单随时会改，
而且**下游全都要求已确认**（采购计划 `loadBom()`、采购单 `refs()`、生产单候选）——
放开草稿建 BOM 只会造出"有 BOM 但什么都开不出来"的死角。

顺手补一句人话：列表为空时**才**多问一次草稿张数（`?status=draft&page_size=1` 取 `meta.total`），
空状态从"暂无已确认销售单"变成"还有 N 张销售单是草稿：BOM 只能建在已确认的单上"。
这次请求**不在 `Promise.all` 里**（失败不影响主数据，也不动那条有守卫盯着的绑定表）。

### 2. 记账凭证导出：一行一条**分录**、带摘要

排查：**Excel 导出原先不存在**（凭证纸与导出 PNG 都已带摘要，只有 Excel 没有出口）。
而摘要与会计科目是**分录行**上的字段 —— 所以新导出的粒度是**一行一条分录**，
否则"这笔钱记到什么科目、凭什么"恰恰看不见。

列：`凭证号 | 日期 | 期间 | 状态 | 来源 | 行号 | 摘要 | 会计科目 | 借方金额 | 贷方金额 | 币种 | 备注`。
四条口径：摘要**空则回退凭证总摘要**（与凭证纸/PNG 同一口径）；借/贷分列**空白的一边是空单元格**
（写 0 会被读成"确实为零"）；金额落**数值类型**；**不设合计列**（一列里可能混币种）。
端点 `GET /finance/vouchers/export.xlsx`：路由名是单段，**必须排在 `@Get(":id")` 之前**；
不加管理员门（与列表同一份数据、同一道 finance 门，导出多不了一层保护）。

## 第四轮：采购订单导出收列 + BOM 建表页的物料搜索

用户原话：

> 1.采购部分，采购订单导出时，那个excel表单里面，可以不用有供应商这一个column。采购单号这个字段也不需要导出。交货日期也不需要这个column
> 2.建立BOM表的页面，生产和采购都是，在添加行，选择物料的时候，要支持搜索功能，搜索物料清单里面的

第 1 条有一处会误删的歧义（表头也有「供应商名称：」与「交货日期：」两格），先问了一轮：
用户选「两个都保留」——**只删明细表里逐行重复的那两列 + 表头那一格「采购单号：」**。

### 1. 采购订单导出：明细 9 → 7 列，表头 12 → 11 格

`purchase-order-export.service.ts` 一个文件：

- 明细删「供应商」「交货日期」→ 序号 / 产品名称 / 规格型号 / 单位 / 含税单价 / 数量 / 含税总价；
  表头网格删「采购单号：」→ 实填 11 格（第 4 行只剩「付款方式 / 电话」，右端一格留空，不重排位置）。
- 两个字段是**整条链路**删的：`PurchaseOrderDocumentLine` 的两个字段、`ExportItem.supplier`、
  明细 include 里的逐行供应商都删了（留着没人读的字段，下一个人会以为那一列还在）。
- **小计公式的列由 `COLUMNS` 推出来**（含税总价第 7 列 = G），不再写死 `SUM(H…:H…)`：
  写死的 H 会指向空列，纸面小计变 0 且不会有任何报错。
- `LAST_COLUMN` 拆成两件事：`SHEET_LAST_COLUMN = "I"`（标题/地址/条款/备注/签署栏这些整行合并的右边界，
  表头网格天然占 9 列）与明细表自己的 `COLUMNS.length`；H/I 补 `HEADER_GRID_TAIL_WIDTHS = [12, 14]`
  给值格宽度。共用一个常量的话，表头第三组的值格会落到列定义之外。
- **采购单号仍留在 document 上**，只用于**工作表名**（批量导出一簿多单要认单，表名不打印）——
  这条判断写进了字段注释，测试里钉了「纸面任何一格都不出现它」。

### 2. BOM 建表页：物料下拉改成可搜索

`components/bom/bom-workbench.tsx` 的物料单元格从 Radix `Select` 换成全站既有的 `SearchableSelect`
（采购 / 生产 / 采购单三个入口共用一个组件，一处生效三处）。物料池本来就是**全量**下发的
（`GET /materials` 无分页），所以前端过滤即可，没动接口。

配套两处：

- `ui/searchable-select.tsx` 新增可选 `title`（挂在**触发器**上：省略号发生在触发器里，挂根 div
  会在展开后弹出与搜索框无关的气泡）。物料列 20% 宽、名字长，被省略的字必须有地方 hover。
- CSS 那两条省略号规则**一行没改**（两种下拉的触发器都带 `.ui-select-trigger` 类），
  只补了一条 `.bom-col-material .ui-searchable-select-popover { min-width: 320px }`：
  弹层默认跟列同宽 ≈236px，几十字的物料名会折三行。
