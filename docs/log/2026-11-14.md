| # | 决定 | 理由 |
|---|---|---|
| 1 | 放 `tools/` 不放 `apps/` | 放 apps 会改根 `package-lock.json`，进而影响生产 `npm ci`；实测放 tools 后 lockfile 零改动 |
| 2 | 分诊不调模型，先用规则 | 分诊判错最贵，必须能固定语料回归；模型兜底留到规则不够时 |

### 测试逼出的两个真实缺陷

这两条值得单独记，因为都不是我先想到的，是断言逼出来的：

1. **症状被误当期望。** 「1.5MB 的文件提示读取失败」原本被判为"已说清目标"直接开工。
   但这句话只说明哪里坏了，没说要变成什么样 —— Agent 会自己猜目标。
   修正：症状词只用于区分缺陷/需求，不参与期望判定。现在会追问「你希望它变成什么样」。

2. **停止不拦追问。** 原实现停止只拦入队，于是停止后来的新消息还会被追问一句，
   用户会觉得机器人没听懂停止。修正：停止判定移到分诊之前。

### 踩的坑

- `tsconfig.json` 不能继承仓库根共享配置：本目录会被整体复制到服务器独立运行，
  base 不存在会让 tsc 退回默认值并产生一串假错。已改自包含。
- 第一版漏了 `devDependencies`，服务器上 `npx tsc` 去下载了无关的 `tsc@2.0.4`，
  类型检查看起来跑了其实没跑。
- **Windows 上 `Set-Content -Encoding utf8` 毁掉了中文源码**，一个文件被写成 ANSI 重读后中文全乱。
  修复方式是重写。此后所有源码写入统一用 `[IO.File]::WriteAllText` + `UTF8Encoding($false)`。

### 飞书 "app not online" 的根因与解决

飞书事件台报 `errorInfo: "app not online"`、`address: ""`、`httpCode: 0`。
根因不是配置错，是**当时没有任何客户端连着长连接**。建连后事件立刻恢复。

过程中发现凭据在 `.env` 里用的是 `APPID` / `APP_SECRET` 两个键，不是 `FEISHU_APP_ID`。

探针结果：机器人「迪礼顾问」，`open_id=ou_a6b196a246b21fde14a4368c550666a9`，`activate_status=2`。

**实证：用户 17:37 在群里发的「你好」被旧版机器人收到了**，日志有记录。
所以长连接从一开始就是通的。

### 三个真实缺陷（都是实测逼出来的）

1. **超时留孤儿进程（严重）**：`kill(-pid)` 杀不到被 `setsid` 的孙进程，
   `npm run typecheck` 与 `tsc` 残留 36 分钟，把下一次 run 也拖死。
   修法：给子进程注入 `DILEE_RUN_ID`，超时时扫 `/proc/*/environ` 按标记清杀；
   启动时再 `sweepStaleRuns()` 清场。

2. **prompt 诱导全量测试（严重）**：写「必须跑 typecheck 与相关单测」，
   Agent 就并发跑 `test:unit:web`（84 个 vitest 文件），2 核上 17 分钟没完。
   修法：显式点名禁止全量命令，给 8 分钟预算，说明是 2 核机器。
   实测 typecheck 单跑 186 秒，预算足够。

3. **分诊过严（中等）**：要求「模块+期望+入口」三项齐全，
   把「新建文件 X，内容 Y」这种完全可执行的任务判成含糊。
   修法：只有「期望」阻塞；动作动词（新建/删除/改成/实现…）也算期望信号。
