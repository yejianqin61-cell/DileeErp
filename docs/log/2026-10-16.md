## 排查：原料入库单过账了（入库状态=入库成功），但库存里看不到那个物料

用户原话：

> 现在排查一下，原料入库单批准之后，入库状态也显示入库成功了，备注显示质检通过自动生成入库草稿。但是库存里没有看到相应的物料

先问了一句确认现象（因为这决定了是"取数失败"还是"那一行没了"），用户选：
**「整张表都是空的（其他物料也看不到库存）」**。

### 1. 根因：库存汇总的取数请求被 nginx 以 414 打回（不是库存没写进去）

| 环节 | 事实 |
| --- | --- |
| 页面取数 | `warehouse/raw-material-storage` 把**全部物料 id** 拼进查询串（每个 UUID 37 字节） |
| 生产机链路 | 浏览器 → nginx（`.deploy-run-118/nginx-dilee.conf` 的 `location /api/`）→ PM2 `dilee-api` |
| nginx 限制 | 那份配置没放宽请求头，走默认 `large_client_header_buffers 4 8k`，**一条请求行最多 8192 字节** |
| 越线点 | 物料 **≈219 个**；300 个物料时实测请求行 **11165 字节**（本机测试复现） |
| 结果 | nginx 回 414，请求**到不了 API**。库存事实一直在库里，是**读**不到 |

三条症状逐条对上：① 入库单来自短 URL 的 `GET /raw-material-inbounds`，所以照常显示「入库成功」；
② 余额请求失败后 `balances` 留空 → 库存汇总**整表空**（空态还写着「暂无原料库存」，把故障说成没库存）；
③ 只影响这一页 —— 另外两处调同一接口的地方不带 `material_ids`。

### 2. 修法

- **不再拼 `material_ids`**：接口不给筛选时返回全部原料余额，而这一页本来就要全部物料
  （每个物料补一行 0），所以是**同一个结果集、没有 URL 上限**（与 `warehouse/page.tsx`、
  `material-slip-editor.tsx` 一致）。8k 算式写在 `RAW_MATERIAL_BALANCES_PATH` 的注释里。
- **取数失败不再冒充「没有库存」**：余额那次请求单独 try/catch（`balanceError`），
  失败时那张卡不渲染表、直接给原因 + 重试；「当前原料汇总条目：0」也不再报。
  入库单那张表保持可用（入库是否生效的唯一凭证，恰恰是那时最需要能看的）。

### 3. 排查时顺带发现的第二个成因（同一个症状，不同成因，已修）

`ensureUnusedAndDelete` 的引用检查漏了「数量所在的那几处」：物料只数 `bomItem`，
单位只数四张"主数据与工艺"表。于是**已经收过货、账上有库存**的物料/单位能被软删 ——
`GET /materials` 与库存余额查询（要求 `material.deletedAt = null` 且 `unit.deletedAt = null`）
同时把它挡掉：**库存事实还在，库存汇总里那一行静默消失**，而入库单列表照旧显示它。

补上：物料 + `purchaseOrderItem / rawMaterialInbound / rawMaterialMovementLine / inventoryFact / stocktakeLine`；
单位 + `purchaseOrderItem / rawMaterialInbound / rawMaterialMovementLine / inventoryFact`。
没有新错误码（沿用「基础资料已被业务引用，只能停用」）、没有迁移。

## 修：备用金付款（= 资金搬运）的凭证会计科目 + 旧凭证一并纠正

用户原话：

> 财务部分,凭证管理,如果该笔应付选择的是备用金付款,该笔凭证的会计科目没法正常显示.我需要其正常显示.;
> 并排查,凭证这边,是否能够正常显示所有相应的会计科目.

问了三轮才动手（现象决定改哪一侧、口径决定改不改账），用户选：
凭证纸里那笔是 **借 应付账款 / 贷 库存现金**；期望 **借 库存现金（备用金）/ 贷 银行存款**
（「从银行取现到备用金」）；确认时不该出现应付账款；**旧的那些也一起纠正过来**。

### 1. 根因

「备用金付款」是一条其他应付，它的「会计科目」被选成了**资金科目** `库存现金（备用金）`
—— 表达的是「把钱从银行搬进备用金柜」，不是欠款。而代码一律按应付两步走：
确认挂账（借 库存现金（备用金）/ **贷 应付账款**）→ 付款销账（**借 应付账款**/ 贷 资金侧）。
用户点开的就是后一张。外加 `fundLineFor` 只看结算方式文本里有没有「现金」二字，
「备用金现金」这种文本把**去向**当成**来源**，于是净效果是「借 库存现金（备用金）/ 贷 库存现金」。

### 2. 口径与改动

- **资金科目的其他应付 = 资金搬运，不挂账**：`createAccrual` 里判定（三条确认入口自动同一口径），
  跳过时写 `voucher.accrual_skipped` 审计。
- **未挂账的付款，借方取条目自己的科目**（人工选的 > 条目 > 来源候选链）：备用金付款于是
  一张凭证记完 —— 借 库存现金（备用金）/贷 银行存款。已挂账的付款借方仍是应付账款；
  此时付款单上人工选的科目改走「收支类目」（原来会顶掉借方，等于把挂过的账再记一遍成本）。
- **`fundLineFor` 第 0 条判定**：业务科目本身就是现金科目 → 资金侧只能是银行存款。
- **三大报表**：`库存现金（备用金）` 算资金科目（取现 = 内部划转，不进现金流量表；
  用备用金报销费用时才作为资金侧进表）。**有意不**对「银行存款」用前缀匹配 ——
  `美金转入` 那类历史数据把银行账户名当业务科目，前缀匹配会把客户货款判成内部划转、整笔消失。
- **旧凭证纠正**（用户要求）：`GET/POST /finance/vouchers/cash-transfer-repair` + 凭证管理页按钮。
  预览先报数（草稿删几张 / 已过账红冲几张 / 重算几张 + 逐条清单），执行时：草稿直接改/删、
  已过账的先红冲再重开成草稿、流水主科目改成条目科目；**混着非资金搬运的流水不动，只点名**。
- **红字凭证一并撤掉**（`dropReversalsOf`）：挂账凭证与付款凭证纠正后，它们那条红冲记录必须撤 ——
  报表只认 `posted`，原凭证 `reversed` 不进表，红字留着就是一笔**悬空的反向金额**（比不改还糟）。
- **顺带修的必然缺陷**：`vouchers(source_type, source_id)` 是**全量**唯一索引（软删行照样占键），
  「删掉草稿凭证 → 再生成」原来会撞唯一键报数据库错误。两条生成路径 + 红冲改走 `createOrReviveVoucher`
  （**原地复活**那一行）。纠正之后这条路径必然被走到（删掉草稿挂账凭证 → 回退应付 → 再确认）。
- **纠正已过账的付款凭证时，红字凭证一并软删**：它是「旧内容」的对冲件，而旧内容马上被重写成新口径；
  报表只认 `posted`，原凭证已 `reversed` 不进表，红字还留着就会剩下一笔悬空的反向金额。

### 3. 排查中发现、本轮**没有**改的一条（留档）

三大报表只取 `status = "posted"` 的凭证，而红冲把原凭证置 `reversed`、另开一张 `posted` 的反向凭证
—— 按现有取数，「原凭证 + 红字凭证」在表里剩下的是**反向那一笔**（不是净零），
而 `finance-three-statements-2026-09-24.md` 写的是「净额正确」。这条影响**所有**红冲，不只是备用金，
要不要动请用户定。本轮的纠正动作因此把红字凭证一并软删，不留悬空的反向金额。

### 4. 门禁（真跑）

|---|---|
| `npm test`（typecheck + deploy 脚本 + API + web lib + web 组件） | **exit 0**（冻结工作树后跑的最终一遍） |
| API 全量单测 | **2478/2478**（本轮 +13：域 3 / 挂账跳过 1 / 付款借方 1 / 现金流量表 1 / 纠正 6 / 复活 1） |
| web 组件测试（65 文件） | **1138/1138**（本轮 +3：凭证纠正 2 / 应付确认文案 1） |
| web lib 测试 | **344/344** |
| deploy 脚本测试 | **32/32** |
| `tsc --noEmit`（api / web） | 双绿 |

**先红后绿**：三条新域用例在改 `fundLineFor` 前红（贷方是「库存现金」而不是「银行存款」）；
`isFundSubject` 那条在改前缀前红（取现被算成非资金凭证）；纠正那组在加接口前红；
「删掉草稿再生成」那条在加复活路径前红（撞唯一键）。
