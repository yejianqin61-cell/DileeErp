# 2026-11-07

## 用户反馈（两条）

> 1.「采购板块，领料单的导出件也要有订单号」
> 2.「成品提交质检入库，成品质检页面要显示所有待质检列表。」

设计文档：[material-slip-order-no-and-finished-goods-pending-qc-2026-11-07.md](../design/material-slip-order-no-and-finished-goods-pending-qc-2026-11-07.md)。

## 排查与落点

### 需求 1：全站只有一处「领料单导出」

- 入口 `GET /production/reports/material-issue.xlsx?movement_id=…`（批量 `material-slips.xlsx`），版式在
  `MaterialSlipExportService`；纸头是「标题 + 三行 × 4 组『标签 + 填写格』」。
- 采购单导出件**早就印订单号**（`purchase-order-export.service.ts` 的「订单号：销售单号（货号）」），
  只有领料单/补料单的纸头缺这一格 —— 用户说的「采购板块」是采购/原料这一片（领料单入口在
  【仓库 → 原料流转】与【生产单详情】，采购/仓库人员共用）。
- 数据源现成：`MaterialIssueDocument.orderNo` / `MaterialReplenishmentDocument.orderNo` 本来就组装好了
  （`productionOrder.orderNo`），只是排版没用它 —— 不需要新查询，不碰数据库。

### 需求 2：成品质检页只有「按订单号查询」，没有跨订单工作队列

- `/qc/finished-goods` 原来必须先输入/点一个订单号才能看到要检什么；页面底部只有一句
  「全部订单概览：请选择订单号进入二级详情」的占位说明。跨订单的待检工作量在页面上完全看不见。
- 数据其实早就拉全了：`load()` 同时取 `GET /finished-goods/inspection-submissions`（全量、带 qcRecords）
  与 `GET /finished-goods/qc/sources`；缺的只是把「已提交待检」的行渲染出来。

## 决策

| # | 决策 | 理由 |
|---|------|------|
| D1 | 订单号落在模板**预留空格**：领料单第 3 行第 4 组（`G5` 标签、`H5:J5` 合并写值）；补料单第 3 行第 3 组（`E7/F7`），补料原因仍在第 4 组 | 样例 xlsx 第 3 行第 4 组本来就是空的；不动任何已有字段位置，纸样不用重排 |
| D2 | 导出 xlsx 与浏览器打印件**同位置同顺序**补这一组 | 纸与 Excel 是同一份单据数据；两边格子对不上，仓库与车间对料就各说各话（2026-10-29 已吃过一次） |
| D3 | 补料单同步补订单号 | 与领料单同一入口/同一纸头结构，只补领料单会让同一页两张单据的纸头不一致 |
| D4 | 「待质检」行集 = `submitted`（待质检）+ `inspecting`（质检中），排除 `draft` / `qc_completed` / `cancelled` | 用户说的是「成品提交质检入库」之后要检的队列；草稿还没提交、已检完的进了「质检合格待入库」 |
| D5 | 排序 = 送检日期升序、同日送检单号升序 | 工作队列要「先送检先检」，不按「谁最后改过」——否则刚检完一张，整张表的行就跳位 |
| D6 | 已检/待检数量在**服务端**算：`inspectedQuantity` = active QC 记录合计；`pendingQuantity` = max(送检 − 已检, 0) | 累计口径只允许一份实现（`createQcRecord` / `correctQc` 的上限校验都是 active 合计）；前端再算就会「列表说还能检 2、点进去说超量」。`corrected` 记录不能重复计入 |
| D7 | 待质检列表放页面**第一个**内容块，替换底部「全部订单概览」占位 | 质检员打开页面第一眼就是待办；占位块唯一用途（告诉用户按订单号查）已被新块说明与「按订单号查询」覆盖 |
| D8 | 行内「录入质检」直接带入该送检批次；双击行进该订单的质检详情 | 复用现有 `openQc(orderNo, { submission_id })` 与 `loadOrder()`，不新开一套弹窗/详情 |

# 同一日第二轮：会计科目「类目」可增删改查

## 用户需求

> 「针对财务模块的会计科目，现在要允许用户自行对会计科目的类目进行增删改查，现在是否有前后端支持？如果没有，加上去」

设计：[accounting-subject-category-crud-2026-11-07.md](../design/accounting-subject-category-crud-2026-11-07.md)；
任务与交付清单：[docs/task/2026-11-07-accounting-subject-category/README.md](../task/2026-11-07-accounting-subject-category/README.md)。

## 现状盘点：科目有 CRUD，类目没有

- 科目本身前后端都能增删改停用：`GET/POST/PATCH/DELETE /finance/accounting-subjects`（写仅管理员）+ 会计科目页
  （`/finance/cash-flow?tab=subjects`）。
- **类目没有**：`accounting_subjects.category` 只是个 `VARCHAR(30)`；`GET /finance/accounting-subjects/categories`
  返回「5 个内置类目 ∪ 库里出现过的取值」的**只读派生**字符串数组；前端分类只是下拉，不能新增、不能改名、
  不能删除（新增科目时也只能选已有类目）。所以「增删改」都没有，「查」也只是派生清单 —— 需要补。

## 决策

| # | 决策 | 理由 |
|---|------|------|
| D1 | 类目升成一等实体：新表 `accounting_subject_categories`（name 唯一 / sort_order / is_system / 审计列） | 改名要原子级联、删除要能判断「还有没有科目」、新增要留审计 —— `SELECT DISTINCT` 给不了这三件事 |
| D2 | `accounting_subjects.category` **保留字符串**，不改外键 | 三大报表与凭证按类目名硬编码匹配科目（会计制度口径），改外键要在运行时翻译名字；改名由服务层同一事务级联 UPDATE |
| D3 | 内置五类（资产/负债/成本/所有者权益/损益）**只读**：不许改名、不许删除 | `finance-three-statements.ts` 与 `voucher.service.ts` 按这五个名字取数，改名会让报表静默变空表（不报错、最难查） |
| D4 | 改名：同一 `$transaction` 里改类目行 + `updateMany` 全部科目（**不加 `deleted_at` 过滤**） | 科目唯一键 `@@unique([category, name])` 不认软删；只改未删的会在旧名下留一颗未来撞唯一索引的地雷 |
| D5 | 删除：有未软删科目（含停用）422 并写明还有几个；空类目**物理删除** | 停用科目仍在列表与历史流水上；物理删除让「删掉写错的类目 → 用同名重建」可行（软删 + 唯一索引会让同名建不回来）。被使用的类目直接拒删，与宪法《Configurable Business Categories》一致 |
| D6 | 科目写入口校验类目必须存在（`ACCOUNTING_SUBJECT_CATEGORY_NOT_FOUND`） | 否则任何客户端都能写进一个没人看得见的分类，类目清单与筛选下拉立刻不可信 |
| D7 | 旧数据/绕过接口写入的「历史类目」合成 `id:null` 行返回：筛选与编辑科目下拉可见，**新增科目下拉不可见**，无改名/删除按钮 | 历史类目没有实体，新增时选它必被 D6 拦成 422 —— 不给用户一个注定失败的选项；编辑时不换分类仍要能改其它字段 |
| D8 | 列表顺序：内置五类按会计制度顺序 → 自建按 sortOrder/名称 → 历史类目最后；计数由库侧 `groupBy` 聚合（含停用，另给启用数） | 与「分类小计必须连续」的既有口径一致；不把科目明细搬到应用层 |
| D9 | 兼容接口 `GET /finance/accounting-subjects/categories` 保留（`string[]`），改读类目表 ∪ 历史取值 | 老前端/第三方脚本不用改；地址与形状不变 |

> 「通览当前项目，你是本项目的全栈工程师。针对财务板块，你给我现在仔细梳理一下所有业务流程，业务规则。当前，用户反馈财务的应付，收支流水，凭证这条路上，会计科目，借方贷方的记录都不令人满意，应该是有一些业务流程上的错误」

## 核心结论（四点）

1. **借贷方向没有写反，凭证也没有算错**：21 张未删除凭证全部 2 行、借贷恒等；自动路径的借/贷在代码里是对的（挂账：借业务科目/贷应付账款；付款：借应付账款/贷银行存款）。
2. **但库里的科目/方向偏差 100% 与手工改单相关**：12 张挂账凭证中 6 张贷方不是「应付账款」，恰好就是 6 张有 `voucher.update` 记录的；未改过的 6 张贷方全对。凭证相关审计 183 次中 182 次由 `caiwu` 一人完成，审计只记 `{line_edited:true}`，无改前/改后科目。
3. **流程确实有错，且是会让账错的错**：草稿挂账凭证被当「已挂账」（P0-1）、收付款凭证按单据全额而非核销额（P0-2）、四套状态机互不联动（P0-3）、确认与挂账跨事务且红冲后不可补开（P0-4）、确认弹窗选的科目不落库（P0-5）、自动凭证可任意手改无护栏（P0-6）。
4. **报表不可信不是算错，是「两套来源 + 文本快照」**：三大报表只认已过账凭证、收支报表读流水、期初绕过凭证直改、凭证科目是「分类/名称」文本（生产库 23.5% 的行已与主数据失配）。

生产库关键数字：应付 183 条 **100% `source_type=other`**（采购入库→应付链路从未跑通）；未删除 105 条应付仅 2 条有 posted 挂账凭证，57 条已付中 55 条没有；总账 posted 仅 5 张、借贷各 14,778.20，**其中 0 行涉及「应付账款」**，而应付台账 86,188.67；收支流水 164/166（98.8%）已红冲；已过账付款 43 笔 0 张 posted 凭证。
