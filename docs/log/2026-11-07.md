# 2026-11-07

## 用户反馈（两条）

> 1.「采购板块，领料单的导出件也要有订单号」
> 2.「成品提交质检入库，成品质检页面要显示所有待质检列表。」

设计文档：[material-slip-order-no-and-finished-goods-pending-qc-2026-11-07.md](../design/material-slip-order-no-and-finished-goods-pending-qc-2026-11-07.md)。

## 排查与落点

### 需求 1：全站只有一处「领料单导出」

- 入口 `GET /production/reports/material-issue.xlsx?movement_id=…`（批量 `material-slips.xlsx`），版式在
  `MaterialSlipExportService`；纸头是「标题 + 三行 × 4 组『标签 + 填写格』」。
- 采购单导出件**早就印订单号**（`purchase-order-export.service.ts` 的「订单号：销售单号（货号）」），
  只有领料单/补料单的纸头缺这一格 —— 用户说的「采购板块」是采购/原料这一片（领料单入口在
  【仓库 → 原料流转】与【生产单详情】，采购/仓库人员共用）。
- 数据源现成：`MaterialIssueDocument.orderNo` / `MaterialReplenishmentDocument.orderNo` 本来就组装好了
  （`productionOrder.orderNo`），只是排版没用它 —— 不需要新查询，不碰数据库。

### 需求 2：成品质检页只有「按订单号查询」，没有跨订单工作队列

- `/qc/finished-goods` 原来必须先输入/点一个订单号才能看到要检什么；页面底部只有一句
  「全部订单概览：请选择订单号进入二级详情」的占位说明。跨订单的待检工作量在页面上完全看不见。
- 数据其实早就拉全了：`load()` 同时取 `GET /finished-goods/inspection-submissions`（全量、带 qcRecords）
  与 `GET /finished-goods/qc/sources`；缺的只是把「已提交待检」的行渲染出来。

## 决策

| # | 决策 | 理由 |
|---|------|------|
| D1 | 订单号落在模板**预留空格**：领料单第 3 行第 4 组（`G5` 标签、`H5:J5` 合并写值）；补料单第 3 行第 3 组（`E7/F7`），补料原因仍在第 4 组 | 样例 xlsx 第 3 行第 4 组本来就是空的；不动任何已有字段位置，纸样不用重排 |
| D2 | 导出 xlsx 与浏览器打印件**同位置同顺序**补这一组 | 纸与 Excel 是同一份单据数据；两边格子对不上，仓库与车间对料就各说各话（2026-10-29 已吃过一次） |
| D3 | 补料单同步补订单号 | 与领料单同一入口/同一纸头结构，只补领料单会让同一页两张单据的纸头不一致 |
| D4 | 「待质检」行集 = `submitted`（待质检）+ `inspecting`（质检中），排除 `draft` / `qc_completed` / `cancelled` | 用户说的是「成品提交质检入库」之后要检的队列；草稿还没提交、已检完的进了「质检合格待入库」 |
| D5 | 排序 = 送检日期升序、同日送检单号升序 | 工作队列要「先送检先检」，不按「谁最后改过」——否则刚检完一张，整张表的行就跳位 |
| D6 | 已检/待检数量在**服务端**算：`inspectedQuantity` = active QC 记录合计；`pendingQuantity` = max(送检 − 已检, 0) | 累计口径只允许一份实现（`createQcRecord` / `correctQc` 的上限校验都是 active 合计）；前端再算就会「列表说还能检 2、点进去说超量」。`corrected` 记录不能重复计入 |
| D7 | 待质检列表放页面**第一个**内容块，替换底部「全部订单概览」占位 | 质检员打开页面第一眼就是待办；占位块唯一用途（告诉用户按订单号查）已被新块说明与「按订单号查询」覆盖 |
| D8 | 行内「录入质检」直接带入该送检批次；双击行进该订单的质检详情 | 复用现有 `openQc(orderNo, { submission_id })` 与 `loadOrder()`，不新开一套弹窗/详情 |

## 实现

### API（`apps/api/src/modules/production/`）

- **`material-slip-export.service.ts`**
  - 领料单 `addSheet`：表头第 3 行的 `null` 换成 `["订单号：", document.orderNo]`（`G5` 标签、`H5:J5` 合并）；
  - 补料单 `addReplenishmentSheet`：第 3 行第 3 组换成 `["订单号：", document.orderNo]`（`E7/F7`），补料原因留在 `G7/H7`；
  - 单张与批量导出共用这两个方法，一处改动两边生效；明细列/小计/标题/纸张方向未动。
- **`finished-goods-qc.service.ts`**：`listSubmissions()` 每行新增 `inspectedQuantity` / `pendingQuantity`
  （字符串十进制，只加字段不改旧字段；复用 include 里已有的 `qcRecords`，不额外查库）。

### Web（`apps/web/`）

- **`lib/material-slip-print.ts`**：`materialSlipHeadRows` 同步补订单号 —— 领料单第 3 行第 4 组、
  补料单第 3 行第 3 组（补料原因不挪）；打印组件 `material-slip-print-sheet.tsx` 未改（它渲染 headRows）。
- **`components/qc/finished-goods-qc-panel.tsx`**
  - 新增「待质检（全部订单）」DataTable（面板第一个内容块，替换底部占位）：标题 + 「共 N 张」+ 口径说明 + 空态指引；
  - T24 十列（送检单 / 订单号 / 生产单 / 成品 / 来源 / 送检数量 / 已检数量 / 待检数量 / 状态 / 操作），
    声明宽度合计 **84%**，另 16% 给 `auditColumns()` 的创建人/最后修改人；长文本列一律 `accessorFn`
    返回屏幕上那串字，DataTable 自动挂 `title`（省略号 hover 看全文）；
  - 状态中文：`submitted → 待质检`、`inspecting → 质检中`；已检/待检直接渲染服务端字段（缺失才 `-`），前端不重算；
  - 行内「录入质检」→ `openQc(orderNo, { submission_id })` 预选该批次；双击行 → `loadOrder(orderNo)`；
  - 新增 testid：`finished-goods-qc-pending` / `-pending-count` / `-order-detail` / `-choose-order`
    （顶部与行内同名「录入质检」，给测试一个稳定定位）。

  字段位置未动）；采购订单样例重生成后与 HEAD 逐格 0 差异，已恢复、不留无关二进制 diff。

## 没做 / 遗留

- **未连真实 PostgreSQL**：`listSubmissions` 用假 Prisma 验证（改动只是在返回前读 include 里已有的
  `qcRecords` 求和，Prisma include 语义未变）；待质检列表的服务端字段建议上线前在真库抽一张送检单核对一次。
- 待质检表不做「待送检」（来源里可送检但还没建送检单）的跨订单列表：那是另一个工作队列，用户这轮说的是
  「提交质检之后」的待检列表。
- 列表不显示来源通知单号/批次：送检单 DTO 只有 `sourceId`（UUID）；要看通知号/批次，双击进订单详情的
  「成品来源」表。真需要再加字段，不在这一轮硬塞。
- 不做待质检的批量操作（批量录入/批量判定）：一次质检的数量配平必须逐单核对。
- 订单详情「送检记录」状态列仍是英文原值（既有 KNOWN_DEFECT，`finished-goods-qc-panel.test.tsx` 里有注释）：
  本轮只要求新待质检表用中文状态词，没有顺带改既有缺陷。
- 未 commit、未部署（按约定由用户提交）。
