# 2026-09-24

## 财务三大报表：先出方案（模板解读 + 分期；后续小节记录落地）

财务交付 `example/财务/财务三大报表（标准格式）(2).xlsx`（财政部一般企业格式 2019：
资产负债表 A1:H41 含勾稽核对行 / 利润表 A1:D27 / 现金流量表 A1:D41 / 填表说明），要求「需要财务三大报表」。

**看了模板 + 盘了系统之后，结论是不能直接套**，两条结构性前提不成立：

1. **凭证只能由收支流水生成**（`POST /finance/vouchers/from-cash-flow/:entryId`，没有「手工新增凭证」入口）
   → 折旧、摊销、计提工资、结转成本这类**非现金分录在系统里没有落点**；
2. **确认即收付**（确认应收 = 借银行存款/贷主营业务收入，见 `receivable.service.ts:149`）
   → 应收账款、应付账款永远是 0，资产侧只剩货币资金。

现在硬算，得到的是一张「只有货币资金 + 未分配利润」、形式上还能勾稽平衡（G41 显示「✓ 平衡」）的空心表
—— 平衡不等于完整，所以这一期没有动手实现，而是把**方案 + 科目→报表行映射初稿 + 缺口清单**交给财务，
连同三个必须她拍板的口径（成本类科目归属 / 外币是否折算 / 退税口径）与一个大前提
（要不要补分录层、把「确认即记账」改成「挂账 → 销账」两步）。

设计文档：`docs/design/finance-three-statements-2026-09-24.md`（含按模板行次列出的四张映射表与分期方案）。

### 随后落地：口径内核（映射 + 取数 + 公式 + 守卫）

方案不是一堆表格就完事 —— 把「科目 → 报表行」直接写成**可执行、可单测**的代码，才不会在实现时走样：

- `apps/api/src/modules/finance/finance-three-statements.ts`：四张表的行定义（模板行次 + 公式
  `sumOf`/`minusRows` + 现金流量行的 `flow: in/out`）、余额与发生额聚合（`sumVoucherLines`）、
  `buildBalanceSheet` / `buildIncomeStatement` / `buildCashFlowStatement`、以及**缺口上报**
  （未归位科目、认不出落行的对方科目、非现金凭证、内部划转张数）；
- `apps/api/src/modules/finance/money.ts`：金额运算抽出成一份实现（`toUnits` / `formatUnits` /
  `toPositiveUnits`），`finance-slip.ts` 的 `parseAmount`/`formatAmount` 变成它的两个薄包装 ——
  三处（单子、凭证、报表）各写一份点分转整数，迟早出现「单子上 149.5、报表上 149.49999999」；
- 16 条单测（`finance-three-statements.test.cjs`）。其中最要紧的一条是**覆盖度守卫**：
  科目表 122 条逐条必须有归属、同一张表同一方向不能被两行同时认领、声明了 `match` 的行不能一条都
  匹配不到，而且**守卫本身也被测**（喂一份故意写错的映射必须被抓住）。

实现时踩到/查出来的四个坑（都写进了注释与测试）：

1. **「行次」不是「Excel 行号」**：模板里「流动资产合计」（行次 14）的公式是 `SUM(C5:C17)`
   = 行次 1..13。按 Excel 行号写会漏掉前四项，而**勾稽照样平**（漏的是两侧各自的行，差额被未分配利润吸收）。
2. **资金分录的科目键是裸名**（`银行存款`），业务分录是 `分类/名称`（`voucher.domain.ts` vs
   `voucher.service.ts`）—— 只认一种，「货币资金」整行为空，看起来像「系统里没有银行流水」。
3. **现金流量表必须看方向**：借短期借款是「取得借款收到的现金」、还它是「偿还债务支付的现金」，
   科目是同一个。只看科目不看方向，还款会被算成借款（金额方向全反、小计净额一路错、勾稽照样平）。
4. **备抵科目不要写成「减项」**：累计折旧按「借 − 贷」算出来天然是负数，直接相加即净额；
   写成「减：累计折旧」在财务按准则（贷累计折旧）记账时会把数**加成正的**。

另外发现一处数据缺口（已进设计文档 §8.5）：银行账户档案有期初余额，其它科目没有。
只把银行期初加进货币资金、不给对应的权益/负债期初，资产负债表会一直差一个「期初余额」的差额 ——
内核把这笔差额显式返回并要求写进表尾，不是算错。

**未接的部分**（等口径拍板）：取数服务（读库）、预览/导出路由、页面页签。

  摆一个永远无效的开关只会让人以为选了它数字会变。页签**追加在最后**，不动默认页签

**两处口径在这轮定下来**（都写进代码注释与文档）：

1. **「上期金额」**：整月期间取**上一个自然月**（8 月对 7 月，天数不同也对）；非整月期间取紧邻之前**等长**的一段。
   一律按等长天数会让 9 月（30 天）对到 8/2–8/31、3 月（31 天）对到 1/29–2/28 —— 财务对不上「上月」这个数。
2. **期初余额只在一侧**：银行档案有期初、其它科目没有。取数只往货币资金加期初，勾稽差额**恰好等于期初余额**，

   免得以后有人把它当成报表 bug 去改公式。

### 二期 ①：手工新增凭证（折旧 / 摊销 / 计提 / 结转终于能录了）

**为什么要动库结构**：凭证原先只能由收支流水生成，`vouchers.source_id` 是 `NOT NULL` ——
而折旧、摊销、工资计提、结转成本这些**非现金分录根本没有流水**（钱没动），于是它们在系统里
无处可录，三大报表的固定资产 / 累计折旧 / 应付职工薪酬 / 库存商品等行永远填不上
（这正是设计文档 §2 的事实②）。

**迁移** `20260924100000_voucher_manual_source`：只做一件事 ——
`ALTER TABLE "vouchers" ALTER COLUMN "source_id" DROP NOT NULL;`

为什么不「填一个随机 UUID」蒙过去：`source_id` 是一个**引用**（列表页靠它取来源流水号、
红冲凭证靠它指向被红冲的那张）。填一个编造的 id 会让这一列在语义上说谎，以后每一处按来源追溯
都要额外判断「这个 id 是不是真的」。可空是这条事实的诚实写法。
唯一索引 `(source_type, source_id)` **不动**：PostgreSQL 的唯一索引不约束 NULL，
所以多张手工凭证 `(manual, NULL)` 可以共存，而「一条来源一张凭证」（生成接口的幂等根）对流水来源依然成立。
守卫测试 `voucher-manual-source-migration.test.cjs`（4 条）钉住：只放宽 NOT NULL、不改历史数据、
不删列删表、DDL 不碰那个索引、schema 与迁移一致。

**服务与界面**：
- `VoucherService.createManual`：日期（决定会计期间，非法即 422）、币种（默认 CNY，走币种字典校验）、
  至少一借一贷、借贷必须相等、金额必须为正、科目必须有名称（快照 `分类/名称`）、
  资金行引用的银行账户必须存在（`VOUCHER_BANK_NOT_FOUND`，而不是等外键在提交时报数据库错误）；
  编号与流水生成的凭证同一套（`记-YYYYMM-####` 期间内顺延）；落库为**草稿**（核对后再过账）。
  审计 `voucher.create` 里记 `source_type: manual`。
- `POST /finance/vouchers`（集合路由，声明在 `from-cash-flow/:entryId` 之前）。
- 凭证页新增「新建凭证」→ 与「编辑分录」**共用同一个编辑器**的新建态：
  日期与币种在这里填、默认给出一借一贷两条空行、保存走 POST；模板栏在新建态不出现
  （模板接口是 `vouchers/:id/templates`，新建时还没有 id）。
- 顺带修掉两处由「source_id 可空」暴露出来的读侧：`list` 按来源取流水时要滤空值、
  `get` 只在来源 id 存在时才查来源/红冲对方、`regenerate` 对手工凭证显式拒绝（它没有来源可重算）。

**验证**：API 1939（+8：服务 4 + 迁移守卫 4）、web 组件 916（+1 新建凭证用例）、web lib 247、deploy 27、
typecheck 干净。

### 二期 ②：科目期初余额表（让勾稽真正为 0）

银行的期初只有货币资金，其它科目没有 —— 只往资产侧加期初，勾稽就永远差一个期初余额的差额。
`accounting_opening_balances`（建账日 + 科目 + 币种，方向 + 正数金额）让财务录一次全科目期初：

- **整批替换**（`PUT /finance/opening-balances`）：界面上这张表就是「我现在的期初」，没出现的行由服务层软删；
  唯一键 `(as_of_date, subject_key, currency)` 软删后仍占位，所以「删了再加同一科目」走 upsert 恢复而不是新插一条；
- **借贷不平不拦但实时显示差额**（财务可能分批录），科目下拉带搜索（科目表一百二十多条）；
- 取数侧：有期初表时报表 = **建账期初 + 建账日之后**的凭证（建账日之前的已含在期初里，再取一遍就是算两遍）；
  期初里的**资金类部分**要加进现金流量表的「期初现金」（漏了它期初现金会变成 0，期末余额一路跟着错）；
- 迁移 `20260924130000_accounting_opening_balances`（守卫测试 4 条：只新增表、不改历史数据、三元组唯一、schema 一致）。

### 二期 ③：期末汇率表 + 外币折算（外币的钱终于能折成人民币）

凭证上有 `currency` 却没有汇率，而三大报表是人民币报表。新增 `exchange_rates`
（期间 `YYYY-MM` + 币种 + `1 外币 = rate 人民币`，精度 `DECIMAL(18,8)`）：

- **按期间整批替换**（`PUT /finance/exchange-rates`）：财务维护的心智是「9 月的汇率」，
  月底是 28/30/31 号不该影响取数；本币 `CNY` 不录（对自身恒为 1，录进来只会多一个「报表用哪条」的歧义）；
- **折算点在分录层**：非本币凭证**逐行**乘汇率折成人民币后才进内核 —— 行匹配、勾稽、公式全都不用知道汇率的存在；
  本币报表取全部币种；报表币种换成外币时不折算（「1 外币 = X 人民币」的方向反了），退回「不跨币种相加 + 表尾说明」；
- **三个时点各用自己那个月的汇率**：期末存量与本期流量用期末月、年初存量用上年 12 月、期初现金与上期流量用上期期末月；
  某月没维护就**回退**到「不晚于它的最近一个月」并在表尾写明用的是哪一期（拿未来汇率折过去的余额是错的；
  「没汇率就不折算」又会静默丢钱 —— 回退 + 写明是既不丢数也不出假数的做法）；
- **汇率变动对现金的影响（行次 32）** = 期末资金（按期末汇率）− 期初资金（按期初汇率）− 本期资金净流量（按期末汇率）。
  由取数层算好传给内核（内核只看凭证，看不到「资金余额折成多少」，硬算会算错）；本币业务下恒为 0；
- **折不了的币种不许静默丢**：一条汇率都没有的币种，其凭证与期初都**不折进本表** —— 钱少了、两侧都少，
  勾稽照样平，这是最难发现的一类错。所以单独进 `gap.unconverted`，表尾点名「哪个币种多少张凭证没折进来，
  请到期末汇率页维护」（这一条有专门的测试钉住）；
- 顺带把取数里两处口径收紧：期初的「建账日之后」改成**按币种各自的建账日**判断（不同币种可以各录各的建账日），
  期间切片也一起按它过滤（否则建账日之前的凭证会在「期初」和「本期流量」里算两遍）；
- 界面：会计科目页新增「期末汇率」面板（期间选择 + 币种/汇率/备注行 + 回退提示），与期初余额同一页 ——
  财务的月度动作就这两件。迁移 `20260924160000_exchange_rates`（守卫测试 4 条）。

### 二期 ④：权责发生制两步（应收侧已落地：确认 = 挂账，收款 = 销账）

方案先写、后动代码（用户 2026-09-24 明确「改动现有确认流程前先出方案并补测试」）：
`docs/design/finance-accrual-two-step-2026-09-24.md`。

**当年的事实**：确认应收一步做两件事 —— 改状态（应收成立）**并**写一条收支流水（钱进银行）。
于是钱还没到就先记了收款；而三大报表取的是凭证，那些流水在「生成凭证」之前又完全不存在。
（用户 2026-09-16 的原话是「一旦确认应收，金额就要进入对应的账户」，所以这不是 bug，是她当时要的口径。）

**这一轮落地（应收链）**：

- `VoucherService.createAccrual()`：挂账凭证 = 借 `应收账款` / 贷 收入类科目，**没有资金分录**、落草稿，
  幂等靠唯一键 `(source_type, source_id)`（同一条应收被两个入口先后确认只挂一张账 —— 挂两遍＝收入翻倍）；
  科目缺失显式 422、0 元往来不挂空账。手工凭证与它共用同一段落库逻辑（分录校验/借贷平衡/期间编号/审计逐字一致）。
- 确认应收的**四条路径**（逐条 / 勾选批量 / 按订单 / 按对账单）全部改为挂账：不再写收支流水；
  响应新增 `accrual_voucher_id(s)`，`cash_flow_entry_ids` 变为空，`bank_missing` 恒为 false
  （挂账与银行无关，却还在提示「没选银行」只会让人以为账没记上）。
- **销账有条件**：收款过账那条现金分录，若这批核销的应收**都挂过账** → 贷 `应收账款`；
  有一条没挂过（历史数据）→ 仍贷收入。历史不动，也不会让「应收账款」变成负数。
- 界面：确认成功的提示改成「已确认并挂账（借应收账款 / 贷收入）；收到钱后在「登记收款」里记现金」。
- 测试：`cashFlowCalls` 在确认用例里被留成**反向护栏** —— 哪天有人把 `recordConfirmation` 加回确认路径，
  用例立刻红。

**还没做**：应付侧仍是「确认即记账」（`supplier-payable.service.ts` 与两个对账入口），
改法与应收完全对称（科目换 `应付账款` / 成本类，销账侧是 `supplier-payment.service.ts`），下一轮做。

### 二期 ④（续）：应付侧对称改造 —— 两条链现在同一口径

- `SupplierPayableService.confirm` / `batchConfirm`、`SupplierPayableReconciliationService.confirmPayables`
  三条确认路径全部改为挂账：借 成本/存货类科目（按来源类型选候选链：原料入库 → 主营业务成本/原材料，
  外加工 → 加工费）/ 贷 `应付账款`；不再写支出流水，响应 `accrual_voucher_id(s)`、`bank_missing` 恒为 false。
- 销账：`SupplierPaymentService.post` 那条现金分录，若这批核销的应付**都挂过账** → 借 `应付账款`；
  有一条没挂过（历史数据）→ 仍借成本/存货。与应收侧用同一个 `accruedSourceIds()`。
- 界面：应付侧三条确认入口的成功提示改成「已确认并挂账（借成本 / 贷应付账款）；付款后在「登记付款」里记现金」。
- 至此**两条链口径一致**：确认 = 挂账（无现金流动）、收付 = 销账（借贷一方必为应收/应付），
  历史数据在两条链上都保持原样。

## 「不能一起付款」：一次勾选拆成多张，而不是报错

**现象**：财务反馈「还是不能实现一起付款，只能算是一起确认了，然后还是一个个的改付款单」。

**根因**：批量确认一直是对的（勾选 N 条 → 一个银行 + 一个科目 → 每条写一条流水）。
坏的是紧接着的出单那一步 —— 跨供应商 / 跨币种时 `payment-slips/draft` 直接 422
（`PAYMENT_SLIP_MULTI_COUNTERPARTY` / `_MULTI_CURRENCY`，提示「请按供应商分批导出」），
于是她只能一家一家重新勾、重新开弹窗。**确认是一个动作，出单变成了 N 个动作**；收款侧一模一样
（`RECEIPT_SLIP_MULTI_*`），「收束收款」也只收束了确认那半步。

**修复**：模板本身就是分组依据（「收款单位 / 开户银行 / 银行账号」各只有一格），所以由系统拆，不让她手工拆。

- `groupSlipEntries()`（纯函数）按「对方单位 + 币种」分组，保持首次出现顺序；
  `draft()` 返回 `FinanceSlip[]`，控制器包成 `{ data: { slips }, meta: { slip_count } }`；
- 每张单子各自算单号 / 附单据张数 / 开户行（**按本组的流水判** —— 拿全批的账户去填会让一张单子
  印上另一家那笔钱走的账户）；`suggestNumber` 加 `offset`，避免同一家拆两张时拿到同一个编号；
- 队列编辑器（`finance-slip-editor.tsx`）：标题带对方单位与币种（`2. 富雨鑫（USD） 合计 70`），
  每张各自保存编辑；**「全部导出」**（`.../batch.xlsx`）渲染成**一个工作簿多工作表**
  （逐张下载会被浏览器拦掉，财务只拿到第一张还不知道丢了几张）；工作表名带序号（同名 ExcelJS 抛错）；
- 队列底部接回确认：`确认这 N 条（付款 / 收款）` → 关队列、按同一批 id 打开原来的批量确认弹窗
  （`batchConfirm(ids?)` 加了可选入参：队列可能是从行内单条打开的，传勾选会按到别的条目上）。

顺带修掉「确认这 N 条（**付款**）」在收款单队列里照抄的问题 —— 抽成
`slipConfirmPendingLabel(kind, count)`，并逐字断言两种单据的文案。

## 银行账户互转：跨行转账单（可编辑 + 打印 + 导出）

用户：「银行账户互转的时候，`跨行转账单.html`，支持编辑这个样式的表单，并且支持导出打印」。

模板 `example/财务/跨行转账单.html` 有 19 个 `data-docx-field` 占位符，字段名照抄进类型
（`payer_account` / `payee_bank_no` / `amount_cny`…），预填按互转单与两个银行账户逐格对应：

- 「折合人民币」取**是人民币的那条腿**（转出是人民币取转出、转入是人民币取转入、外币转外币留空）；
- 「联行号」**留空**：`banks` 表没有这一列（只有 `swift_code`），不猜一个号（错的联行号会把钱转到别人账上）；
- 四个签字格只预填制单人，其余留空 —— 那是手签的位置；
- **金额大写只有后端一份实现**：财务一改金额就把大写清空（留空 = 导出时按金额重算），
  自己写则必须与系统算出来的一致（否则 422 并把正确写法写进消息里）。

弹窗里那张纸就是可编辑的表单（每格是无边框输入框，屏幕上看着就是一张填空的单子），
打印时 `@media print` 只留 `.transfer-slip-sheet` 并把灰底标签强制印出来；
导出 XLSX 走 `POST /finance/bank-transfer-slips.xlsx`（裸 fetch，**自带 `/api/v1`**），
请求体带 `transfer_id` 只进审计（从这张纸追得回那笔资金动作）。单据不落库。

## 物料图片、销售单引用物料、工艺单行高与带图导出（本轮第二批，四件事）

用户一次给了四条（原话与三个拍板见
[设计文档](../design/material-images-and-sales-order-material-refs-2026-09-24.md)）：

### ① 收/付款单：我方与对方账户分开

模板上「收款单位 / 开户银行 / 银行账号」说的都是**对方**，而预填塞的是 `cash_flow_entries.bank`
—— 我们自己那张卡。于是付款单印出来是「收款单位：富雨鑫，开户银行：农业银行 4039…」，
而那个账号是迪礼自己的：**单据内容错**，不是文案问题。

- `FinanceSlip` 拆成 `our_bank_name/account` + `counterparty_bank_name/account`，
  **删掉旧的 `bank_name`/`bank_account`**（有意的破坏性改动，前后端同一提交改完）；
- 版式多一行 R5（我方开户银行/账号），分录区下移一行 —— 行号写成 `HEADER_ROW`/`FIRST_LINE_ROW`
  常量，避免「合计行压在最后一条分录上」这种不报错的错位；
- 我方预填自确认流水；对方从供应商 `settlementInfo` 里认（`counterpartyBankOf`，认不出留空）；
  **客户主数据没有结算信息列**，所以收款单的对方账户一律留空由财务照回单填。

### ② 工艺单行高按内容自动算

ExcelJS **不做自动行高**（`row.height` 只有写死与不写两种），所以算在服务端：
`apps/api/src/platform/excel/row-height.ts`（纯函数）。口径四条：按**显示宽度**（汉字/全角/emoji =
2 个单位，按字符数算会让全中文格子少算一半行数 —— 那正是「太扁」的病根）、可用宽度留 1 个单位的
余量（否则最后一个字被挤到下一行）、显式 `\n` 各占一行、左右两栏取 max；下限 20 磅、上限 300 磅
（注意事项 2000 字不封顶会把工艺单撑成两页）。工具是通用的，但**只接了工艺单**。

### ③ 物料图片：浏览器压成 WebP，服务端只校验

- 表是**独立 1:1 从表** `material_images`：`materials` 是热表（采购/BOM/库存/生产到处 findMany），
  字节挂在主表上会让每次列表查询都把图片读回来。列表只 select 元数据；
- 压缩在前端（用户选了「不引 sharp」那条路）：canvas 转 WebP，quality 0.82、最长边 1600；
  **旧 Safari 会静默回退成 PNG**，所以显式检查 `blob.type`，不是 WebP 就报「换 Chrome / Edge」；
- 服务端把容器**真的解开看一眼**：RIFF/WEBP + `VP8 `/`VP8L`/`VP8X` 读出真实像素尺寸 + 大小/边长上限。
  单测里的三个 WebP 夹具是 sharp 生成的**真实字节**（三种容器各一份）—— 只用手搓的字节测，
  解析器「只认自己造的那种格式」也会全绿；
- 读接口挂在 ANY 模块的 `MasterDataReadController` 上：**销售**也要看物料图，
  放写侧（procurement）控制器里销售会拿到一排 403 破图；带 `ETag` = sha256 + 304。

### ④ 销售单材料明细引用物料 + 工艺单带图导出

- 新表 `sales_order_material_refs`（一行一栏位，唯一键 `(sales_order_id, spec_key)`）；
  **替换是 upsert 而不是「软删 + 新建」** —— 唯一索引不看 `deletedAt`，删了再建必然撞唯一约束，
  改一次引用就 500。引用同时进版本快照；
- 「部件」= 材料明细 18 项（用户拍板）：每格既能手打文字、也能从物料清单引用；
  选中会把 `名称 规格型号 颜色` **写进格子**（工艺单印的是文字），并显示缩略图；
  清除引用**不动已写好的文字**；
- 导出：新增 `GET /sales-orders/:id/export-images`（候选）与
  `POST /sales-orders/:id/production-sheet.xlsx`（**multipart**，字段名 = `spec_key`）。
  为什么是 multipart 而不是 JSON：图片走 JSON 会撞上 Express 默认 100KB 的 body 上限；
  为什么浏览器转 JPEG：**Excel 不认 WebP**（ExcelJS 只支持 png/jpeg/gif），
  而服务端转码要解码器 = 用户不要的那个原生依赖；
- 表尾图片区：一排 5 张、每张占 2 列 7 行，图片正下方是「序号 + 栏位名 + 物料编码/名称」；
  锚用 `oneCellAnchor`，用户在 Excel 里一拖就走（正是「让用户自行拖拽就好了」）。

设计文档：[material-images-and-sales-order-material-refs-2026-09-24.md](../design/material-images-and-sales-order-material-refs-2026-09-24.md)。

## 遗留

1. **供应商/客户主数据没有正式的开户行与银行账号列**：付款单/收款单的对方账户本轮只从
   供应商的 `settlement_info`（自由 JSON）里认，认不出就留空；客户那边连结算信息列都没有。
   要长期规整（并让预填稳定）需要加列 + 迁移 + 两个主数据页面。
2. **物料图片的字节只校验到容器头**（RIFF/WEBP + 块头尺寸），不做像素解码 ——
   这与「不引 sharp 那种原生依赖」这个用户拍板的前提直接相关。哪天愿意引，可以做
   「服务端重新编码」这条更硬的保证；工艺单导出的图片同理（只验 JPEG 头）。
3. **行高工具只接到了工艺单**：`platform/excel/row-height.ts` 是通用的，采购单/领料单/
   财务报表有同样的「太扁」问题，但一次改十个版式会同时动十份版式测试，留到下一批逐个接。
4. **联行号没有存档**：要长期留存需给 `banks` 加一列（与 `swift_code` 同构 + 一条迁移 + 守卫测试）。
5. **「收到的税费返还」的口径**仍未定：科目表里退税挂在「营业外收入」，而准则要求退税进「收到的税费返还」。
   要不要为退税单独立一个科目（设计文档 §8.3）。
6. **权责发生制两步：两侧都已落地**（确认 = 挂账、收付 = 销账；历史数据保持原样）。
   剩下的只是**运营侧的两件事**：挂账凭证落草稿，要财务在凭证管理里过账后才进三大报表；
   以及「确认」弹窗里那个入账/支付银行与款项性质现在只对收款/付款登记有意义（界面还没有把它们从确认弹窗里拿掉）。
7. 应收、应付两条链路上更早暴露的 P0 仍未动：订单工作台 `issuedQuantity` 把 `reversed` 算成已发出、
   `cash-flow.service.ts` 的冲销缺事务、`ReverseDto` 缺 `@MaxLength`；
   以及 `suppliers.settlement_info` 的 PATCH 传 `null` 会 5xx。
