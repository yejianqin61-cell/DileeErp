## 新建销售单必然 400「请求参数校验失败」

**现象**：新建销售单只填必填项，保存必然弹「请求参数校验失败」，且看不出是哪一格。

**根因**：整页编辑器的 `specPayload()` 把 37 个细化键**全部**带上（不填的给空串）——
这是有意的，不带键就永远清不掉一格；而后端 `SalesOrderSpecDto` 里这 37 格**只有 5 个布量是数值列**
（`@IsOptional() @Matches() @IsDecimal()`），`@IsOptional()` 只跳过 `null`/`undefined`，
空串会一路走到 `@Matches` 被判「不是合法小数」。文本列没事（`@IsString()` 收空串、服务层落 NULL），
所以症状只在默认全空的 5 个布量上发作：**最常见的填法 100% 失败**。

**修复**：

- 新增 `platform/http/empty-string-to-null.decorator.ts`，给 5 个布量字段加上：空串 → `null`，
  `@IsOptional()` 跳过校验、服务层 `specScalars` 原样落库 —— 语义仍是「清除这一格」，
  **不是** `EmptyStringToUndefined` 的「不动」（两者写反的后果正好相反，见文件头注释）。
- 顺带修掉「看不出哪一格错」的根因：`exceptionFactory` 原来只读顶层 `error.constraints`，
  `@ValidateNested()` 的错误挂在 `children` 上 → 嵌套失败时 `details` 是**空数组**（recon D10）。
  抽成 `platform/http/validation-exception.factory.ts` 并递归拍平成 `spec_details[1].quantity`；
  `contract-guardrails.test.cjs` 的 D10 护栏已从「断言 details 为空」翻转为「断言能定位」。
- 前端新增 `lib/api-error-text.ts`（纯函数 + 6 条测试），销售单编辑器改用它，
  失败提示变成「请求参数校验失败：数量：明细数量必须是不小于 0 的十进制数」。
  字段路径做人话化，表里没有的键原样显示（宁可看到 `fabric_usage_canopy`，也不要吞掉这条错误）。

**为什么会潜伏**：`sales-order-dto.test.cjs` 的 `dialogBody` 是**旧弹窗时代**的载荷（没有那 37 个键），
新编辑器上线后契约测试再没覆盖过真实请求体。现在加了一条从 `apps/web/lib/sales-order-spec.ts`
源码里抽出 37 个键、与后端 `SPEC_SCALAR_FIELDS` 逐键按序比对的用例 —— 两份清单分叉会直接变红。

设计文档见 `docs/design/sales-order-create-400-fix-2026-09-20.md`。

## 采购 → 物料清单：批量导入物料（新增功能）

用户 2026-09-20：「新增一个批量导入物料。我们提供模板，用户填写并上传。模板的 column 口径你来定」。

**模板 7 列**（= `Material` 表上人能填的全部字段 = 「新建物料」弹窗的字段集合）：
物料编码 / 物料名称 / 规格型号 / 颜色 / 默认单位 / 物料类型 / 备注。
必填只有**物料名称**与**默认单位**；物料编码**留空即自动生成**（`MAT-当天日期-序号`，
与弹窗的「自动生成」同一套规则）。表头名即口径，列顺序不绑、无关列如实回显。

三条刻意的取舍：

1. **不自动新建单位**：单位是主数据，靠物料表顺手建出来只会让「米 / m / 公尺」各占一条。
   找不到就逐行报错，并把单位池现有的单位列在提示里（与盘点导入「找不到物料不自动建档」同一条纪律）。
2. **只新增不修改**：撞上已有记录的行给行级错误并指出占用者；不给 upsert ——
   「一次误传把主数据改烂且没人看得出来」比「多改几次」贵得多。
3. **查重必须带上已软删的记录**：唯一索引（`material_code`，以及 `name+specification_model+color`）
   **不看 `deletedAt`**，漏查就会在写库那一刻变成 P2002、整批失败且说不清哪一行。
   命中软删记录时给的是另一句话（说明编码仍被占用 + 两条出路）。这条单测各有一条用例专门钉。

实现：`modules/procurement/material-import.ts`（纯函数：列口径 / 同义词 / 模板生成 / 逐行解析）+
`ProcurementMasterDataService.importMaterials()`（解析 → 匹配单位 → 查重 → 一个事务批量建档）+
`GET /materials/import-template.xlsx`、`POST /materials/import`（只要 procurement 模块权限，
与 `POST /materials` 同档；路由声明在 `materials/:id` 之前）。前端在物料清单页新增导入面板，
结果整份留在页面上（逐行错误 + **含自动生成编码的新增清单** + 忽略的列 + 提示）。
「部分成功」不许说成全部成功：档位判据用 `imported` 而不是后端 `status`。

设计文档见 `docs/design/materials-bulk-import-2026-09-20.md`。

## 销售单材料明细「写了、保存了，再打开就没了」

用户 2026-09-20：「销售订单的材料明细，我是写了，然后还保存了，但是再打开就又没有了。」

**根因：数据在库里，是读的时候按错的键名取。** 一个字段有三个名字 —— 请求键 `snake_case`
（`rib_spec`，表单与请求体用的）、Prisma 列名 `camelCase`（`ribSpec`，也是 `GET /sales-orders/:id`
返回的形状）、界面中文名。后端有一张**单向**表 `SPEC_SCALAR_FIELDS` 驱动写入，所以保存是对的；
但两个**读取**侧（前端表单回填、工艺单导出）都拿请求键去索引 camelCase 的行 → 全部 `undefined`。
37 格里只有 `factory` 一个碰巧没坏（它的请求键与列名同名）。

**影响面比「没显示」严重**：编辑页 37 格全空 → 用户重开再点一次保存 → `specPayload()` 照设计把
37 个键全带上、没填的给空串 → 后端「空串 = 清除这一格」把库里真实的值**写成 NULL**。
只打开一次、再点一次保存，材料明细就真的没了。

**工艺单导出同一个根因、更早就在错**：探针用真实 Prisma 行跑 `document()`，
`materialLines: 0 / processLines: 0 / fabricUsage: [] / attentionNote: ""`——发给工厂的工艺单上
「材料」与「工艺要求」整块是空白，`completionText` 还丢了「进仓」后缀。

**为什么测试没抓到**：两个读侧的测试夹具都写成了**请求键形状**（也就是错代码期望的形状），
于是「按请求键索引 camelCase 行」这个错在前后端各绿了一次。夹具抄错比代码写错更贵：
代码错了测试会红，夹具错了测试会说谎。另外 `ExportOrder` 上挂着 `[specKey: string]: unknown`
索引签名，这条错**编译期也过得去**（已删除）。

**修复**（一处翻译、两个读侧共用）：

- 后端新增 `specScalarRow(row)`（`sales-orders.service.ts`）：列名 → 请求键，**两种形状都认**
  （`sales_order_versions.snapshot` 存的就是请求键，两种形状在这个库里都真实存在），
  空串**不回落**到列名（空串是「用户清了这一格」）。`document()` 统一过一遍它。
- 前端新增 `specFromOrder(order)` + `snakeToCamel(key)`（`lib/sales-order-spec.ts`），
  编辑器那三行换成一行。机械驼峰而**不再抄第三份映射表**：后端 `SPEC_SCALAR_FIELDS` 是权威表，
  「列名 = 请求键的驼峰」这条假设由测试逐键钉住。
- 两个读侧的测试夹具改成**真实形状**（camelCase Prisma 行），并加「回归 2026-09-20」用例
  明确断言材料 14 行 / 工艺 8 条 / 布量 / 注意事项都不许是空的。

**已受损数据**：`sales_order_versions` 的 **v1 快照**存着建档时按请求键写的全部值，是恢复来源
（之后被擦掉的版本记的是空串，所以口径是「每个键取最新的一个非空快照值」）。
本机没有可用数据库、无法先验证，本轮**只落只读诊断 SQL 与恢复口径，没有生成写库脚本**。

设计文档见 `docs/design/sales-order-spec-read-snake-camel-mismatch-2026-09-20.md`。

## 采购单「下单状态」不及时/不更新

用户 2026-09-20：「采购单中有些物料已经下单了，但是新建采购单中 column 下单状态没有及时更新。
但是我刚刚试了一单，又可以了？」—— 时对时错，所以至少两个独立机制，两个都找到并修了。

**根因 1（后端·口径错，先跑红）**：`PUT /boms/:id/items`（界面上的「保存 BOM 表」，
采购单页里就有「编辑BOM表」入口）走的是**软删全部旧行 + 整批建新行** —— **存一次 BOM，所有行 ID 都换**；
而采购明细里存的 `bom_item_id` 是**下单当时那一版**的 ID。`bomItemOrderStatus` 原来按「当前未删除的行
ID」去 `in`，老行已软删 → 那些量**整块统计不到** → 显示「未下单」→ 采购员再下一张 = 重复采购
（正是这一列要防的事）。「有些物料」= 只有保存过 BOM 的那些行中招；「刚刚试了一单又可以了」= 没保存过
BOM 的行一直是对的。

修：归集范围改成**采购单挂的那张 BOM**（`purchase_orders.bom_id`）；行 ID 还在的按行**精确**归集
（既有行为不变），行 ID 被换掉的按**物料**摊回该物料在当前 BOM 的第一行；`bom_item_id` 为空的
BOM 外新增行不占需求量；物料已从 BOM 删掉的不摊到别的行上（宁可少显示，也不张冠李戴）。

**根因 2（前端·不刷新，先跑红）**：这一列只在「带入 BOM 明细」那一刻拉过一次。页面上**已经有**
焦点/可见性刷新（2026-09-14 为「入库状态没有及时更新」加的），但它只刷采购单列表 —— 偏偏漏了
草稿表里这一列。同事或另一个窗口刚下的单，切回来还是「未下单」。

修：新增 `refreshListAndOrderStatus()` 把两个数据源合成一个刷新入口，焦点/可见性刷新（静默）与
列表操作后的刷新都走它；当前草稿的 BOM 用 **ref** 记（焦点监听只挂一次，闭包里的 `purchaseDraft`
停在打开那一刻，直接读会打到上一张 BOM 上）；刷新失败**不再一律清空** —— 换了一张 BOM 才清，
同一张 BOM 刷新失败则留着上一次的结果（把「已下单」刷成「未下单」正好会诱发重复采购）。

**顺带收紧一条已经变空的守卫**：`refresh-policy.test.mjs` 的「后台刷新必须静默」原来只查
「文件里出现过 `load({ silent: true })`」，而采购单页在「保存打印信息」里也有这一句 ——
于是焦点刷新改成非静默也照样绿。现在断言的是 `const refresh = () => …` 那一段本身必须静默。

设计文档见 `docs/design/purchase-order-bom-item-status-not-refreshing-2026-09-20.md`。

**没修的相邻问题（已报出）**：在采购单页里编辑并保存 BOM 之后，已打开的草稿行仍指着旧行 ID，
提交时会被 `PURCHASE_BOM_ITEM_MISMATCH` 整张拒掉且看不出是哪一行 —— 修它要先定口径
（重新带入 / 转成补料行 / 有草稿时禁止改 BOM），没有自作主张。

## 工资：税/社保上表 + 工资付款归类到「工资支付」

用户两条：「工资的确认支付也要加上会计科目，会计科目里面多加一个工资支付。这样确认支付工资的时候
就能归类到工资支付里面。好做账，好出表。」「工资现在还要体现出 税，社保。这些字段允许财务自行填写。
最终总工资要扣掉税和社保。」

**先纠正一个容易误判的地方**：`social_insurance` / `individual_tax` **早就在库里、在 DTO 里、
在应发公式里**（`payrollBaseAmount` 一直在减它们），弹窗里也能填。缺的是**在工资台账主表格上
「看得见、填得进」** —— 它们被叠进只读的「其他增减」净额，财务既看不到单独的数、也没法逐行改。

**税/社保**：

- 把两项从 `payrollOtherAdjustmentAmount`（只读的「其他增减」）里**摘出来**，各自成为表上一列；
  不摘出来会出现「社保显示两次、应发只扣一次」的错觉。新增 `payrollDeductionAmount()` 统一两项的合计口径。
- 表格加「社保」「个税」两列，与绩效/房补同级：可逐格编辑、可合计。「可见列之和 = 应发」这条不变式
  按新列集重算（八个可编辑列 + 其他增减 − 社保 − 个税）。
- 符号口径写死：**正数 = 被扣掉的金额**（不是填负数）。已写进注释与设计文档。
- 工资付款表与按月导出加这两列（18 → 20 列，五个数值列参与合计），
  表尾新增一句「『应发工资』= … − 社保（个人部分）− 个税，即实际应发放给员工的金额」——
  没有这句，财务看到应发比工资表低会以为漏发。

**工资支付科目**：

- 科目表新增「工资支付」（成本类 / 借 / `sortOrder` 715）。**没有**直接塞进
  `ACCOUNTING_SUBJECTS`：那份 121 行清单是财务 `科目表(2).xls` 的照抄，有长度与分类计数的守卫
  守着（「老库升级 / 新库初始化种出同一张表」的唯一保障）。改成
  `ACCOUNTING_SUBJECTS`(121) + `SUPPLEMENTARY_SUBJECTS`(新增) = `ACCOUNTING_SUBJECT_SEEDS`(122，按 sortOrder 归并)。
- 候选链首位改成「工资支付」（`salary_payment: ["工资支付", "临时工资", "基本生产成本"]`）：
  **不额外选科目也会自动归类**；后两个保留只为兼容科目被停用/改名的历史环境。
- `salary_payments` 加 `subject_id`（新迁移，可空 + `ON DELETE SET NULL`，**不建索引**）——
  与 `customer_payments` / `supplier_payments` 同一口径（这两张表早就有，工资付款一直缺）。
  故意不建索引：两张同类表的 `subject_id` 都没有索引、`schema.prisma` 也没声明，
  多建一个 Prisma 不认识的对象会让 `prisma migrate dev` 想把它 DROP 掉（schema drift）。
  优先级：过账时传的 → 付款单上存的 → 按来源自动归类。`requireSubject` 在建单前与过账前各校验一次，
  非法科目 422 且不落任何单据；`usageCount` 补上 `salaryPayment`（否则删科目会撞外键 RESTRICT）。
- 行内付款与批量付款弹窗加会计科目下拉：默认预选「成本类 / 工资支付」，可改选，
  也可显式选「（不指定，按来源自动归类）」—— 后者**不发送** `subject_id`（发空串会被 `@IsUUID` 判非法）。

设计文档见 `docs/design/salary-payment-subject-and-tax-insurance-2026-09-20.md`。

## 付款单导出（可编辑）+ 其他应付 / 应付对账删除

用户两条（附了一张手写的 Excel「付款单」样张）：

1. 「针对财务板块，她需要在付款界面能导出付款单……允许用户编辑付款单中的一些字段。
   比如**我要付款 100，我可以自己填加行，我可以写付款备注**。」
2. 「其他应付的条目支持删除。包括**删除确认应付**和**应付对账**。」

**付款单**：模板逐格对照表见设计文档 §1。两条接口 —— `POST /finance/payment-slips/draft`
（按勾选的应付条目预填，不写数据）与 `POST /finance/payment-slips.xlsx`（把界面上改好的那张渲染成
xlsx）。**付款单不落库**：它是一张打印件，所以单号只是建议值（`FK-<年月>-<序号>`，序号 = 该供应商
本月第几笔付款）、导出不影响任何账务，草稿行与已确认行都给这个入口。

三条预填口径：① 一行一条应付、**金额全额，不自动拆进项税**（含税价按税率拆在普票 / 优惠税率下
必然填错；「要拆」正是财务说的「自己填加行」）；② 总账科目取**确认时实际记账的那个科目**，
查不到才退回按来源的候选链；③ 跨供应商 / 跨币种直接 422 并给下一步，不静默取第一条。

校验前移也做全了：前端把不能导出的原因**写在界面上**（禁用的按钮点不动，原因不能只在点击后出现），
后端一次把全部问题（含行号）说完并拒绝下发；借贷合计用 BigInt「分」精确相加；空白行提交时整行丢掉。
**人民币大写只有后端一份实现**（前端刻意不预览，避免两处各写一套「金额转中文」）。

**删除**（`removeOther` / 新增的 `remove`）：

- 其他应付的**草稿与已确认**都能删；已确认的删除时**在同一个事务里回冲那笔支出**（钱回到账上）。
  为此把「找到流水 → 置为已冲销」抽成 `CashFlowService.reverseSourceFlowInTransaction`，
  `autoReverseFromPayment` 复用它 —— 「怎么算冲销」只有一处实现。软删除提交了、回冲却失败的话，
  条目已经从列表上消失、用户再也点不到它去补救，所以这两件事必须同生共死。
- 已被付款核销（部分付款 / 已付清）的拒删；原料入库 / 外加工签收形成的应付依旧拒删（到货事实的账）。
- **删除 ≠ 冲销**：行软删除、**不改状态**，审计里记 `status_when_deleted` 与回冲掉的流水号。
- **应付对账单也能删**（新的 DELETE 接口）：这条入口就是那句「请先处理那张对账单」的下一步 ——
  在此之前它指向一个**不存在的**操作。已用于确认应付并记账的对账单拒删，并在错误里点名那笔支出流水
  （对账范围内哪几条应付是它确认的没有单独记录，删了会让那笔支出失去来源单号）。
  删掉后被它覆盖的草稿应付重新回到「待创建对账」，也就重新可删。
- 入口补齐：「应付对账 → 待创建对账」行内也能删其他应付（此前只有「确认应付」页有）。

设计文档见 `docs/design/finance-slip-and-merged-reconciliation-2026-09-20.md`（这一轮把上一版
`payment-slip-export-and-payable-deletion-2026-09-20.md` 并入了同一份：单据是同一套实现，
拆成两份会让「收/付款单的差异」散落在两个文件里）。

## 收款单 + 「对账 / 确认」合并 + 集中收付

用户三条：

1. 「应收管理中，应收对账和确认应收我们合并在一起。合并到一个视图里。**但是仍然需要用户进行
   先创建对账，再确认的这两个动作**。同样的，应付管理中，应付对账和确认应付也要合并在一起，
   仍然需要两个动作。」
2. 「应收，应付。**支持勾选多选条目，进行收束集中收款付款**。并提供付款单的编辑和导出。
   **同理，收款单的编辑和导出**。」
3. （上一轮的付款单 / 删除沿用，见上一节。）

**一份实现、两种单据**：`payment-slip*` 重命名为 `finance-slip*`，用 `kind: "payment" | "receipt"`
区分。差别只有三条 —— 用词（收款单位 ↔ 付款单位、领款人 ↔ 交款人、`FK-` ↔ `SK-`）、
钱走哪一侧（付款是贷银行存款、收款是借银行存款）、勾的是哪张表
（`payable_entry_ids` ↔ `receivable_source_ids`）。版式、借贷合计、大写、校验、渲染全是同一套：
写成两份的代价不是多敲一遍字，而是「付款单修好的一个大写金额 bug，收款单上还在」。

**四条路由**：`POST /finance/{payment,receipt}-slips/draft`（预填）与
`POST /finance/{payment,receipt}-slips.xlsx`（导出）。**修掉一个真实缺陷**：预填走 `apiPost`
（api-client 自己补 `/api/v1`），导出走 `downloadPost`（裸 fetch，必须自带前缀）——
上一轮付款单导出写成了 `/finance/payment-slips.xlsx`，生产上会打到 Web 服务拿回 404 的 HTML，
用户只看到「导出失败」。两个 helper 现在各自带注释，测试逐字断言这两条路径。

**合并**：应收从 3 个页签变 2 个（成品出库条目 / **应收对账与确认**），应付从 4 个变 3 个
（原料入库条目 / 外加工签收 / **应付对账与确认**）。合并后的页签里三张表按业务顺序排开
（待创建对账 → 对账单 → 确认台账）。**故意不把两步合成一步**：对账对不清的金额不该被确认成
生效负债（`confirmPayables` 至今拒绝 `difference`）。
老地址不丢：`confirmed` 通过 `RECEIVABLE_TAB_ALIASES` / `PAYABLE_TAB_ALIASES` 折到合并后的 key，
解析集中在 `resolveFinanceTab` 一处，页面与组件都用它（不认别名的那条路会**默默落到第一个页签**，
看起来就像功能没了）；两个遗留重定向也跟着改到合并后的 tab。
顺带给两张对账单表补了带 testid 的容器（`*-reconciliations`）—— 合并之后「数一页有几行」必须能按表定位。

**集中收付**：勾选 → 批量确认（钱动一次、账逐条记，早就有了）+ 勾选 → 一张付款单/收款单
（行内也给单条入口）。两者互不依赖：可以先出单再收付，也可以付完再补单。
