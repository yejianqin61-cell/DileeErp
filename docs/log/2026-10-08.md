# 2026-10-08

## 草稿销售单可删除、生产月报表导出、应付合并付款（一轮三件事）

### 1. 用户原话

> 「1.销售单部分，draft状态的销售单支持删除。
> 2.财务部分，请问现在支不支持，应付部分，同一个供应商的多个订单一起支付
> 3.生产部分，要支持，导出每月的生产月报表。展示这个月所有的订单的生产总量。这个是模板：Dilee\example\财务\2026.6月同安.xlsx」

第 2 条是**问题**，不是要求 —— 答案是"部分支持"，见下面第 3 节；查清楚之后用户把「合并付款」也排进了本轮。

按用户习惯先问后做（每题给推荐项、等他选）：

| 问题 | 选项与他的回答 |
|---|---|
| 生产月报表第一版出什么 | **总表（订单号 × 各工序数量）+ 12 张工序明细 sheet**（整本模板的形状）✓ |
| 「本月某订单某工序的生产数量」按哪套日报算 | **与生产进度页现有口径一致：工序日报与员工日报取大** ✓ |
| 删除草稿要不要强制填原因 | **不用填，直接删**（仍是软删 + 审计）✓ |
| 合并付款的界面要不要这一轮做 | **这一轮一起做** ✓ |

### 2. 应付「同一供应商多订单一起支付」——现状答案（先回答，再动手）

**结论：部分支持。** 两半要分开说：

| 这一半 | 支持吗 | 依据 |
|---|---|---|
| 出一张**合并付款单**（纸/Excel 凭据） | ✅ 已支持 | 界面「集中付款单」按「供应商 + 币种」拆张（`finance-slip.ts:182-191`），同供应商同币种的应付落同一张单 |
| 一次操作**真正核销**多笔、改账面 | ⚠️ 后端能、界面没接 | 核销是 `POST /finance/supplier-payments/:id/post`（`supplier-payment.service.ts:78-138`）：`allocations` 是数组、付款单头 `order_no` 为空即可跨订单，末尾还写收支流水（`cashFlow.autoCreateFromPayment`，带 `bankId`） |

也就是说，**今天点界面上的「付款单」并不会让账上的应付减少** —— 它是打印件，不写核销行、不改应付状态、不动银行流水。这是本轮要接的那条线。

### 3. 草稿销售单可以删除（第 1 件事）

改动前全链**没有任何删除能力**：`sales-orders.controller.ts` 只有 18 条路由、零个 `@Delete(`，
`sales-orders.service.ts` 里也没有 `delete/remove`。表上其实早就备好了 `deleted_at` / `deleted_by`。

- **软删，不是硬删**：整条销售链 14 张子表的外键在迁移里全是 `RESTRICT`（唯一 `SET NULL` 是
  `customer_payments` 的可选引用），草稿单又天然带着版本快照、细分明细、物料引用 —— 硬删必然被
  Postgres 拒。所以走 `audit.softDelete` + 审计事件 `sales_order.delete`。
- **只有 draft 能删**：`SALES_ORDER_NOT_DELETABLE`。先读单判状态，事务内 `SELECT ... FOR UPDATE`
  再复查一次（`confirm` 会并发翻状态），与 `revertToDraft` 同一把锁、同一个顺序。
- **下游事实盘点按 11 张表数**，不是照抄 `revertToDraft` 只数 BOM/采购/生产：
  回退草稿那条路从没看过成品出库、出库通知、退货、应收/收款、应收调整/对账。
  删除比回退更彻底（列表上直接消失），守卫就按「库里到底有没有下游事实」数，
  报错文案直接列出卡在哪几类（`SALES_ORDER_DOWNSTREAM_EXISTS`）。
- **删除不弹确认框、不填原因**（用户 2026-10-08 选定）：点一下即删，与
  `outsource-logistics-panel` 的草稿删除同一形状；「谁删的、删的是哪张单」在审计里。
- **删除不释放订单号**（普通唯一索引，不看 `deletedAt`）：这是本轮发现的副作用 ——
  「删掉号写错的草稿 → 再用同一个号建单」必然撞 P2002，而那时列表上已经看不到那个号。
  所以把建单路径的报错从一句"订单号已存在"改成说明「曾被一张已删除的销售单使用，系统不释放
  已用过的订单号，请换一个号」，并在 `details` 里回带占用单的 id/状态/是否已删除。
  **这是本轮遗留的一个待定项**：要不要改成部分唯一索引（`WHERE deleted_at IS NULL`）让删除真正
  释放订单号 —— 那是一次迁移，见第 6 节。

### 4. 生产月报表导出（第 3 件事）

设计依据：[`production-monthly-report-2026-10-08.md`](../design/production-monthly-report-2026-10-08.md)

用户给的模板 `example/财务/2026.6月同安.xlsx` 是一本 17 张 sheet 的手工台账；用户选了
**总表 + 每道工序一张明细 sheet**，数量口径**与生产进度页一致：工序日报与员工日报取大**。

- 新路由 `GET /api/v1/production/reports/monthly-production-report.xlsx?month=YYYY-MM`，
  文件名 `迪礼ERP-生产月报表.xlsx`；入口＝生产页导出面板第 6 个按钮「生产月报表」。
- 总表＝`月份 | 订单号 | 订单数量 | 规格 | <工序…> | 各工序合计（非完工量）`，一个订单一行；
  工序列**读工序字典**（运行时可改），模板工序列在前（`验伞面→验片`、`品验→品检` 按字典名列出，
  `拉边` 按生产单执行方式分本厂/外发），其余按字典顺序追加，最后补「有数据但已不在字典里」的历史工序名 ——
  三层兜底，**数量不会被静默丢掉**。
- **口径＝逐日取大**：`max(工序日报日合计, 员工日报日合计)`，键为
  `(订单号, 工序, 单位, 生产单执行方式, 日期)`。逐日而不是整月：两个面常录在不同日期，
  整月取大会丢掉其中一天。单位与执行方式进键，于是「数量不跨单位合计」在数据结构上就落地了。
- 总表每格与对应明细 sheet 的「汇总数量」**同源同值**（明细直接调用总表用的取数函数，不是另算一遍）。
- 模板里**填不出来**的都写进了文件自身的说明：`大裁` 的布/伞带/布套拆分与 `计时` 列没有数据源，
  `房补` 全库没有字段，`是否完成` 刻意不做（`targetQuantity` 挂在生产单工序上，一个订单可有多张生产单，
  按「订单 × 工序」给完成判定等于自己发明口径）；完工量请读「包装」列。
- 末列原叫「合计」，评审时改成「**各工序合计（非完工量）**」：同一件产品要过好几道工序，
  横向相加会把同一批货数好几遍（缝伞 218 打 + 包装 218 打 = 436 打，而订单只有 218 打），
  生产进度表因此干脆不做横向合计。留着这一列只为量级核对，所以口径必须进**列名** ——
  写在备注里的口径没人会读，列名是唯一一定会被看到的地方。
- 新抽 `buildBook()` 支持多 sheet；既有 6 个单表导出走 `buildSheet()`（＝单 sheet 特例），输出未变。

### 5. 应付合并付款（第 2 件事的落地）

设计依据：[`payable-merge-payment-2026-10-08.md`](../design/payable-merge-payment-2026-10-08.md)

**没有任何后端改动** —— 后端本来就支持「付款单不写 `order_no` ⇒ 一次核销同一供应商多张订单的应付」，
缺的只是界面。本轮补齐：

- 新增「合并付款」弹窗（`payable-merge-payment-dialog.tsx`）：建草稿付款单 → 过账核销，
  一次核销多条已确认应付、可跨订单；应付状态、核销行、收支流水（含 `bankId` → 银行余额）都真的落库。
- 勾选从「只对草稿开放」放宽为「草稿 **或** 可核销（已确认/部分付款且未核销余额 > 0）」，
  两个按钮各按自己的子集启用；打印件那条线（集中付款单）行为一字未改。
- 供应商 + 币种是硬边界：第一条选中的是可核销应付的「锚点」，其它币种/供应商的行**复选框锁掉并把原因
  写在行上**，而不是勾完再吃 422。银行账户必填（过账要把 `bankId` 写进流水，没银行的付款不动任何余额）。
- 金额唯一真源＝逐行「本次核销金额」，表头合计是派生只读值，相加走**整数分**（不写浮点求和）。
- 过账失败时点名已建出的那张草稿，并说明再提交会**复用同一张草稿**（同一个幂等键），
  且核销合计不能超过草稿金额 —— 否则用户会陷在「改了金额 → 一直报核销超过付款金额」的死循环里。

### 6. 验证与已知边界

| 门禁 | 结果 |
|---|---|
| `npm run typecheck` | 双工作区干净 |
| `npm run test:unit:api` | **2304/2304**（基线 2275；本批 +7 删除 / +17 月报表 / +5 合并付款） |
| web `npm run test:unit` | lib **301/301** + components **1049/1049**（60 文件；基线 1035） |
| `npm run test:deploy` | **32/32** |
| `npm run build --workspace=@dilee/web` | 通过 |
| 独立验收（Lead 自跑） | 用真实服务 + 自己的假 prisma 生成真 xlsx，openpyxl 读回 **16/16**：逐日取大得一格 70（50+20；整月取大会得 50、相加会得 100）、软删与跨月数据不进表、拉边本厂/外发分列、总表与 4 张明细汇总逐个同值、数量格是数值类型 |

**本环境测不到（必须知道）**：没有本地 Postgres、也没有跑起来的 API，所以
`test:api`（HTTP 契约）、`test:integration`、`test:e2e` 全部**没跑**；合并付款的
「真实过账改了台账与银行余额」只有服务层单测与请求契约作证，**没有端到端实测**；
生产月报表的 38 条断言也只跑在编译产物 + 假 prisma 上（另加一份真 xlsx 读回）。

**本轮遗留的三个待定项**（都需要用户拍板，不是实现问题）：

1. **台账「已付/未付」还是旧口径**（`ledger-filter.ts:44` 把 `confirmed` 算已付）：
   确认在 2026-09-24 已改成**挂账**（钱没动），本轮又把第二步真核销接到界面 ——
   于是「未付」默认视图只列草稿，合并付款要勾的已确认应付被默认筛掉（要切「全部」）。
   改它同时影响应收侧、导出台账的「付款情况」列与约 6 个测试文件，故未擅动，只在页面上给了实话提示。
   建议改成 `未付 = draft + confirmed + partially_paid`、`已付 = paid`。
2. **删除不释放订单号**：软删占着唯一索引，再用同一个号建单会被拒（报错已说清原因）。
   要真正释放需要改成部分唯一索引（`WHERE deleted_at IS NULL`）—— 一次迁移。
3. **`确认应付` 仍需人工确认**：合并付款只对已确认应付开放，所以「接收 → 确认 → 付款」三步不变。
