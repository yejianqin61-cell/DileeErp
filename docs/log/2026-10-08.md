# 2026-10-08

## 草稿销售单可删除、生产月报表导出、应付合并付款（一轮三件事）

### 1. 用户原话

> 「1.销售单部分，draft状态的销售单支持删除。
> 2.财务部分，请问现在支不支持，应付部分，同一个供应商的多个订单一起支付
> 3.生产部分，要支持，导出每月的生产月报表。展示这个月所有的订单的生产总量。这个是模板：Dilee\example\财务\2026.6月同安.xlsx」

第 2 条是**问题**，不是要求 —— 答案是"部分支持"，见下面第 3 节；查清楚之后用户把「合并付款」也排进了本轮。

按用户习惯先问后做（每题给推荐项、等他选）：

| 问题 | 选项与他的回答 |
|---|---|
| 生产月报表第一版出什么 | **总表（订单号 × 各工序数量）+ 12 张工序明细 sheet**（整本模板的形状）✓ |
| 「本月某订单某工序的生产数量」按哪套日报算 | **与生产进度页现有口径一致：工序日报与员工日报取大** ✓ |
| 删除草稿要不要强制填原因 | **不用填，直接删**（仍是软删 + 审计）✓ |
| 合并付款的界面要不要这一轮做 | **这一轮一起做** ✓ |

### 2. 应付「同一供应商多订单一起支付」——现状答案（先回答，再动手）

**结论：部分支持。** 两半要分开说：

| 这一半 | 支持吗 | 依据 |
|---|---|---|
| 出一张**合并付款单**（纸/Excel 凭据） | ✅ 已支持 | 界面「集中付款单」按「供应商 + 币种」拆张（`finance-slip.ts:182-191`），同供应商同币种的应付落同一张单 |
| 一次操作**真正核销**多笔、改账面 | ⚠️ 后端能、界面没接 | 核销是 `POST /finance/supplier-payments/:id/post`（`supplier-payment.service.ts:78-138`）：`allocations` 是数组、付款单头 `order_no` 为空即可跨订单，末尾还写收支流水（`cashFlow.autoCreateFromPayment`，带 `bankId`） |

也就是说，**今天点界面上的「付款单」并不会让账上的应付减少** —— 它是打印件，不写核销行、不改应付状态、不动银行流水。这是本轮要接的那条线。

### 3. 草稿销售单可以删除（第 1 件事）

改动前全链**没有任何删除能力**：`sales-orders.controller.ts` 只有 18 条路由、零个 `@Delete(`，
`sales-orders.service.ts` 里也没有 `delete/remove`。表上其实早就备好了 `deleted_at` / `deleted_by`。

- **软删，不是硬删**：整条销售链 14 张子表的外键在迁移里全是 `RESTRICT`（唯一 `SET NULL` 是
  `customer_payments` 的可选引用），草稿单又天然带着版本快照、细分明细、物料引用 —— 硬删必然被
  Postgres 拒。所以走 `audit.softDelete` + 审计事件 `sales_order.delete`。
- **只有 draft 能删**：`SALES_ORDER_NOT_DELETABLE`。先读单判状态，事务内 `SELECT ... FOR UPDATE`
  再复查一次（`confirm` 会并发翻状态），与 `revertToDraft` 同一把锁、同一个顺序。
- **下游事实盘点按 11 张表数**，不是照抄 `revertToDraft` 只数 BOM/采购/生产：
  回退草稿那条路从没看过成品出库、出库通知、退货、应收/收款、应收调整/对账。
  删除比回退更彻底（列表上直接消失），守卫就按「库里到底有没有下游事实」数，
  报错文案直接列出卡在哪几类（`SALES_ORDER_DOWNSTREAM_EXISTS`）。
- **删除不弹确认框、不填原因**（用户 2026-10-08 选定）：点一下即删，与
  `outsource-logistics-panel` 的草稿删除同一形状；「谁删的、删的是哪张单」在审计里。
- **删除一开始并不释放订单号**（当时的 `sales_orders_order_no_key` 是全表唯一索引，不看 `deletedAt`）：
  「删掉号写错的草稿 → 再用同一个号建单」必然撞 P2002，而那时列表上已经看不到那个号。
  第一轮先把建单路径的报错从一句"订单号已存在"改成说明「曾被一张已删除的销售单使用……」，
  并把「要不要真正释放订单号」交回给用户 —— **他当天就拍板要释放**，于是有了第二轮的迁移，见第 7 节。

### 4. 生产月报表导出（第 3 件事）

设计依据：[`production-monthly-report-2026-10-08.md`](../design/production-monthly-report-2026-10-08.md)

用户给的模板 `example/财务/2026.6月同安.xlsx` 是一本 17 张 sheet 的手工台账；用户选了
**总表 + 每道工序一张明细 sheet**，数量口径**与生产进度页一致：工序日报与员工日报取大**。

- 新路由 `GET /api/v1/production/reports/monthly-production-report.xlsx?month=YYYY-MM`，
  文件名 `迪礼ERP-生产月报表.xlsx`；入口＝生产页导出面板第 6 个按钮「生产月报表」。
- 总表＝`月份 | 订单号 | 订单数量 | 规格 | <工序…> | 各工序合计（非完工量）`，一个订单一行；
  工序列**读工序字典**（运行时可改），模板工序列在前（`验伞面→验片`、`品验→品检` 按字典名列出，
  `拉边` 按生产单执行方式分本厂/外发），其余按字典顺序追加，最后补「有数据但已不在字典里」的历史工序名 ——
  三层兜底，**数量不会被静默丢掉**。
- **口径＝逐日取大**：`max(工序日报日合计, 员工日报日合计)`，键为
  `(订单号, 工序, 单位, 生产单执行方式, 日期)`。逐日而不是整月：两个面常录在不同日期，
  整月取大会丢掉其中一天。单位与执行方式进键，于是「数量不跨单位合计」在数据结构上就落地了。
- 总表每格与对应明细 sheet 的「汇总数量」**同源同值**（明细直接调用总表用的取数函数，不是另算一遍）。
- 模板里**填不出来**的都写进了文件自身的说明：`大裁` 的布/伞带/布套拆分与 `计时` 列没有数据源，
  `房补` 全库没有字段，`是否完成` 刻意不做（`targetQuantity` 挂在生产单工序上，一个订单可有多张生产单，
  按「订单 × 工序」给完成判定等于自己发明口径）；完工量请读「包装」列。
- 末列原叫「合计」，评审时改成「**各工序合计（非完工量）**」：同一件产品要过好几道工序，
  横向相加会把同一批货数好几遍（缝伞 218 打 + 包装 218 打 = 436 打，而订单只有 218 打），
  生产进度表因此干脆不做横向合计。留着这一列只为量级核对，所以口径必须进**列名** ——
  写在备注里的口径没人会读，列名是唯一一定会被看到的地方。
- 新抽 `buildBook()` 支持多 sheet；既有 6 个单表导出走 `buildSheet()`（＝单 sheet 特例），输出未变。

### 5. 应付合并付款（第 2 件事的落地）

设计依据：[`payable-merge-payment-2026-10-08.md`](../design/payable-merge-payment-2026-10-08.md)

**没有任何后端改动** —— 后端本来就支持「付款单不写 `order_no` ⇒ 一次核销同一供应商多张订单的应付」，
缺的只是界面。本轮补齐：

- 新增「合并付款」弹窗（`payable-merge-payment-dialog.tsx`）：建草稿付款单 → 过账核销，
  一次核销多条已确认应付、可跨订单；应付状态、核销行、收支流水（含 `bankId` → 银行余额）都真的落库。
- 勾选从「只对草稿开放」放宽为「草稿 **或** 可核销（已确认/部分付款且未核销余额 > 0）」，
  两个按钮各按自己的子集启用；打印件那条线（集中付款单）行为一字未改。
- 供应商 + 币种是硬边界：第一条选中的是可核销应付的「锚点」，其它币种/供应商的行**复选框锁掉并把原因
  写在行上**，而不是勾完再吃 422。银行账户必填（过账要把 `bankId` 写进流水，没银行的付款不动任何余额）。
- 金额唯一真源＝逐行「本次核销金额」，表头合计是派生只读值，相加走**整数分**（不写浮点求和）。
- 过账失败时点名已建出的那张草稿，并说明再提交会**复用同一张草稿**（同一个幂等键），
  且核销合计不能超过草稿金额 —— 否则用户会陷在「改了金额 → 一直报核销超过付款金额」的死循环里。

## 第二轮（同日）：删除释放订单号 + 台账「已付/未付」口径重定义

用户对上面第 6 节三个待定项的回答：**1 可以 / 2 可以 / 3 不行**。
第 3 条（把「确认 + 付款」并成一步）**不行** —— 所以这一轮一个字节都没动它：
「接收 → 确认 → 付款」仍是三步，合并付款只对**已确认**应付开放这一点也不变。

### 7.1 删除释放订单号（有迁移）

- 唯一性从「全表唯一」改成「**未删除行上唯一**」：迁移
  `apps/api/prisma/migrations/20261008100000_sales_order_no_active_unique` 先检出未删除行里的重复订单号
  （有就 `RAISE EXCEPTION` 中止），再 `DROP INDEX "sales_orders_order_no_key"` +
  `CREATE UNIQUE INDEX "sales_orders_order_no_active_key" ON "sales_orders"("order_no") WHERE "deleted_at" IS NULL`。
  照抄 `boms`（`20260826100000_unique_editable_bom`）与 `purchase_plans` 的先例。
- `schema.prisma`：`SalesOrder.orderNo` 去掉 `@unique`（写 `@unique` 生成的是全量唯一索引，等于把这件事偷偷改回去），
  改成 `@@index([orderNo])`（部分索引只覆盖带 `deletedAt` 条件的查询，别的反查入口还要靠普通索引）。
- 服务层三处「占用判定」全部改成**只认未删除的行**：改号预检、影响面预览、建单撞 P2002 时的文案查找。
  文案随之简化（不再有「被一张已删除的销售单占着」这一支）。
- **改号那套「按值改」的推理仍然成立，但依据变了**：唯一性只在未删除行上成立，而**删除守卫保证被删的单
  没有任何下游行**，所以带这个号的下游行只可能属于存活的那张。已知的**窄例外**写在
  `sales-order-order-no.ts` 的登记表注释里：两张**手工单据**（收支流水、其他应付）的订单号是手输的 ——
  若有人把号手输成一张草稿的号、随后删掉那张草稿、再用同一个号建单，这张草稿的号码会被后续改号
  一起带走（只动引用文本，金额与账务不受影响）。要彻底消除这个窗口，就把那两张表也加进删除守卫的盘点清单。
- 测试：改号冲突与影响面预览两条用例**反过来**（软删单占过的号现在必须放行），建单文案两条重写，
  新增 `apps/api/test/unit/sales-order-no-active-unique.test.cjs` 钉住迁移与 schema 的形状
  （内存替身看不到迁移里的索引，历史上就漏过一次）；替身的 `findFirst` 也改成真的执行 `where`
  （否则「软删已释放」这条断言测的只是替身自己）。

### 7.2 台账「已付 / 未付」口径重定义（用户说可以）

- 新口径：**未付/未收 = 草稿 + 已确认 + 部分付款**；**已付/已收 = 已付清/已收清**；作废/冲销仍只在「全部」。
  理由：2026-09-24 起「确认」只是**挂账**（钱没动，`supplier-payable.service.ts:204` 明写不写流水、不动银行），
  而「部分付款」还欠着钱。旧口径（`confirmed` 算已付）来自「确认即记账」年代，前提已经不成立。
- 改动：`ledger-filter.ts`（新增 `UNPAID_LEDGER_STATUSES`、`PAID_LEDGER_STATUSES` 收窄为 `["paid"]`、
  `paymentBucket` 由两个集合推出、头注释重写）+ web 侧同口径镜像；导出台账的「付款情况 / 收款情况」列
  与表尾脚注同步（`confirmed` 由「已付/已收」改成「未付/未收」）；控制器参数注释改正；
  「确认应付」页那条「另有 N 条被筛选藏着」的提示和它的派生状态一并删掉（它成立的前提消失了）。
  **应收侧一并改了**：两边共用同一份口径文件与同一个 `payment` 参数，只改一半会自相矛盾。
- **反向效果（预期，不是回归）**：现有数据下「未付」计数会变大（已确认的全部从已付档移入），
  界面上的「未付（N）/ 已付（M）」与导出条数同步变化。
- 顺手修了 4 处**仍然在教旧口径**的方法注释（`receivable.service` 与 `supplier-payable.service` 的
  「确认即记账」标题，以及两条对账单批量确认路径的同款说明）—— 代码早就改成挂账了，只有注释没跟上，
  而「照着注释理解系统」正是这次口径出错的根源。复核确认那两条对账单路径实际调用的也是
  `createAccrual`（挂账），**不存在「一条路径挂账、另一条路径记现金」的口径分裂**。

## 第三轮（同日）：材料明细「其它」自定义类目行

### 8.1 用户原话与那一问

> 「1.然后编辑销售订单的材料明细最后还需要加一个"其它"，可以自行添加类目。有时候还需要别的物料。
> 允许用户增删改。」

先问后做：**「其它」行要不要也能引用物料清单里的物料（缩略图 + 导出勾选带图）→ 用户选「要，和 18 格一致」**。

### 8.2 做了什么

- **一张新表** `sales_order_material_extras`（类目 + 内容 + 可空引用物料 + 排序 + 审计列）。
  为什么是行而不是列、为什么不复用细分明细表、为什么引用挂在这一行上而不进
  `sales_order_material_refs`：三条理由都写在 [`design/sales-order-material-extras-2026-10-08.md`](../design/sales-order-material-extras-2026-10-08.md) §2。
- **接口**：`material_extras` 进 `SalesOrderSpecDto`（新增 `MaterialExtraDto`），
  与明细/引用同一条**整块替换**语义（不传 = 不动、`[]` = 全删、若干行 = 重建）。
  校验在后端独立再判一次：类目必填、内容与引用至少有一个、类目 ≤ 50 字、内容 ≤ 1000 字、
  最多 20 行、引用的物料必须存在；**先校验后写**（一行不合法时一个字节都不写）。
- **界面**：材料明细**同一块面板**里的子块（用户说的位置就是「材料明细最后」）：
  每行「类目 + 内容 + 从物料清单引用（可搜索下拉 + 缩略图 + 清除引用）+ 删除这一行」，
  区块头「加一行」（到 20 行上限时禁用并提示），逐行错误在页面上先摆出来、保存前再拦一刀。
- **导出**：工艺单材料区印在 18 项之后（类目用用户起的字，内容空则用引用物料摘要兜底；

- **返单与快照**：随单进版本快照；返单照抄来源单，来源单引用的物料已被删时**保留文字只摘引用**并回报。

  「MAT-1 伞骨」，规格与颜色在纸上消失）。抽成一份 `EXPORT_MATERIAL_SELECT`，两处共用，
  并加了一条**钉住查询参数**的测试。

### 8.3 与 18 格故意的两点不同（都会有人问）

1. 选中物料时**只在内容为空时**预填「名称 规格 颜色」：18 格是模板上固定的某部件规格，
   覆盖就是替人省手打；「其它」行的内容是人手写的自由文本，覆盖等于把工厂要照做的那句话悄悄改掉。
2. 「删除这一行」没有占位规则（明细表保底留一行空行，「其它」允许 0 行）。
