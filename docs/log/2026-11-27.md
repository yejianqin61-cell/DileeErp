## 2. 一个真实的交互缺陷：连着说同一件事，被当成四件事

用户那四句是**一件事的四个片段**。机器人对每一句都 `ask_more_info`，于是群里连着被追问四遍，
用户还得一句句回。这比不回答更烦 —— 他在描述一个 bug，机器人却在跟他玩问答。

修法（prompt 层）：明确「用户连着说同一件事」的判据与处置：

1. 上一条也在说同一个问题、那张单还是 `needs_info` → `append_ticket`；
2. 消息本身信息不完整（只有一个单号、一个「是」、一句「还是不行」）→ 它几乎一定是在补充，
   **不要**新建工单，也**不要**再追问一遍；
3. 只有明确换了个页面/模块/问题时才 `create_ticket`。

同时保留原来那条底线（点出具体页面/模块就直接建单，别为「没说清期望」追问），
两条不冲突：前者管「接着说」，后者管「第一次说」。

## 3. 分页上限 200 → 1000

### 3.1 200 不是 bug，是护栏

它当初的用意是「一次拉全量再前端过滤」的防呆上限（防止某个调用方写 `page_size=100000`
把数据库拖死）。厂里的单据量越过了它，表现就是「第 201 张单永远看不见」——用户以为是 bug。

### 3.2 为什么先扩到 1000，而不是直接做归档

用户自己说了「这个先扩充到 1000 单，以后我们要优化单据完毕归档机制」。
1000 是止血，归档才是根治：已完毕的老单据移出活动列表，单量继续涨也不会变慢。
`MAX_PAGE_SIZE` 的注释里写明了这一层，免得下次有人以为 1000 是终局。

### 3.3 真正的毛病：这个数散在六处

原本它被各写一遍：控制器 `@Max(200)`（4 个文件）、工作台服务 `MAX_PAGE_SIZE = 500`、
报表服务 `Math.min(..., 200)`、告警服务 `Math.min(..., 200)`、前端各页面 `page_size=200`（7 处）。

「改一处漏五处」的必然结果是两种故障，而且都很难查：
- 前端传 1000、后端 DTO 拒绝 → 400，用户看到「加载失败」；
- 后端放宽了、前端还传 200 → 用户还是只看到 200 单。

现在真源只有一处：`apps/api/src/platform/http/pagination-query.dto.ts` 的 `MAX_PAGE_SIZE = 1000`，
控制器、服务层、前端全部引用它。前端另有具名常量 `SALES_ORDER_LIST_PAGE_SIZE`（`sales-order-sort.ts`）。

### 3.4 顺手修掉一个真实缺陷：报表导出被列表上限夹住

`reports.export()` 请求 `page_size: 5000`，但 `take()` 硬夹 200 —— 于是：
- 导出**永远只出 200 行**；
- 而「结果 >= 5000 就报 `EXPORT_LIMIT_EXCEEDED`」那条护栏因为夹取在前、比较在后，**永远不触发**。

用户拿到不完整的 CSV，且没有任何提示。仓库里原本就有一条用例把这个记成已知缺陷：

```
test("KNOWN_DEFECT: reports.export_silently_truncates_to_200_rows", ...)
// 修复后（导出上限与 take 上限对齐）此断言应变红。
```

这次正好把它修了，用例按它自己的指引改成断言已修复。**导出上限（5000）与列表上限（1000）
现在是两个概念**：一个是「屏幕上一次显示多少」，一个是「一次拉多少写 CSV」。

## 4. 新增守卫：上限一致性

`apps/web/test/pagination-limit-consistency.test.ts`（6 条，静态检查源码文本）：

- 真源是 1000；
- 没有控制器再写死 `@Max(200)`；
- 服务层引用真源而不是各写一个数；
- 报表导出不受列表上限夹取；
- 前端没有页面再写死 `page_size=200`；
- 前端传的量不超过后端上限（超了就是 400）。

**已实测它真的会红**：故意把 `workbench.tsx` 一处改回 `page_size=200`，
它精确报出「前端不再有页面写死 page_size=200」这一条失败。

这类守卫和 `testid-pages` 是同一个思路 —— 跨文件一致性只能靠静态检查钉住，
因为「跑相关测试」永远覆盖不到「另一个文件里那个必须同步改的数字」。
