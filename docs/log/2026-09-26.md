## 当天稍后（用户）：付款单的汇率与保存键 + 交税凭证模板

用户原话：**「付款单要有填写汇率的地方，保存键。生成凭证时要有交税的那一项。」**
（同一条消息里还有「提交，push」——那件事是：把积压的文档提交为 `c00b05d` 并推送，
`origin/main` 与本地 0/0。）

三件事各拍了一次口径，落地方式与**刻意不做的部分**都写在
`docs/design/finance-slip-archive-and-tax-voucher-template-2026-09-26.md`，这里只记要点与代价：

1. **汇率与折合人民币**：单子版式加一整行 R6（币种 / 汇率 / 折合人民币），分录区与合计行整体下移。
   汇率精度取 **8 位**（与 `exchange_rates` 同精度），不跟跨行转账单的 6 位 —— 汇率的精度只该有一个出处。
   **不自动折算**：折合人民币是手填的一格，留空就是留空（与「不按税率自动拆进项税」同一条口径），
   界面上把这句话写出来（这两格看起来是一对，不说财务会以为系统算过了）。
2. **保存键 → 单子落库**：新表 `finance_slips` + `finance_slip_lines`（迁移
   `20260926120000_finance_slips`）。边界是这一轮最要紧的事：**保存不改任何账** ——
   不写收支流水、不生成凭证、不动应付/应收状态；「钱付没付」仍由确认付款回答。
   校验随之**分层**：`validateFinanceSlipShape`（保存：只拦结构）与 `validateFinanceSlip`
   （导出：另加编号、对方单位、借贷平衡）—— 逼财务填平才能存，等于把保存变成「必须一次做完」。
   新板块「收付款单」（`/finance/slips?kind=`）：找回、打开继续改（**覆盖同一张**）、再导出、作废（原因必填）。
3. **交税凭证模板**：借 应交税费 / 贷 银行存款，落在既有的模板机制里；候选科目只到「应交税费」本体，
   不猜税种明细（猜错了凭证上看不出异常）。

## 第八轮（货号与返单工作流）：销售单货号字段（P1）

老板要求：「每个销售单多一个字段，叫做货号。以后客户返单，从系统里面调取，返单客户货号不变。
可以调取该货号。查看当时该批货号的采购，生产，QC 的所有表单，信息」。
本轮先做 P1（字段本身），4 个提交，每步都跑过全量单测。设计与任务清单：
`docs/design/reorder-item-no-and-summary-2026-09-26.md` + `docs/task/0926-reorder-item-no-and-summary/`。

### 1. 数据层（`3a1b7ba`）

`sales_orders` 加 `item_no` / `reorder_from_order_no` 两列（都可空）+ `(item_no, order_date)` 索引。
**刻意不做**的三件事由 7 条迁移守卫钉住：不加 NOT NULL（历史单没有货号）、不加唯一约束
（返单的本质就是同一货号多张单）、不建自引用外键（返单链不该因老单被删/改而断裂）。
货号**不冗余到采购/生产/QC**：下游已冗余 `order_no`，再加一列就有两个真源；
查询走「货号 → 订单号集合 → 下游 by orderNo」，正好吃既有 `orderNo` 索引。

### 2. 写读侧与归一（`6e81848`）

`apps/api/src/modules/sales/item-no.ts` 是归一与匹配键的唯一实现：入库值去首尾空白并把内部连续空白
（含全角空格 U+3000）折成一个半角空格，匹配键再去空白转大写。不做归一，`27621` 与 `27621␠`
会各成一组 —— 那正是老板要「调取该货号」时最怕的结果。货号进每一版快照且**先归一**。

### 3. 印刷面（`0e2c9f3`）

工艺单印在「完工日期」那一行（该行右边本来是空的）；采购单并入「订单号」格。
两处都**不新增行列**：表头 12 格是用户点名的、明细 9 列牵着列宽与小计公式。
**没有货号时两张导出件与改造前逐字相同**。

### 4. 界面（`257eae6`）

新增 `ItemNoInput`：可挑既有货号、也可直接输新的。没用 `searchable-select`（它只能选不能建），
也没用原生 `datalist`（全站治理轮已移除原生控件）。销售单列表加货号列、货号搜索与
「未填货号（待补录）」筛选。`apps/web/lib/item-no.ts` 是 api 侧归一函数的镜像，
两份用同一组测试向量钉住（无共享包的既有约定）。

### 5. P2 返单建单与前端入口（`7d10cdb`、`f28a536`）

**建单**（`7d10cdb`）：`POST /sales-orders` 接受 `reorder_from_order_no`，服务端把来源单的值
填进「请求没给的键」，然后走**与普通建单完全同一条** `create()` 路径 ——
另写一条 `createFromReorder()` 会绕过币种校验、客户解析、材料存在性校验与唯一键冲突处理，
而绕过不会当场报错，只会在几个月后以「返单能建出一张没有客户的单」的形式爆掉。

三条守卫：来源不存在 404 / 草稿来源 422 / 来源无货号 422（文案带单号，现场知道去补哪张）。
复制「这一单卖的是什么」，**不复制**「卖多少、什么时候交、走到哪了、由数量派生的三个金额」。

开工后补掉的一个缺口：**来源单引用了已删除的物料**会让整张返单被一个用户看不见的旧引用卡死
（`assertMaterialsExist` 抛 MATERIAL_NOT_FOUND，文案还叫人「刷新物料清单后重选」——
而复制的这条路上没有"重选"这个动作）。现在复制时剔除并用 `reorder_warnings` 回报；
请求自己带了 `material_refs` 则不过滤（那是用户在界面上确认过的，缺物料就该当场报错）。

**入口**（`f28a536`）：`/sales/orders/new?reorder_from_order_no=…` 拉预览并**一次性**预填
（逐键 set 会与浅合并产生竞态，填了一半的表单最危险）；四格必须重填并标「返单必填」；
改货号会提示「会归到新的货号下」。

实测发现的一处必须改的地方：**预览失败时只留错误横幅是不够的** —— 横幅下面那张空白表单
仍然可以提交，而它看起来就是「这一单本来没有工艺要求」。现在失败即不渲染表单，只给重试与返回。

### 6. P3 前半：读模型 API 与导航栏目（`e193816`、`c947163`、`8d638a4`、`8699bd7`）

**读模型**（新模块 `modules/reorder`，纯读）：

- `GET /reorder/articles` 货号清单 —— 三步走：拉全部匹配订单的**轻字段** →
  **内存里按归一键归并** → 排序分页后只对当前页做下游聚合。
  归并必须在内存里做：`groupBy` 按**列值**分组，`27621` 与 `27621␠` 会各占一行，
  而它们按业务是同一个货号（Prisma 又不支持按表达式分组）。不归并的后果正是老板最怕的：
  查 `27621` 只看到两批，另外三批躲着。
- `GET /reorder/articles/:item_no` 详情 —— 历次批次 + 跨批汇总 + `can_reorder`（带中文理由）。
- `GET /reorder/articles/:item_no/documents?order_no=` —— **17 组单据**（老板原话的落点）。
  空组也返回；没给 `order_no` 就 400；该单不属于这个货号就 404（否则这是一条绕过货号口径、
  取任意订单全部单据的通道）。
- `GET /reorder/articles/:item_no/timeline` —— 审计倒排，超 200 条回报 `truncated`。

口径上守住的几件事：数量按单位分行、金额按币种分行、QC 合格率分母为 0 给 `null`（不是 0）、
Decimal 一律字符串、已关闭默认纳入、软删默认排除、`meta.total` 是**货号数**不是销售单数。

**排序不用 `localeCompare`**：它受运行环境 ICU/locale 影响，会让「同一页里行的先后换台机器就变」，
测试也跟着变成环境相关。统一按码位比 —— 这条是测试先红（`支` 与 `打` 的顺序）才发现的。

**修掉一个真缺陷**：货号清单起初把 `{...article}` 展开，于是响应**同时**给了 `itemNo`（camel）
与 `item_no`（snake）两套键名。一个响应两种键名正是本仓库反复踩过的那类坑。
现在统一 snake_case，两个测试文件都钉住。

**交叉一致**：新增一条与工作台对照的测试 —— 同一订单的采购金额与 QC 合格数两边必须相等。
工作台把采购金额跨币种加成一个数（它自己的既有口径），所以对照用单一币种。

**导航**（`8699bd7`）：表面栏目 `reorder` 归 `full` + `general`，**不加进 `hr`** ——
那会让"只能看人事"的角色看到全公司的采购/生产/质检汇总。
已知：`/reorder` 页面是 T11，在它完成前这条 tab 是死链；本批次全部完成前不 push，
所以最终形态里两者同时到位。
