## 销售板块拆二级页、引用物料的导出兜底、明细自定义列名（一轮五件事）

设计依据：[`sales-order-subpages-and-detail-labels-2026-09-30.md`](../design/sales-order-subpages-and-detail-labels-2026-09-30.md)

### 1. 用户原话

> 「针对销售单部分，
> 1. 成品出库总览，客户池，销售单，都收进二级页面。
> 2. 新建销售单，材料明细那边，如果是使用引用的资料，在导出的 excel 中无法显示。
> 3. 材料明细，引用的下拉列表也支持搜索。
> 4. 细分明细那边，可以改成自定义字段名称。
> 5. 销售单导出的部分，工艺要求那边，每一点的标题也需要显示。」

按用户习惯先问了三处**不猜**的地方（每题给推荐项、等他选）：

| 问题 | 选项与他的回答 |
|---|---|
| 「收进二级页面」照财务那套做吗 | **照财务：`/sales` 只剩三张卡片，各自独立子页面** ✓ |
| 引用物料在导出里缺的到底是哪一半 | **那一格是空的（物料名称/规格没印出来）** ✓ |
| 「自定义字段名称」是哪件事 | **明细表的列名每一单都能自己改，导出跟着变** ✓ |

### 2. 一件一件看，这一轮实际改了什么

- **销售页拆页**：`/sales` 变成纯导航页（三张卡片），三个板块各自一个二级页
  （`/sales/finished-goods`、`/sales/customers`、`/sales/orders`）；实现搬进
  `components/sales/{finished-goods-overview,customer-pool,sales-orders-list}.tsx`，
  行为与 testid 一字未改；板块清单落在 `lib/sales-sections.ts`。
  `/customers` 仍渲染同一个客户池组件（它是另一个表面栏目自己的入口）。
  编辑器保存/取消后的返回目标从 `/sales` 改成 `/sales/orders`。
- **引用物料的导出兜底**：导出侧在「格子里没有字」时，用**引用的物料**生成
  `编码 + 名称 + 规格 + 颜色` 印出来（`materialRefText`），并新增落格用例；
  「空盘位自动省略」这条口径没动（既没字也没引用的栏位仍然不印）。
- **引用下拉支持搜索**：材料明细 18 格的引用控件从平铺 Radix `Select` 换成
  `ui/searchable-select`（按编码/名称/规格/颜色都能搜、搜不到给可读空态）。
- **明细列名按单自定义**：新列 `sales_orders.spec_detail_labels JSONB NOT NULL DEFAULT '{}'`
  + 迁移 `20260930120000`；编辑器加「修改列名」（6 格一次改完，留空 = 恢复默认名），
  导出件按这一单改过的名字印；进版本快照、返单沿用来源单。
- **工艺要求带标题**：落格从 `1.<内容>` 改成 `1.样品要求：<内容>`，
  文档形状 `processLines` 从 `string[]` 改成 `{label, value}[]`。

### 3. 几处值得记下来的判断

1. **「引用」与「格子里那行字」是两条记录，能不同步 —— 所以导出必须能自己站起来。**
   格子的文字是 `sales_orders.rib_spec` 那种标量列，引用是 `sales_order_material_refs` 一行。
   原来的导出只看文字，文字为空就把**整个盘位**省掉：纸上少一个部件，而系统里那格"有东西"。
   兜底用引用的物料生成文字（带物料编码，车间能对回物料清单）。
   **刻意不做"保存时把文字补回格子"**：那是拿导出需求去改用户的数据。
2. **列名可以按单改之后，「页面上的名字」与「印出来的名字」只能是同一份。**
   这带来一处**有意的默认值统一**：导出件里那一格原写「颜色」，而编辑页上一直写「颜色/配色」，
   现在两边都用 `SPEC_DETAIL_LABELS` 的默认名 —— 不是顺手改写，是"列名只有一个真源"的必然结果，
   已写进导出测试的注释里（免得下一个人以为是漂移）。
3. **不认识的自定义列键要报错，不能静默忽略。** 静默忽略的表现是
   「界面上改了名字、导出还是老名字」，而请求里明明带着那个键 —— 这种错没人能查。
   同理列名超 20 字要报错（表头要印在一格里），前端也在保存前拦一次。
4. **纯导航页不许发业务请求。** 拆页的收益就是"每页只拉自己那一个接口"，
   所以一级页的用例直接断言 `calls` 为空、二级页的用例断言"没拉别人的接口"——
   否则"拆了页却还是一次拉三个"会一路绿着走过去。
5. **`processLines` 改成对象数组而不是在渲染时拼标题。** 标题是**数据**：
   测试要按标题取值、以后要按标题排印，拼在落格函数里就取不到。

## 采购计划明细加高、不在池里的物料仍显示、引用下拉长文字换行（同一天第二批）

设计依据：[`purchase-plan-readability-and-ref-wrap-2026-09-30.md`](../design/purchase-plan-readability-and-ref-wrap-2026-09-30.md)

### 1. 用户原话

> 「1.采购计划那边，要展示相应的采购物料啊，有的地方没有显示相应的采购物料。采购物料那个表单
> 高度太小了，可以高度大一点，这样视图更方便
> 2.并且检查采购计划下单之后，能否自动流转到采购单那边去。
> 3.销售单部分，引用库存的信息，如果页面不够展示，那就换行，而不是超出页面显示范围」

问了三处不猜的地方：**「有的地方没显示」= 他看错了**（所以采购计划列表没有加列）；
**「表单高度」= 采购计划明细表的行高/输入框**；**「引用超出页面」= 引用下拉的选项文字，要换行**。

### 2. 实际改了什么

- **明细表那一格永远显示这一行的物料/单位**（`plan-detail-sheet.tsx`）：物料停用/软删/改成成品后
  就不在 `GET /materials` 里，Radix 的 `SelectValue` 找不到对应项就退回占位符「请选择物料」——
  计划里明明记着物料的那一格看起来是空的。服务端 `get()` 早就把 `materialName` / `unitName`
  从快照兜回来了，前端把它丢掉了。现在选项 = 物料池 + **这一行自己那个值**，补进来的一项
  `disabled`（显示得出来、选不到别的行上——真选了服务端会拒整份计划）。
- **明细表加高**：单元格内边距 `4px 5px → 8px 6px`、行内控件 `30px → 34px`、字号 `11px → 12px`。
  行高由"内边距 + 控件高度"决定，13 列宽度总和仍是 100%（不横滑没丢）。
- **引用下拉的选项文字换行**（`.ui-searchable-select-option-text` 加 `min-width: 0` +
  `overflow-wrap: anywhere`）：原来选项是个 flex 项（最小宽度 = min-content），既不换行也不收缩，
  弹层横向滚动、那行字被切在可视范围之外。刻意**不用省略号**——用户要的是看全。
  这是共用原语，会计科目筛选/BOM 供应商/生产单候选一起受益。
- **第 2 条是核查，没改代码**：下单 → 采购单**已经是自动的**（同一事务建单 + 回写计划行链接，
  状态 `ordered`，而采购单列表的范围正是 `ordered/partially_arrived/arrived_complete`）。
  只补了一条守卫断言"落成的是**已下单**而不是草稿"——落成草稿的话单子永远不进采购单列表，
  而界面上不会有任何报错。

### 3. 值得记下来的判断

1. **"下拉里显示不出来"这类症状，根因往往是"值不在选项列表里"，而不是"值丢了"。**
   Radix 的 `SelectValue` 只认选项；停用/软删的主数据一从列表里消失，那一格就变成占位符。
   供应商那一次（2026-09-27）踩的是同一件事，这次是物料与单位。判据：**接口有没有把名字给回来**。
2. **补回来的选项必须是 `disabled`。** 只为"显示"而加一个可选中的选项，等于把
   "这份计划会被整单拒绝"这个坑留给用户去撞（服务端 `PURCHASE_PLAN_REFERENCE_NOT_FOUND`）。
   选中的项即使用户点不到，Radix 也会把它的文字放进触发框，所以显示与可选可以分开。
3. **共用原语上的 CSS 只改一处。** 长文字溢出不是销售页独有的，改
   `.ui-searchable-select-option-text` 比在一个页面上加一个类名好。
4. **"检查 XX 能不能自动流转"这类要求，答案要落到一个可回归的断言上。** 链接回写、事务、
   状态枚举三件事里，只有"状态不是草稿"是那种"错了也不报错、只是永远看不见"的错，
   所以守卫断言状态，而不是"接口被调用了"。

## 采购计划加价格字段（单价 / 行总价 / 计划合计）+ 采购↔财务对齐度排查（同一天第三批）

设计依据：[`purchase-plan-pricing-2026-09-30.md`](../design/purchase-plan-pricing-2026-09-30.md)；
排查结论另见 [`procurement-finance-alignment-2026-09-30.md`](../design/procurement-finance-alignment-2026-09-30.md)。

### 1. 用户原话

> 「针对当前的采购计划，要求添加价格字段，单价，总价。不然财务没法付钱。
> 你也排查一下采购链路和财务链路的对齐度」

### 2. 先问清楚的四个口径（每题给推荐项、等他选）

| 问题 | 选项与他的回答 |
|---|---|
| 「总价」到什么粒度、币种怎么记 | **明细加「行总价」+ 列表/头部加「计划合计」；币种按行记，默认人民币，收束下单时按该供应商组选的币种写回，合计按币种分列** ✓ |
| 财务"付钱"的入口 | **只是「提前看 / 对账」：付款仍只认入库金额**（不动账务链路） ✓ |
| 单价 0 能不能下单 | **不能**：收束下单前要求每行单价 > 0 ✓ |
| 采购明细的 `extra_fee` 不进应付 | **保留字段，把差异写进口径文档** ✓ |

### 3. 实际改了什么

- **先查清一件事**：单价**本来就有**（明细表第 8 列，`purchase_plan_items.unit_price`）。
  缺的是**总价**。而"不然财务没法付钱"这句指向的是两件更硬的事，不是"少一格显示"。
- **对账（行总价）**：紧挨单价右侧一列，只读、**本地即时算**（改一次数量或单价就看见钱变了）；
  单价为 0 的未下单行**标红**（漏填报价最快的入口）。
- **计划合计**（表下方，**按币种分列**，「金额不跨币种合计」）：全部行的合计 + **其中未下单**。
  「还要花多少钱」才是采购员和财务真正问的那个问题。
- **计划列表**加「计划金额」列，按币种分列显示服务端算好的金额；一行价都没填时显示「未填价」
  而不是 0（**0 与"还没谈"是两件事**）。
- **币种按行记**：新列 `purchase_plan_items.currency`（NOT NULL DEFAULT 'CNY'，迁移
  `20260930140000_purchase_plan_currency`）。**不在明细表里开「币种」列** ——
  币种的唯一决策点本来就是「收束下单」预览里按供应商组选的那一格（口径 10），
  下单时把该组币种**写回这一组每一行**，于是已下单行的币种永远等于那张采购单的币种。
- **单价 > 0 才能下单**（两处）：计划侧逐行校验（新错误码 `PURCHASE_PLAN_PRICE_REQUIRED`，
  报文说清是第几行、以及"应付金额就是按这一行数量 × 单价算出来的"），
  采购单侧的下单门禁同步从 `isNonNegative` 收紧成 `isPositive`；前端在下单前也先拦一次。
- **金额口径只实现两遍，用同一组向量钉住**：后端 `purchase-plans.domain.ts`（Prisma Decimal）
  与前端 `lib/purchase-plan-amount.ts`（**BigInt 按 1/10000 为单位**，不走浮点），
  两边测试用同一批数字（17.5 / 0.1×3 / 23.5 / 2.225 半进位）。

### 4. 值得记下来的判断

1. **"添加价格字段"这句话里，真问题不在那一格。** 单价早就在，缺的是"这张单一共要花多少"；
   而"财务没法付钱"真正的成因是**入口不设防**：BOM 带出来的行单价是 0，
   而下单门禁只要求"不为负" —— 0 元采购单 → 0 元应付，**全链路不报错**。
   所以这一轮的重点是那道门禁，不是那个显示格。
2. **金额不落列。** 计划**不落** `amount` 列（`数量 × 单价` 的纯派生量）：落列就有第二个真源，
   改数量忘了改金额时两个数都"看起来对"。这与采购明细**故意不同** ——
   那边的 `amount` 含独立的 `extra_fee`，是另一笔钱，必须落列。
3. **币种属于"一张采购单"，不属于"一份计划"。** 计划里同时有多个供应商，
   把币种固定在计划头上等于把"不同供应商报不同货币"从数据模型里删掉；
   而按行记 + 下单写回，是"一次输入、两处记录"，不是"两次输入"。
4. **金额的前端计算必须与后端逐字相同。** 界面为了让用户边改边看钱，只能本地算；
   浮点的 `0.1 × 3` 是 0.30000000000000004，而 `(2.225).toFixed(2)` 是 `"2.22"`
   而后端 decimal.js 的 ROUND_HALF_UP 给 `"2.23"` —— 各说一个数，谁也查不出为什么。
   所以前端按 1/10000 做 BigInt 整数运算，并**半进位**。
5. **"合计按币种分列"要写进类型里。** 后端返回 `amounts: [{currency, amount}]` 而不是
   `{currency, total}`：后者只能标一个币种，而它看起来是对的。
6. **0 与"还没谈"是两件事。** 列表里一行价都没填时显示「未填价」而不是 `CNY 0.00`；
   计划里单价 0 的行在下单前被拦下，而不是变成一张 0 元采购单。

### 6. 排查出来的、本轮**没修**的东西

采购↔财务的对齐度排查单独成文（[`procurement-finance-alignment-2026-09-30.md`](../design/procurement-finance-alignment-2026-09-30.md)），
按严重度列了 13 条，**一条都没在本轮动**（用户选定：付款链路只"提前看/对账"，不改账务）。
其中最要紧的四条：

1. 应付冲销 / 删除「其他应付」**不回冲已挂账凭证** → 台账说已冲销、总账仍挂应付账款，
   报表虚增，而系统不会提示（它去回冲的那类流水自 2026-09-24 起就没有写入方了，回冲是空操作）；
2. 外加工签收冲销**不校验应付状态**（原料入库侧有对称闸门）→ 已付款的应付其来源可被冲销；
3. 「回退草稿 → 改金额 → 再确认」**不会更新凭证**（按 `(sourceType, sourceId)` 幂等命中即返回旧凭证）；
4. 采购对账明细的**合计行跨币种相加**（同一批功能里收支明细/应付台账导出都不做合计，口径不一致）。

还有一条历史上一直在生效的：**四处"已财务过账不可撤销"在比一个从来不存在的状态值**
（`payable_sources.status === "posted"`，而该列只有 `pending_finance` / `received` / `voided`），
目前靠旁路条件兜住。

## 销售单订单号可改 + 全链联动改名（同一天第四批）

设计依据：[`sales-order-no-rename-2026-09-30.md`](../design/sales-order-no-rename-2026-09-30.md)。

### 1. 用户原话

> 「创建销售单，订单号写错了要支持编辑和修改。要做好全链条订单号的联动调整」

### 2. 先查清的两件事

1. **不是"不能改"，是"能输入、保存时被丢掉"。** 编辑页那一格一直可编辑（`BASE_FIELDS` 里的普通
   `Input`，没有 readOnly），但 `save()` 里有一句 `delete payload.order_no`；后端
   `SalesOrderUpdate` 也把 `order_no` 排除在类型之外，DTO 里更没有这个键（`forbidNonWhitelisted`
   → 真发出去是 400）。所以真实体验是：**改完点保存 → 提示"已保存" → 号还是旧的**。
   这类静默丢弃比报错更难查（用户以为系统没保存上，反复重试）。
2. **订单号不是一格数据，是全库的引用键。** `sales_orders.order_no` 是唯一索引，另外 **40 个列**
   存着它的副本（38 张下游表 + `audit_events` + 源头自己），而读路径**大量按订单号 join**：
   采购下单按它找销售单与 BOM（`purchase-orders.service.ts:560,568`）、领料预览按它聚合
   已下单/已入库（`raw-material-movements.service.ts:481-482`）、财务报表按它反查客户
   （`finance-report-query.service.ts:705`）、对账单按它取范围（`reconciliation.service.ts:249`）、
   工作台按它取单（`order-workbench.service.ts:20`）。
   **只改一格 = 让同一张单同时存在两个号**，上面每一条 join 都会**静默少数据**（不报错），
   最后只在财务对账时以差额的形式暴露。所以"改一半"比不改更糟 —— 这是本轮必须做全链联动的原因。

### 3. 先问清楚的四个口径（每题给推荐项、等他选）

| 问题 | 选项与他的回答 |
|---|---|
| 什么时候允许改号 | **任何时候都能改，全链同步**（含已确认、已有 BOM/采购/生产/入库/应付/凭证的单；必须填原因；保存前先给影响面确认）✓ |
| 版本快照与审计里的旧号怎么办 | **版本快照跟着改，审计保留旧号**（另记一条改名事件带 from→to）✓ |
| 要不要能拿旧号反查到新单 | **不要新增"曾用单号"列**，按旧号反查走审计 ✓ |
| 改号入口 | **只在销售单编辑页**（列表页不加"改号"快捷按钮）✓ |

第 3 条的直接后果：**本批没有任何数据库迁移**（不加列、不加表）。

### 4. 实际改了什么

- **联动清单是一张登记表**（`apps/api/src/modules/sales/sales-order-order-no.ts`，
  `ORDER_NO_RENAME_TARGETS`，**38 项**）。每项就是一条
  `tx.<model>.updateMany({ where: { orderNo: 旧 }, data: { orderNo: 新 } })`。
  之所以能"按值改"而不必逐表判断这列到底指谁：`sales_orders.order_no` 全局唯一，
  于是"值 = 旧单号"与"指向这张单"是**同一件事**。用 Prisma 模型委托（而不是 raw SQL）写，
  模型名写错是**编译错误**而不是静默漏改。
- **一条覆盖守卫测试**：扫 `schema.prisma` 里全部 `@map("order_no")` 列，与「登记表 ∪ 豁免清单
  （只剩 `SalesOrder` 与 `AuditEvent`，各带理由）」做**集合相等**比较。以后谁新增一张带
  `order_no` 的表却忘了登记，测试直接红。
- **一个事务里原子改名**（`SalesOrdersService.update()`）：先 `SELECT ... FOR UPDATE` 锁本单行
  （与生产单/采购单建单同一把锁，把并发建单压到改名提交之后）→ 扫 38 张表 →
  改别的单上的 `reorder_from_order_no` → 重写本单全部版本快照的 `order_no` →
  **残留校验**（任一表还有旧号即 409 整事务回滚）→ 最后改源头那一格。
- **影响面预览**（新只读接口 `GET /sales-orders/:id/order-no-impact?order_no=新号`）：
  返回逐表条数、本单历史版本快照数、别的单上的返单来源数、以及新号是否已被占用
  （**预检不带 `deletedAt` 过滤** —— 唯一索引跨软删行，软删单占的号也不能用）。
  预览与执行共用同一份登记表，所以"说会改的表"与"真改了的表"不可能不一致。
- **守卫**：改号必填原因（文案带旧号→新号）；空串**不当作"不动"**（DTO 用 `@IsNotEmpty()`，
  不加 `EmptyStringToUndefined`）；新号被占用 409 `ORDER_NO_CONFLICT`（并发抢号由 `P2002` 兜底，
  且**只在改号时**才把它翻译成这个码，否则会把版本号并发冲突说成"订单号已存在"）；
  已关闭单的例外从"只有货号"扩到"货号/订单号"，且**只能单独改**（带上别的字段仍拒绝）。
- **`order_no` 不进 `coreFields` 锁**：那份清单锁的是"会改变下游事实/金额"的字段，
  改号不动任何一张单的数量与金额，所以已有 BOM/采购/生产的已确认单**直接可改**，不要求先回退 ——
  否则用户最常见的场景（下单后才发现号写错）仍然走不通。
- **审计两条**：既有 `sales_order.update`（带 `previous_order_no`）另加
  `sales_order.rename_order_no`（`from` / `to` / `reason` / 逐表 `targets` / `total` /
  `version_snapshots` / `reorder_references`）。`audit_events.order_no` 列**不回写**。
- **前端**：编辑页订单号那格给出"改这里会同步改下游全部单据"的贴边提示；保存时若号变了，
  先拉影响面弹确认框（`ActionDialog` 的 `info` 格显示"将同步更新 2 类下游单据共 4 条
  （采购单 3、BOM 表 1），另有历史版本快照 1 条、返单来源 1 条"），原因必填；
  确认后才 PATCH，并把 `order_no` 与 `reason` 一起发出去。失败时**弹窗不关闭**，错误留在弹窗里
  （用户填的 37 格不会白填）。

### 5. 值得记下来的判断

1. **"支持编辑和修改"这句话里，真问题是静默丢弃。** 那一格本来就是可编辑的，
   坏在保存时被删掉且不报错。修它不只是"放开一格"，而是要把**它牵动的整条链**一起放开 ——
   放开一格而不改链，就是制造"一半新号一半旧号"。
2. **联动清单必须是"不许漏"的清单，而不是"我想到的那几张"。** 38 张表靠人工回忆必然漏，
   所以清单配了一条**与 schema 的集合相等守卫**：漏一个 → 测试红。这与数据库唯一索引
   不靠"代码里记得查重"是同一个思路。
3. **改号要按值扫，不需要按语义证明。** 全局唯一索引让"值相等"本身就能推出"指向同一张单"，
   于是 38 张表的差异只剩下"别漏"。这条性质值得写在代码里 —— 否则下一个人会以为
   得逐表证明"这一列到底是销售单号还是采购单号"。
4. **"任何时候都能改"意味着不能把它塞进核心字段锁。** 核心字段锁的目的是"改了要重算下游"，
   而改号是"下游跟着改名"，金额一分不变。把这两件事混在一起，会让老板最常遇到的场景
   （下单后发现号写错）必须先回退 BOM/采购/生产 —— 那是把修错号的代价抬到不可用。
5. **版本快照跟改、审计不回写**，两者看似矛盾，判据是"这一列记的是现在指向谁，还是当时发生了什么"。
   版本快照是"这一单"的历史（回看时不该看到一个已作废的号）；审计是事件流，
   旧号必须留在事件里，改名事件里的 `from` 就是它的落点。
6. **并发窗口不假装被消除。** 锁本单行能挡住"会锁同一行"的下游建单路径，残留校验能挡住其余
   绝大多数（提交前可见的），极端时序下仍可能有一行带旧号落库。取舍写进了设计文档 §五.3：
   **宁可让改号失败重试，也不留下半个改名**；要绝对消除得靠数据库触发器或给每张下游表加
   "改名序号"列，代价与收益不成比例。
7. **JSON 快照里的旧号不追改，理由要能被 grep 证明。** 五处 JSON 里嵌着订单号，
   其中四处（BOM/薪资快照）**只写不读** —— 全仓库 12 处引用全是写入与类型声明，
   没有任何一处 `select` 回显。所以它们是"存档证据"，与审计同性质；
   唯一例外是本单的版本快照，那个跟改（用户拍板）。

新增测试里最该记住的两条：

- **`renameSalesOrderNo` 的假事务桩是"按委托名泛型"的**：不逐个模型手写 38 份桩

  它挡住"为了改号而把 `order_no` 无脑发出去"这种改法（那会让一次普通编辑也去动全链）。

### 7. 已知边界（写进设计文档，不在本批修）

- **存量错号不批量迁移**：没有迁移文件，历史里写错的号由业务在界面上逐张改
  （批量改哪张、改成什么，只有业务知道）。上线后的核查 SQL 在 `PENDING-USER-COMMITS.md`。
- **按旧号反查要走审计**：`audit_events` 里 `action = 'sales_order.rename_order_no'` 的事件
  （details 带 `from` / `to` / 逐表条数）。用户选了"不加曾用单号列"，这是那个选择的代价。
- **`test:api` / 集成 / e2e 仍跑不了**（本机没有 PostgreSQL 与 API 实例）；
  HTTP 契约测试里的新路由与 PATCH `order_no` 断言按源码口径改好了，但**没在真实服务上跑过**。
- 顺带修的一处口径不一致：`sales-orders-contract.test.cjs` 里"PATCH 的 DTO 比创建窄
  （`order_no`/`customer_id` 只读）"这条断言按新口径拆成两条 ——
  `order_no` 放行（未知 id 落到 404）、`customer_id` 仍被白名单拦下。
