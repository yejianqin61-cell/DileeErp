### 第十七轮（凭证重新生成 + 银行存款引用银行账户 + 确认页只列未收未付 + 两处台账导出）

用户五条：①「现在要支持凭证重新生成。」②「凭证中的那个会计科目的银行存款，要引用的是具体的
银行账户」③「确认应付，确认应收，表单里如果是已付或者已收款，那个条目就不要出现在那里了！」
④「冲销是什么意思？」⑤「确认应收，确认应付，两处表单。要支持导出excel。支持按照已付未付，
已收未收。还有按照时间范围筛选。」设计见
`docs/design/finance-voucher-regenerate-and-ledger-export-2026-09-16.md`。

- **凭证重新生成**：`POST /finance/vouchers/:id/regenerate`。门禁四条 —— 只对草稿开放
  （已过账是账务事实，只能红冲）、红冲件不能重算（它的内容由被红冲那张决定）、
  来源流水必须存在、来源流水必须未冲销。实现是**事务内 `FOR UPDATE` 复查状态 → 删掉全部分录
  → 按当前流水重算重建**，并把凭证头的日期/会计期间/摘要/币种/借贷合计一起刷新
  （日期跟着流水走，否则「7 月的流水重算成 8 月的凭证」会落进错误期间）；审计 `voucher.regenerate`
  记 before/after（重新生成会覆盖财务手工改过的分录，审计里必须看得出覆盖前是什么）。
  为什么删旧分录而不是逐条 diff：分录条数会随收支项目/资金科目变化，逐条改会留下孤儿行。
- **银行存款 → 引用具体银行账户**：`voucher_lines` 新增 `bank_id`（可空、`ON DELETE SET NULL`、
  建索引），取值优先级 = 流水上的 `bank_id`（财务确认/收付款时从银行池选的账户）→ 结算方式含
  「现金」→ 无账户的 `银行存款`。三条约束：①`subject_key` **仍是「银行存款」**，账户是
  **引用**（`bank_id`，给报表 join）+ **名称快照**（`subject_label` = `银行存款—农业银行5706`，
  给账户改名/停用后凭证纸仍可读）两层，科目保持可汇总；②快照格式与收支流水「结算方式」列同口径；
  ③红冲分录带着同一 `bank_id` 一起红。
- **确认页默认只列未付/未收**：确认即记账（第十三/十五轮），一条应付确认后钱已经从所选账户出去，
  留在「确认应付」里没有任何可做的事。所以那是**待办清单** → 默认收窄到未付/未收；
  但用户第⑤条又要「按已付未付筛选」，两者不矛盾：**默认收窄，不是删除**，
  筛选器可切「已付/已收」与「全部」。
- **两处台账的筛选与导出**：新增 `GET /finance/payable-entries.xlsx`（应付台账 17 列）与
  `GET /finance/receivable-sources.xlsx`（应收台账 16 列）。筛选三条件与搜索框是**与关系**：
  付款情况（`未付（n）/ 已付（n）/ 全部（n）`，括号里是当前筛选后的实时条数，默认未付/未收）、
  日期范围（**应付 = 确认日期** `confirmation_date`；**应收 = 出库日期** `created_at`，
  标签按此区分不写含糊的「日期」）、关键字。**导出是所见即所得**：前端把当前
  `payment/from/to/q` 原样带给后端 —— 表格是前端分页的，若导出走后端全量，用户会拿到一份
  和屏幕对不上的文件。金额与数量是 **Excel 数值类型**（否则财务在 Excel 里 `SUM` 得 0）；
  **不做合计行**（多币种同表，跨币种相加没有意义），含两种以上币种时在表尾写一行
  「本表含 CNY / USD 共 2 种币种，金额列不做合计」。
- **「已付/未付」的口径（本轮唯一需要业务确认的语义决定）**：未付/未收 = `draft`；
  已付/已收 = `confirmed`（确认即记账）；部分付款/已付清 = `partially_paid`/`paid`
  （来自收付款核销）；已冲销/已作废/已取消/已关闭**既不算未付也不算已付，只在「全部」里出现**。
  界面上没有第二步付款，若把「已付」定义成「有付款单核销」，这个筛选项永远是空的。
- 新增两份**同口径实现**：后端 `apps/api/src/modules/finance/ledger-filter.ts`（给接口，
  接受任意客户端直接调 `.xlsx`）与前端 `apps/web/lib/finance-ledger-filter.ts`（给界面，
  要立刻响应、要出计数），两个文件顶部互相点名「改一处必须改另一处」，前端那份有 lib 单测钉住。
- 抽出 `sendWorkbook()`（原 `finance-report.controller.ts` 里的内联下载头）供三条导出路由共用。

### 第十六轮（财务表格一屏看全，不用左右拖动）

用户一句：「财务部分的表单，我希望能一次性在页面上展示全貌，不需要左右拖动条来拖动。你有什么好办法吗」
（屏幕条件：1600 / 1920）。设计、实测数据与被否掉的做法见
`docs/design/finance-table-fits-on-screen-2026-09-16.md`。

排查结论：**不是列太多，而是单元格不换行**。表格可用宽度被 `.content-area { max-width: 1440px }`
卡在 **1376px**（1920 屏也一样）；而 `white-space: nowrap` 让每个单元格的 min-content 等于它的
完整文本宽度 —— 「香港迪礼国际贸易有限公司」这种长客户名会把整列撑宽、把整张表顶出容器。
实测证据：只把 `th` 改成可换行，列宽**一点没变**（min-content 仍 1304px）；`td` 也放开后立刻降到 800px。

改前实测（真实 Chromium + 本项目 CSS + 真实列头，静态复现页；本机没有 PostgreSQL）：

| 表 | 列数 | 1366 | 1440 | 1600 | 1920 |
| --- | --- | --- | --- | --- | --- |
| 应付对账 | 17 | 溢出 227px | 153px | ✅ | ✅ |
| 应收对账 | 16 | 108px | 34px | ✅ | ✅ |
| 销售对账明细表（老报表） | 23 | 624px | 550px | 390px | 318px |
| 工资台账 | 19 | 455px | 381px | 221px | 149px |
| 应付台账 / 银行账户池 | 11 | ✅ | ✅ | ✅ | ✅ |

- **内容区上限 1440 → 1920px**：1920 屏表格可用宽度 1376 → 1624px。保留上限而不是 `max-width: none`
  （超宽屏上纯文本页行长会失控）。
- **紧凑**：内边距 14 → 8px、内容 13 → 12px、行高 44 → 38px、数字 `tabular-nums`，每列省约 12px。
- **表头与单元格都允许换行**（关键那条）：中文可逐字断行；表格放得下时不折行，放不下才折行 ——
  折行是「不横向滚动」的必然取舍。
- **金额不被折断**：`money()` 里金额与币种之间改用**不换行空格**（U+00A0）。放开换行后普通空格会把
  「500.0000」与「USD」拆到两行；数字本身没有断行机会，因此不需要逐格加类。
- **没有采用**：`table-layout: fixed` + 逐列宽度（宽度之和超容器时表格反而变宽，等于没解决）；
  币种移到表头（应收/应付是多币种同表，格内去掉会看错钱）；逐列省略号截断（与「看全貌」相反）；
  列显示配置（多一层交互且要业务先定默认列集，本轮字段一个没动）。
- **规则全部限定在 `.finance-page`**：其它模块表格各自调过密度（领料单 11px、采购工作台固定列宽），
  全站 `.data-table` 仍是原来的 nowrap。
- 新增源码守卫 `apps/web/lib/finance-table-width.test.mjs`（5 条）：把内容区上限、紧凑尺寸、
  th/td 可换行、`money()` 不换行空格、规则限定在财务页钉住 —— 这些是排版约束，类型检查与组件测试
  都发现不了，改回去最宽的表就会重新出现滚动条。

### 第十五轮（财务文案精简 + 应收/应付「勾选批量确认」）

用户三条：①「财务部分，这种说明性的语句，全部去掉。比如说每次成品出库过账生成一条应收来源；
一个订单分批出库就是多条，双击查看全部字段」；②「应付管理，原料入库条目这边，已接收的条目，
就不要在这边的表单出现了」；③「确认应付这边，就不要再搞那么多繁琐的步骤了。不要又是登记付款
又是确认应付了。直接就是支持勾选，批量确认」。第三条做完后追问应收侧，用户选择
「应收侧也改成勾选 + 批量确认」—— 于是**两侧对称**都改。设计与决策见
`docs/design/finance-batch-confirm-and-copy-trim-2026-09-16.md`。

排查结论：**「确认应收/应付」在第十三轮改成「确认即记账」之后，页面里还留着原来的
「登记收款/付款 → 过账核销」，而过账会再写一笔流水 —— 同一个账户被同一笔款/同一笔应付
多算一次**（应收多进一次钱、应付多扣一次钱）。所以用户说的「繁琐」背后是重复记账，不只是操作多。
另一头：`原料入库条目` / `外加工签收` 是**待接收工作清单**，却把已接收的行也列在里面
（只是换了按钮文案），财务得自己认哪些已经处理过。

- **说明句换成数据，而不是整行删掉**（D1）：删的是「解释系统怎么运作 / 该怎么用」的句子
  —— 页面与子栏目的 `description`（23 条）、`panel-heading` 说明句、独立说明段、
  `EmptyState` / 详情弹窗的 `description` 与 `sections[].note`、字段 label 里的解释性括注、
  `type: "info"` 确认文案里的说明句（`将确认应收 AR-001（120 USD）…确认不可逆。` → `确认应收 AR-001：120.0000 USD`）。
  **保留**数据（「共 N 条」「待接收 3 条 · 已接收 1 条」「合计 800.0000 CNY」）、校验规则括注、
  状态/按钮/表头/错误提示。理由见设计文档第 1 节：两类文字混在一起，全删会把数据也带走。
- **已接收的来源从两个「待接收」列表移出**（D2）：判定 `!payable_entry && status === "pending_finance"`
  （两个条件都要 —— 历史数据里有「状态停在 pending_finance 但已有应付单」的行）；用户只点名了原料入库，
  外加工签收是同一类清单，**同规则**；行移出但总数不隐藏，标题旁显示「待接收 N 条 · 已接收 M 条」。
- **两侧的「确认」都改成勾选 + 批量确认**（D3）：表格首列勾选框（**只有草稿行有**）、表头全选、
  工具条「已选 N 条」+「批量确认（N 条）」；弹窗只问银行账户与收支项目（整批共用）。
  行内单条确认保留（同一条路，只是快捷方式）。**移除**：行内「登记收款 / 登记付款」、
  收款/付款子表与它们的折叠开关、以及应收侧那份额外的「按订单批量确认」表 ——
  勾选 + 筛选能精确到某张订单，两套批量机制正是用户嫌的「又是这个又是那个」。
- **新增两条批量确认接口**：`POST /finance/payable-entries/batch-confirm` 与
  `POST /finance/receivable-sources/batch-confirm`（共用 `BatchConfirmDto`：
  `{ ids[], bank_id?, cash_flow_item_id? }`）。整批一个账户 + 一个项目，
  **每条各写一条流水**（与既有 `batchConfirmByOrder` 同口径 —— 每条都有自己的单号，
  合并成一条就追不回是哪批货/哪批料的钱）；只确认 `status = draft`，已确认/已取消
  （应付侧还有来源作废）的计入 `skipped_count` 并点名（跳过而不是整批失败）；
  一条都不可确认时 422 `NO_DRAFT_RECEIVABLES` / `NO_DRAFT_PAYABLES`，空 `ids` 422
  `*_IDS_REQUIRED`；银行/项目**在事务之前**校验；行锁之下状态若被并发改动，整批回滚
  （`*_CONFIRM_CONFLICT`）—— 宁可拒绝也不要「界面说确认了、库里没确认」；
  合计**按币种分组**返回（`amounts`），`bank_missing` 仍驱动错误态警告。
- **两侧台账都去掉「已收/已付、未收/未付」四列**（D4）：这些数来自收付款单核销，
  而本轮把收付款流程从确认页去掉了；留着只会让每条已确认的条目显示「未收/未付 = 全额」，
  与「钱已经进出账户」自相矛盾，且永远不再变化。核销明细仍在双击后的详情里，数据没丢。
- **收付款的接口与数据一个都没删**（D5）：`/finance/customer-payments`、`/finance/supplier-payments`
  全套、`*_payment_allocations`、对账单的 `paymentAmountSnapshot`、
  `receivable-sources/batch-confirm-by-order` 全部保留（历史核销、采购侧通知、报表仍依赖），
  去掉的只是两个确认页上的入口。**本轮不改 schema，因此没有新迁移。**

  `docs/task/0914-finance-module-refactor/11-batch-confirm-and-copy-trim.md`（README 补行 11）、
  更新 `02-receivable-workspace.md` / `03-payable-workspace.md` / `10-bank-balance-and-transfer.md`
  与 `bank-balance-and-transfer-2026-09-16.md`；并把四份「页面上写明了 X」的设计文档改成
  「X 只由文档承载」。

### 第十四轮（工资付款的发放银行 + 原料出库的仓库确认 + 领料单详情弹窗）

用户三条：①「工资支付那边也是全部要加上银行账户，因为发工资都是要用银行账户发放的工资」；
②「生产领料单，条目，双击条目，弹出居中悬浮窗口，展示本条领料单所有的领用的物料」；
③「生产领料单已确认，仓库那边不能直接原料出库，要有一个待确认的地方，确认过后才能原料出库，
进行原料仓储的流转。因此仓库页面，再多一个待出库通知的地方」。
设计与决策 D1–D9 见 `docs/design/salary-bank-and-material-outbound-confirm-2026-09-16.md`。

排查结论：**工资付款根本没有银行账户列**（只有 `paymentMethod`/`bankReference`），过账写的收支流水
`bank_id` 为空 —— 按第十三轮 D2「没指定账户的流水不进余额」的口径，工资这笔支出**系统性**地不进
任何账户余额，银行余额与真实银行账永久差一笔工资（这不是历史数据问题，是活代码）；**领料单草稿
可以直接过账**，过账即写 `inventoryFact` —— 也就是生产单方面扣掉了仓库的库存，仓库连一张单都没看到，
「仓库确认出库」这一步在系统里根本不存在；领料单只有一张「N 项 / 合计 X」的汇总行，想知道领了哪些料
只能导出 Excel。

- **工资付款的发放银行是必填**（D1）：与收付款/对账共用 `requireActiveBank`（存在 + 未删除 + **未停用**）。
  `payLedger`（「生成工资应付 → 确认应付 → 建付款 → 核销过账」四步编排）把银行校验收在**第一步** ——
  走到一半才发现银行非法会留下一张刚生成的工资应付要人工清理（D2）。`post` 过账前再要求一次，
  并把 `bankId` 写进收支流水，工资这才真的动银行余额。编辑草稿允许 `null` 清空、`undefined` 不改。
- **原料出库改两段式**（D3）：`draft` →**生产「确认提交」**→ `pending_outbound`（待仓库出库）
  →**仓库「确认出库」**→ `posted`（这一步才写 `inventoryFact`）。核心不变式：**只有 `pending_outbound`
  能被出库**，草稿直接过账一律 422 并在错误信息里写明「请先由生产确认提交」。补料单同规则（D7）——
  它同样是原料出库，只让领料单走确认等于给仓库留了个后门。
- **不另建「出库通知」表**（D4）：「待出库通知」= `raw_material_movements where status = 'pending_outbound'`。
  这张单本身就是通知（单号/生产单/订单号/物料明细/数量全在里面），另建影子表只会让两张表的状态互相漂移。
- **提交时就校验库存，出库时再校验一次**（D5）：前者让生产**当场**知道这批料领不出来，
  后者防两次之间库存被别的单据改变。库存事实只在出库那一步写。
- **撤回提交 = `pending_outbound` → `draft`**（D6）：这时还没有任何库存事实，改状态即可，不写冲抵事实；
  没有这一步的话生产填错数量就再也改不了，只能等仓库照错单出库。已过账回退草稿仍是原来的冲抵逻辑。
- **`submittedAt` 单独一列**（D8）：`updatedAt` 会被任何一次写入改动，而通知要显示的是「这张单什么时候
  交过来的」。待出库清单按提交时间**正序**（D9），仓库按先来后到处理。
- **双击领料单条目弹居中悬浮窗**：复用全站既有的 `RecordDetailDialog`，展示单据头字段 + 「领用物料」明细表
  （物料编码 / 名称 / 规格型号 / 单位 / 数量 / 备注），数据取 `GET /production/material-movements/:id`
  （列表行只有 `materialId`，物料主数据必须走详情接口）。生产单详情面板与「领料单 / 补料单」列表页都有。
- **仓库页新增「待出库通知」面板**：列单据号 / 类型 / 生产单号 / 订单号 / 业务日期 / 物料明细 / 明细数 /
  提交时间，行内「确认出库」走 `post` 或 `post-replenishment`（按单据类型分流）；该接口单独 `catch` 兜底，
  不可用时不会把整页（含待入库通知）一起打空。

### 第十三轮（银行余额管理：期初金额 + 账户互转，以及「确认应收/应付即记账」）

用户五条要求：① 财务新开「银行余额互转」栏目，能在银行池的账户之间互相转账（表单要本方账户 /
本方币种 / 对方账户 / 对方币种），并允许设置银行**初金额**；② 应收应付一旦确认，金额就要
**进入或转出对应的账户**；③ 应收应付所有表单都要能填**银行账户**；④ 都要能填**收支项目**；
⑤ 因此收支明细表才能按收支项目正确统计。设计与决策 D1–D11 见
`docs/design/bank-balance-and-transfer-2026-09-16.md`，落地清单见
`docs/task/0914-finance-module-refactor/10-bank-balance-and-transfer.md`。

排查结论（为什么「余额」此前根本算不出来）：`banks` 表没有余额概念；收支流水的
`settlement_account_id` 指向的是**结算账户字典**（老表「结算方式」的文本 `农业银行5706`），与
`banks` 没有任何外键关系，`matchSettlementAccount()` 只能按账号去**猜**；确认应收/应付只改状态、
完全不动钱；收支项目只有「过账」那一刻能临时选，单据本身没有这一列；收支明细表照抄老表 6 列，
**没有项目列**，汇总表说「货款 5000」明细里根本对不上号；账户之间调钱只能录两条手工流水，
把收支口径污染成「一笔收入 + 一笔支出」。

- **余额是一个公式，不是一列数**：`余额 = 期初 + 生效收入 − 生效支出 + 转入 − 转出`。
  只有期初是存下来的（`banks.opening_balance`），其余全部聚合。存一个「当前余额」列会在每次动账时
  都要记得改，漏改一次就永久对不上。口径只有一处实现：新增纯函数模块 `bank-balance.domain.ts`
  （`bankBalance` / `transferAmounts` / `transferEffect`），`BankService.balances()` 只负责取数
  （三个查询：一次账户、一次 `groupBy(bankId,direction)`、一次全部生效互转，不做 N+1）。
- **流水落到具体账户**：`cash_flow_entries.bank_id`（可空，SET NULL）+ `(bank_id,status)` 索引；
  手工流水、收付款过账、确认应收/应付自动生成的流水都带它。没指定账户的流水仍然是收支事实
  （报表里有），但**不进任何账户余额** —— 这不是漏算，`bank_missing` 会让界面明确提示。
- **银行余额互转**：新表 `bank_transfers`（`transfer_no` 唯一、`from/to_bank_id` + `from/to_currency`
  + `from/to_amount` + `exchange_rate` + `status` + `reversal_reason`），新接口
  `GET/POST /finance/bank-transfers`、`POST /:id/reverse`，新页面 `/finance/bank-transfers`。
  四条硬规则：两个账户必须存在+未删除+**未启用**、不能自己转给自己、币种必须与所选账户一致、
  **同币种两边金额必须相等**（差额没有科目承载）；跨币种必须显式填到账数，汇率按 `to/from` 记 6 位快照。
  互转**不写收支流水**（写成 A 支出 + B 收入会让收支汇总表凭空多一笔收入与一笔支出），
  只在余额里体现。余额不足**只提示不拦截**（期初可能还没录、银行到账有时间差），
  响应带 `source_balance_before/after` 与 `insufficient_balance`。
- **确认即记账，且「确认」与「记账」同生共死**：`recordConfirmation()` 把本次确认金额记进收支流水
  （应收=收入、应付=支出），落到对账单的银行账户上。银行/项目的校验**在事务之前**做 ——
  等事务提交完才发现银行非法，应收已经确认、流水却没写，比直接拒绝糟得多。
  **三条确认入口都记账**（D5b）：按对账单一键确认（一条按对账单汇总的流水）、逐条确认（每条一条）、
  批量确认（每条一条，批量没有单张单据可挂，逐条才追得回去）。
  （2026-09-16 起界面上的批量入口是**勾选批量确认**，原来的「按订单批量确认」表已下线，
  接口 `batch-confirm-by-order` 保留；见第十五轮。）
  金额是**累加**不是覆盖：先按对账确认 100、再逐条确认新来的 50，回头再点一次对账确认，
  覆盖会把对账那条改成 50、总额凭空少 100；累加则只会单调增长。日期保留**首次确认日**
  （一条累计流水只有一个日期），银行与项目取最新一次。
- **收支项目在**建单时**就落库**：`customer_payments` / `supplier_payments` /
  `receivable_reconciliations` / `supplier_payable_reconciliations` 各加 `cash_flow_item_id`，
  建单时校验（不存在/已停用 → 422，不静默换成别的项目）；过账/确认时优先级为
  「过账参数 > 单据上存的 > 按业务来源自动归类（原料入库→原材料 成本、外加工签收→成品外加工费、
  客户收款→货款）」。
- **收支明细表补两列**（用户第 5 条）：从老表 6 列扩到 **8 列**，新增「收支项目」与「银行账户」。
  这是**有意偏离**老表版式：没有项目列，汇总表按项目分类的数字在明细里对不上号。
  项目缺失时留**空单元格**而不是横杠（空单元格在 Excel 里能筛选能求和，横杠会被当文本混进数值列）。

### 第十二轮（应收侧对齐第十一轮的四条：待对账逐条、覆盖点名、产品规格型号、收款收纳）

用户看过第十一轮后追加：「帮我把应收侧的对应的问题也都改了」。应收侧的结构与应付侧不同 ——
**没有「来源 → 应付」两步**，成品出库过账直接生成 `receivable_sources` 草稿，财务的动作是「确认应收」，
因此 ① 落成「逐条列出待对账条目」而不是「推进来源状态」，②③④ 一一对应。
设计与对照表见 `docs/design/payable-pending-reconciliation-2026-09-16.md` 第 5 节。

- **② 覆盖口径**：`receivable.domain.ts` 新增 `receivableInReconciliationScope` /
  `coveringReceivableReconciliation` —— 范围是「**订单号填了才收窄到该订单，否则按客户** + 币种 + 期间
  （左闭右开，右端含结束日整天）」，与 `ReconciliationService.scopeWhere/entries/snapshot/confirmReceivables`
  完全同口径；`ReceivableService.list()` 给每条应收标出覆盖它的对账单（`reconciliation`，按
  `customerId OR orderNo` 取回涉及的对账单，两种建单方式都不漏）。
- **① 待创建对账的条目改逐条**：一行一条草稿应收（客户 / 应收来源 / 待对账月份 / 订单号 / 出库单 /
  产品 / 规格型号 / 应收金额 / 出库日期），行内「创建对账」按该条的客户 + 月份建单；
  标题右侧给出「N 条 / 合计 X」。已被对账单覆盖的草稿移出并**点名去向**
  （`receivable-covered-drafts`：`AR-009（REC-001，可在对账单行内一键确认）`）。
- **③ 对账明细补产品与规格型号**：`ReconciliationService` 新增 `flow`
  （`entry_count / draft_count / draft_amount / can_confirm_receivables / order_nos / product_names /
  product_specifications`），`list()` 与 `get()` 都返回（一次 OR 查询 + 内存过滤，不做 N+1）；
  `entries()` 补 `product_name / product_specification`（出库快照口径，与「成品出库条目」一致）。
  对账列表新增「订单号 / 产品 / 规格型号 / 待确认应收」四列，详情弹窗字段区与「纳入对账的应收条目」
  明细表都加上产品与规格型号。
- **④ 收款可折叠收纳**：`useCollapsiblePanel("receivable-payments")`；开关放在 `<h2>收款</h2>` **外面**
  （标题的可访问名保持「收款」，`panel("收款")` 类定位继续有效），收起时说明 + 筛选条 + 表格一起隐藏。
- **顺带对齐**：「一键确认应收」原来只要状态是 matched/resolved 就出现（范围没有草稿时点了空转 0 条），
  现在与应付侧一致，只在 `flow.can_confirm_receivables` 时出现，否则给「范围内没有待确认应收」；
  详情弹窗里的按钮同样改看 `details.can_confirm_receivables`。

### 第十一轮（应付：接收 → 对账的可见性、对账明细的物料规格、付款收纳）

用户四条：① 「原料入库条目点击接受应付，为什么没有在待创建对账中看见这条条目」；
② 「待创建对账中，对某条条目创建对账单之后，就不该继续展示这条条目了」；
③ 「已创建对账单，双击某个条目，弹出的表单还应当显示这个订单的物料名称和规格型号」；
④ 「确认应付中的付款部分，支持折叠收纳」。设计与根因见
`docs/design/payable-pending-reconciliation-2026-09-16.md`。

- **① 的根因是三件事叠加**：(a) 接收应付**从不推进来源状态** —— 全库没有一处把 `payable_sources.status`
  从 `pending_finance` 改掉，于是「原料入库条目」永远显示「接收应付」、流转看板①永远不下降
  （`finance-status.ts` 里的 `received → 已接收` 一直是死代码）；(b) 重复接收是**静默幂等**
  （命中已存在的条目就直接返回旧的，界面照样提示「已接收…」）—— 这正是「点了没反应」的来源；
  (c) 待创建对账是「供应商 + 月份」**汇总行**，新接收的那条只让计数 +1，用户要看的**那一条**不在表里。
- 因此：`createFromSource()` 在事务内把来源置为 `received`（`status != voided`，幂等，`markSourceReceived`）；
  两条来源列表（原料入库 / 外加工签收）都带出 `payable_entry: { id, payableNo, status }`；界面据此
  显示「已接收 → 应付单 AP-xxx（状态）」，未接收才给按钮，历史数据（状态没改但条目已存在）靠关联兜住。
- **② 的根因**：前端只看 `status === "draft"`，不知道草稿是否已落进某张对账单；而「哪些应付属于这张
  对账」由服务端的**供应商 + 币种 + 期间（可收窄订单/采购单）**决定，前端拿不到 `purchaseOrderId`。
  新增纯函数 `payableInReconciliationScope` / `coveringPayableReconciliation` 作为**唯一定义**
  （对账服务的 where 与内存过滤、应付台账的覆盖判断三处共用），`SupplierPayableService.list()` 给每条
  应付标出 `reconciliation: { id, reconciliation_no, status, period_start, period_end } | null`。
- **待创建对账从「分组」改成逐条**：一行一条草稿（供应商/应付单号/待对账月份/来源批次/订单号/采购单号/
  物料/规格型号/金额/确认日期），行内「创建对账」仍按该条的供应商 + 月份建单。已被覆盖的草稿不再出现在
  这张表，但**必须点名**：`另有 N 条草稿已纳入对账单、不在此重复对账：AP-009（APREC-001，可在对账单
  行内一键确认）` —— 财务最怕「账不见了」，不是「表长了」。
- **③**：`flow` 新增 `material_specifications`（与 `material_names` 同序去重），`details.payable_entries[]`
  新增 `material_specification`，两处查询补 `material.specificationModel` 并保留 `materialSnapshot` 兜底；
  `get()` 也返回 `flow`（列表与详情同一份摘要口径）。详情弹窗字段区加「采购物料 / 规格型号」，
  「纳入对账的应付条目」明细表加「规格型号」列，对账列表也加一列。
- **④**：`useCollapsiblePanel("payable-payments")` + 新增 `.subsection-heading` 样式；**开关按钮放在
  `<h3>` 外面** —— 塞进标题会让可访问名变成「付款 收起」，`getByRole("heading", { name: "付款" })`
  这类定位（含既有用例）会直接失准。收起时说明与表格一并隐藏，选择记本机。

### 第十轮（凭证一键导出 PNG）

用户看过第九轮方案后追加：「还要一键导出 PNG」。**不引新依赖**：
`voucherSvg()` 把凭证重新组版成 SVG（纯函数、可单测）→ `Blob(svg)` → `new Image()` →
`canvas.drawImage` → `canvas.toBlob('image/png')` → `<a download>`，2 倍分辨率出图。

- 为什么不用 html2canvas / html-to-image：两者都要新增前端依赖（本机也无法假设能联网安装），
  且靠遍历 DOM + 内联样式「猜」版式；凭证纸是固定表格，SVG 更可控更清晰。同源 `blob:` 不污染 canvas，
  不引外部字体/图片，离线也能出图；
- 两个渲染视图分工：HTML 凭证纸服务打印/另存 PDF，SVG 服务出 PNG，用同一批字段；
- 失败给**可执行**原因：canvas 不可用时抛「请改用『打印 / 另存 PDF』」并 toast，不静默、不丢英文异常；
- 细节：文件名安全化（`/:*?"<>|` 与空格 → `-`）、XML 转义（摘要含 `&<>"'` 不破坏 SVG）、
  单元格按 CJK 1em / ASCII 0.55em 估算裁剪加省略号、画布高度随分录行数增长；
- 新增 `lib/voucher-image.ts`（9 条纯逻辑用例）与凭证纸上的「导出 PNG」按钮（组件 2 条接线用例）。

### 第九轮（凭证管理：从收支流水生成记账凭证）

用户两条：① 工资台账/工资付款改成悬浮居中窗口（见第八轮）；② 「凭证管理，从收支流水中 fetch，
每条收支条目都可以生成对应的条目。这个凭证怎么做才好呢？做一个图片返回来？」
设计见 `docs/design/accounting-vouchers-2026-09-15.md`。

- **答「做一个图片返回来？」：不做图片**。图片不可搜索、不可复制（财务要复制凭证号、核对金额）、
  打印会糊、改一个字就要重生成，服务端出图还要引入 canvas/无头浏览器。凭证的本质是**结构化分录**：
  因此落地的是「`vouchers` + `voucher_lines` 记录 + HTML 记账凭证纸 + 浏览器打印/另存 PDF」，
  真需要 PNG 时在打印视图上套一层截图即可，不动数据模型。页面也把这条口径写出来了。
- **迁移 `20260915170000_accounting_vouchers`**：两张新表；`vouchers` 上
  `@@unique([source_type, source_id])` 是**幂等根**（一条来源只能有一张凭证，重复点生成就是返回原凭证）；
  分录 `ON DELETE CASCADE` 随凭证删、来源流水 `ON DELETE SET NULL`（流水被删凭证仍留得住）；
  科目名做**快照** `subject_label`（字典改名后历史凭证不变）。金额恒正、方向由 `direction` 决定。
- **生成规则**：收入=借 银行存款/库存现金、贷 收支项目；支出=借 收支项目、贷 银行存款/库存现金；
  资金科目按结算方式/账户名里是否含「现金」区分；摘要 `对方 · 项目（备注）`；
  凭证号 `记-YYYYMM-####` 取同期间最大值 +1；**已冲销的流水不生成凭证**（钱没真的动过）。
- **科目从哪来**（本期口径，可替换）：库里没有正式科目表，于是损益/成本类科目直接用**收支项目字典**
  （财务本来就按这张表分类），资金科目两选一；将来接正式科目表只改 `voucher.domain.ts` 的取值来源，
  模型/页面/打印都不用动。草稿还允许**整组分录人工编辑**（改科目名与金额），编辑后必须借=贷。
- **状态机**：生成 → draft（可编辑/删除/过账）→ posted（不可改不可删，只能红冲）→ reversed；
  红冲 = 原凭证标 reversed + **同事务**生成一张借/贷对调的红字凭证并直接过账
  （否则会出现「原凭证已红冲、对冲凭证未过账」的空档）。
- **接口**：`GET /finance/vouchers`、`GET /:id`、`POST /from-cash-flow/:entryId`、`PATCH /:id`、
  `POST /:id/post`、`POST /:id/reverse`、`DELETE /:id`（仅草稿软删除）。
- **页面**（`/finance/voucher` 重写，替换原占位页）：上半张表是**收支流水**（可筛「未生成/已生成」），
  每条流水行内「生成凭证」；下半张表是**记账凭证**，行内 凭证纸/编辑/过账/删除/红冲；
  凭证纸对话框按记账凭证版式排版（凭证号、期间、币种、来源、摘要、科目、借贷金额、合计、签字栏），
  「打印 / 另存 PDF」调 `window.print()`。打印 CSS 用 `visibility` 让祖先隐藏、凭证纸重新可见，
  并把对话框在打印时改回普通文档流（否则 `position: fixed` 会被裁成一页的一部分）。

    匹配到**结算账户字典**（老表 `农业银行5706` / `中国银行（美元）7624`），匹配不上留空
    （银行来自 `banks` 表、结算账户来自字典，没有外键关系，不造假关联）；对方名称不再退化成 UUID；
  - 修复三：新增 `autoReverseFromPayment`，收付款冲销时把对应流水置为 `reversed`（原先只写过账不处理冲销，
    收支汇总会比银行账多一笔）；
  - 仍未自动纳管的部分（房租水电差旅备用金、退款实际出账、退税利息等）如实写进设计文档，
    需要新模块（费用/退款单）才能自动进流水。

### 第二轮（用户追加要求：入口页 + 行内付款）

用户看完第一轮后追加两条：① 工资台账和工资付款做成全屏表格 UI，**工资管理页只提供这两个功能入口**，
其余全部收到对应二级页；② 工资付款应当**直接把当月工资台账搬过去**，但 column 只保留总工资，
付款操作都在表格中完成。

- 页面结构：`/finance/salary` 变成纯入口页（两个板块卡片，本身**不发任何请求**），
  新增 `/finance/salary/ledger`（工资台账）与 `/finance/salary/payments`（工资付款）两个二级页；
  用真实路由而不是查询参数切 tab —— 两个表格都要占满整屏，地址也能直接收藏。
- 工资付款表 = 当月工资台账的付款视图：同一套筛选与按月导入，但**类目列全部收掉**，
  只留 总工资/已付/未付/状态/币种，外加付款日期与付款方式（整页统一设置）。
- 行内付款：`POST /hr/payroll-ledgers/:id/pay` 一次完成「生成工资应付 → 确认应付 → 建付款草稿 →
  核销过账」，操作员只需在行上填金额点一次；金额先按台账实发与已付余额校验（超付 422 且不产生
  任何单据），后续任何一步失败都会把本次草稿**软删除并审计**，不留孤儿单据。
- 行内冲销：`POST /hr/payroll-ledgers/:id/unpay` 把该台账下所有已过账付款逐张走既有 `reverse()`
  （每张各自刷新台账/应付状态、回冲现金流），原因必填。
- 不可付款的行仍然显示（当月台账全都在），只是把输入框换成原因：待确认 / 已过期 / 已付清。
- 工资付款页不再有「新建付款草稿」入口：草稿无法自行过账，只会堆积；接口保持可用。

### 第一轮（工资台账可编辑 + 生产工资自动汇总）

  1. **每月自动导入全部员工**：新增 `POST /hr/payroll-ledgers/import-month`（幂等，只补建缺失的草稿台账），

## Decisions

- **（第十五轮）说明性文案的删减口径是「说明句换成数据」，不是「整行删掉」**：界面上长期混着两类文字，
  一类是数据（有几条、多少钱、什么状态），一类是说明书（这个模块怎么运作、你该怎么用）。
  用户要删的是第二类；把两类一起删会把「待确认应收 3 笔 / 合计 120.00」也带走。
  因此独立说明段整段删，`panel-heading` 里的说明句换成计数，表单 label 里的解释性括注删掉，
  而 `type: "info"` 的确认文案压成纯数据（`确认应收 AR-001：120.0000 USD`）—— 不可逆动作前
  「看得见要动多少钱」是安全底线，不属于说明书。
- **（第十五轮）「确认应付」只保留一条路**：第十三轮已把确认改成「确认即记账」（金额从所选银行账户支出），
  而付款过账会**再写一笔支出流水** —— 两条路都走一遍就是同一个账户被同一笔应付扣两次。
  所以行内「登记付款」与付款子表下线，改成**勾选 + 批量确认**；付款的接口与数据全部保留
  （历史核销、采购侧通知、报表仍依赖），去掉的只是这一页上的入口。
  台账同时去掉「已付 / 未付」两列：它们来自付款核销，流程去掉后只会显示「未付 = 全额」，与事实相反。
- **（第十五轮）待接收清单按「未接收」过滤，但计数里点名**：判定要同时看
  `!payable_entry && status === "pending_finance"`（历史数据里有状态没推进但已有应付单的行）。
  行移出列表、总数不隐藏（`待接收 N 条 · 已接收 M 条`）—— 前几轮反复修过「东西不声不响地消失」。
- **（第十五轮）应收与应付必须对称**：先按用户字面只改了应付，追问后用户选择应收也改。
  两侧「确认即记账 + 还留着登记收付款」是同一个重复记账形状，只改一边等于把同一个坑留在另一半 ——
  凡是「同一笔钱的第二个入口」，两侧要一起下线。
- 老列**不改语义、只加新列**：`allowance_amount`（补贴）不复用成「房补」，`attendance_deduction`（考勤扣款）
  不拆成三种扣款再写回；新增四列的唯一代价是一次 `ALTER TABLE`，换来历史金额不被重新解释。
- 6 个可编辑类目之外的老类目必须**显示**（只读「其他增减」）：藏起来就会出现应发与可见列之和对不上。
- 车间工人的 `base_salary` 手工改成非零 → 422（生产工资就是基本工资，两个来源必然漂移）；
  但允许清零，给历史数据留一条清理路。
- 表格内只有 `draft` / `expired` 可改；已确认台账格子上写明「先回到草稿」，整条编辑仍在弹窗里填原因。
- 「每个月自动先导入全部员工」落地为**幂等导入 + 进页面自动触发**：浏览即写库是用户明确要的行为，
  重复访问同一月份零写入。该月不在职（任职区间与该月无交集）的员工不导入，但会计数回传。
- 薪资构成类目的后台增删改（2026-08-20 备忘第 7 条「灵活为上」）确认是**后期**能力，本次不做：
  固定 6 个类目 + 只读兜底格已能覆盖当前诉求。
- （第二轮）工资管理页**只做入口**、功能进二级页，且用真实路由而不是查询参数：两个表格都要占满整屏、
  地址可收藏，也就不需要「切 tab 保留筛选」这类补丁；入口页不发任何请求，进错页不会触发按月导入写库。
- （第二轮）工资付款**只保留总工资**：付款只关心「这个月该发多少、已经发了多少」，类目明细留在台账页，
  两页同行数同行来源（同一套筛选与导入），不会出现「付款页看到的人与台账页不一样」。
- （第二轮）付款的四步链路收成**一次行内调用**，但每一步仍复用既有服务、没有另写金额或状态判断；
  失败时软删除本次草稿 —— 付款单没有删除接口、只有过账后能冲销，孤儿草稿会一直挂在列表里。
- （第二轮）冲销按**台账**聚合（该台账下所有已过账付款逐张走既有 reverse），而不是让操作员去付款单列表里找，
  避免出现「台账已冲销一半」的状态。
- （第三轮）**应付对账必须含待确认草稿**：这是「先对账、再确认应付」的前提；应收侧本来就含草稿
  （`status: { not: "cancelled" }`），应付侧只算已确认属实现偏差，按应收口径对齐。
- （第三轮）**流转必须在列表行上可见可点**：摘要走列表接口而不是详情接口 —— 用户不点开详情就该知道
  自己卡在哪一步、下一步点哪里。
- （第三轮）**资金动账缺字典项时，报错优于静默丢弃**：规则是「每一笔过账的收付款都要在流水里有落点」，
  做不到就得让人看到（422 + 需要哪些项目 + 去哪补），而不是悄悄把账做丢。
- （第三轮）**不自动创建收支项目**：项目是管理员可维护的业务类目，程序自动往字典里塞会让字典失控；
  缺项时给可执行的报错。
- （第四轮）生产进度表的**列顺序是导出显示偏好，不是生产顺序**：偏好只走导出参数 + 本机记忆
  （localStorage，按订单号），不写回 `sequence_no`、不新增表；没提到的工序按原相对顺序排在后面，
  存过顺序不会让新增工序丢列；只有生产进度表认这个参数，其它导出收到就 400 而不是静默忽略。
- （第十一轮）**来源状态由后端推进，界面再用关联兜底**：`received` 让数据模型自证，
  `payable_entry` 关联让历史数据（升级前接收过、状态没改的行）也不再被重复提示接收。只做一半都会撒谎。
- （第十一轮）**「哪些应付属于这张对账」只能是服务端的一个定义**：范围含 `purchaseOrderId`，前端推不出来；
  服务端顺带返回 `reconciliation_no`，界面才能回答「它进了哪张单」。
- （第十一轮）**不隐藏、只转移**：已纳入对账单的草稿移出「待创建对账」，但同页点名（单号 + 对账单号 +
  能不能一键确认）。
- （第十一轮）**待创建对账逐条而不是分组**：分组唯一的好处（一次建一张供应商+月份的对账单）行内按钮
  已经在做，而分组让「这条条目在不在」无法回答 —— 粒度服从用户的问题。
- （第十一轮）**对账范围仍是「活的范围」**：之后同供应商同期间新接收的草稿也落在已建对账单的范围内
  （`flow` 每次实时算，故「确认 N 条应付」会重新出现）。这是既有语义，本次只是把它在界面上说清楚。
- （第十三轮）**余额是算出来的，不是存下来的**：`余额 = 期初 + 生效收入 − 生效支出 + 转入 − 转出`。
  存「当前余额」列意味着每次动账都要记得同步改它，漏一次就永久对不上；聚合永远与明细自洽。
  只有**期初余额**是列（`banks.opening_balance`，非空默认 0 —— 0 与「没录期初」必须可区分）。
- （第十三轮）**互转单独一张表，不写收支流水**：写成「A 支出 + B 收入」会让收支汇总表凭空多一笔收入
  与一笔支出。互转只进余额。因此收支明细表里**看不到互转行 —— 这是有意的口径，不是漏算**。
- （第十三轮）**只算落在本账户上的流水**：没指定 `bank_id` 的流水仍是收支事实（报表里有、汇总算），
  但不进任何账户余额。界面用 `bank_missing` 明说，而不是让那笔钱看起来凭空消失。
- （第十三轮）**同币种互转两边金额必须相等**：`−100 / +99` 不是转账，是凭空少 1 块钱；这种差额只能
  是汇兑损益或手续费，而这两个概念本系统还没有科目承载，所以宁可挡住也不静默接受。跨币种必须显式
  给到账数，汇率只做快照不做换算。
- （第十三轮）**余额不足只提示不拦截**：期初可能还没录、银行到账有时间差，硬拦会挡住真实业务；
  但财务必须看到（响应带 `source_balance_before/after` 与 `insufficient_balance`）。
- （第十三轮）**「确认」与「记账」同生共死**：银行/项目的校验放在事务**之前**。等事务提交完才发现
  银行非法，应收已经确认、流水却没写，账面上凭空少一笔钱 —— 比直接拒绝糟得多。
- （第十三轮）**确认入口有三条，三条都记账**：按对账单一键确认、逐条确认、按订单批量确认。
  只在其中一条上记账，用户点另一条时看到的仍然是「确认了但银行余额没动」。
  对账单维度写一条汇总流水（对账单本身就是一张凭证），逐条/批量维度每条一条（批量没有单张单据
  可挂，逐条才追得回去）。
- （第十三轮）**同一来源的流水金额累加，不覆盖也不跳过**：对账范围是活范围，确认一次后同期间新来的
  草稿还能再确认；「跳过」会让银行账停在第一次的数字上，「覆盖」会让两条入口交叉时总额凭空变少
  （先按对账确认 100、再逐条确认 50、回头再点对账确认 → 被改写成 50）。累加只会单调增长。
- （第十三轮）**收支项目建单时就落库**：表单里填过的东西不能在过账/确认之前丢掉。优先级是
  「过账/确认时选的 > 建单时存的 > 按业务来源自动归类」，人工选过就绝不静默替换。
- （第十三轮）**收支明细表加列而不是保持老表 6 列**：没有项目列，汇总表按项目分类的数字在明细里
  对不上号（用户第 5 条要的正是这个）。项目缺失留空单元格而不是横杠 —— 空单元格在 Excel 里能筛选
  能求和，横杠会被当成文本混进数值列。
- （第十三轮）**本期不做历史回填**（沿用用户口径「先不用管历史数据」）：升级前已有流水的 `bank_id`
  全为空，因此不进任何账户余额；老库的 `banks` 表本来就是空的，期初余额需要财务手工建账户 + 手填。
- （第十四轮）**工资付款的发放银行必填，而不是可选**：可选会重演第十三轮的缺口（一笔支出写进了流水却不属于
  任何账户），而这次没有任何「历史数据」可以当借口 —— 用户说的就是「发工资都是要用银行账户发放的」。
- （第十四轮）**银行校验放在编排的第一步**（`payLedger`）：四步链路走到一半才发现银行非法，会留下一张
  刚生成的工资应付要人工清理。
- （第十四轮）**原料出库两段式，不变式是「只有 `pending_outbound` 能被出库」**：生产提交时**不动库存**，
  真正扣料只发生在仓库确认那一步。草稿直接过账一律 422，错误信息指引「请先由生产确认提交」。
- （第十四轮）**「待出库通知」不另建表**：领料单/补料单本身就是通知，另建影子表只会让两张表状态漂移。
- （第十四轮）**提交与出库各校验一次库存**：提交时校验是为了让生产当场知道领不出来（而不是等仓库点确认时
  才失败，那时人已经离开）；出库时在事务内再校验，因为两次之间库存可能被别的单据改变。
- （第十四轮）**撤回提交 ≠ 冲销**：`pending_outbound → draft` 只需改状态（还没有库存事实），
  不写等额冲抵事实；已过账回退草稿才需要冲抵。两条路径共用一个 `reopen` 接口，都必须填原因。
- （第十四轮）**补料单与领料单同规则**：它同样是原料出库，只让领料单走仓库确认等于给仓库留了个后门。
- （第十四轮）**`submittedAt` 不复用 `updatedAt`**：后者会被任何一次写入（改备注、编辑、审计）改动，
  而通知要显示的是「什么时候交过来的」。
- （第十七轮）**凭证重新生成只对草稿开放，且是「删旧分录重建」而不是原地改**：已过账凭证是账务事实
  （要改只能红冲）；分录条数会随收支项目/资金科目变化，逐条 diff 会留下孤儿行。
  凭证头的日期与会计期间也一起跟着流水刷新 —— 只改分录不改期间，会得到一张期间错误的凭证。
- （第十七轮）**重新生成覆盖手工修改，所以审计必须记 before/after**：财务能在过账前手改整组分录，
  重算会把那些改动抹掉；没有前后对照，事后无法回答「我改的那笔去哪了」。
- （第十七轮）**银行存款的 `subject_key` 保持「银行存款」，账户用 `bank_id` + 名称快照两层**：
  科目名若写成「银行存款—农业银行5706」，按科目汇总时每个账户一行，「银行存款」总额就没有了；
  而只存 `bank_id` 又会在账户改名/停用后让凭证纸失去可读性。快照格式与收支流水的
  「结算方式」列统一（同一件事在两个页面同一个写法）。
- （第十七轮）**「未付/未收 = 草稿、已付/已收 = 已确认」是有意的口径**：确认即记账之后界面没有
  第二步付款，若把「已付」定义成「有付款单核销」，这个筛选项永远是空的。已冲销/已作废/已取消
  既不算未付也不算已付，只在「全部」里出现。
- （第十七轮）**确认页默认收窄到未付/未收，而不是删掉已付的条目**：用户第③条要的是「待办清单里
  不要再出现已经办完的事」，第⑤条又要「按已付未付筛选」—— 默认收窄满足前者，筛选器满足后者；
  同一个筛选器上带实时条数（`未付（3）/ 已付（5）`），点一下就能确认没丢数据。
- （第十七轮）**导出必须所见即所得，所以筛选在前端、导出只是把当前条件带给后端**：
  表格是前端分页的，若导出走后端全量，用户会拿到一份和屏幕对不上的文件；
  这也是为什么前后端各有一份同口径实现（`ledger-filter.ts` / `finance-ledger-filter.ts`），
  且两个文件顶部互相点名。
- （第十七轮）**台账导出不做合计行**：应收/应付是多币种同表，跨币种相加是一个没有意义的数；
  含两种以上币种时在表尾写一行说明，而不是给一个错的合计。
- （第十七轮）**设置了时间范围时，没有日期的行不算命中**：它们无法证明落在区间内，
  宁可少列几条也不要列错（导出件是要拿去对账的）。
- （第十七轮）**没有把「红冲后允许重新生成」一起放开**：那会破坏
  `vouchers_source_type_source_id_key` 的唯一性语义（同一流水两张凭证），
  已过账凭证的更正仍走「红冲 + 另建更正流水」这条路。
- （第十八轮）**搜索语义全站只留一份（`lib/fuzzy-search.ts`）**：池子各写一句 `includes` 时，
  单字查询看不出差别，「香港 迪礼」这种多词查询却会给出不同结果；用户在别的池子里学到的搜索行为
  必须在每个池子里都成立。
- （第十八轮）**「所有池子都要有搜索」写成反向守卫**（`lib/pool-search-guard.test.mjs`）：
  除了「清单里的池子必须有搜索框」，还要检查「任何把『池』写进界面文案的文件都必须在清单里」——
  否则新增池子时漏加搜索框只能等用户来发现。
- （第十八轮）**池子的空态要区分「没有数据」和「搜不到」**：后者点名关键词并给出总数。
  不区分的话，用户搜错一个字会以为整个池子空了（新建引导会把人带偏）。
- （第十八轮）**搜索字段要按用户脑子里的词来定**：物料类型存的是 `finished_product`，
  但人搜「成品」；物料的默认单位存的是单位 id，但人搜「米」——所以先把它们解析成界面上的说法再匹配。
- （第十八轮）**「新建物料」只留一份表单**（`components/bom/material-create-dialog.tsx`）：
  物料清单页与三处 BOM 入口共用，字段与校验不会在两个页面之间漂移。
- （第十八轮）**新物料必须先进页面的物料池，再回填 BOM 行**：BOM 行的物料下拉是按 options
  渲染名字的，只把 id 填进行里会让那一格变成空白。
- （第十八轮）**共享弹窗给两个 ActionDialog 不同的 `key`**：`ActionDialog` 是按字段名保留已填值的
  （`current[field.name] || field.defaultValue`），「新建物料」与「新建单位」都有 `name` 字段，
  不换实例会让单位的名称框带上物料名（实测拼成「伞骨打」）。
- （第十八轮）**单位建好后要吃掉 ActionDialog 那次 `onOpenChange(false)`**：
  `submit()` 成功后会再喊一次关闭回调，而我们为了回到物料表单已经切了页 ——
  当成用户关窗就会把刚建好的单位选中态与整份草稿清掉（用 `keepOpenRef` 标记程序切页）。
- （第十八轮）**采购单页补回「编辑BOM表」入口**：2026-09-14 拆枢纽页时 `openBom()` 失去了调用方，
  BOM 工作区在那一页彻底不可达；只给 `onCreateMaterial` 接线而不把入口补回来是没有意义的。
- （第十八轮）**表单里的下拉本轮不做成可搜索下拉**（用户明确选择只做池页面）：
  新建采购单/销售单时从供应商、客户、物料下拉选值仍要滚动；池子变大后这是下一个该做的。
- （第十九轮）**「本批总数量」单独一列，不塞进「送检」格**：塞成「40 / 100」看着省一列，
  但送检/合格/条件接收/不合格这四列是一组求和关系（合格+条件+不合格=送检），
  中间插一个复合值会破坏这一组的可比性。
- （第十九轮）**单位优先取采购单列表里的那个批次**：质检记录自带的 `purchaseReceipt` 只有数量没有单位名，
  而采购单列表里的批次带单位（页面本来就已经拉了这份数据），所以显示「100 米」而不是光秃秃的 100；
  拿不到单位时只显示数字，不编一个单位出来（单位错比没有单位更误导）。

  若财务习惯用这个页面查历史，需要适应切筛选；也可以把默认档记在 localStorage 里（本轮没做）。
- 第十八轮的**表单下拉仍不可搜索**（用户选择只做池页面）：新建采购单/销售单时从供应商、客户、
  物料下拉里选值仍要滚动。池子变大后应把这些下拉换成可输入过滤的 `SearchableSelect`
  （组件已存在，`type: "searchable-select"` 在 ActionDialog 里已支持）。
- 第十八轮的**员工目录没有并入统一语义**：它自己写的是 `employeeNo + name` 子串匹配，
  本轮没动是因为该文件正由另一个 agent 修改（身份证解析），避免同工作树互相踩。
- 第十八轮的**池子搜索是前端过滤**：池页面一次性把主数据拉全（无分页），搜索不发请求。
  几千条以上时需要后端搜索 + 分页，那时前端这套 `fuzzyMatch` 要改成「把关键字交给接口」。
- 第十八轮的**「新建物料」弹窗没有重复预检**：同名同规格同颜色的物料由后端 409 拒绝，
  前端只负责把原因显示在弹窗里（不关闭、不用重填）。
