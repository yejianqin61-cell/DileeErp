两个盲区的验证本身也踩了坑，都修了：

1. **正向财务的断言差点是恒真的**。第一版只断言「completed 且无 `AGENT_TOOL_FORBIDDEN`」—— 模型回一句「我查不了财务」也能通过。

2. **`model_steps` 从未被计数过**。它原来写成 `observability?.record({ step: ++modelSteps })`：`observability` 没接时可选链整体短路，

## 4. 顺带修的两处

- **检索词上限 100 → 200**。单号列是 `VarChar(100)`，超过 100 字符的检索词在库里不可能命中 —— 那是「查无结果」不是「参数非法」。
  原来的 100 上限让模型白占一次失败预算去读懂 400。改成 200 后，100~200 之间的检索词照常查询、由既有空结果说明回答。

## 1. 那个「执行失败」的需求：T-0027

需求是「结算方式加入中国银行-人民币账户、备用金（招商银行账户）」。表面是执行失败，
查下来是**三层口径同时说错话**：

| 环节 | 系统说的 | 实际发生的 |
|---|---|---|
| run 收尾 | `completed`（因为收到 SIGTERM 后退出码 0） | 跑到 43 分钟被软截止，还在 `verifying` 阶段 |
| 工作区收尾 | 「已合入主干 29dcb9ad」 | `git merge` 只回了 `Already up to date`，主干一个字节没变 |
| 工单状态 | `gated`（有产出待部署） | 产出只存在一个 stash 里，主分支什么都没有 |

也就是说：**用户被告诉「已完成、待部署」，而实际上一行代码都没进主干**。
比「执行失败」严重 —— 失败会有人去看，这种是没人会去看的静默错误。

三处都改了：切断一律 `truncated`（不再是 completed）；零提交不调 merge、`merged` 只在 HEAD
真前进时为真；状态映射改成「completed 且主干真的有改动」才进 `gated`。

## 2. 看门狗

- `watchdog.ts`：纯判定 `alive/suspect/ceiling`，零副作用、不读时钟。三条判据
  （事件静止 ≥10 分钟、进程 CPU <3%、无子进程 >5%）**缺一不可**，连续 2 个采样点才报。
- `run-sampler.ts`：读 `/proc` 算进程树 CPU，复用 `run-janitor` 的 `DILEE_RUN_ID` 标记发现进程。
- `harness-runner.ts`：`timeoutMs` 从「45 分钟超时」改成「6 小时绝对资源上限」+ 60 秒收口；
  新增 `abortSignal`（用户截断）与看门狗回调。
- `coordinator.ts` + `dispatcher.ts`：疑似死锁 → 群里申请截断（**同一单只问一次**，
  记账落在工单上，重启后不复读）→ 用户回「继续」重置采样基线 / 回「截断」走 `abort`，
  与到顶同一套两段式收口。
- 机器人**永远不自己截断**。唯一会杀的两条路：6 小时上限、用户明确说截断。

## 3. 真机探针救了这条功能一次

看门狗的全部输入是 `/proc` 的 CPU 读数。在 2 vCPU 服务器上实测：

| 场景 | 读数 |
|---|---|
| 父进程烧 CPU | total=99.8% |
| 父闲子忙（真 fork） | total=99.6%，`busiestChild=99.6%`，2 个进程 |
| 父子都闲 | total 在 **1.6%** 与 0.0% 之间抖动 |

原设计地板是 1%。**一个完全空转的 node 就有 1.6%** —— 死锁现场会被判成「还在干活」，
看门狗永远不报，而且安静得让人以为一切正常。地板改成 3%。

同一轮还修掉一个接线 bug：采样读不到时我原先喂 `-1` 当「未知」，而判据是 `cpuPercent < 3`，
`-1` 直接满足「没在干活」，凑上事件静止就是一次误报。改成「读不到就跳过这一轮判定」。
