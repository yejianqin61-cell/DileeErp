## 2. 当时的判据为什么错

`deploy.ts` push 阶段的门禁本身是对的（不 force push、不覆盖别人的提交），错在**失败后
没有自救动作**：

```
fetch → rev-parse origin/main → merge-base --is-ancestor → （失败就抛错）
```

缺少的正是一步 `git pull`/`rebase`。这和「Agent 自主部署」直接冲突：一个正常人会立刻做的
动作，机器人不会。

## 3. 修法：push 阶段自己同步远端

改动 `tools/ticket-agent/src/deploy.ts`（递交 `57ce46b`）：

| 本地状态 | 动作 |
|---|---|
| 只落后（HEAD 是 `origin/main` 祖先） | `git merge --ff-only origin/main` |
| 有本地提交、与远端分叉 | `git rebase origin/main`（把本地提交重放到远端之上） |
| rebase 冲突 | `git rebase --abort` 原子回退，报「需人工解决后再部署」并中止 |

要点：

- **不 force push、不改远端历史**这条底线不变，仍是「远端必须是 HEAD 祖先」才推。
- 同步会换 sha（rebase 重写提交），所以 `state.release` 跟着新 HEAD 更新；后续
  `git archive HEAD` 打包、切换、核验都对着同一份提交，不会出现「核验比对的提交已不存在」。
- 中止时把 `git` 的 stderr 尾部带进失败信息，冲突文件一眼可见。

单测（`tools/ticket-agent/test/deploy.test.ts`）补三条：自动 rebase 后继续、只落后走快进、
同步冲突回退且不构建不切换。`npm test` 222 条全过（本地 221 过 + 1 条 Linux-only 跳过）。

## 6. 教训

1. **失败信息要说「下一步动作」，但动作得机器人自己做。** 「先同步仓库再部署」对人有效、
   对机器无效；凡是人能一步解决的，就不该抛回群里。
2. **只读门禁 + 自动修复，比只读门禁 + 人工兜底更接近自治。** 同步动作天然可原子回退
   （rebase 失败即 abort），风险低于把线上停在那里等人。
3. **多端写同一分支必然分叉。** 本地机器推文档提交、部署仓推代码提交，两边都是 main 的
   合法写入者；只要发布流程要求「远端必须是祖先」，就必须自带同步。
