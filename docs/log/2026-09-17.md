## Decisions

- **科目表是全站财务口径的唯一来源**，`accounting-subject-catalog.ts` 是它在本仓库的唯一留存处；
  迁移 SQL、`seed.ts`、并入映射、自动归类候选链全部从它生成或与它比对（由 3 组守卫测试钉住）。
- **迁移只做加法**：唯一的 `DROP` 是那张用完即弃的临时映射表；业务表与列一律**改名**而不是重建
  （`DROP COLUMN` 会连数据一起丢）。
- **不做银行账户 → 银行存款明细科目的映射**：科目表里有 `100201`–`100205` 五个银行存款明细科目，
  但 `banks` 没有科目字段，所以凭证的资金分录仍是「银行存款—农业银行5706」这种名字快照，
  不是真正的科目引用。要做需要给 `banks` 加 `subject_id` 并迁移存量账户，本期**明确不做**。
- **本期只接「收支」两张报表的统计口径**，利润表/资产负债表虽有科目表支撑，但不在这句需求里。
- **不上「未分类」以外的兜底分类**：迁移只在「对照表覆盖不到的自定义旧项目」场景下用「未分类」，
  且它是提示财务来改的信号，不是长期分类。

### 第二轮（采购列序、工资批量付款与按月导出、外汇一览表）

开工前先问了 6 个问题（用户逐条选定后才动手）：明细行粒度 = 一次成品出库 + 一张客户汇总 sheet；
期间按**收款到账日期**；定金/货款靠**新增的「款项性质」**区分；批量付款**每人一张付款单**；
跟单与银行手续费**留空 + 表尾写清**；款项性质**加在收支流水上**并给收入流水加一个可选订单号。

**第四问的前提被推翻**：提问时我以为系统里还有「客户付款单」可以加字段，开工后发现它已于
2026-09-16 从界面撤掉（改为「确认即记账」）。已回头向用户说明真实情况并重新征询，而不是照着一个
不存在的前提动手 —— 最终「款项性质 + 订单号」加在 `cash_flow_entries` 上。

做了什么：

- **采购对账明细表**：产品名称移到采购单号之前（用户要求的唯一一处刻意偏离 R1）。金额/含税金额仍在
  最后两列，合计列下标不变；单测同时钉住列序与合计列下标。
- **工资付款批量付款**：`POST /hr/payroll-ledgers/pay-batch`，复用既有 `payLedger` 逐人串行执行、
  逐条 catch 隔离；发放银行在动手之前校验一次；前端勾选/全选/清除，失败行保留勾选并点名原因。
- **工资付款按月导出**：`GET /hr/payroll-ledgers/payment-sheet.xlsx`，18 列，含用户要的**「是否付款」**
  （无需付款 / 已付清 / 部分付款 / 未付款）。三个金额列是 Excel 数值类型；**单币种才给合计**，
  混币种不给并在表尾说明（绝不跨币种相加）。取数不按状态过滤 —— 导出必须与页面同批。
- **外汇一览表**：新的报表 key，导出是**一个工作簿两张表**（外汇一览 + 客户汇总）。
  为此把 `tableFor()` 改成返回 `ReportTable[]`、`sendWorkbook()` 接受数组，页面用 `extra_sheets`
  明说「导出文件还包含：客户汇总（N 行）」。归属规则、四处刻意偏离、不做的事都写进了设计文档。
- **收支流水加两列**：`payment_nature`（定金/货款/尾款/其他）与 `order_no`（可空）。
  确认应收的三条入口（逐条 / 勾选批量 / 按对账单一键）都在弹窗里问款项性质（默认货款），
  由 `recordConfirmation` 落到流水上；手工录定金则在流水表单里填客户名 + 订单号 + 性质。
  `requirePaymentNature` 是全站唯一实现（三条确认入口 + 流水新建/更正共五处都走它）。
  更正时 `undefined = 不改`、空串 = 清空 —— 不区分就会出现「只改金额把性质抹掉」或「永远清不掉」。

过程中发现并修掉的三个真缺陷：

1. `receivable_source` 流水被挂到「订单最早那次出库」上：一张订单多次出库时每笔货款都堆到第一次
   出货，那一行欠尾款变成负数、后面几行虚高。已改为「自己指向的那次出库」，只有订单级收款
   （出货前收到的定金）才退化成「最早那次」。
2. 既没有订单号也没有来源的手工收入流水被**静默丢掉**：候选收款按「订单/来源」收窄查询捞不到它们，
   于是连表尾都进不去 —— 表里的汇入总金额会小于银行流水，财务看不出少在哪。已把「期间内的全部
   收入流水」并回候选集合。
3. `cash-flow-page` 的单测断言歧义：新增两列后有多个 `-`，原来的 `getByText("-")` 匹配到多个元素。
   改为按行、按列计数断言（顺带把款项性质与订单号也纳入了断言）。

做了什么：

- **保存 / 下单统一收束**：新建走 `POST /purchase-orders/split`，收束一张已存在的单走

  为什么不「新建 N 张再把原单取消」：草稿从没发给供应商，重新组织它的内容不是一次「取消」业务，
  标成已取消会让列表凭空多一条作废记录、白烧一个采购单号。
- **编辑范围放开**：`assertEditable` 只在「有到货事实」或状态不在 `draft|ordered` 时拒绝。

- **BOM 外新增原因**：见下面的缺陷 2。
- **换物料清 `bom_item_id`**：见下面的缺陷 3。
- **服务层抽件**：`collectGroups`（结构校验 → 参照物解析 → 下单前校验，新建与收束共用同一套）、

过程中发现并修掉的三个真缺陷：

1. **「勾选框太宽」是 CSS 权重泄漏，不是审美问题。** 采购工作区的 Sheet 带着 `material-issue-sheet`

做了什么（口径层面值得记的）：

- **核算表**：老表 19 列（两行合并表头）拉平成 20 列单行表头，多出的那列是**「分摊单位」**。
  老表**没有单位列**，而「55 元/打」与「55 元/支」差 12 倍 —— 照抄老表等于把单位混算的风险抄进来。
  费率**不四舍五入**（22 万÷3700 打除不尽），金额是权威值、单价由金额反推，这样
  `单价 × 数量 = 金额` 在任何小数位上都成立。三段费用的「占比」三列用**同一条规则**：
  金额格为空则占比格为空（老表这里是 `#DIV/0!`）；只给一列加闸更坑，会得到
  「原材料总价空、原材料占比 0.00%」这种读起来像「这项成本是零」的假话。
- **计件人工 = 0 与「收入留空」是两件事**：没有计件日报 = 这个月没录，Σ 空集就是 0（老表这一格也是 0.00）；
  外币订单缺本币金额是**真的缺数据**，写 0 会被读成「这单收入是 0」。两处取舍故意相反，注释写明了。
- **管理费单独一张表**（`overhead_allocations`，`period` 唯一），不汇总「管理费用类科目的流水」：
  财务的口径是先有总额再有费率，而流水常常滞后（月底费用下月才报销），
  直接汇总会让本月费率凭空偏低且表上看不出来。软删过的同期间记录**恢复它**而不是新建
  （否则「删了再录」直接撞唯一索引，用户看到的是一句数据库错误）。
- **凭证「不能改」的确切含义被查清了**：服务端 `PATCH` 一直支持整组分录，是**页面**只能改已有两行的
  科目与金额（还是手打文本），一借三贷/两借一贷表达不出来。所以这一条不是加功能而是补 UI：
  分录编辑器（增删行、改方向、科目下拉、BigInt 分实时算借贷合计、不平不让存）+ 模板。
  模板金额留空是刻意的：系统里采购单价是含税价，`含税 ÷ (1+税率)` 在取得普票（不抵扣）或
  优惠税率时会被自动填错，而那种错在凭证上看不出来。
- **模板的科目用「名称候选」解析**：财务的科目表里没有「应交个人所得税」也没有
  「应交税费——应交增值税（进项税额）」，所以每行给一串候选名，全落空就返回 `subject_id: null` +
  建议名让财务自己选。没有为这两条「顺手把科目表补全」—— 科目表是照抄财务那张 `科目表(2).xls` 的，
  补一条就是改口径（已列入待确认）。
- **顺带修掉一个真缺陷**：`update()` 对没传 `bank_id` 的分录按**行号**沿用原分录的银行账户，
  而 `null ?? 原值` 让「显式说不挂账户」也退回按行号沿用 —— 在资金行前插一行之后，
  那张卡会挂到新插入的业务行上，**银行存款明细账从此对不上银行对账单且凭证上看不出来**。
  改成区分 `undefined`（没传 → 沿用）与 `null`（显式不挂），并在写入前校验账户确实存在。

三条修复里最值得记的是第 3 条 —— **根因不是规则不够，而是规则没生效**：

- `globals.css` 在 2026-09-16 就为财务表写好了「紧凑 + 允许换行」四条规则（当年用真实 Chromium
  在 1366/1440/1600/1920 四个视口实测过溢出像素从 227/153/108/34 降到 0），
  但它们的选择器是 `.finance-page .data-table`，而 `DataTable` 渲染出来的 `<table>` 带的是
  **`ui-table`**（`components/ui/table.tsx`）—— `.data-table` 这个类在财务页一个都不存在。
  于是那四条规则对财务的每一张表**一条都没生效**，单元格一直是 `.ui-table-cell` 的
  `padding: 12px` + `white-space: nowrap`，最小宽度等于整段文本宽度，列多的表必然溢出。
  用户第 3 条说的横向滚动条，就是这么来的（不是「列太多」）。修法是把 `.ui-table*` 一并写进那四条，
  并补 `overflow-wrap: anywhere` 让单号这类长串也能断行；`finance-table-width.test.mjs` 补了守卫，
  钉住「规则必须同时命中 `.ui-table`」与「基础表格类从来不是 `.data-table`」。
- 第 6 条与第 3 条方向相反（一个要换行收窄、一个要固定列宽 + 省略号），
  所以做了按列的元数据 `meta: { width, ellipsis }`：**只要有一列给了宽度就切 `table-layout: fixed`**，
  否则「宽度」只是建议值、长摘要照样把表顶出容器。省略号的样式权重必须压过
  `white-space: normal`（`(0,2,1)`），写成 `.cell-ellipsis`（`(0,1,0)`）会**静默失效** ——
  页面看起来只是「没省略」，所以叠到 `(0,4,1)` 且不依赖样式表先后顺序。
- 第 7 条在应付侧与应收侧不是同一个缺口：应付侧的搜索框一直有，只是**没接上「已创建对账单」那张表**
  （渲染的是原始数组，打字没有任何反应）；应收侧更差 —— 搜索框只画在「成品出库条目」那一段里，
  而它一直是「确认应收」页的实际筛选器（`matchedSources` 就吃它），切过去只能看到一个来路不明的
  关键字在生效，「应收对账」页连筛选器都没有。现在搜索框提到页签外面、四张表全部接上。

遗留（都已写进设计文档 §5）：

- **没有真实 PostgreSQL**：`overhead_allocations` 的迁移、`period` 唯一键与「软删后恢复」的实际行为
  只在替身上验证过；`laborByOrder` 的 `groupBy` 同样只验证了 `where`/`_sum` 形状。
- **计件日报的数量口径要财务过目**：自动分摊数量按工序单位过滤后跨工序相加，同一件货经过三道工序会
  重复计件 —— 这是有意留成「参考值 + 人工覆盖」的，但第一个月的实数出来后应当和财务核对一次。
- **科目表缺两个科目**（应交个人所得税、应交税费——应交增值税（进项税额））：要不要补进科目表需财务确认。
- 财务侧的迁移与采购侧的迁移要一起在真库上跑一次（两边都在本工作区、都有未提交的迁移）。
- `SearchableSelect` 与 Radix Select 的焦点交接：测试里「先选一个 Radix 下拉、紧接着打开会计科目搜索框」
  需要显式等一个宏任务（Radix 关闭时**延迟**把焦点还给它的 trigger，会顺手把搜索框的焦点抢走并触发
  blur 关闭）。真实用户两次点击之间隔几百毫秒，碰不到；只按测试时序处理并在用例里写明了原因。
