# 2026-09-27

## 采购计划与按供应商收束下单（一轮 19 个提交）

设计依据：[`purchase-plan-and-supplier-collapse-2026-09-27.md`](../design/purchase-plan-and-supplier-collapse-2026-09-27.md)
任务批次：[`docs/task/0927-purchase-plan/`](../task/0927-purchase-plan/README.md)

### 1. 用户原话与本轮结论

> 「现在，生产模块里面的 BOM 表里面不用填写供应商。然后采购模块那边多一个采购计划栏目。
> 采购计划就承接的是原来的采购单草稿。在采购计划里面，每个销售单对应一份的 BOM 对应一份的采购计划。
> 还要加上供应商，供应商地址，联系人这些column。然后根据供应商收束下单，下单到采购单模块。
> 也就是说，采购单模块就是所有已经经过供应商收束下单的采购单了。
> 注意，表单要保证一次性展示所有column。可以限制每个column的宽度，如果超出就省略。
> 鼠标hover的时候再展示全部文本。」

开工前按用户要求**逐条 grill 了 15 个问题**（每题给推荐答案、等确认），全部答案写进设计文档 §2。
最要紧的一条是**粒度**：

| | 采购单 | 采购计划 |
| --- | --- | --- |
| 粒度 | 一个供应商 × 一个币种 | 一个销售单 / 一份 BOM |
| 头部语义 | 供应商、币种、金额都有单一含义 | 这三样在下单前没有单一含义 |
| 寿命 | 对外的凭证（发出去就冻结） | 内部的工作台（一直改到买完） |

原来的"草稿"是**多供应商工作台硬塞进单供应商凭证**的产物：保存草稿要按供应商拆成 N 行，
拆完头部三格才勉强有意义。所以这次新建两张表（`purchase_plans` / `purchase_plan_items`），
并**有意反转** 2026-08-20「什么狗屁采购计划？只有采购单」与 2026-09-17 设计文档第 6 节的决定 ——
反转理由写在新设计文档 §1，免得下一个人以为是漏读了文档。

### 2. 一件一件看，这一轮实际改了什么

- **数据层**：两张新表 + 两条迁移（建表 / 把历史草稿按 `bom_id` 归并成计划）。
  「一个 BOM 一份计划」用**部分唯一索引**（`WHERE deleted_at IS NULL`）而不是 `@unique` ——
  后者会让"软删一份计划之后再建一份"撞约束，而那正是口径允许的操作。
- **API**：新模块 `purchase-plans`（列表 / 候选 / 新建 / 详情 / 保存 / 软删 / 收束下单）。
  新建就**自动带出该 BOM 全部明细行**并预填 BOM 上标过的供应商。采购单侧：列表只返回已下单及之后、
  `PATCH :id` 只收打印信息、新增「退回采购计划」并删掉 `revert-draft` 与 `cancel`。
- **Web**：新页面 `/procurement/plans`（列表 + 13 列明细 Sheet + 按供应商收束预览），
  采购单页瘦身成凭证层，BOM 工作区的供应商列在生产侧隐藏，
  「固定列宽 + 省略 + 悬停看全文」那套规则从财务页提为**通用**规则。

### 3. 实现期间发现、而且**不修就是坏功能**的四个坑

这些都是写代码时撞出来的，不在最初的口径里；每一条都补进了设计文档。

1. **BOM 存一次会换掉全部行 ID，计划会再也保存不了。**
   `BomsService.replaceItems` 是"软删全部旧行 + 整批建新行"，而计划是长期存在的（不像草稿是一次性的）。
   按原样校验，BOM 改过一次之后这份计划里所有行都带着"当前 BOM 里不存在"的 ID →
   `PURCHASE_BOM_ITEM_MISMATCH` → **计划整体存不下去**。改成**按物料找回**当前 BOM 的对应行，
   找不回才当 BOM 外的行处理（那一步才要求填原因）。与 `bomItemOrderStatus` 既有的"换行 ID 就按物料摊回"同一口径。
2. **口径 7 与"预计到货"打架。** 已下单行的内容锁死之后，如果把 `expected_date` 也锁上，
   系统里就**再没有任何地方**能改这个日期（采购单页的明细编辑已经关掉了），
   而"供应商说这周到不了、下周到"是每天都发生的事。结论：已下单行**允许改预计到货**，
   并**同步写进那张采购明细**（不同步就是同一行两个日期，而采购员拿去跟供应商对的是采购单上那一份）。
3. **`PURCHASE_ORDER_NOT_REVERTIBLE` 其实早就有了。** 它藏在要删掉的 `revertToDraft()` 里
   （守的是同一条不变式），一行到底的单行方法，按同族的 `PURCHASE_ARRIVAL_NOT_REVERTIBLE` 找会漏掉。
   所以退回计划是**把这个码搬过来**，不是新起一个。
4. **`expected_date` 与 `remark` 同时是"打印字段"。** 把 `PATCH :id` 改成"只收打印信息"时，
   很容易顺手把这两个键列进"明细键黑名单"—— 那样打印路径就被打死了（交货日期与备注填不进去）。
   单测里专门留了一条回归。

### 4. 顺手修掉的两个既有缺陷

- **`sales-order-spec-migration` 守卫的懒正则**：`migrationSql()` 把全部迁移拼成一份大字符串，
  而 `CREATE TABLE "sales_order_spec_details"[\s\S]*?"quantity" DECIMAL(18,4) NOT NULL`
  会一路跨到**后面任意一张表**。本轮新增的 `purchase_plan_items` 同样有这一列，
  于是那条断言红了而它盯的表完全正常。改成只看这张表自己的建表块。
  这个坑对后来人有用：**以后任何一条新迁移只要在它后面加了同类型的列，都会踩到同一个假失败**。
- **鉴权矩阵的控制器计数过期**：`authorization-matrix-contract.test.cjs` 断言覆盖 39 个控制器文件，
  而 `CONTROLLER_FILES` 在 2026-09-26 收付款单存档那轮已经加到 40 —— 数字没跟着改，
  于是它在真实库上**一直是红的**（该文件需要 `TEST_DATABASE_URL`，本地跑不到，所以没人看见）。
  本轮加到 41 并补了一句 `covered.size === CONTROLLER_FILES.length`，以后漏登记会直接报红。

### 5. 这一轮把"约定守卫"撞红了 6 次，每次都是它们在干活

页面一改，源码级 lint 立刻报红：`refresh-policy`（采购单页瘦身时漏掉焦点刷新）、
`page-data-alignment`（采购单页只剩一个接口、不再是位置型解构；四条主数据加载搬到计划页）、
`finance-table-width`（那三条 CSS 规则提为通用）、`audit-columns-coverage`（新页面要么接两列要么进白名单）、
`testid-pages`（新页面必须登记）。**这是这套守卫的价值证明**：它们盯住的东西类型检查与组件测试都发现不了。

其中两处守卫自己也盯错了形式（不是语义），一并修正并把理由写进注释：
绑定表按**前缀**比（计划页第一个请求带查询串）；"响应有没有写进状态"的正则允许
`setRows((plans.data ?? []).map(...))` 这种形态。

### 7. 部署注意（**先迁移，再切代码**）

- 两条迁移：`20260928090000_purchase_plan`、`20260928100000_purchase_plan_backfill_drafts`。
  **后者搬的是真实数据**（把历史草稿归并成计划），本机没有库、**从未执行过**。
  部署前请：① `pg_dump` 备份；② 影子库干跑；③ 核对 `purchase_plans` 行数 = 有明细的草稿 BOM 数、
  `purchase_plan_items` 行数 = 被搬草稿的未删明细数；④ 确认 `status='draft'` 且未删的采购单为 0。
- **部分唯一索引会让 `migrate diff` 的基线漂移小幅增加**（与 `boms` / `raw_material_inbound_notices`
  那三条同源：Prisma 不认识部分索引）。基线原本是 **293 行**，本轮之后请把新的行数与 md5 记在这里。
  判定标准是"新增漂移只来自这一条 partial unique index"，不是"漂移必须是 0"。
- 反过来（先切代码后迁移）会直接 500：计划页/计划接口的表不存在。

### 8. 明确没做完

- 13 列的固定宽度**没有在真实浏览器里量过像素**（jsdom 不排版）："1366/1440/1920 无横向滚动条"
  只能部署后目测。**"测试全绿"不能当 CSS 生效的证据。**
- 「退回采购计划」的并发行为（两个人同时退同一张单）只靠事务与行锁推断，没有压测。
- 计划**不做 Excel 导出**（用户没提；要加是纯增量）。
- 没有"不建计划直接下单"的旁路：只要存在一条不经过计划的采购单，计划的计算就不再权威。
- `purchase_plan_items.supplier_snapshot` 与 BOM 行上的供应商快照是两份，**暂不合并** ——
  一份是 BOM 的长期知识、一份是这批的采购事实，合并会把两个生命周期绑死。
