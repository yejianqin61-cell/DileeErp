## 2. 连锁反应

一次门禁失败 = 一次部署失败 = 工单留在 `gated`。而部署是「一次带上 HEAD 上全部改动」的，
所以：

- T-0028（跨仓调拨）自己没问题，但它的页面没登记 → 门禁红 → 卡在 `gated`
- 11-23 09:30 第一次失败（T-0027 残留导致 Web 有 1 条红）
- 11-24 03:54 自动部署失败（T-0028 页面未登记）
- 11-24 04:34 用户手动「部署」又一次失败（同上）
- 期间所有新工单都被堵在后面

## 3. 根因：Agent 不知道这条守卫存在（结构性，不是马虎）

工单 Agent 的 prompt 里写着：

> 「只跑**与本次改动相关**的测试」「**禁止**跑全量命令，它们要十几分钟会把 run 拖到超时」

这条约束对 2 核机器是必要的。但 `testid-pages` 这类守卫检查的是**整个仓库的一致性**，
不在「相关测试」范围内 —— 新增页面的 Agent 根本无从知道要跑它。

T-0027 更典型：它的页面写的是 `<SettlementAccountWorkspace testId="page-finance-settlements" />`，
**写法完全正确**（正是守卫认可的透传形式），只差清单里那一行。如果合入主干，会立刻再红一次。
所以这次是在合并前先补掉，而不是等它上线后再发现。

## 4. 改了什么（三层，从止血到治本）

1. **止血**：补登记 `warehouse/transfers/page.tsx`（T-0028）与

2. **治本（给 Agent 说明）**：prompt 增加「全仓守卫：不跑全量测试也必须过」一节，
   按「你动了什么」对号入座：新增 `app/**/page.tsx` → 跑 `testid-pages.test.ts`；
   动接口/权限/导航 → `testid-contract.test.tsx`；动 prisma → 迁移守卫。
   并点明这类守卫的共同特征：**只在你「新增」了某个东西时才失败，而失败原因通常不在你改动的那一行。**
3. **治本（让报错说人话）**：`deploy.ts` 增加 `pickGateFailures`，门禁失败时从几千行输出里
   挑出 `FAIL` / `not ok` / `error TS` 行放到报错最前面。此前群里只看到几百行 ✓ 加一句
   `Test Files 1 failed`，三次失败都像同一个说不清的怪问题 —— 失败信息必须指向那一行。
