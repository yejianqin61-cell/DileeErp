用什么口径评、边界在哪

  • 端到端可跑（不只在库里落一行）
  • 异常有出口（更正 / 回退 / 冲销）
  • 有门禁与口径
  • 有交付物（打印 / 导出）
  • 有测试守卫

联动度：四条判据

  • 覆盖多少下游域
  • 载体强度（硬外键 > 文本冗余）
  • 方向（单向 / 双向 / 回写）
  • 一致性有没有守卫

只评销售域及其直接联动。返单与总结、订单工作台只作为联动证据，不单独评分。不含 UI 视觉与性能。

和别的模块联动有多深

方向图：销售单是起点，三支下游各自一条链；实线框＝有硬外键，虚线框＝只带 order_no。所有下游都另带一份订单号，一致性靠改号级联维持。

销售单 →建单 BOM 表 →收束下单 采购计划 →下单 采购单 →登记到货 到货 / QC →质检入库 原料入库 →挂账 应付台账 采购链
生产链 生产单 →领料 领料单 →日报 工序 / 员工日报 →计件 计件工资
钱链 出库通知 →发货 成品出库 →过账计价 应收来源 →收款核销 收款单 →对账 应收对账单

硬外键：不会指向不存在的单（11 张跨模块表） · 只带 order_no：文本冗余，查询快但不自证（38 张表）

要点：应付不在这条因果链上 —— 应付由采购驱动，订单号只是共享维度；销售侧看不到应付，这是边界不是缺陷。

联动的结构性问题是什么

问题 1：一硬一软两套引用，软的那套只靠一条路径保证一致

11 张跨模块表有硬外键；另 38 张只靠文本 order_no。文本冗余换来查询速度，但一致性只由改号级联这一条路径维持（本轮才补齐）。

后果很具体：任何一次人工 SQL 改名都会留下脏引用，而脏引用只表现为「查询少数据」，不报错 —— 最后在财务对账差额里才暴露。

问题 2：单向推送 + 锁死，销售单回答不了「这单走到哪了」

销售单一经下游引用，核心字段（数量 / 单价 / 币种 / 金额）就改不动，必须先回退 BOM、采购、生产（错误码 SALES_ORDER_CORE_FIELDS_LOCKED）。

下游也不回写销售单：销售单只有草稿 / 已确认 / 已关闭三态，发货与收款进度都是派生视图（工作台、成品视图）。这是设计取态，不是 bug，但它决定了销售要跨页看进度。

问题 3：钱的口径是全链最紧的一环，同时刻意留了尾差

出库→应收有三档优先级：应收金额 ÷ 订单数量 › 结算币价 › 销售单价；整单出库时直接取应收金额本身，避免 4 位小数折算误差。

分批出库时每单按比例折算，逐单相乘会有尾差；代码把它写进应收备注（finished-goods-settlement.ts:61-67）：逐单尾差 ≤ 0.0001，合计以销售单应收为准。财务看到不为零的小尾差时要按这条口径读，不要当错账。

建议下一步做什么

  1. 给订单号定规则（前缀 + 日期 + 流水），或至少加格式与重复的软校验。成本小、收益直接 —— 现在能改号，但「能改」不该是主要防线。
  2. 把「这单走到哪了」嵌进销售单详情：工作台的汇总接口已经存在，缺的只是把它嵌到销售单页面。销售不必再跳两个页面。
  3. 往商务前段走之前，先答两个问题：报价是否要版本化？信用额度是硬门禁还是提示？这两个决定决定数据模型 —— 先别写表。
